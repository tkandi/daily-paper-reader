Abstract
Emerging dataflow accelerators offer exceptional energy effi-
ciency and throughput for machine learning workloads, yet
remain largely opaque to developers for performance analy-
sis. Unlike CPUs and GPUs, where instrumentation frame-
works enable fine-grained introspection, dataflow hardware
exposes little information. This lack of transparency limits
the ability of compiler engineers, system designers, and ap-
plication developers to analyze, tune, or debug accelerator
behavior.
In this paper, we introduce DFIT (DataFlow Accelerator
Instrumentation Tool), an instrumentation framework de-
signed specifically for dataflow architectures. DFIT directly
instruments operations, regions, and compiler transforma-
tions at the graph IR and backend-lowering stages using
semantic program representation. DFIT captures high-level,
semantically meaningful data that reflect the true dataflow
of computation. These data can be exported for visualization
and analysis. Our approach demonstrates how instrumen-
tation can be generalized beyond traditional hardware to
support heterogeneous architectures, providing portability
without modifying tool logic.
By opening the black box of dataflow execution, DFIT
establishes a foundation for new classes of performance anal-
ysis tools for AI accelerators. It provides a practical path to-
ward reproducible, architecture-aware introspection across
heterogeneous systems, bridging the long-standing visibility
gap between compiler design, runtime scheduling, and hard-
ware realization. Evaluation across Cerebras, SambaNova,
and TPU shows practical overhead of 3.53%–13.62% across
instrumentation modes with robust cross-platform portabil-
ity.

Introduction
Emerging machine learning accelerators, including TPUs [18,
19], Cerebras Wafer Scale Engine [27], SambaNova [9], and
other spatial dataflow architectures [6, 25, 35], achieve excep-
tional throughput by mapping tensor computations directly
onto systolic arrays. Their execution model exploits parallel
tensor pipelines, deterministic data movement, operator fu-
sion, and backend-specific scheduling strategies to deliver
substantial speedups for modern AI and scientific workloads.
However, despite this performance advantage, these systems
remain largely opaque to developers and compiler engineers.
The only visibility typically provided comes through coarse
aggregate metrics such as device utilization, kernel latency,
or global memory throughput [7, 8, 47], which offer little in-
sight into tensor movement, partition boundaries, or transfor-
mation effects during execution. As modern workloads grow
more irregular, this absence of fine-grained introspection se-
verely limits the ability to diagnose performance bottlenecks,
verify correctness, or study microarchitectural behavior. As
a result, the demand for transparent, low-overhead, semanti-
cally aligned instrumentation for dataflow accelerators has
never been more pressing.
While dynamic instrumentation has a long history on
CPUs and GPUs, existing approaches do not translate cleanly
to MLIR-based [24] machine-learning compiler stacks [3] or
to systolic-array accelerators. Frameworks such as Pin [32],
DynamoRIO [4], and Valgrind [36] rely on sequential in-
struction streams, register-level semantics, and conventional
control-flow graphs. GPU-oriented tools such as NVBit [53],
CUPTI [37], and SASSI [15, 51] assume SIMT execution
models with thread blocks, warps, and instruction decoders
that allow trampolines to be inserted around SASS instruc-
tions [51]. These approaches fundamentally depend on the

As a result, existing approaches force an undesirable trade-
off: low-level instrumentation offers detailed runtime visi-
bility but loses semantic meaning, while framework-level
profilers preserve model semantics but provide little com-
piler or transformation awareness. This gap becomes even
more severe for closed accelerator backends, where neither
binary rewriting nor direct IR instrumentation is possible. As
illustrated in Figure 1, binary-level instrumentation hooks
are introduced only after the program has been fully lowered
into machine-level instructions, where higher-level operator
structure and tensor relationships have already been erased.
In contrast, the simplest we can do is to instrument earlier in
the execution pipeline, spanning the Graph IR and backend-
lowering stages where operator identity, tensor lineage, parti-
tion boundaries, and dataflow mappings [30] remain explicit
and can be preserved for later runtime correlation.
Instead of depending on instruction-level rewriting, and
to provide unified observability across accelerator stacks,
we introduce a comprehensive framework, DFIT (DataFlow
Accelerator Instrumentation Tool). This framework com-
bines metadata propagation, runtime adapters, capability-
aware backend interfaces, and normalized trace correlation
to recover execution behavior in a form that remains use-
ful for tool construction, portability analysis, and compiler-
aware performance debugging. DFIT is designed around
four reusable services: a stable metadata and manifest layer, a
capability-driven backend adapter interface, a policy-controlled
trace pipeline, and a tool-facing API for developing cus-
tomized analysis tools. This architecture enables the same
tool logic to operate across Cerebras [27], SambaNova [9],
and TPU while remaining robust to varying levels of backend
capabilities.
This paper makes the following contributions:
• We present DFIT, an instrumentation framework for
heterogeneous dataflow accelerators that enables in-
strumentation where no intermediate representation
is exposed.
• We introduce a stable metadata model and normalized
trace model that preserves operator identity, trans-
formation lineage, tensor information, and execution
boundaries across heterogeneous backends.
• We design a capability-driven adapter and policy archi-
tecture that enables portable instrumentation across
closed compiler stacks and is demonstrated through
TPU, Cerebras, and SambaNova.
• We demonstrate the practicality of DFIT through (1)
an Overhead Analysis Tool to demonstrate the over-
head cost, scalability, and lightweightness, and (2) a
Program Analyzer Tool to demonstrate the portability
and extensibility.

Background
2.1
Dataflow Architecture
Modern machine learning accelerators such as Google’s Ten-
sor Processing Unit (TPU) [14], Neural Processing Units
(NPUs) [26, 52], Cerebras’s Wafer Scale Engine [27] are de-
signed around a dataflow execution model, which differs
fundamentally from the control-flow paradigm of CPUs and
the SIMT model of GPUs [35]. Instead of issuing sequences
of instructions from a centralized control unit, a dataflow
accelerator triggers computation when operands become
available, as shown in Figure 2. Each Processing Element
(PE) performs a fixed micro-operation, typically a multi-
ply–accumulate (MAC), and forwards results to neighboring
elements through spatial interconnects [14, 18, 19]. This en-
ables massive parallelism and high utilization for dense linear
algebra workloads.
At the architectural level [9, 18, 27], these accelerators
employ large systolic or spatial dataflow fabrics, commonly
organized as two-dimensional grids of PEs interconnected
through short, regular data paths, as illustrated in Figure 2.
Each PE receives streams of operands, typically activations
and weights, performs a fixed micro-operation such as mul-
tiply and accumulate, and forwards partial results to neigh-
boring elements in a pipelined manner. The figure highlights
this shared organization through SRAM-backed operand
staging buffers, a spatial PE fabric, and a dedicated output
path for reduction and writeback, which together capture
the common execution structure across modern dataflow
accelerators. Although the three platforms differ in realiza-
tion, they share the same core architectural principle: execu-
tion is driven by operand movement and local propagation
rather than by a centralized instruction stream. TPUs empha-
size regular systolic execution for dense tensor workloads,
Cerebras extends the spatial model to a wafer-scale fabric
with distributed on-chip resources, and SambaNova adopts
a more reconfigurable spatial dataflow organization. Con-
sequently, the performance of these systems is governed
primarily by the efficiency of operand propagation, tiling,

Unlike binary instrumentation for CPUs or GPUs [15, 17,
32, 50, 51, 53], where program analysis tools can instrument
individual instructions or kernel launches, dataflow accel-
erators execute highly optimized firmware-controlled ker-
nels [19] whose internal operations are not directly visible
to developers. The microcode sequences that manage PE
scheduling, tensor tiling, and activation streaming are pro-
prietary and often opaque. This lack of observability makes
it difficult to determine how efficiently PEs are utilized, how
synchronization barriers affect throughput, or how different
layers of a neural network interact during pipeline execution.
Existing vendor profilers expose only aggregate utilization
and latency statistics, offering little insight into runtime be-
havior [7, 47].
2.2
MLIR Overview
2.2.1
Compiler Abstraction. A defining characteristic
of ML and dataflow accelerator stacks is the progressive
transformation of computation across multiple compiler ab-
straction levels. High-level graph operators may first be low-
ered into dialect-specific tensor operations [24, 30], then
transformed through scheduling, fusion, partitioning, and
memory-layout optimization passes before finally reaching
a backend runtime representation. Each stage introduces
performance-critical decisions while simultaneously mov-
ing the execution farther away from the original semantic
source [31].
Traditional instrumentation systems are poorly aligned
with this compiler structure because they typically assume
a single stable observation layer. However, in multi-level
compiler infrastructures such as MLIR [24], semantic value
is intentionally preserved across abstraction levels for as
long as it remains useful. This compiler philosophy creates
an opportunity for a fundamentally different form of instru-
mentation: rather than observing only the final execution
form, the instrumentation framework can preserve stable
identities, transformation lineage, and stage-aware meta-
data across lowering boundaries. This compiler-aware view
is essential for understanding how optimization decisions
manifest as runtime effects.
2.2.2
Semantic Preservation. The central systems chal-
lenge is therefore preserving semantic correspondence across
transformations that intentionally rewrite, fuse, reorder, or
partition the computation. A single high-level operator may
expand into multiple backend partitions, while multiple source
operators may be fused into one execution region [30]. With-
out a stable semantic contract, runtime events become diffi-
cult to attribute to source-level intent, compiler transforma-
tions, or tensor-level behavior [20, 33].
Addressing this challenge is a central design goal of DFIT.
Semantic preservation must survive both direct IR transfor-
mations and lowering passes, and must be reconstructable
through canonical metadata manifests, graph artifacts, and
boundary-level execution correlation. Treating semantic iden-
tity as a first-class instrumentation concern enables sharing
a unified trace model, which later supports transformation
attribution and cross-backend comparison.
2.3
Instrumentation Fundamentals
Dynamic Binary Instrumentation (DBI) provides a mecha-
nism for observing, analyzing, and modifying a program’s ex-
ecution without requiring access to source code or recompi-
lation. Unlike static analysis, which inspects binaries offline,
DBI systems interpose on execution and inject user-defined
analysis routines directly into the running program. This
enables fine-grained inspection of events such as instruction
execution, memory accesses, synchronization points, and ar-
chitectural state transitions, while preserving the functional
correctness of the original program.
At a high level, building an instrumentation tool on any
conventional platform, CPU or GPU, requires three founda-
tional capabilities. First, the instrumentation system must
be able to observe the execution stream, typically through
decoding or intercepting the instructions that the processor

a code cache or translation table [4, 32, 36], to ensure that
instrumented instructions execute correctly and efficiently.
DFIT addresses these requirements by treating semantic
identity, backend portability, and low overhead as first-class
design constraints, as detailed in Section 3.1.
3
Architecture and Framework Design
3.1
Design Challenges and Key Decisions
Building an instrumentation framework for heterogeneous
dataflow accelerators raises three systems challenges that
do not arise in conventional binary instrumentation.
C1: Semantic identity across compilation boundaries.
Unlike CPUs and GPUs, where a stable instruction stream
provides natural instrumentation anchors, dataflow acceler-
ators progressively transform and partition operators across
multiple compiler stages. A naive approach of attaching meta-
data at a single stage loses correspondence as operators are
fused, tiled, or reordered. We address this by propagating
stable semantic identifiers from the IR level through all low-
ering stages, so that runtime events can always be mapped
back to their source operators regardless of backend trans-
formations.
C2: Heterogeneous backend visibility. Backends differ
fundamentally in what they expose. None of the three eval-
uated platforms provides a compiler-visible pass interface:
Cerebras emits a dump of compiler artifacts, the Edge TPU
emits a compiler report and a model file, and SambaNova
exposes runtime logs and sidecar artifacts. A single instru-
mentation mode cannot cover these. We address this through
capability discovery at session initialization, which selects
between compiler-visible semantic tagging and artifact re-
construction without changing the tool-facing API.
C3: Tool portability without lowest common denom-
inator APIs. Portable frameworks often achieve portability
by restricting tools to the weakest available abstraction. We
instead normalize all backend observations into a common
semantic event schema at the framework level, preserving
the richest available information from each backend while
exposing a single stable contract to tool developers.

Semantic APIs. DFIT exposes a richer semantic ser-

The services shown in Listing 3 allow a tool to reason

3.3.3
Artifact-Reconstruction Services. Moreover, DFIT
provides artifact reconstruction services. Using these APIs,
semantic meaning is rebuilt from the last visible graph arti-
fact together with runtime boundary observations.
The goal of the API family presented in Listing 4 is to

operating over a stable abstraction. Graph import and se-

This design allows the same tool logic to remain valid even
when the backend only exposes runtime artifacts and profiler
summaries.

3.4
Software Components
The workflow above is implemented through a set of soft-
ware components that correspond directly to the stages
shown in Figure 3.
The common runtime core consists of the session manager,
tool registry, policy controller, trace sink, and event normal-
izer. These components are shared among instrumentation
modes. The session manager controls the lifecycle of a trac-
ing session, while the tool registry binds the selected analysis
module to the normalized trace stream. The event normal-
izer guarantees that both instrumentation paths converge
into the same normalized semantic event schema, which is
the key portability contract exposed to tools [1, 17]. Each
backend contributes its own adapter implementation to this
component stack, allowing the same session and normaliza-
tion pipeline to remain unchanged while backend-specific
artifact collection and runtime hooks vary underneath. At
the control plane, DFIT orchestrates backend selection, tool
registration, session execution, and result export, providing
a single user-facing entry point to the full software stack.
DFIT builds on the toolchains rather than replacing any
part of them. It compiles no models, schedules no kernels,
and links no vendor SDK. Each backend already emits a

3.5
Backend Adapter
The adapter layer is DFIT’s answer to Challenge C2: it iso-
lates backend-specific artifact collection behind a uniform
lifecycle contract, so that the capability discovery mecha-
nism in Section 3.1 can select the appropriate instrumen-
tation mode transparently. Backend portability in DFIT is
realized through a uniform adapter contract that separates
backend-specific artifact collection and runtime hooks from
the mode-independent tool interface described in Section 3.3.
Rather than exposing backend-specific compiler or instru-
mentation APIs directly to tools, each backend implements
the same lifecycle-driven adapter interface [17, 23, 24] and re-
ports its semantic and runtime visibility through a capability
descriptor. This contract allows the framework to preserve a
stable execution workflow even when the backend exposes
very different levels of compiler access.
Listing 6 explains how the framework unifies different
backends into a single execution path using capability dis-
covery and adapter creation. All backends follow a common
lifecycle—covering preparation, compilation, execution, and
metric collection—ensuring consistent higher-level tool be-
havior. This design enables easy extensibility, where new
accelerators only need to implement adapter and capability
logic, as shown by the Cerebras and SambaNova adapters
evaluated in Section 4.3.
3.5.1
Supporting a New Backend. A new backend must
expose a graph description in some readable form, name op-
erators consistently enough that identifiers assigned before
lowering still resolve afterward, and emit some record of
execution. Given those, the work divides predictably. Every
adapter implements the lifecycle methods in Listing 6 and
returns a capability descriptor, and that structure carries over
from an existing adapter. What changes is the reader for the
format the backend emits, which dominates the effort. Cere-
bras needs a reader for the operators, shapes, and lineage
in its emitted MLIR [24]. The Edge TPU needs two, one for
the compiler report and one for the model file, because the
report gives operator types without shapes. Neither adapter
touches the trace pipeline, the normalizer, or the tool API.

4.3
Portability and Extensibility Analysis
Beyond raw overhead and semantic fidelity, a central claim of
DFIT is that analysis logic can be developed once and reused
across heterogeneous dataflow accelerators with minimal
backend-specific effort. To evaluate this claim, we present a
portability-driven analysis centered on a portable semantic
analysis plugin.
4.3.1
Cross-Backend Tool Portability. The key design
principle enabling portability is that all backend adapters
lower their observations into the same normalized event
representation. Each event carries stable semantic identifiers,
operator lineage, tensor metadata, execution duration, and
memory movement statistics, independent of whether the
information originated from compiler-visible MLIR passes,
runtime callbacks, or reconstructed sidecar metadata. As a
result, the analysis plugin interfaces exclusively with the
normalized schema and never directly accesses backend-
specific artifacts.
This separation allows the analyzer implementation to re-
main identical across all evaluated platforms. TPU, Cerebras,
and SambaNova rely on reconstruction from compile reports,
sidecar metadata, and runtime logs. Despite being fundamen-
tally different architecturally and capability-wise, the plugin
requires no backend-specific branches, custom parsers, or
hardware-specialized logic beyond supplying platform peak
throughput and peak memory bandwidth constants as meta-
data inputs.
To quantify portability, we measure the analysis reuse
ratio [11], defined as the fraction of analyzer code shared
unchanged across backends:

5.1
Semantic Attribution
The semantic attribution tool reports which line of model
code each compiled operator came from. A developer tun-
ing a model needs that mapping to know where to spend
effort. On a CPU or GPU, debug metadata carries it: an in-
struction belongs to a source line, and a profiler reports time
against that line. Dataflow accelerators break the mapping
in two places. The compiler fuses and partitions operators,
so one source construct becomes many compiled operators.
Automatic differentiation and optimizer expansion then gen-
erate operators the developer never wrote at all, and these
outnumber the ones they did. A profiler that reports cost
per compiled region gives a number attached to something
absent from the source.
The tool recovers the mapping from the transformation
lineage the compiler emits. That lineage lists the frames an
operator passed through, from the innermost dispatch frame
out to the launcher, and the frame that identifies model code
sits between the two. The tool takes the first frame outside
framework infrastructure.
On ViT, 998 of 10,262 operators resolve to a line of model
code. Autodiff and optimizer expansion produced the re-
mainder, which retain a module path but carry no source
line. Compiled for inference, the same model resolves all 810
of its operators, and BERT, DiT and Mixtral behave the same
way.

5.2
Dataflow Memory Proxy
The dataflow memory proxy tool computes the peak resi-
dent tensor footprint of a compiled model, the quantity that
determines whether the model fits within an accelerator’s
on-chip memory. On general-purpose hardware, this quan-
tity is observable at runtime through the process’s resident
set. Edge accelerators expose no equivalent: the Edge TPU
executes a compiled model as a single fused operator, its
8 MiB on-chip SRAM is inaccessible to the host, and the
only memory accounting available is the compiler’s static
report. That report is limited to parameters, recording how
much weight memory the compiler cached on-chip and how
much it scheduled to stream from host memory. Activation
memory is not reported, so a model may satisfy the com-
piler’s parameter budget and nonetheless exceed the device’s
capacity during execution.
The tool derives the activation footprint from operator
metadata. Each value is live from its producing operator
until its final consumer, and a forward walk over the graph
yields the peak concurrent volume. Weights are excluded
from the computation: they remain live for the duration of
execution and would otherwise dominate the result, masking
the activation behavior that differentiates models.
Figure 11 presents both components for fifteen models,
with the compiler’s parameter figure as the lower segment
and the recovered activation footprint above it. No parameter
figure exceeds 7.15 MiB, so every model satisfies the 8 MiB
budget by the compiler’s accounting alone. Including activa-
tions, six of the fifteen exceed it. DeepLab-v3 illustrates the
discrepancy: the compiler reports 2.26 MiB of cached param-
eters with no streaming, suggesting substantial headroom,
while its activation footprint reaches 7.57 MiB. Inception-v4
exhibits the inverse profile, streaming 36 MiB of parame-
ters while requiring only 2.13 MiB for activations. The two
components vary independently, and an admission decision
based on the compiler’s report alone would accept six models
that do not fit.
6
Limitations and Future Work
Limitations: DFIT also has important limitations. First,
semantic fidelity in the reconstruction path depends on the
quality and availability of graph artifacts, metadata, compile
reports, and runtime records. When a backend exposes only
coarse artifacts, the framework can preserve tool portability
but cannot recover semantic detail that was never avail-
able. Second, DFIT does not attempt to provide the same
machine-level visibility as instruction-oriented binary in-
strumentation systems. This is an intentional design choice,
but it also means that the framework is not the right abstrac-
tion for studies that depend on exact instruction streams or
microarchitectural binary behavior. Third, while the adapter
model provides a clean portability contract, integrating a
new backend still requires implementing lifecycle hooks and
metric normalization interfaces.
Future Work: A particularly important next step is to ex-
tend the framework beyond runtime artifact analysis toward
direct compiler-pass instrumentation, where MLIR transfor-
mation passes can be instrumented natively and evaluated
through an open compilation stack such as IREE [29]. This
direction would enable finer-grained pass-level attribution,
richer transformation lineage analysis, and more direct vali-
dation of compile-stage instrumentation strategies.
Two additional features are particularly important for
broadening the practical impact of DFIT. First, the frame-
work can be extended to support distributed multi-host corre-
lation, enabling unified tracing across host CPUs, accelerator
fabrics, and inter-device communication boundaries in large-
scale training and inference deployments. This would allow
end-to-end attribution of latency, synchronization, and ten-
sor movement beyond a single execution domain. Second,
richer support for dynamic and evolving graphs remains
an important next step, particularly for adaptive serving
pipelines, mixture-of-experts models, and workflow-driven
accelerator applications where graph structure changes at
runtime.

proaches impossible. DFIT draws on their tool-centric design
philosophy but replaces instruction-level anchors with se-
mantic operator identities and normalized tensor events that
survive compilation and backend lowering.
Vendor and Framework Profilers. Vendor profiling
tools such as the Cerebras performance profiler [5], Sam-
baNova profiling APIs [48], and Google’s XLA profiler [13]
provide platform-specific performance visibility within their
respective stacks. Higher-level framework profilers including
PyTorch Profiler [3], TensorFlow’s TFLite profiler [7], and
MLPerf benchmarking [47] offer workload-level timing and
throughput summaries across frameworks. Distributed trac-
ing systems such as OpenTelemetry [45] and Perfetto [12]
provide structured event collection pipelines for multi- com-
ponent systems. While these tools are useful for single-stack
debugging, none provides a portable tool-building abstrac-
tion that operates uniformly across compiler-visible and
closed accelerator backends. DFIT addresses this gap through
a capability-driven adapter model and a normalized semantic
event schema that decouples analysis tools from backend-
specific profiler formats.
ML Compiler Observability. MLIR [24] established the
value of progressive lowering, multi-level IR transformations,
and preservation of higher-level semantics across compila-
tion stages. The Transform dialect [30] and related work
on compiler-pass instrumentation demonstrated how se-
mantic information can be made traceable across lowering
boundaries. IREE [29] provides an open compilation stack
that exposes MLIR-level passes for direct instrumentation
and serves as a natural future target for DFIT’s compiler-
visible path. Recent work on HIR [33] and MLIR-based GPU
code generation [20] similarly shows the value of preserv-
ing tensor-level semantics through backend lowering. DFIT
differs from these compiler infrastructures in that it is not
a compilation framework: it treats the compiler as an in-
formation source rather than a transformation engine, and
extends semantic correspondence into the runtime domain
even when direct IR access is unavailable through artifact
reconstruction.
Performance Analysis Frameworks. HPCToolkit [1]
and Score-P [21] provide portable performance measurement
and analysis for HPC workloads, demonstrating the value of
normalized trace collection and multi-platform portability
in performance tooling. Caliper [17] introduced a flexible
annotation-driven measurement framework that separates
measurement concerns from application logic. Roofline anal-
ysis [54] established arithmetic intensity as a portable perfor-
mance abstraction across memory and compute hierarchies.
DFIT builds on these ideas by extending portable measure-
ment and roofline-style analysis to heterogeneous dataflow
accelerators, where neither instruction-level observability
nor shared hardware counter interfaces are available.
8
Conclusions
Modern dataflow accelerators deliver exceptional perfor-
mance for machine learning workloads, but their closed com-
piler stacks and opaque execution models make systematic
instrumentation extremely difficult. Existing binary-level
and framework-level approaches either lose semantic cor-
respondence or fail to generalize across heterogeneous ac-
celerator ecosystems. This gap has limited the development
of reusable analysis tools for compiler-aware performance
debugging, transformation attribution, and cross-platform
studies.
This paper presents DFIT, a semantic instrumentation
framework for heterogeneous dataflow accelerators that pre-
serves operator, tensor, and execution-boundary identities
across compilation and runtime stages. By combining stable
metadata propagation, capability-driven backend adapters,
and normalized trace correlation, DFIT enables the same
analysis tool logic to execute across TPU, Cerebras, and
SambaNova without backend-specific rewriting. Our evalua-
tion demonstrates that this portability can be achieved with
practical overheads, ranging from 3.53% in IDs-only mode
to 13.62% under full semantic instrumentation, averaged
across all three platforms.
Beyond a single profiler, DFIT establishes instrumentation
as a reusable systems framework for emerging accelerator
stacks. We believe this abstraction is an important step to-
ward making next-generation accelerator stacks observable,
analyzable, and ultimately more programmable.
