FastEEP: Fast Intra-Instance Elastic Scaling for
Expert-Parallel MoE Serving
Yunfei Feng∗, Jingkai He∗, Shiqi Liu, Cheng Zhang, Dong Du, Erhu Feng†
Institute of Parallel and Distributed Systems (IPADS), Shanghai Jiao Tong University
Abstract
Large-scale expert parallelism (EP) has become the stan-
dard deployment configuration for Mixture-of-Experts (MoE)
models in production. Meanwhile, the highly dynamic na-
ture of LLM workloads requires providers to continuously
adjust serving capacity to match fluctuating demand. Scaling
MoE serving cannot be efficiently achieved by simply adding
or removing serving instances; instead, it often requires re-
sizing the EP group within an existing instance, which we
refer to as intra-instance scaling. Existing inference engines
primarily rely on instance-level scaling, which destroys and
reconstructs entire serving instances, incurring substantial
scaling overhead.
We present FastEEP (Fast Elastic Expert Parallel), a fast
intra-instance scaling system for MoE serving based on the
principle of Partial Reuse. FastEEP reuses existing runtime
state across worker execution, GPU memory, and commu-
nication by separating reusable execution structures from
the resources activated by the current EP configuration.
This separation enables coordinated resource reclamation
and reconfiguration while preserving costly-to-reconstruct
state, allowing fast EP scaling without full instance tear-
down and reconstruction. Our evaluation shows that Fas-
tEEP achieves 4.5×–11.7× faster scaling than the existing
vLLM-based approach across different models, enabling effi-
cient, fine-grained scaling of MoE serving.

Introduction
Mixture-of-Experts (MoE) models have become the domi-
nant paradigm for large language models (LLMs), scaling
from billions to trillions of parameters [1–3]. By selectively
activating experts, MoE balances model capacity with per-
token computation overhead.
Consequently, Expert Parallelism (EP) [4, 5] has emerged
as the primary deployment strategy for MoE models. Under
EP, experts are partitioned across multiple GPUs, tokens are
dispatched to their routed experts for computation, and the
resulting outputs are subsequently aggregated. In distributed
inference clusters, increasing the EP degree effectively re-
duces redundant expert weights, which leaves more GPU
memory available for KV caches and runtime execution. As
a result, real-world MoE deployments scale EP across tens

Conversely, opting for a smaller EP degree improves scaling
elasticity, but incurs a heavy memory penalty due to the
redundant replication of model weights.

instance elasticity via dynamic EP scaling, which en-

However, enabling dynamic EP scaling is non-trivial. An
MoE inference instance operates as a stateful, tightly coupled
system rather than a collection of independent workers. As
a result, scaling the EP degree up/down requires reconstruct-
ing global cluster state. Existing implementations trigger
instance-wide execution stalls lasting from several seconds
to tens of seconds, leaving GPU resources idle and causing
severe Service Level Objective (SLO) violations for requests.
Our key insight is partial state reuse. We divide serv-
ing state into persistent and reconfigurable components.
Reusing persistent structures, such as per-GPU runtimes and
pre-negotiated collective communicators, avoids expensive
distributed re-initialization. Asynchronous online reconfigu-
ration updates the remaining state while serving continues,
leaving only a brief coordinated transition.
To this end, we present FastEEP, an elastic MoE inference
system that operationalizes partial state reuse. Specifically,
FastEEP addresses the following three challenges.
Challenge-1 (Network): Immutable communication
groups. EP inference relies on Data Parallel (DP) collectives
and EP All-to-All communication, both of which operate over
pre-established communicators (e.g., NCCL groups [17]). Un-
der the Single Program, Multiple Data (SPMD) paradigm,
these collective operations mandate that every rank enters
the call before execution can proceed. Existing communi-
cation groups cannot dynamically accommodate changing
membership. Every EP scale-up/down forces the cluster to
tear down active communicators and perform distributed
re-initialization for new ones, which takes several to tens of
seconds and incurs a cluster-wide stop-the-world pause.
Challenge-2 (Memory): Memory reclamation de-
stroys execution contexts. Scaling down must aggres-
sively release GPU memory. Although model weights and
KV caches consume a large share of memory capacity, our
empirical analysis reveals that transferring/reloading them
is not the primary latency bottleneck. Instead, rebuilding
components of the execution context, such as computation
graph [18] buffers, kernel workspaces, and communication
buffers, accounts for the vast majority of scaling latency.
Purging these runtime states destroys persistent execution
structures and forces costly network handshakes and graph
recapture during scale-up.
Challenge-3 (Runtime): Safe worker retention and
reuse. To eliminate GPU worker creation and initialization
overheads during scale-up, the system retains scaled-down
workers so they can be recycled. A target worker must stop
GPU computation and remain alive, while active workers
continue serving outside a brief coordinated transition. How-
ever, a worker’s execution is tightly coupled with the rest
of the cluster: it computes attention for its local requests
and executes expert layers for tokens dispatched from re-
mote ranks. Even if a worker drains its local requests, remote
GPUs may still route tokens to its hosted experts. The sys-
tem must therefore toggle a worker’s participation safely
without discarding its initialized state.
To solve the challenges, we propose the following designs.
Design-1: Reusing communicators through flexible
group splitting. FastEEP creates a parent NCCL commu-
nicator over the maximum worker set and retains its rank
identities and bootstrap state. Each resize derives a subgroup
containing only active workers, so collectives do not wait
for inactive ranks. For expert dispatch and combine, a NIXL
mask hides the same inactive ranks while connections among
active peers remain in place. Switching the subgroup and
mask together changes who communicates without rebuild-
ing the distributed instance. Because every subgroup comes
from the parent, later scale-up can reintroduce previously
inactive workers.
Design-2: Reusing GPU context with fine-grained
offloading. FastEEP reclaims HBM from an inactive worker
while preserving the runtime objects that are expensive to
create. CUDA virtual memory lets it retain the device ad-
dresses of weights, KV-cache allocations, and graph buffers
while releasing the physical pages behind them. Contents
follow their use: data that must survive is backed up, repli-
cated weights are fetched from active workers, and request-
specific KV state is moved or reconstructed. Graph buffers
return to the addresses recorded in captured CUDA Graphs,
allowing replay without recapture. Communication buffers
are reclaimed only after remote access has stopped, so their
release does not invalidate the retained communication state.
Design-3: Safe worker retention and reuse through
coordinated sleep. FastEEP drains or moves requests off a
target worker while making its experts available on the re-
maining workers. At a safe point, it switches request routing,
expert placement, and communication membership together.
After in-flight work finishes, the target skips GPU execution
but keeps its process, executor, and CPU control threads
alive; peers no longer send it tokens. On scale-up, the same
worker rejoins only after its memory and connections are
restored, avoiding reinitialization.
We implement FastEEP on vLLM and evaluate it across EP
sizes from 2 to 16. Across six transitions on each measured
model, FastEEP scales in 4.2–13.4 s, achieving geometric-
mean speedups of 7.0× over vLLM Elastic EP and 22.0×
over restart. FastEEP also preserves steady-state throughput
and enables colocated services to release and reassign GPUs
without instance reconstruction.

Characterizing the Cost of MoE Scaling
Large-scale MoE inference requires dynamically provision-
ing GPU resources to match fluctuating traffic demands
while maximizing compute utilization. However, Expert Par-
allelism (EP) fundamentally dictates both how GPU memory
is partitioned and how flexibly resources can be reclaimed.
2.1
MoE Serving and Elasticity Requirement
Expert parallelism. In MoE architectures, each token
is dynamically routed to its top-𝑘experts. Because expert
parameters dominate modern model footprints (e.g., 97%
of all parameters in DeepSeek-V3 [3]), Expert Parallelism
(EP) partitions these expert weights across 𝐸𝑃ranks. Spread-
ing experts reduces the per-GPU weight memory footprint,
freeing HBM to accommodate larger KV caches. Attention
is typically replicated across data-parallel (DP) workers or
sharded under tensor parallelism (TP), with serving engines
enforcing EP = DP × TP [19]. Production clusters routinely
deploy EP degrees in the hundreds [3, 20], driven further by
advancements in high-speed interconnect fabrics [6, 7].
Demand moves faster than instances do. Real-world
LLM inference workloads exhibit extreme short-term traffic
volatility. In the two-month BurstGPT trace [21] (1.4M re-
quests), 59% of ten-second windows experience no incoming
requests, while busy periods exhibit a 25× swing between me-
dian and 99th-percentile arrival rates. Even in denser produc-
tion environments like the Azure conversation trace [22, 23]
(27M requests over one week), traffic fluctuates by 1.7× with
equally transient spikes.
Facing such fluctuations, cluster operators are forced into
a severe dilemma: provision for peak traffic and suffer se-
vere idle overheads during troughs, or provision for median
traffic and violate Service Level Objectives (SLOs) during
bursts. This inefficiency is unsustainable in multi-tenant
clusters where MaaS platforms, RL rollouts, and spot work-
loads contend for shared GPUs [9–11, 13, 24, 25]. Despite
extensive efforts [12, 14–16, 26–30], existing frameworks op-
erate strictly at the coarse granularity of whole instances,
preloaded configurations, or full replicas. Crucially, none
permit dynamically reconfiguring the active EP degree of a
live, running instance.
The scaling must be fine, fast, and reversible. Effective
intra-instance scaling must satisfy three requirements:
• Fine-grained: As shown in Figure 1, instance-level scal-
ing operates at a granularity far too coarse (dozens of
GPUs) for demand shifts.
• Fast: Existing intra-instance resizing takes 36.4–92.0 s
(§2.2), which is significantly longer than the median dura-
tion of the traffic excursions it is meant to handle.
• Reversible: Because traffic bursts are transient, resources
added during a spike must be promptly reclaimed without
incurring heavy tear-down and rebuild penalties.
2.2
The Cost of MoE EP Resizing
Existing designs resize whole instances. Current LLM
serving systems manage capacity changes through coarse-
grained instance manipulation or static pre-allocation. A
naive restart tears down the entire instance and initializes
a new one from scratch. vLLM’s Elastic EP avoids process
restarts but still reconstructs the distributed runtime—re-
creating Ray workers, rebuilding process groups, and re-
capturing CUDA graphs [31]. Conversely, preloading ap-
proaches keep all parallel configurations resident simultane-
ously, paying exorbitant memory penalties [12, 16, 29, 30].
Runtimes with shadow modes preserve processes and ex-
ecution graphs but freeze the parallel topology. Similarly,
fault-tolerance mechanisms (e.g., SGLang rank-failure re-
covery [32]) mask failed peers and remap experts without
yielding physical memory back to the GPU pool. While re-
parallelization and migration have been studied for full in-
stances [11, 33] and systems like ElasticMoE require warmup
periods during scale-up [8], no existing system can dynami-
cally reconfigure the active EP degree of a live instance while
returning individual GPUs to the shared pool.
A resize costs a rebuild. Figure 2 quantifies the latency
breakdown of an instance rebuild, taking 126 s from process
launch to steady-state serving across six distinct phases: 24 s
startup, 13 s communicator construction, 10 s weight loading,
32 s operator profiling and compilation, 6 s KV sizing, and
36 s CUDA graph capture. Crucially, loading model weights
takes only 10 s; the remaining 116 s is consumed by build-
ing the execution environment. In fact, 6.32 GiB of HBM

Analyzing the state destroyed during a resize (Table 1)
reveals that the overhead stems primarily from components
invariant to the EP degree itself. Worker processes, compiled
kernels, CUDA contexts, communication infrastructure, and
captured graphs depend strictly on the model architecture,
device, and maximum world size rather than the immedi-
ate EP degree. Memory allocations follow a similar trend:
because NIXL transfer buffers are dimensioned for the maxi-
mum world size, an instance capable of scaling up to eight
ranks allocates memory for eight ranks from startup, much
of which is allocated outside the serving engine’s managed
pools by driver-level libraries. What the EP degree truly dic-
tates is merely a minimal set of dynamic state: active rank
participation, expert-to-node placement mappings, physical
page residency, and peer connectivity.
Three rigid bindings force the rebuild. Current infer-
ence runtimes enforce three structural bindings that make
dynamic EP scaling impossible without a full rebuild:
• Immutable Communicator Binding: Collective com-
munication groups are constructed for fixed rank sets. Un-
der standard SPMD collective semantics, every member
rank must synchronously enter a call, meaning dropping
or adding a rank forces the destruction and distributed
re-initialization of the process group—unless subcommuni-
cators are derived from a persistent parent group spanning
the maximum rank set [17].
• Static Memory & Address Binding: Captured CUDA
graphs, operator kernel arguments, and registered RDMA
memory regions tightly bind to hardcoded virtual mem-
ory addresses. Deallocating or resizing a buffer invali-
dates the execution path even when data shapes remain
unchanged—unless virtual address spaces are decoupled
from underlying physical page allocations.
• Tightly Coupled Worker Execution: An inference
worker concurrently manages local request state, KV
caches, and hosted experts serving remote token dis-
patches. A worker cannot independently pause or exit
without triggering remote hangs—unless remote peers
dynamically mask the rank and remap expert routes,
similar to fault-recovery mechanisms [32].

conventions rather than hardware constraints, no deployed

FastEEP Overview
Given a running MoE serving instance, FastEEP changes
its EP size quickly while minimizing disruption to request
processing. Scaling down releases GPUs for other workloads;
scaling up restores GPU capacity when throughput and KV-
cache demand increases.
3.1
Existing Designs
Existing systems expose two approaches to changing the EP
size of a serving instance.
Preloaded-instance switching. One approach pre-
initializes several instances of the same model with dif-
ferent parallel configurations. Inactive instances offload
their weights and KV cache to host memory, then restore
them when selected. This avoids a full cold start, but each
configuration still retains its processes, CUDA Graphs, and
communication state. For MoE serving, that residual foot-
print is substantial: communication and driver allocations
alone consume several GiB per GPU, while the full runtime
state can exceed 10 GiB (§2.2). Moreover, preloading can
cover only a fixed set of configurations, trading memory
consumption for limited scaling flexibility.
Intra-instance reconstruction. The alternative recon-
structs the running instance at the target size. vLLM Elastic
EP [31] follows this approach: it changes the Ray worker set,
rebuilds communication groups, and captures new CUDA
Graphs. SGLang provides a related mechanism for rank-
failure recovery [32], rather than deliberate resource scaling.
Reconstruction supports more configurations than preload-
ing, but repeats expensive initialization on every transition.

3.2
Challenges
Reconfiguring a fixed communication fabric. Wide-
EP inference couples two communication paths with differ-
ent semantics: DP collectives synchronize attention workers,
whereas EP All-to-All, implemented as point-to-point trans-
fers, dispatches tokens to remote experts and returns their
outputs. Their rank membership, transport endpoints, topol-
ogy, channels, and registered buffers are established during
initialization (§2.2) and are assumed to remain fixed dur-
ing execution. Under SPMD collective semantics, a single
inactive rank can prevent the remaining ranks from making
progress; conversely, stale EP routing may direct remote ac-
cesses to buffers that have already been reclaimed. An EP re-
size must therefore switch both communication paths to one
consistent active-rank view. Reconstructing that view from
scratch requires distributed bootstrap and topology setup—
close to 20 s for an eight-GPU group in our measurements—
and imposes a cluster-wide stall.
Reclaiming HBM without invalidating runtime state.
Scaling down must release not only model weights and
KV cache, but also the CUDA Graph storage, operator
workspaces, and communication buffers that account for a
substantial fraction of each worker’s HBM footprint. These
allocations are not interchangeable byte arrays: captured
CUDA Graph executables embed their device addresses,
while communication libraries retain registrations and
remote-access metadata for their buffers (§2.2). Conven-
tional deallocation destroys these address and registration
invariants, so scale-up must rebuild communicators and
repeat graph warm-up and capture even if tensor shapes
are unchanged. In our evaluated configurations, graph re-
capture alone takes 25–82 s. The memory challenge is thus
to reclaim physical HBM without discarding the logical
allocation identity required to reuse the execution context.
Quiescing workers without stopping service. Avoid-
ing worker reconstruction requires a scaled-down worker
to remain alive but quiescent while the rest of the instance
continues serving. Reaching this state is difficult because
each worker simultaneously owns local requests and their
KV cache, participates in DP synchronization, and executes
experts for tokens routed from remote ranks. Draining its lo-
cal request queue therefore does not eliminate remote expert
traffic or outstanding communication. A safe transition must
jointly update request ownership, KV-cache placement, ex-
pert placement, token-routing tables, communication mem-
bership, and in-flight operations before any compute or mem-
ory resource is released. Otherwise, the resize can lose re-
quest state, invoke a collective with mismatched membership,
or access reclaimed memory. This cross-subsystem transition
must complete with only a brief coordinated pause rather
than stopping the entire instance for worker teardown and
reconstruction.
3.3
System Overview
FastEEP replaces reconstruction with partial reuse: it initial-
izes the instance once, retains expensive long-lived state,
and changes only the resources that participate in the active
configuration.
At the memory layer, tagged CUDA virtual-memory pools
preserve virtual addresses while selected physical pages are
offloaded or released. Weights can be restored from host
memory or active peers, expired KV-cache pages can be dis-
carded, and CUDA Graph storage can be restored without
recapture. At the communication layer, FastEEP derives ac-
5


tive NCCL subgroups from a persistent parent group1 and
reconnects or masks NIXL peers instead of rebuilding the
entire communication domain.
At the execution layer, FastEEP removes target workers
from request routing, drains or re-issues their in-flight re-
quests, remaps required experts, and masks inactive ranks
from expert dispatch. The worker processes, executors, and
compiled kernels remain alive for rapid reactivation.
A resize is executed as a staged transaction: prepare re-
sources concurrently, commit the new active configuration
at a short global quiescence point, and reclaim idle resources
after request processing resumes. Together, these mecha-
nisms preserve correctness while reducing scaling latency
by 4.5–11.7× relative to vLLM Elastic EP (§5.2).

FastEEP Design
The three challenges above arise from a common cause: exist-
ing systems bind active resources to initialized runtime state
within one lifecycle. Changing the EP size therefore destroys
not only GPU resources, but also communication domains,
device addresses, CUDA Graphs, and worker contexts, all of
which must be rebuilt during scale-up.
FastEEP addresses this problem through partial state
reuse, separating stable structural state from active state
that changes with the EP size. It first decouples the physical
communication network from logical participants, allowing
different EP sizes to share one substrate. It then decouples
virtual addresses from physical HBM, allowing shadow
workers to release memory while preserving their execution
contexts. Finally, the runtime combines changes to commu-
nication, memory, request routing, and expert placement
into one consistent worker-state transition.
4.1
Reusing the Communication Network
MoE inference uses collectives for synchronization and ag-
gregation and All-to-All communication for token dispatch
and combine. Point-to-point peers can be controlled inde-
pendently, but collective participants are fixed in a group.
Rebuilding that group requires bootstrap, topology discov-
ery, connection setup, and buffer allocation. FastEEP instead
retains a global group over all workers. It suspends this group
and releases its resources when idle, then reuses its context
and control-plane state to derive a group for the current
active workers.
All-to-All communication: dynamically changing
point-to-point reachability. MoE dispatch and combine
logically form an All-to-All operation. Resizing changes both
active ranks and expert placement, so each token must reach
the rank currently hosting its expert and return to its source
under the same active view.

represents visibility in a device-side mask read by dispatch
and combine kernels. During scale-down, it masks a rank
after replicas of its experts become available. During scale-
up, it unmasks the rank only after its buffers and endpoints
are ready. Membership thus changes without rebuilding the
All-to-All domain.
Collective communication: retaining the parent do-
main and switching the active subgroup. NCCL commu-

every member must enter each collective. As long as an in-
active rank remains a member, all other ranks must wait for
it. Masking inactive ranks in P2P operators does not resolve
this issue because the inference communicator must include
only the active ranks.

time of the instance (less than 300 MB in total). Its data-plane
resources can be selectively offloaded to host memory dur-

4.2
Fine-Grained GPU Memory Management
Leaving distributed execution does not release a worker’s
GPU memory. Besides weights and KV cache, it holds CUDA
Graph buffers, operator workspaces, communication buffers,
and runtime caches whose setup dominates startup cost.
FastEEP therefore preserves their logical identities and ex-
ecution contexts while offloading contents or unmapping
physical pages. A shadow worker (see §4.3) can reclaim HBM
and later restore this state in place.
Preserving virtual addresses while changing physi-
cal mappings. Using CUDA Virtual Memory Management,
FastEEP creates separate CuMem pools for shared weights,
expert weights, KV cache, and CUDA Graph buffers. Scale-
down unmaps and releases physical pages while retaining
virtual addresses, tensor metadata, and object references.
Scale-up maps new pages at the same addresses.
Stable addresses preserve kernel arguments, tensor point-
ers, and allocator objects, allowing wake-up without rebuild-
ing runtime structures. Irreplaceable contents are backed up
before unmapping; data available from another worker or
cheap to reconstruct is discarded. This trades host-memory
use for recovery latency without sacrificing address reuse.
Restoring weights and KV cache according to their
semantics. Under EP, non-expert weights such as attention
weights are replicated. A shadow worker can discard them
and later restore them from an active rank over NVLink at
their original addresses. Expert weights use the same device-
to-device path. The control plane computes the target place-
ment and source–destination rank pairs so that every logical
expert has a replica in the active set. It batches transfers by
tensor or expert, while the data plane performs asynchro-
nous peer copies on a separate CUDA stream.
For request-specific KV cache, FastEEP chooses among
three policies for each block: discard and recompute it from
the prompt and generated tokens after rescheduling; migrate
it asynchronously to an active rank over NVLink; or swap
it to pinned host memory and reload it later. This balances
recovery latency, interconnect bandwidth, and host-memory
use without retaining a shadow worker’s complete KV cache.
Offloading CUDA Graph buffers. CUDA Graph capture
fixes kernel arguments and device pointers in the graph
executable. A reallocated buffer therefore invalidates replay
if its address changes, even when its shape and contents do
not. Repeating warm-up and capture also adds substantial
scale-up latency.
FastEEP routes capture-time allocations to a dedicated
CuMem graph pool. During the sleep transition, FastEEP
backs up required contents and unmaps physical pages while
preserving virtual addresses; on wake-up, it remaps pages
and restores data at the same locations. The graph’s pointers,
arguments, and topology remain unchanged, enabling direct
replay without recapture. Thus, FastEEP preserves the graph
execution context, not its original physical pages.
Communication-buffer reachability. Communication
buffers may remain accessible to remote peers or in-flight
kernels. Releasing one locally can therefore redirect remote
writes into reallocated pages. FastEEP uses collective-group
switching and point-to-point visibility as safe lifetime bound-
aries for these buffers.
For collectives, FastEEP first installs the new active sub-
group and drains old operations. It then offloads idle parent-
group buffers to pinned host memory and releases their HBM,
retaining the group identity, rank information, and bootstrap
context. Before the next resize, it restores the buffers at their
original addresses and derives a new subgroup. The parent
can thus persist without keeping its full data plane in HBM.
For point-to-point communication, the NIXL mask con-
7


trols reclamation. During scale-down, the target is first re-
moved from expert routing and the mask; after in-flight
traffic drains and endpoints disconnect, FastEEP reclaims

establishes endpoints while the rank remains invisible, then
unmasks it. Both paths follow one rule: revoke reachabil-

4.3
Reusing Worker Execution Contexts
The preceding mechanisms make communication member-
ship switchable and decouple memory identity from physical
residency. The runtime combines them into one consistent
worker-state transition.
Partial reuse changes worker state rather than creating or
destroying workers. Scale-down stops target computation,
removes the worker from the data plane, releases network
buffers, and offloads physical memory. Its process, execu-
tor, compiled kernels, virtual addresses, CUDA Graph exe-
cutables, and control state remain intact. Scale-up restores
memory and communication reachability and re-enables
computation, avoiding process startup, model initialization,
graph capture, and communication reconstruction.
The shadow worker state. A shadow worker retains its
execution identity without consuming GPU compute re-
sources. Its process, CPU threads, executor, virtual addresses
and control state persist. Physical memory for weights,
KV cache, graph buffers, and communication buffers is
unmapped or offloaded, leaving only the device state re-
quired for recovery. Wake-up restores these contents at their
original addresses.
The worker is excluded from the NCCL subgroup and
hidden by the NIXL mask, so it receives neither collectives
nor dispatch and combine traffic. Its global rank, bootstrap
information, and control connections remain available for
recovery and later reconnection.
Before model execution, the runtime checks the active
state. Shadow workers bypass the forward pass and launch
no attention, expert, or communication kernels. Their CPU
threads handle only control commands and barriers, yielding
GPU compute while remaining ready to wake at a coordi-
nated transition point.
Algorithm-level contraction. In DP+EP, attention par-
allelizes requests along DP, while experts parallelize tokens
along EP. Each worker handles local requests and KV cache
while serving expert tokens from peers. Scale-down must
close both paths: stopping request scheduling alone does not
stop remote expert traffic.
On the request path, FastEEP marks the target as draining
and removes it from the active DP set. Existing requests drain
or migrate. Once no active request or KV state remains, the
runtime skips its attention forward pass.

The control plane moves workers between active and in-

for request routing, expert placement, and communication.
A configuration becomes visible only after all required re-
sources are ready.
Scale-down. The control plane inspects each rank’s state,
request queue, and KV-cache occupancy to select targets.
It stops new admission, then drains requests or migrates
their state. In parallel, it rearranges experts and transfers
any weights missing from the contracted placement. Once re-
quests and experts no longer depend on the targets, FastEEP
offloads their weights, KV cache, and CUDA Graph buffers
and releases the HBM. It derives a new subgroup from the
global NCCL group, updates the NIXL mask and endpoints,
and switches views at a safe point. After old operations fin-
8


ish, it offloads unused global-group and inactive rank buffers
to the CPU, then marks the targets inactive.
Scale-up. The control plane selects shadow workers to
wake, remaps their physical pages, and reloads CUDA Graph
and communication buffers from the CPU. Through the re-
tained global communication relationships, it copies non-
expert weights, expert weights, and required KV blocks from
active ranks to their original addresses. It then derives the
expanded NCCL subgroup, registers NIXL buffers, and es-
tablishes peer endpoints. Once all connections are ready, the
control plane atomically publishes the expert mapping, com-
munication view, and request routing and marks the ranks
active. They can now receive requests without reinitializing
their execution contexts.
5
Evaluation
We evaluate the performance benefits of FastEEP under real
workloads, focusing on its ability to reduce the latency of
scaling a running service and the resulting interference with
live requests. We also evaluate the effectiveness of dynamic
scaling in multi-model deployments.
Testbed. Experiments run on two GPU nodes. Each node
has two Intel Xeon Platinum 8575C CPUs and eight NVIDIA
H20-3e GPUs (140 GiB HBM each). The GPUs are connected
by 900 GB/s intra-node NVLink. Inter-node communication
uses eight BlueField-3 integrated ConnectX-7 NICs (400 Gb/s
per NIC).
Implementation. FastEEP is implemented on vLLM
v.0.27.0, Python 3.12, PyTorch 2.11.0+cu130, NCCL 2.28.9,
and NIXL 1.2.0. The implementation adds about 5K lines of
production code for elastic EP scaling, request transfer, NIXL
rank masking, expert remapping, and weight refilling. These
components are integrated with the vLLM scheduler and
GPU worker without changing the MoE serving interface.
Baselines. For scaling comparisons, we evaluate three
systems using the same software stack:
• Restart. It terminates the serving instance and relaunches
vLLM with the target EP size.
• vLLM Elastic EP baseline [31]. It creates or removes Ray
engines and reinitializes distributed communication.
• FastEEP. It leverages the elastic scaling mechanisms devel-
oped in this work for GPU communication, GPU memory
management, and worker execution, thereby enabling ef-
ficient intra-instance scaling.
Models and workloads. Our scaling study covers six

End-to-End Scaling Latency
We evaluate six scale-up and scale-down transitions among
{4, 8, 12, 16}. Figure 9 reports results for six models. FastEEP
consistently reduces scaling latency across models and
transitions. Across all models and six transitions, FastEEP
completes scaling in 4.2–13.4 s, while its FullAsync variant

92.0 s, and a full restart takes 126–293 s across all six models.
Across all model-transition pairs for which Elastic EP is
available, FastEEP achieves a 4.5×–11.7× speedup, with a
7.0× geometric mean; the FullAsync variant increases the
geometric-mean speedup to 9.3×. Across all model-transition
pairs, the geometric-mean speedups over restart are 22.0×
and 29.3× for FastEEP and its FullAsync variant, respectively.
Scale-up is generally more expensive than scale-down, but
FastEEP is faster than both baselines for every available
comparison, consistent with the benefit of reusing workers,
communication state, and CUDA Graphs across model sizes
and transition directions. The official vLLM Elastic EP im-
plementation could not successfully run DeepSeek-V4-Flash
and Mistral-Small-42; therefore, we omit Elastic EP results
for these two models.
Expert re-layout and state restoration dominate the
scaling path. Figure 10 compares the phase breakdowns of
vLLM Elastic EP (a, b) and FastEEP (c, d) for the EP 8 →4

6
Discussion
The space–time trade-off. Fast scaling trades memory
for reconstruction time. Rather than retaining a complete
instance or preloaded replica, FastEEP manages workers,
communicators, and memory regions independently. For
state that is expensive to rebuild, it retains only the meta-
data needed for reuse, while releasing or offloading data
resources unused by the active configuration. This enables
fast transitions without the memory cost of an entire inactive
configuration.
Prioritizing GPU resource reclamation. Persistence
does not imply GPU residency. FastEEP maintains a commu-
nication group at the maximum world size, but after each
resize it offloads inactive GPU data buffers to CPU memory
(2–4 GB, excluding the KV cache) and retains only the meta-
data needed for reuse. Initializing the system at the maximum
world size therefore does not require the corresponding GPU
resources to remain occupied throughout execution.
Scope and scalability. Unlike systems that recover failed
ranks or switch entire models [13, 32], FastEEP focuses on
changing the EP width of a running MoE instance. We eval-
uate FastEEP on a two-node, 16-GPU cluster with NCCL
communication and inter-node RDMA. Although our evalu-
ation is limited to 16 GPUs, the design scales to larger clusters
by replacing centralized connection reconstruction with dis-
tributed state offloading. This decentralized approach should
scale more favorably than existing scaling mechanisms. Our
implementation is open source and has been submitted to
vLLM as a PR.
Limitations. FastEEP scales only within the maximum
topology initialized at startup. Scale-up requires sufficient
available GPU memory, and larger topology changes still
require reconstruction.

Related Work
Elastic MoE serving. vLLM Elastic EP [31] changes world
size but rebuilds communicators. ElasticMoE [8], evaluated
on Huawei’s Ascend NPUs, offloads only model weights
and KV caches yet remains fundamentally instance-level:
scale-up switches to a preinitialized instance and requires
warm-up. MoEless [41] scales individual experts as server-
less functions. Rank-failure recovery [32] preserves CUDA
Graphs through peer masking and expert remapping, with-
out reclaiming GPU memory. FastEEP supports bidirectional
rank scaling within one preinitialized maximum topology,
reusing graphs and communication state while reclaiming
inactive ranks’ physical memory.
Instance scaling and scheduling. Instance-level sys-
tems optimize loading and cold starts [12, 16, 29, 30, 42] or
multiplex models and requests [13, 24, 25, 33, 43]. EP size
offers an additional allocation knob for goodput-oriented
schedulers [44]; elastic sequence parallelism and memory
pools provide complementary dimensions [45, 46]. Autoscal-
ing policies decide when to resize [14, 15, 23, 26–28]; our
mechanism supplies the transition and supports either side of
prefill/decode disaggregation [47–49], although we evaluate
a non-disaggregated deployment.
GPU virtual memory. vAttention and KunServe grow
KV capacity with VMM [50, 51]; Prism, WarmServe, and
vLLM sleep mode release pages without changing virtual ad-
dresses [42, 52]. Related abstractions manage tensors, defrag-
mentation, memory ballooning, and MoE experts [53–56].
Foundry [57] uses deterministic addresses for graph transfer
across processes; FlashBoot [58] accelerates weight loading
and avoids NCCL group formation. FastEEP combines page
release with graph replay and RDMA registration renewal
across repeated EP resizes.
8
Conclusion
We presented FastEEP, a system for fast intra-instance EP
scaling in MoE serving. Through partial state reuse, FastEEP
preserves workers, stable virtual addresses, and the startup
communication topology while selectively reclaiming and
reconfiguring GPU resources. This design substantially re-
duces scaling latency and allows a running instance to adjust
its GPU allocation without reconstruction. FastEEP enables
MoE services to adapt to changing demand beyond fixed
instance boundaries.
