## ABSTRACT 

Large language models (LLMs) on mobile devices can act as agents that call external software tools to complete complex tasks, but the major challenge of supporting on-device mobile agentic AI with LLMs is the long latency of LLM tool calling on mobile devices. In particular, the decode phase is the main contributor of such long latency, but is hard to speed up on mobile processors as it is bound by memory bandwidth rather than compute power. To address this limitation, in this paper we present SchemaWeaver, a new on-device mobile agentic AI technique that enforces schema-guided parallel decoding in the decode phase of LLM tool calling, to reduce its latency by producing multiple tokens in each decode pass. SchemaWeaver can be generically applied to the LLM inference engine on mobile devices without involving any training efforts or changes on LLMs, and our experiment results on major mobile SoCs and LLM families show that SchemaWeaver can reduce the LLM tool calling latency by up to 3.9 times, compared to the competitive baselines. 

## 1 INTRODUCTION 

In recent years, Large Language Models (LLMs) have been used as the backbone of agentic AI systems. When given proper context, LLM agents can interpret user instructions, select the proper external software tools, and call these tools to complete complex tasks [27, 52, 53, 77]. For example in Figure 1, when being asked for driving directions, the LLM agent selects the get_route software tool from the available tools for this task. It then calls this tool for route planning and returns the results back to the user in natural language. In this process, the LLM agent perceives each tool from its schema ,which is a machine-readable description that gives the tool’s description and the names and types of its arguments [27]. The LLM agent, then, calls the tool by generating the text command with values of the tool’s arguments. Currently, LLM agents on mobile devices (e.g., smart-phones) have become increasingly popular, allowing intelli-gent and automated operations on the user’s personal data [11, 47, 62]. Agentic AI functionalities on mobile devices have also been supported by mainstream mobile OSes, via Android AppFunctions [2, 3] and iOS App Intents [4]. The major challenge of supporting on-device mobile agen-tic AI, however, is the long latency of LLM tool calling on mobile devices. In inference, an LLM produces its output through repeated forward passes that constitute a prefill phase and a decode phase . The prefill phase uses the first pass to read the input prompt, and the decode phase then generates the response using the other passes, each of which produces one output token [51, 72]. As shown in Figure 2(a), in traditional conversation-based LLM uses, one prefill is usually followed by a large quantity of decoded text tokens that the user reads as they arrive, and most of the decode latency is hence “hidden” in user reading [40, 68]. Agentic LLM operations, in contrast, first decode a structured tool call command for tool execution, and text tokens in response can only be produced after the completion of tool execution. The decode latency experienced by the user, hence, becomes significantly longer, especially when executing complicated agentic tasks such as on-device content search that involves multiple tool calls of different types. In these tasks, our ex-periments show that the decode latency constitutes up to 81% of the wall-clock time being taken (Sec 2.2). Unfortunately, it is difficult to accelerate this decode phase on mobile devices, which is bound by the device’s limited memory bandwidth rather than by compute power [28, 51]. Since each decode pass only produces one output token, the decode latency is determined by the speed of memory bus, which is usually much slower than the mobile processor speed and hence causes processor starvation. Our experiment results on the OnePlus 12R phone with Snap-dragon 8 Gen 2 SoC show that the decode speed on mobile CPU is > 5× slower than the prefill speed (Sec 2.3). Using mobile GPU or NPU cannot help much, due to the shared memory architecture in mobile SoCs [8, 11, 34, 72]. The key to accelerating the decode phase in mobile agentic AI, hence, is how to allow producing multiple output tokens in one decode pass, to fully utilize the on-device compute power. One straightforward approach is speculative decod-ing [9, 20, 32], which first uses a much smaller draft model to guess the next few tokens and then lets the target model check the correctness of these guesses in one pass. Since a tool call is highly structured, most output tokens are highly predictable. For example, with a SmolLM2-1.7B as the target model and SmolLM2-135M as the draft model, 74% of guesses are correct. However, these correct guesses only result in 31% speedup, because the draft model still decodes one token per pass and is bounded by memory bandwidth as well. Another option is constrained decoding [16, 21, 33, 64, 82], which builds a set of grammatical rules from the tool’s schema and forbids any output token that makes the LLM tool call ill-formed. These rules can be further used by jump-forward decoding [82] in each decode pass, to skip the cur-rent decode computation when only one legitimate output token exists. These skipped tokens can then be processed in batch by a single prefill pass. However, since tokens can only be skipped when they are being computed, the overall decode latency is still bound by the number of decode passes, which can only be sequentially computed. To fundamentally overcome this limitation of sequential decode computations, we instead aim to allow decoding the argument values of an LLM tool call in parallel, by leverag-ing the pre-known and fixed information contained in the tool schema. More specifically, the schema describes the po-sition of each argument’s value in the tool call command, and each position is always fixed. For example, in the call 

get_weather() shown in Figure 2(b), the value of argument 

city is a string that begins after city=" and ends at the closing quote, and the value of argument days is an integer after days= . Hence, instead of decoding these argument val-ues sequentially, we can decode all of them as one batch in parallel to save unnecessary passes. On the other hand, the fixed names of arguments need no decoding, and can instead be loaded by the LLM inference engine via one prefill pass. Based on this idea, in this paper we present SchemaWeaver, a new on-device mobile agentic AI technique that enforces schema-guided parallel decoding in the LLM inference en-gine. First, SchemaWeaver parses the fixed parts in the tool schema to build a tool skeleton that provides information about the position of each argument value (Sec 4.1). It then places argument names as parallel token sequences, so that arguments share the same prompt and tool call prefix to facilitate parallel decoding of argument values. To handle rugged value lengths, we pad decode sequences on the fly for the maximum compute efficiency (Sec 4.2). Since decode results of argument values may not share exactly the same sequential prefix, we add a write-back phase after parallel decoding to realign the decode results and rebuild the LLM agent’s KV cache accordingly. To avoid this write-back phase from blocking tool executions, we assemble a valid tool call at the same time and emit the tool call early to further reduce the end-to-end latency (Sec 4.3). Many tools called by the LLM agent may include optional arguments. For example, when calling the weather query tool, the LLM agent may opt to specify the temperature unit or not. The values of optional arguments have to be decided after all required argument values are generated, and cannot adapt to parallel decoding. Instead, we have to decide and generate values of optional arguments in a sequential man-ner, after parallel decoding of required argument values (Sec 5). To minimize the extra latency caused by this sequential decoding, we design provisional calls for read-only tools to emit early only with required arguments, which can be later replaced by a corrected call once the LLM agent adds the optional argument values (Sec 5). To our best knowledge, SchemaWeaver is the first system design that accelerates on-device LLM tool calling on mobile devices, without involving any training efforts or changes

• The gain of SchemaWeaver grows as the memory band-width falls. When the memory bus is slowed by 4 .7×,serial decoding slows by 3 .2× but SchemaWeaver only slows by 2 .4×, and its speedup rises from 3 .0× to 3 .9×.

• Applying SchemaWeaver costs <2% of tool calling cor-rectness across different LLM settings. 

• SchemaWeaver is lightweight and efficient. With 8.9 MB of extra peak memory being used compared to base-lines, it reduces the energy consumption of a tool call by 2 .1×.

## 3 OVERVIEW 

As shown in Figure 5, SchemaWeaver decodes the argu-ment values of an on-device agentic AI tool call in parallel, and leaves everything fixed in the tool schema as prefill. To that end, we assume that every available tool comes with 

> 2The optimal sizes of token batch are multiples of 4, because LLM inference engine’s CPU matrix routines handle 4 sequences at a time in a pass [22].

a schema that lists its arguments, types of arguments, and whether each argument is required or optional. This avail-ability of tool schemas is guaranteed in most existing agentic frameworks, such as LangChain and AutoGen [31, 65]. SchemaWeaver sits inside the on-device LLM inference engine and does not alter other components outside of tool calling. Without loss of generality, in SchemaWeaver design we assume that the software tool being called is decided by a specialized Tool Selector given the user request, and Schema-Weaver hence focuses on accelerating the corresponding call of the selected tool. In practice, such tool selection has been recognized as an easy NLP task, on which a small LLM (e.g., Octopus-v2-2B [13] or TinyAgent-1.1B [17]) can succeed. 

## 3.1 Tool Skeleton Builder 

As stated in Section 1, an argument value can only be de-coded in parallel with others if the inference engine knows its position, but traditional serial decoding learns the position of an argument value only when decoding of the previous value has ended. SchemaWeaver, instead, makes the posi-tions of all argument values pre-known before decoding, by building a tool skeleton that contains all the fixed parts of tool call, namely the tool name and names of required ar-guments, from the tool schema. Argument values remain unfilled in the tool skeleton, as exemplified in Figure 5 for the tool get_weather with two arguments city= and days= .Positions of argument values can then be derived by tokeniz-ing the texts in tool skeleton with the argument names laid out in parallel and letting the LLM agent read these tokens in one prefill pass: the first token of each argument value can be located immediately as after the last prefilled token of the corresponding argument name. Special handling, however, is needed at the boundary be-tween the tool skeleton and an argument value, because the model may write the last character in the skeleton and the value’s first character as one fused token, which distorts the 

> 4

parallel decoding of argument values. More details about the tool skeleton and such special handling are in Section 4.1. 

## 3.2 Parallel Value Decoder 

In parallel decoding of argument values, each argument value corresponds to one token sequence that starts from the token corresponding to the argument’s name in the tool skeleton. All these token sequences can be computed as one batch, and a token sequence stops when the corresponding argument value is completely decoded, depending on the argument’s type. For example, a string ends with the closing quote, and a number ends at the first token that cannot continue as a number. Decoded argument values hence differ in length, and the decoder applies padding to token sequences when necessary. More details are in Section 4.2. The decode results cannot be directly used as input to the LLM agent, because each sequence contains only part of the tool call command (i.e., the corresponding argument and its value). The LLM agent cannot continue its inference on any sequence, as it cannot read the full text of tool call command. To address this issue, SchemaWeaver writes the decoded argument values back to a sequential space in device memory after the parallel decoding completes, to reassemble the complete call text and enter it into the LLM’s KV cache as one new sequence. The write-back costs a single prefill pass instead of decoding the call again token by token, since the assembled call can be handed to the tool for execution before write-back, such reassembling does not incur extra latency on tool execution. More details about such write-back are in Section 4.3. 

## 3.3 Optional Argument Resolver 

Optional arguments involved in the specific tool call need to be separately handled. Only after the write-back of required argument values, SchemaWeaver decides the optional argu-ments one at a time with the Optional Argument Resolver, to ensure the correctness of generated tool call command. To minimize the latency of such serial decisions, SchemaWeaver starts the tool early as a provisional call that carries only the required arguments, while the Optional Argument Resolver decides the optional arguments. If the tool call indeed in-volves optional arguments, these are later added towards a corrected call that replaces the provisional call. Early execution of the provisional call is feasible only when the tool is read-only and its execution does not apply any changes to the mobile system. For example, a provisional call to the weather lookup tool illustrated in Figure 2 is feasible, but other tools such as sending a message cannot be executed by a provisional call. ## 4.1 Building the Tool Call Skeleton 

The tool skeleton is determined jointly by the tool schema and the LLM’s tool call format being used, which fixes the tokens that open and close a call and the keys around the tool name and list of arguments. Different LLM families use different tool calling formats, and SchemaWeaver’s Tool Skeleton Builder adapts to them, by recognizing the format being used from the special tokens in the model’s vocabulary. For example, for Qwen3 models [74], the shared head of tool skeleton uses the opening <tool_call> tag and the key 

arguments . The closing brace and the closing tag come after the last argument value, and so they are added at the write-back (Sec 4.3). For Llama 3.2 [24] models, the head has no tag and uses the key parameters .Figure 6 shows how the tool skeleton is laid out. The shared head of the call lists the tool name and the beginning part of the argument list. They are shared and visible to all token sequences in decoding, each of which corresponds to one argument and starts at the same position after the shared head. A single prefill pass processes the head and all argument names together; afterwards, the starting position of every argument value (in decoding) is known, as decoding follows from the skeleton’s next token in the sequence.

## 4.3 Assembling the Tool Call 

When decoding of all token sequences has finished, the re-quired argument values are all known. However, since differ-ent argument values are simultaneously generated in parallel sequences, such parallel decoding invalidates the token se-quences’ corresponding entries in the LLM agent’s KV cache, when these entries are integrated into a single sequence to complete the tool call 3. For example in Figure 8, one token sequence ends with "city":"New York" and the other ends with "days":0 , but neither of them completes the tool call. SchemaWeaver tackles this issue with the Tool Call Re-assembler, which discards KV caches in diverged token se-quences, reassembles the decoding results from parallel to-ken sequences into a single sequence, and recomputes the affected KV cache for the complete tool call. The assembled argument texts are then written back to the KV cache in a single prefill pass. For tool calls in the BFCL dataset [50], the write-back prefills 34.5 tokens on average and takes 522 ms on the OnePlus 12R, about the time of 9 decode passes. However, note that this write-back may not increase the end-to-end tool call latency, because the recomputed KV cache is only needed in the next conversation of LLM agent (e.g., when the LLM agent reads the tool’s result and writes its reply to the user). ## 5 HANDLING OPTIONAL ARGUMENTS 

Many tool calls also contain optional arguments (e.g., 66% in the BFCL dataset [50]). Figure 9 illustrates the two cases that SchemaWeaver handles, namely tools without and with optional arguments. We first explain when the optional ar-guments should be decided, and then how provisional calls are designed to minimize the tool call latency with optional arguments. 

Deciding optional arguments. For a specific tool call, while its required arguments are pre-defined by tool schema and can be decoded in parallel based on such information, the optional arguments being involved depend on values of required arguments and cannot be decided in advance. Table 4 shows why the time of deciding the involved op-tional arguments matters. If the optional arguments are de-cided before any value of required arguments is generated, the correctness of deciding the optional arguments is 17% lower than that with serial decoding, as the LLM agent has to make guesses in many cases. The correctness of the tool call, correspondingly, also drops by 13.5%. Another choice is to include all the available optional arguments into the tool skeleton but usually involves unused arguments, further reducing the argument correctness by another 5.2%. Hence, SchemaWeaver opts to decide the optional argu-ments after values of required arguments are decoded, using serial decoding, and such late decision of optional arguments improves the argument correctness to 79%. On the BFCL dataset [50], such serial decoding adds 13.5 decode passes on average.

## 6 IMPLEMENTATION 

We implemented SchemaWeaver on llama.cpp [22] (commit 

d59d455f , August 2026), the most commonly used open-source LLM inference engine for Android smartphones. Our implementation consists of a library of 930 lines of C++ code on the public API of llama.cpp, together with a 350-line patch to its server as a hook on tool calls to its decode loop. When the LLM agent chooses to emit a tool call, the hook lets SchemaWeaver produce the call, and returns the provisional call to the agent app as soon as it is assembled, before the optional arguments are decided. When the call is complete, the hook feeds its tokens back to the server exactly as if they had been decoded in serial. The engine itself is otherwise unchanged. Figure 10 shows how the pieces fit together. SchemaWeaver is deployed on two smartphone models with different mobile SoCs, i.e., a OnePlus 12R with Qual-comm Snapdragon 8 Gen 2 SoC and 16 GB of memory run-ning Android 14, and a Google Pixel 7 with Google Tensor G2 SoC and 8 GB of memory running Android 16. The LLM inference engine and SchemaWeaver are built from source with clang 21.1 in Termux, and we use the publicly released GGUF files of LLMs in 8-bit (Q8_0) and 4-bit (Q4_0) quanti-zation. Both smartphones are controlled from a desktop over the Android Debug Bridge (adb), which launches Schema-Weaver and the baselines to collect experiment data. 

## 7 EVALUATION 

In our evaluation, we use open-sourced LLMs including Qwen3 [74], Llama-3.2 [24] and SmolLM2 [6]. The model size varies from 0.6B to 4B to fit the memory and compute limits of smartphones. We use the following tool call datasets to evaluate the on-device performance of tool calling: 

• BFCL-v4 [50] consists of 2,501 single-turn tool call samples across 991 tools, with up to 9 arguments per call and 2.4 on average. Our evaluation uses a subset of 100 calls, uniformly sampled over the number of arguments per call. 

• DroidCall [69] is a dataset for Android system in-tents, i.e., tool calls that open apps, set alarms or send messages on the phone, from which we take its 154 single-call requests over 23 tools. 

Experiment protocol. To ensure fair comparisons, the in-ference engine process is pinned to 4 performance cores of mobile CPU, at a fixed CPU clock under a cooling fan, since thermal throttling would otherwise change CPU frequency in the middle of a run. The choice of the core set and CPU clock is given in Appendix A. Peak resident memory is read from the mobile processor’s VmHWM counter polled once per second. Time consumption is measured via the phone’s builtin monotonic clock. 

Baselines. We compare the performance of SchemaWeaver with the following four decoding schemes, and every baseline runs in the same engine software build as SchemaWeaver. 

• Unconstrained decoding , shown as No Grammar in tables and figures, lets LLM write the call freely. 

• Constrained decoding [16, 21, 22, 64] applies the schema constraint built into llama.cpp on top of un-constrained decoding. 

> 8

• Jump-forward decoding [82] skips the tokens that the schema fixes when the decoder meets them, as described in Section 4.1. 

• Speculative decoding [32] guesses the next tokens using a smaller draft model for the target model to check its correctness. Due to the limitation in available draft and target models in LLM families we use, we test two different schemes with different models: 1) EAGLE-3 [36] with a draft layer of 59M to 247M parameters that reads the target model’s hidden states, available for every model in our set except SmolLM2; 2) DFlash-2 [10] with Qwen3-4B as target model and a 1.0 GB block-diffusion draft model. 

Metrics. Our primary evaluation metric is the tool call la-tency . For SchemaWeaver, we compute the latency as the elapsed time between the start of generating tool call texts and the start of tool execution. For the baselines, the latency ends at the last token of the tool call. Latency is reported as the geometric mean [18, 26] over the repetitions of each call and then over the calls, since it is the mean that summarizes ratios consistently. We report a speedup as the ratio of two such means. Besides, we also evaluate the whole-call correctness , i.e., the percentage of the tool calls made whose tool and ar-guments match the accepted answers in the dataset. The number of forward passes per call, the peak resident mem-ory and energy cost per call are also evaluated and reported as more detailed information about the compute costs of tool calls.

## 7.4 Impact of the Number of Arguments 

The gain of SchemaWeaver grows with the number of argu-ments of the call, since every argument adds to the decode parallelism. Figure 12 shows the latency by the number of arguments. A one-argument call has nothing to decode in parallel, and its 1 .9× speedup comes from the skipped fixed tokens and the provisional call alone, so the gap to jump-forward decoding is the smallest there. Calls with four or more arguments gain 2 .5×, since the parallel pass batches the most values there, and the gap to jump-forward decoding is the largest. The three-argument calls gain less than the two-argument ones (1 .9× against 2 .2×), because the model adds an optional argument after the provisional call in 72% of them, against about half of the other calls, so their tool call is more often the corrected call that waits for the write-back and the serial decision.

## 8 RELATED WORK 

On-device LLM agents. Many mobile agents operate ex-isting applications through the GUI [57, 62, 63, 79]. Mobile platforms are recently adding native, schema-described tools, such as Android AppFunctions [2, 3], iOS App Intents [4] and MCP [27]. Agent-X [15] accelerates the on-device agent pipeline by reusing the unchanged parts of the prompt across turns, while SchemaWeaver shortens the generation of the tool call within each turn, so the two can be used together. SPORK and PASTE [5, 56] guess the tool call while the model is still generating it, start the tool early, and discard the result if the guess was wrong, which partially inspires the optional argument handling in SchemaWeaver. 

Parallel text generation. Another line of work generates several segments of text in parallel: Skeleton-of-Thought [46], APAR and PASTA [29, 41] target free-form texts only. Sim-pleTool focuses on tool calls and decodes a function’s name and arguments in parallel from the same independence ob-servation [55]. However, it trains special tokens into the model and evaluates on a desktop GPU. HyFunc also short-ens function calls, with a trained cascade that hands the call from a large model to a small one and fills the fixed syntax from a template [38]. SchemaWeaver is training-free, runs off-the-shelf quantized models on phones, and grounds its design in their memory-bandwidth profile. 

Speculative decoding. Speculative decoding drafts several tokens with a cheaper mechanism and verifies them in one forward pass of the target model; the draft comes from a smaller model, from small heads trained onto the target model, or from the model’s own recent output [9, 20, 32, 35, 36]. Newer drafts come from the workload itself: Suf-fixDecoding and AgentSpec reuse the repetitive outputs of agent pipelines on a serving cluster [48, 60], and ToolSpec drafts a tool call from its schema and from retrieved past calls of the same tools [66]. These gains rely on a history of similar calls, which the first tool call on a phone does not have, and a wrong draft still costs the batched pass that rejects it. On phones, speculative systems keep the draft model in memory and load the target from flash only to ver-ify a batch of drafted tokens as in LLMCad, EdgeLLM and Lever [58, 70, 71], or schedule the draft and the verification on different processors [14, 43]. Self-speculative decoding drafts with the target model itself by skipping some of its layers, as in Draft & Verify [81] and SWIFT [67], so it needs no second model. However, they are designed for larger mod-els (e.g., 13B) that cannot fit onto a phone. In every case, the draft model is a second set of weights that the memory bus must also move. SchemaWeaver needs no second model, and the passes it saves are fixed by the schema rather than by how well a draft guesses. The two can be combined: a draft model shortens each value sequence while SchemaWeaver decodes the sequences together. 

## 9 DISCUSSIONS 

Mobile accelerators. SchemaWeaver runs on the mobile CPU. The schedule change itself is not CPU-specific, since every pass it adds or removes is an ordinary batched forward pass, but it brings no gain on the phone’s other processors to-day. On the GPU, a pass that advances four value sequences costs 2.5 serial decode steps against 1.2 on the CPU, a serial step is 1.7 × slower than the CPU’s at the same clock, and running the whole design there makes the call slower than constrained decoding (0.39 ×). The contention with the GUI and the longer initialization time on GPU are also problem-atic. On the NPU, a four-sequence pass costs about three serial steps, and a serial step takes about 3 × longer than on the CPU, since the inference engine keeps the model’s output layer on the CPU for now and every decode step then pays a round trip between the two processors. What the accelera-tors do offer is a cheap prefilled token, 10 × cheaper than a decode step on the GPU and over 70 × on the NPU [11, 72]. This matches the skeleton and write-back prefills of Schema-Weaver; letting the NPU run those prefills while the CPU decodes the value sequences is our future work, if moving the state between the two processors costs less than it saves. MNN-AECS [28] runs the bandwidth-bound decode on fewer and slower CPU cores to save energy; SchemaWeaver short-ens that same phase, so the two designs can be combined. 

Other inference engines. SchemaWeaver needs two things from an engine: a schema-derived grammar and attention masks supplied by the caller in the batched decode pass. Only llama.cpp offers both today, while MNN-LLM [61], Execu-Torch, Google AI Edge SDK [23] and MLC-LLM [44] with TVM [12] miss necessary features on Android. Since the technique behind SchemaWeaver is not engine-specific, we expect similar speedup on other inference frameworks. 

## 10 CONCLUSION 

In this paper, we present SchemaWeaver, a new technique to accelerate the use of LLM tools on mobile devices by allowing the parallel generation of argument values for tool calls. SchemaWeaver achieves up to 3 .9× speedup in tool call latency without noticeable correctness loss compared to the 

> 12

existing schemes, and also reduces energy consumption by 2.1 ×.

## A THE CORE SET OF THE MEASUREMENT PROTOCOL 

The measurement protocol of Section 7 pins one engine thread to each of four CPU cores and fixes the clock of these cores. On the OnePlus 12R, the four cores are the A715 cores at 1.79 GHz; on the Pixel 7, they are the two X1 cores at 1.745 GHz and the two A78 cores at 1.663 GHz. These are the highest clocks that the two phones sustain under continu-ous load with the cooling fan on. The pinning is necessary. Without it, the Android scheduler stacks two or three of the four threads on one core and leaves another core idle, and the same engine decodes 1 .4× to 2 .3× slower on the 12R. Table 10 explains the choice of these four cores. It lists the cost of a serial decode step, a four-sequence step and a prefill token on different core sets of the two SoCs, measured with llama.cpp’s batched benchmark on Qwen3-1.7B at Q8_0 with the clocks pinned as above.

Three observations follow. First, the extra cost of a four-sequence step over a serial step is the lowest on the four chosen cores, 1 .22 × on the 12R and 1 .11 × on the Pixel 7, and adding more cores does not lower it (1 .18–1 .25 × on the 12R, 1.19 × on the Pixel 7). Second, the little cores slow down every step, serial and batched alike. The engine waits for all threads after every layer, so a pass runs at the speed of the slowest core. Using all eight cores is 9% slower than using four on the 12R and 27% slower on the Pixel 7, and the four little cores of the Pixel 7 alone are two to three times slower. Third, the largest core of the 12R, the X3, shortens every pass when it is added, the serial step by 20% and the prefill token by 43%. However, its clock is not sustainable under continuous load, and it shortens the baseline and SchemaWeaver alike, so the protocol leaves it out. The two X1 cores of the Pixel 7 already saturate its memory bus, since two threads decode as fast as four.
