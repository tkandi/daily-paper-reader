# Characterizing CPU-GPU Memory Sharing over Unified Memory Architecture 

## Jinrong Yang, Zimeng Wang, Rong Chen ∗, Haibo Chen 

Institute of Parallel and Distributed Systems, School of Computer Science, Shanghai Jiao Tong University 

Abstract 

Unified Memory Architecture (UMA) enables the CPU and GPU to share a single physical memory. However, its com-plexity and opacity often drive applications back to ineffi-cient copying or to incorrect direct access that sacrifices per-formance or even correctness. This paper presents a compre-hensive study of CPU-GPU memory sharing on UMA, cov-ering correctness and performance across data-plane trans-mission and control-plane coordination on four platforms. It yields four findings that guide libumsh , a portable library that delivers correct and efficient memory sharing across platforms and extends to emerging ones (e.g., NVIDIA DGX Spark). Applied to nine real-world systems, libumsh re-duces data-plane time by 16–75% and control-plane overhead by 7–90%.

1 Introduction 

Heterogeneous SoCs that couple a CPU with one or more accelerators—GPUs, NPUs, or ASICs—have become the dom-inant substrate for model inference, graphics rendering, sci-entific computing, and generative AI. Across edge and client devices, including embedded systems [8, 38, 82, 102], mo-bile phones [9, 76, 101], laptops [11, 45, 100], and emerging mini AI supercomputers [10, 15, 111], vendors increasingly integrate these accelerators with the CPU under a Unified Memory Architecture (UMA), in which both processors share a single physical memory. In contrast to the traditional Dis-crete Memory Architecture, which keeps CPU and GPU memory physically separate and connects them over PCIe or NVLink C2C [81], UMA offers a simpler programming model, a larger memory footprint available to each processor, and the elimination of explicit cross-device copies. This paper studies CPU-GPU communication via memory sharing on UMA platforms—a basic building block that deter-mines both the correctness and the performance of hetero-geneous computing. Such communication serves two quali-tatively distinct purposes. Data-plane transmission moves bulk data into or out of GPU computation, including model

parameters, inference inputs/outputs, textures, and point clouds, typically at task boundaries; representative scenar-ios include model loading [31, 49, 98], image preprocess-ing [90, 119], output sampling [91, 122], and frame composi-tion [59, 115]. Control-plane coordination exchanges small but frequent state—flags, counters, and locks—within and across kernels to sequence work or arbitrate shared resources between the CPU and GPU, as exemplified by hybrid infer-ence [20, 33, 126, 127], model offloading [19, 39, 66], and GPU filesystem operations [67, 99, 110]. Although UMA platforms natively support direct access 

to shared memory, mainstream applications routinely fail to exploit this capability correctly or efficiently. In practice, most applications either treat the platform as if it were dis-crete and incur unnecessary copy overhead [25, 31, 49, 83, 89, 98, 114, 120], or apply UMA features incorrectly and suffer data inconsistency or crashes [60, 61, 87, 88]. For example, widely used deep learning frameworks such as PyTorch [98] and OpenVINO [49], as well as LLM serving systems such as vLLM [120] and llama.cpp [31], still rely on redundant copies for weight loading and I/O processing on UMA platforms, wasting both time and memory. Rendering engines such as MoltenVK [115] exhibit incorrect usage patterns that cause data inconsistency between the CPU and GPU. These failures are not matters of engineering preference; they arise from the inherent complexity and opacity of UMA platforms along three aspects. (i) Hardware : platforms dif-fer in interconnect type (Ring vs. NoC), in the presence of memory-side cache (MSC) in front of DRAM, and in support for GPU-to-CPU coherence, and each combination alters which access patterns are correct and which are efficient. (ii) Software : critical configurations such as page size, cache policy, and coherence direction are buried within closed-source drivers and proprietary runtimes, while the OS ab-stractions above them silently fall back under load [65, 94]. (iii) Semantics : data-plane and control-plane traffic impose opposing objectives—bandwidth on large transfers versus low-contention atomics on small flags—so no single memory-sharing recipe is universally optimal. In response, we present the most comprehensive study of CPU-GPU memory sharing over UMA to date. We pursue completeness along three dimensions (Figure 1) that mirror the source of complexity above: applications (semantics), implementations (software), and platforms (hardware).

Findings. Our analysis covers what we believe are the most representative CPU-GPU memory sharing applications and UMA platforms in use today, yielding correct implementa-tions for each platform and four performance findings (§4). 1. Page size dominates setup cost and propagates into access cost . For large regions, 4 KB pages inflate setup time by nearly 100 × over 2 MB pages and degrade subsequent bandwidth through TLB pressure. For small regions, forcing 2 MB allo-cations wastes memory and is up to 5 × slower on Lunar and Orin. Transparent Huge Pages (THP) [71] selects an appro-priate size automatically; we therefore recommend enabling THP and prefaulting the region at setup. 2. Uncached memory is simple and platform-agnostic, but its cost is substantial . Uncached (UC) memory makes direct ac-cess correct without code changes—as with Orin’s default GPU policy for registered host-memory sharing [79]—yet it inflates single-threaded CPU latency by up to 300 ×. GPU par-allelism can hide UC overhead in microbenchmarks, but real workloads still incur a measurable penalty: an L2-optimized GEMM on Orin loses 16% of its GFLOPS. UC should therefore be reserved for cases in which neither code modification nor coherence support is feasible. 3. One-way cache coherence simplifies implementation at near-zero cost on MSC-enabled platforms . GPU-to-CPU cache co-herence (CC), supported on most UMA platforms, allows the CPU to correctly access write-back (WB) memory without any application-level changes. CC introduces overhead on GPU accesses, but this cost is negligible when a memory-side cache (MSC) is present. On Arrow, which lacks an MSC, GPU write time with CC is 2.07 × that without CC. 4. Under high concurrency, control-plane coordination is bot-tlenecked by contention rather than access latency . For small shared regions, the choice among correct implementations is nearly irrelevant; what matters is the number of GPU threads that touch the flag concurrently. Block-level barriers handle up to 1,000 threads with minimal code complexity. Beyond this threshold, grid-level barriers eliminate contention at the cost of deadlock-avoidance complexity, and a single-thread kernel remains a safe fallback. 

Library and extensibility. libumsh automatically selects correct, efficient implementations through high-level sender-receiver operations, based on the platform and application sharing requirements (Table 2, §5). An AI-assisted three-step porting workflow (§5.1) extends it to NVIDIA DGX Spark [111], validating extensibility to two-way coherence. 

Case study. We applied libumsh to nine real-world sys-tems that span data-plane and control-plane patterns across the four target UMA platforms. On the data plane, libumsh 

eliminates redundant copies in model loading (PyTorch), im-age preprocessing (OpenCV), output sampling (OpenVINO GenAI), and point-cloud processing, reducing transmission time by 16–75%. On the control plane, libumsh replaces heavyweight runtime events and CPU-side delegation with lightweight memory-based signaling and atomics in hybrid inference (EdgeNN), model offloading (Accelerate, Demand Layering), GPU filesystem operations (GPUfs), and cross-device file locking (GoFS), reducing coordination overhead by 7–90%. 

Contributions. This paper makes three contributions: 

• We develop a systematic methodology spanning applica-tion semantics, memory-sharing implementations, and UMA properties (Figure 1). 

• We characterize four UMA platforms and reveal how page size, cache policy, coherence, MSC, and contention jointly shape data-plane and control-plane performance. 

• We build libumsh , to our knowledge the first library whose high-level CPU–GPU sharing APIs automatically select correct, efficient implementations by platform and application sharing requirements. The library, correctness tests, and benchmarks are available at https://github.com/ xpuos/libumsh .

2.1 Unified Memory Architecture 

Unified memory architecture (UMA) enables the CPU and GPU to share a unified physical memory [107]. UMA is widely deployed in edge devices, including embedded sys-tems [8, 38, 82, 102], mobile phones [9, 76, 101], laptops [11, 45, 100], and emerging mini AI supercomputers [10, 15, 111], due to its simplified programming abstraction and increased available memory. In contrast, discrete memory architecture, the traditional mainstream approach, uses physically sepa-rate CPU and GPU memory spaces connected by buses such as PCIe or NVLink C2C [81]. Figure 2 illustrates these two memory design approaches. With discrete memory, CPU-GPU communication requires explicit data copying (I/O op-erations) [16, 69]; in UMA, all processors can directly access the same data without additional data movement. However, this approach requires a deep understanding of UMA hard-ware features and careful coordination between CPU and GPU to ensure both correctness and optimal performance. 

UMA hardware features. UMA is deeply integrated into SoC internals, so interconnect designs vary across vendors and even chip models (Figure 2). 

CPU-GPU Interconnection. The studied UMA platforms use a Ring or network-on-chip (NoC) fabric interconnect. For Ring interconnects, CPU cores and the GPU share a distributed last-level cache (LLC) accessed over the ring [44, 92]. This requires minimal SoC design changes but scales poorly. NoC connects them at the cluster level, scaling better to additional components [3]. In our NoC platforms, CPU caches are not directly accessible to the GPU as a shared cache tier. Some NoC platforms introduce a shared system-level cache above main memory (memory side cache, MSC) [17, 22]. These cache-sharing and coherence properties depend on platform design, rather than interconnect topology alone. 

Data Coherence. Cache coherence (CC) between the CPU and GPU provides a consistent shared-memory view and sim-plifies UMA programming. On Ring-interconnect platforms, the GPU, CPU cores, and the LLC all function as agents on a shared ring bus [42]. This enables them to participate in a unified cache coherence protocol that naturally extends the CPU’s own inter-core coherence mechanism, such as MESIF, although GPU private caches generally remain non-coherent with the CPU [30]. This coherence is managed automatically and is not exposed to the driver for configuration [70]. The studied NoC platforms use I/O coherency [17, 74], allowing the GPU to issue coherency transactions to the CPU subsystem. Coherent GPU reads can retrieve the lat-est data from CPU caches; coherent GPU writes invalidate stale CPU cache copies as required [12, 79]. All four target platforms provide only one-way coherence : GPU-initiated accesses can maintain consistency with CPU caches, but the CPU cannot reciprocally snoop or invalidate GPU caches. The cost of GPU-to-CPU coherence depends on the coher-ence implementation and cache organization. Raptor uses the ring’s shared-LLC coherence protocol, while the studied NoC platforms use I/O-coherency transactions with the CPU subsystem that can add memory-access overhead (§4.2). 

2.2 CPU-GPU Communication 

CPU-GPU communication is a key building block for het-erogeneous computing. It spans two purposes: data-plane transmission and control-plane coordination .1

Data-plane transmission. This covers producer-consumer transfers between CPU and GPU, including model parame-ters, inputs, and outputs. For example, during model infer-ence, data is transferred to and from the GPU at the start and end of task execution. Similar transfers occur in GPU rendering, 3D image processing, scientific computing, and autonomous driving. Data-plane transmission has two types: 

CPU-to-GPU and GPU-to-CPU transfer. The volume of trans-ferred data varies considerably—ranging from a few integers for simple inputs to gigabyte-scale model weights. The com-munication pattern is characterized by low frequency, as data transfers generally occur only at GPU task boundaries. 

Control-plane coordination. This involves the exchange of control information between the CPU and GPU, including

For example, in model offloading scenarios, the CPU iteratively prepares data for the GPU—such as loading per-layer parameters or a KV Cache— before launching the corresponding kernel. This unidirec-tional synchronization pattern is referred to as asymmetric synchronization . It can be effectively managed through a wait-based mechanism for task dependencies. Furthermore, some heterogeneous workloads (e.g., GPU filesystem) require more complex coordination like cross-device contention con-trol, where both the CPU and GPU must wait for each other at specific execution points to ensure correct operation se-quencing. This requires advanced synchronization primitives (barriers or locks) to enable CPU-GPU coordination. This pattern is referred to as symmetric synchronization . To main-tain tight coordination between the CPU and GPU during task execution, control-plane coordination involves small payloads (typically just control messages or flags) yet occurs much more frequently within GPU tasks. 

2.3 Memory Sharing 

CPU-GPU communication can be modeled as one processor (the sender ) transmitting a unit of data to another processor (the receiver ), where either the CPU or GPU can act as the sender or receiver. Memory sharing between them enables CPU-GPU communication. Two primary approaches exist for memory sharing: data copying and direct access .

Data copying. Analogous to pass-by-value in programming, this approach implements memory sharing through explicit copy operations between two individual memory regions. As shown in Figure 3, the sender first writes data to a designated memory region, and then the receiver copies this data into its own memory region and reads it. This approach imposes minimal demands on underlying hardware capabilities, mak-ing it broadly applicable to both discrete and unified memory architectures. However, this approach incurs overhead from additional memory copy operations and increases memory footprint by maintaining duplicate data copies. 

Direct access. This approach, akin to pass-by-reference , uti-lizes a physically shared memory region accessible to both sender and receiver, as shown in Figure 3. It eliminates copy operations and extra memory consumption. However, it re-quires direct CPU and GPU access to the same physical mem-ory region, a capability provided by UMA platforms. 

In the wild. Despite native support for direct access on UMA platforms, many existing systems fail to fully leverage this capability. Our analysis of popular open-source LLM infer-ence frameworks [95], including llama.cpp [31], Ollama [89], vLLM [120], and DeepSpeed [25], as well as general-purpose model inference frameworks, including PyTorch [98], Ten-sorFlow [114], TensorRT [83], and OpenVINO [49], reveals that these frameworks predominantly rely on data copying for weight loading and input/output processing. GPU runtimes provide APIs for direct access, and develop-ers of rendering and computation frameworks use them to optimize performance on UMA platforms. However, direct access is easy to implement incorrectly: missing cache flushes and memory barriers often result in data inconsistency be-tween CPU and GPU, or application crashes [60, 61, 87, 88]. Even with correct implementation, suboptimal approaches can greatly impact performance. For example, inadequate understanding of memory access characteristics may cause direct access to underperform data copying [86]. The model loading optimization for Apple UMA platforms in llama.cpp does not effectively bypass the copy operation. Similarly, improper synchronization granularity often introduces addi-tional overhead in control-plane coordination [35, 67]. 

Root causes and challenges. These problems stem from two factors. First, these systems were initially designed for discrete memory architectures. To reduce development effort, existing data copying implementations are directly adapted for UMA platforms. Second, substantial variations in hard-ware architecture, software interfaces, and performance across UMA platforms [108] mean that developers often lack the experience needed to efficiently implement memory sharing via direct access [14, 36, 74]. Achieving correctness and opti-mal performance on UMA platforms requires precise control over data visibility and consistency—a significant challenge in CPU-GPU heterogeneous environments. 

3 Target Platforms 

Our core study covers four platforms with one-way CC. The x86 Intel subset—Raptor, Arrow, and Lunar—spans Ring, NoC without MSC, and NoC with MSC, enabling comparisons within one driver/runtime ecosystem. Orin adds an ARM-based NVIDIA platform with NoC and MSC. 

3.1 Ring Interconnect: Raptor 

The Raptor platform is built around an Intel Core i5-14500 (Raptor Lake) processor with a Ring interconnect linking the CPU cores, GPU, and memory controller. Its 24 MB LLC is distributed across ring-connected slices and shared by CPU cores and the GPU [44]. The system has dual-channel DDR4-3200 memory and an integrated Intel UHD 770 GPU. Both the GPU and memory controller are integrated as agents on the ring bus. Memory requests leaving the GPU traverse the ring nodes hosting the LLC’s coherence agents, enabling coherent access to the shared LLC and memory. However,

this coherence is one-way, as the GPU’s private caches re-main non-coherent with the CPU [30]. The ring organization remains relevant in low-power, cost-sensitive products such as Intel Processor N-series (e.g., N150 and N250) [46, 51]. 

3.2 NoC Interconnect without MSC: Arrow 

The Arrow platform uses an Intel Core Ultra 285H (Arrow Lake) processor with a scalable fabric NoC interconnect. The CPU, integrated Intel Arc 140T GPU, and other agents connect at the cluster level. This architecture offers better scalability. The CPU’s LLC is shared within the compute tile and is not directly accessible to the GPU as a shared cache tier [47]. The system includes dual-channel DDR5-5600 mem-ory. Coherence transactions across the fabric maintain data consistency. This is also one-way: GPU-initiated accesses can maintain consistency with CPU caches, but not vice versa. The absence of an MSC makes this platform essential for evaluating how a system-level shared cache impacts perfor-mance. The NoC-without-MSC organization also appears in newer embedded devices, such as AMD Versal Prime Series Gen 2 models 2VM3104 and 2VM3654 [1]. 

3.3 NoC Interconnect with MSC: Lunar and Orin 

Lunar and Orin platforms feature a NoC interconnect and include an MSC, with one-way coherence. Apple SoCs [22, 125] and AMD APUs [121] also adopt this organization, but some coherence differences will be discussed in §7. 

Lunar. The Lunar platform, powered by an Intel Core Ultra 258V (Lunar Lake) processor, targets energy-efficient mobile computing with graphics and AI acceleration. The system includes an Intel Arc 140V GPU and LPDDR5-8533 memory. Its key feature is an 8 MB MSC—a cache logically located between the processors and main memory [17]. The MSC reduces main memory access delays. 

Orin. The Orin platform is a Jetson AGX Orin embedded sys-tem, built on an ARM Cortex A78AE CPU with an integrated NVIDIA Ampere GPU, and demonstrates these architectural trends in the ARM ecosystem. It also uses a scalable NoC interconnect and includes a 4 MB MSC to improve memory performance. By including it, we conduct a broader analysis of UMA behaviors beyond x86 architecture, providing a more comprehensive understanding of the underlying principles. 

4 Communication via Memory Sharing 

Analyzing the correctness and performance of CPU-GPU communication over UMA presents significant challenges due to two key factors. First, it requires cooperation between heterogeneous processors (CPU and GPU) with distinct hard-ware characteristics, across UMA platforms that vary in their interconnects and configurations. Second, CPU-GPU commu-nication serves different purposes, such as data-plane trans-mission and control-plane coordination, each with unique be-havioral patterns and requirements. To facilitate analysis, we decompose the execution flow of CPU-GPU communication via memory sharing into two stages: sending and receiving ,with unified memory serving as the boundary. These stages can be implemented independently and combined flexibly, enabling systematic analysis of correctness and performance. 

4.1 Correctness of Memory Sharing 

Communication via memory sharing involves four opera-tions: 

• Bind establishes a shared memory region and configures its attributes separately for the sender and receiver. 

• Write populates the memory with data from the sender. 

• Read retrieves data from the memory for the receiver. 

• Unbind revokes access permissions and frees memory. 

Methodology. We model memory sharing as two stages: sending (Bind-Write-Unbind) and receiving (Bind-Read-Unbind). Each stage involves a single processor (CPU or GPU) and can be configured and implemented independently (e.g., memory attributes). We empirically test candidate send-ing and receiving combinations in both CPU–GPU directions under selected memory configurations, keeping control state separate from the tested data. A single-thread persistent GPU kernel participates in each test. After reading the previous payload, the receiver checks every word of a new determinis-tic payload written by the sender. The verdict is fixed before kernel exit. An exact match records a successful transfer; sta-ble failure requires reproducible mismatches after bounded retries. Timeouts and infrastructure errors are inconclusive, while unsupported configurations are skipped. These tests evaluate data visibility between a single sender and receiver. Write-write contention is outside these tests; atomic synchronization and contended locks are examined separately (§4.1.4). We assume that the driver and hardware apply the requested page size, cache policy, and coherence settings. The results provide empirical evidence for the tested platforms, configurations, and sharing model, without formal guarantees for general CPU–GPU shared-memory interac-tions. The testing tool is included in the libumsh artifact. 

4.1.1 Bind and Unbind 

Bind allocates a shared memory region from unified physi-cal memory and configures its memory attributes by setting page tables of both the CPU and GPU, which may act as the sender and receiver. Three critical attributes collectively de-termine sharing semantics and performance characteristics. 

Page Size. Both CPU and GPU support multiple page sizes. The CPU typically uses a small page size (4 KB) by default. In contrast, the GPU’s page size depends on the kernel-space driver and user-space runtime implementation. While most GPUs support common page sizes, they typically prefer a large page size (2 MB) for better streaming memory access performance [29, 55]. When CPU and GPU share memory, the shared region must satisfy the page-alignment require-ments of both the CPU and GPU [43].

4.1.2 Write 

To ensure data is properly written to memory and visible to the receiver, three Write implementations are available. Figure 4 illustrates these implementations, and Table 1 lists the correct combinations of them and memory attributes. 

Write-Alone (WA). A write instruction (e.g., mov or store )can correctly write data to memory only when configured as UC. However, if the receiver has CC enabled, Write-Alone also functions correctly with memory configured as WB. 

Write-then-Flush (WF). After writes, flushing instructions en-sures data is written back to shared memory, even with WB caching. Two approaches can evict cached data: 1) device-specific flush instructions, and 2) external flush commands. Flush instructions are widely supported on CPUs (e.g., cl flushopt on x86 and dc on ARM), although GPU support varies across platforms. Arrow and Lunar provide lsc_-fence [41], while Raptor and Orin do not include such in-structions in official documents or compilers. On our target platforms, the CPU driver can issue external flush commands to evict cached data to memory for the GPU via MMIO, while the reverse is not supported. On all three Intel GPUs, the flush command is enqueued as a task in the hardware queue and processed in order. Upon completion of the current ker-nel, data written by that kernel is flushed from the GPU’s internal cache to memory. In contrast, on Orin, a flush com-mand is triggered by writing to a special register (BAR), which suggests this process operates independently of ker-nel execution. 

Write-Bypass (WB). Certain specialized instructions enable di-rect memory writes that bypass the private cache hierarchy, ensuring correct operation on memory configured as WB. For CPUs, non-temporal store instructions (e.g., movntdq )write directly to memory and reduce cache pollution. How-ever, these instructions serve as hints rather than strict guar-antees. Furthermore, I/O devices (e.g., SSD) can bypass the cache and write to memory directly via DMA. For GPUs,

4.1.3 Read 

To ensure data from the sender is properly read, three Read implementations are available to retrieve data from memory. Figure 4 illustrates these implementations, and Table 1 lists the correct combinations of them and memory attributes. 

Read-Alone (RA). A read instruction (e.g., mov or load ) can correctly read data from memory only when configured as UC. However, if the sender has CC enabled, Read-Alone also functions correctly with memory configured as WB. 

Read-after-Inval (RI). This implementation first invalidates the private cache, then performs read instructions on mem-ory configured as WB. Similar to Write-then-Flush, two ap-proaches can invalidate cached data: (1) device-specific in-validation instructions, and (2) external invalidation com-mands. Due to data integrity concerns, most platforms do not provide dedicated invalidation instructions (or commands). Instead, they rely on flush instructions (or commands) to implement invalidation, even though no actual writeback occurs. Among our target platforms, only the ARM CPU provides the dc ivac instruction, which invalidates cache lines within a specified region without writeback. 

Read-Bypass (RB). This implementation mirrors Write-Bypass, its counterpart for direct memory writes. I/O devices use DMA to bypass the cache and read memory directly, while GPUs use load instructions with cache-bypass modifiers. 

4.1.4 Acquire and Release 

To enable sophisticated CPU-GPU coordination (e.g., locks and barriers), control-plane symmetric synchronization re-lies on two atomic operations built on memory sharing: 

• Acqire reads the current state to check availability and conditionally writes to establish ownership. 

• Release writes to the state to relinquish ownership, mak-ing it available once more. Traditional cross-device implementations of these operations rely on a delegation mechanism [67], where the CPU serves as an arbiter to handle acquisition and release requests from the GPU, or vice versa. 4.2 Performance of Memory Sharing 4.2.1 Memory Binding 

Memory binding time represents substantial overhead (about 50%) in scenarios like model loading, where each CPU-GPU communication requires one memory binding. Binding time consists of three parts: memory allocation and page table configuration for both the CPU and GPU. Memory allocation time depends heavily on memory utilization, while the page table configuration process and performance characteristics remain consistent across the CPU and GPU. Therefore, we fo-cus on examining page table configuration time for the GPU. As shown in Figure 5, page size primarily influences mem-ory binding performance and varies across UMA platforms. Cache policy and data coherence settings have negligible impact since these configurations are applied per PTE. For large memory regions exceeding 32 KB, the default 4 KB page size incurs significant time overhead, dominated by PTE population. Hugepages (2 MB) show substantial ad-vantages. For small memory regions fitting within a single physical page, performance varies across platforms. The In-tel drivers on Raptor and Arrow show comparable times for 4 KB and 2 MB pages, while 4 KB pages significantly outper-form 2 MB pages on Lunar and Orin (reaching about 5 × on Orin). This happens because the driver scans the input mem-ory range before modifying page table entries to determine page size and PTE count. Registering large pages forces the driver to process a full 2 MB-aligned region even for small memory regions, introducing unnecessary overhead. Since 4 KB pages can incur nearly 100 × higher bind over-head and degrade access performance due to TLB pressure [7, 52, 129], GPU runtimes typically enforce a 2 MB minimum al-location. Intel Arc GPUs. Arrow and Lunar feature high-performance Intel Arc GPUs [17, 50]. They support fine-grained control over the caching of read/write instructions and explicit cache management [48]. RI/Inst supports both inter-kernel and intra-kernel boundaries. We implemented RI/Inst by performing one flush per block with intra-block synchronization. This ap-proach balances performance and generality: it reduces inval-idation frequency compared to per-thread invalidation, while eliminating the need for implementations to avoid deadlocks in global synchronization scenarios. However, even with these optimizations, RI/Inst is still the slowest option on both Arrow and Lunar.

4.2.4 High Contention 

Control-plane coordination suffers from performance degra-dation due to massive contention on small shared data, such as concurrent reads on the GPU side. As shown in Figure 8 (left), on all platforms, Read-Bypass ( RB) performance de-grades sharply as thread count increases. We evaluated three approaches to limit concurrency on Orin (see Figure 8 right): 

• Baseline uses no barriers—all threads read concurrently. 

• Block enables block-level barriers—only one thread in each block reads the shared data. It offers a simple imple-mentation that scales well for thread counts up to 1,000. 

• Grid enables grid-level barriers—only one thread across all blocks reads the shared data. It requires support for Cooperative Groups [78] or atomic operations with dead-lock avoidance techniques [32]. While incurring a fixed overhead, this approach offers stable performance and outperforms Block when exceeding 1,000 threads. 

• Kernel uses a separate kernel with one thread to read shared data. Its performance is consistently lower than Grid due to kernel launch overhead, but it avoids deadlock risks and requires no special instructions. 

Implications. High GPU concurrency severely degrades per-formance in control-plane coordination, making contention management essential. We recommend block-level barriers to mitigate contention when thread counts are below 1,000. For higher concurrency, grid-level barriers are preferred to elimi-nate contention entirely, though they require more complex implementations. The kernel-level approach should be used only when source code modification is infeasible (Finding 4). 

5 libumsh and Platform Extension 

Drawing on these findings, we built libumsh , a library that delivers correct and efficient CPU-GPU memory sharing across UMA platforms. Developers compose sending and re-ceiving processes from six core operations: bind , unbind ,

write , read , acquire , and release . On top of these, 

libumsh provides high-level helpers for control-plane co-ordination: wait and set (built on read and write ) and 

lock and unlock (built on acquire and release ) for asymmetric and symmetric synchronization, respectively. Applications specify the transfer direction, I/O origin, and inter-kernel or intra-kernel boundary. Given these require-ments and the compile-time target platform, libumsh auto-matically selects default Read and Write implementations and cache and coherence settings (Table 2). The backend handles platform-specific binding and cache maintenance. We deploy libumsh on all four UMA platforms (see §3). It builds on the stock Intel GPU runtime on Raptor and the CUDA runtime on Orin; Arrow and Lunar additionally require custom runtime modifications to expose the fine-grained CC control APIs. The core logic spans about 1,000 lines of code (LoC). libumsh also ships with a companion suite of correctness tests and performance benchmarks for characterizing hardware behavior on new platforms. With compile-time defaults, template-based backend dispatch, and inlined functions, libumsh adds less than 1% overhead over manually applying the same implementation choices. 

5.1 Porting Workflow 

Extending libumsh to a new UMA platform requires two tasks: identifying which platform properties behind our find-ings still apply on the target, and learning how to configure each through the APIs exposed by its driver and runtime. We use the correctness and performance suite from §4 to validate behavior, and rely on AI-assisted reading of code and doc-umentation to narrow the search. • Locate APIs. AI-assisted scanning of runtimes, drivers, kernel modules, and documentation surfaces the APIs that configure page size, cacheability, and coherence, and flags internal behaviors with no public API.

7 Discussion 

Limited visibility and control through OS abstractions. 

OS abstractions simplify development but hide critical pa-rameters (page size, device CC status, and cache policy) from user space. For example, THP treats hugepage allocation as a best-effort hint and silently falls back to 4 KB pages under fragmentation, causing unpredictable performance 

> 13 Jinrong Yang et al.

drops [65, 94]. libumsh mitigates the worst cases by pre-faulting THP regions (§4.2.1) and patching the driver to ex-pose hidden parameters (§5), but the underlying lack of vis-ibility remains a systemic obstacle to correct and efficient CPU-GPU memory sharing. 

The evolution and caveats of hardware coherence. Hard-ware CC reduces the software burden of memory sharing, but using it correctly still demands platform-specific analysis. The shift from one-way to two-way coherence appears to simplify development, yet in practice it complicates analysis and optimization. AMD’s two-way coherence omits the GPU L0/L1 caches and still requires Write-Bypass instructions for correctness [73]; NVIDIA explicitly recommends bench-marking because of potential overheads [79]. The DGX Spark extension in §5.2 illustrates why a wider coherence domain still requires validation of cache coverage and performance. 

Beyond CPU-GPU memory sharing. Our methodology applies to other heterogeneous components in UMA plat-forms, such as NPUs and ASICs. While the logic for ana-lyzing correctness and performance is universal, most ISAs and runtimes remain closed and undocumented [21, 37, 57]. The AI-assisted porting workflow (§5.1) narrows the search for controls, as the DGX Spark extension demonstrates. Ap-plying it to other accelerator classes still requires access to their hardware controls and validation of cache visibility and synchronization behavior. 

8 Related Work 

Memory performance of UMA platforms. Prior research on UMA memory performance can be categorized into three categories. First, many studies examine isolated architectural features, such as interconnects [26, 105, 112], memory ac-cess [13, 64, 96, 125], and cache coherence [2, 5, 6, 77, 97, 130]. Second, most are designed for specific platforms, limiting their applicability across different architectures [24, 30, 34, 40, 54, 121]. Third, while some cross-platform analyses ex-ist [18, 74, 113, 118, 128], they either focus on performance data without addressing correctness, or they target narrow application scenarios. Our analysis provides a comprehen-sive methodology that spans both correctness and perfor-mance across diverse platforms and use cases. 

CPU-GPU communication. Prior research has extensively investigated and optimized CPU-GPU communication. For data-plane transmission, researchers have used unified mem-ory to achieve transparent data transfer between the CPU and GPU [4, 28, 56], or optimize transmission for specific scenarios [72, 106]. For control-plane coordination, opti-mization efforts have mainly focused on hybrid comput-ing [20, 62, 68, 124, 126, 127] and task scheduling [23, 108]. Cross-platform libraries such as Kokkos [63] abstract mem-ory spaces, while CUDA [79] provides vendor-specific al-location and registration APIs. However, these efforts are largely conducted in isolation. Our work provides a com-prehensive analysis of the application-level requirements governing CPU-GPU communication and a library that au-tomatically selects implementations across platforms. 

9 Conclusion 

This paper systematically characterizes the correctness and performance of CPU-GPU memory sharing on unified mem-ory architectures. By decomposing sharing into memory binding and paired write and read operations, our methodol-ogy exposes how page size, cache policy, coherence, MSC, and contention interact across four representative platforms. Our correctness tests and four performance findings show why direct access alone does not ensure correct and efficient sharing: implementation choices must account for both the platform’s memory hierarchy and the visibility and synchro-nization requirements of each sharing pattern. Guided by this, we developed libumsh , which encapsu-lates platform-specific implementations behind high-level sender-receiver operations and automatically selects defaults according to application requirements. Its application to nine real-world systems demonstrates benefits for both data-plane transmission and control-plane coordination. The NVIDIA DGX Spark extension applies the same methodology and high-level APIs to a platform with two-way coherence. To-gether, the methodology, validation suite, and library pro-vide a reusable approach to supporting new UMA platforms through correctness testing, performance measurement, and adaptation of platform-specific implementations.

We hypothesize that this pattern is a direct consequence of implementing two-way CC using the AMBA CHI protocol. In CHI terminology, one-way CC corresponds to attaching the GPU as an IO-coherent request node (RN-I, equivalent in role to an ACE-Lite agent): the GPU can issue snoopable requests that invalidate CPU caches, but its own cache is not visible to the fabric and, per the CHI specification, does not 

receive snoops. Two-way CC instead attaches the GPU as a fully coherent request node (RN-F), which by definition holds a hardware-coherent cache, must respond to all snoop transactions, and is registered in the Home Node’s directory. Under WB, every cache line that enters the GPU L2 therefore incurs directory registration on fill, ownership acquisition before a store can retire, and de-registration on eviction— traffic that one-way CC avoids entirely because the GPU L2 is not a participant in the coherence domain. Under UC, the GPU L2 is bypassed, so no cache-line transitions occur and neither CC policy pays this cost.

GPU contention. Figure B.5 shows how Spark handles GPU-side contention when many GPU threads poll the same shared location through RB. The baseline without barriers remains stable at small and moderate thread counts, but even-tually collapses as concurrent requests concentrate on one memory location. Barrier-based throttling is therefore still necessary: block-level barriers reduce thread-level contention with low fixed overhead, while grid-level barriers remove almost all concurrent polling at the cost of stronger syn-chronization requirements. On Spark, however, the kernel-level approach has a much smaller fixed overhead than on Orin, so it becomes the preferred implementation for high-contention polling. Block-level barriers remain the next-best choice when launching a separate polling kernel is unde-sirable or the polling logic must remain inside the original kernel. 

Appendix B.2 Case Study 

We reran the Orin-based case studies on Spark through the same platform-independent libumsh interfaces. No Spark-specific application code is needed once the backend exposes the required operations. 

Hybrid inference. Figure B.6 shows that the Orin opti-mization for hybrid inference also applies to Spark: replac-ing EdgeNN’s runtime-based coordination with libumsh ’s direct-access wait /set signaling reduces normalized op-erator time by 14.7% on average relative to EdgeNN. The gain is smaller than on Orin because Spark’s lower kernel launch overhead leaves less control-plane overhead for the signaling optimization to remove. 

GPUfs and file locking. Figure B.7 shows that the Orin control-plane optimizations for GPU file access also carry over to Spark. In GPUfs, kernel-wide file operations still create GPU-side polling contention, so replacing block-level 

throttling with grid-level barriers lowers synchronization time by up to 5.1% at high block counts. For file locking, replacing the GPU-resident delegation lock with a direct-access CAS lock lets the CPU and GPU coordinate through shared-memory atomics instead of RPC. This reduces lock overhead by about 85%, 37%, and 26% in the CPU-heavy, GPU-heavy, and balanced configurations, respectively.
