ABSTRACT
Large language model serving is increasingly limited not only by model size and GPU speed, but also by scheduling
during autoregressive decoding, where continuous batching interleaves requests at token granularity as sequences
arrive and finish. We study whether lightweight scheduling policies can improve latency-throughput tradeoffs
without changing model architectures, kernels, or deploying learned schedulers. We implement a Python/PyTorch
continuous-batching testbench with real Hugging Face execution and evaluate eight policies across 1,152 GPU-
model-scheduler-workload runs using ShareGPT-derived traffic, six Qwen, Gemma, and Mistral models, and
Modal L40S, A100, and H100 GPUs. Scheduler choice changes throughput, TTFT, completion latency, and tail
behavior under fixed model, GPU, workload, batch size, and prefill budget. Aging shortest-prompt-first is the
strongest practical baseline in many L40S and mixed-workload settings, while oracle remaining-length scheduling
shows that job-size knowledge alone is insufficient because batching and hardware effects also shape performance.

INTRODUCTION
Serving large language models is fundamentally different
from serving traditional neural networks because generation
is autoregressive. A request is not completed by a single
forward pass; instead, the system repeatedly executes de-
code steps, each producing one new token while carrying
forward a growing key-value cache. In an online setting,
many requests with different prompt lengths, output lengths,
and arrival times compete for the same GPU. This makes
scheduling a first-order systems problem: the runtime must
decide which requests receive service at each decode step
while keeping the GPU sufficiently full to maintain high
throughput.
Continuous batching has become a standard technique for
improving LLM serving efficiency. Rather than waiting
for a fixed batch of requests to finish together, the serving
system admits new requests as old requests complete. This
improves utilization and reduces idle time under realistic
online traffic. However, continuous batching does not elim-
inate head-of-line blocking. If long generations remain in
the active batch for many decode iterations, they can delay
shorter jobs that would otherwise finish quickly. A naive
first-in, first-out policy is simple and fair by arrival order,
but it can be inefficient when request lengths vary widely.
This project investigates a practical question: how much
can continuously batched LLM serving improve using only
lightweight scheduling changes? Rather than proposing a
new model architecture, a new inference kernel, or a full
production serving stack, we isolate the scheduling policy
as the variable of interest. We compare simple policies
that use request metadata such as prompt length, target
or estimated remaining decode work, service tier, waiting
time, and observed completion statistics. The goal is not
to find a universally optimal scheduler, but to understand
how scheduler choice affects latency, throughput, and tail
behavior across workloads, models, and GPUs.
This research makes three contributions:
1. We implement a pluggable continuous-batching test-
bench for comparing LLM serving schedulers under
fixed runtime constraints. The testbench executes real
Hugging Face causal language models using PyTorch,
batched prefill, cached one-token decode, and per-
request metric logging.
2. We construct a ShareGPT-derived workload suite with
bursty, low-load, steady, uniform, and mixed short/long
request patterns, allowing scheduler behavior to be evalu-
ated under both benign and head-of-line-blocking-heavy
traffic. The custom dataset includes 22 categories of
tests, each with 8 test cases (100+ requests). The dataset
is also made open-source for benchmarking.
3. We evaluate eight scheduling policies across six open-
weight models and three GPU classes, measuring
throughput, time-to-first-token, completion latency,
p95/p99 latency, batch efficiency, starvation behavior.

PROBLEM DEFINITION AND RESEARCH
QUESTIONS
2.1
Continuous-Batching Decode Scheduling
In autoregressive LLM inference, each request consists of
an initial prefill stage followed by a decode stage. During
prefill, the model processes the prompt and initializes the
request’s KV cache. During decode, the model repeatedly
generates one token conditioned on the previous tokens.
Since decode proceeds incrementally, the serving runtime
has repeated opportunities to choose which requests to in-
clude in the next GPU step.
The runtime maintains future requests that have not yet ar-
rived, active requests that are eligible for service, and com-
pleted requests. When the wall-clock replay time reaches a
request’s arrival time, the request becomes active. At each
decode step, the scheduler ranks active requests and selects
at most max_batch_size requests for service. In our ex-
periments, max_batch_size is fixed at 16. For requests
receiving their first service, the testbench performs batched
prefill; for requests with an existing KV cache, it performs
cached one-token decode.
The scheduler affects at least four outcomes. It affects
throughput because larger or more stable batches improve
GPU utilization. It affects time-to-first-token because ad-
mission and first service determine how quickly a user sees
an initial response. It affects completion latency because
scheduling determines how long each request takes from
arrival to final token. It also affects tail latency and fairness
because aggressive short-job policies can improve average
latency while delaying long or low-priority requests.
The core challenge is that a deployable scheduler usually
does not know the true remaining work of a request. Prompt
length is visible at arrival time, but output length is of-
ten unknown. In our trace-driven testbench, target output
length is known from the ShareGPT response length and
is used to determine when a request completes. This lets
us compare both practical heuristics and an oracle-style
shortest-remaining-tokens policy that uses the trace-derived
remaining output length.
2.2
Research Questions
RQ1: Do short-job-aware schedulers improve latency
and throughput compared with FIFO continuous batch-
ing?
FIFO is attractive because it is simple and pre-
dictable, but it can allow long requests to occupy decode
capacity while shorter requests wait. Policies inspired by
shortest-job-first or shortest-remaining-processing-time may
reduce mean and tail latency by finishing short requests ear-
lier.
RQ2:
How much does estimation quality matter?
Some policies use visible prompt length as a proxy for
job size, while others estimate remaining decode length
from prompt length, request class, and online observations.
We evaluate whether these estimates improve performance
and whether inaccurate estimates can hurt compared with
simpler heuristics.
RQ3: Does the best scheduling policy depend on hard-
ware, model, and workload?
GPU architectures differ
in memory bandwidth, compute throughput, and batching
behavior. Models differ in size, context handling, and de-
code cost. Workloads differ in arrival pattern and length
distribution. We therefore expect no single scheduler to
dominate universally.

RELATED WORK
Orca introduced iteration-level scheduling for transformer
serving, showing that generative inference can benefit from
scheduling at the granularity of decode iterations rather than
entire requests (Yu et al., 2022). This idea is central to
modern continuous batching: requests can enter and leave
the batch dynamically, allowing the system to maintain uti-
lization under variable-length generation. Our work builds
on this observation, but focuses on comparing lightweight
policies inside a controlled continuous-batching testbench
rather than designing a new distributed serving system.
FastServe further shows that preemption and scheduling are
central to interactive LLM serving, using token-level pre-
emption and a skip-join multi-level feedback queue sched-
uler to reduce head-of-line blocking (Wu et al., 2023). Our
study differs by holding the serving mechanism fixed and
comparing lightweight scheduler choices across models,
GPUs, and workload families.
vLLM and PagedAttention showed that KV-cache mem-
ory management is critical for high-throughput LLM serv-
ing (Kwon et al., 2023). By reducing memory fragmenta-
tion and enabling efficient paging of KV-cache blocks, such
systems increase the number of concurrent sequences that
can be served. Our project is complementary and builds
on the same core insight: once a continuous-batching ab-
straction makes many concurrent sequences feasible, sched-
uler choice becomes a practical lever for shaping latency-
throughput tradeoffs. Rather than replacing systems like
vLLM, we study which active requests should receive de-

code service under continuous batching, providing action-
able guidance that can be layered on top of strong execution
engines.
Recent serving systems also show that the interaction be-
tween prefill, decode, and batching policy is a first-order
performance issue. SARATHI uses chunked prefills and
decode-maximal batching to reduce prefill/decode imbal-
ance (Agrawal et al., 2023), while DistServe disaggregates
prefill and decode resources to optimize TTFT and TPOT
service objectives (Zhong et al., 2024). These systems mo-
tivate our emphasis on scheduler behavior, although our
evaluation intentionally keeps the serving architecture fixed.
Classical scheduling theory suggests that shortest-job-first
and shortest-remaining-processing-time can reduce mean
completion time when job sizes are known or well estimated;
Schrage’s (Shortest Remaining Processing Time) result is a
canonical reference for this framing (Schrage, 1968). LLM
serving complicates this because request cost depends on
both prompt length and generated output length. Recent
learning-based work, including learning-to-rank approaches
for LLM scheduling, predicts output length or relative job
cost to approximate these policies (Fu et al., 2024). Our
project explores a lower-overhead design space: heuristic
policies based on prompt length, trace-derived remaining
length, online output-length estimates, aging, and service-
tier fairness.

SYSTEM OVERVIEW
Figure 1 shows the architecture of our evaluation system.
The system is a replay-based continuous-batching LLM
serving testbench. It takes ShareGPT-derived workload
cases, replays request arrivals according to the case def-
inition, ranks active requests with a pluggable scheduler,
executes the selected batch on a GPU-backed Hugging Face
model runner, and logs per-request and per-step metrics.
The system has four main components. The workload gener-
ator builds scheduler-ready cases from ShareGPT-style con-
versations. It extracts human-to-assistant request/response
pairs, tokenizes prompts and responses, filters invalid or
oversized samples, labels requests as short, medium, or
long, assigns arrival times, and emits workload cases. The
scheduler receives snapshots of waiting, active, and com-
pleted requests and returns an ordering of active request IDs.
The model execution layer uses PyTorch and Hugging Face
Transformers to run batched prefill and cached one-token
decode. The metrics logger records request-level statistics
such as queue delay, TTFT, completion latency, generated to-
kens, scheduled steps, decode time, service tier, and request
class, along with aggregate throughput and batch efficiency.
The same workload cases are replayed for every scheduler
under fixed controls. The maximum decode batch size is
16. The prefill-token budget is 4096 padded tokens per pre-
fill sub-batch, implemented as max prompt length in the
sub-batch times the number of prefilling requests. These
controls ensure that performance differences primarily re-
flect scheduler behavior rather than changes in workload
composition or batch constraints.

METHODOLOGY
5.1
Trace-Driven Workload Construction
We evaluate on ShareGPT-derived conversational work-
loads (Aeala, 2023). The workload pipeline builds cases
from the Aeala/ShareGPT_Vicuna_unfiltered
ShareGPT-style dataset using the Hugging Face datasets
library. Prompts and target responses are tokenized with the
Hugging Face GPT-2 tokenizer for workload construction.
Samples with fewer than four input or output tokens are
removed, and prompts or responses above the 4096-token
source cap are filtered out. The source pool is deduplicated
and trimmed to 50,000 cleaned request records.
Each request stores the prompt, input-token count, target
output-token count, arrival time, priority class, service tier,
and source metadata. Priority class is assigned from prompt
length: short requests have fewer than 128 input tokens, long
requests have more than 1024 input tokens, and medium
requests fall between those thresholds. The target output-
token count comes from the ShareGPT response length.
During model execution, this target length determines the
default stopping point, subject to model context limits and
the configured per-request generation cap.
The workload generator can emit eight ShareGPT-derived
workload categories and 22 seeded cases per category, for
176 total generated cases. The final reported analysis uses
one representative seeded case from each category, so the
reported run matrix is at the GPU-model-scheduler-category
level rather than an average over all 22 seeds. The cate-
gories stress different scheduling behaviors: steady short
traffic, steady mixed traffic, bursty conversational traffic,
bursty long-request traffic, flash-crowd spikes, low-load
traffic, short/long mixes, and a uniform baseline. Poisson
arrivals are generated with exponential interarrival times,
while bursty workloads use clustered arrivals with random
intra-cluster spacing. This gives a mix of average-case, low-
contention, and head-of-line-blocking-heavy workloads.

step, they rank active requests and the runtime serves the
first max_batch_size requests in that ordering. Table 1
summarizes each priority signal. Unless otherwise stated,

id.

5.3
Continuous-Batching Testbench Implementation
The testbench is implemented in Python 3.11 using PyTorch
and Hugging Face Transformers on Modal GPU workers.
The model runner loads each model with Hugging Face
APIs, performs batched prefill with cached KV state for
newly admitted requests, and then runs one-token greedy
decode for the selected active batch at each scheduling step.
The execution is hybrid: arrivals and target output lengths
are trace-driven, but model execution is real. Requests stop
after reaching the trace-derived target output length, capped
by model context and a 1024 generated-token limit, so every
scheduler receives the same intended work.
The runtime owns request state, arrival release, prefill split-
ting, decode execution, timing, and metric logging. The
scheduler only sees request metadata and runtime progress
through SchedulerSnapshot objects and returns an ordering
of active request IDs, which makes each policy comparable
under identical model, case, batch, and prefill settings.
5.4
Adopted Components and Implemented
Components
To avoid conflating infrastructure with our contribution, we
separate reused components from the artifacts we imple-
mented for the project.
We adopted the ShareGPT-style conversational data source,
Hugging Face tokenizers and model-loading APIs, PyTorch
tensor execution, Modal GPU infrastructure, and open-
weight Qwen, Gemma, and Mistral models. We also adopt
the general continuous-batching abstraction used by modern
LLM serving systems as the conceptual setting.
We implemented the workload curation pipeline, request-
class labeling, arrival-process generation, scheduler API,
eight scheduler policies, continuous-batching testbench,
Hugging Face prefill/decode runner, Modal experiment run-
ner, and metrics collection. The repository also contains
optional Triton and torch.compile kernel-proxy code,
but kernel optimization was not part of the final scheduler
evaluation. The final project scope is an empirical scheduler
study, not a kernel optimization paper.

6.2
Experimental Controls
For each GPU and model setting, every scheduler is eval-
uated on the same representative workload cases. We fix
max_batch_size at 16 and max_batch_prefill_
tokens at 4096. The final analysis contains 1,152 exe-
cuted GPU-model-scheduler-category runs: three GPUs, six
models, eight schedulers, and eight workload categories.
Each reported category run uses the same selected work-
load case for all schedulers in that GPU-model setting; it
is not an aggregate over the 22 available seeds. The model,
request arrivals, target output lengths, and runtime limits
are held constant while the scheduler changes. This control
is important because otherwise a scheduler might appear
better simply because it saw easier traffic or admitted larger
batches.
6.3
Metrics
Throughput is measured as generated tokens per second over
wall-clock runtime, with completed requests tracked per run.
Time-to-first-token measures arrival-to-first-token respon-
siveness, mean completion latency measures arrival-to-final-
token time, and p95/p99 latency captures tail user experi-
ence, especially in mixed workloads where mean latency
can improve while long or unlucky requests worsen. Batch
efficiency uses average batch size, decode-step count, and
average decode-step time to show whether a scheduler im-
proves queueing behavior, GPU utilization, or both. Fairness
and starvation behavior are evaluated through request-length
breakdowns, service-tier behavior, and mixed short/long
workloads.

RESULTS AND ANALYSIS
We organize the results around the three research questions.
First, scheduler choice changes the latency-throughput fron-
tier: runs with the same model, GPU, workload family,
batch limit, and prefill budget land at different points de-
pending only on the scheduler. Second, short-job-aware
policies are often beneficial, but the strongest versions in-
clude aging or fairness mechanisms to avoid starving longer
requests. Third, scheduler behavior is hardware-dependent;
policies that are competitive on one GPU are not necessarily
best on another.
7.1
Scheduler Choice Shifts the Latency-Throughput
Frontier
Figure 2 shows the latency-throughput frontier across GPU,
model, and scheduler runs. Each point averages across work-
load categories for one GPU-model-scheduler configuration.
Points with lower p95 latency and higher throughput are
preferred. Faceting by GPU with independent axis ranges
makes within-GPU model and scheduler variation easier
to read, while the model markers preserve the model-level
variation that drives much of the frontier. Within these
model/GPU envelopes, scheduler color still shifts points
toward or away from the efficient region, indicating that
scheduling policy is a meaningful performance knob even
without changing the model or serving stack.
Model size and GPU type strongly affect absolute perfor-
mance. Smaller models and faster configurations tend to
occupy the high-throughput, lower-latency region, while
larger or slower configurations move toward lower through-
put and higher p95 latency. The scheduler effect is smaller
than the model/hardware effect, but it is still visible within
each region. This is the main empirical pattern: scheduling
is useful, but it should be tuned against the target model,
hardware, workload mix, and metric.
Figure 3 shows why TTFT and completion latency must
be reported together. The left panel shows that scheduler-
workload-GPU combinations spread substantially in both
dimensions, especially under bursty traffic. The right panel
summarizes this variation with scheduler means: short-job-
aware policies such as shortest prompt first and aging SPF
move left by reducing average TTFT, but they do not al-
ways minimize completion latency. FIFO, service-tier pri-
ority, and longest-prompt-first can have slower first-token
response while remaining competitive on completion la-
tency. A scheduler evaluation that reports only one of these
metrics would miss this tradeoff.

7.3
Better Estimates Do Not Always Produce Better
Schedules
RQ2 asked whether estimation quality matters. Tables 2
and 3 show that it does, but more complex estimates do not
automatically dominate simpler heuristics. Prompt length
is an imperfect proxy for total request cost, yet shortest
prompt first and aging SPF perform well in several set-
tings. Estimated shortest tokens first and adaptive fair LCB
are competitive but not universally best. Most importantly,
shortest remaining tokens first has oracle-style access to
trace-derived remaining output length, yet it often fails to
dominate and can hurt tail latency. The takeaway is that
scalar job-size minimization is not the whole objective in
GPU serving: batch stability, prefill behavior, cache pres-
sure, aging, and fairness also matter.
7.4

lower-latency region, while A100 and H100 runs occupy
different parts of the frontier and show different scheduler
ordering. This means scheduler choice should not be treated
as a fixed algorithmic fact independent of the deployment
target.

DISCUSSION AND LIMITATIONS
This project shows that lightweight scheduling can improve
LLM serving behavior, but the evaluation is still a controlled
testbench rather than a full production serving stack. Produc-
tion systems may add admission control, KV-cache eviction,

and network variability. The ShareGPT-derived workload
suite also may not match code generation, long-document
summarization, or agentic traffic. Because our workloads
are replay-based, they do not model feedback effects such
as users cancelling slow requests or traffic shifts caused by
streaming responsiveness.
The testbench is trace-driven with respect to output length.
This keeps the target work fixed across schedulers, but gives
shortest remaining tokens first more information than a real
online scheduler would normally have. We measure serving
latency and throughput, not semantic output quality, and
kernel optimization is not part of the evaluated contribution.
The practical deployment implication is to treat the sched-
uler as a low-cost tuning parameter rather than a universal
default: FIFO and service-tier priority remain useful for
predictability, aging SPF is strong for interactive latency
under mixed workloads, and estimated or adaptive policies
should be validated on target traffic.
Key takeaways.
RQ1: short-job-aware scheduling of-
ten improves latency and sometimes throughput, especially
when aging prevents long-request starvation. RQ2: better
length estimates help only when they preserve batching sta-
bility and fairness; oracle remaining length is not enough by
itself. RQ3: the best scheduler changes with GPU, model,
and workload, so serving systems should expose scheduling
as a deployment-time control.

CONCLUSION
This project evaluates lightweight scheduling policies for
continuously batched LLM serving across workloads, mod-
els, and GPUs. Using a testbench with real batched prefill
and KV-cache decode, we compare eight schedulers on
ShareGPT-derived workloads. The key result: scheduler
choice materially affects throughput and tail latency even
under fixed system settings. Aging shortest-prompt-first is
a strong practical baseline, especially on L40S and mixed
workloads, but the best choice is deployment-dependent.
Oracle remaining-length results show job-size knowledge
alone is insufficient—batching and hardware effects also
matter—so scheduling should be treated as a workload-
aware deployment parameter.
