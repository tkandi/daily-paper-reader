# ProvQML: Efficient Provenance Capture for Machine Learning as Recursive Aggregate SQL [Extended Version] 

NKECHI J. AKINWALE, University of Cincinnati, USA 

SEOKKI LEE, University of Cincinnati, USA Expressing ML algorithms as recursive aggregate SQL queries over distributed systems enables large-scale declarative data analytics, yet no existing system supports scalable provenance capture, necessary for ML explainability. We present ProvQML, a provenance-aware recursive aggregate SQL engine that efficiently captures fine-grained provenance while evaluating ML algorithms as recursive aggregate queries. We capture two types of provenance: (i) local provenance that records the contribution of each training instance to gradient computation at a specific model state, and (ii) global provenance that encodes the sequence of model parameter updates across the iterations. Extensive experiments on widely used ML datasets demonstrate that our approach efficiently captures both provenance for various ML models over widely used ML datasets. 1 Introduction 

Expressing ML algorithms as recursive aggregate SQL queries over distributed systems such as Apache Spark has gained traction [40, 48]. For iterative ML tasks, aggregation within recursion is essential for fixpoint convergence [50]. There is also an increasing need for ML explainability [24, 30, 43]. In the context of ML as a declarative query, explainability of ML aligns with the database community’s long-standing work on explaining query results [4, 6, 7, 9, 25, 27, 32]. These studies rely on provenance, the record of how a query result is derived from input tuples, which is a well-studied method for such explanations. For ML queries, [3, 45] envision that provenance can trace how training instances drive model parameter updates, supporting model validation and debugging. It also enables the possibility of computing feature importance [24, 30], which quantifies each feature’s statistical contribution to the trained model. Despite this, no existing system supports scalable provenance capture for recursive aggregate SQL that is needed for ML explainability. Example 1 (Motivating Example). Optimization for Provenance Capture. Capturing local and global provenance introduces two challenges, both of which are reflected in the optimized query plan shown in Figure 2. First, the window functions required for update of model’s parameters involve sorting and shuffling across worker nodes at every iteration. ProvQML addresses this by broadcasting the small delta model relation 𝛿 M to all workers, eliminating the join shuffle entirely, and by partitioning the input training data T by instance identifier I once upfront. Since the prediction window function partitions on I, this upfront partitioning eliminates its reshuffle; only a single shuffle per iteration remains for the gradient window function, which partitions on C. Second, accumulating global provenance over 𝑘 iterations incurs 𝑂 (|T | · 𝑘 ) memory growth. ProvQML joins only with 𝛿 M𝑗 −1 at each iteration based on the observation that tuples from earlier iterations yield no valid join results due to mismatched iteration keys. Furthermore, it evicts per-iteration RDDs once the accumulated

Usability of Provenance. Provenance-aware recursive training pipelines provide a principled mechanism for exposing the dependency structure of iterative optimization. By materializing intermediate values such as per-instance predictions ( 𝑃𝑟𝑒𝑑 𝑖 ) and per-tuple gradient contributions (𝐺𝑟𝑎𝑑 𝑖 ) at each iteration 𝑗 , the system makes explicit the lineage linking individual training in-stances to parameter updates. Instead of observing only the final weight vector, analysts like Tom, can reconstruct how specific instances contribute to the aggregated gradient and how these contributions propagate across recursive state transitions. This fine-grained provenance enables systematic identification of influential records and feature-level sensitivity as indicated in [3, 45] without re-executing the recursive query entirely (retraining the model). In regulated settings, the resulting provenance can constitute a formally defined mapping from input training instances to final model parameters, supporting auditability of the training process. Beyond interpretability, embedding provenance within the recursive relation enables compu-tational reuse and adaptive optimization. By persisting iteration indices ( 𝑗 ), gradient aggregates, and their contributing instances, the system supports warm-start execution, allowing training to resume from a previously materialized iteration state without recomputing earlier steps. Fur-thermore, the availability of cross-iteration lineage enables convergence diagnostics based on the evolution of gradient magnitudes and directions. Such diagnostics can guide dynamic adjustment of hyperparameters (e.g., learning rate or sampling ratio) within the same declarative framework. By integrating provenance into the recursive query dataflow, the system reduces reliance on external monitoring while enabling selective retraining and incremental refinement grounded in explicit dependency analysis.

• We develop ProvQML, a recursive aggregate SQL engine on top of Apache Spark that executes the rewritten queries with optimizations that reduce shuffle overhead and bound memory growth during provenance capture (Section 6). 

• We evaluate ProvQML using 5 ML algorithms and 4 real-world datasets, demonstrating efficient provenance capture (Section 7). 2.2 PreM and PCC Properties 

PreM. The Pre-Mappability (PreM) property [17, 50] provides formal conditions under which extrema aggregates, i.e., min and max, can be pushed into recursion while preserving the semantics of the equivalent aggregate-stratified program. Formally, given a relational algebra expression 

𝑇 (𝑅 1, . . . , 𝑅 𝑚 ) where 𝑅 𝑖 is the vector of relations, and a constraint 𝛾 , 𝛾 is PreM to 𝑇 if 

𝛾 (𝑇 (𝑅 1, . . . , 𝑅 𝑚 )) = 𝛾 (𝑇 (𝛾 (𝑅 1), . . . , 𝛾 (𝑅 𝑚 ))) 

When the PreM property holds, the semi-naive fixpoint computation of the unstratified program produces the same results as the equivalent aggregate-stratified program, providing both a formal declarative semantics and a more efficient evaluation by eliminating the need to defer the aggregate to a post-recursion stratum. However, PreM applies only to extrema aggregates and is insufficient for aggregates such as sum, count, and avg. 

PCC. To address the limitation of PreM for non-extrema aggregates, the Pre-Countable Cardinality (PCC) property [48] provides formal semantics for the use of sum, count, and avg in recursion. The PCC property holds when the cardinality of the delta relation 𝛿𝑅 𝑖 at each iteration 𝑖 of the semi-naive fixpoint computation is nonzero, remains constant across all iterations, and can be pre-computed before the fixpoint computation begins. Under this condition, non-monotonic aggregates such as sum can be computed using only monotonic constructs, since the incremental computation of continuous count and sum is monotonic. Consequently, a recursive program satisfying PCC is equivalent to an aggregate-stratified program where the cardinality is pre-computed at a lower stratum, providing its formal declarative semantics. This condition is naturally satisfied by ML workloads such as gradient descent, where the number of training instances processed per iteration is fixed and known ahead of time.

3 Problem Definition 

We consider an ML query that encodes an ML algorithm over a verticalized training data T . A recursive relation M (such as Model in Figure 3) maintains the parameters with one tuple per feature dimension. The goal is to capture provenance that traces how training instances influence model parameter updates through per-instance predictions and gradient computations.

4 The ProvQML Language 

ProvQML query language extends RaSQL [17], a recursive aggregate query engine that runs on Apache Spark, which itself extends standard SQL, especially Common Table Expressions (CTEs) to support the use of basic aggregates (i.e., min, max, sum, count) in recursion. The RaSQL system addresses the limitation of Spark SQL’s compiler, i.e., its lack of native support for aggregates in recursive queries, through a two-step compilation process: first recognizing recursive table references in the query to construct a recursive plan, then executing the plan iteratively via a fixpoint operator until convergence or the maximum iteration is reached [17]. RaSQL focuses solely on recursive aggregate queries for graph problems such as reachability and shortest paths, supporting neither ML tasks nor provenance computation. ProvQML further extends in three key ways that are necessary to efficiently capture provenance for ML queries: support (i) window functions to capture provenance during recursive query evaluation, (ii) subqueries within the recursive query, and (iii) for user-defined functions (UDFs), such as last() , for the recursive query. While a previous work [48] addresses the ML limitation by demonstrating how ML workloads can be expressed as recursive aggregate queries in Datalog, but it does not support provenance computation. Furthermore, the query construct described therein (e.g., its SQL version in Figure 3) involves complex mutual and non-linear recursions with joins over multiple recursive relations, which would incur prohibitively high computational costs for provenance capture. ProvQML addresses these limitations through the aforementioned extensions.

Challenges of the Extension. These extensions are non-trivial within RaSQL’s fixpoint framework. Window functions in the recursive case require the query compiler to correctly scope them to the intra-step relation recProv rather than the accumulated recursive relation, re-executing the window evaluation fresh at each fixpoint step. Their semantic correctness within recursion also requires explicit justification via the PCC property (Section 2.2), since standard SQL semantics for window functions do not account for fixpoint convergence. The nested subqueries require RaSQL’s plan recognition pass must correctly classify each table reference in the recursive case as either an inter-step recursive dependency (e.g., ModelProv ) or an intra-step non-recursive view (e.g., recProv , predProv , gradProv ) resolved fresh at each iteration. Without this distinction, the compiler could incorrectly flag inner view references as recursive or fail to resolve them entirely, neither of which RaSQL’s original pass handles. Finally, the UDF last() is necessary because model weights are non-monotonic and no standard aggregate captures the most recently computed value. Its correctness relies on the iteration counter J acting as a total order over fixpoint steps, ensuring the fixpoint operator selects the highest J tuple per feature dimension at convergence.

6 Optimization 

Although the ProvQML’s instrumentation algorithm (Section 5) eliminates mutual and non-linear recursions, capturing PL and PG during recursive evaluation introduces two distinct computational challenges. First, computing PL at each iteration 𝑗 requires evaluating window functions over the relation recProv , which requires sorting and shuffling data that can dominate execution time.  

> Proc. ACM Manag. Data, Vol. 1, No. 1, Article . Publication date: October 2026. ProvQML: Efficient Provenance Capture for Machine Learning as Recursive Aggregate SQL [Extended Version] 19

Second, maintaining PG across all iterations requires persisting PL at every 𝑗 , which causes intermediate result sizes to grow as 𝑂 (|T | · 𝑘 ) where 𝑘 is the maximum number of iterations. 

6.1 Optimizing Local Provenance Capture 

Evaluating 𝑄 ′ 

> 𝑀𝐿

to capture PL relies on window functions over the relation recProv to compute 

𝑃𝑟𝑒𝑑 𝑖 and 𝐺𝑟𝑎𝑑 (e.g., Figure 5). In a distributed setting, window functions require data to be partitioned by a specific key before aggregation, which triggers a shuffle operation to redistribute tuples across worker nodes. Specifically, computing 𝑃𝑟𝑒𝑑 𝑖 requires partitioning by (J,I) and computing 𝐺𝑟𝑎𝑑 requires partitioning by (J,C) . If these shuffles are performed naively at every iteration 𝑗 , the overhead accumulates linearly with the number of iterations, significantly degrading the performance. We address this with two complementary techniques. First, since M𝑗 is much smaller than T

(it contains one tuple per feature dimension, while T contains one tuple per feature per training instance), we broadcast M𝑗 to all worker nodes at each iteration. This allows recProv to be formed via a local join on each partition of T without any shuffle of the training data. Second, we partition 

T by the instance identifier I once at the beginning of query evaluation and reuse this partition throughout training. Since recProv inherits the defined partition, it is already co-partitioned with the prediction window function (e.g., 1/(1+exp(-(sum(V*P)) OVER (PARTITION BY J,I) in Figure 5), eliminating its reshuffle. Note that since J is uniform within each recursive step, the effective partitioning key is driven by I, making the upfront partition on T by I sufficient. The gradient window function (e.g., sum((YP-Y)*V) OVER (PARTITION BY J,C) in the figure) requires a single reshuffle of recProv from I to C at each iteration 𝑗 , which is unavoidable. Partitioning T by C

instead would introduce two reshuffles per iteration, one for predictProv from C to I, and another back to C for the gradient computation. Thus, partitioning by I minimizes total shuffle overhead to exactly one reshuffle per iteration. Figure 7 shows the resulting optimized query plan. T (Trainv 

partitioned by I) and 𝛿 M (ModelProv broadcasted) form recProv via a local join with no shuffle. The single Shuffle [C] between predictProv and Grad (e.g., lines 14–17 in Figure 5) is the only inter-node in the plan redistributing data required per iteration. Furthermore, since the size and structure of recProv for evaluation at each iteration remain fixed at |T | tuples across all iterations (Section 6.2), the sorted order within each partition produced by the gradient reshuffle can be cached and reused at every subsequent 𝑗 , reducing the sort cost within a partition. This optimization is valid for the ML algorithms in Table 1 because the join key between T and 

M𝑗 is the feature dimension C, and the aggregation keys for 𝑃𝑟𝑒𝑑 𝑖 and 𝐺𝑟𝑎𝑑 are I and C, regardless of the specific predict function 𝑓 or gradient function 𝑔 . Furthermore, since T is read-only throughout training, its partitions remain valid across all iterations, making upfront partitioning a sound and stable optimization. This mirrors the replica mechanism of [48], which similarly avoids repeated shuffles of the base relation by co-partitioning it with the recursive relation on the required join keys. Note that this optimization extends to any ML algorithm whose training loop joins a fixed base relation with a small delta model relation on a stable key and computes per-instance and per-feature aggregations on fixed partition keys. Algorithms with additional aggregation levels or multiple join keys would require a corresponding extension of the partitioning strategy. 

6.2 Optimizing Global Provenance Capture 

PG is defined as the union of PL across all 𝑘 fixpoint iterations (Definition 3). Since PL at each iteration 𝑗 has size 𝑂 (|T |) , maintaining PG naively requires 𝑂 (|T | · 𝑘 ) space. For large training datasets and number of iterations, the intermediate result can far exceed the size of the final model output, placing significant memory and I/O overhead. A further overhead arises from the join in recProv . Without careful management, the join between T and M at each iteration 𝑗 could  

> Proc. ACM Manag. Data, Vol. 1, No. 1, Article . Publication date: October 2026. 20 Nkechi J. Akinwale and Seokki Lee

include model states from prior iterations that are still resident in memory, producing stale or redundant provenance that inflates PG unnecessarily. To address this issue, we adopt a strategy analogous to the delta-based optimization of [48] through DSN (Section 2.3). At each iteration 𝑗 , only the delta relation 𝛿 M𝑗 , i.e., the model parameters updated in the most recent fixpoint step, is used as the input to the join in recProv . Consequently, 

recProv at each 𝑗 joins T exclusively with M𝑗 −1, producing exactly |T | tuples with no contribution from the previous model states. This is correct because the join key between T and M includes the iteration counter J, so tuples from earlier iterations carry mismatched J values and would produce no valid join results, analogous to the observation in [48]. To maintain PG , the PL captured at each iteration 𝑗 is accumulated as a chain of RDDs, preserving the full optimization trajectory across all fixpoint iterations. To bound memory usage, the PL RDD from iteration 𝑗 − 1 is unpersisted at the end of each fixpoint step once its content is subsumed by the accumulated PG , while remaining accessible via Spark’s DAG lineage on demand. At any point during the recursion evaluation, only the cached T and the PL snapshot from the latest iteration 𝑗 are physically resident in memory which keeps the memory usage bounded at 𝑂 (|T | + |P L |) = 𝑂 (2 · |T |) per iteration. Including older model states would produce no additional tuples, while retaining them in memory would incur unnecessary overhead. The incremental accumulation of PG as a union of per-iteration PL

snapshots is similarly justified. Since PG can be queried post-hoc for explanation or debugging rather than consumed during training, evicting 𝑗 − 1 RDDs after each fixpoint step introduces no correctness concern, as the accumulated PG already subsumes all prior PL snapshots by Definition 3.

7.5 Discussion 

One of the widely used methods for computing model explanation is marginal feature contribution, formalized by Shapley value (SV) [41]. SV attributes the contribution of each feature to a model out-put as the weighted average of its marginal contributions across all possible feature coalitions. The computation introduces substantial overhead as SV requires an exhaustive evaluation of all possible feature coalitions, where each coalition is a model. Despite this expensive cost, we observe the feasibility of computing such explanations by extending ProvQML based on the prior work [3, 45]. To test, we encoded all possible coalitions of features as data, which we refer to as explanation data . For that, we augmented the input dataset with an additional attribute which encodes feature coalitions. This schema design provides two benefits: (i) it provides support for evaluations over all feature coalitions without requiring changes to the ML query and (ii) it shifts complexity that would otherwise arise at the query level to the data level. We implemented this extension in ProvQML by augmenting the recursive relation schema with an additional coalition identifier column, e.g., ex-tending the Model relation in Figure 5 to Model(C, CF, YP, GI, Grad, last() AS P, max() AS J) ,where C and CF partition the training data by feature coalition and allow the existing query structure to evaluate all coalitions in a single recursive execution. Interestingly, our investigation extracted that the computational overhead may not be completely unmanageable. We run our experiments on the BikeSharing and SpamBase datasets using queries 

𝑄 1 and 𝑄 4, varying the number of features. Note that, with the naive extension, the evaluation could be conducted for the small number of features. The result is shown in Figure 16. The feature size and the corresponding data size are shown on the x-axis. The experimental results highlight several observations. First, runtime scales roughly linearly with the number of feature coalitions. Secondly, the per-iteration cost increases more drastically as the intermediate result size is larger than the one for a single model. Note that the runtime of this evaluation includes provenance capture time for every feature coalition. A promising solution is relying on sampling that generates a representative subset of explanation data to compute explanations similar to the existing approximation-based methods in ML explanations [36]. Without approximation, we envision that the computational overhead may be further reduced by leveraging the captured provenance across coalitions to avoid redundant recomputation, and by pruning coalitions that are unlikely to contribute significantly based on properties of the model or gradient structure. This broadly captured information will enable new types of explanations, e.g., quantifying the influence of a group of training instances and a subset of features on the model’s parameters. Further investigation of such explanations is an interesting avenue for future work.

8 Related Work 

Recursive Query Processing. Processing recursive queries in SQL [31, 39] and Datalog [29, 42, 48] has been extensively explored. Support for aggregates within recursive queries was initially formalized in [23]. Subsequent work showed that aggregates in recursion [31, 37, 42, 48] increase the expressive power of recursive queries and provide formal declarative semantics for correctness, enabling ML workloads to be expressed in familiar declarative languages. However, none of these systems support provenance, which provides the information needed to explain ML model behavior. 

Database Provenance. Provenance for database queries has received significant research attention over the past decade [7, 14, 16, 20–22, 26, 27], including provenance for aggregate queries [4, 5]. Provenance for recursive queries is understudied [10]. Outside the database context, [35] proposes a JSON-based library to capture provenance in ML systems, [37] tracks provenance for training runs and predictions, and [38] captures provenance for ML tasks integrated with Git. However, these systems operate outside the database setting and require additional tools. In contrast, ProvQML is a SQL-based system that leverages query rewriting to capture fine-grained provenance for ML workloads expressed as recursive aggregate SQL queries, without requiring additional integration. 

In-Database Machine Learning. In-database machine learning integrates ML pipelines directly within database systems enabling tasks such as data preprocessing, model training, and validation. Systems such as MADlib [18], BigQuery ML [15], and Umbra [39] support in-database ML via SQL interfaces, but implement ML algorithms as user-defined functions or system-internal extensions rather than as recursive aggregate SQL queries. As a result, they neither expose the recursive structure of the ML computation nor support provenance capture during training. 

Distributed Machine Learning Systems. Apache Spark [49] has gained significant attention as a general platform for large-scale analytics and machine learning. SystemML [13] supports ML workloads on Spark using R or Python, while BigDatalog [42] and Radlog [48] support declarative large-scale iterative computations on Spark using Datalog. 

9 Conclusions 

In this paper, we presented ProvQML, a provenance-aware recursive aggregate SQL engine built on Apache Spark that efficiently captures fine-grained provenance while evaluating ML algorithms as recursive aggregate queries. Our approach instruments complex ML queries into queries with standard linear recursion, using window functions and a chain of provenance subqueries. We experimentally demonstrate that ProvQML efficiently captures provenance for a range of ML models across widely used benchmark datasets. Interesting directions for future work include extending ProvQML to (i) identify the influence of groups of instances, e.g., subpopulations sharing a feature value or label, by applying provenance summarization techniques [4, 27, 28] over PG ; (ii) support deeper recursive dependencies in more complex ML algorithms such as neural networks, and (iii) compute new types of explanations using captured provenance and explanation data to quantify marginal feature contributions.
