## Abstract 

GPU architecture research requires representative bench-marks that can execute on new designs. However, many vendor-tailored workloads and library kernels cannot run directly on research architectures because their implemen-tations are closed-source or rely on programming models unsupported by the target architecture. Migrating existing kernels requires manual effort to adapt their implementa-tions and validate their behavior. This creates a need to automate workload migration to target platforms. We present VortexSynth, a framework that uses profile-guided benchmark reconstruction to construct GPU bench-marks from reference workloads. Our workflow selects hot kernels through profiling, synthesizes implementations in the target programming language, verifies output equiva-lence, and measures profile differences using a translated proxy implementation. The resulting profile signature gap is supplied to an agent for iterative refinement. We evaluate the method on Vortex, an open-ISA GPGPU, using robotics as the application domain. All active kernel pairs pass both output-equivalence checks, and the case studies show that iterative refinement can reduce profile distance.

## 1 Introduction 

Machine learning, scientific simulation, and other compute-intensive applications increasingly rely on GPUs for parallel computation and high memory throughput. These growing demands motivate new GPU architectures and changes to ex-isting designs. Several open-source GPU designs have been proposed [4, 28, 44]. For example, Vortex is an open-source GPGPU based on RISC-V. These open GPU designs enable reproducible research and transparency in architectural ex-ploration. Evaluating architectural ideas and optimizations

requires workloads that exercise the behavior they are in-tended to improve. Researchers therefore need representative benchmarks that can run on their specific architectures. As applications evolve, new models, operators, and numerical formats change the kernels these benchmarks must repre-sent. In addition, new GPU architectures may require exist-ing kernel implementations to be adapted or retuned [39, 40]. Benchmark preparation is therefore a recurring effort as both workloads and target architectures change. However, researchers starting work on a new design have a limited set of benchmarks to use as baselines, as many vendor-tailored workloads and library kernels do not run directly on a research architecture. Migrating an existing workload requires adapting its kernels and library dependen-cies to the target, then validating the resulting implemen-tation. Compiler support can reduce part of this work. For example, VOLT translates CUDA and OpenCL programs for Vortex and its variants [21], but incompatibilities due to hard-ware differences (e.g., tensor-core and asynchronous-copy support) can still require substantial manual adaptation. An open-source library may still rely on closed-source ker-nels. For example, deep-learning frameworks call NVIDIA GPU libraries such as cuBLAS and cuDNN [35, 36]. When the required kernel implementation is unavailable, porting the surrounding code is not enough. Researchers must imple-ment replacement kernels for the target architecture, adding to the manual effort needed to prepare benchmarks. Making these computations available as benchmarks on open GPUs would let researchers evaluate hardware, compiler, and run-time changes using representative application workloads. ## 2 Background 

2.1 Vortex GPGPU 

Vortex is a full-stack open-source RISC-V GPGPU research platform with SIMT execution, OpenCL software support, simulator and RTL flows, and a modifiable compiler, dri-ver, and runtime stack [44]. Its recent release adds a Tensor Core Unit extension with a tensor API and low-precision multiply-add support [45]. We choose Vortex as the target for profile-guided benchmark reconstruction, as the architecture supports mechanisms including SIMT scheduling, memory system changes, atomics, and tensor-core extensions. Vortex is the evaluation target in this paper. Applying the method to another GPU would require its programming interface, implementation constraints, and validation tools. 

2.2 Vortex Benchmark 

A Vortex benchmark is a C/C++ benchmark that targets the Vortex software stack. The host code uses Vortex run-time calls to allocate device buffers, transfer inputs, launch a kernel, and copy results back for checking. Compared to a CUDA kernel, the device kernel in a vortex program is com-piled by the Vortex toolchain into RISC-V GPGPU instruc-tions executed by Vortex cores [46], rather than into NVIDIA PTX/SASS or calls to CUDA libraries. Table 1 lists the Vortex intrinsics a C/C++ kernel uses for thread launch, lane mask-ing, barriers, local memory, and tensor-core multiply-add.

2.4 LLM 

LLMs can assist GPU kernel migration by translating source code into implementations for a different architecture or programming model [17, 24]. However, translation remains challenging when the target programming model is less fa-miliar to the model, and a single generation attempt may not produce a correct implementation [14]. Iterative work-flows allow generated implementations to be checked and revised using compiler diagnostics and execution results. This feedback helps the model identify and correct errors that remain after the initial translation [6]. These findings motivate the iterative process in our framework. In addition to output-correctness feedback, we supply measured profile differences to guide revisions toward closer agreement with the reference kernel.

## 3 VortexSynth:Profile-guided benchmark reconstruction 

Figure 2 illustrates VortexSynth, the benchmark reconstruc-tion workflow. A revision is one pass through the refinement loop, in which an LLM applies an optimization change, gen-erates code, and records the change. Each revision produces two candidates , a CUDA implementation that runs on an NVIDIA GPU and a Vortex implementation that runs on SimX, the Vortex simulator. The loop retains a candidate only when it lowers the profile distance; otherwise it reverts to the last retained pair. When all optimization axes are ex-hausted, the loop ends and the retained candidates are locked .The framework delivers the locked Vortex implementation as the reconstructed benchmark .

3.1 Reference Program Context 

The workflow begins with a reference workload, the target application whose kernels we reconstruct. We first profile the workload at the PyTorch level to record each operator call and the cuBLAS or cuDNN kernel it dispatches to. From the call and its tensors we take the shapes and the operand and accumulator data types. From the demangled kernel name we take the engine class, scalar SIMT or tensor core. From the profiler we take the block size and launch grid. A property read from the kernel name is used only when the measured launch geometry agrees with it; properties encoded by undocumented naming conventions are left for the search to determine. 

3.2 Source Profile Signature 

Profiling the reference workload produces its profile signa-ture , the set of Nsight Systems and Nsight Compute mea-surements that describe the reference behavior. It records hot-kernel rank, cumulative time, launch parameters, and the ten metrics listed in Table 2. We reconstruct each hot kernel separately at its profiled shape, which keeps every benchmark within a simulation budget suited to architec-ture studies while preserving the shape that determined the reference’s behavior. 

Profile signature metrics. The ten Nsight Compute met-rics describe hardware utilization and serve as the behavioral target for refinement. A benchmark is used to evaluate an architecture or a compiler change, so what it must preserve is where the kernel puts pressure, not the exact instruction sequence that produces it. We therefore group the metrics by the hardware resource an experiment would vary. Each group describes the pressure that such an experiment would examine. The ten metrics are selected form four groups. The two cache hit rates and coalescing efficiency describe where the traffic is served . Achieved peak compute, tensor MFU, and atomics per instruction describe which engine does the work and what it costs to commit a result . Arithmetic intensity and achieved memory bandwidth describe work per byte and the rate of data transfer . Active-lane fraction and occupancy describe how much of the machine the kernel keeps busy .Datacenter GPUs such as H200 report all ten metrics, while edge devices such as Jetson AGX Orin omit arithmetic in-tensity and achieved DRAM bandwidth. Signature distance. We use the signature distance to compare a generated candidate with the reference. Each measured metric contributes a distance between zero and one, and the signature distance 𝐷 is their mean. Percent metrics use the absolute difference over their range, the two rate metrics use a log ratio so that a factor of two counts the same in either direction, and the active-lane fraction and the atomics rate use the direct difference. A metric the platform cannot measure is left out of the mean rather than scored as a full distance. 

Signature scope. The signature describes which hard-ware resources a kernel uses and how heavily it uses them. Similar resource-use patterns can arise from different instruc-tion schedules, stall reasons, shared-memory bank conflicts, and register allocations. Coalescing efficiency is averaged over ordinary global load instructions. For kernels that move operands through asynchronous or bulk copies, it reflects only the remain-ing ordinary loads. If the reference issues none, we report coalescing efficiency as 0 and retain it in 𝐷 . Tensor MFU measures tensor-core use. A candidate that executes entirely on scalar SIMT units has a measured tensor MFU of zero. We retain this zero in 𝐷 to capture the difference in engine use between that candidate and a tensor-core reference. 

3.3 Refinement Sandbox 

An LLM generates the kernel code and then revises it inside a sandbox defined by a constraint set and a validation proce-dure. The constraints specify which changes a revision may make, which constructs it may use, and which properties must remain fixed. The agent may only edit the files named in the task, and it may not substitute a different algorithm, change the swap target, call the vendor library instead of the generated kernel, replay cached outputs, or tune constants in ways that break correctness. The validation procedure specifies how a candidate replaces the vendor kernel, how output equivalence is checked, and which tolerance applies to each precision path. These rules are fixed before refine-ment begins and apply to every revision. 

Allowed Code optimization axes. The constraint set de-fines the agent’s search space through the optimization axes in Table 3. Each permitted axis must be expressible on Vortex so that the CUDA and Vortex candidates implement corre-sponding changes. To make all four profile-pressure groups in Section 3.2 actionable, the search space includes portable optimizations that primarily target each group. Shared-memory staging, read-once staging, and lane-contiguous mapping alter where operands are served and how lanes access them. Tile dimensions, register tiling, and software prefetching adjust data reuse and load–compute overlap. Tensor-core lowering, fused-activation stripping, and split-K alter the execution engine or result-commit behavior,

3.4 Candidate Generation 

Each selected hot kernel is reconstructed independently, with its own candidates and its own revision chain. The LLM gen-erates code from an input bundle containing the reference program context, source profile signature, sandbox defini-tions, and revision history. All reported runs used Claude Opus 5 [3]. 

CUDA candidate. For every revision, the LLM generates a CUDA candidate . The first candidate is built from the refer-ence program context alone. From that context we extract four reference properties (Table 4). They remain fixed during refinement and constrain four of the twelve optimization axes. For example, per-block decomposition and tile dimen-sions must preserve the measured block size. The engine class and the data types bound tensor-core lowering, and the profiled shape bounds the split factor for split-K. From the second candidate onward, the LLM enters the refinement loop and normally applies one axis from Table 3 for each revision.

Swapped execution. We insert the CUDA candidate into the reference workload by wrapping selected PyTorch oper-ators, such as torch.matmul and F.linear . The wrapper saves the original function and replaces its Python entry point. On each call, it checks the input shapes against the pro-filed matrix dimensions (𝑀, 𝑁 , 𝐾 ) or convolution shape. A matching call is routed to proxy.forward , which launches the generated CUDA kernel. Other calls use the saved original function, preserving the rest of the workload. The wrap-per logs the call signature and dispatch decision so that the output checker can verify that the candidate actually ran. This lets us validate and profile the replacement within the application. 

3.5 Output Equivalence 

Each revision must pass the source-output equivalence and candidate equivalence checks before we measure its profile signature distance. A precision path comprises the data types used by the reference kernel, the CUDA candidate, and the Vortex candidate. Table 5 specifies the per-element absolute and relative tolerances for each path. 

Source-output equivalence. We compare the CUDA can-didate with the original framework or library operation on the same sampled inputs and verify that the replacement actually executed. When an operator-level swap is unavail-able, a CPU/PyTorch implementation of the same operation supplies the reference outputs. 

Candidate equivalence. We run the CUDA candidate on an NVIDIA GPU and the Vortex candidate on SimX using the same input value, then compare their outputs. The tolerances reflect the precision path and accumula-tion differences in each check. FP32 comparisons use tight tolerances, while BF16 comparisons allow for rounding on the BF16 output grid. Tensor-core reference paths use wider relative tolerances to accommodate cuDNN’s TF32 execution for some shapes. The CUDA-to-Vortex check also accounts for the change from TF32 to FP16 on Vortex. 3.6 Profile-Guided Refinement 

Each refinement revision starts from the best retained de-sign. The LLM normally selects one optimization axis from Table 3, applies it to the retained design, and generates the corresponding CUDA and Vortex candidates. When single-axis attempts no longer improve the profile, the agent may combine two permitted axes in a revision. The harness then runs the source-output equivalence and candidate equiva-lence checks. A failed check rejects the revision. Otherwise, the harness profiles the CUDA candidate within the work-load and computes its signature distance 𝐷 .A revision is retained if it lowers 𝐷 by more than the measurement-noise margin, 𝛿 = 0.005. Otherwise, it is re-verted . For revisions that apply a single axis, the change in 𝐷 

from the retained design is attributable to that axis. The per-metric changes show which parts of the signature the axis affects, forming the basis of the analysis in Section 4.3. The next revision starts from the retained design and receives the per-metric distances, so the agent can choose an axis that addresses the largest remaining differences. The agent decides when to stop based on the revision history and remaining profile differences. It typically stops after trying the applicable axes and judging that no further change is likely to improve profile agreement. The agent can revisit an axis through a different implementation or direc-tion of change, so one failed attempt does not exhaust that axis. The best retained pair is then finalized as the bench-mark and its CUDA proxy. We report the final distance and revision history to show the agreement reached under these constraints. 

Revision record. Each kernel has a revision record that is supplied to its next revision. The record identifies the applied optimization and the output or profile condition it targets. It also documents why the candidate still implements the same kernel, the outcome of both output checks, changes in the profile and signature distance, and the retain or revert decision. Reverted attempts remain in the record so the agent can see which changes did not help and avoid repeating them. ## 4 Evaluation 

We use robotics as the evaluation domain, testing whether profiles from ACT, Diffusion Policy, and Pi0 can guide the construction of Vortex benchmarks. All workloads are pro-filed at batch size one, matching the online inference regime. The evaluation proceeds in five steps. First, we measure how much H200 and Jetson AGX Orin GPU time the selected hot kernels cover, and list the suite they yield. Second, we confirm that every benchmark passes both output checks. Third, we read the revision records as experiments, measur-ing which pressure group of Section 3.2 each optimization axis moves, and in which direction, for each benchmark type. Fourth, we follow one benchmark through its full re-vision chain as a case study. Fifth, we reverse the order of refinement and iterate on the Vortex candidate first, to test whether refining on the reference GPU is what makes the profile signal usable, and read that result against cross-GPU metric variation.

4.2 Output Equivalence Results 

All 26 benchmarks pass both output checks under the toler-ances in Table 5. Against the reference operation, the largest errors are 1 .6×10 −6 absolute for FP32, 1 .1×10 −2 relative for TF32, and 4 .9×10 −4 absolute for BF16. Across CUDA and Vortex, all nine FP32 pairs pass the can-didate equivalence check within the specified tolerance. The TF32-to-FP16 pairs have the largest relative error, 9 .5×10 −2,reflecting the change in precision. BF16 pairs reach 3 .2×10 −2

relative error on near-zero outputs and pass the combined absolute and relative tolerance. Near zero, the absolute term allows small rounding differences that appear large when expressed as relative error. These checks establish output agreement for the tested inputs across all three precision paths. 

4.3 How Optimization Axes Move the Signature 

We use revisions that apply one optimization axis to examine how each axis changes the profile signature. For each revi-sion, we compare its metrics with those of its retained parent using the distance transform in Table 2, keeping the sign of the change. Percentage metrics are expressed as fractions of their range, and rate metrics use a log ratio. Both retained and reverted revisions contribute to this analysis because an unsuccessful change still shows how an axis affects the measured behavior. Figure 4 summarizes these responses by benchmark type. Rows represent optimization axes, and columns represent the ten metrics organized into the four pressure groups of Section 3.2. Each cell is the mean signed response across re-visions that applied that axis alone. Red indicates an increase and blue a decrease. Either direction can improve agreement, depending on the reference value. A value near zero can reflect small changes or opposing responses across revisions. The figure includes 157 revisions across 26 benchmarks, with 90 from H200 and 67 from Orin. We exclude 13 revisions that combined two axes because their responses cannot be attributed to one axis. We also exclude three revisions that restored a fixed property and one re-measurement. Generic K range and fused activation stripping are determined by the profiled shape and operator in the seed, so neither appears as a refinement row. Gray rows indicate that an axis was never applied alone for that benchmark type. Arithmetic intensity and DRAM bandwidth use H200 measurements only. Asterisks mark cells whose revisions ran only on Orin, where those metrics were unavailable. Staging and lane mapping primarily affect where traffic is served . Across these axes, the mean magnitude of the plotted responses is 0.16 for the traffic metrics, compared with 0.05 for work per byte . The linear-layer panel shows the clearest example. Shared-memory staging lowers the L1 hit rate by 0.55 and raises coalescing by 0.56 on average. This pattern is consistent with moving repeated reads into shared memory and organizing the remaining global loads into contiguous cooperative fills. Read-once staging moves these metrics in the opposite direction on linear layers and matmuls, as repeated global requests can be served by L1. The reference determines which direction is useful for 

lane-contiguous mapping . On matmuls, five of the seven lane-mapping revisions reduce coalescing, and all five are retained. Applying the axis in reverse helps match references that read few useful bytes per memory sector. Read-once staging provides another example. It is retained on three mat-mul benchmarks but reverted on Linear-2 and Linear-4 ,whose references have L1 hit rates near zero. Raising L1 hit rate moves those linear-layer candidates away from their references. 

Tile dimensions , register tiling / ILP , and software prefetching connect work per byte with where traffic is served . Their mean response magnitudes are similar in the two groups, about 0.06 in each. Register tiling increases arith-metic intensity on linear layers as each thread reuses inputs across a larger output tile. It also lowers mean occupancy by 0.07–0.13 across the four benchmark types, consistent with greater register demand per thread. Tile dimensions is the most frequently applied axis, but its effects vary across benchmark types. Changing a tile’s reduction depth, area, or aspect ratio changes both reuse and memory access. Mean coalescing rises on linear layers, matmuls, and 2-D convolu-tions, but falls on 1-D convolutions. Software prefetching illustrates why these effects must be evaluated together. It raises mean DRAM bandwidth in all four panels, yet all seven applications to 1-D convolu-tions are reverted. Six increase the overall distance, and one lowers it by less than the retention margin. The 1-D con-volution panel also shows substantial changes in cache hit rates. Overlapping loads with computation can therefore improve bandwidth without improving agreement with the reference’s full profile. The engine and commit and machine busy groups respond less strongly overall, although their metrics behave differ-ently. Atomics remain zero because the references use none and the sandbox excludes them. Tensor MFU changes little, and active-lane fraction is nearly unchanged outside the 1-D convolution cases. These patterns are consistent with pre-serving the engine class, block size, and shape. Occupancy is more responsive because several axes change resource use or the amount of work in flight. ## 5 Related Work 

5.1 Compiler-Based Retargeting and Workload Cloning 

Source-level retargeting tools translate a program for a differ-ent backend and preserve its semantics by construction. HIP-IFY [2] and SYCLomatic [19] rewrite CUDA source for AMD and SYCL targets, CuPBoP [1, 11, 16] compiles CUDA onto processors without a CUDA runtime, and MLIR-based flows lower a common representation to several backends [26]. Whenever the executed kernel is available as source and the target exposes comparable primitives, these routes are preferable to synthesis. Operator-level compilers such as TVM [12] relax that requirement to an operator graph, but their autotuners [52] emit whichever kernel is fastest on the target, so the result bears no intended relation to the profile of the kernel the reference stack actually ran. Our setting removes both options: the hot kernels are vendor library binaries selected at run time, so there is no source or intermediate representation to retarget, and the goal is a benchmark whose measured behavior approximates a spe-cific observed kernel rather than one that merely computes the same function. The closest prior formulation is workload cloning, which distills a proprietary application into a distributable bench-mark that reproduces its measured characteristics [22, 23]. That line of work synthesizes whole applications for CPUs from microarchitecture-independent program characteris-tics. The same goal has since been pursued at the granularity of a single GPU kernel, where a synthetic clone is generated to mimic “control flow, branch divergence and memory ac-cess behavior” [48] — the execution behavior of the kernel, not the values it computes — and so cannot be run in place of the original. We keep the goal and change the setting: the unit is one GPU kernel, the specification is its profile signature plus the operator it implements, the target is a different ISA, and the artifact must additionally reproduce the reference output so that it can be substituted into the original stack and checked.

5.3 Robotics Accelerators and Kernel Baselines 

Prior architecture works cover important slices of the robot-ics stack. Most of them still target one robot type or algo-rithm family at a time. Navion [41] and eSLAM [29] target VIO and ORB-style feature pipelines. These overlap with the suite’s ORB descriptor-extraction and Hamming-matching kernels. TorchSparse [43], Ada3D [51], and PointPillars-style work [25] overlap the sparse 3D side of the suite. Robo-morphic Computing [33], RoboShape [32], cuRobo [42], and pRRTC [18] target motion planning and robot dynamics. Edge-oriented learned inference is covered by NanoVLA [10], Shallow-𝜋 [20], FastDepth [47], and NeuFlow [49]. These studies show the breadth of robotics kernels, but usually focus on one robot type or algorithm family at a time. 

5.4 LLM Kernel Generation 

Benchmarks including KernelBench [37], TritonBench [27], and TritonGym [15] evaluate whether LLMs can generate correct and efficient GPU kernels from PyTorch, Triton, or operator-level specifications. These works are closest to our use of LLMs as a code-generation mechanism, but their primary goal is to evaluate generated kernel quality. Our framework instead uses kernels generated by an LLM as benchmark candidates derived from profiled robotics work-loads. Output equivalence establishes correctness, and profile deviations are returned to the LLM to synthesize the next candidate. KForge uses a similar profile-guided LLM refinement loop, but it starts from available reference implementa-tions and leaves synthesis for closed-source kernels for future work [39]. Kevin and KernelCraft use iterative feed-back as well. Their optimization objective is to improve execution speed rather than match a reference kernel’s be-havior [5, 34]. CUDA-L2 further uses reinforcement learning to exceed cuBLAS performance across matrix multiplica-tion shapes [40]. This objective differs from constructing a representative benchmark. ## 6 Conclusion 

VortexSynth reconstructs portable benchmarks from CUDA workloads without the original kernel source. It uses work-load context, output-equivalence checks, and profile feed-back to generate and refine kernels for the target architec-ture. Using VortexSynth, we construct VX-Robotics, a suite of 26 Vortex/CUDA pairs from ACT, Diffusion Policy, and Pi0, profiled on H200 and Jetson AGX Orin. All pairs pass both equivalence checks, and refinement lowers profile distance in the detailed case studies. The suite provides reusable kernels for Vortex architecture research. We will release VortexSynth and the VX-Robotics benchmark suite as open source to support benchmark construction on Vortex and other open GPUs.
