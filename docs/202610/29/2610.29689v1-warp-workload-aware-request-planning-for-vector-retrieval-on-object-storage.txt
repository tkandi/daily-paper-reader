Abstract
Modern vector search systems keep payload vectors in cloud object
storage and only a compact routing index on fast local storage,
typically using cluster-based ANN indexes. This design inherits
a problem existing systems do not address. On object storage,
small Range-GETs have latency dominated by fixed per-request
overhead and are billed per request. Existing readers either issue
one request per probed cluster, or coalesce adjacent ranges with
hand-tuned gap or span thresholds that do not transfer across
datasets or query workloads.
We formulate the grouping of probed-cluster byte intervals into
object-store requests as a global per-query optimization problem
and present WaRP, a workload-aware request planner that solves
it efficiently. Given the sorted byte intervals, a limit on the number
of requests per query, and an estimate of how many object-store
requests from one query can proceed concurrently under the tar-
get serving configuration, WaRP searches for a merge plan that
minimizes a concurrency-aware latency surrogate while satisfy-
ing the request limit. Using an optimized dynamic program and
adaptive frontier search, WaRP returns a plan within (1+𝜖) of the
optimum, with per-query planning overhead under 10 ms even in
the most demanding tested settings. A lightweight offline reorder-
ing pass further improves request mergeability without changing
the semantics of ANN search.
We implement WaRP inside Lance’s I/O scheduler and evaluate
it on AWS S3. We build IVFPQ indexes on seven datasets, including
SIFT100M and DEEP100M at the 100M-vector scale. WaRP + Re-
order improves QPS by 1.09–3.48× and reduces GETs by 2.12–5.19×
relative to Lance, while preserving Lance’s recall.

Introduction
Large-scale vector search is increasingly deployed over disaggre-
gated storage, with payload vectors placed in cloud object stores to
reduce storage cost and decouple storage from compute [13, 15, 26,
45, 49, 50]. In these systems, a compact routing structure remains
on fast local storage, while query execution first selects a probe set
and then fetches the corresponding payloads remotely. This separa-
tion is well suited to cluster-based index families such as IVF [32]
and IVFPQ [33], and to systems built on them such as SPFresh [55].
Once probing finishes, the system knows which cluster payloads
are required, but it must still decide how to translate their byte
intervals into remote requests.
Object-store Range-GETs have much higher fixed overhead than
local reads and exhibit high tail latency. As Figure 1 shows, a 1 KB
request takes roughly 25 ms, while a 1 MB request takes only about
30 ms. Small cluster reads are therefore dominated by per-request
overhead. Object stores also charge per API request, so fragmented
retrieval increases both latency and GET charges. Figure 2 makes
the resulting choice concrete. Probe selection has picked three
cluster payloads in the same object. Reading them separately takes
three Range-GETs. Merging the first two saves one request and
overfetches the 0.3 MiB gap between them. Merging all three leaves
a single request but overfetches 2.7 MiB, because the last payload
sits 2.4 MiB away. Probe selection determines the required cluster
payloads. Request planning groups their byte intervals to balance
per-request overhead against overfetch.

Existing systems typically handle this stage with local coalescing
heuristics, such as greedy merging with fixed gap thresholds [15,
36, 57]. Such hand-tuned rules are hard to rely on because the best
thresholds vary across datasets and query workloads. We confirm
this empirically in Section 7.2. Careful tuning works well on one
dataset, but performance drops sharply when the same parameters
are applied to another. Request planning is therefore better treated
as a global optimization problem over the ordered payload intervals
exposed after probe selection.
Another way to reduce per-request overhead is to cluster more
coarsely when building the ANN index. Each remote read then
covers more payload and amortizes the fixed overhead over a larger
transfer. But this only shifts cost from I/O to compute and index
maintenance without changing how requests are formed. In IVF
terms, the index has fewer, larger clusters and the query probes
fewer of them. As shown in Table 1, at matched recall the coarser
setting cuts request count by 58% but enlarges the candidate set by
nearly 50%, raising per-query compute. Larger clusters also weaken
pruning, make updates and rewrites costlier, and limit flexibility
under filters or mixed workloads. Tuning probe granularity is there-
fore not a substitute for solving request planning directly.
We propose WaRP, a workload-aware online request planner
that addresses this trade-off, and pair it with an offline method
that reorders IVF cluster payloads specifically for object-store re-
quest planning. Given a request budget, an estimate of how many
object-store requests from one query can proceed concurrently un-
der the target serving configuration, and a request-time surrogate
calibrated offline from object-store measurements, WaRP returns a
merge plan provably within (1+𝜖) of the optimum, with per-query
overhead under 10 ms even in the most demanding tested settings.
By bounding the number of GETs per query, the request budget
directly bounds the query’s GET charge and provides a single knob
for balancing that charge against latency. The reordering method
places likely co-accessed clusters nearby, shrinking the gaps that
merged reads must bridge and reducing overfetch. Request plan-
ning and reordering preserve probe selection and recall. For a fixed
probe set, all methods retrieve the same clusters and differ only in
how the selected payloads are laid out and fetched.
We implement WaRP inside Lance’s I/O scheduler [36] and pair
it with offline reordering of IVF cluster payloads. Across seven
datasets on AWS S3 [3], WaRP + Reorder delivers 1.09–3.48× the
QPS of Lance and a 2.12–5.19× GET reduction while preserving
Lance’s recall.

This paper makes four contributions. First, we identify request
planning as a missing optimization layer between probe selection
and payload retrieval in object-storage-backed ANN search. We
formulate it as a global per-query optimization problem. Second,
we make this optimization practical with an optimized dynamic
program and adaptive frontier search. The resulting planner is
fast enough to run on the query critical path. Third, we introduce
offline reordering of IVF cluster payloads for object-store request
planning, creating better merge opportunities with less overfetch
while preserving probe selection and recall. Finally, we implement
WaRP in Lance and evaluate its end-to-end performance across
seven datasets on AWS S3.
2
Background and Motivation
In this section, we discuss cluster-based ANN indexes and the I/O
characteristics of cloud object storage. We also describe the execu-
tion pipeline of cloud-based ANN queries.
2.1
Cluster-Based ANN Indexes
Cluster-based ANN indexes, such as IVF [32], partition vectors
into clusters. To answer a query, the system first selects a probe
set by comparing the query to cluster centroids, then fetches the
payloads of those clusters for candidate evaluation. We use cluster-
based ANN indexes broadly to include plain IVF and its variants,
such as IVFPQ [33] and SPFresh [55]. We also include designs that
build an auxiliary graph or tree over the cluster centroids—using
HNSW [37], Vamana [30], NSG [18], or a KD-tree [10]—to accelerate
probe-set selection. These auxiliary structures change how clusters
are selected, not how their payloads are retrieved. All such methods
therefore remain in the cluster-based setting considered here.
2.2
Cloud Object-Store I/O Characteristics
Cloud object stores provide low-cost, elastic capacity for ANN index
payloads. Representative services include Amazon S3, Azure Blob
Storage, and Google Cloud Storage [3, 23, 38]. Two aspects of their
I/O behavior matter here. Each Range-GET carries substantial fixed
overhead, and request latency is highly variable with a long tail.
The latency decomposition in Figure 1 shows the fixed overhead
of each Range-GET, while Figure 4b shows that both average and
p95 query latency rise markedly as more 1 KB requests are issued
in parallel. Merging requests reduces this fan-out but may over-
fetch data, creating a trade-off between latency, request count, and
transferred bytes. Request count also determines GET charge. In
the common same-region setting, data transfer is not billed [4], so
GET requests are the primary monetary cost. Where transferred
bytes are billed, overfetch also incurs data-transfer charges.

2.3
Execution Pipeline and Planning Challenge
As illustrated in Figure 3, we target deployments in which cluster
payloads remain in object storage. For each query, we use a local
routing structure to select the nearest cluster centroids, then fetch
payloads that miss the local cache from object storage. Even when
an index fits in local memory, loading the entire index from object
storage before serving queries can be slow, while a QueryNode
serving multiple datasets may not have enough local capacity to
keep every index resident. The resulting pipeline exposes a key step
that has received little attention in prior work: deciding how to turn
the required payload accesses into actual object-store requests. We
call this step request planning. A direct implementation issues one
Range-GET per cache-missing cluster, so its request count grows
with cache misses. Request planning instead decides which nearby
reads to merge into fewer requests. Optimizing this step is the
focus of WaRP. After the planned Range-GETs complete, candidate
evaluation or reranking proceeds.

Cluster Payload Reordering
Request planning decides how to group required byte intervals into
requests, but it does not change the cluster layout. By exploiting re-
curring cluster co-access patterns, cluster payload reordering places
frequently co-accessed clusters closer together, thereby reducing
the gaps between required intervals. We call this property co-access
locality. In Figure 6, the original layout needs three requests to fetch
the required intervals without reading the large gaps between them.
After reordering, one request can fetch all required intervals while
overfetching only one extra cluster payload.
5.1
Layout Materialization and Maintenance
Cluster reordering runs offline during index build or rewrite.
Throughout our evaluation, we compute one cluster permutation
for the entire IVF index. We materialize the resulting cluster
layout by emitting payloads in that order during the existing
payload-writing phase. Each payload is still written once, so
reordering requires no additional rewrite or upload pass. Its only
added work is computing the permutation, which Section 7.4
shows takes milliseconds for thousands of clusters.
For indexes with incremental updates, newly added data gradu-
ally weakens co-access locality. Such indexes typically use rebuilds
or segment merges to maintain index quality. During these opera-
tions, the affected index data is rewritten. We recompute the cluster
permutation and apply it when writing this data. Thus, we update
the reordered cluster layout as part of normal index maintenance
without a separate rewrite pass. The next two subsections explain
how we measure co-access locality and compute the permutation.

S3 Vectors [5] are closed services, so we cannot instrument or
modify them. Lance is the open-source system that comes closest. It
includes a native IVF reader and a concurrent Range-GET scheduler
over S3, and is in production use for vector search today. Lance can
merge adjacent ranges within a batched I/O submission using a gap
threshold and a request-size cap. Its IVF reader, however, submits
probed clusters separately, so these heuristics do not apply across
clusters. We preserve this behavior in the end-to-end comparison.
We first evaluate end-to-end performance in Section 6.2. We then
study the effect of bounded caching in Section 6.3 and concurrency
scaling in Section 6.4. We use microbenchmarks in Section 7 to
examine request planning and reordering in more detail.

noted, all three methods use 𝑄= 32 and an I/O concurrency limit

6.2
Overall Performance
Across seven real-world datasets, we measure the end-to-end impact
of request planning and reordering. Figure 8a shows that Lance’s
p50 and p95 latencies plateau by an I/O concurrency limit of 2048,
so this setting does not limit performance.
Across all seven datasets in Figure 7, both WaRP variants improve
throughput and reduce GETs relative to Lance. WaRP alone reaches
1.06–2.89× Lance’s QPS and reduces GETs by 1.14–2.60×. Adding
reordering widens these ranges to 1.09–3.48× and 2.12–5.19×. Both
variants also reduce p95 and p99 latency on six of the seven datasets.
The exception is GIST1M. Its 960-dimensional vectors make each
cluster substantially larger, so each GET already amortizes more
fixed overhead and fixed request overhead accounts for a smaller
share of latency. A similar effect appears for the high-dimensional
datasets in Section 7.1.
Table 4 reports fetched bytes, overfetch, payload bandwidth, and
cost for the same 10,000-query workloads. Because merging fetches
extra bytes while increasing QPS, both WaRP variants use more
payload bandwidth than Lance. We apply Tokyo’s S3 price of $0.0037
per 10,000 GETs. Same-region data transfer is free, while the cross-
region case adds $0.09/GB for transfer to Northern Virginia [4].
Both variants lower same-region cost on all seven datasets, but
their cross-region cost is higher than Lance’s.
6.3
Effect of Caching
We also evaluate request planning with a warm cluster cache. The
SIFT100M IVF index contains 10.3 GiB of cluster data, and we al-
locate 10% and 50% of this size to Lance’s cluster cache. For each
setting, a fresh process first runs the same 10,000 queries to warm
the cache and then reports results from a second pass. In the three
rightmost groups of Figure 7, a 10% cache reduces remote GETs
by 4–8%, while throughput and p95 latency change little. At 50%,
remote GETs fall by 27–43%, and all three methods improve in
throughput and p95 latency. Both WaRP variants still outperform
Lance at both cache sizes. Caching and request planning are there-
fore complementary. Caching eliminates some remote reads, while
request planning reduces the cost of those that remain.
6.4
Concurrency Scaling
Finally, we test whether these gains persist as query load approaches
saturation. Using the SIFT100M setup from Section 6.2, we first vary
Lance’s I/O concurrency limit. As shown in Figure 8a, latency stops
improving beyond roughly 2,000 concurrent requests. We therefore
set the I/O concurrency limit to 2048 for the remaining experiments.
Figure 8b and Figure 8c then vary query concurrency 𝑄from 16
to 128. Both WaRP variants achieve higher throughput and lower
p95 latency than Lance across all tested concurrency levels. Lance
peaks at about 99 QPS at 𝑄= 64, whereas WaRP + Reorder reaches
about 150 QPS at 𝑄= 96. At 𝑄= 128, WaRP + Reorder still delivers
1.47× Lance’s QPS and reduces p95 latency by 1.46×, confirming
that its advantage persists near saturation.

Microbenchmarks
The remaining experiments isolate request planning and layout ef-
fects from the rest of the ANN query pipeline. Section 7.1 examines
the tradeoff between throughput and planned range reduction. Sec-
tion 7.2 tests robustness to planner parameters and the deployability
of greedy alternatives. Section 7.3 measures planner overhead and
the contribution of each optimization layer. Section 7.4 compares
reordering methods. Section 7.5 tests sensitivity to probe count and
cluster granularity.
Setup. Unless stated otherwise, the microbenchmarks use Faiss
(faiss-cpu v1.13.2) [32] to build an IVF-Flat index and store its cluster
payloads in a single flat file on S3. Within each experiment, all
methods receive the same selected cluster intervals and use the
same I/O concurrency limit. Reordered variants use PCA 𝑛-D +
Z-order with 𝑛selected as in Section 6.2, except in Section 7.4,
which compares the alternatives. We measure I/O completion only,
excluding distance computation and reranking.
Baselines. We compare WaRP with Separate, Lance, and Oracle-
Tuned Greedy. Separate issues one Range-GET per probed cluster
and serves as the reference for planned range reduction. Many
storage engines expose fixed thresholds for merging nearby reads.
Lance uses its default settings, which merge adjacent ranges when
their gap is at most 64 KB and split merged ranges larger than
16 MB. Oracle-Tuned Greedy tests a stronger fixed-threshold policy.
It sweeps gap thresholds from 64 KB to 16 MB and size limits from
1 MB to 32 MB, doubling both at each step for 54 settings in total. It
uses measured performance on each evaluation workload to select
the best setting, making it an optimistic reference within the tested
grid. We also pair Lance and Oracle-Tuned Greedy with reordering
to separate layout and request-planning effects.

Throughput and Planned Range Reduction
We then compare the methods at different planned range counts.
Across six datasets, we report how QPS and p95 latency change
with planned range reduction.
All runs use query concurrency 𝑄=4, an I/O concurrency limit of
64, 𝑃=16, 𝑛𝑙𝑖𝑠𝑡=4096, and 𝑛𝑝𝑟𝑜𝑏𝑒=128. To trace each WaRP curve,
we vary 𝐾to obtain merge plans with different planned range
counts. Each Greedy point represents one gap/span setting, while
Lance and Separate each produce one point per dataset.
Figure 9 shows that both too few and too many planned ranges
hurt performance. When the count is too low, the planner merges
distant intervals into large Range-GETs and therefore fetches more
unnecessary bytes. Too many planned ranges create small Range-
GETs that add per-request overhead and consume I/O slots. An in-
termediate count maximizes QPS and minimizes p95 latency. Across
all six datasets, WaRP + Reorder achieves the highest peak QPS.
Lance stays close to Separate under its default settings. Reordering
lifts it, but leaves a wide gap to WaRP + Reorder. Oracle-Tuned
Greedy matches WaRP + Reorder on several datasets once tuned to
its best setting. Its winning gap and span, however, differ widely
across datasets. The second experiment in Section 7.2 fixes one
setting in advance and tests how well it transfers.
The combined benefit of request planning and reordering
depends strongly on co-access locality. It is largest on SIFT1M and
DEEP1M, where throughput reaches about 3× that of Separate,
and smaller on GloVe. It is smallest on Random1M, whose i.i.d.
Gaussian vectors exhibit no co-access locality and leave reordering
with nothing to exploit. OpenImage and MSong fall below GloVe,
reaching only 1.6–1.7× the QPS of Separate, but for a different
reason. Under IVF-Flat their 512- and 420-dimensional vectors
make each cluster several times larger, so every GET already
amortizes more of its fixed overhead and merging has less left to
recover. Product quantization could reduce per-cluster payload
and increase the benefit of merging.
7.2
Parameter Robustness
We first examine how the choice of 𝑃affects WaRP and whether a
simple default works well across datasets and runtime conditions.
We then test whether Greedy’s gap and span settings, once tuned
on one workload, remain effective when the query workload or
dataset changes.
As defined in Section 3, 𝑃estimates how many requests from
one query can progress concurrently. We therefore use the I/O
concurrency limit divided by 𝑄as its default, corresponding to
an even share of the available I/O slots among concurrent queries.
Throughout the sweep, WaRP uses a request budget of 𝐾max=64. We
sweep 𝑃under three runtime configurations. The relaxed setting
uses query concurrency 𝑄=1 and an I/O concurrency limit of 64, the
moderate setting uses 𝑄=4 and a limit of 64, and the stressed setting
uses 𝑄=4 and a limit of 8. Figure 10 shows the results. QPS favors
larger 𝑃as more I/O concurrency becomes available to each query.
Stars mark the default 𝑃in each runtime configuration. Across the
18 panels, these defaults achieve on average 97% of the best QPS
reached by any tested 𝑃, so we can recommend this simple rule
without per-workload tuning.
We next test whether a Greedy policy tuned on validation queries
still works when the workload changes. Using an IVFPQ index on
SIFT1M with 4,096 partitions, we select the best gap and span from
the same 54-setting grid used for Oracle-Tuned Greedy, but select
them only on the validation workload and then keep them fixed.
We call the resulting policy SIFT-tuned Greedy. We evaluate this
fixed setting under four shifts. In the locality shift, the same amount
of required data is spread over a byte span about six times wider.
The probe-count shift increases 𝑛𝑝𝑟𝑜𝑏𝑒from 32 to 256. The joint
shift combines these two changes, and the dataset shift applies the
same setting to MSong. All runs use 𝑄=4 and an I/O concurrency
limit of 64, with WaRP at 𝑃=32 and 𝐾max=128. Figure 11 shows that
SIFT-tuned Greedy matches WaRP on the validation workload but
falls behind WaRP after the workload or dataset shifts.

We compare the reordering methods introduced in Section 5.3 based
on their offline computation time and the co-access locality they
produce. Figure 13 shows the results. We measure computation time
on cluster sets of size 𝐶∈{1024, 8192}, using random SIFT1M base

GloVe using the normalized weighted co-access gap 𝐺(𝜎)/𝐺(𝜎id)
defined in Section 5.2. Here, 𝜎is the permutation produced by a

𝐶=8192, closer to a production configuration, the spread widens.
The projection methods take 1.4–30 ms while the spectral methods

8
Related Work
ANN Indexes. ANN indexes include tree-based methods (KD-
trees [10], RP-trees [14]), hashing (LSH [22, 28]), partition methods
(IVF/IVFPQ [32, 33], IMI [8]), and graph methods (HNSW [37],
NSG [18]). These indexes are often paired with compression
schemes such as PQ [33], OPQ [21], and RabitQ [19]. Disk-aware
variants (DiskANN [30], SPANN [12], Starling [52], PipeANN [25],
PageANN [35]) reduce random I/O on local SSDs through graph
layout and pipelining. Dynamic and filtered variants have also
been studied [31, 48, 54, 55, 58]. WaRP instead operates after IVF
probe selection and optimizes retrieval of the selected clusters
from object storage.
Object Storage, Remote I/O, and Vector Retrieval. Within the same
region, object-store reads incur per-request charges and substantial
fixed latency, making request granularity and concurrency central
to throughput. AnyBlob [16] empirically identifies a request-size
sweet spot for analytics, while Delta Lake [7] highlights broader
object-store limitations, including costly metadata operations and
limited storage semantics. Vector systems use object storage at
different points in the serving path. Weaviate [53] and Qdrant [46]
serve active indexes from memory or local storage, while Milvus
full-load mode [39] caches object-store-resident segments before
search. Other designs access object storage during query process-
ing. Milvus Tiered Storage [40] fetches data chunks or whole per-
segment index files on demand, while turbopuffer [49] reads un-
cached data directly from object storage and caches it locally. Such
on-demand object-store access is useful when the full working set
cannot remain local or when loading an entire index before serving
queries is undesirable. For IVF indexes in this setting, WaRP reduces
the number of object-store requests by coalescing the byte intervals
of cache-missing cluster payloads into fewer Range-GETs. On this
query path, Lance [36] and the published Databricks design [15]
expose fixed gap or span thresholds for merging adjacent ranges.
WaRP instead formulates request merging as a global optimization
problem and provides an efficient planner. Our microbenchmarks
in Figure 9 compare WaRP with this fixed-threshold family and
show that WaRP + Reorder achieves the highest peak QPS across
all six datasets.
Data Reordering and Locality Optimization. Space-filling curves
such as Hilbert [34] and Z-order curves [43] have long been used
in databases to linearize multidimensional data while preserving
spatial locality [29]. Modern data lake systems such as Apache
Hudi [6] apply Z-order and Hilbert ordering to improve data skip-
ping and reduce I/O for analytical queries. In the disk-based ANN
setting, DiskANN++ [42] and Starling [52] reorder graph vertices
within fixed-size storage pages so that each page read contains
more useful neighbors. WaRP instead reorders variable-size IVF
cluster payloads in a flat object-store layout to reduce the gaps
among payloads likely to be probed together. The online planner
can then choose variable-length Range-GETs for each query. WaRP
therefore optimizes the layout for object-store request planning
rather than for a fixed-size read unit.
9
Conclusion
We present WaRP, a planner that optimizes how a vector index
issues requests to object storage. It uses a request-time surrogate to
estimate each request’s completion time and an optimized planning
algorithm that is fast enough to run on the query path. We also
introduce offline payload reordering to improve co-access locality
and create more merge opportunities. Across seven datasets, WaRP
+ Reorder delivers 1.09–3.48× Lance’s QPS and a 2.12–5.19× GET
reduction. Together, these results establish request planning as
a practical optimization layer between ANN probe selection and
object-store reads.
