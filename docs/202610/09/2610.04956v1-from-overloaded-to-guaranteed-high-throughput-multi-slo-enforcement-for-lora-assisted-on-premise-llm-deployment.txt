JING YANG, JIUCHEN SHI, CHEN CHEN, YOUMIN CHEN, YU FENG, and MINYI GUO, Shanghai Jiao Tong University, China As Large Language Models (LLMs) become essential in privacy-sensitive sectors like hospitals and government agencies, the on-premise LLM servers offer a cost-effective and secure alternative to public cloud services. However, these resource-constrained servers struggle to guarantee heterogeneous Service Level Objectives (SLOs) when serving multiple LoRA-adapted services simultaneously. Existing serving frameworks suffer from severe SLO violations due to the computational overhead of LoRA layers and the rigid nature of batch scheduling. To address this, we propose HALO, a scheduling method tailored for LoRA-assisted on-premise LLM deployment. HALO introduces two key innovations: a spatial multiplexing strategy that overlaps Base and LoRA computations by partitioning GPU Streaming Multiprocessors (SMs), and an SLO-aware scheduler that decouples request execution based on "request-level slack." By prioritizing urgent tasks and utilizing idle budget for traffic shaping, HALO significantly mitigates resource contention. Our evaluation demonstrates that HALO minimizes SLO violations while improving throughput compared to state-of-the-art baselines. 1 Introduction 

As LLMs achieve state-of-the-art performance in many domains[9, 24, 35], the on-premise LLM deployment has become the preferred choice for sensitive sectors like hospital and government[10, 11, 23, 36]. Compared to public LLM services like ChatGPT, the on-premise deployment offers two advantages: cost efficiency and data privacy. For instance, a single server equipped with four NVIDIA A100 GPUs costs about $150,000. In contrast, consuming the same volume of tokens via a public service can cost about $1,500,000 per year[5, 25]. More importantly, using LLM services have risks of exposing proprietary data to third-party providers. Figure 1 shows a hospital workflow served by such an on-premise LLM server. The server hosts four services, which share a frozen base model and use Low-Rank Adaptation (LoRA)[14] for task-specific optimization[6, 18, 30, 31]. These LoRA services have different Service Level Objectives (SLOs). For example, the Analysis Assistant requires a strict Time-to-First-Token (TTFT) of 1000ms for the prefill phase and Time-Between-Tokens (TBT) of 50ms for the decode phase. In contrast, the Intelligent Triage tolerates a looser latency budget (2000ms TTFT, 200ms TBT). Given the strict SLOs inherent to these workloads, efficient scheduling is critical. However, current on-premise LLM servers rely on the default scheduling policies of mainstream frameworks (vLLM[16] and SGLang[42]), which lack support for multi-SLO scheduling. These performance issues stem from two fundamental causes: LoRA-induced throughput degradation and SLO violations driven by blind batching. 

LoRA-induced throughput degradation. While existing frameworks adopt the chunked-prefill mode to improve system throughput, serving LoRAs still introduces non-negligible overhead. Specifically, chunked-prefill splits prefill into smaller chunks. Each chunk merges with the decode batch to form a mixed batch, improving the overall throughput. However, LoRA adds adapters on top of the model backbone and increases computation for both prefill and decode. Our results in §2.4.2 show that LoRAs bring an average 44.6% throughput drop. On resource-constrained on-premise hardware, this overhead intensifies resource contention and elevates SLO violations. 

SLO-unaware blind batching. While batching is essential for GPU efficiency, it forces all requests in a batch to advance in lockstep regardless of their individual SLOs. For example, serving Llama3-8B[13] with LoRAs on an A100 GPU yields a decode latency of 47ms at batch size 384 and 57ms at batch size 512. If we set the maximum decode batch size for 50ms targets, 100ms-target requests in the decode batch easily block newly arrived 50ms-target requests from entering computation due to the limited request slots. This further causes TTFT violations. If we set the maximum batch size for 100ms requests, the 50ms target requests directly suffer TBT violations. Although many works attempt to optimize SLO guarantees for LLM serving, they are insufficient for the constraints of on-premise servers. Specifically, Punica[6] reduces LoRA execution time via custom kernels, but it still suffers from sequential execution of LoRA adapters and base model operators. Meanwhile, VTC[32] and QoServe[12] focus on adjusting request serving order for inter-service fairness and SLO guarantees. Once a request enters computation, it does not leave the running batch. Therefore, no existing method addresses both the throughput degradation caused by LoRA and the SLO violations caused by blind batching. Under these circumstances, we identify two opportunities to improve the SLO guarantee in the on-premise LLM server. First, we could mitigate LoRA overhead via spatial multiplexing. By partitioning Streaming Multiprocessors (SMs) between frozen backbone (base layer) and LoRA layer, we could enable the concurrent execution of two layers. This further helps improve hardware utilization and end-to-end latency. Second, heterogeneous SLOs provide a resource dimension overlooked by existing work: temporal slack. Requests with relaxed SLOs such as TBT of 100ms have headroom relative to their deadlines in each decode iteration. When the actual decode latency is 50ms, a request with a 100ms TBT target can execute every two iterations without violating its SLO. those facing SLO violations. This helps on-premise LLM serving increase acceptable concurrency and heterogeneous SLO guarantees under resource constraints. However, capitalizing on these opportunities is non-trivial. First, determining the optimal SM partition involves a complex configuration space. The ideal split is highly sensitive to batch size, LoRA injection points (e.g., QKV vs. FFN), and hardware characteristics. This makes finding the ideal partition difficult. Second, as a request accumulates more slack, it could better improve concurrency. But once it exits, its accumulated slack drops to zero immediately. How to coordinate slack accumulation with attained throughput is a challenging problem. Furthermore, LLM inference has two stages. How to coordinate slack management across both stages to maximize system performance is another challenge. To this end, we propose HALO, a scheduling method for LoRA-assisted on-premise LLM servers. HALO consists of a lightweight partition searcher and an SLO-aware stage-unified scheduler. The lightweight partition searcher finds the optimal SM partition for each base-LoRA layer pair with minimal overhead. The SLO-aware stage-unified scheduler jointly manages slack across both stages. It flexibly adjusts the compute allocation between decode and prefill within each decode iteration to maximize SLO guarantees and system throughput. Specifically, during the serving framework initialization, the searcher automatically identifies the optimal SM partition for each base-LoRA layer pair under current hardware. To navigate the large configuration space, the searcher proposes a feedback-driven exploration strategy that minimizes the overhead. At runtime, the scheduler introduces a decoupling mechanism to maximize efficiency. It maintains an output token queue that releases generated tokens to the client precisely at their TTFT and TBT targets. This mechanism effectively acts as a traffic shaper, smoothing out bursts by buffering tokens generated during low-load periods and releasing them steadily at a high load. Further, the scheduler introduces a novel metric called request-level slack. It unifies slack from prefill and decode and consolidates fragmented slack into longer time slices. By monitoring this slack, the scheduler identifies requests that can bypass some decode iterations without violating TBT targets. This helps prioritize urgent tasks facing SLO violations. Specifically, these urgent requests may be in the prefill stage or the decode stage. The scheduler jointly manages request scheduling across both stages to support both TTFT and TBT guarantees. Our evaluation demonstrates that HALO effectively resolves resource contention in on-premise servers. Compared to state-of-the-art baselines, HALO improves P99 TTFT (99%-ile TTFT) by 2.1 ×

to 5.0 ×, and achieves 19.5% to 29.5% throughput improvement. The main contributions of this paper are as follows: 

• Characterization of Resource Contention. We identify that severe SLO violations in on-premise LLM servers stem from two primary sources: the computational overhead of LoRA layers and the blind batching mechanism. 

• Automated Spatial Multiplexing. We propose a lightweight partition searcher that spatially partitions SMs between Base and LoRA layers. This enables concurrent execution that effectively hides LoRA latency overhead without manual tuning. 

• SLO-aware Stage-unified Scheduling. We design a scheduler based on a novel request-level slack metric. This decouples request execution from batch processing, allowing the system to dynamically prioritize urgent tasks and utilize the latency budget of non-urgent requests.

2.1 LLM Basics 

2.1.1 LLM Model Structure. Modern large language models (LLMs), such as Llama[13] and Qwen[34], are primarily built upon the decode-only Transformer architecture. As shown in Figure 2, these models consist of a stack of identical transformer layers. Each transformer layer comprises two primary sub-layers: Self-Attention and a Feed-Forward Network (FFN). In the attention layer, input hidden states are projected into Query, Key, and Value vectors via weight matrices ( 𝑊 𝑄 , 𝑊 𝐾 , 𝑊 𝑉 ). The mechanism then computes attention scores to capture contextual dependencies between tokens, aggregating the results via an output projection ( 𝑊 𝑂 ). Subsequently, the FFN applies non-linear transformations, typically implemented as expansion (Gate/Up) and reduction (Down) projections. 

2.1.2 LLM Inference. LLM inference consists of two phases: prefill and decode. The prefill phase processes the input prompt to generate the first token, while the decode phase generates subsequent tokens autoregressively. Performance is evaluated against two SLOs: Time-To-First-Token (TTFT) for the prefill and Time-Between-Tokens (TBT) for the decode. While prefill is compute-bound, decode is memory-bound, easily suffering from low GPU uti-lization. To mitigate this, current systems (vLLM[16]/SGLang[42]) adopt chunked-prefill [1] as the default serving mode. It splits the prefill requests into smaller chunks. Each chunk merges with the decode batch to form a mixed batch for improving the GPU utilization and overall throughput. 

2.1.3 Low-Rank Adaptation (LoRA). Low-Rank Adaptation is a parameter-efficient fine-tuning technique designed to adapt pre-trained LLMs to specific downstream tasks [14]. As shown in Figure 2, instead of updating the massive weight matrix 𝑊 ∈ R𝑑 ×𝑑 , LoRA freezes 𝑊 and introduces two low-rank matrices, 𝐴 ∈ R𝑑 ×𝑟 and 𝐵 ∈ R𝑟 ×𝑑 . The rank 𝑟 is chosen to be significantly smaller than the weight dimensions 𝑑 . The forward pass is modified such that the output is ℎ = 𝑊 𝑥 + 𝐵𝐴𝑥 .When serving a single LoRA, we can merge 𝐵𝐴 into 𝑊 beforehand. However, when serving multiple LoRA adapters, weight merging is infeasible. The term 𝐵𝐴𝑥 must be computed explicitly.

2.4 Inefficiencies 

Since existing frameworks lack support for multi-SLO guarantees, current on-premise deployments set the maximum running batch size based on the strictest TBT target. Under the chunked-prefill mode, this maximum batch size limits the total size of the mixed batch (decode batch size + prefill chunk size). Meanwhile, because chunked-prefill prioritizes TBT over TTFT, existing systems rarely encounter TBT violations but mainly suffer from TTFT violations. 

2.4.1 SLO violations. In this experiment, we configure the LLM server with a single NVIDIA A100 GPU to host the four hospital services. The system serves Llama3-8B using SGLang[42] in chunked-prefill mode. The maximum batch size is set to 384 based on the 50ms TBT target. Figure 3(a) shows the TTFT violation rates across varying load levels (requests per second, RPS). As shown, services with strict SLOs begin to violate deadlines when the load exceeds 10 requests per second. After the load passes 12 requests per second, all services suffer significant violations. This demonstrates that the scheduling policies of existing frameworks fail to maintain SLOs under limited compute resources. 

2.4.2 Root Causes. Our in-depth analysis attributes these SLO violations to two primary ineffi-ciencies: sequential and inefficient LoRA execution, and SLO-agnostic blind batching. Firstly, we collect the latency and throughput performance with four LoRA services enabled. Our results show that LoRA-enabled inference suffers an average 94.5% latency increase and 44.6% throughput degradation (Input Length: 128 and 1024, Output Length: 8). This is because the base layer and LoRA layer execute sequentially even though they have no data dependency. To address this problem, Punica employs specialized kernels to accelerate LoRA execution. Figure 3(b) shows the normalized performance of LoRA-enabled serving compared to the vanilla baseline. It still incurs an average 31.7% latency degradation and 23.8% throughput degradation. This indicates that LoRA serving with Punica[6] still suffers from significant performance loss. Secondly, we show why existing systems suffer from SLO violations and why existing methods cannot solve this problem. Figure 4 shows the scheduling effects of the FCFS method and two state-of-the-art scheduling methods, VTC[32] and QoServe[12]. Specifically, VTC adjusts the request serving order to guarantee inter service fairness. This means multiple services process a fair number of tokens within a given time period. QoServe attempts to prioritize user-facing services and defer low-priority offline inference to optimize SLO guarantees. In addition, QoServe dynamically adjusts the maximum batch size based on the strictest user-facing service TBT target in the running batch to improve GPU utilization. 2.5 Opportunities and Challenges 

In a nutshell, while existing serving frameworks simplify multi-service deployment through batch-ing, they suffer from the throughput degradation inherent to LoRA computation and the rigidity of SLO-agnostic scheduling. Facing these limitations on resource-constrained on-premise LLM servers, we identify two major opportunities to improve performance. 

• We can reduce LoRA overhead using spatial multiplexing. By splitting the SMs between the base layer and the LoRA layer, we can run both components simultaneously. This parallelism aligns their completion times and improves the latency. 

• Heterogeneous SLOs provide a resource dimension overlooked by existing work: temporal slack. Requests with relaxed SLOs have headroom relative to their deadlines in each decode iteration. This slack can be used to increase the concurrency capacity and improve overall SLO guarantees. However, utilizing these two opportunities is non-trivial. First, implementing spatial multiplexing requires finding the optimal SM partition from a great search space. Finding the optimal one is challenging as it changes based on batch size and the specific LoRA layers used (e.g., QKV vs. FFN). Second, slack accumulation does not necessarily translate into throughput improvement. 3 Design Overview 

In this section, we present HALO, a scheduling method designed to enforce heterogeneous SLOs on resource-constrained on-premise LLM servers. As shown in Figure 5, HALO consists of two core components: a lightweight partition searcher and an SLO-aware stage-unified scheduler. The partition searcher addresses LoRA induced throughput degradation by finding the optimal SM partition for concurrent base-LoRA execution. The scheduler addresses SLO violations by exploiting temporal slack from heterogeneous SLOs. Specifically, it jointly manages request scheduling across both the prefill and decode stages to maximize SLO guarantees and system throughput. The workflow begins with the offline partition searcher, which automatically locates the optimal SM partition for each base-lora layer pair at different batch sizes. Since the optimal configuration varies significantly with LoRA injection points (e.g., QKV vs. FFN), batch size, and hardware char-acteristics, exhaustive search is infeasible. The searcher first automatically profiles the independent execution time of two layers at different SM ratios. Then, it utilizes a feedback-driven profiling method to locate the optimal resource configuration for each base-lora layer pair. At runtime, the SLO-aware stage-unified scheduler replaces default First-Come-First-Served policies with a deadline-aware mechanism. Upon arrival, each request is tagged with its specific SLO targets (TTFT and TBT). The scheduler continuously calculates a novel metric called request-level slack. This slack quantifies the dynamic headroom between the current time and the strict deadline of the next token to be generated. This metric unifies slack from both the prefill and decode stages, consolidating fragmented slack into actionable time slices. Requests with small slack are flagged as urgent for execution, while those with ample slack are candidates for deferral. Leveraging this analysis, the scheduler performs decoupled batch formation. It breaks the "lock-step" constraint of traditional batching by constructing execution batches that include only urgent requests and skip non-urgent ones. This allows requests with slack to yield their compute slots to urgent requests facing imminent TTFT or TBT violations in either the prefill or decode stage. By jointly managing scheduling across both stages, the scheduler flexibly adjusts the compute allocation between decode and prefill within each iteration to maximize SLO guarantees. Finally, the output token queue acts as a traffic shaper to decouple variable decode latency from the user experience. Generated tokens are buffered and released to the client strictly according to their TBT intervals. This smooths execution jitter, ensuring a steady stream of text. Crucially, this mechanism allows the system to "bank" time credits; if tokens are generated faster than required, the queue holds them, building a buffer that enables the scheduler to absorb future high-priority traffic bursts without violating SLOs. Note that the base-LoRA parallelism improves performance only during the decode phase and has no effect for the prefill, since LoRA computation during prefill already achieves high utilization. 

4 Lightweight Partition Searcher 4.1 Requirements and Challenges 

4.1.1 Requirements. While leveraging base-LoRA layer parallelism could improve system through-put, it imposes two critical requirements on the serving system. First, the system must be capable of identifying the optimal SM partition configuration for arbitrary models under varying execution contexts. Second, the configuration search process needs to run automatically during framework initialization, which makes it essential to use an exploration method with very low overhead so that startup latency remains minimal. 

4.1.2 Challenges. However, satisfying the above two requirements presents a non-trivial challenge due to the combinatorial explosion of the configuration space. First, current LoRA services insert adapters to all possible positions (QKV, O, Gate/Up, Down), but their ranks can be chosen independently[30, 40]. Second, modern frameworks rely on CUDA graph to accelerate execution, which requires capturing a separate CUDA graph for each batch size. As a result, the optimal SM partition must be prepared for every batch size before CUDA graph capture. Third, even for a single base-LoRA layer pair, the partition search space is already very large. 4.2.2 Search Algorithms. Based on these observations, we design a feedback based search method. The method proceeds in five stages. (1) We use 𝑛𝑐𝑢 to statistically measure the performance curves of the base layer and the LoRA layer with different SM allocations for every batch size setting. (2) Using these performance curves, we select the SM allocation for the base layer such that its performance drops by less than 10% from the optimum. We identify this point by collecting all performance spike points across the curves. At a spike point, such as 64 SMs for the Gate/Up layer, allocating 60 SMs leads to a performance drop of more than 10%, while increasing SMs yields no improvement of 10% or more. We find that these spikes have average improvement of 40.9%, which makes this cutoff a reliable way to preserve near optimal performance. (3) We choose the smallest SM number for the LoRA layer whose computation time is close to that of the base layer. When memory contention is ignored, this choice allows the two layers to finish at roughly the same time. (4) We fix the SM allocation for the base layer and gradually increase the allocation for the LoRA layer. As long as the decoding latency continues to improve, we keep increasing it. Once a performance drop is observed, we reverse direction and reduce the allocation until we reach the best performance point. (5) After fixing the SM allocation for the LoRA layer, we apply the same procedure to the base layer. We increase its allocation while decoding latency improves, and once performance degrades, we decrease it until the optimal point is found. Figure 7 illustrates an example of this search process. As shown in the figure, the method first identifies an initial allocation of 56 SMs and 8 SMs. It then adjusts the allocation for the base layer to refine this result, followed by adjustments to the allocation for the LoRA layer to further improve performance. Overall, this method finds a performance point within 1% of the optimal in 85.4% of cases, and in the remaining cases the performance loss is within 3%.

5.1 Current Workflow 

Since the decode phase easily suffers from low GPU utilization due to its memory-bound nature, existing systems (SGLang and vLLM) adopt chunked-prefill proposed by Sarathi-serve to improve overall GPU utilization and system throughput. Specifically, when a new request arrives, its prefill computation is divided into multiple prefill chunks. These chunks merge with the decode batch to form a mixed batch for execution. Under the chunked-prefill mode, every iteration includes the decode batch. This causes the system to prioritize TBT targets over TTFT targets. As a result, existing systems generally set the maximum running batch size based on the strictest TBT target. This value limits both the mixed batch and the normal batch. Figure 8(a) shows a specific scheduling example with a maximum batch size of 256. Initially, the decode batch size is 128. When R1 with an input length of 384 arrives, it is divided into multiple prefill chunks. The chunk size is calculated as max batch size minus decode batch size, which is 256 minus 128, giving 128. Therefore, the prefill computation of this request is divided into three prefill chunks. They participate in three decode iterations. After the three mixed batches complete, the serving system falls back to the normal decode batch with a batch size of 129. From the above process, existing systems are unaware of heterogeneous SLOs across requests. This causes requests with relaxed targets to occupy valuable request slots, leading to SLO violations for requests with strict targets. To address this, we attempt to break the blind batching in existing systems and exploit slack from relaxed requests to improve overall SLO guarantees. However, this introduces several challenges. 

5.2 Challenges for Efficient Scheduling 

First, the slack of a request is generated per token, but there is not always a need to exploit it due to the fluctuated workload. However, once a request exits, its accumulated slack becomes meaningless. More importantly, directly exploiting fragmented slack introduces significant scheduling overhead. Therefore, how to efficiently utilize fragmented slack is the first challenge. Second, each request has two stages: prefill and decode. When requests cannot enter the decode batch in time, they first suffer TTFT violations. This introduces the second challenge: how to jointly manage compute allocation across both stages. In addition, breaking blind batching also allows the system to exceed the preset maximum batch size. However, increasing running capacity without limits will eventually cause TBT violations. This introduces the third challenge: how to set the maximum running capacity to guarantee that TBT is not violated. 5.4 Stage-Unified Management 

After solving the first challenge, we propose stage unified management to address the second challenge. First, we derive an observation from managing the standard deviation of 𝑆𝑙𝑎𝑐𝑘 𝑟𝑒𝑞 across requests. We should consider how to minimize the standard deviation of 𝑆𝑙𝑎𝑐𝑘 𝑟𝑒𝑞 before a request enters computation. Therefore, when a request arrives, its initial 𝑆𝑙𝑎𝑐𝑘 𝑟𝑒𝑞 is zero. It should complete its computation as quickly as possible. By finishing computation sooner, we can reach an equilibrium of 𝑆𝑙𝑎𝑐𝑘 𝑟𝑒𝑞 across all requests faster. Therefore, whenever a new request arrives, we should yield slots from requests in the current decode batch that have available slack. These requests stop computation temporarily to help the new request finish its prefill computation as quickly as possible. For example, when multiple requests have accumulated slack of N decode iterations, they should yield their request slots for the next N iterations to accelerate prefill completion. Meanwhile, breaking blind batching removes the default maximum batch size constraint. How-ever, continuously increasing running capacity will eventually cause TBT violations. To avoid TBT violations, similar to the default scheduling policy, we need to calculate the maximum capacity under the current scheduling method. We find that we can compute the actual capacity usage based on TBT targets. For example, if the strictest TBT target is 50ms, a request with a 100ms target only participates in computation once every two iterations. This means its actual capacity usage is 0.5. Based on this calculation method, we can compute the actual capacity usage of all requests and ensure it remains below the originally set maximum batch size. This guarantees that HALO does not violate TBT targets. Finally, we apply the EDF (earliest deadline first) strategy to sort queued requests. Specifically, as shown in Figure 13, all baselines begin to suffer TTFT violations once RPS exceeds 13. This is because they cannot exploit TBT slack to enable earlier prefill computation. This is because long context requests (like 4K length) cause some decode iterations to exceed the TBT target (set based on 1K length). In contrast, HALO exploits TBT slack to serve newly arrived requests faster and reduce TTFT violations. It also uses TBT slack to mitigate TBT violations caused by long context lengths.

6.6 The Effect of Base-LoRA Parallelism 

Figure 15 shows the end-to-end decode latency improvement and the reduction in LoRA-induced overhead for four models under different batch sizes. As shown in the figure, when the sequence length is 128, base-LoRA parallelism achieves an average performance improvement of 8.3%, with a maximum improvement of 14.7%. It reduces LoRA-induced execution overhead by 31.1% on average and by up to 53.5% at maximum. These results demonstrate the effectiveness of base LoRA parallelism. When the sequence length increases to 1024, the average performance improvement decreases to 6.4%. This reduction occurs because, although base-LoRA parallelism itself is insensitive to sequence length, another major component of inference, attention computation, increases with sequence length. As the baseline decode latency grows, the relative benefit of base-LoRA parallelism becomes smaller. We also note that prefill is computationally intensive, and base-LoRA parallelism does not improve performance during the prefill phase. 

6.7 Ablation Study 

In this experiment, we conduct ablation studies to understand the contribution of each component of HALO. We construct HALO-P, which enables only base-LoRA parallelism, and HALO-S, which enables only SLO-aware scheduling. The experiment is performed on Llama3-8B using a single A100 GPU. Figure 16(a) shows the latency distribution for TTFT and TBT in the Hospital Scenario. HALO achieves 18.3%, 4.1%, and 10.3% throughput improvement compared to SLoRA, HALO-P, and HALO-S, respectively. The results show that enabling only base-LoRA parallelism still leads to significant SLO violations. In contrast, enabling only SLO-aware scheduling is constrained by sequential base-LoRA execution. These findings indicate that both components are necessary to achieve the performance benefits of HALO. This is because Llama3-8B with a batch size of 256 at sequence length 256 requires 49ms for decode computation. When the input length exceeds 256, the baselines suffer from severe TBT violations. On the other hand, if we set the maximum batch size below 256 such as 128, the decode computation encounters severe GPU underutilization. The results show that HALO continues to deliver strong performance and efficiently support GPUs beyond the A100. 

6.9 Overhead 

HALO’s overhead primarily comes from two sources. Firstly, HALO needs to determine the base-LoRA partition during the serving startup phase. Secondly, during runtime scheduling, HALO needs to decide which requests enter the running batch. For the partition search, the process requires 12.4 profiling runs on average. For a typical setup (𝑁 𝑙𝑜𝑟𝑎 = 4, 𝑁 𝑏𝑠 = 8, 𝑁 𝑐𝑜𝑛𝑓 = 12 .4,𝑇 𝑑𝑒𝑐𝑜𝑑𝑒 = 100 𝑚𝑠 ), the profiling time exceeds 39.7 seconds per model, which is tolerable for the framework startup. For the runtime scheduling, the sorting process on the CPU side is implemented using an asynchronous way, which involves no scheduling overhead. 

7 Related works 

LLM serving optimization: LLM serving optimization has attracted great attention. Existing work explores several directions, including compute management[1, 26, 43], memory management[16, 21, 42], and GPU kernel optimization[8, 39]. Splitwise[26] disaggregates LLM serving into separate prefill and decode instances, while chunked prefill[1] divides the prefill phase into smaller chunks and fuses each chunk with a decode iteration. PagedAttention[16] introduces a paged memory pool that enables reuse of key value caches across the prefill and decode phases. SGLang[42] exploits context aware caching to maximize reuse of key value segments across requests. FlashAttention[8] and FlashInfer[39] focus on designing specialized kernels to accelerate attention computation. These approaches target general improvements to the serving framework, and are orthogonal to the techniques proposed in HALO. 0:20 Zeshen Zhang, Han Zhao, Weihao Cui, Quan Chen, Yu Liu, Yongjun Deng, Jing Yang, Jiuchen Shi, Chen Chen, Youmin Chen, Yu Feng, and Minyi Guo 

LoRA serving optimization: Existing works[6, 19, 27, 31, 38, 40] on LoRA serving optimization largely fall into two categories. One line of work targets fast switching among multiple LoRAs, while the other focuses on reducing LoRA execution latency. SLoRA[31] enables scalable serving of thousands of adapters by introducing unified paging. LoRAX[27] supports just in time dynamic loading of adapters through a tiered caching (GPU, CPU, and disk). CaraServe[19] concentrates on the synchronization between CPU and GPU to hide the latency of fetching adapters. These systems are designed to handle scenarios where thousands of LoRA adapters. In contrast, an on-premise deployment typically supports only a small number of LoRA adapters, which makes these approaches ineffective. In addition, Punica[6] proposes a new CUDA kernel to accelerate LoRA execution. However, our results show that this optimization is still far from optimal when considering end-to-end latency. 

LLM scheduling strategy: Recent researches[7, 15, 32, 37] have devoted substantial effort to LLM scheduling strategies that aim to minimize average job completion time. LoRAServe[15] applies dynamic adapter placement and request routing to balance load across multiple GPUs. FastServe[37] uses preemptive scheduling to mitigate head of line blocking caused by long running requests. VTC[32] introduces a deficit round robin scheduler based on virtual tokens to provide fairness in LLM serving. SLOs-Serve[7] supports multiple SLOs and multi-instance deployment through dynamic request routing. While these approaches can reduce job completion time in certain scenarios, they do not address multi-SLO optimization in the on-premise LLM deployment. This is because the on-premise deployment generally has a single instance and tightly constrained computational resources. 

8 Conclusion 

In this paper, we present HALO, a specialized scheduling framework that addresses the performance bottlenecks of LoRA-enabled on-premise LLM servers in privacy-sensitive sectors. By introducing a spatial multiplexing strategy that partitions GPU Streaming Multiprocessors to overlap Base and LoRA computations, and an SLO-aware scheduler driven by "request-level slack," we successfully decouple execution from the constraints of rigid batching. Our evaluation demonstrates that HALO effectively mitigates resource contention and significantly reduces SLO violations while improving aggregate throughput compared to state-of-the-art baselines, providing a robust foundation for secure, high-performance local LLM inference.
