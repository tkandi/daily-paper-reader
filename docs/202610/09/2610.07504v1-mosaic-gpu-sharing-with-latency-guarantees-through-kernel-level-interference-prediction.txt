## Abstract 

GPUs are increasingly in demand for AI workloads, yet of-ten remain substantially underutilized, motivating workload colocation. However, colocation introduces interference that can degrade latency-critical workloads. Existing approaches mitigate interference using either heuristic-based scheduling or interference predictors. Heuristics rely on coarse-grained metrics that overlook important interference sources, while predictors often depend on simulator-specific or similarly coarse metrics. However, GPU interference is complex and arises from multiple mechanisms, including thread-block placement, memory hierarchy contention, and intra-SM re-source contention. We present Mosaic , a kernel-level interfer-ence predictor that explicitly models these mechanisms using a combination of analytical and lightweight learned models. Across four GPU architectures, Mosaic reduces prediction error by up to an order of magnitude compared to prior pre-dictors. We integrate Mosaic into a scheduler, MosaicSched ,that performs online kernel admission control and selects be-tween full-GPU colocation and SM partitioning to maximize best-effort throughput while satisfying latency SLOs. Across all workloads, MosaicSched keeps the p99 latency below or very close to the target SLO. 

## 1 Introduction 

Graphics Processing Units (GPUs) are widely used to train and serve modern AI models. As AI adoption continues to grow, so does the demand for GPU resources. Paradoxically, despite their high demand, GPUs are often substantially underutilized. A week-long study of a production ads in-ference service at Meta shows that the GPU utilization re-mained between 20%-40% over the entire period [5]. Mi-crosoft reports less than or equal to 50% GPU utilization across 400 training and inference jobs [11]. GPU underutiliza-tion can arise from various factors, such as communication and data-processing overheads, checkpointing, stragglers, small batch sizes, and varying resource demands across a workload [13, 15, 33, 34, 50]. Such underutilization results in significant cost and energy inefficiencies, as GPUs that are

A common approach to improve GPU utilization is to spatially colocate multiple workloads on the same GPU, al-lowing them to execute concurrently. There are two main approaches that GPU schedulers use to try to minimize interference. The first is relying on heuris-tics to guide scheduling decisions, using coarse resource characteristics such as Streaming Multiprocessor (SM) occu-pancy, memory bandwidth, or overall compute and memory resource usage [15, 32, 34]. The second approach is explicitly predicting the slowdown caused by colocation and using these predictions to guide scheduling [14, 37, 43, 47, 49]. While this should enable more informed scheduling decisions, it is challenging to accurately predict interference. Today’s predictors are inaccurate be-cause they either rely on simulator-specific metrics that do not generalize in real GPUs [37, 47, 49] or they use coarse-grained hardware statistics that fail to capture the diverse sources of GPU interference [14]. The above mechanisms are suboptimal because GPU inter-ference is a complex phenomenon. GPU interference arises from multiple distinct mechanisms—including thread-block placement, memory hierarchy contention, and intra-SM re-source contention—that existing heuristics and predictors ei-ther ignore or conflate [8]. Accurately modeling these mech-anisms is essential for practical interference-aware GPU scheduling. We present Mosaic, a kernel-level interference predictor that explicitly decomposes GPU interference into its dif-ferent sources and models each separately. Mosaic enables GPU schedulers to provide guarantees such as p99 latency SLOs. The Mosaic predictor design is guided by three key observations. First, accurately predicting slowdown requires capturing how kernels overlap in space and time, which in turn requires modeling thread-block placement across SMs. Second, aggregate hardware metrics such as memory bandwidth are often insufficient, as slowdown depends on finer-grained properties such as memory access behavior and latency-hiding capability. Third, while some interference mechanisms can be modeled analytically, others are better captured with lightweight learned models. Mosaic combines both to predict slowdown for kernels running on default CUDA streams or Green-Context-based streams that parti-tion GPU SMs. Across four GPU types (H100, A100, V100, and RTX-3090), Mosaic reduces prediction error by up to an order of magnitude compared to prior predictors. Using the Mosaic predictor, we build MosaicSched, a GPU scheduler that performs online admission control for best-effort kernels, in order to maintain p99 latency guarantees for the high-priority job. For every kernel submitted by the best-effort job, MosaicSched queries the predictor to get the estimated slowdown on the colocated high-priority ker-nel and admits the best-effort kernel only if and when the predicted end-to-end latency of the high-priority workload remains within a user-specified service level objective (SLO). MosaicSched also optimizes performance by automatically selecting between two colocation modes: 1) full-GPU coloca-tion, where both workloads can use all SMs and therefore dynamically share GPU resources, and 2) SM partitioning with CUDA Green Contexts [24], where each workload is restricted to a dedicated subset of SMs, reducing interference at the cost of limiting available resources. Across all work-loads and SLO targets, MosaicSched keeps the p99 latency below or very close to the target SLO. Our experiments also reveal important insights about GPU sharing. First, neither colocation mode is universally optimal. The tradeoff between full-GPU and SM partitioning colo-cation depends on the resource characteristics of both the high-priority and best-effort workloads. While full-GPU exe-cution offers more resources to best-effort kernels, it can also lead to stronger interference, reducing admission opportuni-ties for the best-effort kernels. Conversely, SM partitioning reduces interference but limits the throughput attainable by the admitted best-effort kernels, and the optimal partition depends strongly on the workloads’ compute and memory characteristics. Second, maximizing GPU utilization does not necessarily minimize deployment cost. While beneficial for many workload pairs, GPU sharing may require throttling the best-effort workload so extensively to meet the high-priority latency target that its completion time increases substantially, eliminating the cost advantage of sharing a single GPU. 

## 2 Background 

We describe the architecture of modern GPUs, focusing on NVIDIA GPUs and using NVIDIA/CUDA terminology. 

GPU architecture: NVIDIA GPUs consist of Stream-ing Multiprocessors (SMs), grouped into Texture Processing Clusters (TPCs). Each SM contains several subpartitions (SM-SPs), each with a warp scheduler, register file, and execution pipelines (e.g., FMA, Tensor Cores, LSU). Each SM has con-figurable on-chip memory that can be divided between L1 cache and shared memory (the L1/shared-memory carveout ), while all SMs share the L2 cache and off-chip memory. 

GPU programming model: Users submit work to the GPU by launching kernels, and specifying the number of blocks (grid size) and the number of threads (block size) for each kernel. Kernels and memory operations are submitted through streams, which enforce ordering among operations within a stream while allowing operations from different streams to execute concurrently. By default, a kernel’s blocks can execute on any available SM. CUDA Green Contexts al-low a stream to be associated with a subset of SMs, restricting its kernels to that partition [24]. 

Thread scheduling: Thread blocks are assigned to SMs and remain on the same SM until completion. The number of resident blocks per SM is limited by available threads, reg-isters, and shared memory. When a kernel has more blocks than can simultaneously reside on the GPU, its execution pro-ceeds in successive waves , where each wave consists of the blocks that can execute concurrently given these resource constraints. A GPU executes kernel threads at the granu-larity of warps, typically consisting of 32 threads. Once a block is scheduled on an SM, its warps are assigned to one of the subpartitions. ## 3 Why existing GPU schedulers are not enough 

Despite the growing demand for high-end GPUs, production clusters consistently exhibit low GPU utilization, leading to substantial cost and energy inefficiencies [5, 11, 19, 39]. Spatial colocation of GPU kernels is a promising way to im-prove utilization, both across workloads and within a work-load. Multiple works explore inter-workload GPU colocation (especially for inference jobs), since kernels from separate jobs are independent, and can potentially execute concur-rently [5, 15, 32, 34, 40]. Distributed training and inference systems commonly use intra-workload colocation to overlap communication and computation [2, 44, 46], and recent LLM inference frameworks such as NanoFlow [50] and Nexus [31] concurrently schedule compute-, memory-, and network-bound operators as well as prefill and decode phases. How-ever, concurrent execution can cause interference as kernels contend for shared GPU resources, including SMs and the memory hierarchy [8], potentially negating the benefits of colocation by increasing execution times for both intra- and inter-job settings [5, 31, 34], as shown in Figure 1. Conse-quently, effective GPU scheduling depends on accurately modeling kernel interference, which remains challenging for existing approaches. 

3.1 Heuristic-based GPU schedulers 

Table 1 summarizes existing GPU schedulers and indicates which sources of inter-SM and intra-SM interference they consider. No scheduler addresses all sources of GPU inter-ference. For example, Usher [32] colocates workloads based on their achieved occupancy and memory bandwidth usage, while iGniter[40] finds pairs for colocation based on their L2 cache usage. Reef [15] schedules kernels based on their SM demand, while Orion [34] additionally schedules kernels with complementary resource requirements. However, as Elvinger et al. [8] show, GPU interference arises from mul-tiple sources, making single-metric heuristics insufficient. Even LithOS [5], which partitions TPCs across concurrently executing kernels, does not account for contention in the shared L2 cache and memory subsystem. Although heuristics help guide scheduling decisions, the lack of accurate kernel- or workload-level interference pre-diction makes it impossible for these schedulers to give accu-rate performance guarantees. For example, when colocating an instance of GEMV from cuBLAS with different instances of cuBLAS GEMM or CUDNN Conv, on an RTX-3090 using separate SMs per kernel, the slowdown of GEMV due solely to inter-SM interference can vary from 1.02 × to 2.15 ×. Ex-isting GPU schedulers lack mechanisms to model or predict the degree of slowdown in each specific colocation scenario. As a result, they cannot distinguish between cases that cause minimal interference and those that lead to severe perfor-mance degradation, potentially resulting in SLO violations and suboptimal scheduling decisions. 

3.2 Existing interference predictors 

Existing GPU interference predictors operate at either the workload or kernel level. Workload-level approaches such as Horus [42], Abacus [6], and Mudi [3] rely on workload-specific features such as model architecture, layer types, or batch size—limiting their generality. Instead, kernel-level pre-dictors model interference between individual kernels and thus generalize better across applications. However, existing kernel-level predictors remain inadequate. Most kernel-level predictors are developed and evaluated in GPU simulators, re-lying on performance metrics that are unavailable or difficult to obtain on real GPUs [37, 47, 49]. Even methods designed for real hardware rely on coarse-grained performance coun-ters that fail to capture the complex interactions underlying kernel interference [14]. Our evaluation in section 6 con-firms that current predictors exhibit large prediction errors on modern GPUs, substantially under- or overestimating colocation-induced slowdowns. Foteini Strati, Ethan Graham, Leo Stephan, Paul Elvinger, and Ana Klimovic 

Interference prediction has also been studied extensively in CPUs [9, 10, 17, 35, 36] but existing techniques do not directly translate to GPUs because they similarly depend on simulation or fine-grained microarchitectural metrics that GPUs do not expose [9, 35, 36]. For example, CPI-stack-based methods assume execution cycles can be decomposed into well-defined stall sources, whereas GPUs’ massive thread-level parallelism and latency hiding make such attribution harder, and GPUs expose only limited microarchitectural state for fine-grained analysis [10, 17]. These limitations motivate the need for an accurate, hardware-based kernel-level interference predictor that generalizes across applications while capturing the diverse sources of GPU re-source contention. 

## 4 Mosaic: GPU kernel interference predictor 

We present Mosaic, a kernel-granularity GPU interference predictor. As shown in Figure 2, Mosaic takes as input two GPU kernels and their isolated execution profiles, collected using selected metrics from Nsight Systems and Nsight Com-pute. It outputs the expected slowdown of each kernel under colocation. Mosaic supports two execution modes: (1) strict SM separation, where concurrent kernels are assigned to disjoint SMs, e.g. using Green Contexts, and (2) full-GPU execution, where kernels may execute concurrently on the same SMs, as with default CUDA streams. Mosaic estimates slowdown with four main components: 

Thread-block placement (§4.1) models kernel overlap and block execution in the SMs; Block packing (§4.2) captures the slowdown caused when a kernel executes with a differ-ent per-SM block density than in isolation; Inter-SM inter-ference (§4.3) captures contention for shared L2 and HBM resources even when kernels occupy disjoint SMs; and Intra-SM interference (§4.4) captures contention for resources shared by blocks of different kernels executing on the same SM. Mosaic combines analytical models for structured be-haviors with lightweight learned models for the remaining effects. It selectively applies these components based on the execution mode, as described in §4.5. The remainder of this section presents each component, starting with empirical observations across four GPU types (H100, A100, RTX-3090, and V100) and a collection of kernels from Table 8, Appendix A. 4.3 Modeling Inter-SM interference 

When kernels execute on separate SMs, they contend for L2 capacity and bandwidth, as well as main memory bandwidth. The interference experienced by a kernel depends on both the pressure it places on the memory subsystem and its sensitivity to cache capacity and memory bandwidth. 

Observation 1: Memory interference is multidimensional. 

Aggregate memory throughput is insufficient to characterize inter-SM interference. Modern GPU memory systems exhibit multiple forms of contention, and read and write traffic affect colocated kernels differently. 

Figure 3. FDTD3d vs a memthrash kernel, colocating in separate SMs on an H100 GPU For example, Figure 3 shows the slowdown of FDTD3d [25] when colocated with memThrash, a custom microbenchmark that generates high L2 and global memory pressure while bypassing L1 using inline PTX. We vary memThrash’s write ratio from 0% (read-only) to 100% (write-only) in 10% incre-ments, while keeping the working sets of both kernels within L2. We execute FDTD3d and memThrash on 40 and 92 SMs, respectively, on an H100 GPU. FDTD3d experiences sub-stantially higher slowdown with read vs. write interference. Moreover, the aggregate bandwidth of memThrash increases as the slowdown of FDTD3d decreases, demonstrating that aggregate bandwidth alone does not capture the interference behavior. 

Observation 2: Latency tolerance determines slowdown. 

Contention in L2 capacity and bandwidth, and global mem-ory bandwidth, may translate to prolonged memory accesses. The extent to which a kernel tolerates this latency determines its performance degradation. For example, we consider silu-mul from FlashInfer [41] and FDTD3d [25] with similar L2 hit rates, L2 and HBM bandwidth, that are colocated with the same memThrash kernel. silumul experiences a slow-down of 1.3x while FDTD3d a larger slowdown of 2x. silumul has more eligible warps, higher compute-pipeline utilization, and fewer long-scoreboard stalls, indicating greater ability to tolerate increased memory latency. 

Implications for predictor design: These observations motivate a feature-based model that captures both memory pressure and latency tolerance. Mosaic distinguishes read and write traffic and includes separate L2 and HBM band-width metrics. To capture latency tolerance, we use eligible warps, stall behavior, and relative compute- and LSU-pipeline utilization. Mosaic uses a lightweight XGBoost [38] model to map the features in Table 2 to slowdown. A linear model is in-sufficient because the interaction between memory pressure and latency tolerance is nonlinear, whereas XGBoost cap-tures these interactions while remaining lightweight enough for practical prediction.

## 5 MosaicSched 

§4 described how Mosaic predicts the execution time of two colocated kernels. We now present MosaicSched, a GPU scheduler that uses the Mosaic predictor to enable colocating a high-priority (HP) job with a best-effort (BE) job while providing p99 latency guarantees for the high-priority job. Mosaic can be used to build GPU schedulers with different policies and targets, such as enforcing throughput or median latency SLOs. We focus on p99 latency here as tail latency is a key performance objective for GPU colocation and is particularly challenging to control under interference [5, 15, 16, 34]. As shown in Figure 5, MosaicSched takes as input a set of jobs (where one is designated as HP), a p99 latency SLO expressed a slowdown tolerance 𝑝 for the HP job’s p99 latency, and profiling information described in §4. The scheduler aims to maximize BE throughput while ensuring that the HP p99 slowdown remains within 𝑝 .We build MosaicSched on top of Orion [34], an open-source, state-of-the-art GPU scheduler that makes runtime, per-kernel scheduling decisions without modifying the un-derlying models. Mosaic is scheduler-agnostic and can also be integrated with schedulers operating at other granulari-ties, such as thread blocks [5, 48]. We retain Orion’s inter-ception mechanism but replace its scheduling policy with Mosaic-based admission control, described in §5.1. The sched-uler maintains the execution state of the HP and BE work-loads, including completed kernels, in-flight kernels, and their predicted completion times. We use CUDA events [21] to track kernel completion. Furthermore, MosaicSched se-lects between having the two jobs sharing the full GPU or enforcing strict SM separation. For the latter, we maintain a pool of streams associated with SM subsets created using Green Contexts; otherwise, the jobs execute on dedicated default CUDA streams 1. We select between these execution modes using offline profiling, as described in §5.2.

5.2 Selecting the GPU execution mode 

MosaicSched chooses between full-GPU sharing and strict SM separation to maximize BE throughput while remain-ing below the HP p99 slowdown tolerance. We perform this selection offline using short profiling runs for candidate con-figurations. We test full-GPU execution, where we run the scheduler using the user-specified slowdown tolerance 𝑝 

and measure BE throughput. We also test SM separation, where we first use Mosaic’s packing model (§4.2) to esti-mate the HP execution time for candidate SM allocations and discard allocations whose isolated slowdown already ex-ceeds 𝑝 . For each remaining allocation, we run the scheduler with adjusted slowdown tolerance with the corresponding Green Context configuration and measure BE throughput. MosaicSched selects the mode and SM allocation with the highest BE throughput. We restrict candidate SM allocations to multiples of eight to reduce the search space. Although the scheduler supports different allocations across consecutive HP kernels, in this paper, we use a fixed allocation to avoid the overhead of frequent Green Context transitions. 

5.3 Minimizing prediction overheads 

To reduce the overhead of computing predictions, we precom-pute engineered features, compile the XGBoost trees into optimized C++, and preallocate fixed-size feature vectors. These optimizations reduce prediction latency to approxi-mately 1 𝜇𝑠 for inter-SM prediction and 7 − 8 𝜇𝑠 for full-GPU prediction. Since kernels in ML workloads are repeated, we further reduce the prediction time by caching the predictions for unique pairs of kernels.

GPU scheduler baselines: We compare with default CUDA streams, a Green-Context baseline, and Orion [34]. ## 7 Discussion 

We discuss current limitations of the Mosaic predictor (§7.1) and applicability to GPUs from other vendors (§7.2). 

7.1 Limitations of the Mosaic predictor Power throttling and frequency deviations: Mosaic does not explicitly model the effects of power throttling, which can occur under spatial GPU co-location and reduce GPU frequency, thereby increasing kernel execution time. Our experiments show that throttling is relatively infrequent but varies across GPU generations and systems (e.g., on-premise H100 clusters vs cloud-based V100 instances), While some throttling effects may be implicitly captured by our XG-Boost learned models, further experimentation is necessary to model these effects. 

No support for CUDA stream priorities: The thread block placement predictor (§4.1) assumes equal CUDA stream priorities. Stream priorities can influence scheduling by fa-voring thread blocks from higher-priority streams when they are available, thereby altering block interleaving and execu-tion time. Supporting priorities is future work. 

GPU-specific model calibration: The inter- and intra-SM XGBoost models and analytical parameters (§4.4) are calibrated per GPU, so supporting new GPU generations requires retraining. Reducing this overhead is future work. Foteini Strati, Ethan Graham, Leo Stephan, Paul Elvinger, and Ana Klimovic 

7.2 Applicability to AMD GPUs 

Although we focus on NVIDIA GPUs, we have also experi-mented with AMD GPUs. Several Mosaic components trans-fer directly. For example, L2-cache and memory interfer-ence can be modeled accurately using XGBoost and existing features. However, AMD’s greedy thread-block scheduler can mix blocks from different kernels, unlike the behavior observed in §4.1. Thus, extending Mosaic to AMD GPUs is feasible but requires adapting its scheduling model to vendor-specific behavior. 

## 8 Conclusion 

We presented Mosaic, an accurate and lightweight kernel-level predictor for GPU interference. Mosaic combines ana-lytical models for thread block scheduling, warp scheduling, and compute pipeline contention with xgboost models for the memory subsystem, achieving up to an order of mag-nitude lower p50 and p95 error than prior predictors while keeping per-prediction latency in the microsecond range. Using Mosaic, we built MosaicSched, a GPU scheduler for workload colocation. We demonstrated that it enables ex-plicit, user-defined performance guarantees for high-priority jobs while admitting best-effort work whenever headroom allows, improving GPU utilization with reliable guarantees.
