# TRANSIT: Transparent Scale-in for Multi-Node LLM Training 

## Hyungyo Kim 1† , Nicholas Satchanov 1, Hrishi Shah 1, Gaohan Ye 1, Jiaqi Lou 1,Robert Walkup 2, Shweta Salaria 2, I-Hsin Chung 2, Hubertus Franke 2,Seetharami Seelam 2, Apoorve Mohan 2∗ , Nam Sung Kim 1∗ 1University of Illinois at Urbana-Champaign 2IBM Research 

## Abstract 

TRANSIT is a transparent scale-in framework to enable multi-node model training on fewer GPUs while maintaining train-ing efficiency by transparently leveraging CPU DRAM as an extension of GPU memory during distributed training. It achieves this through a user-space interposition layer, requir-ing no modifications to the application, training framework, cluster scheduler, device driver, or operating system. Fur-thermore, TRANSIT achieves higher efficiency by leveraging a zero-copy data path for CPU-GPU transfers. We evaluate TRANSIT on dense and MoE models across scales up to 64 NVIDIA H100 GPUs and multiple parallelism configurations over a RoCE network. Our evaluation shows that TRANSIT can: (a) outperform state-of-the-art framework-managed offloading techniques, achieving up to 68%, 59%, and 42% higher per-GPU throughput than TorchTitan, ZeRO-Offload, and ZeRO-Infinity, respectively, (b) enables training with 50% fewer GPUs while maintaining over 90% of baseline per-GPU throughput, (c) lower per-node network traffic by up to 33%, and (d) improve per-GPU throughput by up to 35% in communication-bound settings. 

## 1 Introduction 

Motivation: The cost of training large AI models has grown to the point where it shapes fundamental decisions about in-frastructure, methodology, and organizational strategy [16]. A common root cause underlies the constraints practition-ers face: GPU memory cannot accommodate modern models within a reasonable number of devices [21], forcing scale-out across additional GPUs for memory capacity. For many orga-nizations, training may fail before it begins due to GPU short-ages, procurement overheads, export controls, and budget constraints, leaving sufficient GPU capacity unavailable [18]. For those who can provision enough GPUs, scale-out in-troduces a new problem: as the number of GPUs increases to meet memory requirements, so does the number of par-ticipants in collective operations, increasing communication

Memory capacity and communication demand are therefore coupled through node count: adding nodes to relieve one constraint tightens the other. This sensitivity is exacerbated by datacenter network de-sign. Oversubscribed spine layers reduce effective bandwidth under load [20, 37, 44], and synchronized collective commu-nication can induce congestion and unpredictable perfor-mance [17, 22, 44, 54]. Prior work on production RDMA-based AI training clusters shows that network contention degrades performance in up to ∼36% of training jobs [17], where congestion alone can cause slowdowns exceeding 30% [38, 42], and up to 50% under packet loss [11]. These results highlight the fragility of collective communication in modern AI clusters and the increasing likelihood of network bottlenecks as systems scale out. Such scale-out ultimately affects cluster efficiency, as train-ing jobs are forced to be provisioned with a static resource configuration. Users specify the number of GPUs required for a training job, and the scheduler must allocate the exact number requested before execution can begin. Thus, if the exact requested number of GPUs is not immediately avail-able at the time of submission, jobs are forced to wait in the queue [23, 25, 35, 51]. This delay is particularly costly in development environments, where rapid iteration often matters more than peak throughput. 

Questions: The limitations practitioners face, i.e., in-frastructure cost, GPU memory capacity, and network con-straints in oversubscribed and congested scale-out AI clus-ters, thus prompt the following questions: (i) Is it possible to enable multi-node training of models on fewer GPUs with-out modifying or requiring support from existing training frameworks, while preserving per-GPU performance? (iii) Does reducing node count translate into measurable reductions in rack-level and spine-level net-work traffic in datacenter deployments? Opportunity: Modern GPU servers provision hundreds of gigabytes to terabytes of CPU DRAM capacity, far exceed-ing GPU HBM, and unlike remote GPU memory, accessing this capacity does not require inter-node communication. Critically, local DRAM access over PCIe is 4–6× faster than remote GPU HBM access via GPUDirect RDMA for small transfers, narrowing to 2–3 × at larger sizes, with the gap widening further under network congestion (see §2.3). Ab-sorbing memory overflow locally rather than distributing it across the network can therefore reduce communication vol-ume, lower sensitivity to inter-node bandwidth, and enable training configurations that the GPU memory limit would otherwise preclude. 

Prior Art: Several recent efforts have explored ways to extend effective GPU memory capacity for LLM train-ing [27, 30, 40, 41, 53]; however, they suffer from various limitations (see Table 1). The most widely adopted scale-in approaches today rely on framework-managed offloading systems such as ZeRO-Offload [41], ZeRO-Infinity [40], and TorchTitan [30]. These systems explicitly manage model parameters, gradients, and optimizer states to extend ef-fective GPU memory capacity. While effective at enabling larger models to fit, they require framework-specific integra-tion and support, limiting deployment across heterogeneous training environments. Furthermore, they typically manage memory at a coarse granularity and move substantially more data than the workload actually requires, thus leading to in-efficiency (see §4.2). An alternative is Unified Virtual Memory (UVM) [2, 13], a virtual memory abstraction supported in modern GPU runtimes that transparently extends GPU memory capac-ity using host memory without requiring modifications to applications or training frameworks. UVM is therefore an at-tractive foundation for transparent scale-in. However, UVM is rarely used as the default mechanism for large-scale train-ing because its performance is "widely perceived to be in-efficient" [4]. Recent works have sought to improve UVM performance by modifying runtimes, kernels, and device drivers [27, 53]. While effective in controlled settings, their reliance on privileged changes to the system software stack limits deployability in large-scale shared clusters. As a result, they have been demonstrated only within a single node, leav-ing their practicality for large-scale distributed training less established. Consequently, no existing approach simultane-ously satisfies the requirements of transparency, efficiency, deployability, and distributed scalability. Finally, existing approaches do not support multiple data movement policies. 

Requirements: For scale-in to deliver cluster-wide ben-efits, it must satisfy the following requirements: First , it must preserve training efficiency: saving GPUs while pro-portionally extending training time leaves cluster efficiency unchanged. Second , it must be transparent and broadly de-ployable, requiring no modifications to applications, frame-works, schedulers, runtimes, or device drivers. Third , it must be effective in distributed multi-node environments, where memory pressure and communication overhead are most pronounced. Fourth , it must be fine-grained to minimize data movement between CPU memory and GPU memory, thereby limiting its impact on training efficiency. 

Our Approach: We present TRANSIT (TRANsparent Scale-In for Training), a lightweight scale-in framework for dis-tributed LLM training workloads. TRANSIT enables existing training workloads to execute on fewer GPUs without requir-ing modifications to applications, frameworks, schedulers, kernels, or device drivers. It transparently instruments LLM training workloads at execution time to leverage CPU DRAM as an extension of GPU HBM using UVM. TRANSIT further extends UVM capabilities to augment or override its default reactive behavior at execution time, enabling policies such as fused prefetching and zero-copy access. Zero-copy allows the GPU to directly fetch CPU-resident data into the GPU L2 cache without copying it to GPU HBM, reducing data movement overhead (see §3). At a high level, TRANSIT comprises three components: a memory allocation interceptor that transparently redirects all GPU memory allocations (e.g., parameters, gradients, op-timizer states, and activations) to UVM-backed memory; an activity recorder that captures kernel launch activity and migration history; and a policy optimizer that reduces data transfer overhead between CPU and GPU memories. 

TRANSIT tracks all managed memory allocations to un-derstand memory allocation patterns during initial training iterations (i.e., warm-up period) and strategically applies optimization policies at key points during each training iter-ation (e.g., around the midpoint of the iteration) to minimize data movement overhead between CPU and GPU memory. This allows frequently reused data, such as activations and half-precision model parameters, to remain resident in GPU memory, while less frequently accessed data (including opti-mizer states and full-precision parameters), is accessed di-rectly from host memory through zero-copy. As a result, our approach significantly reduces unnecessary page migrations and page faults, improving overall training efficiency.

## 2 Background and Motivation 

2.1 Distributed LLM Training 

A typical node in a modern GPU cluster consists of 4 to 8 GPUs, interconnected via high-speed, low-latency fabrics such as NVIDIA NVLink [10] or AMD Infinity Fabric [6], pro-viding on the order of hundreds of Gbps of bandwidth. Each node is further equipped with multiple high-performance NICs ( e.g., NVIDIA Mellanox ConnectX [3]), each typically providing 100–400 Gbps of bandwidth, to support high ag-gregate network throughput. Across nodes, communication relies on either Infini-Band [8] or Ethernet-based networking. InfiniBand provides low latency and high bandwidth with native RDMA support, while RDMA over Converged Ethernet (RoCE) [1] offers sim-ilar zero-copy semantics over Ethernet infrastructure. Com-bined with GPUDirect RDMA (GDR) [5] or PeerDirect [7], these technologies enable direct GPU-to-GPU communica-tion across nodes, bypassing CPU staging buffers and reduc-ing communication overhead during collective operations. To accommodate the large memory footprint of the model states, modern LLM training frameworks employ a combina-tion of parallelization techniques across multiple dimensions. Within a node, tensor parallelism (TP) [43] is commonly used to exploit high-bandwidth interconnects by partition-ing model parameters across GPUs and performing fine-grained collective operations. Across nodes, pipeline paral-lelism (PP) [26, 33] partitions layers into stages to distribute memory and computation, while fully sharded data paral-lelism (FSDP) [30] and ZeRO [39] partition model parameters, gradients, and optimizer states across data-parallel work-ers, trading additional communication for improved mem-ory efficiency. More recently, expert parallelism (EP) [29] has been introduced for Mixture-of-Experts (MoE) models, distributing experts across devices and incurring all-to-all communication depending on routing decisions. In practice, these strategies are composed into hybrid multi-dimensional parallelism configurations [30, 43, 48]. Through such multi-dimensional parallelism, the aggregate memory capacity of the cluster is effectively pooled, enabling models to be trained beyond the limits of a single device or node, while introducing corresponding communication and coordination overheads that must be carefully managed. 

2.2 Scale-Out vs. Stragglers and Failures 

Distributed training relies on tightly synchronized execu-tion across GPUs, where collective operations ( e.g., all-gather, reduce-scatter) introduce global barriers. Thus, each iteration is gated by the slowest participating device, making training highly sensitive to tail behavior. Even a single GPU or node experiencing degraded performance—due to network con-gestion, transient interference, or resource contention—can delay the entire job [32, 50]. In our experiments, limiting the NIC bandwidth of a single node to 100 Gbps while others op-erate at 400 Gbps reduces training throughput by 50% when training Llama4-Scout on 64 H100 GPUs across 16 nodes. Scale-out further increases exposure to failures: as a job spans more GPUs and nodes, the probability of at least one unavailable component rises, while recovery requires more simultaneously healthy replacement resources. Reducing the number of nodes required to train a model therefore mitigates both stragglers and failures by involving fewer participants and reducing traffic across shared network in-frastructure.

2.3 Local DRAM vs. Remote GPU HBM Access 

During distributed training, collective communication gath-ers and reconstructs model states that are partitioned across GPUs. Consequently, each device frequently accesses remote HBM residing on GPUs in other nodes. Remote access in-curs additional overheads due to network latency, synchro-nization, and contention, making the effective access cost significantly higher. In contrast, CPU DRAM within a node provides a large-capacity memory tier that can be accessed without inter-node communication. While DRAM access over PCIe has lower bandwidth and higher latency than local HBM, it avoids distributed communication overheads such as collective synchronization and network-induced variability. Figure 1 compares the latency of fetching data from lo-cal CPU DRAM with that of accessing remote GPU HBM on another node via GPUDirect RDMA (GDR) on an H100 system. We evaluate a range of transfer sizes, where local CPU–GPU communication occurs over PCIe Gen5, while remote accesses traverse a 400 Gbps ConnectX-7 (CX-7) NIC. For small transfers, local DRAM access is 4–6 × faster than remote HBM, primarily due to the absence of network round-trip latency and synchronization overheads. As transfer size increases, this gap narrows to 2–3 ×, as higher bandwidth al-lows remote HBM accesses to better amortize their fixed over-heads. However, remote accesses continue to incur coordina-tion and potential congestion costs that are absent from local memory accesses. As discussed in Section 1, these commu-nication overheads become increasingly dominant at scale, particularly in oversubscribed datacenter networks where ef-fective bandwidth degrades under contention [38, 42]. These results reveal an opportunity to improve performance in communication-bound regimes by prioritizing local DRAM over remote HBM, thereby avoiding network overheads and reducing sensitivity to congestion. cudaMalloc  cudaMallocManaged

## 3 TRANSIT Overview 

We present TRANSIT (TRANsparent Scale-In for Training), a framework that transparently instruments distributed train-ing workloads at execution time to leverage CPU DRAM as an extension of GPU HBM, without modifying the applica-tion, training framework, or cluster scheduler. 

3.1 Design 

The design of TRANSIT follows the requirements established in Section 1: preserving training efficiency, remaining trans-parent and deployable, operating effectively at multi-node scale, and minimizing unnecessary CPU–GPU data move-ment. To satisfy these requirements, TRANSIT builds on NVIDIA’s UVM as a transparent memory substrate and aug-ments it with runtime-guided optimization policies. Modern GPU runtime and driver ecosystems expose ab-stractions that naturally support transparent memory man-agement: UVM enables dynamic data movement between GPU HBM and CPU DRAM without application involvement. In practice, however, these mechanisms are rarely used in distributed training due to their high and unpredictable la-tency overheads under the default reactive page-fault policy. 

TRANSIT leverages this ecosystem as its substrate and aug-ments it with runtime-driven optimization policies that ad-dress the second and third requirements, converting reactive, fine-grained fault-driven behavior into proactive, overlap-friendly data movement guided by observed access patterns. As shown in Figure 2, TRANSIT comprises three compo-nents: a memory allocation interceptor, an activity recorder, and optimization policies. The interceptor transparently redi-rects all GPU memory allocations to UVM-backed memory, enabling oversubscription without application changes. The activity recorder captures kernel launch activity and migra-tion history during a short warm-up phase, providing the runtime observations that guide placement decisions. The op-timization policies use these observations to improve UVM efficiency while preserving full transparency. Together, these components realize the requirements above: the interceptor

3.2 Opportunity for Prefetch and Zero-copy 

NVIDIA introduced Unified Virtual Memory (UVM) in CUDA 6 [13], providing a unified address space shared by CPU and GPU. Under UVM, memory allocated via 

cudaMallocManaged is accessible from both processors, and the runtime transparently manages data placement by mi-grating pages on demand or enabling direct access when possible. This abstraction eliminates the need for explicit host–device memory copies, simplifying programming while allowing applications to operate on datasets that exceed the physical GPU memory capacity. When a GPU accesses a page not resident in GPU memory, the default UVM behavior is to trigger a page fault and mi-grate the page from CPU memory. As shown in the red path in Figure 3, when CUDA/Tensor cores issue a memory access to a page not resident in GPU memory, address translation misses in the TLB and the page table walk detects a non-resident page, triggering a page fault. The fault is buffered in the GMMU and forwarded to the UVM driver on the host CPU. If GPU memory is oversubscribed, resident pages may be evicted to free space. The requested page is then migrated from CPU memory to GPU memory via DMA, the page table is updated, and the faulting warp resumes after stalling. Such migration introduces significant latency overhead when a page fault occurs. 

Runtime guidance mechanisms for UVM. While the default UVM behavior uses on-demand paging, 

cudaMemAdviseSetAccessedBy allows a given processor (e.g., a specific GPU) to maintain valid page table mappings and directly access data via zero-copy even when it is not resident on that processor. These two paths exhibit different performance trade-offs. Page migration is beneficial when data exhibits high tempo-ral locality, as the cost of transferring a page to GPU memory can be amortized over many subsequent accesses. In contrast, zero-copy is preferable for data with low reuse or streaming access patterns, as it avoids the overhead of page faults and migration by servicing accesses directly from CPU memory. In addition, cudaMemPrefetchAsync provides an explicit mechanism to proactively migrate memory pages to a tar-get device before they are accessed. Unlike demand pag-ing, which reacts to page faults, prefetching allows data movement to be overlapped with computation and reduces stall latency during execution. Prefetching can be issued asynchronously on a CUDA stream, enabling finer-grained control over data movement without requiring full manual memory management. 

Migration pattern during LLM training. LLM training workloads exhibit structured spatial and temporal locality across tensors, including parameters, gradients, optimizer states, and activations. Spatial locality arises within each tensor due to contiguous accesses, while temporal locality varies across tensors: some are accessed repeatedly within short windows, whereas others are touched only once per iteration. During the forward pass, parameters are accessed layer by layer to produce activations, which are revisited in the backward pass. Consequently, parameters, activations, and their gradients are accessed multiple times within an iteration, especially when multiple forward and backward passes are performed before an update ( i.e., due to gradient accumulation). In contrast, optimizer states and the higher-precision parameter copies used for updates are accessed primarily during the parameter update step, resulting in more temporally separated access patterns. We therefore ex-plore runtime-guided UVM mechanisms that exploit these locality patterns by adapting data movement and access be-havior during execution. 

3.3 Implementation 

TRANSIT is implemented as a user-space shared library, injected via LD_PRELOAD at job launch time. This allows 

TRANSIT to interpose on CUDA runtime APIs without modi-fying or recompiling the original program. As shown in Fig-ure 2, TRANSIT interposes on CUDA memory management APIs, redirecting device allocation calls to UVM-backed al-locations at runtime. For example, cudaMalloc is replaced with cudaMallocManaged , ensuring that all allocations (in-cluding model parameters, gradients, optimizer states, and intermediate activations) reside in a unified virtual address space accessible from both CPU and GPU. We verify that this interception covers the full training set by ensuring that all GPU memory allocations route through this path. By do-ing so, TRANSIT enables seamless memory oversubscription beyond physical GPU capacity, allowing training to proceed even when the working memory size exceeds device mem-ory limits, while preserving original program semantics and execution flow. In contrast to prior approaches that require explicit user annotations, API changes, or deep integration into training frameworks, TRANSIT is entirely transparent and immediately deployable across a wide range of work-loads. This configuration corresponds to TRANSIT -Base. While TRANSIT -Base provides transparent oversubscrip-tion, its default reactive behavior leads to two key inefficien-cies under memory oversubscription. First, page-fault-driven migrations are inherently fine-grained, clustering in the KB-to-tens-of-KB range and poorly amortizing per-migration overheads such as fault handling, scheduling, and DMA setup, resulting in low effective PCIe bandwidth. Second, the interaction between on-demand migration and UVM’s heuristic eviction policy leads to data thrashing: different working sets take turns occupying limited GPU memory, generating redundant transfers and repeated page table up-dates. 3.4 Policy Exploration 

We denote the unoptimized baseline as TRANSIT -Base, which relies solely on default UVM behavior without additional optimization. While TRANSIT -Base provides transparency by automatically managing data placement and migration through UVM, its default behavior driven by reactive page-fault handling often leads to inefficient data movement un-der memory oversubscription. In particular, two key limi-tations arise. First, page-fault-driven migrations are inher-ently fine-grained, resulting in low effective bandwidth due to poor amortization of per-migration overheads. Second, the interaction between on-demand migration and UVM’s heuristic, access-driven eviction policy can lead to frequent page movement and thrashing. To address these limita-tions, TRANSIT implements two complementary policies that improve UVM behavior without sacrificing transparency. First, TRANSIT -Prefetch introduces a merged prefetching mechanism that transforms fine-grained, fault-driven mi-grations into coarse-grained transfers, improving migration efficiency. Second, TRANSIT -Advise leverages zero-copy ac-cess via cudaMemAdvise to reduce unnecessary data move-ment and stabilize data placement. Note that both techniques operate entirely in user space and require no modifications to applications, training frameworks, or the UVM driver.

Improving migration efficiency. To mitigate the ineffi-ciency arising from fine-grained HtoD migrations, TRANSIT -Prefetch coalesces the migration events. The key observa-tion is that although HtoD migrations are triggered by page faults, these faults tend to exhibit strong spatial locality dur-ing LLM training due to accesses to large tensor objects (Fig-ure 4). TRANSIT -Prefetch first profiles HtoD migration events for two warm-up training iterations using CUPTI unified-memory counters while concurrently recording kernel ac-tivity. To associate each migration with a kernel, TRANSIT -Prefetch injects an external correlation ID at every kernel launch that uniquely labels each kernel launch by its order within that iteration. Each migration event is assigned to the most likely kernel based on timestamps and the external correlation ID. From the assigned events, TRANSIT -Prefetch constructs per-kernel address ranges [addr, addr+bytes) 

and coalesces them to amortize the migration overhead. In addition to merging contiguous regions, it merges ranges whose gap is within a fixed threshold ( e.g., 128KB), which reduces the number of prefetch calls and increases effective migration granularity. After profiling completes, profiling is disabled and the final per-kernel mapping is used for replay: on each subsequent kernel launch, TRANSIT -Prefetch issues 

cuMemPrefetchAsync for the merged ranges on the same CUDA stream prior to kernel execution. Figure 5 shows that TRANSIT -Prefetch significantly re-duces the number of small-sized migrations by merging them into larger transfers. As a result, large migrations ( i.e., 

>1 MB) dominate, where migration throughput is substan-tially higher. By prefetching data prior to kernel execution, 

TRANSIT -Prefetch also avoids page-fault-driven on-demand migrations, thereby eliminating fault events. Figure 6 shows that TRANSIT -Prefetch reduces page faults by 97% while in-creasing average PCIe bandwidth utilization by 2.4 ×.

(b) TRANSIT -Advise. While TRANSIT -Prefetch improves the efficiency of on-demand migration, it does not funda-mentally alter the data placement dynamics of UVM. Under memory oversubscription, UVM migrates data between host and GPU memory on demand. When new data is brought into GPU memory, existing data must be evicted to make space, resulting in a tightly coupled migration–eviction cy-cle. As a result, different working sets take turns occupying limited GPU memory in a round-robin-like manner, leading to severe data thrashing. For example, when training a 6B-parameter variant of Llama (derived from the 8B model) with UVM, even a modest oversubscription of 10 GB beyond a single H100 GPU’s 94 GB memory capacity causes the entire working set to be migrated at least once. This back-and-forth movement not only incurs redundant data transfers but also introduces additional overhead from repeated page table updates, ultimately degrading performance. Zero-copy ad-dresses this limitation by allowing such data to remain in host memory while still being directly accessible by the GPU, thereby eliminating unnecessary migrations and breaking the migration–eviction cycle. 

Stabilizing data placement. To realize this, TRANSIT -Advise leverages UVM’s zero-copy mode to stabilize data placement and reduce unnecessary movement. Instead of migrating data into GPU memory on demand, zero-copy enables the GPU to directly access host-resident data via PCIe through persistent mappings, mitigating thrashing. 

TRANSIT -Advise enables this behavior using cudaMemAdvise 

with SetAccessedBy set to the GPU. To apply this mecha-nism across all managed data, TRANSIT -Advise maintains a table of memory allocation regions, constructed during the interception of cudaMalloc calls and their replacement with cudaMallocManaged . cudaMemAdvise is then applied to all tracked allocation regions in this table. TRANSIT -Advise applies memory advice during the forward/backward execu-tion, allowing frequently reused data ( e.g., activations and half-precision parameters) to remain resident in GPU mem-ory during compute-intensive phases, while less frequently accessed data ( e.g., optimizer states and full-precision param-eters) is served via zero-copy from host memory, reducing unnecessary migrations. To realize this, TRANSIT -Advise in-tercepts execution-level events to identify iteration bound-aries ( i.e., the optimizer step) and uses CUPTI callbacks to track kernel launches and estimate the total number of ker-nels per iteration. After a short warm-up phase, we apply 

cudaMemAdvise at the midpoint of each iteration, based on the observed kernel count. This heuristic is motivated by the phase structure of training iterations: forward and backward computation repeatedly touch activations and half-precision parameters, while optimizer-related states are primarily ac-cessed near the update phase. This preserves hot data in GPU memory while allowing cold data to be served through zero-copy access from host memory.

## 5 Discussion 

Potential improvements to TRANSIT . While TRANSIT -Prefetch and TRANSIT -Advise are conceptually complemen-tary, in our current design TRANSIT -Advise installs zero-copy mappings for all spilled data, effectively eliminating migra-tions and leaving little opportunity for TRANSIT -Prefetch to contribute. A more flexible design could selectively apply zero-copy and rely on migration for the remaining data, en-abling the two mechanisms to operate in tandem. Realizing such a design requires identifying which data should remain migration-based versus zero-copy, allowing prefetching to improve transfer efficiency while retaining the benefits of stable placement. However, identifying such distinctions is challenging due to the limited visibility available at the shim layer. Among the available signals, migration history proves to be a poor proxy for true access patterns, as it captures when data is moved across CPU and GPU but not how fre-quently it is reused; a page may be accessed many times by the GPU after a single migration before being evicted, which is not reflected in migration activity alone. Accurately cap-turing access patterns would require fine-grained tracking of data reuse at the GPU, which is not exposed through existing profiling interfaces such as CUPTI and would require deeper integration with the runtime or driver. 

Co-optimizing communication, compute, and memory offloading. Prior work has explored optimizing distributed training performance by searching over parallelization strate-gies and training configurations, such as tensor/pipeline par-allelism and local/micro batch size, to balance computation and communication costs [15, 47, 55]. However, these ap-proaches typically treat GPU memory capacity as a hard constraint, limiting the feasible design space to configura-tions that fit within aggregate device memory. Transparent memory offloading relaxes this constraint by extending GPU memory with host memory, enabling training under more flexible parallelization and configuration choices that would otherwise be infeasible. This expanded design space intro-duces new opportunities to reduce communication overhead, for example by operating with fewer GPUs or favoring paral-lelization strategies with lower synchronization costs while demanding larger memory. At the same time, offloading introduces additional data movement overheads, making performance dependent on the interplay between compu-tation, communication, and memory offloading. Designing efficient strategies that navigate this enlarged space, while accounting for the dynamic costs of offloading, remains an important direction for future work. 

## 6 Related Work 

Training LLMs with data offloading. Fine-grained sys-tems such as G10 [27], TeraIO [52], and SSDTrain [49] tightly integrate with the training framework, using run-time profiling and scheduling to orchestrate data placement across memory tiers ( e.g., GPU HBM, CPU DRAM, or NVMe SSDs). While effective, they require deep integration and be-come increasingly complex under multi-dimensional paral-lelism. In contrast, widely adopted solutions favor simplicity. ZeRO-Offload [41], ZeRO-Infinity [40], and TorchTitan [30] adopt coarse-grained strategies that offload entire classes of data ( e.g., parameters or optimizer states), trading effi-ciency for ease of deployment. These framework-dependent approaches are tightly coupled to specific implementations, limiting portability across models and systems. To improve programmability, recent work explored application-transparent offloading via NVIDIA Unified Vir-tual Memory (UVM) [13], decoupling memory management from the training framework. However, default UVM behav-ior is often inefficient for training, motivating prior work to introduce custom prefetching and migration policies [27, 31]. These approaches require deeper system support: Forest [31] modifies the UVM driver for fine-grained control over page placement and migration, while DeepUM [27] introduces a custom kernel-space driver alongside runtime integration to intercept page faults and orchestrate prefetching. These re-quirements limit deployability: modifying the UVM driver or introducing kernel-level components makes such approaches difficult to apply transparently, restricting their use not only in containerized environments and public clouds, but also in private clusters where administrative control is limited. 

Communication optimizations for distributed LLM training. Prior work mitigates network bottlenecks by re-ducing communication volume, restructuring parallelism, improving job placement, or overlapping communication with computation. ZeRO++ lowers communication cost via low-precision transfers and hierarchical partitioning [46]. 

> 12

Pipeline parallel approaches such as PipeDream replace fre-quent global synchronization with stage-wise communica-tion, while improved schedules reduce pipeline inefficien-cies [24, 34]. Another line of work focuses on topology- and bandwidth-aware job placement, mapping training jobs onto clusters to minimize cross-node communication and avoid network contention [17, 23, 35, 55]. Orthogonally, systems such as ByteScheduler improve overlap by introducing fine-grained, priority-based communication scheduling, enabling better utilization than conventional greedy overlap [36]. De-spite these advances, existing approaches primarily optimize communication given a fixed degree of parallelism and re-source allocation, and do not address the regime where scal-ing to more GPUs to meet memory capacity exacerbates network bottlenecks. 

## 7 Conclusion 

We presented TRANSIT , a transparent scale-in framework that enables distributed LLM training to run on fewer GPUs by using CPU DRAM as an extension of GPU mem-ory. By augmenting UVM with runtime-guided data move-ment policies, including fused prefetching and zero-copy access, TRANSIT improves CPU–GPU data movement effi-ciency without requiring changes to applications, frame-works, schedulers, runtimes, kernels, or device drivers. Our results show that appropriate user-space runtime orchestra-tion can overcome UVM’s poor default performance, with zero-copy avoiding migration thrashing and preserving high per-GPU efficiency under scale-in. As a result, TRANSIT out-performs default UVM and framework-managed offloading while reducing network traffic, queueing delay, and cluster resource pressure.
