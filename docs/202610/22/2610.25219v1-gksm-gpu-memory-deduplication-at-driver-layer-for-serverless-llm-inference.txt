## Abstract 

In serverless LLM inference, cloud providers commonly lo-cate multiple instances on a single GPU to improve utiliza-tion. However, each instance independently maintains its model weights and runtime state, making duplicate GPU memory the primary bottleneck. Memory deduplication is a widely-used technique for eliminating duplicate data in CPU systems, but extending it to GPU memory faces fundamental challenges. Effective GPU memory deduplication must avoid redundant data movement between CPU and GPU while preserving write isolation for shared pages without native copy-on-write (COW) support. This paper presents gKSM, a transparent GPU memory deduplication framework for serverless LLM inference. gKSM addresses these challenges through CPU-GPU collaborative hash management that offloads hash computation to GPU kernels, zero-copy model weight deduplication that elimi-nates duplication before model weight transfer, and a cross-privilege page fault handler that combines a lightweight ker-nel hook and CUDA Virtual Memory Management (VMM) remapping in the user space. gKSM also designs a stable page scanning algorithm and a reuse-aware placement policy in cluster scale. Experiments show that gKSM reduces GPU memory usage by 59.8% while maintaining high through-put compared to ServerlessLLM. Under memory constrained workloads, gKSM improves aggregate throughput by 2.15 ×

and supports five instances concurrently. In cluster level sim-ulation, gKSM achieves a service rate of 99.97%, compared to 78.2% for SLInfer and 26.9% for ServerlessLLM.

## 1 Introduction 

Large language models (LLMs) are increasingly deployed as managed inference services in public cloud and private plat-forms [5, 12, 19, 54]. In many enterprise scenarios, to satisfy service level objectives (SLOs) and deployment customiza-tion in vertical industries, enterprises often deploy private model instances in the cloud instead of using public inference services [2, 15]. These private services have different SLOs and dynamic request rates, making statically reserved GPU resources inefficient and expensive [1, 36, 54, 58]. To address this problem, serverless inference [12, 20, 27, 40, 59] has emerged as an attractive deployment, allowing users to scale private model instances on demand without managing and scheduling GPU resources. Such services have already been adopted by major cloud providers, including Google [15] and Alibaba Cloud [2]. However, LLM inference fundamentally differs from traditional serverless functions [26, 41, 50, 51]. To avoid expensive model reloads during invocation, each inference instance must retain large model weights in GPU memory [12, 46]. As a result, serverless LLM inference is con-strained by persistent GPU memory consumption [12, 29]. Since online inference workloads are highly dynamic and intense, providers commonly locate multiple serverless infer-ence instances on a single GPU to share compute resources arXiv:2610.25219v1 [cs.OS] 18 Oct 2026 over time [6, 27, 59, 60]. Although colocation improves com-pute utilization, each instance independently maintains its model weights, KV cache, and runtime state [24, 62], making GPU memory the primary bottleneck that limits the num-ber of colocated instances. Moreover, GPU memory usage across colocated instances is often highly duplicate. In prac-tical deployment, many instances serve the same popular models or fine-tuned models derived from the same base model [5, 10, 21, 28, 45]. Even when instances use different inference frameworks [9, 19, 24, 35, 63], their model weights remain largely identical. This duplication severely constrains the serving capacity of the inference system. Existing works have proposed model-aware scheduling strategies to mitigate GPU memory waste. ServerlessLLM exploits the locality of model weights to reduce cold start and migration overhead [12]. Prism dynamically offloads instances by tracking the access frequency of different mod-els [60]. SLInfer consolidates instances of the same model onto shared nodes via live migration and merges small re-quest batches into larger ones [55]. These strategies improve resource elasticity and GPU utilization [11, 64]. However, they operate at the level of instance scheduling and batch ag-gregation rather than directly eliminating duplicate memory pages at the physical level. They cannot share memory be-tween instances running on different inference frameworks or exploit partial weight duplication between similar models. Furthermore, live migration introduces tail latency while weakening instance isolation. As a result, these scheduling approaches do not fully resolve the GPU memory duplication problem. The scale of duplication is substantial. To confirm this problem, we perform a trace driven simulation of an A100 GPU cluster running a serverless inference workload of Al-ibaba Cloud [6, 29, 50]. Our experiments show that Server-lessLLM and conventional load balancing strategies accumu-late up to 2000 GB of duplicate GPU memory, corresponding to a 70% duplication rate. Even SLInfer, which explicitly consolidates identical instances, still retains a duplication rate of more than 50% (see Figure 2). Memory deduplication is a widely used technique in CPU systems, such as Linux KSM [44]. KSM identifies identical memory pages by scan-ning and merging them into a single physical copy, relying on COW to maintain data consistency when modifications occur. A transparent page level deduplication technique on the GPU side could therefore effectively eliminate duplicate model weights and runtime data across colocated instances. However, CPU memory deduplication cannot be directly transplanted to GPU environments. Three fundamental chal-lenges arise from the architectural differences between the two domains. First, duplicate data reside on the GPU while the metadata required for page tracking and sharing coor-dination is managed on the CPU. This separation makes CPU-side hashing prohibitively expensive and rules out a purely GPU-side management approach. Second, model weights must be loaded from the host to GPU memory over the PCIe bus during instance initialization. A conventional pipeline that copies first and deduplicates afterward wastes PCIe bandwidth and temporarily occupies duplicate mem-ory, which leads to potential out-of-memory (OOM) risk. Third, after duplicate pages are shared, write isolation must be enforced. CPU KSM relies on the kernel’s native COW mechanism, but the GPU driver, which is only partially open-source with a closed user-mode component, provides no COW semantics for deduplicated virtual memory. To address these challenges, we propose gKSM, a GPU memory deduplication framework operating at the CUDA driver layer. Mainstream inference frameworks are built on CUDA software stack, their GPU memory operations pass through CUDA driver APIs. These interfaces provide a com-mon interception point where gKSM can track allocations and copies and manage physical page sharing while pre-serving application-visible virtual addresses. This enables transparent page-level deduplication across independent in-stances, including those running different inference frame-works, without modifying the frameworks. Our major con-tributions are summarized as follows. 

• We design a CPU–GPU collaborative hash management for page scanning. gKSM computes page hashes in the GPU, manages metadata and hash buckets in the CPU, and verifies candidate pages by exact comparison. 

• We propose zero-copy model weight deduplication based on duplicate data detection. By hooking CUDA memory copy during model loading, gKSM detects duplicate pages before transfer and avoids redundant memory allocations. 

• We design COW across user space and kernel space for shared GPU pages. gKSM captures write faults in the UVM path, reports them to a user space handler, and uses CUDA VMM to create private copies. 

• We implement gKSM at the CUDA driver layer, incorpo-rating a stable page scanning algorithm for dynamic GPU memory and a reuse-aware instance placement policy for cluster deployment. Evaluated on a single GPU and cluster workloads, gKSM reduces GPU memory usage by up to 59.8% with negligible overhead, and improves throughput by up to 2.15 × under memory constrained workloads.

2.2 Memory Duplication in Serverless Inference Systems 

Serverless deployment enables elastic scaling of inference instances across GPU resources. However, traditional in-ference instances adopt a static resource allocation model, where the system reserves fixed GPU memory and compute resources during instance startup and cannot dynamically adapt to fluctuations in the real-time request load [27, 40]. To address this, existing works such as ServerlessLLM [12], Prism [60] and SLInfer [55] have proposed model-aware scheduling strategies [47]. ServerlessLLM exploits the model weight locality to reduce cold start and migration overhead. Prism dynamically offloads instances by tracking the access frequency of different model instances in real time. SLIn-fer aggregates instances of the same model onto the same node via live migration and merges small batches into larger ones, addressing the memory redundancy caused by dupli-cate model weights. These strategies mitigate unnecessary GPU memory waste, enable elastic resource sharing, and improve GPU utilization [11, 64]. However, under existing model-aware scheduling strate-gies, inference clusters still face significant GPU memory duplication. To confirm this problem, we simulate and replay the cluster level inference process based on Alibaba Cloud inference traces [6, 29, 50] to quantify GPU memory dupli-cation under different scheduling strategies. As shown in Figure 2b, as the cluster size scales, the memory duplication of ServerlessLLM and traditional load balancing strategies reaches 2000 GB, with an overall duplication rate of 70%, while SLInfer achieves a duplication rate of 50%. Traditional load balancing strategies are model-agnostic, dispersing in-stances of the same model across different nodes and causing widespread memory duplication within the cluster. Although ServerlessLLM reduces cold start overhead by exploiting model weight locality, it tends to aggregate instances of the same model within GPU nodes. As a result, each GPU node still holds duplicate copies of model weights in its memory. SLInfer schedules instances with identical model weights to the same node and mitigates duplication by merging request batches, yet its scheduling strategy still faces fundamental limitations. Existing scheduling strategies suffer from three intrinsic limitations. First, when the same model runs on different inference frameworks, such as vLLM [24], SGLang [63], and TensorRT-LLM [35], instances on different frameworks can-not share memory with each other. These frameworks differ fundamentally in request batching, prefill scheduling, and memory management, preventing cross-framework batch merging even when instances serve the same model. Accord-ing to industry data, vLLM and TensorRT-LLM together dom-inate the NVIDIA inference ecosystem, with adoption rates of approximately 55% and 45% respectively, while SGLang is deployed on more than 300,000 GPUs [63]. Second, exist-ing strategies only deduplicate the entirely identical model instances and cannot exploit partial weight sharing across different models. Many models are fine-tuned from the same base model [5, 10, 21, 28, 45] or extend a shared language backbone with different vision encoders [4, 25, 30]. As shown in Figure 2a, sharing the common base model of Qwen3-8B [56] saves 15.2%–81.6% GPU memory, yet existing sched-ulers cannot perceive such partial duplication. Third, live instance migration and batch merging [47, 64] introduce additional system overhead and undermine inter-tenant iso-lation. Live migration transfers instance context including runtime states and KV cache, incurring network overhead and service pauses that lead to tail latency [16, 53]. Mean-while, merging requests from different tenants into shared batches weakens the instance resource boundaries, causing performance interference under varying request patterns and latency SLOs [16, 61]. 

2.3 Opportunities and Challenges of GPU Memory Deduplication 

Current approaches rely on the scheduling layer to continu-ously decide placement and migration, which fail to inher-ently eliminate duplicate memory footprints while incur sub-stantial overhead in the scheduling and coordination layer. Memory deduplication [7, 18, 33, 38, 49] is an established technique that reduces physical memory usage by identify-ing and merging identical memory pages through scanning and comparison, while relying on COW to maintain data consistency when modifications occur. This approach has been widely implemented in CPU memory systems, such as Linux’s KSM [44] and virtualization platforms [33, 42, 52]. In serverless inference scenarios, extending traditional CPU memory deduplication to the GPU offers an opportunity for transparent memory sharing across colocated instances. GPU memory deduplication at CUDA driver layer can pro-vide an efficient and transparent solution that significantly reduces duplicate memory usage without affecting infer-ence services. Existing mainstream inference frameworks, including vLLM and SGLang, are built on the CUDA software stack. Although they implement their own logical memory managers, their model weights, KV cache buffer, and other GPU runtime memory must ultimately be allocated and man-aged through CUDA driver APIs. This allows us to track all these allocations and memory copy operations without mod-ifying any framework, preserving each allocation’s virtual addresses while managing the physical backing pages. In contrast, runtime-level sharing is coupled to each frame-work’s memory manager, making it less efficient and less transparent than driver-layer deduplication. However, fundamental differences in memory manage-ment models, driver interfaces, and hardware capabilities between CPU and GPU architectures prevent direct trans-plantation of mature CPU deduplication mechanisms to GPU memory. The lack of native support for COW semantics and fine-grained page sharing in current GPU systems presents particular challenges [23, 34, 37]. In general, these challenges can be summarized in the following three aspects: 

Challenge 1: Deduplication in heterogeneous mem-ory. The lifecycle of GPU memory is managed from the CPU side, including physical memory allocation, virtual address remapping, access control and coordination. However, du-plicate memory reside in the GPU side. Copying GPU pages back to host memory for CPU-side hashing introduces sub-stantial data transfer overhead, and CPU hash computation throughput is much lower than what GPU parallelism can achieve. Therefore, metadata must be maintained on the CPU side, while hash computation and page comparison are per-formed on the GPU. However, moving the entire scanning and management logic to the GPU is infeasible because page metadata such as allocation handles, access permissions, and sharing state requires the logical control and data structure management capabilities of the CPU runtime. This physical separation between GPU-side data and CPU-side metadata creates a fundamental coordination challenge. Efficient du-plicate detection requires a collaborative mechanism that leverages GPU parallelism for hash computation while re-taining CPU-side metadata management, without incurring expensive data movement from GPU to CPU. 

Challenge 2: Eliminating redundant data transfer in the critical path. GPU inference workloads must first load model weights from CPU to GPU memory over the PCIe bus during instance initialization. A conventional deduplication pipeline would fully copy the model weights to the GPU, then scan and merge duplicate pages. This incurs unneces-sary PCIe bandwidth consumption and temporarily occupies duplicate GPU memory before deduplication completes, lead-ing to significant memory spike. The challenge is to implement COW semantics for shared GPU pages while keeping kernel modifications minimal and preserving system stability.

3.1 Overall Architecture of gKSM 

We propose gKSM, a GPU memory deduplication system operating at the CUDA driver layer. Compared to traditional CPU memory deduplication such as KSM, gKSM addresses three fundamental challenges. First, GPU memory on the de-vice and deduplication metadata on the host leave CPU hash-ing limited by data transfer and computation overhead, while GPU metadata management is limited by CPU coordination. gKSM addresses this through CPU–GPU Collaborative Hash Management (Section 3.2), which offloads hash com-putation to GPU kernels while retaining metadata control on the CPU. As illustrated in Figure 3, gKSM implements this design through a transparent deduplication framework and a reuse-aware instance placement policy. The framework realizes GPU-accelerated stable page scanning that periodically iden-tifies sharing opportunities in dynamic KV cache and activa-tion pages [14, 62], and transparent GPU page sharing via CUDA VMM that remaps duplicate pages to shared physical handles while preserving instance virtual address spaces. The placement scheduler decomposes each instance’s mem-ory into a shareable portion and a private portion, then selects the GPU with the lowest incremental memory cost under compute constraints. Figure 7 contrasts this policy with ServerlessLLM and SLInfer. Instead of relying on live migration or instance merging, gKSM exposes reuse oppor-tunities directly to the memory layer. Since driver-layer deduplication requires reusable pages to reside on the same GPU [11], the placement policy locates instances that bene-fit from memory sharing. The workflow first deduplicates model parameters during initialization, then the background scanner identifies stable pages, while the COW handler pre-serves write isolation at runtime. On the CPU side, gKSM maintains a per-GPU metadata table that stores information including the virtual address, access permission, and hash value for each managed page. To coordinate deduplication across instances, gKSM further maintains a global shared table organized as hash buckets. This global table, implemented as an indexed array, supports efficient lookups and updates. A hash lookup returns can-didate shared pages that share the same hash value. It is important to note that the above implementation still carries the risk of hash collisions. Therefore, a hash match does not directly lead to page sharing. Instead, it triggers an exact com-parison of the page contents. Only when the page contents are completely identical will the current page be remapped to an existing shared page. If a hash collision occurs, the current page remains independent. By combining GPU-accelerated hash computation with optimized CPU-side metadata man-agement, gKSM addresses the challenges of computational bottlenecks and cross-processor coordination, enabling fast and scalable page comparisons across instances. 

3.3 Zero-Copy Model Weight Deduplication 

As discussed in Section 2.3, a conventional pipeline that copies data first and deduplicates afterward wastes PCIe bandwidth and temporarily occupies duplicate GPU memory. These overheads are significant in the cluster scale, where hundreds of instances may load overlapping model weights concurrently, causing transient memory spikes and increas-ing the risk of OOM errors. To address this, gKSM introduces a zero-copy deduplication method integrated into the mem-ory copy path. The core idea is to intercept the model weight transfer before it reaches GPU memory, so that duplicate data are never physically copied. Concretely, gKSM inserts a hook into the cudaMemcpy() 

path from CPU to GPU. Since model weights already reside in CPU memory before transfer, gKSM performs page hashing, candidate lookup, and exact content verification all on the CPU side. gKSM computes batched hashes in the hook path and uses them to query the global shared page table for candidate pages with matching hashes. If a match is found and the exact content comparison with the candidate pages retained pinned CPU buffer confirms this duplication, the virtual address of the current page is directly remapped to the physical handle of the existing shared page. The originally allocated physical memory is released immediately, without data ever being written there. If no match is found, the page is copied to the GPU as usual, and the new page is registered in the shared table and pinned buffer for future deduplication. This approach ensures that only one physical copy of each unique model weight page is retained on the GPU, re-gardless of how many instances load the same model. To avoid unnecessary hash computation for model weight pages and other already-deduplicated data during subsequent back-ground scans, these pages are marked with a flag so that they are excluded from further scanning. By avoiding redundant PCIe transfers and immediately releasing duplicate GPU al-locations, zero-copy model weight deduplication achieves efficient memory savings with negligible impact on model initialization latency. 

3.4 Cross-Privilege Page Fault Handler 

After GPU memory deduplication, gKSM must preserve write isolation for shared GPU pages mapped by multiple instances. When one instance writes to the shared page, it must receive a private copy without affecting the other instances that are still reading from the original [23]. In traditional CPU memory deduplication, the kernel’s native COW mechanism handles write isolation transpar-ently within the privileged kernel context. However, the GPU environment lacks this native support. The partially open-source GPU driver provides no COW semantics. CUDA VMM lacks automatic page copy and remap services, and the UVM kernel module does not coordinate with user-space VMM APIs. To address this while keeping kernel modifica-tions minimal, gKSM proposes a cross-privilege page fault handler that splits the COW workload across kernel space and user space. As shown in Figure 5, the kernel realizes a lightweight fault detection and reporting, while the user space handles page copying and virtual address remapping through CUDA VMM APIs. After deduplication, gKSM maps all shared pages as read-only. When a GPU kernel attempts to write to a shared page, the access triggers a GPU page fault. For each captured fault, the kernel module records a fault descriptor that contains the fault address, fault type, instance identifier, and device iden-tifier, then inserts it into a waiting queue exposed through a character device. The kernel does not perform expensive page copying or CUDA VMM remapping. Instead, it only reports fault events to the user space. The fault queue is protected by locks with a narrow scope, which reduces lock contention and keeps the GPU driver path simple and stable. On the user side, a dedicated COW handler thread period-ically fetches fault records from the waiting queue in batch. For each fault, the handler first validates the current local and global metadata. If the faulting instance is not the owner of the shared handle, the COW handler creates a private copy of the fault page for this instance using CUDA VMM allocation and memory copy. It then redirects the virtual ad-dress to the private copy via cuMemMap() and makes the new mapping writable via cuMemSetAccess() . The local meta-data is updated to record the page as a private page, and the global shared table removes this reference from the sharer list of the original page. A COW fault is triggered only on the first write to a shared page. After a COW process is finished, subsequent writes to this private page follow the normal access pattern. The ownership of the shared handle is then transferred to the new owner, and the faulting former owner is allocated a new private page. During COW operations, gKSM protects the metadata of the faulting page with a shared memory mutex to prevent concurrent modification of the same shared page by multiple fault handlers. All page copying, ownership management, and remapping logic resides in the user space, where CUDA VMM APIs provide a stable and well supported interface. 

3.5 Implementation 3.5.1 Transparent GPU Page Sharing. Once duplicate pages are identified, gKSM must share the underlying physi-cal memory across instances while preserving each instance’s virtual address space. In CPU-side KSM, the kernel directly modifies page table entries to share physical frames. The GPU environment lacks such direct page table manipulation, and conventional CUDA interfaces do not allow indepen-dent remapping or sharing of physical pages across instances. gKSM therefore implements transparent GPU page sharing on top of CUDA VMM APIs [37], which expose fine-grained control over GPU virtual memory. These APIs support creat-ing shareable physical handles, importing them into different address spaces, and independently controlling access per-missions. gKSM leverages these primitives to turn duplicate pages into a single shareable physical handle while keeping each instance’s virtual address unchanged. Concretely, gKSM intercepts GPU memory allocation re-quests and manages them at page granularity. For each man-aged page, gKSM maintains metadata to track its owner-ship, sharing state, and page permissions. Our implementa-tion uses 2 MB as the deduplication granularity [3], which matches the allocation granularity reported by CUDA VMM on our platform. This granularity is also well suited for LLM inference workloads, since model weights are typi-cally stored as large contiguous tensors with stable memory layouts across instances. As a result, most duplicate model weight regions can already be captured at 2 MB granular-ity, while using smaller pages would significantly increase metadata management, hashing, and remapping overhead. As shown in Figure 6, the sharing process works as fol-lows. Duplicate pages are identified either through zero-copy interception during model loading or through the back-ground stable page scanner. Once identified, gKSM exports a shareable physical handle from the source instance using 

cuMemExportToShareableHandle() . This handle is then im-ported into the target instance’s virtual address space, and the target’s virtual address range is remapped to the imported physical handle via cuMemMap() . The target instance’s orig-inal duplicate allocation is then released. Throughout this process, the virtual addresses of both instances remain un-changed. Inference kernels continue to access memory at the same addresses without any modification. After remapping, all shared pages are marked read-only via cuMemSetAccess() 

to preserve isolation across instances. This sets up the nec-essary condition for the COW fault handler described in Section 3.4. During normal inference execution, instances continue accessing GPU memory through their original virtual ad-dresses. All reads are served directly from local HBM with-out remote memory access. gKSM only adds lightweight metadata management and occasional remap and permission updates during page sharing. In practice, these VMM opera-tions occur infrequently and are concentrated mostly dur-ing initialization and deduplication events. They introduce negligible overhead and impact to the subsequent inference execution. For example, even the most expensive VMM op-erations, such as cuMemExportToShareableHandle() and 

cuMemSetAccess() , take only 100 𝜇 s and 296 𝜇 s on average in our implementation. 

3.5.2 Stable Page Scanning. Beyond model weights, LLM inference continuously generates dynamic pages such as KV cache and intermediate activations. These pages may contain significant duplication when instances serve similar requests or share prefix prompts [14], but unlike read-only model weights, they are subject to frequent modifications. Indiscriminately sharing them would lead to excessive COW faults, as a page written immediately after sharing must be privately reallocated and copied. In the GPU context, where COW involves a cross-privilege round trip (Section 3.4), the cost of premature sharing is significantly higher than in CPU-side KSM. gKSM must therefore selectively identify pages that are sufficiently stable to benefit from deduplication. To address this, gKSM introduces a stable page scanning mechanism that employs a lightweight background thread to periodically scan dynamic pages such as KV cache and intermediate activations. The core idea is to track page sta-bility through repeated hash observations. If a page’s hash value remains unchanged for 𝑁 consecutive scans, it is clas-sified as stable and becomes eligible for deduplication. Pages whose hashes change between scans are considered unsta-ble and are excluded from sharing, avoiding unnecessary COW overhead on transient data. The scanning interval follows an exponential-backoff policy: if a scan finds no deduplication opportunity, the interval doubles up to a con-figured maximum. Successful deduplication resets it to the base interval. The maximum interval controls the tradeoff between scanning overhead and responsiveness to new shar-ing opportunities: a smaller cap revisits dynamic pages more frequently, while a larger cap reduces repeated scanning when few stable duplicates are available. The background scanner leverages the same CPU–GPU collaborative hash computation mechanism described in Section 3.2, while the GPU computes page hashes and the CPU manages the global shared table. Specifically, the GPU computes the current hash values for each page. If the hash value differs from the previous scan, the page is considered unstable and its stability counter is reset. If the hash remains consistent for 𝑁 consecutive scans, the page is deemed stable and gKSM proceeds to look up the corresponding hash bucket in the global candidate table. For each candidate page 𝑞 in the bucket, gKSM recomputes its hash value to filter out pages that may have been modified after being inserted into the candidate table. If 𝑞 resides in an-other instance, gKSM requests a hash recomputation on the remote instance. A matching hash alone does not guarantee page sharing due to the possibility of hash collisions. Before merging, gKSM performs an exact content comparison be-tween the local page and the candidate. The two pages are remapped to the same physical page only if their contents are fully identical. If the comparison fails, gKSM treats the case as a hash collision or a stale candidate and continues to check the remaining candidates. If no candidate passes verification, the local page remains independent and may be inserted into the candidate table for future matching. By combining GPU-parallel hashing with stability-gated deduplication, gKSM effectively identifies sharing opportunities in transient data while minimizing scanning and COW overhead.

## 5 Discussion 

Security. As in other CPU memory deduplication systems, there are side-channel risks in gKSM [18, 44, 49]. However, their practical impacts are limited by the lower sensitivity in LLM inference scenarios and trust-domain restrictions. Com-pared with conventional CPU memory deduplication, gKSM operates at 2MB page granularity, making fine-grained prob-ing more difficult. For public or authorized model weights, a deduplication signal may reveal only a few model weight pages, which is insufficient to reconstruct the entire model weight. Considering that KV cache retains attention states derived from prompts [14, 24], gKSM can restrict its dedu-plication to operator-defined trust domains. 

Deployment and Native Support. GPU memory dedupli-cation can be provided by the cloud vendor or hardware provider. If NVIDIA provides GPU memory deduplication service, most parts of gKSM remain necessary, such as page management, duplication detection, stable-page scanning, and reuse-aware placement. In particular, reuse-aware place-ment remains relevant because sharing opportunities de-pend on colocation, as demonstrated in CPU virtualized sys-tems [52]. However, NVIDIA may implement COW and page merging more efficiently in its kernel.

## 7 Conclusion 

This paper presents gKSM, a transparent GPU memory dedu-plication framework for serverless LLM inference. Motivated by the large amount of duplicate GPU memory across colo-cated model instances, gKSM enables transparent memory sharing while preserving instance isolation. Our results show that memory deduplication can substantially improve GPU memory efficiency and system scalability for serverless infer-ence. We view gKSM as a first step toward transparent GPU memory sharing for large scale LLM serving. As model de-ployment continues to grow, new opportunities will emerge to exploit memory duplication in the AI world.
