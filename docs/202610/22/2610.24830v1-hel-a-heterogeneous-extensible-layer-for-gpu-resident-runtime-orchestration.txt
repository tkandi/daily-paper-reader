We describe a GPU-resident runtime system, HEL, built on stateful services that persist throughout the lifespan of a user application. A HEL programmer expresses a workload as an application that spawns coroutine-like tasks, which are then scheduled and run by the HEL runtime. HEL supports synchronous and asynchronous tasks, tasks with runtime dependencies, batched task submission, and automatic retries. Applications and tasks run alongside each other on the spatially partitioned GPU. Using producer-consumer and host-RPC benchmarks together with a PFPL compression case study, we show that HEL demonstrates a performance advantage for underutilized GPUs and for scenarios where HEL enables hiding task latency. 

## 1 Introduction 

Modern GPU workloads increasingly execute entire multi-stage pipelines rather than isolated computational kernels. Applications such as scientific simulations, data science tasks, and machine learn-ing inference often involve sequences of GPU kernels with data-dependent coordination between stages. Despite GPU support for sophisticated execution features such as dynamic work genera-tion, direct access to I/O devices, and asynchronous execution, coordination of these stages remains CPU-driven. Applications typically orchestrate GPU computation through host-side control loops that launch kernels, synchronize results, and determine sub-sequent work. This approach incurs kernel launch overhead, limits opportunities for latency hiding, and requires embedding orchestra-tion logic directly within application code. As GPU parallelism has grown, sustaining full utilization has become harder for irregular, multi-stage workloads that require fine-grained coordination across execution phases. This coupling exists because current GPU runtimes are typically structured around individual kernel invocations. Runtime logic that coordinates GPU work is often implemented in host-side control code or as device code that is scoped to the lifetime of a kernel. As a result, orchestration mechanisms lack portability and must be reim-plemented for each new workload. This structure limits modularity and prevents active runtime state from persisting across phases of GPU computation. A more flexible approach would allow orches-tration logic itself to execute persistently on the GPU as a reusable runtime service. While a persistent-kernel implementation [10] that combined application and runtime logic could potentially provide this desirable property, such an architecture both forces the applica-tion into using persistent-kernel logic and would intimately couple the application and runtime logic into a single whole, preventing a clean and desirable separation between application and runtime. In this paper, we introduce HEL (Heterogeneous Extensible Layer), a runtime architecture in which a monolithic GPU applica-tion is decomposed into inline application work and HEL-managed work, with the latter expressed as explicit compute and control planes and executed by a persistent GPU-resident service. We use 

compute plane to denote the user-defined task computation and 

control plane to denote the task-generation, dependency, and sched-uling logic that governs execution. In HEL, the application defines both planes, while the persistent GPU-resident service executes and orchestrates them under bounded resources. Instead of coordinating GPU work through host control loops, HEL accepts asynchronous task requests and keeps orchestration resident on the GPU. HEL tracks dependencies, detects readiness, and schedules tasks under bounded resources. This persistent ser-vice executes concurrently with the application through spatial GPU partitioning, overlapping control with computation and avoid-ing host involvement between kernel phases. We implement a functional prototype of HEL in CUDA and evaluate its behavior across workloads that vary in orchestration overhead and computational intensity. Our experiments focus on characterizing the operating regimes in which GPU-resident run-time orchestration is, or will become, beneficial. Using parameter-ized producer-consumer pipelines and controlled workloads, we study control-heavy, compute-heavy, and latency-hiding execution scenarios. These experiments explore the fundamental tradeoffs be-tween runtime coordination overhead and application computation when orchestration is executed by a persistent GPU service. This paper makes the following contributions: 

• HEL Runtime Architecture : A system that shifts the GPU control-plane to a persistent, GPU-resident service capable of coordinating application tasks across kernel boundaries. 

• Task-based Orchestration Interface : An asynchronous work-submission model with explicit dependency tracking, allowing GPU workloads to be decomposed into runtime-managed tasks. 

• Multi-Granularity Task Dispatch : A runtime implementation that supports thread-, warp-, and block-granularity tasks, en-abling the service to match dispatch granularity to the workload. 

• Persistent GPU Service Model : A demonstration of long-lived runtime services executing concurrently with kernels via spatial partitioning to overlap coordination and computation. 

• System Characterization : A CUDA-based evaluation across control-heavy and latency-hiding regimes, plus a realistic compression-service case study, identifying the tradeoffs between coordination overhead and computational intensity. 

## 2 Background and Prior Work 

HEL is fundamentally different than prior GPU “runtime” work. 

The term “runtime” is broad and different readers may interpret it differently. The fundamental distinction between HEL and prior GPU-runtime work is that HEL acts as a resident system service completely resident on the GPU (effectively a microkernel for the GPU), whereas prior GPU-runtime efforts are primarily host-side arXiv:2610.24830v1 [cs.DC] 17 Oct 2026 Łupińska, Porumbescu, and Owens 

(CPU) workload managers. Because HEL occupies dedicated hard-ware resources and runs fully on the GPU, it has a level of auton-omy and low-latency orchestration that host-side runtimes cannot achieve. Unlike mainstream heterogeneous runtimes such as StarPU [2], Legion [4], and PaRSEC [5], which utilize the host CPU as a central-ized orchestrator to manage task dependencies and kernel launches, HEL’s control plane is entirely on the GPU. Host-side runtimes are subject to the latency of the PCIe bus and CPU-side scheduling overheads, which HEL avoids by acting as a GPU-resident service. While OpenMP [17] and IRIS [12] have introduced “GPU-ready” tasking, they still fundamentally rely on a “push” model where the host manages the task queue; HEL, conversely, implements a “resident-pull” model where the runtime service autonomously schedules tasks onto spatially partitioned SMs. Furthermore, while CUDA Graphs provide a mechanism to reduce launch overhead, they are primarily static structures that must be pre-defined or “captured” on the host; they lack the dynamic, stateful reactivity of HEL’s persistent service, which can handle asynchronous coroutine yielding and automatic retries without host intervention. Finally, HEL differs from application-internal schedulers like Atos [6] or recent persistent-kernel frameworks like GTaP [14]. While those systems use persistent kernels to hide launch latency, they are typi-cally integrated within the application’s own execution context and share resources temporally with the compute workload. HEL’s use of NVIDIA MPS to create a spatially isolated, independent runtime layer allows it to function as a separable system service that pro-vides orchestration as a utility to one or more applications, rather than being a specialized scheduler baked into a single kernel. 

Coroutines, Task Programming. Coroutines provide an execution model where computation can suspend and resume while preserv-ing execution state [15]. This model decomposes work into a task dependency graph, enabling the runtime to schedule execution ac-cording to precedence rules. While common in CPU environments, such execution models are not directly supported on GPUs, which generally lack native mechanisms for suspending and resuming execution contexts. Zheng et al. [22] addresses this limitation by introducing coroutines into GPU kernel programming itself and by developing a coroutine execution model and schedulers for split-ting and scheduling irregular rendering tasks. Unlike HEL, however, Zheng et al. does not use a persistent service runtime that allows overlapped orchestration. Given this lack of native support, HEL enables task-based decom-position by shifting coordination logic to a persistent GPU-resident runtime service that does not rely on compiler-driven features. HEL exposes an explicit interface for submitting tasks and expressing dependencies. The runtime service then manages task state and schedules the resulting task graph on the GPU. 

GPU Spatial Partitioning. Modern GPU frameworks support spa-tial partitioning [1] to enable multiple processes or kernels to exe-cute concurrently on different subsets of GPU hardware resources. Unlike temporal multitasking, which allocates different time slices of the entire GPU to different processes, spatial partitioning enables simultaneous execution on separate portions of the device. HEL leverages this capability through NVIDIA’s Multi-Process Service (MPS) [16] to manage and execute its runtime service along-side application workloads. (AMD data-center GPUs have a similar hardware-based “CPX” mode for compute partitioning.) By reserv-ing a fixed set of Streaming Multiprocessors (SMs) for the service, HEL can manage task scheduling and dependencies without inter-rupting application execution. This isolation [3] allows runtime orchestration to proceed in parallel with application computation. 

## 3 Design Goals, Decisions, and Programming Model 

Our goal with this work is to provide a clean programming abstrac-tion for a task-based GPU runtime (HEL) without exposing the internals of runtime scheduling to the programmer. At the highest level, our design is guided by two principles: (1) The control plane is implemented entirely on the GPU, and (2) runtime functionality is implemented separably from application functionality. We look to a future where the GPU is increasingly autonomous, and where run-time functionality has increased importance and thus deserves its own resources. We acknowledge that, particularly given limitations in the underlying hardware and programming model, that these design decisions may not always lead to the highest possible per-formance. For instance, if we devote a fixed fraction GPU resources to the runtime, and the application has little control complexity, is wholly compute-bound, and scales to all GPU resources, then a traditional CUDA approach will deliver superior performance. While we do show that other parts of the GPU-application design space benefit from our approach (Section 5.3), we believe the work we present here is best seen as an exploration of the design and im-plementation of a system that focuses on the above two principles. We choose to implement our runtime as a persistent service that supports many concurrent tasks with explicit dependencies using bounded resources. It enables parallel execution across the user application and user-created runtime tasks. Our design prioritizes task throughput and steady-state efficiency over individual task latency. We hope to free the programmer from the challenges of inte-grating common runtime functionality into an application and in-stead factor that runtime functionality into a standalone service . For us, services have standardized and consistent interfaces, whereas #including code directly into an application kernel is most often implemented as a custom, one-off interaction between application and runtime. Services can potentially run independently from ap-plication code and can be long-lived, actively maintaining state beyond the scope of an application kernel. Finally, services with standardized interfaces can be implemented once in a modular run-time framework and easily integrated into a variety of applications written by different authors. Separating a workload into application and runtime allows both to run simultaneously, in our case on different pieces of the same GPU. This design goal directly addresses the long-term trend of larger and larger GPUs that can no longer be saturated by even HEL: A Heterogeneous Extensible Layer for GPU-Resident Runtime Orchestration 

medium-sized pieces of work. 1 Our design also allows asynchro-nous execution of runtime components, leading to better GPU utilization. HEL is designed to maximize steady-state task throughput, even if this increases per-task latency. We expect a fixed orchestration overhead relative to monolithic baselines, but we aim to both (i) amortize overhead across many application calls by treating the system as a two-stage pipeline (application posting + service processing), and (ii) hide latency by overlapping service-executed task work (orchestration + task execution) with inline application work. Our evaluation focuses on identifying regimes where these ef-fects outweigh the overhead. We validate these effects in Section 5.3 (amortization and host-RPC overlap). 

## 3.1 Major Design Decisions 

3.1.1 Runtime Functionality via Spatial Partitioning. We see four general strategies to provide user-specified runtime functionality in today’s GPU programming environments. (1) The most common approach is to directly #include runtime functionality (e.g., a user-defined memory allocator) into a monolithic kernel. Such an approach is straightforward to author and allows the compiler to optimize the integration of runtime code into application code. However, it does not fulfill our functionality, concurrency, or modularity design goals. (2) The uberkernel design pattern encapsulates multiple logi-cally distinct kernels—such as the application and runtime— into one via a switch statement at the top of the kernel. The programmer can then implement a custom scheduler. How-ever, it imposes a particular style (and significant burden) on the application programmer, and moreover, does not fulfill our functionality, concurrency, or modularity design goals. (3) We could temporally partition runtime and application func-tionality , where application and runtime kernels run in alternating timeslices, each using the entire GPU. Such an approach disallows concurrent execution of application and runtime and increases the latency of their interaction. The latency issue could potentially be addressed with preemp-tion [19, 21]. (4) HEL chooses to spatially partition runtime and application functionality . We run the application concurrently with the runtime, each using a fraction of the GPU. This design aligns with our primary goals. HEL services run on a ded-icated GPU partition that persists throughout the entire execution of the user application and beyond, maintaining its own independent state.

3.1.2 Application-Runtime Communication. HEL supports a stan-dardized request/respond communication protocol. This ensures consistency across all system components and simplifies the in-tegration of new features or services. A thread makes a request specifying an operation and its parameters. The service processes this request and provides a response once the operation is com-plete. HEL supports both synchronous and asynchronous requests, batched requests, and automatic retries in an application-agnostic way, giving application developers numerous implementation op-tions without the need to embed them into an application. 

## 3.2 HEL Programming Model 

A HEL programmer divides a program into two pieces, an appli-cation (expressed in CUDA) and a set of tasks (managed by HEL). The programmer can expect that the application and tasks run simultaneously and that HEL will optimize the execution of tasks. Tasks are device-callable functions plus their captured context (its inputs/outputs), may optionally produce a result, and may be de-pendent on other tasks. The current HEL implementation supports tasks that map to one CUDA thread, one CUDA warp, or one CUDA block. HEL is particularly designed to target tasks with arbitrary, ex-plicit dependencies; tasks whose control flow may be complex and lead to divergence; small batches of tasks that may not fill an entire GPU; tasks that are latency-tolerant and can overlap their execution with execution of the application; and groups of tasks that benefit from amortizing their control flow across many invocations. Workloads with these characteristics are often a poor match for the traditional GPU programming model of a monolithic kernel that must inline all control flow, synchronization, and task manage-ment into the kernel. Dynamic parallelism offers more flexibility at runtime but DP’s child tasks do not live beyond the lifetime of the parent and lack persistent state. Explicit task frameworks such as Atos [6] offer a task abstraction but do not support explicit or arbitrary task dependencies, and instead of logically separating a workload into application and task pieces, simply support tasks as the application. HEL targets a different point in the design space: explicit dependencies, overlap between HEL tasks and inline appli-cation work, and a persistent service that can accept submissions across application calls within a context. Viewed another way (Algorithms 1–2), HEL provides coroutine-style program decomposition without requiring language-level coroutine support. HEL separates deferred, dependency-managed work (expressed as tasks) from the immediate inline computation (in the application) and lets the HEL runtime process that deferred work asynchronously. HEL’s programming model mirrors how coroutine-style programs are lowered by compilers: programs are decomposed into tasks with dependency relationships, with the remaining control logic executed inline. Programmers submit HEL tasks via a request API. A request creates a task and returns (1) a task-handle for an asynchronous request, or (2) its result for a synchronous get() request (after waiting for completion). The task-handle is a promise of eventual completion and may hold the result. Asynchronous requests are non-blocking with respect to task completion: the caller does not wait for the task to finish, but submission can block if queues are full. HEL also supports a request-retry API that repeats a submission a given number of times or until success. HEL is implemented as a persistent service that runs in parallel with the application and can thus outlive individual application kernels. HEL tasks may await on one or more tasks, suspending until those tasks completes. HEL supports fan-in joins but not fan-out continuations, and respects dependencies between tasks but other-wise makes no guarantees about execution order. HEL tasks may access only memory regions that the application explicitly maps into the service via CUDA VMM with appropriate access permissions. All task granularities can access mapped global memory, and warp- and block-granularity tasks may additionally use HEL-provisioned task-local shared memory. Application shared memory is not visible to the HEL service. 

## 4 Implementation 4.1 Runtime Architecture 

We implemented HEL as a persistent CUDA kernel using NVIDIA MPS for spatial SM partitioning between the HEL runtime and the user application. The service forms a GPU worker pool in which service workers execute tasks to completion, write the result (if any) into the task handle, update task metadata, and perform post-execution garbage collection. Depending on the build configuration, a worker may dispatch a task at thread, warp, or block granularity. Ready tasks are stored in multi-producer, multi-consumer (MPMC) FIFO rings and are executed by service workers when resources are available. The scheduler is work-conserving: when runnable work exists and resources are available, workers continue making progress. HEL supports two service-execution modes. Recursive mode en-ables coroutine-style service continuations: a service task may sus-pend and spawn a high-priority follow-up task. These high-priority tasks are lightweight because their scheduling metadata resides in shared memory, but supporting them requires reserving shared-memory capacity and dedicating worker warps to the recursive path. HEL therefore also provides a leaf-only mode for workloads without service-side continuations. In that mode, recursive execu-tion is disabled, all worker warps service application-submitted low-priority tasks, and the shared-memory budget otherwise used for recursive handling is made available to the low-priority path. The runtime and application execute concurrently in separate CUDA contexts (they do not share a device/heap stack). Communi-cation between contexts is passed via pointers through global device memory (DRAM). Submissions generated inside the HEL context (service-to-service) communicate via data structures in CUDA’s fast shared memory, and warp/block tasks may also use task-local shared memory scratch regions provisioned by the runtime. We evaluated CUDA Green Contexts as a possible replacement for MPS, but they are not suitable for HEL’s execution model. HEL requires concurrent forward progress between the application ker-nel, which posts requests, and the service kernel, which consumes them. In our experiments on A100, green-context kernels could be serialized despite disjoint SM partitions, which can deadlock HEL’s submission/consumption protocol. We therefore use MPS as the partitioning mechanism in HEL. The runtime terminates the service when three conditions hold: (i) the application has finished posting requests, (ii) DRAM queues storing low-priority tasks are empty, and (iii) SMEM queues storing high-priority tasks are empty. 

## 4.2 Runtime Data Structures 

HEL manages tasks using several runtime data structures designed for concurrent access and bounded memory usage. A task stores a device-callable function and its captured inputs. Tasks live in task buffers and are executed by service workers. Handles store task metadata (dependencies, completion state, optional result) and are managed through pool allocation and reference counting. Tasks are organized into lineages that represent families of tasks derived from a common root submission through spawn and dependency rela-tionships. Each lineage maintains its own state , including lineage-local queues/pools and counters. Ready tasks are stored in MPMC FIFO ring buffers (global for low-priority tasks, lineage-local for high-priority tasks). Waiting tasks are stored in MPMC pools until their dependencies complete. ## 4.3 Task Lifecycle 

Tasks in HEL transition through three primary phases: submission, dependency resolution, and execution. These phases describe how tasks enter the runtime, become eligible for execution, and are ultimately executed by service workers. 

Task Submission. Tasks are submitted to the HEL service through an asynchronous request interface. The request contains the task body, dependency information, and metadata describing the task’s lineage and execution context. Because the runtime and application execute in separate CUDA contexts, submissions from the applica-tion must reference data structures located in global device memory (DRAM) so that they are visible to both contexts. Upon submission, HEL creates a task handle that stores metadata associated with the task, including its dependency state and exe-cution status. Tasks whose dependencies are already satisfied are inserted into ready queues, while tasks with unresolved dependen-cies are placed into waiting pools until their dependencies become available. 

Dependency Resolution. HEL tracks task dependencies using meta-data stored in task handles. When a task completes execution, the runtime updates dependency counters for tasks waiting on its re-sults. If resolving a dependency satisfies the remaining require-ments of a waiting task, that task transitions from the waiting pool into a ready queue. Importantly, HEL provides storage only for the active set of tasks, consisting of tasks that are either ready to run or waiting on unresolved dependencies. Completed tasks release their associated runtime state through post-execution garbage collection, allowing resources to be reused. 

Task Execution. Low- and high-priority ready tasks are parti-tioned across multiple ready queues. Ready tasks are stored in MPMC FIFO rings. FIFO order is preserved within a single ready queue for a given producer-to-queue mapping, but order is not preserved across queues. There is no global FIFO order across all application calls.

## 5.3 Results 

HEL successfully delivers new functionality to GPU programmers, embodied in a runtime service that runs dynamically created tasks, with dynamic dependencies and possibly asynchronous execution, in parallel with an application. At a high level, HEL can outperform a monolithic application when the application is underutilized or when latency can be hidden. When the baseline fully saturates hardware, HEL typically loses or ties. In the experiments, we report three latency curves: monolithic —the mean end-to-end latency of the monolithic (baseline) appli-cation; modular or app —the mean latency of the modular (HEL) application; and service —the amortized service latency per appli-cation call. We also report the corresponding throughput curves under the same per-application-call normalization. 

System Amortization. We vary the number of sequential PD_mod

## 6.1 Application 

The application is a 3D 25-point eighth-order acoustic-wave sten-cil from the heavy-stencil benchmark class [7, 20] (25 multiplies and 24 adds per cell, four-cell halo per axis). It periodically emits the live domain as a checkpoint after compression with PFPL [9], a four-stage lossy floating-point compressor with absolute error bound. PFPL combines integer quantization, neighbor-difference encoding, byte transposition, and run-length zero elimination, and operates on independently compressible chunks, making it a natural fit for service-side execution. In our sweep, the stencil runs for 1000 timesteps, emits every 100 timesteps, and compresses 1024-double chunks. The HEL configuration runs the stencil on a 104-SM appli-cation partition while a 4-SM service partition compresses those chunks concurrently. This case study uses HEL’s warp-granularity task mode because PFPL contains warp-collective stages. The mono-lithic baseline performs the same checkpointing and compression, but launches the compression phase from the CPU at each emis-sion point on all 108 SMs. From the application’s perspective, HEL keeps the checkpointing delta small: the stencil submits checkpoint-compression work at each emission point, while the service per-forms the compression asynchronously.

## 6.3 Structural Advantages Beyond Latency 

Beyond the latency win shown above, the service abstraction pro-vides structural advantages independent of any single benchmark. It decouples application code from the compression algorithm (mod-ularity), supports multiple concurrent services on one partition without inflating kernel complexity (composability), preserves run-time state across application invocations (persistence), exposes the application/runtime resource split as an explicit MPS partition rather than implicit time-multiplexing (governance), and lets new compressors deploy to the service without recompiling applications (upgradability). These advantages would still motivate the service abstraction even on workloads where a hand-tuned monolithic kernel could match or exceed HEL’s raw latency—the same reason-ing that motivates operating systems over bare-metal application stacks. 

## 7 Conclusions and Future Work 

We presented HEL, a modular GPU runtime system based on a persistent service for coroutine-style applications. HEL decomposes a monolithic application into dependent tasks and inline application work that proceed concurrently under bounded resources. It is fundamentally different from prior work in the GPU space in several ways: 

Host-Device Decoupling (Control Plane) “Traditional” GPU run-times (e.g., StarPU and Legion) manage task graphs on the CPU. Every time a task completes, the CPU must be noti-fied (often via an interrupt or polling), and the CPU then Łupińska, Porumbescu, and Owens 

schedules the next task. HEL moves this entire control loop onto the GPU. This eliminates the PCIe latency and CPU-overhead bottleneck, allowing the GPU to autonomously submit and process its own work. 

Spatial vs. Temporal Execution Most runtimes submit kernels that compete for the entire GPU temporally (one after an-other). HEL uses NVIDIA MPS (Multi-Process Service) to partition the GPU spatially. By dedicating a fixed set of SMs to the HEL service, the runtime remains responsive even when the application’s compute kernels are fully saturating the rest of the hardware. 

Independence and Persistence HEL is a separable entity because it is not compiled into the application’s kernel loop. It is a persistent service that exists independently of the lifespan of any single user kernel. This allows it to manage state, retries, and dependencies across kernel boundaries fully on the GPU without (as in traditional GPU runtimes) returning control to the host. 

Coroutine-based Preemption While GPUs are traditionally non-preemptive, HEL’s use of coroutine-like tasks allows it to pause and resume work at a software level within its dedi-cated partition, providing a degree of flexibility lacking in standard CUDA/OpenMP tasks. Implementing HEL exposed several limitations of current CUDA support: coroutines are not natively supported, shared-memory capacity is insufficient for all scheduling structures at the desired scale, and MPS provides neither a shared heap nor a convenient shared-pointer abstraction across contexts. Our results show that HEL can serve as a modular alternative to monolithic applications and improving performance in selected regimes, including pipelined execution, latency-bound workloads, and cases where overlap can hide part of the execution cost. HEL is not expected to outperform a hand-optimized monolithic applica-tion that already saturates the GPU. Its advantage appears instead in underutilized regimes, where overlapping task execution with inline application work improves effective performance. HEL validates the viability of a persistent GPU service for co-ordinating user tasks. We expect future workloads, in light of the trend toward underutilization, 1 will increasingly benefit from our approach. However, future hardware with a more closely coupled CPU and GPU (e.g., NVIDIA Grace Hopper or AMD MI300A) would not suffer from the large overhead penalty characteristic of today’s discrete GPUs, and would benefit less. Future work will broaden the model to support richer dependency structures such as general DAGs, variable-size thread groups, and more flexible scheduling policies with configurable priorities and fairness mechanisms.
