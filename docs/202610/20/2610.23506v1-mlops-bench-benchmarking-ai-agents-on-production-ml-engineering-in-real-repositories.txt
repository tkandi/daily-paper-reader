# MLOps-Bench: Benchmarking AI Agents on Production ML Engineering in Real Repositories 

Quoc Co Tran, Hitesh Laxmichand Patel, Diwakar Mahajan Kshitij Bakliwal, Avi Sil, Katrin Kirchhoff

Abstract 

AI agents are increasingly expected to mod-ify and maintain machine-learning systems in production, yet existing benchmarks primarily evaluate either competition-style ML experi-mentation or generic repository issue resolution. We introduce MLO PS -B ENCH , a repository-grounded benchmark for production ML engi-neering. Unlike prior ML-agent benchmarks, MLO PS -B ENCH evaluates executable lifecy-cle changes inside real ML repositories, span-ning data pipelines, feature engineering, model training, model serving, monitoring, CI/CD and governance, and end-to-end integration. Each task is grounded in repository evidence and includes a natural-language requirement, ora-cle patch, plausible buggy baseline, fail-to-pass tests, pass-to-pass tests, and provenance meta-data. The benchmark contains 212 validated tasks from 31 public ML repositories, with 636 fail-to-pass tests and 856 pass-to-pass tests. We evaluate six agents and find that the best system solves 31.2% of tasks while passing 68.7% of tests, showing that current agents often make partial progress but still fail production-relevant behavioral requirements. MLO PS -B ENCH 1

shifts agent evaluation beyond model build-ing and issue fixing toward repository-native MLOps work where correctness depends on lifecycle reasoning, behavioral robustness, and preservation of existing system behavior. 

1 Introduction 

Operating machine-learning systems in production is becoming a core expectation for AI agents, not just writing code or improving model accuracy. Production ML work differs from both ordinary software maintenance and competition-style ML: a correct change may need to preserve data con-tracts, maintain train/serve consistency, record arti-fact metadata, validate inference inputs, emit mon-

itoring signals, or enforce governance gates. Ex-isting benchmarks only partially measure these ca-pabilities. SWE-bench evaluates repository-level issue resolution (Jimenez et al., 2024), while data-science and ML-agent benchmarks emphasize anal-ysis, experimentation, or model improvement in task or competition settings (Jing et al., 2024; Chan et al., 2024; Huang et al., 2024a; Chen et al., 2025; Jha et al., 2025). They leave under-specified whether agents can make safe, executable MLOps changes inside existing ML repositories. MLO PS -B ENCH addresses this gap with a repository-grounded benchmark for production ML engineering. Its key novelty is that task validity is defined by lifecycle evidence rather than by issue availability, leaderboard performance, or generic programming difficulty: each task must be tied to native repository surfaces such as loaders, schemas, feature transforms, training configurations, model artifacts, serving paths, monitoring outputs, work-flow files, or governance metadata. This grounding reflects known sources of ML technical debt and production-readiness risk (Kreuzberger et al., 2023; Sculley et al., 2015; Breck et al., 2017). MLO PS -B ENCH evaluates agents across six core MLOps stages plus one cross-stage integra-tion category: data pipelines, feature engineer-ing, model training, model serving, monitoring, CI/CD and governance, and end-to-end lifecycle integration. Each task pairs a repository-native re-quest with executable behavioral tests, an oracle implementation, a plausible buggy baseline, and provenance metadata, testing whether agents sat-isfy production-relevant lifecycle contracts while preserving existing behavior and avoiding realis-tic failures: missing validation, train/serve skew, incomplete artifact metadata, malformed-input han-dling, ineffective monitoring thresholds, and non-enforcing governance checks. 2 Related Work 

Repository-level software engineering bench-marks. Agent benchmarks have shifted from isolated code generation toward executable, repository-grounded evaluation. BugsInPy pro-vides reproducible Python bugs for controlled de-bugging; SWE-bench tests whether agents resolve real GitHub issues by editing a codebase and pass-ing tests (Widyasari et al., 2020; Jimenez et al., 2024). This is the closest methodological prece-dent for MLOps-Bench: it treats the repository, not a standalone prompt, as the evaluation environment. Recent variants broaden this along language and modality axes: SWE-bench Multilingual, Multi-SWE-bench and SWE-bench Multimodal extend issue resolution across ecosystems and add visual artifacts (SWE-bench Team, 2025; Zan et al., 2025; Yang et al., 2025) yet their semantics remain cen-tered on issue resolution. MLO PS -B ENCH instead targets production ML lifecycle engineering, where tasks are validated using evidence such as data con-tracts, training artifacts, and monitoring signals. 

Data-science and machine-learning agent bench-marks. A second line evaluates agents on data-science and ML workflows. DS-1000, DSEval, DS-Bench, DataSciBench, and DA-Code study code generation and increasingly realistic data-analysis tasks where agents inspect files, execute code, and recover from errors (Lai et al., 2023; Zhang et al., 2024; Jing et al., 2024; Zhang et al., 2025; Huang et al., 2024b), but their outputs are analyses, note-books, or modeling results rather than repaired op-erational ML systems. Closer to ML engineering, MLAgentBench eval-uates agents as iterative experimenters that write code, run experiments, inspect outputs, and re-vise their approach (Huang et al., 2024a); MLE-bench and MLE-Dojo scale this through Kaggle-derived or interactive ML-engineering tasks span-ning data preparation, modeling, debugging, and repeated execution (Chan et al., 2025; Qiang et al., 2026); and ML-Bench and ML-Dev-Bench shift toward repository-level ML development (Tang et al., 2023; Padigela et al., 2025). MLOps-Bench complements these by shifting evaluation from model development or competition performance to production-oriented lifecycle changes inside ex-isting repositories. 

MLOps, ML reliability, and data-centric eval-uation. MLOps research explains why produc-tion ML systems cannot be evaluated only as conventional software or isolated modeling prob-lems. CRISP-ML(Q) frames ML development as a quality-assured process spanning data understand-ing, preparation, modeling, evaluation, deployment, and monitoring (Studer et al., 2021), and MLOps surveys and architecture studies emphasize orches-tration, versioning, CI/CD, continuous training, monitoring, and feedback loops (Kreuzberger et al., 2023; John et al., 2021; Recupito et al., 2022). Such dependencies shape repository changes: a schema change can break feature computation, a feature fix can require retraining, retraining can invalidate evaluation thresholds, and a serving change can require updated monitoring, or gov-ernance checks. Work on ML reliability and data-centric evaluation identifies many failure modes that motivate MLO PS -B ENCH . Defects4ML col-lects reproducible ML faults, and studies of deep-learning bugs and ML testing show recurring prob-lems around data assumptions, numerical instabil-ity, model construction, and library interactions (Morovati et al., 2023; Zhang et al., 2022; Riccio et al., 2020). DataPerf and ML data validation highlight failures in data selection, schema valida-tion, and distribution monitoring, while pipeline-analysis tools show how preprocessing choices af-fect downstream model behavior (Polyzotis et al., 2019; Mazumder et al., 2023; Grafberger et al., 2023). These works motivate lifecycle-aware evalu-ation but typically study reliability as isolated bugs, data-quality tasks, or analysis settings rather than executable repository-native tasks for autonomous agents. 

Positioning of MLO PS -B ENCH . MLO PS -BENCH sits at the intersection of these lines: Repository-level software benchmarks provide the execution-based methodology, data-science and ML-agent benchmarks provide realistic development and experimentation settings, and MLOps and ML-reliability research identify the lifecycle dependencies and failure modes that make production ML difficult. No existing bench-mark combines all three: repository-grounded executable evaluation, MLOps lifecycle semantics, and behavioral tests distinguishing correct fixes from plausible but incomplete production patches. MLO PS -B ENCH fills this gap with tasks spanning data pipelines, feature engineering, model training, model serving, monitoring, CI/CD and governance, and end-to-end lifecycle integration. 

3 Method 

MLO PS -B ENCH generates executable benchmark tasks from real ML repositories through an evidence-preserving pipeline: repository selection, snapshotting, context extraction, stage-specific task generation, oracle construction, buggy-baseline construction, and executable validation. Each ac-cepted task is traceable to repository evidence and evaluated by tests. Figure 1 summarizes the pipeline. 

3.1 Crawling Repositories 

We identify open-source ML repositories on GitHub using MLOps-related search queries, in-cluding mlops , machine learning , and ml-ops .Candidate repositories must be clonable, non-empty, and show evidence of ML engineering ac-tivity through source structure, issues or pull re-quests, workflow files, or pipeline artifacts. We then manually 3 select 31 repositories for lifecy-cle coverage, domain diversity, data and business context, buildability, and manageable audit size, excluding repositories with weak structure, limited ML pipeline signal, or poor fit for realistic MLOps-stage tasks. The resulting 212 tasks cover primarily Python-based ML systems, with additional cover-age of YAML/config-heavy templates, TypeScript and web-serving code, shell automation, JavaScript utilities, and one C/C++ IoT repository. This scale is larger than SWE-Bench Lite’s 11 repositories while remaining feasible for human audit. 

3.2 Repository Grounding and Context 

For each selected repository, we freeze a source snapshot and record provenance metadata, includ-ing URL, commit hash, license evidence, language, dependency manifests, test commands, workflow files, and likely modification surfaces. This sup-ports reproducibility and auditability by preserving the source snapshot, dependency context, license evidence, and evaluation commands for each se-lected repository. We then construct a context bundle with four views. The business context summarizes the do-main, users, model purpose, and operational risk. The technical context identifies architecture, entry-points, data paths, configuration files, model arti-facts, service interfaces, and tests. The MLOps con-text records lifecycle evidence such as ingestion, feature computation, training, evaluation, serving, monitoring, CI, deployment, and governance. The requirement context converts observed gaps into candidate engineering requirements with relevant files, expected behavior, constraints, and preserved behavior. This context prevents generic task generation. A monitoring task must be tied to an existing pre-diction path, metric output, logging surface, or de-

3.3 Task Generation 

We generate tasks across six core MLOps stages plus one end-to-end integration category: data pipelines, feature engineering, model training, model serving, monitoring/observability, CI/CD and governance, and end-to-end MLOps flow. For each stage, the generator verifies repository evi-dence, derives a testable stage contract, identifies a minimal native modification surface, and writes a requirement that is specific enough to evaluate but does not reveal the implementation. The end-to-end category is reserved for cross-boundary tasks rather than merely larger edits. Ex-amples include training metadata consumed by serving, validation failures surfaced through CI, or monitoring summaries derived from batch in-ference outputs. Table 2 summarizes the stage evi-dence, generated requirements, and oracle surfaces. 

3.4 Problem Generation 

Each accepted problem is written as a repository-native engineering request with five fields. The business motivation explains why the change mat-ters operationally. The technical context points to relevant components and current behavior. The requirement states the desired behavioral change in testable terms. The constraints specify repos-itory conventions, allowed modification surfaces, compatibility requirements, and preserved behav-ior. The evaluation intent summarizes what hidden tests will check without revealing exact assertions. The generator stores the evidence used for each field so reviewers can audit grounding. 

3.5 Oracle, Buggy Baseline, and Tests 

After a problem is accepted, MLO PS -B ENCH gen-erates an oracle solution as one valid implementa-tion of the benchmark contract. Oracle generation localizes the edit surface, applies the smallest na-tive patch that satisfies the requirement, and records a rationale linking each changed file to the business motivation, technical context, and stage contract. The oracle is therefore a feasibility and validation artifact, not the only acceptable solution. Following the controlled-defect tradition in software-testing benchmarks (Just et al., 2014), the pipeline also generates a plausible buggy baseline for the same problem. The buggy patch should resemble a reasonable but incomplete engineering attempt: it may add the requested API but skip schema validation, compute a feature differently in training and serving, write a model artifact without metadata, handle normal inference but not mal-formed inputs, emit metrics without thresholds, or add a governance check that never fails. We avoid trivial baselines such as no-op patches or syntax er-rors because they do not test realistic agent failure modes. Tests are generated after both patches exist. Fail-to-pass (F2P) tests encode the new benchmark con-tract and must fail on the buggy baseline but pass on the oracle. They target externally visible be-havior such as rejected invalid records, stable fea-ture values, saved artifact metadata, prediction re-sponse schemas, emitted monitoring summaries, or failing release gates. Pass-to-pass (P2P) tests pro-tect behavior that should remain unchanged, usu-ally by reusing or lightly extending existing tests around adjacent functionality. A benchmark is ac-cepted only when the oracle passes both test sets, the buggy baseline fails at least one F2P test for the intended reason, and the tests do not depend on external services or hidden state. 

3.6 Validation and Evaluation 

A task is accepted only if grounding checks link the requirement to repository evidence, stage-contract checks confirm the claimed MLOps stage, behav-ioral tests distinguish the oracle from the buggy baseline, and P2P tests preserve existing behavior. During evaluation, an agent patch is applied to the frozen snapshot and scored using task completion rate, test pass rate, runtime, patch size, changed-file count, and error categories. Benchmark construction used a separate develop-ment and evaluation split. We used two repositories and 25 tasks to iterate on generation prompts, ora-cle construction, test construction, and executable validation checks. The reported evaluation uses the remaining 29 repositories and 187 tasks. 

3.7 Dataset Statistics 

Overall, MLO PS -B ENCH contains 212 tasks span-ning six core MLOps stages and one end-to-end MLOps flow. Each task is grounded in a repos-itory snapshot and scored with executable tests. The benchmark includes 25 development tasks and 187 evaluation tasks. In total, it contains 636 F2P tests, 856 P2P tests, and 1,492 tests overall. Ta-ble 3 shows the task and test distribution across stages. The per-stage counts are not exactly bal-anced because five candidate tasks were rejected during quality checks, primarily when the oracle did not pass reliably or the generated tests did not cleanly distinguish the oracle from the buggy base-line.

3.8.2 Test measure generalizable behavior

The annotators examined whether the F2P tests covered the important observable func-tional requirements in the task specification, includ-ing expected outputs, side effects, validation rules, edge cases, and integration behavior, rather than superficial or implementation-specific signals. 3.8.3 Test accepting alternative correct solutions 

Five annotators participated in the study. Each task was independently reviewed by two annotators, yielding 20 task-level annotations in total, with each annotator evaluating four tasks. For every task, annotators examined the problem statement, F2P test suite, oracle patch, agent patch, and rele-vant repository context. The audit was substantial in terms of material reviewed. Because every task was double-annotated, this corresponds to an ag-gregate assigned review volume of 80,698 lines, in addition to any linked repository context inspected as needed. For 8 of the 10 patches, both annota-tors independently judged the agent patch to be a correct alternative implementation. The remaining two cases involved disagreement and were there-fore reviewed by a third annotator, who classified both as correct alternatives. After adjudication, all patches were judged to satisfy the intended task contract while representing valid alternatives to the oracle.

Summary with respect to the research questions. 

For RQ1, current agents can solve a non-trivial fraction of repository-native MLOps tasks, but the best system completes only 31.2% of evaluation tasks. For RQ2, performance varies across life-cycle stages, showing that aggregate scores hide stage-specific strengths and weaknesses. For RQ3, the gap between task completion and test pass rate, together with the error analysis, shows that many patches are partially correct but behaviorally in-complete. 

5 Conclusion 

We introduce MLO PS -B ENCH , a repository-grounded benchmark for evaluating AI agents on production-oriented ML engineering tasks. Unlike Kaggle-style ML benchmarks or generic repository-repair benchmarks, MLO PS -B ENCH targets life-cycle work that is central to operating ML sys-tems, including data pipelines, feature engineer-ing, model training, model serving, monitoring, CI/CD and governance, and end-to-end MLOps integration. Each task is grounded in real repos-itory evidence and paired with executable tests, oracle patches, buggy baselines, and provenance metadata, enabling evaluation of both functional correctness and preservation of existing behavior. Our evaluation suggests that current coding agents make meaningful progress on MLOps tasks but re-main far from reliable production-level automation. In this run, the best-performing system achieves a 31.2% task completion rate and a 68.7% test pass rate, indicating that agents often implement partial or superficially plausible solutions while still missing important behavioral requirements. Stage-level and error analyses further confirm that failures are not limited to syntax or setup prob-lems; many failures involve incorrect functionality, missing imports, dependency issues, or incomplete handling of repository-specific contracts. These results suggest that production ML engineering re-mains a challenging setting for AI agents and that future progress will require stronger repository un-derstanding and better lifecycle reasoning. 

6 Limitations 

MLO PS -B ENCH is intended to evaluate production-oriented ML engineering in real repositories, but several limitations remain. First, MLO PS -B ENCH is constructed from 31 public ML repositories selected for domain diversity, lifecycle evidence, and the ability to be reliably frozen, built, audited, and tested. Although these repositories contain genuine ML lifecycle structure, they are open-source codebases rather than deployed commercial systems. As a result, MLO PS -B ENCH 

measures production-style operational engineering in repository-native settings, but it should not be interpreted as fully representative of all industrial MLOps environments. Second, the benchmark tasks are synthesized from repository evidence rather than collected ex-clusively from naturally occurring production in-cidents. This enables balanced lifecycle coverage, oracle solutions, buggy baselines, and executable fail-to-pass and pass-to-pass tests, but may intro-duce generation and test-design artifacts. Tasks can be more localized, explicit, and test-oriented than real MLOps requests, while finite test suites can only approximate production correctness: they can-not cover every downstream interaction, workload, data distribution, or operational failure mode. Finally, because the generation pipeline relies on one model family while evaluation spans several, a potential concern is that the construction process could advantage same-family agents. We do not ob-serve this in practice — the highest-scoring system (Codex, GPT-5.5) is not from the family used in generation — but we cannot fully rule out subtler stylistic alignment between generated tests and par-ticular agents, and we flag it as a threat to validity that warrants further study. 

7 Ethical Considerations 

MLO PS -B ENCH is constructed from public open-source repositories. We record provenance, source snapshots, dependency information, and license ev-idence for each selected project, and include only repositories whose licenses permit research and benchmark use under the corresponding license terms. Issues and pull requests are used only as public repository-level signals of activity and rele-vance; tasks are generated from lifecycle evidence in the source snapshot rather than from private user data or confidential production incidents. We do not collect private information, creden-tials, secrets, or non-public organizational data, and we exclude repositories with obvious privacy, cre-dential, or reproducibility concerns. The bench-mark is intended for controlled evaluation of AI agents on frozen repositories, not for unsupervised modification of production ML systems. Since gen-erated patches can be incomplete or unsafe outside the benchmark harness, benchmark success should not be interpreted as readiness for autonomous de-ployment without human review. We will release documentation covering construction, licensing, evaluation, and channels for reporting takedown, licensing, or data-quality concerns. The authors used generative AI tools for limited language editing, rewriting suggestions, and assis-tance in improving exposition. All scientific con-tent, experimental design, code, analysis, claims, citations, and final text were reviewed, verified, and approved by the human authors.
