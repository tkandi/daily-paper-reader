Abstract—Real-time streaming video question answering with
vision–language models must answer queries that arrive at any
time with low latency while sustaining the video-processing rate
required by the application. Existing systems construct key–value
(KV) caches for the entire video as it arrives, although a query
typically uses only a few of the preceding frames as evidence.
This highlights a fundamental trade-off: performing more com-
putation as video arrives reduces query-time computation but
can increase processing lag, whereas deferring computation can
increase the video-processing rate but requires additional query-
time computation for retrieved content.
We present StreamAhead, an algorithm–system co-design
that exploits this trade-off through adaptive precomputation:
dynamically controlling how much computation to complete for
each video segment before a query arrives. StreamAhead encodes
video segments independently and lets each remain at a different
representation level, from inexpensive visual features to costly KV
caches, completing KV caches only for the retrieved segments
when a query arrives. StreamAhead profiles offline the cost of
advancing a segment to each representation level. Its runtime
uses these profiles to schedule segment computation concurrently
with query execution, pipelining it across heterogeneous CPU and
GPU resources while maintaining the required video-processing
rate. StreamAhead achieves accuracy competitive with state-
of-the-art methods with up to 10.4× lower time-to-first-token
(TTFT), and up to 5.9× lower TTFT than state-of-the-art
streaming systems. It sustains 30 FPS with P95 TTFT under 0.5 s,
and up to 57 FPS with P95 TTFT under 2 s. To our knowledge,
StreamAhead is the first real-time streaming video QA system
with competitive accuracy, setting a new Pareto frontier between
video-processing rate and TTFT.
I. INTRODUCTION
Streaming video question answering with vision–language
models (VLMs) considers a continuously arriving video stream
in which users may issue questions at arbitrary times [1]–
[6]. An application specifies the video sampling rate and
resolution that the system is expected to process. The system
must sustain this processing rate; otherwise, a growing backlog
creates processing lag, i.e., a delay between video arrival
and completion of the required processing [7], making recent
video unavailable when a query needs it. In this paper, we
therefore study a fundamental question for streaming video
question answering: how can we sustain the required video-
processing rate while simultaneously minimizing time-to-first-
token (TTFT), measured from query arrival to the first gener-
ated token? We call a system real-time when it achieves both:
it keeps pace with the incoming video and answers queries
with low latency.
Existing streaming video QA systems reduce query-time
computation by precomputing reusable video representations,
such as visual features or key–value (KV) caches, that can later
be reused when relevant historical content is retrieved [2], [8]–
[12]. For example, ReKV [2] incrementally constructs reusable
KV states for incoming video and retrieves query-relevant
cached states for answer generation. However, constructing
deeper representations such as video KV caches requires
substantial computation before the relevance of that content to
a future query is known. A particular query typically depends
on only a small subset of the retained video history, which
can be identified through retrieval mechanisms [2], [9], [13],
[14]. Fully constructing deep representations for the remaining
history therefore spends processing capacity on content that
may never be used by that query. This extra computation
can cause the system to fall behind the incoming stream and
accumulate processing lag, without benefiting the query.
Rather than constructing full KV caches for the entire
stream as video arrives, a system can retain intermediate
results and postpone the remaining computation [15]–[17].
This exposes a fundamental trade-off: performing more com-
putation as video arrives reduces query-time computation but
can increase processing lag, whereas deferring computation
increases the video-processing rate but requires additional
computation at query time if that content is later retrieved. This
motivates what we call adaptive precomputation: deciding at
runtime how much computation to complete before a query
arrives, based on the current workload and available resources.
Exploiting this trade-off, however, raises two challenges.
First, the system must be able to complete different amounts
of computation for different parts of the video. Many existing
systems build the KV caches of new frames from the cached
states of earlier frames [2], [9], [10], [18], [19]. Under this
temporal dependency, completing one retrieved segment at
query time first requires completing every earlier segment.
The query-time cost then grows with the length of the video
history, not with the retrieved content required as evidence
for that query. Second, the system must decide at runtime
which segments to precompute and how much computation to
complete for each. It must also decide when to run this work,

To address these challenges, we present StreamAhead, an
algorithm–system co-design for adaptive precomputation in
streaming video QA (Figure 1). StreamAhead divides the
incoming video into fixed-duration segments and precomputes
each segment independently, without any temporal dependency
on other segments’ KV caches. Each segment retains results at
one of three representation levels, corresponding to successive
stages of processing that segment: raw frames and a retrieval
key (L1), visual features (L2), or a query-independent KV
cache (L3). Later processing continues from the stored results
without repeating completed stages. Before a query arrives,
different segments can remain at different levels according to
the available resources. At query time, StreamAhead retrieves
relevant segments, reuses existing KV caches, and completes
KV construction for retrieved segments still at L1 or L2.
StreamAhead then combines the retrieved KV caches through
retrieved representation composition, placing them in video
order with continuous positions to form a single context [20],
[21]. Because segments never attend to one another, we also
propose a lightweight mechanism to recompute each segment’s
short text suffix in this context, adding cross-segment interac-
tion without rebuilding visual KV states.
To address the second challenge, StreamAhead first profiles
offline the compute and memory cost of advancing a segment
to each representation level. It also profiles query TTFT
over segments at each level, and uses both profiles to select
the processing configuration and required representation level
for the target workload [7], [22]. Online, a shared segment
table tracks each segment’s completed representation level and
whether its results are in CPU or GPU memory. It also tracks
ongoing work on the segment, such as advancing it to a deeper
level or moving it between CPU and GPU. With this table,
video processing and query execution run concurrently: a
query that needs a segment already being advanced reuses that
work instead of repeating it. The runtime pipelines segment
computation across heterogeneous CPU and GPU resources,
overlapping CPU preparation and data movement with GPU
execution. It also places representations across CPU and GPU
memory [23]–[25]. Its scheduler keeps pace with the incoming
video, gives priority to query work when a query arrives,
and uses spare capacity for additional precomputation. While
a query runs, processing of newly arriving video may fall
behind. After the query, the runtime first clears this backlog
and only then resumes additional precomputation. We make
the following contributions:
• Algorithm. We process video as independent segments
with three reusable representation levels, so that different
amounts of computation can be completed for each
segment before a query arrives. We combine retrieved
segments through retrieved representation composition,
with a lightweight mechanism that adds cross-segment
interaction.
• Scheduling. We design profile-guided scheduling for
adaptive precomputation. Offline profiling selects the
required representation level. Online scheduling keeps
pace with the incoming video, prioritizes queries, and
uses spare capacity for additional precomputation.
• Runtime. We build a runtime that executes video process-
ing and queries concurrently. It uses a shared segment
table, pipelining across heterogeneous CPU and GPU
resources, and a CPU–GPU memory hierarchy.
StreamAhead achieves accuracy competitive with state-of-
the-art methods with up to 10.4× lower TTFT, and up to 5.9×
lower TTFT than state-of-the-art streaming systems. It sustains
30 FPS with P95 TTFT under 0.5 s, and up to 57 FPS with P95
TTFT under 2 s. To our knowledge, StreamAhead is the first
real-time streaming video QA system with competitive accu-
racy, setting a new Pareto frontier between video-processing


rate and TTFT.
II. RELATED WORK
A. Streaming Video Question Answering
Streaming video question answering requires a model to
retain information from a continuously arriving video and
answer questions issued at arbitrary times [3], [4]. Early
work trains online video assistants that learn when to re-
spond and what to remember as frames arrive [1], [19], [26],
[27]. Memory-based designs summarize the video history into
compact visual features, events, or text [8], [28]–[30], while
retrieval-based approaches select the parts of a long video that
are relevant to a question [13], [14], [31]. Closest to our work,
several methods retain the video history as KV caches, so
that language-model computation can be reused when relevant
content is retrieved [2], [9]–[11], or maintain a bounded KV
cache within a fixed memory budget [12], [18], [32], [33].
These works show that precomputing reusable video rep-
resentations substantially reduces query-time computation. In
most of them, however, the KV caches of new frames are
constructed from the cached states of earlier frames. The
computation completed as video arrives is also fixed by design:
every incoming frame is encoded into the KV cache whether or
not a later query uses it. Moreover, many of these methods are
evaluated on answer quality with the video processed offline,
without requiring that the incoming video be processed as fast
as it arrives. Under real-time streaming, this fixed computation
can fall behind the incoming video and accumulate processing
lag, making recent video unavailable when a query needs it.
StreamAhead instead processes video segments independently
and decides at runtime how much computation to complete
for each segment before a query arrives, i.e., adaptive pre-
computation. It thereby keeps pace with the incoming video
while completing KV caches only for the retrieved segments
at query time.
B. Efficient Streaming Video Inference
A complementary line of work reduces the cost of pro-
cessing each frame so that a system can keep pace with
the incoming video. Token pruning and compression methods
reduce the number of visual tokens processed by the lan-
guage model [34]–[37], and streaming variants apply similar
reductions as frames arrive [38], [39]. Other work invokes
the language model only when relevant events occur [40], ac-
celerates KV retrieval during streaming prefill with dedicated
hardware [41], or reuses computation across overlapping video
windows [42]. Recent systems also treat video-processing
throughput and query latency as explicit goals: one pipelines
model stages to sustain high frame rates, evaluating TTFT
separately [43], and another precomputes only the first layers
of the language model as video arrives and completes the
remaining layers at query time [17]. Evaluation protocols
have likewise begun to measure latency under realistic video
arrival [44].
These advances make each unit of computation cheaper
or better overlapped. They either reduce the visual evidence
processed by the model or fix how much computation is
completed before a query arrives, such as a full KV cache for
every video chunk or a fixed number of layers. StreamAhead
keeps the visual evidence unchanged and adapts the amount of
precomputation to the current workload: when spare capacity
is available, segments advance to KV caches before a query
arrives, and under heavier load they remain at earlier represen-
tation levels so that processing lag does not accumulate. Token
reduction is orthogonal to this decision and can be applied
within each segment.
C. Scheduling Under Rate and Latency Requirements
Systems for live video analytics have long scheduled com-
putation to keep pace with incoming streams. They adapt pro-
cessing configurations to bound processing lag under limited
resources [7], [22], schedule inference across GPUs to meet
latency targets [45], and share accelerators between work that
must keep pace with the stream and background work [46].
Video query systems split computation between inexpensive
processing as video arrives and expensive processing when
a query is issued [15], [16]. In LLM serving, systems meet
latency targets through iteration-level batching, paged KV
memory, chunked prefill, and disaggregated prefill and de-
coding [47]–[51], and multimodal serving systems separate
or overlap visual encoding and language-model prefill [52]–
[54]. Related techniques keep KV caches across CPU and
GPU memory [23]–[25], use idle GPU capacity for deferrable
work [55], or overlap the arrival of streaming input with
prefill [56].
StreamAhead builds on these ideas with two differences.
Unlike video analytics systems, its precomputation produces
reusable model states, and how much work is completed
as video arrives versus at query time is decided at runtime
for each segment rather than fixed in advance. Unlike LLM
serving systems, its input is a continuously arriving video
that must be processed at the required rate while queries
are answered concurrently. StreamAhead’s scheduler therefore
gives priority to keeping pace with the incoming video and
answering queries, and uses spare capacity to precompute KV
caches for segments that future queries may retrieve.
III. PROBLEM DEFINITION
Streaming input. We consider the incoming video as a
sequence of fixed-duration segments s1, s2, . . . of duration ∆,
where segment si becomes available at time ti = i∆. The
application specifies the video sampling rate and resolution.
Each segment therefore contains K frames to be processed,
and the required video-processing rate is r = K/∆frames per
second.
Processing lag. As segments arrive, the system performs their
required processing, which takes time Treq per segment. The
system keeps pace with the incoming video if Treq ≤∆. Oth-
erwise, each new segment adds Treq−∆to the processing lag,
i.e., the delay between a segment’s arrival and the completion
of its required processing. The lag then keeps accumulating
as the stream continues.


Query latency. A query q is issued at time tq, unknown in
advance. A VLM answers it from the segments that have
arrived by tq, and the answer may depend on any of them.
Its time-to-first-token, TTFT(q), is measured from tq to the
first generated token. It includes the computation still needed
for the segments the query uses. Processing lag increases
TTFT, because segments whose processing has fallen behind
need more computation when a query uses them. As lag
accumulates, more of the arrived video is affected. Existing
streaming video QA methods typically measure TTFT on
video that has already been processed, and therefore do not
account for processing lag.
Real-time streaming video QA. We call a system real-
time at rate r with TTFT target τ if it keeps pace with
the incoming video, Treq ≤∆, and answers every query
with TTFT(q) ≤τ. The goal is to remain real-time at the
highest video-processing rate, without reducing the sampling
rate or resolution and without knowledge of future queries. The
two conditions compete for the same resources: processing
performed as segments arrive adds to Treq, whereas processing
deferred until a query arrives adds to its TTFT.
IV. METHOD
As defined in Section III, StreamAhead balances Treq
against TTFT through adaptive precomputation over indepen-
dent segments at multiple representation levels. Before a query
arrives, different segments may complete different amounts of
computation. When a query is issued, StreamAhead retrieves
a small set of relevant segments, reuses the deepest committed
representation available for each segment, completes only
the remaining computation required by those segments, and
composes the resulting representations for answer generation.
We use precomputation to denote the computation completed
for each segment before a query arrives. Figure 2 gives an
overview of StreamAhead.
A. Independent Segment Processing
StreamAhead partitions the continuous video stream into
fixed-duration segments s1, s2, . . . , sn. Each segment is pro-
cessed under the same fixed textual prefix, but its visual
representation and query-independent language-model state
are constructed without using state from other segments. This
independence is essential for adaptive precomputation: if a
segment depends on reusable states constructed from earlier
video, deferring its computation may also require completing
the preceding dependent history before the segment can re-
sume computation. StreamAhead removes this cross-segment
dependency, allowing each segment to advance, remain at an
intermediate representation, or resume later without requiring
neighboring segments to reach the same processing stage.
Computed segment states therefore serve as the basic units
of precomputation and runtime scheduling.
Independent construction is not equivalent to jointly en-
coding multiple segments because the reusable state of one
segment has not attended to the visual content of other
segments. StreamAhead accounts for this distinction when
retrieved segment representations are combined at query time.

V. SYSTEM DESIGN
StreamAhead builds on independent segment processing and
representation levels to support adaptive precomputation. A
shared segment table maintains each segment’s committed rep-
resentation, placement, and in-flight state, providing a consis-
tent view for concurrent video processing and query execution.
The system combines offline profiling with an online runtime
(Figure 3). Offline profiling characterizes computation, query-
time, and memory costs to select a processing configuration
and required representation level. During online execution,
the scheduler uses these profiles and the shared segment
state to select representation transitions and assign execution
priorities. A heterogeneous CPU–GPU pipeline executes the
scheduled work through cross-segment pipelining and CPU–
GPU overlap, while reporting execution progress through the
shared table. Further, a CPU–GPU representation memory
hierarchy manages the placement of completed representations
under bounded memory.
A. Offline Profiling and Configuration Selection
StreamAhead profiles continuous video processing and
query-time execution before online execution. For a fixed
model, resolution, segment duration, retrieval configuration,
and composition method, the profiler varies the number of
frames processed per segment, K (Section III). For each candi-
date K, the profiler measures the wall-clock latency of L1 and
retrieval-key construction, L1-to-L2 visual encoding, and L2-
to-L3 KV construction. It also records the corresponding L2
and L3 memory footprints. Using representations constructed
under the same configuration, StreamAhead measures end-
to-end TTFT over segments at each level, and the major

B. Shared Segment Table
StreamAhead maintains a shared record for every retained
video segment. Each record contains the segment’s temporal
metadata and retrieval key, its committed representation level
(the latest completed level) and representation placement (CPU
or GPU memory), any in-flight transition (work currently
advancing or moving the segment), and whether the com-
mitted representation is currently in use. Video processing,
precomputation, query execution, and memory management
consult the same record when operating on a segment. Only
committed representations are visible to other tasks. When
a representation transition begins, the previously committed
representation remains available until the new representation
has been fully constructed. For example, a segment undergoing
an L2-to-L3 transition remains committed at L2 until the
transition completes, after which the new L3 representation
becomes visible. Model execution and data movement occur
outside the table update, so no task sees a partially constructed
representation. The table also records in-flight transitions so
that concurrent tasks do not duplicate the same representation
construction. If a query requires a transition that is already
in progress, it can reuse or wait for that work. Represen-
tations used by an active query are pinned until the query
releases them, preventing migration or reclamation during use.
Retrieval keys remain unchanged as representation level and
placement change, keeping retrieval independent of runtime
representation management.
C. Online Representation Scheduling
After the processing configuration is fixed, StreamAhead
schedules representation transitions to keep pace with the
incoming video while using available capacity for additional
precomputation. For the selected configuration, transitions
needed to reach the required representation level constitute
required video processing, while transitions beyond this level
are additional precomputation. The scheduler uses offline
execution profiles and the shared segment table to select
transitions and assign execution priorities. Required video
processing takes precedence over additional precomputation,
limiting interference with the processing of newly arriving seg-
ments. StreamAhead operates in three runtime states: Normal,
Query-Priority, and Recovery.
1) Normal: Newly arriving segments are prioritized to keep
pace with the incoming video and prevent processing lag from
accumulating. When the required work is caught up, available
execution capacity is used to advance segments toward deeper
representations. The scheduler selects transitions according
to their committed and in-flight states, avoiding duplicate
computation.
2) Query-Priority: When a query arrives, computation re-
quired to complete the retrieved segments and generate the
answer becomes latency-critical and runs first. Newly arriving
video continues to be processed, while additional precompu-
tation receives lower priority. Already executing transitions
are not explicitly aborted or restarted, and compatible in-
flight computation remains reusable. Query execution may
temporarily reduce the resources available for incoming video
processing.
3) Recovery: If required video processing accumulates dur-
ing query execution, StreamAhead enters Recovery to clear


this backlog. Rather than simply resuming normal execution,
the scheduler uses the current backlog and offline profiles
to select an efficient batch size. When multiple compatible
transitions are already ready, it may select batched execution
to improve backlog processing throughput under the avail-
able resource constraints. No additional waiting is introduced
solely to form a batch. Once the required backlog is cleared,
StreamAhead returns to Normal execution and resumes addi-
tional precomputation.
D. Heterogeneous Pipelined Execution
StreamAhead executes scheduled representation transitions
through a heterogeneous CPU–GPU pipeline. The scheduler
selects the work and its execution priority, while the pipeline
provides concurrent execution across segments and processing
stages. Execution progress is recorded in the shared segment
table and made available for subsequent scheduling decisions.
1) Cross-segment pipelining: Segment independence al-
lows different segments to occupy different stages, such as
L1→L2 and L2→L3, concurrently. A segment does not need
to reach the deepest representation level before subsequent
segments begin processing. This enables incoming video pro-
cessing and additional precomputation to overlap while pre-
serving the required computation order within each segment.
2) CPU–GPU overlap: StreamAhead pipelines CPU-side
frame preparation, metadata processing, and data movement
with GPU model execution across segments. Preparation and
data movement for one segment can overlap with GPU com-
putation for another, reducing GPU idle time.
3) Concurrent execution support: The execution pipeline
supports concurrent GPU work at different priorities and
batched execution of compatible representation transitions.
The scheduler assigns priorities and selects batch sizes from
the execution profiles, while the pipeline executes the sched-
uled work and reports completion through the shared segment
table.
E. CPU–GPU Representation Memory Hierarchy
StreamAhead manages representation level and represen-
tation placement independently. For segment si, let ℓi ∈
{L1, L2, L3} and pi ∈{CPU, GPU} denote its committed
representation level and current placement, respectively. The
representation level records completed computation, whereas
placement records where the committed representation is
stored. StreamAhead uses a CPU representation store for
retained representations and a bounded GPU representation
cache for representations needed on the GPU. Migration
changes placement without changing the committed level. For
example, (L3, GPU) →(L3, CPU) preserves the completed
L3 representation, which can later be loaded back to the
GPU without repeating visual encoding or KV construction.
Each segment keeps one committed representation. A tran-
sition or migration may temporarily require both the current
representation and a destination allocation until the operation
completes. Representations pinned by active queries cannot be
migrated or reclaimed until those queries release them. Before
admitting new work, StreamAhead accounts for committed
representations, transition outputs, data movement, and tem-
porary execution workspace. When the GPU representation
cache reaches its capacity, unpinned representations, least
recently used first, can migrate to the CPU representation store
while retaining their committed levels. Query-time position
remapping, representation composition, and answer generation
operate on temporary per-query state and do not modify the
persistent representation stored for a segment.
VI. IMPLEMENTATION
This section presents the implementation of StreamAhead’s
algorithmic components and CPU–GPU runtime.
A. Algorithmic Realization
For each fixed-duration segment, L1 retains the frames
and temporal metadata, L2 stores visual-encoder outputs and
the inputs to the language model, and L3 stores query-
independent KV states and position metadata. A SigLIP image
encoder [57] constructs the retrieval key alongside L1. At
query time, the SigLIP text encoder produces a question
embedding, and retrieval combines the newest segment with
semantically ranked historical segments using cosine similar-
ity. For representation composition, StreamAhead retains one
shared textual prefix, orders retrieved segments by video time,
remaps their positions, and applies MRoPE relocation [58]
to cached keys. Concat directly assembles the positioned
KV caches, while TailRepair, our lightweight mechanism,
recomputes each segment’s short text suffix in the composed
context. Both operate on temporary per-query state without
modifying persistent representations.
B. Shared Segment State
Each retained segment has a CPU-resident record in the
shared segment table containing its temporal metadata, re-
trieval key, committed representation level, placement, storage
handle, in-flight transition, and active-use state. Transitions
follow a begin–compute–commit sequence: computation and
data movement occur outside the table update, and the new
representation becomes visible only after completion. Queries
reuse or wait for compatible in-flight transitions and pin the
representations they use to prevent migration or reclamation
during use.
C. Representation Storage and Query Access
StreamAhead uses a bounded GPU representation cache for
recently used L3 representations and a larger CPU represen-
tation store for L1 data, persistent L2 representations, and
evicted L3 representations. Migration preserves the committed
representation level. Before a transition or migration, the
runtime reserves memory for the required allocations and
execution workspace, and previous storage is reclaimed only
after the new representation is committed and no query still
uses it. At query time, GPU-resident L3 is reused directly,
CPU-resident L3 is transferred to the GPU, and shallower
representations are completed to L3 as needed. Temporary


per-query state is released after generation, and the associated
representations are unpinned.
D. Concurrent Execution Runtime
StreamAhead uses asynchronous CPU workers and CUDA
streams to implement cross-segment pipelining and CPU–GPU
overlap. GPU work is assigned according to its runtime role
rather than a fixed representation level: required video process-
ing and query-critical work use the higher-priority execution
path, while additional precomputation uses the lower-priority
path. CUDA stream priority provides preferential scheduling
at kernel boundaries without explicitly preempting in-flight
representation transitions. During Recovery, compatible ready
transitions may use profiled batched execution when benefi-
cial, without waiting for future segments to form a batch. The
offline profiler measures costs using the same execution paths
to support configuration selection and recovery.
VII. EVALUATION
A. Experimental Setup
Benchmarks and models. We evaluate answer quality and
algorithmic sensitivity on OVO-Bench (Perception and Back-
ward) and StreamingBench (Real-Time). Videos are tempo-
rally sampled at the evaluated video-processing rate, with
source frames repeated when the requested rate exceeds the
source frame rate. We evaluate Qwen2.5-VL-7B and Qwen3-
VL-8B, comparing answer quality with published results. For
system comparisons, we select three representative stream-
ing video QA methods: ReKV for KV-cache retrieval and
reuse, StreamingVLM for incremental streaming inference
with temporally dependent KV states, and OASIS for algo-
rithmic optimization through hierarchical video memory and
retrieval. These methods represent complementary approaches
to streaming video processing and query serving.
System configuration. Unless specified otherwise, system
experiments use Qwen3-VL-8B with BF16, FlashAttention-
2, and 448-pixel visual inputs. Each segment maintains a
separate retrieval key, and the default retrieval policy selects
the latest segment plus two semantically ranked historical
segments. Offline profiling selects the required representation
level for each rate. In the rate sweep, the required level is L3
below 30 FPS, L2 from 30 to 80 FPS, and L1 above 80 FPS.
Beyond the required level, the runtime performs additional
L3 precomputation when capacity allows. The online replay
comparison uses L2 as the required level. We use a 16-GiB
GPU representation cache.
Hardware and scope. Experiments run on a server with two
AMD EPYC 9654 CPUs, 1.5 TiB of host memory, and four
NVIDIA RTX 6000 Ada GPUs (48 GiB each). All experiments
use just one GPU.

C. Video Processing Rate vs. Query Latency
We evaluate the rate–latency trade-off through mean TTFT
across video-processing rates and the highest rate satisfying
each P95 TTFT target. For StreamAhead’s rate and TTFT-
target sweeps, each replay processes 20 s of video as 40
segments of 0.5 s. One query is issued at the end of the trace,
and video input stops when the query arrives. Section VII-D
evaluates queries while video continues to arrive. Figure 4(a)
shows three operating regions selected by offline profiling.
Below 30 FPS, L3 is required, so incoming segments complete
their KV representations before queries arrive, enabling low
TTFT through direct reuse. From 30 to 80 FPS, L2 is required
to maintain the video-processing rate, while additional L3
precomputation uses available capacity. As the input rate
increases, fewer segments can reach L3 before query arrival,
increasing the remaining query-time computation and TTFT.
Above 80 FPS, L1 becomes the required level, further re-
ducing mandatory processing per segment while deferring
visual encoding and KV construction until needed. This allows
StreamAhead to process up to 100 FPS, although query latency
increases under the higher workload. Figure 4(b) quantifies
this trade-off under P95 TTFT targets: StreamAhead supports
28, 30, 38, 57, and 90 FPS under targets of 0.2, 0.5, 1, 2,
and 5 s, respectively, with P95 processing lag within 1 s. At
100 FPS, P95 TTFT exceeds the 5-s target, highlighting the
need to consider processing rate and query latency jointly.

D. Online Representation Scheduling
We evaluate how StreamAhead accumulates and clears
temporary processing lag under continuous video arrival. We
use 0.5-s segments at 30 and 40 FPS, containing 15 and 20
frames, respectively, with L2 as the required representation
level. Generation budgets of 1, 16, 60, and 128 tokens produce
different Query-Priority durations, while video continues to
arrive throughout query execution and recovery. During Query-
Priority, StreamAhead continues L1 construction for incoming
segments while prioritizing query-critical work on shared
resources, so required L2 processing can temporarily fall
behind. After query execution, Recovery prioritizes pending
L2 work and pipelines it with the processing of newly arriving
segments. Once the required backlog is cleared, the runtime
returns to Normal and resumes additional L3 precomputation.
Figure 5 reports StreamAhead’s peak processing lag and
recovery time as functions of Query-Priority duration. At both
input rates, longer Query-Priority durations lead to higher peak
lag and longer recovery in the measured runs. StreamAhead
then catches up with the incoming video while new segments
continue to arrive. These results characterize the temporary
lag and subsequent catch-up behavior of online representation
scheduling under continuous input.

VIII. CONCLUSION
This paper presented StreamAhead, an algorithm–system
co-design for real-time streaming video QA. StreamAhead
processes video segments independently at three representation
levels and decides at runtime how much computation to
complete for each segment before a query arrives. Its profile-
guided scheduler and concurrent CPU–GPU runtime keep pace
with the incoming video while completing KV caches only
for retrieved segments. StreamAhead maintains competitive
accuracy with up to 10.4× lower TTFT than state-of-the-
art methods, and sustains 57 FPS with P95 TTFT under 2 s,
setting a new Pareto frontier between video-processing rate
and TTFT. These results show that how much computation to
complete before a query arrives should be a runtime decision.
StreamAhead has limitations. Because segments are encoded
independently, they do not attend to one another, and suffix
recomputation adds only limited cross-segment interaction.


Our system evaluation uses a single GPU, and rates above the
source frame rate repeat source frames. Offline profiles also
assume a stable workload; extending StreamAhead to multiple
GPUs and changing workloads is future work.
