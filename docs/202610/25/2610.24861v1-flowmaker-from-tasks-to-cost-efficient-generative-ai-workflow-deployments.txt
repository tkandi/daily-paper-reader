# ABSTRACT 

Generative AI workflows execute user tasks by composing sequences of LLM calls, where each call performs a sub-task (e.g., summarization or translation), forming a workflow. Executing such workflows requires decisions over work-flow structure, model assignments, and deployment configurations, which jointly determine latency, cost, and accuracy under dynamic workloads and resource con-straints. Existing systems optimize these decisions in isolation or fix them early, leading to suboptimal cost and goodput. We make two key observations. First, ef-ficient serving requires jointly exploring all combinations of workflows, model choices, and deployment configurations under dynamic cluster state. Second, reuse of deployed LLMs is critical for reducing cost, but must be performed on-the-fly, as reuse depends on current load and resource availability. Together, these make selecting a workflow-variant—a combination of workflow, models, and de-ployment configuration—a time-critical problem. We present FlowMaker, which exposes a task-level interface and selects workflow-variants on behalf of users. To realize this, we design a constraint-guided load-aware pruning algorithm for fast, on-the-fly decisions. FlowMaker improves goodput by up to 10.14 × and reduces cost by up to 2.77 × compared to state-of-the-art baselines, including Murakkab.

However, existing workflow frameworks typically fix these decisions statically (Chase, 2022; LangChain, 2025; CrewAI, 2024; Wu et al., 2024; Hong et al., 2024), while managed platforms leave them to manual tuning (Amazon Web Services, 2025; Google Cloud, 2025; Microsoft Azure, 2025). Across our experiments, such fixed choices incur up to 4.00 × the serving cost ( 2.93 × on average) and achieve up to 12 .84 × lower goodput than a system that jointly adapts these decisions (§ 5.1). In this paper, we study how to serve generative AI tasks under dynamic workloads and resource constraints. Our goal is to increase goodput, the rate of requests completed while satisfying their Service-Level Objectives (SLOs), while reducing serving cost. Existing systems optimize only sub-sets of the decisions that determine a workflow-variant (Chase, 2022; LangChain, 2025; CrewAI, 2024; Wu et al., 2024; Google Cloud, 2025; Microsoft Azure, 2025; Zhang et al., 2025; Chen et al., 2025; Ong et al., 2025; Liakopoulos et al., 2025; Agrawal et al., 2024; Li et al., 2023). AFlow (Zhang et al., 2025) focuses on task decomposition; LLMSelector (Chen et al., 2025) and RouteLLM (Ong et al., 2025) focus on model selection; and MaverIQ (Liakopoulos et al., 2025), Vidur (Agrawal et al., 2024), and AlpaServe (Li et al., 2023) support deployment selection. Murakkab (Chaudhry et al., 2026), the closest prior system, jointly considers model and deployment choices but fixes the user-provided workflow. Although effective within their respective dimensions, these approaches do not jointly revisit workflows, model assignments, and deployment configurations as workload and cluster conditions change. Consequently, they fail to capture opportunities that arise only when these decisions are made jointly: particularly reuse of LLMs across tasks and adaptation to the cur-rent cluster state (e.g., already deployed models, load, and resource availability). We find that this leads to suboptimal performance and resource utilization (§ 2.1–2.2). For example, when serving seven tasks, we observed that an oracle that searches across all three dimensions reduces serving cost by 1.85 × and increases goodput by 1.69 × relative to Murakkab (§ 2.1). We argue that serving systems need to make these decisions on behalf of users, rather than relying on statically fixed choices or requiring manual configuration. We propose a task-level interface :users specify only the task along with accuracy and performance SLOs, and the system selects a 

workflow-variant —a combination of workflow, model choices, and deployment configurations. To support this interface, the serving system needs to explore the full design space of workflow-variants and select one per task to improve serving cost and goodput. Joint selection is especially important as different tasks can reuse the same deployed LLM. When a suitable model is already deployed and lightly loaded, reusing it can avoid the cost of an additional deployment. The same decision may violate latency SLOs when that model is heavily utilized. Because deployed models, their load, and available resources change as tasks arrive, reuse decisions cannot be fixed offline. Instead, the serving system must select a workflow-variant and make on-the-fly reuse decisions to determine which deployed models can be reused based on the current cluster state. This turns workflow-variant selection into an online constrained-search problem. However, existing off-the-shelf algorithms are not well-suited for this setting. For the task in Fig-ure 1, exhaustively evaluating the variants induced by three workflows, 11 models, and 10 deploy-ment configurations per model consumes approximately 40 CPU-minutes. On a single CPU, this is approximately 4.7× the task’s most relaxed latency SLO of ∼ 510 s. Recent profilers (Liakopoulos et al., 2025; Agrawal et al., 2024; Hsia et al., 2025; Lee et al., 2025) reduce the cost of profiling individual LLM configurations, but do not eliminate the cost of evaluating workflows composed of multiple models. General-purpose methods such as Bayesian optimization (Moˇ ckus, 1975; Garnett, 2023; Zhou et al., 2022; Acun et al., 2026) and evolutionary search (Eiben & Smith, 2015; Walter et al., 2022) also rely on repeated candidate evaluations. In our setting, this evaluation cost must be paid whenever changing load or reuse opportunities alter the feasible choices. Thus, meeting the online decision budget requires exploiting the structure of this problem to eliminate candidates before evaluating complete workflow-variants. To this end, we build FlowMaker , an inference serving system for generative AI workflows that meets user SLOs while minimizing serving cost. FlowMaker exposes the task-level interface: users specify only the task along with any latency and accuracy SLOs. FlowMaker generates can-didate workflows for each task and lets users select the suitable ones. Involving users in selecting among the generated candidate workflows is intentional for two reasons: (1) task decomposition is often ambiguous and can yield multiple valid interpretations (Huang et al., 2025), and (2) current LLMs are unreliable as autonomous planners (Valmeekam et al., 2023; 2025; Kambhampati et al., 2024). FlowMaker then selects a workflow-variant for each task by jointly reasoning over work-2Preprint. To make this search fast, we design a novel load-aware pruning algorithm that progressively narrows the candidate space using accuracy feasibility, operational cost, and performance under the current load. It then selects a low-cost workflow-variant estimated to satisfy the user’s latency and accuracy SLOs, when one exists, while considering opportunities to reuse already deployed models. We make the following contributions: • We formulate serving generative AI workflows as a joint selection problem over workflows, model assignments, and deployment configurations. We show that considering all three dimensions and making reuse decisions from the current cluster state materially improve goodput and serving cost. • We design a load-aware workflow-variant selection algorithm that searches across this joint space without exhaustively evaluating variants. In our evaluation, it reduces search time by 3.7× relative to Aquatope’s (Zhou et al., 2022) Bayesian optimization while accounting for reuse across tasks. • We implement FlowMaker atop TensorRT-LLM. # 2 PROBLEM SETTING AND MOTIVATION 

We first define the decisions involved in deploying a generative AI task. We then show why effective serving requires (1) jointly selecting workflows, models, and deployment configurations and (2) deciding whether to reuse deployed LLM instances based on the current cluster state. 

Task, request, and workflow. A task is a high-level user objective accomplished through one or more stages, including LLM calls. A request is an invocation of a deployed task with a concrete input. A workflow is an executable decomposition of a task into stages, their dependencies, and execution order. A stage may be a non-LLM operation (e.g., PDF-to-text conversion) or an LLM call (e.g., summarize or translate). Figure 1(a) shows the stages and relationships for our example task; Figure 1(b) shows three candidate workflows with different decompositions or execution orders. 

Workflow variant. A workflow can be realized using different models and deployment configura-tions. A workflow-variant specifies a workflow and, for each LLM stage, the model used to execute it (e.g., Llama-3.1-8B or Qwen-2.5-7B) and the model’s deployment configuration (e.g., its tensor-and pipeline-parallelism degrees). Variants of the same workflow can therefore differ in accuracy, la-tency, memory consumption, and serving cost. For the example in Figure 1, evaluating 3 workflows, 11 models, and 10 deployment configurations generates ∼ 24 K variants across which latency varies by 189 .3× (0.6–119 s), cost by 8725 × (2 × 10 −5–0.17 ¢), and accuracy by 3.3× (14 .4–48 .0% ). 

Deployment and reuse. A selected workflow-variant must be mapped to model deployments. For each LLM stage, the system can deploy a new model instance or reuse a compatible one already deployed for another task. We define reuse as sharing a deployed LLM instance across stages of different tasks. Reuse can reduce serving cost, but adds load to the shared instance and can increase request latency. Thus, reuse is a cluster-state-dependent decision for realizing a workflow-variant. 

Problem formulation. Given a task, its user-approved candidate workflows, latency and accu-racy SLOs, and the current cluster state, the serving system must make two decisions: (1) select a workflow-variant, and (2) realize that variant by mapping each LLM stage to either a new or a compatible existing model instance. This decision is made when the task is deployed; subsequent requests use the selected deployment. The system seeks a low-cost selection predicted to satisfy both SLOs. We measure its cluster-level effectiveness using goodput : the rate of requests that complete within their latency SLO while using a workflow-variant that satisfies the task’s accuracy SLO. 2.1 WHY SELECT WORKFLOWS , M ODELS , AND DEPLOYMENT CONFIGURATIONS JOINTLY ?

Interacting decision dimensions. A task may admit multiple user-approved workflows; each LLM stage may use one of several compatible models; and each model can run under multiple tensor- and pipeline-parallelism configurations. These choices cannot be made independently: the workflow determines the stages and dependencies, model assignments determine attainable proxy accuracy and resource requirements, and deployment configurations determine latency, capacity, and cost. In Figure 1, W1 and W2 each contain two LLM stages, whereas W3 performs summarization and translation through one joint LLM stage; PDF conversion is a fixed non-LLM stage. With 11 models and 10 deployment configurations per LLM stage, this yields 2(11 · 10) 2 + (11 · 10) = 24 ,310 work-flow variants. Requirement 2. The serving system should therefore make reuse decisions based on the current load and capacity of deployed model instances. Together, efficient joint selection and load-aware reuse motivate FlowMaker ’s design in the following section.

FlowMaker ’s life-cycle consists of three steps. 

Model registration and profiling. When amodel is registered through register model ,

FlowMaker stores its weights and profiles its sup-ported tensor- and pipeline-parallelism configura-tions. The Profiler builds on MaverIQ (Liakopoulos et al., 2025) to estimate the latency and memory requirements of each configuration. These profiles are stored and reused across tasks. 

Task deployment. When deploy task is invoked, the Workflow Generator uses an LLM to decompose the task into candidate workflows and refines them through user interaction (§ 3.1). It caches the user-approved workflows and passes them to the Workflow-Variant Selector. The Selector combines these workflows with model profiles, user SLOs, and the current cluster state, including deployed models, their load, and available GPU memory, to select a workflow-variant and reuse plan. The Deployer then launches only the model instances that cannot be served through reuse. 

Request execution. After deployment, the Orchestrator executes incoming requests using the se-lected workflow, models, configurations, and reuse mappings. Intermediate outputs are passed ac-cording to the workflow dependencies, and the final result is returned to the user. Workflow-variant selection is therefore performed when the task is deployed, rather than for every request. 3.2 WORKFLOW -V ARIANT SELECTION PROBLEM 

Inputs. The selector receives a task T , its accuracy SLO α, latency SLO λ, and expected request arrival rate ρ, estimated from historical request traces (Li et al., 2023; Chaudhry et al., 2026). It also receives the task’s user-approved candidate workflows W, supported models M, and deployment configurations C. Finally, it observes the current cluster state, including the set of deployed model instances D = {n1, . . . , n d}, their configurations and serving loads, and available GPU memory.

If a selected node ni is in D, the stage reuses that model instance; otherwise, FlowMaker deploys a new instance.

Estimating workflow accuracy. To our knowledge, no general method estimates the end-to-end accuracy of an arbitrary generative AI workflow from per-model accuracies before execution. Fol-lowing prior work (Liakopoulos et al., 2025), we use the average score across six Open LLM Leader-board benchmarks (Fourrier et al., 2024) as each model’s accuracy estimate. Motivated by evidence that per-stage and end-to-end accuracy are correlated (Chen et al., 2025; Dai et al., 2025), we ap-proximate workflow accuracy as the minimum accuracy across its stages. More advanced task- or workflow-specific estimators can be incorporated without changing the remainder of the selector. 3.3 CONSTRAINT -G UIDED WORKFLOW -V ARIANT SELECTION 

Directly enumerating all workflow-variants is too expensive at task-deployment time. As shown in § 2.1, even our translation–summarization example contains 24,310 variants and requires ap-proximately 40 CPU-minutes to evaluate with MaverIQ (Liakopoulos et al., 2025). Precomputed lookup tables also cannot directly capture changing reuse opportunities and model loads. Evolution-ary search and Bayesian optimization, often used to manage resources for CPU-based workflows deployed on serverless platforms (Zhou et al., 2022; Bilal et al., 2023), avoid complete enumera-tion of the search space. However, for generative AI inference serving, they still require repeated evaluations of complete candidate configurations and introduce additional modeling or tuning over-head (Moˇ ckus, 1975; Garnett, 2023; Eiben & Smith, 2015). We further discuss these alternatives, along with graph-based formulations, in Appendix D and why generative AI workflows differ from traditional serverless workflows in Appendix B. 

FlowMaker instead exploits when different constraints become evaluable. Accuracy can be checked after choosing models; incremental deployment footprint can be evaluated after construct-ing a model assignment and accounting for reuse; and latency, capacity, and memory feasibility can be evaluated after selecting deployment configurations and placement. FlowMaker orders its search according to this dependency structure, applying inexpensive constraints before expanding the next decision dimension. Algorithm 1 implements this strategy in three stages. It prioritizes finding a low-cost feasible workflow-variant quickly over slow yet globally optimal selection. 

Stage 1: Pruning by accuracy. For each workflow stage, FlowMaker retains only models that support the required skill and satisfy the accuracy SLO. Under our minimum-stage accuracy esti-mator, any assignment containing a model below α is infeasible. If no model can serve a stage, 

FlowMaker skips the workflow. Because this check is independent of deployment configuration, it eliminates model–configuration combinations before constructing them. 6Preprint. Under review. 

Stage 2: Pruning by operational cost. After accuracy pruning, FlowMaker constructs candidate model assignments. Evaluating every deployment configuration at this point would remain expen-sive, so it uses model size as a proxy for deployment cost: model memory and latency generally increase with parameter count (Liakopoulos et al., 2025). The parameter budget β is the aggregate size of the smallest accuracy-feasible model for each stage, assuming no reuse. For an assign-ment m, C OMPUTE ACTIVE SIZE counts the parameters of the distinct models that must be newly deployed after accounting for existing deployments and reuse within the workflow. FlowMaker 

retains assignments whose active size does not exceed β and considers them in ascending active-size order. This heuristic favors assignments that exploit reuse or require a small incremental deployment footprint, but does not guarantee that every potentially lower-cost assignment is retained. 

Stage 3: Pruning by system constraints. For each retained model assignment, in ascending active-size order, FlowMaker enumerates its valid tensor- and pipeline-parallelism configurations. It discards configurations that violate the end-to-end latency SLO or would cause a model instance to exceed its serving capacity. It then invokes L EAST LOADED , which attempts to map the required model shards to GPUs with sufficient free memory while preferring less-loaded GPUs. 

FlowMaker keeps each assignment’s lowest-cost feasible configuration. It compares the first fea-sible assignment with the current best selection and proceeds to the next workflow. Thus, it selects the smallest-footprint feasible assignment per workflow and returns the lowest-cost selection across workflows.

# 4 IMPLEMENTATION AND EXPERIMENTAL SETUP 

Prototype and testbed. We implement FlowMaker in ∼3K lines of Python atop TensorRT-LLM (NVIDIA Corporation, 2024), with a centralized CPU controller and per-worker daemons reporting model load and free GPU memory; the Profiler uses MaverIQ (Liakopoulos et al., 2025). Experiments run on 8×NVIDIA RTX A6000 GPUs (48GB each) with a 64-core AMD EPYC 7763 CPU, and all systems execute inference through the same backend (see Appendix F for details). 

Workloads and models. We evaluate seven generative-AI tasks (Data and Beyond, 2025; Khurana et al., 2023; AIMonk Team, 2026), each with three candidate workflows of 1–3 stages, using inputs from six public datasets (See et al., 2017; Hermann et al., 2015; Chen et al., 2021a; Zhang et al., 2015; Chen et al., 2021b; Fan et al., 2018) and a catalog of 11 open-weight LLMs (1B–72B) from the Llama, Qwen, and Mistral families (Grattafiori et al., 2024; Qwen et al., 2025; Jiang et al., 2023). Following prior LLM-serving evaluations (Liakopoulos et al., 2025; Zhong et al., 2024; Li et al., 2023), we replay a bursty code and a sustained conversation Azure trace (Patel et al., 2024) at four offered-load levels (25–100%), preserving each trace’s arrival structure and yielding 212–484 requests per run. Appendix G provides more information regarding the experimental details. 

Comparison methods. The baselines differ in which decisions they fix. LangChain (Chase, 2022) fixes all three, receiving a default workflow, the smallest proxy-accuracy-feasible models, and TP = 1 , PP = 1 . RouteLLM (Ong et al., 2025) frees model choice within a fixed workflow, routing each request between Qwen-2.5-14B and Qwen-2.5-7B at thresholds favoring maximum quality, minimum cost, or balance the two; we provision enough replicas to avoid queuing, inten-tionally favoring its latency, and count all replicas in its cost. Murakkab (Chaudhry et al., 2026) also frees deployment configurations but fixes the workflow and decides reuse offline; as its im-plementation is unavailable, we reconstruct its optimizer and run its selections on our backend, so our comparison concerns this configuration rather than its broader feature set. We also evalu-ate FlowMakerNoReuse , which applies FlowMaker ’s selector without reuse, and compare the selector against brute force and Aquatope-style Bayesian optimization (Zhou et al., 2022) (see Ap-pendix G for more details). 

SLOs and metrics. To set latency SLOs, for each task we measure its latency in isolation and set STRICT –R ELAXED latency SLOs as 2–5× this value, following prior work (Zhong et al., 2024; Ahmad et al., 2024; Liakopoulos et al., 2025; Li et al., 2023). To set accuracy SLOs, we define a model’s proxy accuracy as its average score across six Open LLM Leaderboard benchmarks (Four-rier et al., 2024), and a variant’s score as the minimum across its models. Following Murakkab, BEST , G OOD , and B ASIC accuracy SLOs correspond to the p95, p80, and p50 achievable variant scores. We compare FlowMaker with brute-force (BF) and Aquatope-style Bayesian optimization (BO) (Moˇ ckus, 1975; Garnett, 2023; Zhou et al., 2022; Acun et al., 2026). BF enumerates the candidate space and returns the minimum-cost feasible variant under Equation 1. BO uses Optuna’s TPE sampler (Optuna Team, 2024), per-forms 200 sequential trials, and penalizes SLO violations. 

Selection quality. Across the seven tasks and every com-parable point in the model-catalog and workflow-depth scaling experiments, FlowMaker , BF, and BO select the same workflow variant. Thus, FlowMaker has a 100% observed match rate, a 0% observed objective gap rela-tive to BF, and the same feasibility and SLO-satisfaction outcome as both reference methods. This provides empirical evidence that FlowMaker ’s algorithm matches the selections of BF without incurring its substantial overheads. 

Time efficiency. Figure 6 (top) shows that FlowMaker is 3.7–8.5× faster than BO and 4.5–61 ×

faster than BF across the seven tasks. BF takes approximately 6.5s for the simpler tasks (T1–T3) and approximately 40s for the larger candidate spaces of T4–T7. BO requires approximately 5s per task for its 200 sequential trials. In contrast, FlowMaker ’s staged heuristic filters candidates using proxy accuracy and active deployment size before evaluating deployment configurations, selecting a variant in approximately one second. The approximately 40s reported here measures BF enumera-tion over already-computed model profiles. In contrast, the approximately 40 CPU-minutes reported in § 2.1 measure end-to-end exhaustive evaluation of the example task, including computing the la-tency and memory estimates required to evaluate its 24,310 variants. 

Scalability. Workflow depth most strongly affects search time (Figure 6, middle). BF’s and BO’s search time exceeds 15 minutes at ≥ 6 stages (indicated by x in the Figure), while FlowMaker 

stays below two seconds for 3–5 stages, yielding 14 .5–443 × speedups. At 7 stages, however, its search time rises to 210s, reflecting the underlying combinatorial growth. FlowMaker also scales better with model-catalog size (bottom): BF times out at 50 models, BO slows by 12 .2× at 125 mod-els, while FlowMaker ’s early filtering reduces the model–configuration combinations explored. 

# 6 CONCLUSION 

FlowMaker is a serving system that takes a task and its latency and accuracy SLOs and jointly se-lects a workflow variant and state-aware reuse plan across workflows, models, and deployment con-figurations. Its constraint-guided selector matches brute-force and Bayesian-optimization selections while reducing selection time by 4.5–61 × and 3.7–8.5×, respectively. At high load, FlowMaker 

achieves 4.73 × Murakkab’s goodput while reducing serving cost by 1.95 × on average, showing the benefits of joint, state-aware selection for cost-efficient generative AI workflow serving. 9Preprint. Under review.

# B EXTENDED RELATED WORK 

Workflow construction and application-level optimization. Prior work automates different as-pects of generative-AI application design. DSPy (Khattab et al., 2023) compiles declarative LM programs by optimizing prompts and demonstrations. AutoFlow (Li et al., 2024) generates natural-language agent workflows using fine-tuning- and in-context-based optimization, while ADAS (Hu et al., 2025) searches over code-defined agentic systems and AFlow (Zhang et al., 2025) refines code-represented workflows using Monte Carlo tree search and execution feedback. Cognify (He et al., 2025) autotunes an existing workflow through hierarchical search over structural changes, step operators—including model choice—and prompts, using workflow-level measurements of out-put quality, latency, and monetary cost. DAAO (Su et al., 2026) instead adapts workflow depth, reasoning operators, and heterogeneous model assignments to individual queries based on their es-timated difficulty. These systems optimize application logic, prompts, or per-query model use. They do not jointly choose physical deployment configurations, such as tensor- and pipeline-parallelism, or determine whether stages should use new or already deployed model instances based on current load and GPU availability. They are therefore complementary to FlowMaker : their generated or tuned workflows can supply candidate workflows, after which FlowMaker selects a deployable workflow-variant and reuse plan at task-deployment time. 

Model selection and routing. LLMSelector (Chen et al., 2025) assigns models to modules in a fixed compound-AI architecture. RouteLLM (Ong et al., 2025) routes each query between a fixed strong–weak model pair, while MasRouter (Yue et al., 2025) additionally selects collabora-tion modes, agent roles, and models for multi-agent systems. Other LLM routers similarly select among available models to balance output quality and inference cost (Jitkrittum et al., 2026). These approaches determine which model processes an input, but do not jointly select alternative workflow decompositions, physical deployment configurations, and new-versus-reused model instances under current cluster state. They can be combined with FlowMaker to route individual requests among the instances selected when a task is deployed. 

Generative-AI workflow serving. Aragog (Dai et al., 2025) assumes a supplied workflow DAG and a configured pool of model-serving engines. For each request, it identifies accuracy-preserving model assignments and selects among them stage by stage using current engine load. Thus, Aragog adapts model routing during the execution of a fixed workflow but does not select the workflow structure or determine which model configurations and instances should be deployed. Murakkab (Chaudhry et al., 2026) exposes a declarative workflow interface and uses offline work-flow and model profiles with periodic MILP optimization. Its optimizer selects workflow parame-ters, executors, model and hardware configurations, parallelism strategies, and instance assignments under predicted load. Murakkab can multiplex model instances across workflows and periodically reconfigure its deployment as demand and resource availability change. FlowMaker addresses a different decision scope and timescale: when a task is deployed, it selects among user-approved alternative workflows and their induced model and deployment choices, and maps each stage to a new or compatible deployed instance using the observed cluster state. Subsequent requests use this 19 Preprint. Under review. selected deployment. Aragog’s request-time routing and Murakkab’s periodic resource planning are therefore complementary to FlowMaker ’s task-deployment-time workflow-variant and reuse selection. 

Workflow orchestration and agent execution. Application frameworks such as LangChain, Lang-Graph, CrewAI, AutoGen, and MetaGPT provide abstractions for composing LLM calls, tools, agents, state, and control flow (Chase, 2022; LangChain, 2025; CrewAI, 2024; Wu et al., 2024; Hong et al., 2024). Their programming models range from explicitly structured workflows to con-versational multi-agent coordination, but the application structure or agent logic is supplied by the developer. Systems work provides complementary execution-time mechanisms. Parrot exposes dependencies among LLM calls through semantic variables to enable application-aware scheduling and context sharing (Lin et al., 2024a). Nalar uses futures and managed state to support policy-driven scheduling, routing, and resource management for dynamic agent programs (Laju et al., 2026), while AIOS provides services for agent scheduling, context, memory, storage, and tool management (Mei et al., 2025). KVFlow and Helium exploit workflow structure to improve cache management, prefetching, or scheduling (Pan et al., 2025; Wadlom et al., 2026). These systems improve the construction or execution of an application, whereas FlowMaker selects its deployable workflow variant and reuse plan under task-level SLOs and current cluster conditions. 

LLM inference, profiling, and deployment. Inference runtimes such as vLLM, TensorRT-LLM, and DeepSpeed provide complementary mechanisms for efficiently executing a selected model, in-cluding KV-cache management, batching, optimized kernels, and distributed parallelism (Kwon et al., 2023; NVIDIA Corporation, 2024; Aminabadi et al., 2022). Profiling and performance-modeling systems reduce the cost of evaluating deployment choices. MaverIQ estimates latency and memory across parallelism configurations through lightweight profiling (Liakopoulos et al., 2025); Vidur simulates LLM inference and supports cost-effective deployment selection (Agrawal et al., 2024); NeuSight forecasts model latency across model–GPU combinations (Lee et al., 2025); and MAD-Max models distributed mappings and parallelization strategies (Hsia et al., 2025). AlpaServe jointly selects placement and model parallelism for a collection of models under bursty demand (Li et al., 2023). 

FlowMaker builds on these execution and prediction mechanisms but operates at a different opti-mization scope. Rather than optimizing the deployment of a predetermined model or model collec-tion, it selects an end-to-end workflow variant, including workflow structure and accuracy-dependent model choices, and accounts for reuse across tasks. 

Serverless workflow resource management. Serverless workflow systems execute user-specified DAGs of functions under latency and cost objectives. Aquatope (Zhou et al., 2022) and Cy-press (Bhasi et al., 2022) provision workflow stages under performance uncertainty; Orion (Mah-goub et al., 2022) sizes, bundles, and prewarms stages; FaaSFlow (Li et al., 2022) optimizes dis-tributed workflow execution and data movement; and ALAP (Sinha et al., 2026) delays resource-allocation decisions to improve efficiency. These systems generally treat the workflow structure and function implementations as fixed and optimize how their resources are provisioned, placed, or scheduled. Generative-AI workflow serving introduces additional decisions. Different models provide dif-ferent output quality, each model admits multiple parallel configurations, and reusing an instance changes its load and capacity available to other tasks. LLM instances also have large, persistent GPU-memory footprints and may span multiple GPUs. Finally, the serving system must select among alternative user-approved workflows rather than receiving a single fixed DAG. Serverless resource-management mechanisms remain complementary, but their fixed-workflow formulations do not directly solve this joint selection problem. We nevertheless compare against the Bayesian-optimization search strategy used by serverless systems (Zhou et al., 2022; Bilal et al., 2023) in § 5.3. 

Cold starts and model loading. A complementary line of work reduces the time required to initial-ize serverless functions or load model state. Prior systems mitigate cold starts and accelerate restora-tion (Du et al., 2020; Ustiugov et al., 2021; Ao et al., 2022), prewarm instances (Mahgoub et al., 2022; Shahrad et al., 2020), or optimize checkpoint loading and live migration for LLM serving (Fu et al., 2024). FlowMaker addresses the preceding decision: it determines which models and con-20 Preprint. # D DESIGN ALTERNATIVES AND THEIR LIMITATIONS 

Lookup table. A straightforward approach constructs a lookup table per task that records latency, throughput, and memory for all workflow variants, selecting the one that meets the objective. How-ever, populating this table is expensive, even with state-of-the-art profilers, such as MaverIQ (Li-akopoulos et al., 2025), NeuSight (Lee et al., 2025), or Vidur (Agrawal et al., 2024), which only 21 Preprint. Under review. reduce per-model profiling cost. For a simple translate-and-summarize task (3 workflows, 11 mod-els, 10 configurations), this requires evaluating over 24K variants and takes ∼ 40 CPU-minutes with MaverIQ (Liakopoulos et al., 2025). The cost further increases with reuse, as the space expands to include previously deployed models, making this approach impractical in an online setting. 

Traditional search algorithms. More sophisticated approaches avoid exhaustive enumeration. Bayesian optimization (BO) and evolutionary search are widely used (Moˇ ckus, 1975; Garnett, 2023; Zhou et al., 2022; Acun et al., 2026). BO builds a probabilistic surrogate (e.g., Gaussian processes) but incurs modeling overhead and scales poorly to high-dimensional, discrete spaces (Frazier, 2018; Papenmeier et al., 2025; Baptista & Poloczek, 2018). Evolutionary methods avoid explicit model-ing but require many evaluations to converge (Eiben & Smith, 2015). Both require careful tuning of surrogates, acquisition functions, and hyperparameters, and incur high decision latency—tens of seconds to minutes—to identify a suitable variant (§ 5.3). This makes them unsuitable for our setting, where selection lies on the critical path. 

Graph algorithms. Graph-based formulations (e.g., Steiner Forest (Agrawal et al., 1991; Goemans & Williamson, 1992; Gupta & Kumar, 2014)) assume a pre-constructed graph, ignoring the cost of building it. In generative AI workflows, the graph G—capturing all workflow-variants—must be constructed on-the-fly, as subtasks and workflows are not known a priori. Even for a single task T ,without reusing deployed models, constructing G costs O(|W|· (|M|·|C| )|S| ), where W, S, M, and 

C denote workflows, subtasks, models, and configurations. This makes runtime graph construction prohibitive and precludes classical traversal algorithms (BFS (Moore, 1959; Cormen et al., 2022), DFS (Tarjan, 1972; Cormen et al., 2022), Dijkstra (Dijkstra, 2022; Cormen et al., 2022), A* (Hart et al., 1968; Russell & Norvig, 2009)).

Progressive SLO relaxation. While users may specify both latency and accuracy SLOs, satisfy-ing both may be infeasible (e.g., no model is both fast and accurate enough). We therefore relax constraints progressively, preserving user intent as much as possible. We first drop the accuracy constraint and select the highest-accuracy workflow variant that meets the latency SLO. If no vari-ant satisfies the latency SLO, we select the lowest-latency variant; if multiple variants have the same latency, we choose the one with the highest accuracy. If only an accuracy SLO is specified and no variant satisfies it, FlowMaker selects the highest-accuracy variant. If no variant is feasible, 

FlowMaker reports that no deployable workflow exists under the given conditions. 

Time complexity analysis. A brute-force approach enumerates all workflow-variants across all workflows, assigning each subtask a model, deployment configuration, and reuse option. For |W| 

workflows, this requires enumerating the Cartesian product across |S| subtasks, each with |M| 

model choices, |C| configuration options, and |D| reuse candidates. This yields a complexity of 

O  |W| · (|M| · |C| · |D| )|S| , which is exponential in |S| .22 Preprint. Under review. 

FlowMaker makes this tractable by shrinking the base of the exponent through pruning: (i) prun-ing by accuracy reduces |M| → |M ′|, (ii) pruning by operational cost reduces |D| → |D ′|, and (iii) pruning by latency, capacity, and memory constraints reduces |C| → |C ′|. We also exit early, avoiding full enumeration of the remaining search space after pruning. Hence, the effective com-plexity becomes O  |W| · (|M ′| · |C ′| · |D ′|)|S| , where |M ′| ≪ |M| , |C ′| ≪ |C| , and |D ′| ≪ |D| .This significantly reduces the base of the exponent. In § 5.3, we empirically demonstrate the time-efficiency of our algorithm.

Prototype architecture. We implement FlowMaker in approximately 3K lines of Python atop TensorRT-LLM (NVIDIA Corporation, 2024). FlowMaker consists of a logically centralized Con-troller and a set of GPU workers. The Controller hosts the Workflow Generator, Workflow-Variant Selector, Profiler, Deployer, and Request Orchestrator. Each worker runs a lightweight Monitoring Daemon, and the components communicate through TCP sockets. 

Profiling and metadata. When a model is registered, the Profiler uses MaverIQ’s fingerprint-based profiling (Liakopoulos et al., 2025) to estimate its latency and memory consumption across sup-ported tensor- and pipeline-parallelism configurations. Profiles are approximately 30KB and are stored as CSV files, while model weights are stored in the Model Repository. Profiles are computed once and reused across task deployments. 

Workflow generation and selection. The Workflow Generator runs as a CPU process. It first queries the Workflow Database, an on-disk JSON catalog of previously approved decompositions. On a cache miss, it prompts OpenAI’s gpt-oss-120b (OpenAI, 2025) using chain-of-thought prompting (Wei et al., 2022) to generate candidate workflows, which are presented to the user for approval. Approved workflows are added to the database. The Workflow-Variant Selector also runs as a CPU process. It maintains an in-memory view of deployed model instances, their load, and available GPU memory. At task deployment, it com-bines this state with stored model profiles, user-approved workflows, and the task’s SLOs to execute Algorithm 1. 

Deployment and request execution. For each model instance that cannot be served through reuse, the Deployer launches a TensorRT-LLM process on the selected GPUs using the chosen parallelism configuration. Each process is assigned an IP/port endpoint stored in an in-memory routing direc-tory. Additional mappings associate tasks with workflow stages and stages with model processes. The Request Orchestrator serves requests in first-come-first-served order. It looks up the endpoint for the first stage, attaches 100–1000 bytes of routing metadata, and forwards the request. This metadata identifies subsequent stages and their endpoints, allowing intermediate outputs to flow directly between model processes over TCP and keeping the Controller off the inter-stage data path. 23 Preprint. Under review. 

Cluster monitoring. Each Monitoring Daemon contains two CPU components. The Memory Mon-itor samples per-GPU memory availability using NVML (NVIDIA Corporation, 2025). The Load Monitor computes each deployed model’s load over a two-minute sliding window. Both update the Controller’s global in-memory state every five seconds. The selector uses the latest snapshot when evaluating reuse and placement.

Tasks. We evaluate seven representative generative-AI tasks (Data and Beyond, 2025; Khurana et al., 2023; AIMonk Team, 2026). Each task has three candidate workflows containing one to three stages. The tasks span six categories: (1) cross-lingual understanding, which translates and summa-rizes text across languages; (2) text processing, which summarizes and simplifies text; (3) analysis and reporting, which extracts key phrases and sentiment to synthesize a report; (4) code documen-tation; (5) opinion mining over product reviews; and (6) document classification and tagging. 

Model catalog. Our catalog contains 11 open-weight models from three families: Llama-3.2-1B, 3B and Llama-3.1-8B, 70B (Grattafiori et al., 2024); Qwen2.5-3B, 7B, 14B, 32B, 72B (Qwen et al., 2025); and Mistral-7B, 12B (Jiang et al., 2023). We treat Llama-3.1-70B and Qwen2.5-72B as fallback models and the remaining nine as the primary catalog. We restrict Llama-3.2-1B/3B and Qwen2.5-3B to stages that perform a single operation because these models do not reliably execute compound operations such as joint translation and summarization. We construct each stage’s candidate-model set using a score that combines model quality from the Open LLM Leaderboard (Fourrier et al., 2024), a logarithmic parameter-count penalty favor-ing deployment efficiency, and a model-family diversity bonus. This procedure provides multiple candidate models per stage when possible. 

LangChain. LangChain (Chase, 2022) represents static workflow execution. We port its execution logic to TensorRT-LLM and provide each task’s default workflow, the smallest model satisfying its proxy-accuracy SLO, and TP = 1 , PP = 1 . These choices remain fixed as cluster conditions change. 

RouteLLM. RouteLLM (Ong et al., 2025) performs request-level routing over a fixed workflow. For every task, we pre-deploy Qwen-2.5-14B and Qwen-2.5-7B as its strong/weak pair and use RouteLLM’s pretrained BERT router. A request uses the routed model for every LLM stage in its workflow. We evaluate three routing thresholds selected to favor maximum quality, minimum cost, or a balance between them. We provision sufficient replicas to serve each model’s offered load without queuing; all replicas are included in the reported cost. 

Murakkab. Murakkab (Chaudhry et al., 2026) uses profile-guided optimization to select workflow parameters, models, deployment configurations, and resource allocations. In our evaluated con-figuration, we supply the same default workflow used by the other fixed-workflow configurations and execute Murakkab’s selected models and configurations using TensorRT-LLM. Because its im-plementation is unavailable, we reconstruct the optimizer described in the paper. Our comparison 24 Preprint. FlowMakerNoReuse . FlowMakerNoReuse uses the same workflow-variant selector as 

FlowMaker , including selection across workflows, models, and deployment configurations, but de-ploys separate model instances for each task. Comparing FlowMaker with FlowMakerNoReuse

Brute force and Aquatope-BO. For the selector study, brute-force search enumerates the com-plete candidate space using cached profiles and returns the minimum-cost feasible variant under Equation 1. This is an adaptation of Aquatope’s search strategy rather than an execution of the complete Aquatope system.
