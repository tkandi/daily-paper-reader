## Abstract 

Semantic data analytics systems integrate AI-powered operators into query pipelines, enabling declarative queries over structured and unstructured data. However, existing systems rely on per-tuple model invocations, ad hoc operator designs, and lack principled cost models, resulting in poor scalability and limited optimization. We present NousDB, a high-performance semantic analytics engine built on Apache DataFusion[22].Through NousDB we propose an extended relational algebra with three semantic operators and for-mal algebraic properties that enable principled query rewriting and cross-operator optimization. We further propose a token-based cost model using equi-depth token histograms to optimize batch sizing under context-window constraints and provide statistical guaran-tees for safe batching. Experiments show that NousDB achieves up to ×86 speedups with both local and enterprise LLMs, while leading competitors in token efficiency and accuracy. These gains extend to complex JOB and Stack workloads augmented with semantic operators, supporting both traditional and semantic analytics. 

## 1 Introduction 

Foundation models [2, 33, 45] have showcased strong capabilities in processing unstructured data, such as language and images. This new form of data processing has given rise to semantic query en-gines (SQEs), which treat models as query operators and allow users to filter, join, extract information from, and summarize tex-tual content in combination with conventional relational operations. However, they challenge several fundamental assumptions underly-ing database systems, including operator semantics, cost estimation, and parallel execution, among others. 

Motivating example. Consider the query “which actors are men-tioned in movie reviews?” over the IMDB schema extended with a relation of reviews. Figure 1 shows this query, denoted Q11 in our evaluation, expressed in NousDB. Its natural execution plan first extends each review with the actors mentioned in its text, join the result with the name relation on whether the extracted mention and a person’s name refer to the same actor, and projects the re-view, movie title and actor name. A naive execution invokes the model once per review for extraction and once per review-name pair for matching, with each invocation processing only one tu-ple or tuple pair. Avoiding this costly tuple-at-a-time execution requires the planner to reason about semantic operators, for which existing SQEs provide insufficient foundations. Using this query as a running example, we next identify the following problems.

Problem 1: Semantic operators without semantics. Existing SQEs expose semantic operators to the query planner as opaque model invocations that use task-specific prompts [11, 29, 36]. This limitation hinders query optimization in SQEs because it prevents the definition of algebraic properties to reason about result-preserving rewrites. In our example, treating semantic operators as black boxes prevents the planner from determining whether it can safely push a selective filter on name below the semantic join, fuse mention extraction and matching into a single model invocation, or partition the work across threads. Missing such rewrites can incur substan-tial model work, often linear in the input cardinality and far costlier per invocation than conventional tuple comparisons. 

Challenge 1: Defining semantics that enable sound plan transfor-mations . A semantic operator is jointly determined by its model and prompt, may behave stochastically, and may be undefined for some inputs. Classical relational-algebra properties therefore can-not be assumed. The challenge is to define semantics that make these behaviors explicit and identify which properties, and thus which plan transformations, are valid under which assumptions. 

Problem 2: Finite context windows. Singleton calls underutilize the context window. In our running example, invoking the model separately for every review and review–name pair repeatedly pays the fixed cost of the prompt while leaving most of the context window unused. Batching multiple tuples into each invocation amortizes this cost and reduces the number of model calls, but risks exceeding the model’s capacity. Thus, batching must respect a hard token budget determined by the prompt and the model’s context window, and becomes a critical optimization decision. 

Challenge 2: Token-distribution estimation. Enforcing this budget requires estimating the token footprint of the input tuples with-out tokenizing the entire input in advance. The engine therefore needs compact per-column token statistics that can be collected and maintained at negligible time and space overhead. 

Challenge 3: Probabilistic batch sizing. Given these statistics and the available token budget, the engine must select the largest batch that fits with high probability. The sizing algorithm must balance invocation efficiency against the risk of truncation or rejection, particularly under skewed token-length distributions. arXiv:2610.28551v2 [cs.DB] 21 Oct 2026 Christos Tsapelas, Georgia Koutrika, and Yannis Ioannidis 

Problem 3: Over-batching can degrade result quality. Although a batch may fit within the model’s context window, batching can change the output produced for each tuple relative to singleton execution due to leakage from neighboring tuples, tuple position in the batch, or formatting errors that misalign inputs and outputs. In our experiments, batching without checking output fidelity reduces F1 by up to 0.42 for a selection query with Qwen3-8B. The engine must therefore determine the largest batch size that preserves fi-delity, meaning agreement with singleton execution, rather than merely the largest batch that fits within the context window. 

Challenge 4: Safe batch sizes cannot be predicted a priori. The batch size at which output quality degrades depends on the model, prompt, and data. At query time, fidelity must be assessed without ground truth or independence assumptions and at a cost substantially lower than the execution being validated. 

Problem 3: Token-skew in row-balanced partitions. Classical engines distribute rows evenly across workers, assuming similar per-row costs. In SQEs, cost depends on token volume, so row-balanced partitions may have highly unequal loads. In our example, a partition containing longer reviews carries several times the token load of its peers, becoming a straggler while other workers sit idle. We call this imbalance token skew . Existing SQEs inherit row-based partitioning from their host engines and do not account for it. 

Challenge 5: Token-aware partitioning. The challenge is to detect token skew and partition tuples by expected processing cost rather than count, while keeping repartitioning overhead below the gains from improved load balance. 

NousDB Contributions. NousDB addresses all four problems. It defines semantic operators declaratively as relation-to-relation functions parameterized by a model and a prompt. These definitions provide engine-independent reference semantics for evaluating im-plementations and reasoning about plan equivalence. We define these semantics at the tuple level, separating what an operator computes from how its inputs are grouped into model invocations. Singleton execution, in which each tuple is evaluated independently, serves as the reference semantics. Batching is therefore a physical execution choice whose fidelity can be evaluated against this ref-erence, rather than an implicit change to the operator’s meaning. NousDB is built as an extension of Apache DataFusion [22] over Apache Arrow’s [3] columnar format (Figure 2). Its semantic op-erators are first-class DataFusion operators, enabling vectorized, columnar, and partition-parallel execution. In a nutshell, NousDB makes the following contributions: 

• An algebra for semantic operators. We define three tuple-level semantic operators (Extend, Selection, Join) under an ex-plicit oracle assumption, which allows us to derive a set of algebraic properties, along with four rewrite rules, two push-downs and two fusions, that NousDB’s optimizer applies. 

• Token-aware batch sizing. We introduce equi-depth token histograms as the catalog statistic of token-priced operators, an iterative algorithm that maximizes 𝑘 subject to an overflow probability 𝛼 , and batched streaming operators that keep a window of packed requests in flight. 

• A fidelity certificate. We define batch fidelity as the probability that a tuple has the same output in a batch as in a singleton

## 2 Related Work 

SQEs expose LLM-powered operators next to relational ones [1, 4, 10, 11, 14, 17, 20, 25, 27, 29, 36, 42, 44, 47–50, 54, 56]. ThalamusDB [17, 18] answers SQL queries with NL predicates over multi-modal data, WannaDB [14, 15] and ELEET [46, 47] extract structure from text, and ZenDB [27] and DocETL [42] target document analyt-ics. Palimpzest [29], optimized by Abacus [40], and LOTUS [5, 36] offer declarative semantic operators, UQE [9] and BlendSQL [11] embed them in SQL, and GALOIS [41] and XMODE [32] query or orchestrate the LLM itself. Benchmarks remain few [5, 34, 55]; the broadest, SemBench [23], shows that operators sharing a name across systems, such as sem_filter and sem_join , do not share se-mantics. In all of them a semantic operator is an opaque model call. NousDB instead defines semantic operators that compose with the relational ones, establishes the algebraic properties that rewrit-ing requires, and measures cost in tokens rather than rows, which exposes batch sizing , batch fidelity and repartitioning as new opti-mization problems. 

Batching and guarantees. Batch prompting amortizes instruction tokens over the inputs of one prompt [6, 26], at a quality cost reported as discounted output [30] and cross-query interference [51]. Statistical guarantees for LLM-powered operators [19, 36, 53] bound a cheap proxy against an oracle to decide which tuples the expensive model must see. NousDB’s certificate is orthogonal: it bounds the fidelity of batched execution to singleton execution (Theorem 4.6) to decide how many tuples may share one call. ## 3 NousDB Algebra 3.1 NousDB Model 

In the relational model, a relation 𝑅 has a set A of attributes, each 

𝐴 𝑖 ∈ A with a domain 𝐷𝑜𝑚 (𝐴 𝑖 ) (numeric, boolean or categorical); for a tuple 𝑟 , 𝑟 [𝐴 𝑖 ] is the value of 𝐴 𝑖 in 𝑟 , and for B ⊆ A, 𝑟 [B]

denotes the projection of 𝑟 on B. Relational systems also admit unstructured attributes through general-purpose types such as 

TEXT or BLOB , but these remain opaque to query semantics: no relational operator or optimizer can reason about their content. NousDB lifts this limitation by drawing models from a registered pool M of foundation models (LLMs, VLMs) that interpret and execute natural-language instructions over their inputs. A model 𝑚 ∈ M maps input values to output values, 𝑚 :

Î𝑖 𝐷𝑜𝑚 (𝑋 𝑖 ) → Î𝑗 𝐷𝑜𝑚 (𝑌 𝑗 ), and is steered by a prompt. We de-fine a prompt constructor 𝑝𝑐 from an operator-specific instruction template 𝑝𝑡 . Given an input 𝑥 , 𝑝𝑐 instantiates 𝑝𝑡 with the relevant attribute values from 𝑥 , producing the prompt 𝑝 = 𝑝𝑐 (𝑥 ) submit-ted to 𝑚 . Combining a prompt constructor with the model gives a prompted model invocation (simply model invocation hereafter) through which our semantic operators compose model inference with classical query processing. 

Singleton semantics. We define the reference semantics of semantic operators in terms of singleton model invocations : each input tuple, or tuple pair for a join, is evaluated independently. 

Deterministic-oracle assumption. Repeated model invoca-tions with the same prompt and input may produce different out-puts. We abstract away this stochasticity by assuming that, for a fixed model 𝑚 , prompt 𝑝 , and input 𝑥 , every invocation of 𝑚 (𝑝, 𝑥 )

returns the same output. Removing model stochasticity from the logical semantics allows us to reason about semantic operators using standard set-theoretic arguments. It is analogous to simplify-ing assumptions used by relational optimizers, such as uniformity and statistical independence, which enable selectivity estimates to compose across predicates [24]. 1

The logical semantics impose these requirements: 

• Model totality. The invocation 𝑚 (𝑝, 𝑥 ) is defined and produces a well-formed output for every input 𝑥 in the operator’s domain. 

• Tuple-local prompt construction. Under singleton execution, the prompt constructor is deterministic and uses only the declared input attributes of the tuple 𝑟 . Thus, for a fixed template and tuple, it always produces the same prompt. Together, singleton execution, deterministic-oracle evaluation, and tuple-local prompt construction provide input locality : the out-put associated with a tuple depends only on its declared input attributes and not on other tuples, the container relation, its evalu-ation order, or its assigned partition. Consequently, each NousDB semantic operator, Extend , Semantic Selection , and Semantic Join 

that are presented next, defines a well-defined function from rela-tions to relations. Furthermore, NousDB logical semantics allows us to define algebraic properties and rewrite rules.

## 4.2 Batch Size Optimization 

The operator definitions in Section 3.2 assume singleton execution, under which each tuple’s output depends only on that tuple ( input locality ). Batching reduces the |𝑅 | singleton invocations to ⌈| 𝑅 |/ 𝑘 ⌉

invocations of up to 𝑘 tuples, amortizing per-call overhead to reduce token usage and improve throughput [6, 8, 16, 26]. However, a batch must both fit within the context window and preserve singleton outputs. Batching is thus a physical optimization valid only when it preserves the logical operator semantics. To define safe batching, we distinguish the two outputs of a tuple under a fixed operator, model mmm, and prompt template.

Because a batch fit depends only on the token lengths of its tuples, the optimizer can determine the maximum feasible batch size at planning time using token histograms, without invoking the model .Christos Tsapelas, Georgia Koutrika, and Yannis Ioannidis 

(ii) Safe batching against per-row invocation. A batch can affect per row results: the output a tuple receives inside a batch may differ from the one it receives when invoked alone. The first concerns the rela-tionship between tuple token lengths and the window capacity, while the second concerns the model behavior. Neither implies the other: batches that fill a small fraction of the window may already lose quality. Figure 4 illustrates this distinction for two cases: IMDB and SemBench reviews. ## 5 Experiments 

We evaluate NousDB through four research questions: 

RQ1: How does NousDB perform end to end? We compare NousDB with competing systems on IMDB, SemBench [23], and semantic extensions of JOB [24] and STACK [13] (Section 5.2). 

RQ2: How do batching and fidelity constraints affect ex-ecution? We measure the token savings from batching and the effects of fidelity constraints on batch size, runtime, and quality (Section 5.3). 

RQ3: What is the contribution of each optimization? We ab-late histogram-guided batch sizing, fidelity-aware batching, token-aware repartitioning, and algebraic rewrites (Section 5.4). 

RQ4: What are the benefits of the semantic algebra? We evaluate its effects on query performance and output quality and discuss it across all sections.

IMDB extends the JOB schema [24] with 10.5K reviews [31]. It contains 11 queries in total, having six single operator queries (Q1–Q4, and the extend-to-aggregate Q5 and Q6) and the rest are pipelines of several semantic operators (Q7–Q11), four of which the rewrites target (Q7, Q8, Q10, Q11). SemBench-Movie [23] has ten queries: retrieval with a LIMIT (SB1, SB2), aggregates (SB3, SB4, SB8), self-joins of one movie’s reviews (SB5 and SB6 with a LIMIT, SB7 exhaustive over 13,924 pairs) and ranking (SB9, SB10). Finally, we extend JOB [24] and StackExchange benchmarks (24M rows un-der the STACK schema [13], with semantic operators, augmenting standard benchmarks used in the query optimization literature.

Token repartitioning as a new shuffling technique (C2). 

Token Repartition shuffles rows, so in terms of tokens and calls is identical to C0. Its gain is the granularity of the shuffle: DataFu-sion’s round-robin partitioning operator shuffles record batches across partitions, while token repartitioning shuffles them based on their tokens. GPT-5.4 shows big gains when the repartitioning is enables, while the exchange already dealt single rows to ten partitions (session batch size of one), and C2 stays within 6% of C0: balance has little to fix. ## 5.5 Summary of Findings 

From our evaluation we extracted the following findings: RQ1: 

NousDB is the fastest system in every benchmark and model set-ting (up to 86 × and 1 .70–5 .25 × in geometric mean on JOB and STACK), spends the fewest tokens on 40 of 42 query cells, and a NousDB configuration is the most accurate in each. RQ2: Batch sizing cuts tokens to ×0.15–0 .32 of per-row execution without a context overflow, but changes up to 45% of the answers. The certifi-cate keeps at least 86% of them, and reasoning, affordable only when batched, raises quality. RQ3: Batch sizing carries the cost reduction, rewriting reduces the work itself, repartitioning lowers latency by spreading requests over all partitions, and the three compose. All optimizations together smoothen the weaknesses caused from each one separately, making NousDB optimizations work coopera-tively rather than competitively. RQ4: Pushdowns remove 20–47% of the tuples that reach a model and preserve the answers up to run-to-run noise, while fusion improves them (Q10’s F1 doubles with Qwen3-8B and quadruples with GPT-5.4-nano). 

## 6 Conclusions 

We presented an extended algebra for semantic query processing by formalizing semantic operators that compose with relational algebra, enabling semantic query rewriting and a system that im-plements it, NousDB. We showed that semantic analytics funda-mentally departs from classical optimization by shifting the unit of cost from rows to tokens, which introduces new challenges in batch sizing and parallel execution under token skew. We addressed these challenges with a token-based cost model, statistical guarantees for safe and accurate batching, and token-aware repartitioning, inte-grated into a modern query engine. Future work includes extending the algebra with additional semantic operators, incorporating qual-ity into cost models, and query optimization.
