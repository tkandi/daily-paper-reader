## ABSTRACT 

Mixture-of-Experts (MoE) inference is increasingly deployed in local and on-premise environments, where expert parameters often exceed GPU memory capacity. In latency-sensitive, low-concurrency settings, repeatedly staging routed-expert weights from CPU memory to the GPU can be prohibitive, leaving routed-expert feed-forward networks (FFNs) on the critical path of multi-socket CPUs. Existing CPU accelerations often rely on intrusive, hardware- or topology-specific requirements, such as AMX-specific weight layouts or manual NUMA-aware placement. These require-ments reduce portability and complicate integration with standard CPU–GPU offloading pipelines. We present HiNa-MoE, a high-performance, non-intrusive operator library for MoE inference on CPUs with matrix engines. HiNa-MoE (1) exploits AMX with an optimized micro-kernel that keeps expert weights in standard lay-outs and instead fuses lightweight layout transforms into token gathering and stores; (2) applies NUMA-aware task partitioning that minimizes cross-socket traffic under a simple page-interleaved

## 1 INTRODUCTION 

Mixture-of-Experts (MoE) large language models (LLMs) offer an appealing quality–efficiency trade-off by using conditional compu-tation: each token activates only a small subset of experts in the feed-forward network (FFN) layers [20, 24, 28, 35]. This sparsity reduces arithmetic work relative to dense LLMs while preserving high model capacity, and it has become a common design point in production models such as Mixtral [8], Qwen-MoE [12], and DeepSeek [1]. arXiv:2610.05123v1 [cs.DC] 4 Oct 2026 PACT ’26, October 19-22, 2026, Chicago, IL, USA Weiling Yang et al. 1 4 16 64 256 1024 4096 Batch size 1416 64 256 Tokens/s  Our focus CPU_AMX CPU_AVX512 GPU

In local and on-premise deployments, MoE in-ference increasingly runs on CPU–GPU nodes with limited GPU memory [3, 15, 18, 23, 29, 38, 39]. Since the complete set of expert parameters can exceed GPU memory capacity, practical systems often keep some or all routed experts in CPU DRAM and execute different experts on the CPU and GPU [3, 18, 29, 38]. Thus, MoE inference in this setting is inherently a heterogeneous CPU–GPU execution problem: depending on the inference workload, a routed expert may be executed either on the CPU or on the GPU. A natural strategy is to execute routed experts on the GPU when-ever they are activated. However, the benefit of GPU execution depends strongly on the number of tokens processed by each ex-pert. At large batch sizes, the cost of transferring expert weights can be amortized over more tokens, making GPU execution attrac-tive [17, 30]. In contrast, during low-concurrency inference, each expert typically processes only a small number of tokens, while its weights remain large. Repeatedly transferring expert weights from CPU memory to the GPU can therefore incur substantial data-movement overhead relative to the computation [18, 29, 38]. In such cases, retaining routed experts in CPU memory and executing their FFNs on the CPU can be preferable. Figure 1 illustrates this trade-off: CPU execution remains competitive at small and mod-erate batch sizes, whereas GPU execution becomes increasingly advantageous as the batch size grows. This workload-dependent execution behavior defines the scope of our work. We do not attempt to redesign the CPU–GPU offload-ing or scheduling policy. Instead, we focus on the CPU execution path, which remains critical when routed experts are retained in CPU memory under low-concurrency workloads. Our goal is to make CPU-side expert execution highly efficient and portable, while preserving the standard weight layouts required by existing GPU li-braries. In this way, HiNa-MoE serves as a CPU-side building block for heterogeneous MoE inference: existing or future offloading poli-cies can continue to choose between CPU and GPU execution, while HiNa-MoE provides an efficient CPU backend when CPU execution is selected. 

Challenge. CPU-based MoE inference is constrained by (1) small/irregular matrix multiplications (few tokens per expert) and (2) cross-socket memory traffic when expert weights reside in CPU DRAM. To exploit matrix engines such as Intel AMX, systems including KTransformers [18] and Intel Extension for PyTorch (IPEX) [3] store expert weights in AMX-specific layouts. While effective for CPU execution, such layouts are incompatible with standard GPU libraries, complicating CPU–GPU offloading and forcing reconversion, duplicated storage, or specialized kernels. Meanwhile, to mitigate cross-NUMA traffic, KTransformers fur-ther partitions weight tensors across NUMA nodes, requiring deep modifications to the inference framework and its memory alloca-tion behavior. Together, these choices improve speed but reduce portability and raise the engineering barrier for real deployments. 

Our approach. We present HiNa-MoE, a CPU-optimized library for MoE operators that delivers high performance while remain-ing non-intrusive : it requires no offline weight reformatting, no framework-level weight sharding, and no custom NUMA-aware allocator (Section 3.1). HiNa-MoE preserves general-purpose ma-trix layouts (row- or column-major) and requires no changes to the framework’s weight storage or memory allocation policies; adopt-ing it amounts to replacing a small, well-defined set of operator implementations. 

Contributions. HiNa-MoE achieves these goals via three comple-mentary techniques: 

• AMX-efficient micro-kernels for general layouts . Based on observations of MoE FFN computation patterns and AMX data layout constraints, we design micro-kernels that keep expert weights in standard layouts and instead fuse light-weight layout transforms into token gathering and stores (“transform intermediate matrix, not weight matrix”), en-abling efficient AMX utilization without any weight refor-matting (Section 4). 

• NUMA-aware task partitioning without framework modifications . Leveraging the fact that expert dimen-sions in modern MoE models are typically multiples of 128 [1, 8, 12], we propose a task-partitioning strategy that reduces cross-socket traffic under a simple page-interleaved policy (e.g., numactl –interleave=all ) without restruc-turing weight storage (Section 5). 

• Attention optimization via MV-to-MM conversion . Dur-ing decoding, we convert memory-intensive matrix–vector operations into compute-intensive matrix–matrix execution to better utilize AMX (Section 6). 

Results. We evaluate HiNa-MoE on three representative multi-core CPUs: Intel Xeon Gold 6430 [6], 6448H [7], and Max 9462 [5]. Across real-world MoE models [1, 8, 12], HiNa-MoE consistently outperforms state-of-the-art baselines [2, 3, 18], achieving up to 3.37 × FFN-kernel speedup and up to 2.09 × end-to-end inference speedup. These results make HiNa-MoE a practical and portable building block for high-performance MoE inference on CPU–GPU nodes.

## 2.3 NUMA Architecture 

Non-Uniform Memory Access (NUMA) is the dominant architec-ture for multi-socket servers. In a NUMA system, a core can access memory attached to its local node with higher bandwidth and lower latency than memory attached to a remote node (cross-NUMA ac-cess) [4]. NUMA systems typically expose three memory allocation policies: 

• First-touch : the default OS policy; a page is allocated on the node of the thread that first writes it. This is convenient but can lead to non-deterministic and suboptimal placement. 

• Interleaved : pages are allocated round-robin across all nodes. This policy is deterministic and easy to deploy (e.g., via 

numactl –interleave=all ) without code modifications. 

• NUMA-aware : the application explicitly allocates pages on specific nodes to optimize locality, but this typically requires invasive code changes. HiNa-MoE shows that, when combined with NUMA-aware task partitioning, the simple interleaved policy can mitigate cross-NUMA bottlenecks without modifying the inference framework’s weight storage or memory allocator. 

## 2.4 Related Work 

In resource-constrained scenarios, MoE inference systems typically combine (i) a high-level policy for placing experts and scheduling transfers across CPU and GPU and (ii) a low-level implementation of operators (FFN and attention). We therefore organize related work along three axes: offloading/scheduling , CPU operator kernels and data layouts , and NUMA locality management [3, 17, 18, 22, 23, 29, 30, 34, 42]. 

2.4.1 Offloading and scheduling. LIA [30] adapts offloading deci-sions based on prompt length, batch size, and inference phase for dense LLMs. MoE-Lightning [17] pages expert weights to GPU mem-ory and overlaps transfers with GPU FFN execution. Fiddler [29] proposes a dynamic offloading strategy and finds that substantial GPU offloading gains occur only beyond a batch-size threshold. Hy-briMoE designs prefetching to proactively fetch frequently invoked (“hot”) experts to increase GPU residency [42]. KTransformers [18] uses a static placement strategy, retaining routed experts on the CPU while placing shared experts and attention layers on the GPU. 

Key differentiation. HiNa-MoE does not propose a new offloading policy. Instead, we focus on making CPU-side operators both fast and portable so they can serve as drop-in building blocks under existing and future policies. 

2.4.2 CPU operator optimization and data layouts. KTransform-ers [18] and IPEX [3] accelerate CPU-side MoE operators by lever-aging AMX, typically through pre-converting expert weights into AMX-specific layouts (e.g., tmm1 in Figure 3). T-MAC [34] targets low-bit dense LLM inference on embedded CPUs by transforming matrix multiply–accumulate operations into table lookups. 

Why “layout-first” can be intrusive. AMX-specific layouts can improve CPU throughput, but they hinder heterogeneous execution because standard GPU libraries expect general layouts. In practice, this often forces extra weight conversions (AMX-specific layout →

## 3 MOTIVATION 3.1 The Case for a Non-Intrusive Design 

In local deployments, MoE inference often runs on multi-socket CPU–GPU nodes, where expert parameters reside in CPU DRAM and CPU-side execution becomes performance-critical. Meanwhile, the operator stack must remain easy to integrate across CPU-only, GPU-offload, and hybrid settings [3, 30]. We argue that this requires a non-intrusive design with two principles: 

• General layouts : expert weights remain in standard row-or column-major formats compatible with CPU and GPU libraries. 

• Framework agnosticism : no changes to weight storage, tensor semantics, or memory allocation. These principles preserve deployment flexibility: models can move between CPU and GPU without layout conversion or dupli-cation, and NUMA effects can be handled via OS-level mechanisms (e.g., numactl –interleave=all ) rather than intrusive changes. 

Non-intrusive criterion. A method is non-intrusive if it requires no (1) offline weight reformatting, (2) framework-level weight shard-ing/replication changes, or (3) custom NUMA-aware allocators. HiNa-MoE satisfies these by preserving general layouts, using page interleaving, and applying NUMA-aware task partitioning (Table 1). Table 1 shows that existing systems trade off performance, porta-bility, and complexity: some retain generality but underutilize CPU performance (e.g., Fiddler), while others achieve high performance via intrusive, hardware-specific optimizations (e.g., IPEX, KTrans-formers). HiNa-MoE breaks this trade-off without sacrificing de-ployability.

To satisfy AMX’s layout requirements, frameworks typically adopt one of two strategies. Runtime conver-sion (e.g., oneDNN) stores weights in a general layout and trans-forms them on the fly during expert execution; this preserves com-patibility, but introduces a recurring conversion overhead. Pre-conversion (e.g., IPEX and KTransformers) stores weights in an AMX-specific layout, maximizing AMX throughput but making the weights incompatible with standard GPU libraries; CPU–GPU offloading then requires a costly reverse transformation, duplicated weight storage, or bespoke GPU kernels. 

Cross-socket (NUMA) penalty. Figure 4 shows that memory-bandwidth utilization drops by about 20% when scaling from one to two NUMA nodes. Systems without NUMA-aware execution (e.g., IPEX and oneDNN) incur substantial cross-socket traffic, reducing effective bandwidth available to memory-bound MoE operators. KTransformers mitigates this by pre-partitioning weights across NUMA nodes to enforce locality, but doing so is intrusive and re-quires modifying tensor storage as well as the framework’s memory allocation behavior. Overall, current approaches either leave performance untapped or bake in hardware-specific assumptions that reduce portability and increase engineering cost. This motivates an operator stack that delivers high performance without intrusion .Motivated by this gap, HiNa-MoE is designed to pursue three goals simultaneously: (1) preserve general matrix layouts to maxi-mize offloading flexibility, (2) fully exploit AMX compute capability, and (3) avoid cross-NUMA accesses without framework modifica-tions.

Why general layouts matter. In mainstream MoE inference frame-works [11], token matrices, expert weights, and output tensors are stored in a unified, general-purpose layout (typically row-major) so the same model state can support both CPU and GPU execution (Figure 6). However, AMX reaches peak throughput only when one MM operand is in an AMX-specific (packed) layout (Section 2.2). To avoid per-inference layout conversion, IPEX and KTransformers pre-convert each expert weight matrix W into an AMX-specific lay-out (Figure 5a). While this improves CPU performance, the resulting weight format is incompatible with standard GPU libraries, which makes CPU–GPU offloading inflexible and can force reconversion or special-purpose kernels. 

Our approach: transform I, not W. HiNa-MoE achieves high AMX performance while preserving the framework’s general lay-outs (Figure 5b). This design remains largely unexplored [3, 18] due to the unclear interaction between AMX and MoE FFN computa-tion. Instead of pre-converting weights, we perform lightweight runtime layout transformations on the intermediate matrix I and fuse them into data movement that the framework already must perform. Concretely, during token gathering, the selected tokens are loaded into registers and written into I. We fuse a register-level transformation into this path so that I is produced directly in an AMX-specific layout (the first transformation in Figure 5b). The overhead is small because (i) I is much smaller than the expert weight matrices and (ii) the transform consists of only a handful of register operations. Specifically, matrix I corresponds to the tile register labeled tmm1 

in Figure 3; this mapping preserves the mathematical form I × W.After computing I × Wgate and I × Wup , we similarly fuse the store path to emit outputs in the layout required by the next AMX MM (the second transformation). Finally, after multiplying by Wdown ,we apply a register-level transpose before writing the output back in the standard row-major layout (the third transformation). In summary, we keep expert weights in the general layout ( tmm0 

in Figure 3) and align I with the AMX-specific operand ( tmm1 ), fus-ing necessary transforms into unavoidable gather/store operations. This redesign is confined to the FFN operator implementation and requires no changes to the framework’s matrix layouts. HiNa-MoE therefore enables the framework to fully exploit AMX without requiring the framework to be aware of AMX-specific layout con-straints. 

## 4.2 Micro-kernel Design 

4.2.1 Determining Micro-kernel Size. Expert FFN performance is dominated by its three MM operators, so micro-kernel efficiency is a first-order concern. We target high efficiency by maximizing the compute-to-memory ratio (CMR) of the micro-kernel [27, 33, 37], which captures how much arithmetic we can perform per byte loaded from memory. Many prior designs are primarily tuned for vector registers and fall back to vector units (e.g., AVX-512) when the row dimension of 

I is small; for example, KTransformers uses AMX only when the row dimension exceeds four [18]. ## 5 NON-INTRUSIVE CROSS-NUMA OPTIMIZATION 5.1 Performance Bottleneck and Opportunity 

In CPU-centric MoE inference on multi-socket servers, the dom-inant NUMA bottleneck is remote access to expert weight matri-ces [18]. In contrast, accesses to the gathered token matrix I are typically not performance-critical. During prefill, 𝑀 is determined by batch size, prompt length, and expert activation rate, and in common local deployments the batch size is small (often 1). When prompts are short, I is much smaller than the expert weights; when prompts are long, prefill becomes compute-bound and is commonly addressed via CPU-GPU or multi-GPU parallelism, which is out-side our scope. During decoding, 𝑀 equals the batch size times the activation rate, and I remains small. To avoid cross-socket traffic on weights, prior systems such as KTransformers use numa_alloc_onnode to partition each weight matrix across NUMA nodes so that each socket primarily accesses its local portion (Figure 7(a)). However, this approach is intrusive because it requires modifying the framework’s tensor storage and memory allocator. HiNa-MoE instead relies on a standard OS mechanism: inter-leaving the physical pages of weight matrices across NUMA nodes (e.g., via numactl –interleave=all ). With 4 KB pages, each page holds 2,048 BF16 elements; for example, a weight matrix with 6,144 columns occupies three pages per row (Figure 7(b)). Given this page-level interleaving, HiNa-MoE uses task partitioning so that each socket predominantly touches pages local to its NUMA node, while preserving the framework’s original weight storage. ## 5.2 Task Partitioning Strategy 

Under an interleaved page layout, high MM performance requires two properties: (1) each socket should primarily read weight ele-ments that are local to its NUMA node, and (2) each socket must still be able to assemble contiguous tiles that efficiently feed AMX (in particular, the operand mapped to tmm0 in Figure 3). With explicit NUMA placement (e.g., numa_alloc_onnode ), these properties are straightforward to satisfy: adjacent matrix rows stored on the same node can be mapped directly to AMX tile rows (Figure 8(a)). Under page interleaving, however, adjacent rows can reside on different NUMA nodes. For example, in Figure 7(b), the first 2,048 elements of row 0 are on NUMA 0, while the first 2,048 elements of row 1 are on NUMA 1. As a result, as shown in Figure 8(b), on NUMA 0 we may need to combine segments from non-adjacent rows to fill AMX tile rows (e.g., elements 0 ∼ 2047 of row 0 and elements 0 ∼ 2047 of row 2), while selecting multiple segments within a row to cover the reduction dimension (e.g., elements 0 ∼ 2047 and 4096 ∼ 6143 of row 0). Next, we show how to systematically identify and organize these segments. Concretely, we address three subproblems: (1) identifying which weight segments are local to each NUMA node under interleaving; (2) selecting local segments that share the same 𝑦 -range so they can form AMX tile rows; and (3) selecting local segments that share the same 𝑥 so they provide contiguous ranges along the reduction dimension. Subproblem (1) enforces locality, while (2) and (3) ensure efficient utilization of AMX. For ease of description, we define the following terms.

Although our design leverages the facts that current MoE models use 128-aligned dimensions and that commercial servers expose only a small number of NUMA nodes, these are not arbitrary as-sumptions; rather, they arise naturally from both hardware con-straints and common model design choices. Overall, HiNa-MoE enables the framework to minimize cross-NUMA accesses to expert weights without requiring the framework to be aware of NUMA details.

## 6 ATTENTION MODULE OPTIMIZATION 

The attention module consists of (i) input projections (three matrix multiplications, producing Q, K, and V), (ii) scaled dot-product at-tention (SDPA), and (iii) an output projection (one matrix multiplica-tion). The projection MMs are optimized by our AMX micro-kernels (Section 4) together with the NUMA-aware task partitioning strat-egy (Section 5.2), and therefore we focus here on SDPA. Prior work has largely optimized SDPA for the prefill phase [19, 25], where computation dominates and batching is higher. We therefore target SDPA optimization in decoding.

In contrast, Qwen3-30B-A3B exhibits a more pronounced benefit from (+a), as its attention accounts for a larger fraction of the decoding computation than in Mixtral-8x7B, making CPU-side attention optimization more impactful on end-to-end performance. This result highlights that the effectiveness of attention optimization depends on both the relative cost of attention and the underlying offloading strategy.

## 8.5 Evaluation on an HBM-based CPU 

We evaluate FFN-kernel performance on a dual-socket Intel Xeon CPU Max 9462 ( 9462 ) [5]. Each socket provides 64 GB of HBM (HBM-only mode). The measured peak bandwidth is 853 GB/s; local NUMA accesses reach 425 GB/s, while cross-socket accesses drop to 89 GB/s. Because HBM capacity is insufficient for full end-to-end MoE inference on our evaluated models, we report FFN-kernel results only. Figure 16 shows that HiNa-MoE outperforms oneDNN and IPEX by 9.65 × and 3.41 × on average. The larger gap on 9462 is explained by the higher penalty of remote accesses: the local-to-remote bandwidth ratio is ∼5× on 9462 versus ∼2.3 × on 6430. As the cost of cross-socket accesses increases, HiNa-MoE’s NUMA-aware scheduling yields correspondingly larger benefits.

## 9 DISCUSSION AND FUTURE WORK 

Our evaluation shows that HiNa-MoE achieves consistent speedups across multi-socket servers and real-world MoE models. While the current implementation targets latency-oriented inference at small batch sizes on AMX-capable CPUs, the underlying design principles generalize. 

Adaptation to other CPU architectures. HiNa-MoE’s core idea— preserve general-purpose weight layouts and adapt the compu-tation kernels—extends beyond AMX. Prior work suggests that Arm’s SME can support tile-oriented micro-kernels similar in spirit to AMX [21]. A natural direction is to apply the same “transform intermediate matrix I, not W” philosophy to SME by fusing light-weight layout transformations into token gathering and kernel execution, with tile sizes chosen to match the available register space and instruction semantics. 

Multi-batch and CPU–GPU collaborative inference. For larger batch sizes and long-prompt prefill, CPU-only routed-expert execu-tion can become a bottleneck because GPU compute and bandwidth are typically higher [17, 30]. A promising direction is dynamic ex-pert offloading based on prompt length, batch size, and available GPU memory, overlapping transfers with CPU computation [38]. Because HiNa-MoE preserves general-purpose layouts and avoids framework-level allocator changes, experts can move between CPU and GPU without layout-conversion overhead, making it a natural substrate for such schedulers. 

## 10 CONCLUSION 

We have presented HiNa-MoE, a high-performance, non-intrusive operator library for MoE inference on multi-socket, multi-core CPUs. It preserves general-purpose matrix layouts for compati-bility with CPU–GPU offloading frameworks, while improving performance through (1) AMX-efficient micro-kernels that fuse token gathering with lightweight, on-the-fly data movement, (2) NUMA-aware task partitioning that exploits the periodicity of in-terleaved pages without modifying the framework allocator, and (3) decode-phase attention optimization that converts memory-bound matrix–vector operations into compute-intensive matrix–matrix multiplications. Across multiple server-class CPUs and real-world MoE models, HiNa-MoE achieves up to 3.37 × FFN-kernel speedup and up to 2.09 ×

end-to-end MoE inference speedup over state-of-the-art baselines, while maintaining near-zero cross-socket traffic and plug-and-play integration.
