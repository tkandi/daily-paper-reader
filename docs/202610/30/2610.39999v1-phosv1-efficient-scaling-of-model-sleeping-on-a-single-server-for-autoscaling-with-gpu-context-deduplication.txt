# ABSTRACT 

Autoscaling is a key mechanism in model-as-a-service systems, where fast scale-up is essential because the scale-up time directly determines how long a model service remains overloaded— which in turn governs serving quality. The state-of-the-art approach—model sleeping, adopted by mainstream serving engines including vLLM and SGLang—achieves near-zero-cost scale-up by pausing pre-spawned engines on the GPU. However, sleeping is not a free lunch: each sleeping model must keep its GPU context resident, and this cost grows linearly with the number of models, degrading serving performance. Because providers must support many models, they face a dilemma between fast scale-up for all models and high service performance. In this paper, we show that a single server can keep many models asleep without paying this GPU context tax. The key observation is that the contexts of sleeping models are largely duplicated: the driver (CUDA) context can be shared across models, and their GPU kernel binaries overlap heavily due to common operators and libraries. P HOS V1 deduplicates this context by transparently delegating each engine’s GPU context allocation to a central daemon through API remoting; therefore, a single server can keep far more models asleep than current engines allow. Our evaluation shows that P HOS V1 matches the scale-up time of vanilla vLLM sleep mode while substantially reducing the GPU memory footprint, improving end-to-end multi-model serving performance. 

Keywords GPU context, LLM serving, cold start, checkpoint and restore, model pooling 

# 1 Introduction 

Model as a service—deploying multiple models on one or multiple shared clusters to serve LLM requests from applications—has become an important component of modern computing infrastructure [1–3]. Autoscaling— dynamically scaling an engine up and down on spare GPUs to serve a model—is essential for model-as-a-service systems. The reasons are twofold. First, a service provider typically deploys models from many vendors (e.g., DeepSeek, Qwen, GLM, and MiniMax), each of which offers models of different sizes. Second, the request arrival rate of a model fluctuates over time [1, 4, 5], because applications choose the requested model dynamically, depending on their budgets and capability requirements. If we statically deploy each model, assigning it a fixed number of GPUs without autoscaling, the model service becomes overloaded because it is underprovisioned when the request rate exceeds the capacity of the deployed GPUs. Conversely, GPUs become idle because of overprovisioning when the request rate decreases. Autoscaling dynamically adjusts each model’s GPU allocation according to its changing request rate. Efficient scale-up is a key system requirement for autoscaling. Scale-up is triggered when the request rate increases, but during the scale-up interval, the newly provisioned GPUs still cannot serve requests, so the model service remains overloaded. As a result, the scale-up time directly determines the duration of this overload, so model-as-a-service providers seek to minimize it. Unfortunately, current model autoscaling has a long scale-up time because starting an engine capable of serving a model requires a complex control plane to create the necessary GPU contexts (§2). To reduce this delay, the state-of-the-art arXiv:2610.39999v1 [cs.DC] 29 Oct 2026 method—adopted by standard engines including vLLM and SGLang—is model sleeping [1, 6]. To avoid creating GPU contexts during startup, the system spawns multiple engines offline, each capable of serving one model online. After all the engines finish initialization, they are paused on the host server. Thus, a scale-up during online serving directly wakes up the engine, enabling near-zero-cost scale-up. Model sleeping is not a free lunch. To keep one model asleep, each engine must keep a substantial amount of context on the GPU—including the driver context (CUDA context) and the model’s GPU kernel binaries. This places a heavy burden on the GPU because GPU memory is limited and precious: in our experiment, sleeping 24 models consumes up to 27 GB (34%) of an 80 GB GPU’s memory, and this occupancy scales linearly with the number of sleeping models. This memory footprint can further degrade throughput by up to 54% when serving one model, because modern models reserve GPU memory for intermediate results (KV cache) to accelerate computation. Sleep mode must preserve the costly parts of this context on the GPU because, unlike model parameters, which can be restored quickly [4], these context components cannot be restored quickly. This poses a dilemma for the service provider: to enable fast scale-up for all models, the server pays online service overhead, while to ensure high service performance, the provider can only sleep a few models on each server, so the service still pays the scale-up costs. In this paper, we show that we can increase the number of sleeping models on one server without paying a linear GPU-context memory tax. The key observation is that the context for each sleeping model contains many duplicate components (up to 99% similarity between two popular models, as shown in Fig. 5): the driver context can be naturally shared across models, i.e., engines created later can reuse the driver context of an earlier engine, and the GPU kernel binaries of different models also substantially overlap because current models share operators and libraries (§3). By deduplicating this context, we can dramatically reduce the memory required to support more sleeping models on one server. To realize GPU context deduplication, we adopt a separation design that delegates each engine’s GPU context allocation to a central system daemon, where we can identify and avoid creating unnecessary contexts. To be compatible with existing engines, we leverage API remoting [7, 8] to implement this delegation transparently. One challenge of deduplication is that many internal GPU buffers allocated during initialization cannot be effectively deduplicated. Fortunately, such buffers can be created on the fly much faster than the other context components, so we treat them differently: we leave them unallocated while the model sleeps and reconstruct them at wake-up time. We have implemented deduplication from scratch and integrated it with vLLM’s sleep mode. Our evaluation shows that P HOS V1 achieves a scale-up time similar to that of vanilla vLLM sleep mode while reducing the GPU memory footprint by 98.1% when sleeping 23 models. This saving improves end-to-end serving performance: in a multi-model trace replay, P HOS V1 reduces average time to first token by 87.0% over vanilla vLLM, which can sleep only a limited number of instances within the memory budget. P HOS V1 instead sleeps all required models without incurring the GPU memory burden of vanilla sleep mode. 

Contributions. In summary, this paper makes the following contributions: • The first characterization of the GPU-context memory tax of model sleeping and the opportunity to deduplicate it across models (§2, §3). • P HOS V1, a transparent GPU-context deduplication system with delegated context management in a service daemon, shares duplicate driver contexts and kernel binaries, and reconstructs non-deduplicable buffers only at wake-up time (§3). • An implementation integrated with vLLM sleep mode and an evaluation showing that P HOS V1 retains its near-zero-cost scale-up while reducing GPU-context memory use and improving end-to-end multi-model serving performance (§4). PHOS V1 is open-sourced at https://github.com/blitz-serving/PhoenixOSv1 .

# 2 System Model and Problem Statement 

Multi-model serving and autoscaling. AI service providers typically host many models of various sizes from different vendors simultaneously in a shared GPU cluster [1–3], because no single model dominates user demand: models differ in capability and cost. Each model occupies one or more dedicated GPUs due to its size. A key challenge for model providers is allocating GPU resources to each model. Static GPU allocation—allocating a fixed number of GPUs to each model at deployment time—is suboptimal because per-model request rates fluctuate over time [1, 4, 5]. Modern service providers therefore use autoscaling to adjust GPU allocation per model in response to traffic (Fig. 1(a)). Specifically, autoscaling makes GPU provisioning for each model elastic: when a model’s load rises, the scheduler picks one or more idle GPUs, starts one or more inference engines on the host servers, and loads the model weights to expand the model’s serving capacity (scale up). When a model’s load falls, the scheduler deallocates a subset of the model’s GPUs, releasing them back to the pool for other models to save GPU time (scale down). A key system requirement of autoscaling is fast startup during scale-up: until the newly launched inference engines become ready to serve, requests to the model being scaled up must queue; a slow startup therefore directly causes request stalls and SLO violations during the scaling window (Fig. 1 (b)). The faster the scale-up, the smaller the performance penalties. 

Goal and design space overview. Our design goal is to reduce the cold start overhead of autoscaling a serving instance. To understand how to achieve this, we first break down the cold start into two stages and then analyze the detailed steps involved to determine how much we can optimize them. Fig. 1(c) illustrates the two stages: a control plane that builds the serving engine’s runtime context on the CPU and GPU, and a data plane that loads the model weights into GPU memory. The control plane builds two contexts. Building the CPU context starts the Python interpreter that runs the inference engine for a model. The interpreter imports the serving stack (e.g., PyTorch and vLLM), loading tens of thousands of Python modules and instantiating engine components such as the request scheduler. Building the GPU context initializes the GPU driver—e.g., by creating the CUDA primary context [9] on the target device— loads the model’s GPU kernels into device memory, and constructs the runtime handles the engine uses to launch GPU work—CUDA streams, cuBLAS, cuDNN, and so on. The data plane copies the model weights from host memory or external storage into GPU memory. Its latency is bounded below by the weight size divided by the link bandwidth (e.g., PCIe or RDMA), and has been optimized to approach the hardware limit through recent work [4] on network-based multicast weight loading. If the server starts from a clean state (without any optimizations), these stages could take seconds or even minutes, as we describe in §4. As a result, prior work has proposed various methods to mitigate the slow startup issue. In this paper, we focus on techniques to reduce the control-plane overhead, as the data plane has been optimized to approach the hardware limit thanks to recent work [4, 10]. 

Current solutions: checkpoint/restore and model sleeping. One intuitive way to accelerate cold start is to use checkpoint/restore [11]. Specifically, we checkpoint an engine that has completed control-plane initialization into an image; on a future restart, we restore from the checkpoint image and thus bypass all the control-plane overhead. First, performance: P HOENIX OS [11], the state-of-the-art system, still incurs 0.57 s of overhead when restoring an engine during scale-up, because it takes time to parse the checkpoint image and restore the process’s memory pages and kernel state, as shown in Fig. 1(c). Second, compatibility: modern inference engines adopt complex optimizations that our CPU-side checkpoint/restore tool (based on CRIU [12]) cannot support today, such as io_uring [13]. Supporting them would require large changes to the current serving engines, or a huge implementation effort in CRIU, which is impractical because serving engines continue to evolve rapidly. Another approach adopted by current systems—including Aegaeon [1] and the sleep mode of vLLM and SGLang [6]—is model sleeping. It resembles the warm-start technique in serverless computing for cold start acceleration [14], but applies it in the model-as-a-service setting. Specifically, to enable fast cold start, the sleep mode prewarms a few engines on the server, each capable of serving one model, and then uses OS utilities [15] to pause these engines before they receive requests. A later scale-up unpauses the required engine, bypassing all the control-plane overhead. After the model is scaled down, the engine is re-paused. In the per-GPU serving model considered here, each GPU may cache multiple sleeping engines, but at most one engine wakes up and executes on that GPU at a time. 

Key issue of model sleeping: memory scales linearly with the number of sleeping models and slows serving. 

Having discussed the issues of checkpoint/restore above, a natural question is whether model sleeping addresses the cold-start issue. One key problem of model sleeping is that it trades GPU memory for fast startup. This limits the number of models that can be prewarmed on each machine, because the memory cost grows linearly with the number of sleeping models. Specifically, to make a later scale-up’s control-plane cost near zero, a paused engine keeps its GPU context resident in GPU memory and its CPU context resident in host memory. The CPU context occupies a relatively small fraction of host memory (e.g., vLLM holds 2.9 GB on the CPU) and can be shared across processes using host-side shared memory, but the GPU context is substantial and currently cannot be shared. # 3 Design of P HOS V1

PHOS V1 therefore has two goals: (1) remove the control-plane cost, even when a GPU is likely to sleep many models at the same time; (2) avoid the GPU memory cost of keeping many models asleep. 

Key design opportunity: GPU context across sleeping models is redundant. PHOS V1 builds upon model sleeping to remove the control-plane cost, which enables fast scale-up. To further address its memory expansion issues, we make a key observation: their GPU contexts contain substantial duplicate content. If we can deduplicate this content, we can dramatically reduce the GPU memory required to keep multiple models asleep. More specifically, we first break down the GPU memory used for each sleeping model in detail in Fig. 4 to assess how much of their context we can deduplicate. Four components contribute to GPU-resident memory: CUDA context—the GPU runtime environment containing control state for virtual-memory management and synchronization events [17]; GPU kernels—the compiled GPU code that runs the model’s inference; GPU buffers—memory allocated for the model’s internal use; and handles—registries for resources and libraries used to access the GPU, such as CUDA streams and cuBLAS [18]. Except for the GPU buffers, which are model-dependent, and the handles, whose memory usage is negligible, we found that most content can be deduplicated. First, the CUDA context can be shared across models. This is straightforward because the driver context itself is model-independent, i.e., the context used by one model can trivially be used for another. Moreover, the kernels used by models also have a high degree of overlap: Fig. 5 provides the pairwise similarity of GPU kernels across models excluding GPU buffers. We choose models with high download counts on Hugging Face [3] because they represent popular models typically served by model-as-a-service providers. Most model pairs have 59–99% kernel similarity. Despite differences in architecture and size, existing models share similar kernels because (1) many operations, such as matrix multiplication, are common across models, and (2) a narrow set of libraries (e.g., FlashInfer [19]) provides these operations because writing them efficiently for GPUs is non-trivial. One may notice that the GPU buffers still account for much of the GPU memory used for some models (e.g., Qwen3.6-27B, as shown in the top panel of Fig. 4). System architecture. To realize deduplication, we need to ensure that all the GPU contexts from different sleeping models are managed together by a central service, so that it can detect duplicate components and avoid creating duplicate resources. Thus, P HOS V1 deploys a per-machine system daemon for managing GPU contexts from different models, as shown in Fig. 6. Specifically, unlike the existing sleep mode, in which each model’s engine process manages its own GPU context (the top panel of Fig. 2), the context service manages GPU kernel binaries in a single CUDA context shared by all models assigned to a GPU, along with per-model resources, such as customized kernels. On a server with multiple GPUs, the daemon manages one such context per GPU, allowing wake-ups on different GPUs to proceed 6independently. The kernels are properly deduplicated: before a model loads a kernel binary, we check whether the load is necessary, i.e., whether the same binary has already been loaded. If so, we skip the load to reduce the GPU memory footprint. Below, we describe P HOS V1 in detail: how we construct the context service offline and how the online serving system uses it to support inference requests after an engine wakes up. 

Offline phase: sleep the models and initialize the context service. The offline phase initializes the sleeping engines to support efficient online scale-up. This phase is optional but recommended: otherwise, the system initializes models in the context service on demand, i.e., upon first startup, incurring a one-time scale-up delay. In practice, this process can also be performed incrementally, by reusing scale-up instances or starting models during request idle time, thereby amortizing its cost and avoiding subsequent scale-up delays. The offline phase works as follows. Given N models that need fast startup via sleep mode on one server, we first initialize a context service as a background daemon that manages the GPU resources. After the daemon is initialized, we start the engines (e.g., vLLM/SGLang) one by one, putting each engine into sleep mode once it finishes starting up. Once asleep, an engine’s per-process state is paused, while its GPU context is held by the context service rather than by the engine itself. To achieve this, the engine does not create GPU resources directly; instead, it delegates resource creation to the context service. We make this delegation transparent to the engine using a well-established GPU virtualization technique: API remoting [7, 8]. Specifically, we use LD_PRELOAD to hook all the GPU resource creation calls at the CUDA Driver API boundary and execute them in the context service, requiring no source-code changes to inference engines. After receiving a resource creation request, the context service examines whether the resource already exists. If the resource (e.g., a kernel) has not been created, the context service creates it and records the creation information, so that later requests can recognize it. We use a lookup table that encodes the API semantics: for example, cuModuleLoadData 

loads a kernel binary into the GPU. A subsequent call with the same binary will be recognized as a duplicate, so the service simply skips the creation. The table incorporates all CUDA APIs that inference engines use for GPU resource management and therefore covers all GPU-context allocations. GPU buffers require special handling. If an engine requests a buffer allocation, the service creates a virtual placeholder for it but delays the real allocation until the online phase. This is fine because, as shown in the bottom panel of Fig. 4 and discussed above, creating these resources online is fast. The GPU buffer’s contents are checkpointed in host memory to ensure correct restoration. 

Online phase: supporting model wake-up and inference requests. During the online phase, after an engine wakes up to serve requests, we only need to direct it to use the GPU context stored by the context service for inference. We use the same resource-management mechanism described above: API remoting. When an engine invokes a GPU kernel, the call is first redirected to the context service, which creates the required GPU buffers if necessary and then invokes the kernel. Remoting the GPU API may add performance overhead to inference. This overhead is negligible in the evaluated workloads (§4.1) thanks to optimizations including batching and synchronization, because inference is primarily bottlenecked by GPU execution rather than CPU-side kernel launches [7]. If the model’s context is not already held by the context service, we perform the sleep procedure described above to store its context there, so that future wake-ups avoid a cold start. Storing a context that the service does not yet hold typically reserves additional GPU memory to accommodate the new model. Left unchecked, this could lead to a large memory footprint as we keep more models asleep. To address the issue, we set a maximum amount of GPU memory that may be reserved for sleeping models, and evict lesser-used models from the context service if necessary. Specifically, we use a least-frequently-used (LFU) strategy to evict sleeping models. Whether other strategies can further improve system performance is beyond the scope of our work.

Baselines. We compare P HOS V1 with three baselines. Cold start launches a vanilla vLLM inference engine from scratch when a model is requested. Workloads and metrics. We describe the end-to-end workload in §4.1. Unless stated otherwise, we use 16 Qwen and Qwen-VL models with high download counts on Hugging Face [3]. We report GPU memory footprint, startup latency, end-to-end time to first token (TTFT), TTFT without queueing delay, and input- and output-token throughput. Measurement methodology. We use NVML [21] to measure GPU memory currently occupied by the vLLM process. When reporting GPU-context memory, we measure GPU memory after putting the vLLM engine to sleep; consequently, model weights are excluded. 

4.1 End-to-end experiments Evaluation setup. To evaluate whether P HOS V1 improves user-visible multi-model serving performance under autoscaling, we construct a multi-model end-to-end trace using Aegaeon’s trace methodology [1]. Specifically, we serve 10 popular Qwen models ranging from 0.6B to 32B parameters [3]. The 10-minute ShareGPT [22] trace is generated with Poisson arrivals, with each model receiving requests at a rate of 0.3 requests/min. We set this per-model arrival rate to represent scenarios with infrequent requests to many long-tail models, where model sleeping is required for fast startup [1]. The vanilla-sleep baseline uses a 6 GB sleep-cache budget, reserving the remaining GPU memory for the active model’s weights and KV cache; it keeps as many sleeping vLLM instances as possible under this budget, 8puts a model back to sleep after inference, evicts models using LFU when the budget is exceeded, and cold-starts a model when it is not cached. This 6 GB budget is the largest that preserves vLLM’s default GPU-memory allocation; a larger budget would reduce the KV-cache capacity and thus the supported context length. We use the same vLLM configuration for both P HOS V1 and vanilla sleep. 

Overall performance. Figure 8 shows that P HOS V1 reduces the average end-to-end TTFT from 146.82 s to 19.09 s, an 87.0% improvement over vanilla vLLM instances limited by the sleep-cache budget. It also reduces p50 TTFT from 142.39 s to 14.65 s, while finishing the same workload in a shorter active serving window (578 s vs. 728 s). The improvement comes from caching and sleeping the required models without consuming the large linear GPU-context memory of vanilla sleep mode; the baseline can only keep a limited set of models warm under the memory budget, so requests for uncached models pay cold-start delay and create queueing that dominates end-to-end TTFT. 

Overhead of our technique. To evaluate the inference overhead introduced by our shared context, we report the throughput (tokens per second) of P HOS V1 and vanilla vLLM in the bottom panels of Figure 8. We can see that PHOS V1’s throughput is at least 97.3% of vanilla vLLM’s, indicating that the overhead introduced by the shared context is small. 

4.2 GPU context memory reduction and startup performance 

Figure 7 (left) evaluates whether P HOS V1 removes the GPU-memory growth that prevents vanilla sleep mode from scaling to many cached models. We use 23 models from Figure 4; model weights are excluded. Figure 7 shows that vanilla sleep consumes 25.67 GiB of GPU memory after caching 23 models, whereas P HOS V1+sleep uses only 0.49 GiB, reducing the memory footprint by 98.1%. The savings come from sharing the CUDA context and deduplicating common kernel binaries in the context service instead of letting each sleeping engine hold a private GPU context. Figure 7 (right) further evaluates whether P HOS V1 preserves the low wake-up latency of sleep mode while adding a context service connection and API-remoting layer. We use 16 models and compare cold start, waking up a sleeping vLLM model, P HOENIX OS, and P HOS V1. Figure 7 shows that P HOS V1 keeps startup latency comparable to vanilla sleep, averaging 4.12 s across 16 models, compared with 4.89 s for vanilla sleep and 24.41 s for cold start. Startup remains low because the expensive control-plane context is already available in the service, and the per-model cost of connecting to the context service is small, averaging 72 ms. 

# 5 Discussion 

This section discusses several assumptions and limitations of P HOS V1. First, P HOS V1 assumes that engines sharing a CUDA context are trusted. This assumption applies to model-as-a-service deployments [1], where the service provider manages the engines that serve different models. Sharing a context across untrusted engines is outside the scope of our work. Second, P HOS V1 uses API remoting to implement context sharing, which may introduce inference overhead. This implementation choice allows P HOS V1 to share a context without modifying NVIDIA’s closed-source CUDA driver. Implementing context sharing directly in the driver could avoid the remoting overhead. Finally, P HOS V1 does not support CUDA graphs. Checkpointing and restoring these graphs requires preserving or reconstructing the device pointers and kernel references embedded in graph nodes, as discussed in prior work [23, 24]. We leave support for CUDA graphs to future work. 

# 6 Related Work 

Fast startup for serverless and LLM serving. Prior work accelerates serverless container startup through caching, checkpoint/restore, and remote fork, reusing initialized execution environments [25–27]. Related techniques accelerate VM startup [28] and GPU checkpoint/restore [11, 29]. For LLM serving, ServerlessLLM exploits storage locality for fast parameter loading [30]. BlitzScale combines network transfer and cooperative execution for fast autoscaling [4], and FaaSwap swaps weights under SLO constraints [31]. Medusa and Foundry accelerate CUDA graph setup through offline materialization [23, 24]. These approaches reduce parameter-loading costs or reconstruct selected execution state, complementing P HOS V1’s deduplication of resident GPU context across sleeping engines. Model sleeping in vLLM/SGLang and Aegaeon [1, 6] avoids startup overhead but retains a separate GPU context for each model (§2). 9OS primitives for GPUs. NVIDIA MPS supports concurrent CUDA processes through shared scheduling re-sources [32]. P HOS V1 instead targets GPU-context deduplication across sleeping engines for fast scale-up. MIG partitions a GPU into isolated compute and memory instances [33], whereas we target serving workloads that use a full GPU for the active model. TGS shares GPUs across containers through rate control and unified-memory oversubscription [34]. REEF provides microsecond-scale kernel preemption; Paella offers software-defined GPU scheduling; and XSched extends preemptive scheduling to diverse XPUs [35–37]. GPU API remoting and virtualization decouple applications from physical devices [7, 8]. P HOS V1 builds on API remoting to provide GPU-context deduplication across sleeping models. 

# 7 Conclusion 

We contribute GPU-context deduplication, the first technique that lets a single server keep many models asleep for fast autoscaling without paying a linear GPU memory tax. The key insight is that the GPU contexts of sleeping models contain largely duplicate components that can be shared across models through a central daemon, transparently to existing inference engines. Our evaluation shows that P HOS V1 preserves the fast scale-up of model sleeping while substantially reducing its memory footprint, improving end-to-end multi-model serving performance.
