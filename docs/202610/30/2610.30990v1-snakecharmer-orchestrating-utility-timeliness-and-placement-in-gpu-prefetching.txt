# SnakeCharmer: Orchestrating Utility, Timeliness, and Placement in GPU Prefetching 

Yuhan Tang †, Tiejun Li †*, Jianmin Zhang †*, An Hu †, Guangyu Sun ‡,Sheng Ma †, Yiqun Lang †, Hanqing Li †, Siqing Fu †† College of Computer Science and Technology, National University of Defense Technology, China Email: {tangyuhan, tjli, jmzhang, huan19, masheng, lyq, lihanqing23013, fusiqingnudt }@nudt.edu.cn

Abstract —GPUs rely on massive thread-level parallelism to tolerate long memory latency, yet they still suffer severe stalls when many warps simultaneously wait for data from the memory system. Address-prediction-based GPU prefetchers can mitigate such stalls, but accurate prediction alone does not guarantee per-formance improvement: a predicted prefetch becomes beneficial only if it is worth issuing, arrives at the right time, and is re-tained without harmful interference. Because these requirements interact, optimizing any single dimension in isolation can simply move the bottleneck to another. We capture these requirements with a predicted-prefetch-to-realized-benefit perspective and propose SnakeCharmer, a uni-fied backend prefetch-control framework for address-prediction-based GPU prefetchers. SnakeCharmer separates address predic-tion from prefetch realization: the frontend predictor generates prefetch candidates, while the backend control path jointly con-trols utility, timeliness, and placement by determining whether each candidate should be issued, when it should be issued, and where the returned data should be retained. SnakeCharmer re-alizes this control path with zero-value-aware filtering for utility, hierarchical feedback-driven distance tuning for timeliness, and a register-assisted prefetch buffer for placement. We design and implement SnakeCharmer primarily on top of Snake, and adapt the same backend-control principles to APOGEE to demonstrate that SnakeCharmer’s benefits are not limited to a single frontend predictor. On an A100 GPU model, SnakeCharmer improves performance/energy efficiency by 12.8%/20.8% over Snake and by 1.7%/3.2% over APOGEE, with modest hardware overhead. 

Index Terms —GPU, prefetching, register file, L1 cache. 

I. I NTRODUCTION 

Modern GPUs rely on massive thread-level parallelism (TLP) to tolerate long memory access latency [1]–[4]. By maintaining many active warps on each streaming multipro-cessor (SM), the warp scheduler can switch to another ready warp when the current one stalls on a memory request, thereby overlapping memory latency with useful computation [5]– [9]. However, as the gap between GPU compute throughput and memory-system latency continues to widen, TLP alone is increasingly insufficient to fully hide long-latency accesses [3], [10]–[13]. When many resident warps simultaneously wait for data from the L2 cache or off-chip memory, the SM can run out

of ready warps and incur substantial idle cycles, leading to un-derutilized compute resources and degraded performance [14]– [18]. To mitigate such exposed memory latency, prior work [19]– [21] has explored address-prediction-based GPU hardware prefetching. These prefetchers typically have a logically sep-arable frontend/backend organization: a frontend predictor generates prefetch-address candidates by exploiting regular relationships among memory addresses, while a backend con-trol path determines how these candidates are issued and managed. This scope differs from scheduling-aware prefetch-ers [22]–[24] whose candidate generation is tightly coupled with warp/CTA scheduling decisions. However, while accurate address prediction is necessary for prefetching, it is not sufficient to guarantee performance improvement, especially in GPUs where many warps concurrently contend for limited cache capacity, MSHR entries, queues, bandwidth, and on-chip buffering resources. As a result, the benefit of a predicted prefetch depends not only on whether a future address can be identified, but also on whether the candidate is worth issuing, when it should be issued, and where the returned data should be retained. We refer to these requirements as 

utility , timeliness , and placement . In this work, utility captures whether a candidate is likely to fetch non-zero data rather than low-utility all-zero data; timeliness captures whether the data arrives before, but not too long before, its demand use; and placement captures whether the data can be retained without displacing demand-fetched cache blocks. Although prior address-prediction-based GPU prefetchers incorporate mechanisms related to these requirements, they typically optimize only one aspect [19]–[21]. This partial treatment is insufficient because utility, timeliness, and place-ment interact. Utility alone cannot replace timeliness control, because even a candidate worth issuing provides little benefit if it arrives too early or too late relative to its demand use. Timeliness alone cannot replace placement management, because even a well-timed prefetch may displace demand-fetched data if inserted into a highly contended cache. Place-ment alone cannot replace utility filtering, because low-utility prefetches may already consume bandwidth, MSHR entries, queues, and on-chip buffering resources before their data is retained. Thus, optimizing only one dimension can simply arXiv:2610.30990v1 [cs.AR] 22 Oct 2026 move the bottleneck to another. This motivates a predicted-prefetch-to-realized-benefit perspective, as illustrated in Fig. 1, which views prefetching as a conversion process in which predicted prefetches must satisfy utility, timeliness, and place-ment requirements before they become realized performance benefits. Motivated by this perspective, we propose SnakeCharmer ,a predictor-agnostic backend prefetch-control framework for address-prediction-based GPU prefetchers. SnakeCharmer separates address prediction from prefetch realization: the frontend predictor generates candidates, while the backend control path determines whether, when, and where each can-didate should be handled so that it can turn into a realized benefit. Because SnakeCharmer operates on prefetch candi-dates rather than on a particular prediction algorithm, it can be integrated with other address-prediction-based prefetchers through only lightweight frontend-specific adaptations, such as candidate metadata and the prefetch-generation interface. We instantiate SnakeCharmer primarily on Snake [19] and further demonstrate its portability by adapting it to APOGEE [20]. SnakeCharmer implements this backend with three mech-anisms. To improve utility, zero-value-aware filtering sup-presses prefetches likely to fetch all-zero data before they consume memory-system resources. To improve timeliness, a hierarchical feedback-driven distance tuner adjusts prefetch distance according to warp execution progress. To improve placement, a register-assisted prefetch buffer opportunistically repurposes idle register capacity to retain prefetched data out-side the highly contended L1 cache. On an A100 GPU model, SnakeCharmer improves performance and energy efficiency by 12.8%/20.8% over Snake and 1.7%/3.2% over APOGEE, showing that its benefits are not limited to a single frontend predictor. A. GPU Hardware Prefetching 

Massive warp concurrency is the primary latency-hiding mechanism in GPUs, but it is fundamentally reactive: a de-mand miss first stalls the issuing warp, and the warp scheduler then attempts to issue another ready warp [1]–[4]. Prior work improves this mechanism by better organizing warp scheduling or expanding the effective warp pool, including two-level warp scheduling [5], criticality-aware scheduling [7], [8], virtual threads [25], pre-execution [26], and lightweight out-of-order execution [15]. These techniques reduce exposed memory latency by providing more ready work to the scheduler, but they remain limited when many resident warps simultaneously wait for long-latency memory accesses [26], [27]. In this regime, thread-level parallelism alone cannot fully hide mem-ory latency, leading to idle execution resources, performance loss, and higher power consumption [14]–[18]. GPU hardware prefetching [19]–[21], [23], [24] comple-ments warp-level latency hiding by acting before a demand miss becomes critical. Instead of waiting for a demand access to stall a warp, a hardware prefetcher issues predictable future memory requests in advance, allowing them to over-lap with other warps’ execution or otherwise idle memory-system windows. Prefetching can therefore provide additional benefit when future accesses are predictable and warp-level concurrency alone is insufficient to cover long-latency misses. However, prefetching is not always effective: when latency is already hidden by available warps or when access patterns are difficult to predict, it may provide little or even negative benefit.

Prior GPU hardware prefetching has largely focused on improving address predictability. Snake [19] is a state-of-the-art GPU hardware prefetcher, and its overall architecture is shown in Fig. 2. The Head Table, indexed by warp ID, records the most recently executed load PC and its corresponding memory address for each warp, thereby capturing address changes between load instructions. The Tail Table, indexed by load PC, organizes and stores observed stride informa-tion, including intra-warp strides, inter-warp strides, inter-PC strides 1, and their training states, to determine whether a stride pattern is stable enough to be used for prefetching. The Throttle Engine controls prefetching aggressiveness based on

the available L1 cache space and current memory bandwidth utilization. When prefetching causes cache space to become insufficient or memory bandwidth to become saturated, it pauses or limits the prefetch requests issued by Snake. Using these structures, Snake supports three prediction patterns: (1) intra-warp prefetching, which predicts addresses across future iterations of the same load within a warp; (2) inter-warp prefetching, which enables leading warps to prefetch data for lagging warps along the same instruction stream; and (3) inter-PC prefetching, which captures correlations across load PCs. These three patterns substantially improve address prediction coverage and accuracy over earlier GPU prefetchers. However, strong address prediction alone does not guarantee speedup, as in cache-constrained, highly concurrent GPUs, prefetches can increase pollution and contention for limited cache and memory-system resources, which motivates backend control over predicted candidates—whether to issue them, when to issue them, and where to retain the returned data—and we quantify these limitations on Snake to show that the key challenge is converting predicted prefetches into realized performance benefits. A demand block refers to a 32B sector fetched by a demand load miss rather than by a prefetch request. Utility. In this paper, we define the utility dimension with respect to whether a predicted prefetch fetches zero-valued data. Specifically, we treat prefetches for zero-valued data as a low-utility case and focus on suppressing such prefetches. This definition is motivated by the fact that, although zero values can be represented compactly in a zero-compressed cache [28]–[30], prefetching such data still incurs cache ac-cesses and consumes bandwidth and buffering resources. Timeliness. Even correctly predicted prefetches may arrive too early or too late to hide latency. We define a prefetch as too late if its demand load occurs before the prefetched block becomes available, and as too early if the block arrives in the L1 cache but is evicted or no longer retained before the demand load. Fig. 4 shows the timeliness distribution of Snake-generated prefetches that are eventually consumed by demand loads. Among these consumed prefetches, 48.3% arrive on time, 28.7% arrive too early, and 23.0% arrive too late. Prefetches that are never consumed are excluded from this timeliness distribution and are captured separately by the accuracy metric. These results show that even correct predictions often fail to translate into effective latency hiding. This mistiming is difficult to avoid with a fixed prefetch distance because, on GPUs, the same prefetch distance does not imply the same interval from prefetch issuance to the consuming demand load. This interval depends on inter-vening computation, memory dependences, warp scheduling, and memory-system contention [20], [21], [31], [32], so a fixed prefetch distance can produce very different timeliness outcomes across applications. b+tree pf hwt sc bfs nn mst dotf sto sssp gemm an rn fr AVG 020 40 60 80 100

Placement. In a conventional GPU memory hierarchy, prefetched blocks are typically inserted into the L1 cache, where they compete with demand-fetched blocks for limited cache capacity. We quantify this placement-induced interfer-ence using prefetch-induced demand evictions. The numerator of this metric is measured at L1 sector granularity and counts replacement events in which the evicted victim sector was originally fetched by a demand load, while the incoming sector is brought by a prefetch request. The denominator is the total number of L1 victim-sector evictions. As shown in Fig. 5, prefetch-induced demand evictions account for 34.0% of all L1 victim-sector evictions on average. This indicates that Snake-generated prefetches place substantial pressure on the contended L1 cache, displacing demand data and reducing the realized benefit of prefetching [22]. 

C. Motivation for SnakeCharmer 

The above analysis shows that better address prediction alone is insufficient for effective GPU prefetching. This moti-vates SnakeCharmer, which targets three backend-control di-mensions that determine realized prefetch effectiveness: utility, timeliness, and placement. First, predictable addresses do not always imply useful prefetches. In sparse GPU applications, recurring access pat-terns can repeatedly prefetch zero-valued regions, and deep learning workloads often contain contiguous zero-valued re-gions produced by activation functions such as ReLU [33], [34]. This motivates filtering low-utility candidates before they consume cache, queue, MSHR, and bandwidth resources. Second, fixed prefetch distances are poorly matched to GPU execution because the same logical distance can correspond to different time-to-use intervals under warp scheduling, memory dependences, intervening computation, and memory-system contention. This motivates runtime feedback that adapts prefetch distance to dynamic consumption behavior. Third, placing all prefetched data in the L1 cache increases contention with demand-fetched blocks and can evict useful data before consumption. At the same time, GPU register files often contain idle capacity that cannot improve occupancy due to CTA-level resource granularity, providing an opportunity to buffer prefetched data outside the contended L1 cache. A GPU application consists of one or more kernels. For each kernel, the CUDA compiler toolchain records in the kernel metadata the number of registers statically allocated per thread, which determines the fixed per-thread register allocation used when the kernel is launched. This value, together with shared-memory usage, thread limits and CTA-slot limits, determines the maximum theoretical CTA residency on each SM. Register capacity improves CTA residency only if all resources required by an additional full CTA are simultaneously available. Thus, leftover registers are useful for occupancy only when there is also sufficient shared memory, thread capacity and CTA-slot capacity. When another resource limits occupancy, or when the remaining registers are fewer than the register demand of the next CTA, the leftover registers cannot admit another CTA and therefore cannot be used to increase residency [25], [35]. Therefore, underutilized registers are common. Fig. 6 quantifies this effect by reporting the average idle register capacity per kernel for each evaluated application, assuming a 256 KB register file per SM. The figure shows that at least 8 KB of register-file capacity remains idle across all evaluated applications, with an average of 21.0 KB idle. This unused capacity motivates using idle register-file capacity as an auxiliary destination for prefetched data, allowing prefetched blocks to be buffered outside the L1 cache when possible. b+tree pf hwt sc bfs nn mst dotf sto sssp gemm an rn fr AVG 016 32 48

III. S NAKE CHARMER DESIGN 

SnakeCharmer consists of three main components (Fig. 7), each targeting one backend-control dimension. First, Snake+ 

extends the Snake address-prediction frontend with zero-value confidence tracking to filter low-utility candidates. Second, the 

SnakeCharmer Controller (SCC) uses runtime timeliness feed-back to tune prefetch distance and gate candidate prefetches. Third, the Prefetch Remapping Table (PRT) buffers prefetched data in idle registers, reducing L1-cache interference from prefetched blocks. SnakeCharmer is designed and evaluated at the maximum warp residency of our GPU configuration, i.e., 64 warps or 2048 threads per SM. Its overhead is fixed per SM rather than per thread: the added structures are fixed-size tables totaling only 2.7 KB per SM (see §V-F). Dynamic accesses are bounded by the SM warp-issue and LD/ST pipeline bandwidth, not by the number of resident threads. Prefetch generation and SCC decisions are off the demand critical path; the only demand-side access is the PRT lookup. Snake+ Prefetcher

When a load instruction is executed, the request is for-warded to Snake+ via the Load/Store (LD/ST) unit. Snake+ uses the Head Table and SC-Tail Table to track memory access patterns and generate candidate prefetch requests, while the Throttle Engine preserves Snake’s protection against excessive cache and bandwidth pressure. These candidates are then sent to the SCC, which issues them only if they satisfy the confidence and timeliness criteria. If a prefetch is issued, the PRT is probed first; if an available or victim entry exists, the returned data is buffered in idle registers, otherwise it is placed in the L1 cache. On a later demand load, the PRT is checked first, and a hit is served directly from the register file; otherwise, the request proceeds to the L1 cache, where it may hit prefetched data, demand data, or zero-value data managed by the zero-compressed cache. The zero-compressed cache stores compact metadata in a fixed number of L1 cache lines, with each bit indicating whether a corresponding 4B word is all zero. 

A. Snake+ Prefetcher 

Snake+ consists of a Head Table, an SC-Tail Table, and a Throttle Engine. The Head Table records, for each warp, the PC of the most recently executed load and its memory access address, indexed by warp ID (WID). On each new load, it updates the corresponding entry and forwards both the previous and updated information to the SC-Tail Table. The 

SC-Tail Table , indexed by PC1 and PC2, stores the detected inter-PC, intra-warp, and inter-warp stride patterns together with their training confidence (T1, T2, T3) and zero-value confidence (Z1, Z2, Z3). The Throttle Engine monitors L1 capacity and bandwidth utilization and disables prefetching when resources are insufficient. We empirically configure all candidate prefetch requests to share a single 128-entry prefetch queue. 

Snake+ without zero-value confidence . Fig. 8 illustrates the training and prefetching flow of Snake+ before adding zero-value confidence. For clarity, we assume that one warp is issued at each time step, and v(t) denotes that a value becomes 

v at time t. In this specific example, a prefetch is generated once the corresponding training confidence reaches 3. Snake+ learns and uses three types of stride patterns: (1) Inter-warp: when consecutive warps execute the same load PC, Snake+ compares their access addresses to learn a stride across warps. For example, warps 1 and 2 access PC 520 at addresses 1000 and 1100, respectively, producing an inter-warp stride of 100; when warp 3 later accesses 1200, T3 is increased and Snake+ prefetches address 1300 for warp 4. (2) Inter-PC: when a warp transitions between two load PCs, Snake+ records the address delta as a PC-chain stride. For example, when warp 1 moves from PC 520 at address 1000 to PC 540 at address 1500, Snake+ records a stride of 500 for the chain PC 520 →PC 540. (3) Intra-warp and combined prefetching: when warp 1 later returns to PC 520 and accesses address 2500, Snake+ can use the learned inter-PC stride to prefetch 2500 + 500 = 3000 ,while also using the inter-warp stride to prefetch addresses 2600, 2700, and 2800 for lagging warps 2, 3, and 4. We set the maximum prefetch distances for inter-PC, intra-warp, and inter-warp patterns to 10, 8, and 63, respectively. 

Snake+ with zero-value confidence . Snake+ uses per-pattern zero-value confidence to filter low-utility prefetches. Each SC-Tail Table entry maintains three 2-bit counters, Z1, Z2, and Z3, for inter-PC, intra-warp, and inter-warp patterns, respectively. Each counter is initialized to 0 and ranges from 0 to 3. A candidate prefetch is suppressed only when the counter associated with its source pattern reaches 3, ensuring that suppression requires repeated zero-value evidence. For an issued prefetch, Snake+ updates the corresponding counter when the candidate block either returns to the L1 cache or already resides in the L1 cache. The counter is incremented if the accessed data is all zero at the tracked access granularity, and decremented otherwise, while remaining bounded within its 2-bit range. Fig. 9 shows an example where the inter-PC candidate is suppressed because Z1=3, while the inter-warp candidate is issued because Z3=0. For a suppressed pattern, Snake+ starts a suppression timer and resets the corresponding zero-value confidence counter to 0 after 128 cycles. We choose 128 cycles because it is sufficient to cover a scheduling pass over the 64 resident warps in our model, thereby avoiding pro-longed suppression after the data phase changes. This update-and-timeout policy reduces false suppression and allows fast recovery when the data phase changes. Zero-value filtering and zero-compressed caching are com-plementary because they act at different points in the prefetch lifetime. Zero-compressed caching is reactive: it is consulted only after a prefetch request has been issued and has entered the cache hierarchy. As a result, identifying a zero-valued block still requires a cache access and consumes cache-side resources, such as cache ports and cache data bandwidth. Once the cache identifies the requested data as all zero, it can avoid accessing lower cache levels or memory. In contrast, zero-value filtering is proactive: it operates before a candidate prefetch is issued, using zero-value confidence to predict whether the candidate is likely to fetch a zero-valued block. When the confidence is high, SnakeCharmer suppresses the prefetch entirely. Thus, zero-value filtering reduces redundant prefetch requests at their source, avoiding the cache accesses and cache-side resource usage that zero-compressed caching alone cannot eliminate. 

B. SnakeCharmer Controller 

As shown in Fig. 10, the SnakeCharmer Controller (SCC) improves prefetch timeliness by adapting prefetch distance from runtime feedback. It consists of a hierarchical Adaptive Window Tuner (AWT) and a Scoring and Gating Unit (SGU). The AWT has an L1 table indexed by SC-Tail rows and an L2 table indexed by prefetch type. L1-AWT tracks on-time, too-early, and too-late outcomes and learns a Local Best Dist after 31 feedback samples; L2-AWT provides a Global Best Dist for cold-start or infrequently executed patterns. Every 15 feedback events, the best distance is updated: it is kept if on-time outcomes exceed 50%, otherwise shifted by one toward the dominant error. The Prefetch Eviction Buffer (PEB) is a 64-entry table that records prefetched blocks evicted before first use, en-abling SCC to distinguish too-early but eventually demanded prefetches from never-used ones. Training feedback is ob-tained as follows: a hit in the PRT or L1 cache is on-time, a hit in the PEB is too-early, and a hit in the MSHR is too-late. C. Prefetch Remapping Table 

SnakeCharmer uses a Prefetch Remapping Table (PRT) to buffer prefetched data in idle physical registers rather than always placing it in L1. PRT reserves registers for returning prefetches, allowing later demand loads to read them directly from the register file (RF). Our simulator explicitly models these RF bank and port conflicts. Motivated by Fig. 6, which shows that each evaluated application provides at least 8 KB of idle register capacity on average across its kernels, we conservatively configure PRT to use at most 8 KB of idle register capacity, corresponding to 64 PRT entries. SnakeCharmer does not assume that every kernel always provides 8 KB of idle register capacity: if less capacity is available, only a subset of entries is enabled; if none is available, PRT is disabled. A 1-bit enable flag ( EN )indicates whether a PRT entry is active. This ensures that PRT uses only registers not used by any active thread. Each PRT entry contains a tag, four physical base indexes, and four state fields, as shown in Fig. 11. The tag records the memory address of the prefetched data. Each physical base index points to eight consecutive idle physical registers, which together store 32B, matching one memory transaction. The state fields track the status of the prefetched data. Initially, all four slots in each entry are INVALID (00). When a prefetch is issued, the corresponding slot is allocated and transitions to WAITING (01). Following prior work [36], [37], we assume that physical registers are allocated sequentially and that unallocated registers remain idle throughout the current kernel. When the prefetched data returns, it is written into the reserved registers and the slot transitions to READY (10). After the data is consumed by a demand load, the slot transitions to CONSUMED (11), and the corresponding block is inserted into L1 to preserve normal demand caching behavior. The L1 refill after consumption is not on the critical path of the triggering demand load. The demand load reads the prefetched data from the RF first, and the data is written back to L1 only afterward. Thus, the refill does not delay the triggering demand load, although it still consumes L1 bandwidth in our model. PRT uses round-robin replacement, prioritizing entries with CONSUMED slots; if a WAITING slot is evicted, the returning data is discarded. The movement of prefetched data through the RF reuses existing datapaths and does not require a new dedicated datapath. Specifically, (1) when prefetched data returns from the memory subsystem to the SM, it is written into reserved registers through the existing LD/ST fill/writeback path; (2) when a demand load consumes prefetched data from the RF, the data is read through the existing RF read path and written back to the destination register through the normal load writeback path; and (3) when consumed prefetched data is sent toward L1, it reuses the existing LD/ST data-movement path from the RF toward the memory hierarchy, rather than requiring a new dedicated RF-to-L1 datapath. Consequently, PRT integration mainly requires lightweight control logic for path selection, state updates, and invalidation. To maintain coherence, PRT adopts a single-placement policy upon prefetch fill: if a PRT entry is available, the prefetched block is placed in the RF; otherwise, it is placed in L1. Thus, a prefetched block does not exist as two inde-pendently valid copies in both PRT and L1. Store requests also probe the PRT tags. If a store address matches a PRT tag, the corresponding slot transitions to the INVALID state, preventing subsequent demand loads from reading stale data from PRT. We model both register-bank conflicts and invalida-tion overhead in AccelSim, and include both in the evaluation results. IV. E XPERIMENTAL SETUP

B. Performance and Energy Efficiency Analysis 

Performance is the end-to-end manifestation of realized prefetch effectiveness. Fig. 13 (top) shows the performance of all evaluated systems on the A100 architecture, normalized to the SK baseline. We make four key observations. First, SK+SC achieves the best overall performance, im-proving instructions per cycle (IPC) by 12.8% on average across all applications and by 14.8% across high-sparsity ap-plications. These results show that SnakeCharmer consistently increases the realized value of predicted prefetches, with larger gains when sparsity is higher. Second, each proposed mechanism is effective in isolation. 

SK+ZF , SK+SCC , and SK+PRT improve performance by 6.0%, 7.0%, and 3.7% on average, respectively. In particular, 

SK+ZF improves performance by 7.6% on high-sparsity appli-cations, confirming that zero-value-aware filtering is especially effective when zero-valued data is frequent. Third, SnakeCharmer’s main benefit comes from preventing bottleneck shifting across utility, timeliness, and placement, rather than optimizing any one dimension in isolation. Im-proving only utility does not eliminate mistimed prefetches, improving only timeliness does not prevent cache contention, and improving only placement does not recover bandwidth wasted on low-utility requests. This interaction is evident in the ablation results: SK+ZF+SCC , SK+SCC+PRT , and 

SK+PRT+ZF improve performance by 10.6%, 9.9%, and 9.1%, respectively, while the full design further raises the gain to 12.8%. Thus, SnakeCharmer’s advantage comes from jointly orchestrating all three backend control dimensions under a single framework. Fourth, SnakeCharmer also generalizes beyond the Snake frontend. Replacing APOGEE’s original backend control path with SnakeCharmer improves performance by 1.7% on aver-age. The gain is smaller than with Snake because APOGEE’s frontend exposes fewer sufficiently accurate and high-coverage prefetch opportunities to the backend. Nevertheless, the con-sistent improvement shows that SnakeCharmer is not specific to Snake and can also improve the realized effectiveness of prefetches generated by APOGEE. To evaluate the impact of SnakeCharmer on overall GPU en-ergy efficiency, we calculate performance per watt, i.e., overall GPU IPC divided by average GPU power consumption, for all systems. Fig. 13 (bottom) presents the results, normalized to the energy efficiency of the SK baseline. SK+SC improves energy efficiency by 20.8% on average across all applications and by 24.9% across high-sparsity applications. In comparison, 

SK+ZF , SK+SCC , and SK+PRT improve energy efficiency by 9.7%, 10.9%, and 6.0%, respectively, while SK+ZF+SCC ,

SK+SCC+PRT , and SK+PRT+ZF achieve 16.5%, 14.9%, and 14.1% gains. Replacing APOGEE’s original backend with SnakeCharmer also improves energy efficiency by 3.2%. These gains come from two reinforcing effects: higher IPC increases useful work per unit energy, while SnakeCharmer’s utility- and timeliness-aware control suppresses unnecessary prefetches and reduces wasted cache, bandwidth, and memory-system activity, thereby lowering power consumption.

E. Upper-Bound and Oracle Studies 

We use oracle studies to quantify the remaining optimization opportunities. Note that these oracles are not practical designs; unless otherwise specified, they operate on the same prediction stream generated by the Snake frontend. Unlike the other oracles, O-L1 is not constrained by Snake’s prediction stream and therefore provides an upper bound on the benefit of eliminating global-memory access latency. Software-Managed Prefetching on NVIDIA GPUs . Prior work has explored hardware GPU prefetching [19], [20], [23], [24], [52], while NVIDIA does not publicly document an L1 hardware prefetcher in its GPUs. NVIDIA instead supports software-managed prefetching, where programmers stage data into shared memory ahead of use [53], with recent architec-tures adding asynchronous global-to-shared copies to better overlap data movement and computation [54], [55]. Such techniques require explicit orchestration of data movement, synchronization, and shared-memory capacity, and work best when access patterns or reuse are known ahead of time. SnakeCharmer operates at a different level by transparently controlling hardware-generated prefetch candidates and their placement, so it can target remaining prefetch opportunities not captured by software staging. Consistent with this, dotf 

and sto already use software-managed prefetching yet still benefit from SnakeCharmer. 

Scheduling-Aware Hardware Prefetchers . SnakeCharmer is primarily designed for address-prediction-based GPU prefetchers whose frontend can expose candidate prefetches to a backend control path. Scheduling-aware prefetchers, such as APRES [23], CAPS [24], and orchestrated scheduling and prefetching [22], are less suitable for direct integration because their candidate prefetches are not generated inde-pendently of warp/CTA scheduling. For example, APRES forms warp groups based on recently executed load PCs and generates prefetches for other warps in the group after observing the leading warp, CAPS obtains useful candidates only after scheduling leading warps early to compute per-CTA base addresses, and orchestrated scheduling creates can-didate prefetches by placing consecutive warps in different scheduling groups so that earlier groups can prefetch for later groups. Applying SnakeCharmer to these designs would therefore require redesigning the scheduler-prefetcher inter-face, rather than simply replacing a backend prefetch-control path. In this work, we therefore focus on address-prediction-based prefetchers such as Snake and APOGEE, while leaving integration with scheduling-aware prefetchers as future work. 

Register-Capacity-Based Storage and Prefetching . Prior work has explored using register or local storage capacity for cache-like storage and prefetching [36], [52], [56]. Gebhart et al. [56] and Linebacker [36] repurpose local/register-file capacity to increase effective cache-like storage, which can reduce cache pressure and preserve useful lines. These designs, however, primarily target capacity management for demand or victim data; they do not consider the placement of prefetched data or its interaction with prefetch utility and timeliness. Spare-register-aware prefetching [52] uses unallocated reg-isters as destinations for prefetched values in graph workloads and later replaces the corresponding loads with register moves. This mechanism must ensure that the prefetched value matches the value that the later load would have returned before the load can be safely converted into a move. Consequently, it is tied to identifiable loop-based dependent load-pair patterns and does not provide a hardware-managed buffer for address-prediction-based prefetches. These mechanisms show that register/local capacity can pro-vide an alternative placement target, but placement alone is not sufficient: low-utility prefetches can still consume bandwidth and storage, while poorly timed prefetches can still arrive too early or too late. SnakeCharmer therefore treats placement as one component of prefetch realization and coordinates it with utility filtering and timeliness control in a unified backend framework for address-prediction-based GPU prefetchers. 

CPU Prefetch-Timing Mechanisms . CPU prefetchers use runtime feedback to adapt prefetch distance [57], [58]. These mechanisms typically operate on one or a few hardware threads per core, so logical prefetch distance often has a relatively stable relationship with consumption time. This assumption breaks down on GPUs, where many warps are interleaved and dynamically scheduled on each SM; a warp may issue a prefetch, be descheduled, and consume the data much later while other warps make progress. As a result, the same logical distance can produce different real-time lead times across warps and execution phases. SnakeCharmer adapts feedback-driven timing to this GPU setting by associ-ating feedback with warp and load-PC context, allowing the L1/L2-AWT hierarchy to learn distances for individual access patterns rather than relying on a single global setting. 

GPU Prefetch-Timing Mechanisms. MT-prefetching [21] throttles prefetching using feedback such as early eviction, while APOGEE [20] adjusts prefetch distance for FOA/TIA patterns. Both mainly target timeliness. SnakeCharmer treats timeliness as one stage of prefetch realization: its two-level tuner learns pattern-local and global timing behavior and co-ordinates with zero-value filtering and PRT-based placement. With APOGEE’s FOA/TIA frontend unchanged, replacing the full backend improves performance by 1.7%, showing the effectiveness of the unified backend. 

Zero-Value Caching. Zero-value caches compactly repre-sent all-zero blocks to reduce cache pressure and memory traf-fic [28], [29], and LazyGPU [30] combines zero-value caching with lazy execution to eliminate some zero-related memory re-quests. SnakeCharmer uses zero-compressed caching as com-mon support across all evaluated configurations, following the same zero-value caching idea as LazyGPU. SnakeCharmer’s new mechanism is proactive zero-value-aware filtering, which suppresses likely-zero prefetches before they consume queues, MSHRs, bandwidth, or cache resources. VII. C ONCLUSION 

This paper presents SnakeCharmer, a predictor-agnostic backend for address-prediction-based GPU prefetchers. It jointly controls utility, timeliness, and placement through zero-value-aware filtering, feedback-driven distance tuning, and register-assisted buffering, improving performance/energy efficiency by 12.8%/20.8% over Snake and 1.7%/3.2% over APOGEE on an A100 GPU model.
