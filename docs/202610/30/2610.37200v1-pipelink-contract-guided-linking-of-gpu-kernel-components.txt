## ABSTRACT 

The fastest machine-learning kernels are compositions of components, such as loaders, matrix-multiply mainloops, epilogues and communication stages, that run concurrently on one GPU streaming multiprocessor and share its on-chip memory, barriers, warps and registers. Because these components hard-code where they sit in this shared space, they cannot be compiled, shipped or replaced on their own: combining components from different sources means forking them by hand or keeping them in separate kernels. We present PipeLink, a contract-guided linker for GPU kernel components. Each component is compiled separately into an LTO object that carries a contract stating what it requires and what it promises; PipeLink checks the contracts against each other, relocates every component by solving one joint placement of the SM’s resources, and generates the transfers between them, and the vendor LTO backend folds the result into constants. Across 51 configurations on Hopper and Blackwell GPUs, linked kernels run within 0.2% of the same sources compiled as one unit. Linking makes new compositions practical: a CuTe attention operator inside a ThunderKittens decode megakernel speeds up decoding by 2.16 ×, a four-owner MoE training megakernel matches the original monolith, one unchanged attention core yields sparse and context-parallel variants that outperform FlexAttention, vLLM and Transformer Engine, and a GEMM + SwiGLU composition whose consumer serves three GPU architectures runs 1.2 × faster on Blackwell than cuBLAS with a compiled activation. 

## 1 INTRODUCTION 

The fastest machine-learning kernels on modern GPUs are no longer single operators. An attention kernel in the FlashAttention family runs a tile loader, a matrix-multiply mainloop, a softmax stage and an epilogue as groups of warps that execute concurrently and hand tiles to each other through on-chip memory (Shah et al., 2024; Zadouri et al., 2026). Megakernels go further and run an entire decode step or training pass inside one persistent kernel (Spector et al., 2025a; Cheng et al., 2026; Jin et al., 2026; Sul et al., 2026b), and communication-overlapped kernels move data between GPUs while they compute (Chang et al., 2024; Zheng et al., 2025b; Sul et al., 2026a). Each such kernel is a composition of components that cooperate at fine grain on the same streaming multiprocessor (SM). Yet these components cannot be built, shipped or replaced as components. They agree on physical facts that no in-terface records: which bytes of shared memory each one owns, which barriers and warps it uses, how many registers it may hold, and which tile sizes its neighbors schedule against. This paper presents PipeLink , a contract-guided linker for GPU kernel components. Each component is compiled sep-arately into an LTO object that carries its contract. In summary, this paper makes the following contributions: • Component contracts , which state what a concur-rently running GPU kernel component requires and promises, so that it can be compiled, distributed and replaced on its own, without its source (Section 3). • A contract-guided linker that checks contracts against each other, relocates components by jointly solving their placement, and generates the data transfers be-tween them (Section 4). • Zero-cost composition of real ML kernels across libraries, owners and GPU architectures (Section 5). 

## 2 MOTIVATION 

2.1 Anatomy of a Fused Kernel 

Our running example is context-parallel attention on Hopper (Figure 1). Its core is a warp-specialized attention kernel derived from FlashAttention-3 (Shah et al., 2024): a load warp copies query, key and value tiles into shared memory, two consumer warpgroups compute attention with an on-line softmax, and an epilogue warp writes the output. In the context-parallel kernel, two more warps push the local key/value shard to the other GPUs. All twelve warps run PipeLink: Contract-Guided Linking of GPU Kernel Components 

concurrently and hand work to each other through mbarrier rings, named barriers and, across GPUs, readiness counters. They share the SM’s shared memory, barriers, warps and register file, and how much of each a component may use depends on which other components share the thread block. 

2.2 Components Are Absolute-Addressed 

Fused-kernel code today fixes all of these assignments in its source. A FlashAttention (Shah et al., 2024) or CUTLASS (Thakkar et al., 2023) kernel declares one 

SharedStorage struct that lays out every buffer and bar-rier at a constant offset, numbers its named barriers in an enumeration, selects roles by comparing the warp index against constants, and calls setmaxnreg with constant budgets. ThunderKittens (Spector et al., 2025b) megaker-nels (Spector et al., 2025a) likewise compile a fixed page and semaphore layout into every operator. In the vocabulary of linkers, these components are absolute-addressed : they hard-code their positions in an address space that is small, shared and spread over several resource kinds. Absolute addressing is harmless as long as one team owns the whole kernel. It becomes the obstacle as soon as a component is meant to be reused. Components written independently each start at shared-memory offset 0, barrier ID 1 and warp 0, so combining them unchanged collides by construction; someone must re-derive every position with knowledge of all the others. 

2.3 Fork or Split 

Because components cannot be relocated, combining com-ponents from different sources leaves two routes: fork their sources into one kernel, or keep them in separate kernels. 

Fork. Forking merges the sources into one translation unit and re-derives every shared assignment by hand. Megak-ernels take this route: one team owns an entire model step (Spector et al., 2025a; Cheng et al., 2026; Jin et al., 2026; Sul et al., 2026b; Zheng et al., 2026), and adopting an operator from another library means porting it to the megak-ernel’s page, semaphore and instruction conventions; recent work automates the port with coding agents that write a new megakernel per model (Li et al., 2026a; Jaber & Jaber, 2026). New attention variants likewise start as forks of an expert kernel such as FlashAttention (Shah et al., 2024; Zadouri et al., 2026), and systems that move context-parallel communication into the kernel write or modify their own attention kernel (Sul et al., 2026a; Qiang et al., 2026; Hu et al., 2026). Every fork is a new kernel to maintain.

2.4 Symbol Linking Is Not Enough 

CUDA already supports separate compilation: relocatable device code and link-time optimization (LTO) combine in-dependently compiled device functions into one kernel as fast as a single translation unit (Scudiero & Murphy, 2014; Sundaram et al., 2023), and NVIDIA’s own libraries ship LTO fragments for this purpose (NVIDIA, c;b). But de-vice linking resolves symbols : it records which names a fragment defines and needs, and nothing about the warps, shared memory, barriers or registers it occupies, or about the facts its neighbors compiled against. The consequence is silent failure. The four owners of our MoE megakernel (Section 5.3) schedule against each other’s tile geometry (Figure 2). We changed one geometry con-stant of one owner at a time, repacked only that owner, and linked it with the others’ unchanged objects. Device linking accepted all five combinations: three kernels hang, and two complete without error but leave part of their output unwrit-ten. Separately compiled components need an interface that carries what they share, and a linker that acts on it. PipeLink: Contract-Guided Linking of GPU Kernel Components 

## 3 COMPONENT CONTRACTS 

3.1 Components 

A component is a separately compiled part of a fused ker-nel. PipeLink supports three kinds. A role is a group of warps with its own entry function, such as a TMA loader, an MMA mainloop or a communication stage. A callable 

is a device function that runs on its caller’s threads, such as an attention mask, a score modifier or an operator body inside a megakernel interpreter. A tensor producer or con-sumer is a role or callable that exports or imports a tile held in on-chip storage. One source file may define several of these, and a component may be written in plain CUDA, CUTLASS/CuTe, ThunderKittens or TileLang. The author packs each component into a package : an LTO object produced by the vendor compiler, plus a manifest that records its contract. Packing compiles the source twice, once to evaluate the annotations that make up the contract and once to produce the object. PipeLink never reads or rewrites the component’s instructions; to the linker the ob-ject is opaque, and the component can be distributed without its source. The vendor LTO backend, which does see the object’s IR, later optimizes the composed kernel as a whole. We considered composing at two other levels. Compos-ing source or compiler IR, as template libraries and warp-specialization compilers do, gives the composer full freedom but requires every component’s source in one compilation, under one toolchain and one owner. Rewriting compiled machine code would avoid that, but the GPU instruction set is undocumented and changes between generations, and patched binaries miss the cross-component optimizations that make a fused kernel fast. LTO objects sit between the two: they are a supported, stable vendor format, they hide the source, and the backend still optimizes across compo-nent boundaries. 

3.2 Contract Vocabulary 

A contract states what a component requires from the ker-nel it joins and what it promises to the other components (Table 1). Four properties of this vocabulary matter. First, every re-source is claimed by handle , not by address: a claim says how much shared memory, how many mbarrier slots or how many warps a component needs, never where they are. Sec-ond, lifetimes let disjoint uses share storage: a claim may live for the whole kernel, for one phase of a megakernel’s instruction stream, or between two events of a tensor con-nection. Third, synchronization is described by protocol rather than by code: an mbarrier ring states its arrival counts as functions of the participating roles’ widths, its transaction bytes, and which role initializes it, so that two endpoints can be checked for agreement without inspecting either body.

Fourth, facts are typed constants, such as a tile size, that one component owns and others schedule against. A consumer does not compile a fact in: it declares a kernel parameter sourced from the fact, and the linker checks that all decla-rations agree and writes the owner’s value into the kernel’s parameters, so a changed tile size (Figure 2) reaches every consumer without recompiling it. 

3.3 Relocatable Components 

A component reads every link-time decision through a han-dle function : an external device function named after the handle, declared but not defined in the component (Fig-ure 3a, orange). Shared-memory bases, mbarrier slots, named-barrier IDs, warp offsets, ring depths and counter slots are all read this way. The object therefore contains unresolved calls instead of constants, much as position-independent code reads addresses through a table filled in by the dynamic linker. Unlike a table lookup, a handle func-tion costs nothing at run time: the linker defines it to return a constant that LTO folds away (Section 4.3). We need the object to stay unchanged across compositions, the binding to be chosen per composition, and the result to cost nothing at run time; the obvious alternatives each lose one of these. Template or macro parameters fold into constants but require recompiling the component for every composition, and so its source. Passing placements as kernel arguments or through constant memory keeps the object fixed but turns every offset into a run-time load and blocks constant folding in address arithmetic. Relocation entries patched into the binary, as CPU linkers use, do not exist for most of these resources: named-barrier IDs, warp ranges and register budgets are instruction operands or control flow, not addresses. Handle functions keep the object unchanged and still compile to immediates. PipeLink: Contract-Guided Linking of GPU Kernel Components 

3.4 Authoring 

Annotations live in the component’s own source file, next to the code they describe, and are evaluated by the com-piler at pack time. The author states only what the compiler cannot see: semantic promises such as which tile an export carries, which protocol a ring follows, which role initial-izes a barrier, and how long a buffer stays live. Everything the compiler can observe is captured instead of restated. Packing measures the size, alignment and field offsets of pa-rameter and descriptor types, records which device symbols the object defines and needs, reads launch attributes from the compiled object, and fits every enumerated layout map to a closed-form expression, rejecting the package if the fit is not exact. For tensor imports written in TileLang, the frontend captures the consumer’s demand from the layout of its destination fragment, so the author writes no placement facts at all (Fig-ure 3). Optionally, the frontend specializes the consumer to a particular producer by adopting the producer’s published register layout; the result still links with any other producer, but the linker can then choose a direct register copy instead of a staged transfer. Figure 3 compares the two SwiGLU consumers of our GEMM + SwiGLU case study, which import the same ac-cumulator. The CUDA consumer states its contract in 10 device-side annotations spanning 38 lines; the TileLang consumer writes no annotations and 14 lines of frontend calls, which name the export to import and choose the chunk size, specialization and completion policy. The rest is taken from the producer’s contract or captured from the compiled kernel. Both consumers share the same 9 host annotations and host provider; the consumer-specific source is 163 lines in CUDA and 56 in TileLang. Elsewhere in our case studies, a new attention load or com-munication component takes 13–20 annotation statements and a megakernel operator 11–15; the four owners of the MoE megakernel write 327 statements in total, against 3,482 lines of component and host-provider source.

4.2 Relocation as Constraint Solving 

A classical linker relocates sections by concatenating them. That does not work on an SM: its resource spaces are small (one thread block gets at most 227 KiB of shared memory, 32 warps and 16 named barriers) and coupled, because the warps a role occupies decide its register group, register PipeLink: Contract-Guided Linking of GPU Kernel Components 

groups share one register file, and buffers may share storage only when their lifetimes are disjoint. PipeLink instead solves one constraint problem per com-position with an SMT solver (de Moura & Bjørner, 2008). The variables are the base of every claimed handle in every domain, the ring depths left to the linker, and the register budget of every register group. The constraints encode ca-pacity, alignment, exact coverage of the warps by roles, and non-overlap. Two claims may overlap only if their phases are mutually exclusive or their lifetimes on one tensor con-nection are ordered, so an epilogue’s scratch can reuse a mainloop’s operand ring once the accumulator is ready. The objective prefers deeper rings and larger register budgets, then a smaller footprint. The solver is deterministic, so a composition always links to the same placement. A greedy allocator would be simpler, but lifetimes turn place-ment into packing, where the order of placement decides the footprint. In the MoE megakernel, first-fit packing in lexical or decreasing-size order misses the smallest shared-memory footprint, which the solver finds and which leaves 1,440 of 232,448 bytes free. Our compositions have 4–42 handles each; the solver proves every objective optimal within 1.3% of its work limit. PipeLink also never reschedules a component. Warp-specialization compilers choose pipelining and role assign-ment for the whole kernel, but they need the source, and the owners of our components have already tuned their sched-ules for their hardware. Keeping each schedule fixed makes the linked kernel’s performance predictable from its parts and keeps the linker out of the components’ correctness arguments. The vendor backend, not the solver, allocates registers. After the device link, PipeLink reads the linked kernel’s register count and re-solves once if the register groups do not fit; if they still do not fit, the link fails with L-REGS .

4.3 Why Linking Costs Nothing 

The linker emits three pieces of code: handle stubs that define every handle function to return its solved constant, 

call trampolines that connect each call site to the export serving it, and a dispatch kernel that assigns warps to roles and sets each register group’s budget once. All three are compiled to LTO IR and device-linked with the components through nvJitLink (Sundaram et al., 2023). The backend inlines the stubs and folds their constants into the compo-nents’ address arithmetic, so a call such as smem base() 

becomes the immediate 1024 . The result is the code a programmer would get by writing the components into one source file with the same placement. Dispatching through function pointers would be simpler to generate, but indirect calls are not inlined, so constants would not fold and every role would run at the register budget of the most demanding one. 4.4 Generated Tensor Transfers 

A GEMM mainloop leaves its accumulator in tensor mem-ory or in registers, and an epilogue wants each of its threads to hold particular elements. Writing that transfer by hand re-quires knowing the producer’s layout, which is the coupling contracts are meant to remove. Instead, the producer’s export publishes the tile’s placement :where each element lives, as a tensor-memory lane and col-umn, a shared-memory address, or a thread and register. The consumer’s import states its demand : which element each of its threads wants (Figure 4). Both are exact maps fitted at pack time. The linker then tries routes from cheap-est to most general: a read from tensor memory straight into the demanded registers, a direct register copy when placement and demand coincide, a warp-local shuffle, or staging through scratch shared memory that the consumer lends. It checks each candidate against a model of the hard-ware primitives for exact delivery of every element, freedom from races and correct ordering, and lowers the first route that passes to CUDA through TileLang (Wang et al., 2026). Transfers move values exactly and never convert them, and their scratch is an ordinary claim. Two simpler designs were available. Always staging through shared memory works for every pair, but it costs a round trip that the direct routes avoid (Section 5.5). Fixing one exchange layout by convention would make every producer and consumer agree in advance, which is the coupling con-tracts remove. At the other extreme, general program syn-thesis could find cleverer routes, but its results are hard to bound and to check. A short ladder of route shapes, each checked exactly, covers every connection in our case studies. 

4.5 Communication and Host Interface 

Communication stays in component code. A component that moves data between GPUs declares the communication domains it joins, the views it needs of a symmetric allocation the caller lends (peer addresses, a multicast address), and system-scope counters for readiness across GPUs. The linker checks that all owners of an allocation agree on its domain and views, binds counter slots like any other claim, and passes the caller’s addresses to the owners. It does not synthesize collectives: communication protocols are specific to their algorithms (a ring push, a dispatch with routing, a reduce-scatter), and the owners who design them are best placed to implement them. ## 6 RELATED WORK 

We group prior work by where the information needed to compose kernel parts lives (Table 7). 

In one source program. Template libraries such as CUT-LASS (Thakkar et al., 2023) and attention libraries that accept mask and score functions or generate variants from templates (Dong et al., 2025; Ye et al., 2025; Chen et al., 2025; You et al., 2026; Chen et al., 2026a) compose at ex-tension points that their authors designed. Domain-specific PipeLink: Contract-Guided Linking of GPU Kernel Components 

languages such as TileLang (Wang et al., 2026), CuTe DSL (NVIDIA, d), ThunderKittens (Spector et al., 2025b) and Triton (Tillet et al., 2019), and fusion libraries such as FKL (Amoros et al., 2025) and CODA (Guo et al., 2026), compose within one program; sparse-attention ker-nels specialize execution to the selection pattern in the same way (Zhao et al., 2026; Li et al., 2026b; Liu et al., 2026). PipeLink instead links components that different authors compiled separately, and can link components written with these tools. 

In compiler IR. Warp-specialization compilers partition a kernel into roles and synchronize them: Tawa (Chen et al., 2026b) uses asynchronous references as channels, Twill (Soi et al., 2026) solves pipelining and warp special-ization jointly, Cypress (Yadav et al., 2025) derives data movement from a mapping, and TLX (Guan et al., 2026) and Gluon (Triton contributors) expose roles and memory to the programmer. Layout systems (Zhang et al., 2026; Zhou et al., 2026; Hou et al., 2026) represent the layouts that con-nect operations. These compilers own and may reschedule the whole kernel; PipeLink keeps each component’s com-piled schedule and works over declared interfaces of opaque objects. 

In runtime task graphs. Megakernel systems sched-ule operators or tiles across SMs in one persistent kernel: MPK (Cheng et al., 2026) and Event Tensor (Jin et al., 2026) compile models into in-kernel task graphs, and other work tunes, searches or generates megakernel schedules, also with coding agents (Spector et al., 2025a; He et al., 2026a;b; Jaber & Jaber, 2026; Dong et al., 2026; Chowdhary et al., 2026; Li et al., 2026a; Yao et al., 2026). These systems decide which task runs where; PipeLink decides how sep-arately compiled components share one SM, so their task bodies could be linked components, as in our Llama-1B megakernel. 

By symbol. Relocatable device code and LTO (Scudiero & Murphy, 2014), exposed at run time by nvJitLink (Sundaram et al., 2023), link separately compiled device functions at no runtime cost; cuFFT (NVIDIA, c) and cuFFTDx (NVIDIA, b) use them to fuse callbacks and library code, and GoPTX (Wu et al., 2025) fuses kernels at the PTX level. PipeLink adds what concurrently running components share and a linker that checks and places it. 

Communication overlap. Many systems overlap com-munication with computation through streams, signals or fused kernels (Chang et al., 2024; Zheng et al., 2025b;a; Awad et al., 2025; Sul et al., 2026a; Qiang et al., 2026; Mao et al., 2026; Ma et al., 2026; Hong et al., 2026; Gond et al., 2026; Zhang et al., 2025; NVIDIA, e), and context-parallel frameworks correct outputs outside the attention kernel (NVIDIA, f; Fang & Zhao, 2024; Gu et al., 2024; Yang et al., 2025). PipeLink contributes no communication algorithm; it lets one owner’s communication component join another owner’s compute components in one kernel. 

Synchronization verification. WEFT (Sharma et al., 2015), GPUVerify (Betts et al., 2012), Descend (K¨ opcke et al., 2024) and Exo-GPU (Akeley et al., 2026) verify synchronization or schedule safety of whole programs. PipeLink checks declared protocols between components and leaves their code to sanitizers and numerical tests. 

## 7 LIMITATIONS AND CONCLUSION 

Limitations. PipeLink checks contracts against each other, not against the code behind them. A component that breaks its own contract, for example by touching shared memory outside its claim, can still produce a wrong kernel; numerical checks and sanitizers therefore remain part of every composition, as they are for any hand-fused kernel. The code PipeLink generates only moves data, and only within one thread block. Arithmetic, precision conversion and communication between thread blocks or GPUs stay in component code, where the linker checks and binds the counters and memory they use but does not write them. A tensor export carries one generation, so a producer that hands its accumulator to another component in this way cannot be persistent; multi-slot rings between components are written in component code. PipeLink does not make components faster. It preserves each owner’s schedule, so a composition performs as well as the components it links; the gap of our dense attention variants to FlashAttention-3 comes from our core. Existing kernels must also be ported to declared interfaces; the four-owner MoE megakernel shows what such a port involves. Finally, packages are compiled for one architecture and one toolkit, because LTO IR is not portable across CUDA major versions. 

Conclusion. The components of fused GPU kernels coop-erate at fine grain on one SM, yet today they are absolute-addressed and can only be combined by forking their source. PipeLink gives them what object files gave whole programs: a contract stating what crosses the component boundary, and a linker that checks the contracts and relocates every component into the kernel it joins. Because the linker’s decisions fold into constants, composition costs nothing, and components from different libraries, owners and GPUs combine into kernels that were previously built by hand or not at all.
