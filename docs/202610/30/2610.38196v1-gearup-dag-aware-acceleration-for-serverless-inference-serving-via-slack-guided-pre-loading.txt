## Abstract 

Serverless platforms increasingly host machine learning (ML) inference workflows, modeled as directed acyclic graphs (DAGs) of interdependent functions. Beyond container startup, each ML node must load libraries, model weights, and CUDA kernels before it can run. These costs accumulate along de-pendent DAG paths and place initialization on the end-to-end critical path. Existing systems optimize one half of this prob-lem. DAG-agnostic pre-loading prepares nodes the request may never reach, wasting host and GPU memory. DAG-aware serving routes and scales whole functions, leaving the loading stages inside a node untouched. This paper presents GearUp , a serverless DAG inference serving system that removes ML-node loading from the end-to-end critical path at low resource cost. GearUp profiles the loading stages of each node and schedules them inside the slack time the DAG exposes, hiding initialization behind upstream execution. It reuses initialized instances within and across requests to avoid redundant cold starts. A prob-abilistic, traffic-adaptive keep-alive policy sets how long idle instances are retained, balancing memory cost against cold-start risk under bursty load. On the AMBER Alert and FINRA-ML workflows with NVIDIA L40S GPUs, GearUp re-duces median end-to-end latency by 64.5% and 75.9% against SMIless, for median speedups of 3 .1× and 10 .0× over cold ex-ecution. Integrated GPU and host memory allocation fall by up to 83.9% and 94.6% against eager pre-loading in InstaInfer. 

GearUp achieves 4 .2× strong scaling on four workers.

## 2 Background and Motivation 

2.1 Serverless ML Inference and Pre-loading 

A cold ML invocation must import libraries, load model weights, transfer them to GPU memory, and initialize CUDA kernels. We call these four steps the node’s loading stages , and they are the unit GearUp schedules. For short inference tasks they dominate end-to-end latency, unlike generic serverless cold starts where container startup dominates. Table 1 summarizes where existing systems fall. One group is ML-aware but DAG-agnostic: InstaInfer [23] pre-loads libraries and model artifacts for individual functions, and PISeL [17] pipelines download, deserialization, and execution within a function. Both treat functions as independent units, so neither knows whether a pre-loaded node will be reached in the current request. The other group is DAG-aware but loading-agnostic: Kraken [3], Orion [14], and iRoute [10] optimize workflow scheduling, routing, and resource siz-ing, serverful systems such as Airflow [1] and InferLine [4] orchestrate DAG execution, and SMIless [13] co-optimizes resource configurations for ML DAGs but still launches each node reactively. No system in either group treats the load-ing stages as work that can be scheduled ahead of invoca-tion using DAG dependencies. The consequence is a timing dilemma: loading too late exposes initialization on the exe-cution path, while loading too early holds expensive GPU memory idle. 

2.2 Reactive DAG Execution Exposes ML Loading Overhead 

DAG-aware scheduling alone does not hide ML loading when node initialization remains reactive. A downstream node waits for its dependencies before starting its own loading stages, causing initialization delays to accumulate along the request path. Figure 1 illustrates this dilemma on one representative AMBER Alert request, executed by all four approaches under the configuration of §7.2. The DAG contains five GPU-backed functions: Object Detection (OD), Human Attribute Predic-tion (HAP), Image Recognition (IR), Face Recognition (FR), and Transcription (TRS), with the dependencies in Figure 2. Figure 1(a) shows SMIless, which starts each function only after its dependencies become ready. This avoids pre-loading and its resource management complexity, but leaves the load-ing stages on the request path. The request spends most of its time loading rather than performing inference, yielding 34.97 s. Hiding that cost requires starting downstream ini-tialization before its predecessors finish.

2.4 Overlapping Pre-loading with Upstream Execution 

The above observations highlight the need to align pre-loading with DAG progress. Our key insight is that DAG dependencies expose opportunities to overlap downstream ML pre-loading with upstream execution, hiding initializa-tion from the end-to-end critical path. Using these depen-dencies and execution slack to place loading stages allows downstream instances to be prepared before invocation with-out keeping them ready throughout upstream execution. 2.5 Design Implications 

Realizing this opportunity requires coordinating loading within a request and managing prepared instances across requests. This raises the three challenges introduced in §1. 

C1: pre-loading must be timely and non-intrusive. 

Unlike lightweight CPU function nodes, ML nodes have heterogeneous initialization costs, so some nodes must start loading several stages before execution. The schedule must use DAG dependencies to find this window while avoiding interference with active inference. 

C2: pre-loading is costly within a request and re-dundant across requests. Preparing every reachable node can hold substantial resources idle or waste preparation on unused branches. The same model nodes also recur across requests, making repeated initialization unnecessary. 

C3. Traffic and topology interact. DAG fan-out can amplify changes in root traffic into larger changes in down-stream demand. Static schedules and per-node policies can therefore retain too many instances or release them too early. 

## 3 An Overview of GearUp 

3.1 Objectives and Challenges 

GearUp pursues two objectives: 1) minimize end-to-end in-ference latency while preserving the DAG’s dependency constraints, and 2) avoid redundant initialization so that con-tainers and GPU memory are not held for nodes that will not run soon. Meeting them requires addressing challenges C1–C3 of §2.5: placing multi-stage pre-loading inside DAG slack, controlling its resource cost within and across requests, and coordinating node lifecycles under dependency-induced traffic. 

3.2 GearUp ’s System Architecture 

GearUp rests on one observation: only the critical path of a DAG determines its end-to-end latency, so every off-path node carries slack that the request is already spending. Ini-tialization placed inside a node’s slack window is therefore free, while the same work placed outside it either delays the request or holds resources before they are needed. Be-fore any of this can be scheduled, GearUp makes initializa-tion schedulable: each container exposes its loading stages— library import, weight load into host memory, GPU transfer, and CUDA-kernel warm-up—as separately invocable, idem-potent steps, and a profiler records the latency of each stage per node (§4.1). Over an inference DAG 𝐺 (𝑉 , 𝐸 ) annotated with these profiles, GearUp then applies three components, one per challenge: 

• Intra-Request DAG-Aware Pre-Loader (C1, §4) com-putes slack from a reversed topological traversal and overlaps each node’s loading stages with upstream execution. 

• Inter-Request Batching and Reuse Scheduler (C2, §5) batches requests by DAG type and reuses unre-leased instances across requests and DAGs that share model images. 

• Dynamic Keep-Alive Manager (C3, §6) sets per-node retention from a topology-aware cost model over observed arrivals. 

3.3 GearUp ’s Workflow 

Figure 4 shows how these components interact, in four phases; the numbers match the callouts in the figure. 

Deployment-time profiling (0). Developers deploy a DAG job with its code and model configuration. Before serv-ing, GearUp runs pilot executions over sampled batch sizes to build the per-node stage-latency profiles used by the pre-loading pipeline of §4.1. 

Admission (1–3). The front end groups arriving requests by DAG type within a time window, amortizing scheduling cost and exposing reuse opportunities across similar work-loads (§5.2). For each batch it loads the DAG metadata and walks the nodes, separating root nodes from downstream nodes. This split decides which policy applies: a root node has no upstream execution to hide behind, so its initializa-tion must be predicted from arrival history, whereas a down-stream node can be hidden inside DAG slack. 

Policy generation (4–6). The workload extractor and on-line profiler supply per-node execution times, stage latencies, and resource usage (§4.1). For a root node, a histogram over inter-arrival times decides when to pre-warm and whether a live instance can be reused (§5.1, §5.2). For a downstream node, reversed-topology analysis yields the critical path and 

𝑇 slack , and the profiled stage latencies determine where inside that window each stage is issued (§4.2, §4.3). 

Execution and feedback (7–9). Policies reach the work-ers as pre-load, request, reuse, and keep-alive commands, and the container scheduler enforces them over a shared GPU container pool, where an idle instance is either reused by an arriving request or released on timeout (§6.1). The retention window 𝐷 ∗ is set per node by the cost model and conditioned on DAG parent activity, so active parents lengthen it and quiet parents shorten it (§6.2, §6.3, §6.4). Runtime observa-tions then update the stage latencies, arrival history, and parent states that these policies read, so they track changing traffic instead of staying fixed.

4.1 Per-Node Multi-Stage Pre-loading Pipeline and Profiler 

Each function container exposes a unified /handle endpoint that supports a staged, idempotent initialization pipeline: 1. preload_libs : import framework libraries (e.g., Py-Torch). 2. preload_model_container : load model weights into host memory. 3. preload_model_gpu : transfer the model to GPU. 4. preload_cuda_kernels : execute a dummy forward pass to trigger kernel initialization. Idempotence lets the scheduler issue the stages one at a time and stop after any of them without leaving the container in a partial state. The scheduler orchestrates these stages se-quentially via the endpoint, and stage latencies are recorded and persisted as JSON profiles for runtime scheduling.

5.2 Request Batching and Instance Reuse Across Requests Request Batching. A batching time window is employed to reduce per-request overhead. Upon the first request for the same DAG, a batching window (default 500 ms) is initi-ated, during which subsequent requests are aggregated. In parallel, the dispatcher prepares execution by either reusing an idle container or launching a new one. After the batching window expires, the aggregated requests are dispatched in a single call, which forwards them to the container for batched execution. 

Instance Reuse. The framework decouples reuse policy from execution mechanism. Two nodes are interchangeable when they declare the same container image and model configuration, so an instance already initialized for one is in the state the other requires. Such nodes recur both across successive requests to the same DAG and across different DAGs that embed the same model, and in either case an idle instance is assigned instead of initializing a new one. The controller makes this decision because it maintains the pool across workers (§6.1); the scheduler’s intra-DAG timing logic is unchanged, and a reused instance simply skips the pre-load stages of §4.1. Reuse and retention are therefore coupled: an instance can only be reused while it is still being kept alive, so the retention window 𝐷 ∗ of §6 determines how much reuse is available, and each reuse hit is a cold start and a model load the request does not pay for.

## 7 Implementation and Evaluation 

7.1 Implementation 

We implement GearUp as a layer that can be integrated into serverless inference serving platforms, spanning the con-troller, workers, function handlers, and DAG orchestrator. The system runs on GPU-enabled nodes, where each ML function is packaged as a Docker container exposing a uni-fied HTTP interface. 

GearUp follows a centralized-controller, distributed-worker design. The controller is the entry point, exposing a REST API through Flask, holding global container state in a thread-safe map, and enforcing a configurable upper bound on GPU memory. DAG specifications are given as JSON adjacency lists, loaded at startup and broadcast to all workers. Each 

worker manages container lifecycles on its node through the Docker SDK, probing readiness over HTTP with exponen-tial backoff and reporting status to the controller. A worker also runs the keep-alive optimizer of §6, with a background thread reclaiming containers past their duration 𝐷 ∗.Each function is profiled offline over sampled batch sizes to measure its four pre-load stages and a representative in-ference latency; profiles, DAG structures, and system param-eters are externalized as JSON and YAML.

The worker maintains a shared container pool and creates, reuses, or releases containers according to controller decisions. 7.4 Effectiveness of GearUp 

End-to-end latency and speedup. Figure 8 compares the latency and speedup distributions of the four systems. For AMBER Alert, SMIless has a median latency of 34.9 s because downstream functions still incur initialization overhead. Ea-ger pre-loading reduces the median to 12.7 s with InstaInfer, while function-local pre-loading achieves 15.8 s with InstaIn-fer Chain. GearUp achieves the lowest median latency of 12.4 s, a 64.5% reduction relative to SMIless. Based on the 38.7 s cold-execution baseline, the corresponding median speedups are 1 .1×, 3 .1×, 2 .4×, and 3 .1×, respectively. The benefit is larger for FINRA-ML, whose deeper and wider DAG provides more opportunities for coordinated pre-loading and reuse. SMIless, InstaInfer, and InstaInfer Chain have median latencies of 38.2 s, 15.2 s, and 21.0 s, respectively. 

GearUp reduces the median to 9.2 s, which is 75.9% lower than SMIless and 39.5% lower than InstaInfer. Based on the 92.6 s cold-execution baseline, its median speedup reaches 10 .0×, compared with 2 .4× for SMIless, 6 .1× for InstaInfer, and 4 .4× for InstaInfer Chain. 

Memory efficiency. Figure 9 shows GPU and host memory allocation and utilization. For AMBER Alert, GearUp cuts integrated GPU memory allocation from InstaInfer’s 304k to 56k GB s (81.6%) and host memory from 244k to 41k GB s (83.2%). GearUp retains the same average GPU utilization as InstaInfer, 0.64, while keeping resources allocated for a much shorter period. For FINRA-ML, the reductions are 527k to 85k GB s (83.9%) and 1,287k to 69k GB s (94.6%). These results show that 

GearUp reduces latency without keeping all DAG stages initialized throughout the workload. 

Traffic adaptation and instance reuse. Figure 10 shows the keep-alive behavior of GearUp under the FINRA-ML workload over the 300-minute trace. Although the number of root requests varies within a relatively narrow range outside the initial burst, each request fans out across the eleven-node DAG. This amplifies changes in root arrivals into larger variations in function invocation pressure. The number of live containers changes with the result-ing invocation demand, while a small idle-warm pool is re-tained across nearby windows. Reuse hits occur mainly dur-ing higher-load intervals, showing that recently initialized instances are reused when subsequent invocations arrive. During lower-load intervals, the live-container population decreases and few containers remain idle-warm. These re-sults show that GearUp adjusts container retention according to the invocation pressure produced by both external arrivals and DAG fan-out. 

7.5 Ablation Study 

We evaluate four GearUp variants on the AMBER Alert work-load. Latency impact. Figure 11 shows the latency and speedup distributions. Disabling adap-tive keep-alive has a smaller latency effect for this trace be-cause many reusable instances are selected directly through inter-request reuse.

## 9 Conclusion 

We presented GearUp , a DAG-aware serverless inference system that coordinates initialization, execution, reuse, and retention across dependent ML stages. GearUp derives each node’s slack from the DAG’s critical path and defers its load-ing stages to the latest point that still hides them, reuses initialized instances across requests that share a model, and sets container lifetimes from a cost model conditioned on parent activity. On the AMBER Alert and FINRA-ML work-flows, GearUp reduces median end-to-end latency by 64.5% and 75.9% against SMIless and cuts integrated GPU and host memory allocation by up to 83.9% and 94.6% against eager pre-loading, while sustaining a 4 .2× strong-scaling speedup on four workers.
