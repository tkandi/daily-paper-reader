## ABSTRACT 

Skywalker Sound, a premier audio post-production facility, operates more than 200 M4 Max Mac Studios on a 10 Gb Ethernet network. When not in use by artists, these machines sit idle, representing massive untapped unified memory and compute capacity. While these fleets are excellent candidates for distributed machine learning alongside existing NVIDIA GPU clusters, PyTorch lacks an accelerated distributed backend for Apple’s Metal Performance Shaders (MPS). To bridge this gap, we introduce the Metal Communication Collective Library (MCCL), the first open-source MPS backend for multi-node PyTorch training over switched Ethernet. We evaluate its performance and scalability across 24 nodes, demonstrating that large all-reduce operations reach 98–99.7% of TCP goodput. Training a 113.5M-parameter Vision Transformer (ViT) scales from 198 to 4,568 samples/s, achieving 95.9% parallel efficiency. Benchmarked against an NVIDIA A100 GPU, one M4 Max Mac equals roughly 1.7 × the throughput of FP32 matrix multiplication, and 5.5 Macs match an A100 using TF32. Harnessing 100 idle Macs for 12 hours nightly offsets approximately $200,000 annually in equivalent cloud compute costs. Our results demonstrate that existing Mac infrastructure can be seamlessly repurposed for high performance distributed training without abandoning the standard PyTorch codebase. 

## 1 INTRODUCTION 

Skywalker Sound, the renowned audio post-production fa-cility behind the iconic soundtracks of Star Wars , Jurassic Park , Indiana Jones and many others, operates more than 200 Apple M4 Max Mac Studios (40-core GPU, 128 GB uni-fied memory) on a single 10 Gb Ethernet network backed by central ZFS storage. By day, they operate as Digital Audio Workstations to create soundtracks; by night, we estimate that at least 100 of them sit idle for 12 hours, representing 438,000 Mac-hours a year. Our machine learning team builds custom audio models for tasks such as stem separation, denoising, and upmixing, and trains them mostly on NVIDIA GPU clusters that are shared across teams and often fully booked. We wanted to use the idle Macs for exploratory prototyping and longer overnight training runs, with the same PyTorch code we run on our GPU clusters. PyTorch, however, has no distributed backend for MPS tensors, and its CPU backend, Gloo, works only if gradients are copied to CPU memory by hand, which stalls the GPU on every exchange (Section 2). Apple-specific frameworks such as MLX provide their own collectives, but adopting one would mean maintaining a second codebase.

Unified memory, shared events, and wire rate. On an M4 Max, the CPU and GPU share the same 128 GB of DRAM, with no PCIe bus between them, so a CPU thread can average a GPU gradient in place. Sharing memory costs little bandwidth. On single-die Apple silicon, the CPU and GPU each reach about 90% of the advertised unified-memory bandwidth (Beischl et al., 2026; Hübner et al., 2025). What sharing does require is explicit order-ing. Atomic operations are not coherent across the two devices (Beischl et al., 2026), and PyTorch queues GPU ker-nels asynchronously onto a single MPS command stream, so a CPU thread cannot tell from memory alone whether the GPU has finished writing a buffer. Metal shared events (MTLSharedEvent ) supply that signal with a counter that the GPU stream and CPU threads can both raise and wait on without draining the device (Apple, 2026b). The network sets the other limit. 10 Gb Ethernet carries 1.25 GB/s at line rate; with 9000-byte jumbo frames, a TCP socket delivers at most 1.238 GB/s of tensor payload, which we call TCP goodput . Because a ring all-reduce sends each byte around the ring twice ( 2( N −1) /N wire bytes per tensor byte), we report bus bandwidth (NVIDIA, 2016b), which compares directly against TCP goodput at any cluster size. Small messages are limited instead by latency, chiefly the 0.59 ms switch round trip. 

## 3 CLUSTER SETUP AND SOFTWARE STACK 

Our controlled testbed (Figure 1) is a 24-node slice of Sky-walker Sound’s workstation fleet. Each node is an Apple M4 Max Mac Studio (16 CPU cores, 40-core GPU, 128 GB unified memory) on a single 10 Gb Ethernet switch, con-figured with 9000-byte jumbo frames and 32 MiB socket buffers. The nodes run PyTorch 2.14.0 and MCCL 6.8.0 (commit 64a359b ) on macOS 26.4 or 26.5.1. We launch jobs with Ray Train (Moritz et al., 2018), the same launcher we use on our NVIDIA clusters. A Linux head node runs the Ray 2.56.1 controller and places Py-Torch Lightning 2.1.0 workers (Falcon & The PyTorch Lightning team, 2019) with a SPREAD placement group, so each worker lands on a different Mac and a job across dozens of machines starts with one command rather than a torchrun invocation on every Mac. The job script is identical to the one we run on GPUs, apart from the head node it connects to. Neither framework supports this setup as shipped, and each refuses one thing. Ray discovers GPUs through CUDA, so every Mac reports zero GPUs (Ray project, 2023). We instead give each Mac one unit of a custom resource (pool:mac ) and have every worker request it, which both makes Macs schedulable and caps each machine at one worker, so two workers never compete for the same GPU and memory. Lightning treats MPS as a single-device ac-celerator and rejects parallel strategies on it (Lightning AI, 2026; Ray project, 2025), and its stock DDP strategy passes CUDA device_ids , which the MPS process group does not accept. A small custom strategy pins each worker to the mps device, returns device_ids=None , and drops the NCCL environment variables Ray sets for GPU jobs. With these changes, importing mccl registers the mccl 

backend for MPS tensors, and a training job on the Mac fleet runs the same way it does on our CUDA clusters, with the same Ray Train script, the same Lightning module, and 

DistributedDataParallel with mccl in place of NCCL. 

## 4 MCCL D ESIGN : T HE SHARED -M EMORY 

## HANDOFF 

Halfway through a backward pass, the GPU finishes com-puting a 25 MB gradient bucket for the later layers of the model while continuing to compute gradients for earlier layers. MCCL must average that bucket across 24 Macs on CPU threads before the optimizer step, under two con-straints. The CPU cannot read the bucket until the GPU has finished writing it, and the optimizer cannot read it until the network has finished averaging it. 

4.1 In-Place Reduction in Unified Memory 

When PyTorch allocates an MPS tensor in shared Metal stor-age (Apple, 2026a), the GPU’s MTLBuffer and the CPU’s MCCL: PyTorch Training Across a Fleet of Macs 

pointer are the same DRAM pages, and since PyTorch 2.12 every MPS tensor is allocated this way (PyTorch contrib-utors, 2026a). MCCL works on those bytes directly. It takes the CPU pointer to the gradient bucket, streams slices out over TCP, and uses Apple Accelerate ( vDSP ) to add in-coming slices from peer Macs into the bucket, accumulating fp16 and bf16 in fp32. vDSP runs on the CPU’s SIMD units, and its element-wise adds are far faster than the 1.238 GB/s the network delivers, so the reduction never limits the ring. When the ring finishes, the averaged gradients are already where the optimizer expects them. We reduce in place not to save memory bandwidth, which the M4 Max has in abundance, but to keep the GPU run-ning. Copying a bucket to a separate CPU buffer would require draining the GPU command stream for every bucket; working in place with event tickets lets backward continue. Before PyTorch 2.12, tensors could live in device-only mem-ory that the CPU cannot address, and MCCL must take that slower path, blitting each bucket through a shared staging buffer and waiting for the copy. The ablation in Section 5.1 forces the same path and shows what it costs. 

4.2 Per-Bucket Shared-Event Ordering 

When PyTorch hands MCCL a bucket pointer, the GPU usually has not written the bucket yet. To keep the CPU and GPU in step without stalling either one, MCCL enforces three rules (Figure 2): 

O1 Producer ordering: the CPU engine does not read bucket bk until the GPU kernels that write bk have completed. 

O2 Consumer ordering: the GPU’s optimizer kernel does not read bk until the CPU engine has written the final reduced slice into memory. 

O3 Single-thread stream ownership: only PyTorch’s main thread encodes or commits commands on PyTorch’s MPS stream. O1 and O2 are enforced by two ticket counters backed by Metal’s MTLSharedEvent (Apple, 2026b), and bucket k

passes through three hands. PyTorch’s thread queues the kernels that write it, encodes a signal on producer ticket k,flushes the command buffer, and moves on to bucket k+1 

without waiting. When the GPU finishes those kernels, the ticket increments, and MCCL’s CPU thread, which has been waiting on it, sends bucket k into the TCP ring. When the ring completes, the CPU thread raises consumer ticket k.When PyTorch later calls wait() before the optimizer step, it encodes a GPU-side wait on that ticket ahead of the optimizer kernels, so nothing blocks on the CPU. MCCL holds bucket k until wait() returns, so PyTorch’s caching allocator cannot reuse its MTLBuffer while the CPU is still writing the reduced slice. We considered two simpler designs. Calling torch.mps. synchronize() before each bucket satisfies O1 and O2, but it drains the GPU 18 times per ViT step, removing the overlap that bucketing is meant to provide. Committing PyTorch’s MPS stream from MCCL’s background thread avoids that stall but violates O3, and in our tests it crashed in-side Metal because PyTorch’s stream wrapper is not thread-safe. PyTorch’s public torch.mps.Event covers only half of this ordering. A CPU thread can wait on an event recorded by the GPU stream, which satisfies O1, but as of PyTorch 2.14, which we use, no public API lets a CPU thread signal an event that GPU work then waits on, which O2 requires. PyTorch 2.15 adds public MPS streams and 

Tensor.record_stream (Hugging Face, 2026); these may simplify parts of MCCL’s integration with PyTorch’s MPS stream, such as buffer lifetime tracking, and we plan to evaluate them once 2.15 is stable. 

4.3 Pipelined TCP Ring and Tree Transport 

Once the CPU thread owns a bucket, MCCL uses conven-tional algorithms, sending buckets above 256 KiB around a pipelined ring (Patarasuk & Yuan, 2009) and smaller mes-sages through a log 2 N recursive-doubling tree (Thakur et al., 2005). The harder problem is that Macs finish back-ward at different times. MCCL has no per-bucket barrier to line them up, and a ring sender is gated only by its own receives, so a rank that finishes backward a few millisec-onds early can run almost the entire reduce-scatter before its slower neighbor has consumed anything. Left unchecked, that rank would push a whole DDP bucket into the receiver. 

Parking and credits. A dedicated reader thread per peer lets the slower rank accept data before it is ready to use it. The reader demultiplexes each incoming frame by its operation, sequence number, and tensor ID and parks it until the receiving rank posts the matching step, up to a fixed park limit. To bound that buffer, the receiver sends a 1-byte credit back to the sender after consuming each chunk of 1 MB or more, which caps the sender’s lead at the pipeline depth plus two chunks. The park buffer therefore holds a few chunks rather than a whole bucket, and a fast Mac runs ahead by that bounded amount instead of waiting for its neighbors. The same mechanism makes a per-collective barrier unnecessary. The TCPStore barrier it replaces would cost one set plus 23 serial round trips on rank 0 for every collective at 24 nodes. 

Issue order. Collectives must also enter the ring in the same order on every rank. In an early version with two pool threads, a plain mutex let one Mac start bucket k+1 while its neighbor was still in bucket k, and each then waited indefinitely for the other’s traffic (Section 6). ## 5 CONTROLLED EVALUATION 

We evaluate three aspects in order. The first is whether the ring saturates the 10 Gb link, the second is whether that traffic stays hidden behind backward computation, and the third is whether training converges correctly at every cluster size. We use microbenchmarks to answer the first two. For the third, we train on CIFAR-10 rather than on our audio data, because a communication backend is indifferent to what the gradients represent. Its behavior depends only on the bytes exchanged per step and the backward time avail-able to overlap them. CIFAR-10 is public and inexpensive, so others can rerun these experiments on their own Macs and use the results to estimate how a model with similar gradient volume, such as an audio VAE, a stem separator, or a diffusion refiner, would scale. Here, we use two models. A 113.5M-parameter Vision Transformer is the throughput and communication stress case, and its 454 MB of gradi-ents per step is roughly three times what our audio VAE exchanges. A 31.6M-parameter GroupNorm ResNet tests convergence across cluster sizes. We close with correctness, shared storage, and sustained reliability. 

5.1 Wire Scaling and Compute Overlap 

We first checked whether the 10 Gb network limits all-reduce throughput as the cluster grows. In a ring, each Mac exchanges data only with its two neighbors, so adding Macs adds hops but not per-link traffic. Consistent with this, 16–256 MB buckets move at 1.21–1.23 GB/s of bus band-width from 4 to 24 Macs, 98–99.7% of the 1.238 GB/s that jumbo-frame TCP can carry on a 10 Gb link (Figure 3, left and center). Small messages behave differently. A 1 MB all-reduce across 24 Macs puts only 42 KB on each hop, so the 0.59 ms switch round trip dominates, which is why MCCL sends messages under 256 KiB over a recursive-doubling tree. We next measured how much of that traffic is hidden be-hind backward computation, using a synthetic step with eighteen 25 MB buckets timed four ways, as compute alone, communication alone, overlapped, and serialized (Figure 3, right). From 4 to 24 Macs, about 94% of communication time is overlapped with backward . At 24 Macs, 0.74 s of all-reduce traffic over 1.09 s of GPU work adds 45 ms to the step, a 4.1% overhead. When we disable the in-place path ( MCCL_UNIFIED_COLLECTIVE=0 ), each bucket is copied through a Metal staging buffer and waited on, the same path a tensor in device-only memory would take before PyTorch 2.12, and overlap drops to zero.

5.3 Studio Storage and Sustained Reliability 

Our audio data lives on central ZFS servers that the Macs mount over SMB or NFS. NFS lists directories faster on a cold start (0.9 vs. 10.6 s for thousands of files), while SMB streams data faster once loading begins (757 vs. 538 MB/s per Mac). Precomputing the file list into a manifest re-moves the cold SMB walk, and after that neither protocol changes step time. To isolate transport correctness under sustained load, we ran a 10-minute stress test across all 24 Macs. It completed 17,784 back-to-back all-reduces per rank, 0.34 TB of traffic per Mac, with no bit errors, while MCCL used 0.31 of one CPU core. Our longest internal training runs span over 3 weeks with no deadlocks or train-ing instability. 

## 6 LESSONS FROM SCALING PAST TWO 

## NODES 

Our early development used two nodes and mainly ran smoke tests of gradient correctness on synthetic data. Scal-ing to 24 nodes with real datasets exposed three problems that did not appear with two nodes. We describe how we found each one and what we changed as others building distributed training on Apple silicon are likely to face the same issues. 

6.1 Unified-Memory Races and Ring Ordering Buffer-reuse race in unified memory. At 24 nodes, we observed occasional corrupted gradients that disappeared whenever we added a print() to investigate. The cause was a temporary GPU tensor that an early version of MCCL allocated, copied out of, and released when the call returned. Under load, PyTorch’s caching allocator handed the same 

MTLBuffer to the next collective while the earlier copy was still pending in the command queue, and MCCL’s CPU thread wrote incoming network bytes over a buffer the GPU had not finished reading. Our unit tests never caught it, because tensor.item() and print() both drain the MPS stream between collectives. MCCL now receives di-rectly into the caller’s output tensor and never allocates temporary GPU buffers on its background thread, and it holds every bucket until wait() returns (Section 4.2). We now also test asynchronous bursts with every host synchro-nization removed, and all 640 operations per rank across 24 Macs are exact. 

Cross-rank bucket ordering in the ring. At 24 nodes, the ring occasionally deadlocked. PyTorch can finish two buckets a few microseconds apart, and early versions of MCCL let worker threads pick up ready buckets in whatever order the OS scheduled them. One rank would sometimes start bucket 2 while its neighbor started bucket 1, and each waited on the other. MCCL now stamps every collective with a sequence number on PyTorch’s main thread and ad-mits work to the transport only in that order. 6.2 A Silent MPS Gradient Bug Above 216 Samples 

The most time-consuming problem we encountered was out-side MCCL. Our audio models train with multi-resolution centered short-time Fourier transform (STFT) losses (Ya-mamoto et al., 2020), and models trained on short clips converged normally on MPS. When we moved our VAE to 1.6 s crops (76,800 samples at 48 kHz), training stopped im-proving, with no errors or NaN values to indicate a problem. Because the same code trained correctly on our NVIDIA clusters, we compared each layer’s backward pass on MPS against a CPU float64 reference. The comparison pinned the fault on the MPS backward ker-nel for F.pad(...,mode="reflect") , which every centered torch.stft calls (Figure 6). The forward pass is bit-exact, but the backward pass is exact only up to 65,535 samples ( 216 −1). Above that length, a single mono signal (N =1 , C=1 ) receives wrong gradients at every length ex-cept exact multiples of 216 , and any input with more than one batch element or channel fails at every length of 216 or more, a pattern consistent with an indexing overflow at 216 

elements. Table 2 shows the effect on training. With native MPS gra-dients, and with the default mps-spectro path, which hands these shapes back to torch.stft , a 300-step waveform-recovery loss rises from 1.821 to 5.525 instead of falling to 0.924. Forcing the custom Metal kernels in 

mps-spectro (ssmall256, 2026) restores exact gradients at 0.8 ms per call, and MCCL ships an independent Ap-ple Accelerate STFT as a permanent reference check. The bug affected every PyTorch version we used, from 2.11 through 2.14, because PyTorch delegated this kernel to Ap-ple’s MPSGraph (PyTorch contributors, 2026c). This was only recently fixed upstream by moving reflection padding to native Metal kernels (PyTorch contributors, 2026d). We now run every new model through this check before training it across the cluster. It executes each layer’s forward 

and backward pass on both MPS and CPU float64 at production tensor shapes and flags any output or gradient whose cosine similarity to the CPU reference falls below 0.99 or whose relative error, ∥xMPS − xCPU ∥2/∥xCPU ∥2,exceeds 10 −3.

## 7 FROM 24 M ACS TO HUNDREDS 

Our evaluation used up to 24 nodes, and the facility has more than 200. Assuming 100 machines are idle each night, the fleet corresponds to roughly 18 A100 GPUs with TF32 matmul, and with all 200 available, roughly 35. Reaching that scale requires solving two problems that do not appear at 24 nodes. The first problem is hop count. A flat ring splits each bucket into N pieces and sends them 2( N −1) hops, and each hop pays a fixed switch cost regardless of message size, 306 μs in our model and consistent with the measured 0.59 ms round trip. A latency-plus-bandwidth model (Hockney, 1994) fit-ted to the 4–24 Mac data matches every measured bucket of 16 MB or more within 1.9%. The model predicts that a stan-dard 25 MB bucket stays bandwidth-bound up to roughly 70 Macs, beyond which a flat ring spends more time wait-ing on switch hops than moving bytes. It also predicts that raising PyTorch’s bucket_cap_mb to 50 MB moves the crossover past 128 Macs and holds 1.23 GB/s at 100 nodes. These values extrapolate the 4–24 Mac measurements and are not measurements at 70 or 100 nodes. For the full fleet, the standard answer is a two-level ring (Jia et al., 2018; Mikami et al., 2018), which reduces within groups of 10–16 Macs on the same switch and then across switches. The second problem is that the workstations belong to artists first, so the training pool must grow and shrink with the studio’s schedule. An empty room does not mean an idle machine, because some editors work from home and connect to their workstations remotely. A daemon on each Mac would therefore need to detect active use on the machine MCCL: PyTorch Training Across a Fleet of Macs 

itself, characterizing active Pro Tools sessions or a remote login, before joining the Mac to Ray, and remove it as soon as either appears. We leave the design of this availability detection to future work. Recovery when a Mac leaves is a separate problem. Ray Train’s elastic training (Ray project, 2026) lets a job spec-ify a range of workers rather than a fixed count. When a Mac leaves, the job restarts from its latest checkpoint with the remaining workers, and when more Macs become available, it resizes the worker group to include them, so a job loses at most the work since its last checkpoint. We have not yet tested elastic training with MCCL. Each Mac would also cache dataset shards on its local SSD, so that 200 workers starting at once do not overload a single ZFS vol-ume. Finally, MCCL already implements the allgather 

and reduce_scatter calls that sharded FSDP train-ing (Zhao et al., 2023) needs, though every job in this paper keeps a full model copy per Mac. 

## 8 LIMITATIONS 

MCCL hides communication only when the backward pass is long relative to gradient volume. At batch 64 per Mac, the ResNet’s 126 MB of gradients cannot be fully hidden at 24 nodes, and per-step time rises from 227 ms to 305 ms. Models with small per-device batches therefore need larger batches, gradient accumulation, or reduced-precision gradi-ents to scale well on our network. The network itself is the larger constraint. NVIDIA train-ing systems connect GPUs with NVLink and NVSwitch at up to 900 GB/s within a node and InfiniBand at up to 400 Gb/s between nodes (van der Ouderaa et al., 2025), and NCCL (NVIDIA, 2016a) moves data over these links with RDMA rather than kernel TCP. Our Macs share a single 10 Gb Ethernet switch, which delivers 1.238 GB/s of TCP goodput per link and costs 0.59 ms per round trip. Large buckets still fill that link, but every collective pays the round trip, so small or frequent messages are latency-bound long before they are bandwidth-bound. Faster links would re-quire Thunderbolt network adapters, since the Mac Studio’s built-in port is 10 GbE, and we have not evaluated lower-latency Ethernet or switched RDMA. Our measurements stop at 24 nodes on one switch, and the predictions in Section 7 are extrapolations. MCCL also does not yet handle preemption itself. A timeout or peer failure errors all in-flight collectives, and recovery relies on restarting from the last checkpoint. Finally, we have not evaluated distributed inference, al-though MCCL exposes the collectives it needs. Our mea-surements suggest how the common strategies would fare. Replicated inference, in which each Mac holds a full model copy and serves its own requests, needs no per-request col-lectives and should scale with the number of Macs, and 128 GB of unified memory fits large models on a single machine. Pipeline-parallel inference sends one small ac-tivation per stage boundary per token, so each boundary would add on the order of half a switch round trip, about 0.3 ms. Tensor-parallel inference is the poor fit. It requires two all-reduces per transformer layer per token, each paying at least one 0.59 ms round trip regardless of message size, so a 32-layer model would spend roughly 38 ms per token on communication alone, capping decoding near 26 tokens per second per sequence. On this network, we would there-fore start with replicated and pipeline-parallel inference and measure both before trying tensor parallelism. 

## 9 CONCLUSION 

MCCL lets us run the same PyTorch Lightning code on our Mac fleet that we run on our NVIDIA clusters. On 24 Mac Studios over 10 GbE, it reaches 98–99.7% of TCP good-put, overlaps about 94% of communication with backward 

computation, and scales a 113.5M-parameter ViT at 95.9% efficiency. The main contribution is not a new collective algorithm, but a way to reduce gradients directly in unified memory without stalling the GPU. Per-bucket Metal shared events coordinate the CPU network threads with PyTorch’s asynchronous MPS stream. Scaling to 24 nodes also exposed problems we had not en-countered in smaller tests, including a buffer-reuse race, a ring-ordering deadlock, and a silent MPS gradient bug. We have tested MCCL on 24 of the facility’s more than 200 Macs. Using the full fleet will require hierarchical collec-tives, local data caching, and a way to release workstations when artists need them. These are the next problems we plan to address.
