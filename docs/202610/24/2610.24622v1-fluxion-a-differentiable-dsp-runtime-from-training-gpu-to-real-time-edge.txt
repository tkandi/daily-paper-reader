Abstract —Native real-time audio engines meet audio deadlines but are hard to connect to machine-learning workflows, while tensor frameworks integrate with machine learning but process audio as offline batches without timing guarantees; runtime layers built on them inherit the host’s scheduling and deployment footprint. This paper presents Fluxion, a Rust audio DSP runtime for cascaded second-order sections, FIR filters, and delay-line effects. Fluxion implements the parts that are specific to DSP: closed-form filter design, forward kernels, analytic adjoints for the recursion, and stability checks. It relies on existing libraries for the autodiff graph, GPU code generation (tested here on CUDA), and array interchange. One graph algebra is lowered to a differentiable training engine and to an allocation-free real-time engine; between them, a trained graph is checked for stability and frozen into a versioned artifact that an edge device checks again before playback. We compare Fluxion with six framework-hosted and native baselines under one float32 protocol. Among the systems that compute the exact recursion, Fluxion has the highest GPU throughput when data stays on the device and the highest throughput on most CPU workloads, while its CPU training step is slower than those of torchaudio and GRAFX. Its test suite checks the audio thread for allocations with an instrumented allocator, and we report measured latency tails. Fluxion is open source at https://github.com/matteospanio/fluxion. 

Index Terms —audio DSP, DDSP, GPU computing, runtime systems, real-time audio, edge computing, Internet of Sounds 

I. I NTRODUCTION 

Native real-time engines such as Faust [1], SuperCol-lider [2], and JUCE [3] run audio with low latency, but they are hard to connect to the machine-learning tools now common in audio research. Tensor frameworks such as torchaudio [4], [5], nnAudio [6], and GRAFX [7] work well with machine learning, but they treat audio as offline batches of tensors, with no streaming state and no latency bound. Trained tensor graphs can be deployed on edge devices through TFLite or ONNX Runtime, but a sample-recurrent filter reaches those runtimes only by unrolling. TorchFX [8], our earlier system, and differentiable-DSP libraries such as FLAMO [9] and ADAC [10] build a runtime layer on top of a tensor framework. TorchFX, for example, records composition as a deferred graph, fuses second-order-section (SOS) cascades into single dispatches, and reuses the host’s autograd. These layers remain limited by their host: the interpreter schedules the real-time path, so the latency tail can be measured but not bounded, and the Python and PyTorch stack weighs gigabytes, which makes edge deployment im-practical. We argue for a different division of work. A DSP runtime should own the parts that are specific to DSP: closed-form co-efficient design, forward kernels, analytic adjoints for recursive filters, and the stability checks that decide whether a trained arXiv:2610.24622v1 [eess.SP] 17 Oct 2026 filter can be deployed. It should rent what general-purpose ML infrastructure already provides: the autodiff graph (Burn [11], PyTorch, or JAX), GPU code generation (CubeCL [12]), and zero-copy array interchange (DLPack [13]). Keeping the adjoints in the runtime lets several autodiff frameworks use them, and relying on existing libraries for the rest keeps the runtime small. We present Fluxion, a Rust audio DSP runtime built this way (Fig. 1). A functional graph algebra (series |, parallel +,feedback ˜, and named nodes) is lowered to two engines: a training engine that composes analytic vector-Jacobian prod-ucts (VJPs), and a lock-free real-time engine that does not allocate on the audio thread. Feedback is not yet lowered to either engine, so our results cover cascades, FIRs, and delay-line effects. Filters are designed in double precision; the single-precision coefficients that run are checked for stability and frozen into a versioned artifact, which the real-time engine plays.

Tensor-framework audio. torchaudio [4], [5] provides exact time-domain recursion over batched tensors but no fused-cascade primitive, which Sec. IV-A measures. nnAudio [6] provides trainable GPU spectral front-ends without recursive filtering, so we do not use it as a comparator. GRAFX [7] com-poses differentiable audio graphs on PyTorch with an exact and an approximate filtering backend, and we measure both. Engel et al. [14] established the idea of learning through signal-processing structure (DDSP). All of these systems inherit their host’s execution model. 

Differentiable DSP. IIR filters can be made differentiable in two main ways. One is to build modules inside a host framework and use its autograd, as in FLAMO’s frequency-sampled modules [9] and ADAC’s FLAMO-to-FAUST com-pilation pipeline [10]. The other is to derive the adjoint of the recursion analytically and register it as a custom operator. This has been done for linear dynamical operators [15], all-pole filters [16], and direct-form filters [17], and torchaudio’s 

lfilter and TorchFX’s opt-in torchfx.ddsp module [8] also ship analytic backward passes. Fluxion takes the second approach and keeps the adjoints in the same runtime that checks and deploys the trained filter. Tab. III compares the cost of both approaches. Filters trained in FLAMO or in TorchFX’s differentiable module can be imported into Fluxion’s freeze pipeline (Sec. III-C). ADAC is a compiler without a filtering runtime of its own, and its published benchmark measures code-generation latency, so we discuss it without measuring it and measure FLAMO, on which it builds. ADAC’s loop-aware stability certificate is the closest prior work to our stability verdicts; Fluxion also applies a stability projection during training (Sec. III-B). 

Native real-time engines. Faust [1], SuperCollider [2], and JUCE [3] run audio with low latency and complement Fluxion; Faust can also be used for training through its JAX back-end [18]. RTNeural [19], the Neutone SDK [20], and anira [21] follow a two-step workflow in which models are trained in Python and then run by a native inference engine. anira is the closest to our setting. It runs ONNX Runtime, LibTorch, and TensorFlow Lite models from an audio callback by moving inference to a thread pool. By default this adds one buffer of latency, and an optional bounded wait in the callback removes it. Fluxion computes the DSP on the audio thread (Sec. IV-C measures both approaches on the same workload) and uses one runtime for training and deployment. 

GPU DSP. Parallel IIR filtering on GPUs builds on prefix scans [22]–[24], which TorchFX’s CUDA path uses. Fluxion’s GPU kernel runs each batch row’s cascade sequentially in time, with one GPU thread per row. gpuRIR [25] and Brian Hears [26] vectorise related audio workloads. Burn [11], CubeCL [12], and DLPack [13] are dependencies of Fluxion. Tab. I compares the systems discussed in this section. III. A RCHITECTURE 

A. Graph algebra and engines 

Users describe processing as a functional expression, in the style of Faust’s block-diagram algebra [1]. Filters and effects are values, | chains them in series, + runs them in parallel and sums the outputs, ˜ closes a feedback loop, and any node can be named. The expression is stored as a small typed graph with self-describing parameters, so Fluxion can validate it when it is built, serialise it, and lower it to different engines. Fluxion has two engines because training and real-time audio have different requirements. A training step benefits from large batches, free allocation, and often a GPU. The sample rate is bound when a graph is lowered, so the same graph can run at any rate. Both engines use the same traversal: a single walk interprets the graph against a backend trait with one method per kernel, so the backend supplies the buffer type and the kernels and the walk supplies the composition. For training the buffer is a differentiable tensor; for real time, a pre-allocated block of samples. Each lowering rejects the operators it cannot support. The training path rejects operators without an adjoint, and the real-time path rejects operators that need more than the current block, such as peak normalisation. Both currently reject feedback, so the engines cover cascades, FIRs, and delay-line effects. 

B. Analytic adjoints 

Recursive filters are a poor fit for generic automatic differen-tiation. If a framework traces the recurrence sample by sample, the tape grows with signal length and cascade depth, and Yu et al. report order-of-magnitude slowdowns for this reason [16]. Input gradients follow by filtering that cotangent with the numerator taps, and coefficient gradients are correlations with the delayed input and output signals. Design-parameter gradients follow by the chain rule through the design map. The design map is closed-form algebra without recursion, so Fluxion computes its Jacobian by central differences, which costs a few extra design evaluations per step and does not grow with signal length. Fluxion registers these vector-Jacobian products in the au-todiff framework the user already works with, as a Burn custom operator or as a custom autodiff operator in PyTorch or JAX. Each operator enters the host graph as one node: forward is the ordinary kernel, backward the hand-derived adjoint, so the host never records the recurrence. The executor that runs a graph on the CPU is the same walk that runs it over autodiff tensors, so series composition chains the adjoints and parallel composition sums the cotangents. Gradients are checked per operator and per composed graph (Sec. IV-B). Training on design parameters is common in differentiable DSP, where cookbook design equations map cutoff, gain, and Q to coefficients [28], [29]. In Fluxion these parameters sit on top of the analytic adjoint instead of an unrolled tape, so a step costs one forward and one backward pass of the recursion (Tab. III). Within the allowed parameter ranges, every set of design parameters gives a stable filter. When raw coefficients are trained instead, a projection moves each optimiser step back into the stable region (Sec. III-C). 

C. Stability check and freezing 

Filters are designed in double precision and then cast to the single-precision coefficients that run; we call this cast freezing .The stability certificate is computed from the frozen values, not from the double-precision design. For an SOS cascade, each section is normalised to a0=1 and the largest pole radius after the cast is recorded. Graphs with explicit feedback also get a small-gain check, the maximum loop gain over a linear frequency grid on [0 , π ]. The shipped echo and reverb nodes have frequency-flat loop gains, so for them the check is exact; for other loops it is a sampled estimate. The general ˜ operator is checked the same way but is not yet lowered to either engine. The check returns one of three verdicts: Stable (all poles strictly inside the unit circle), Marginal (within ±10 −4 of the boundary, accepted but flagged), or Unstable (rejected). We chose the band with the cast in mind. Half-ulp rounding of a float32 coefficient is a relative 6×10 −8, and near the unit circle a pole radius moves by about the same amount, so the band is more than three orders of magnitude wider than the rounding error. The frozen graph is stored in a .fxg file, a JSON document with a format version and a kind tag, so a file with an unknown version is rejected instead of misread. A graph file stores topology and design parameters and is sample-rate independent; a frozen-sos file stores the float32 coefficients and their design rate, so the real-time engine loads it without a design step. The certificate depends only on the file contents, so a device can recompute it at load time instead of trusting the tool that produced the file (Sec. IV-C). It covers stability only and does not authenticate the file. The same pole and small-gain computations are used at design time, during training, and at export. During training, a projection clamps each section’s denominator into the Jury stability triangle shrunk by a margin ( |a2| ≤ 1−m, |a1| ≤ 

1+ a2−m, with m=10 −3 in our experiments; numerators are unchanged) after every optimiser step. The margin is larger than the verdict band because it has to hold until the next step as well as across the cast, and the forward pass only sees iterates inside the stable region. The file contains everything the real-time engine needs, so the trained graph and the graph that runs on the audio thread are the same object (Fig. 3). Checkpoints trained in FLAMO and in TorchFX’s differ-entiable module can be imported into the same pipeline. The importer replays each library’s parameter-to-coefficient map in double precision and applies the same stability check as for a native graph; in CI, fifteen checkpoints from the two libraries reproduce their realised coefficients to within float32 rounding (< 5×10 −5 per coefficient). It handles SISO filters only. 

D. The real-time engine 

The real-time engine runs frozen graphs (cascades, delays, echo, reverb, FIR) block by block with pre-allocated state, and receives parameter changes over a lock-free queue. Preparing a graph for a maximum block size is the only step that allo-cates: it sizes each node’s scratch buffer once, and processing then works in place. The queue is a single-producer, single-consumer ring of plain copyable values, so a coefficient update travels as a fixed-size array of sections instead of a heap-allocated vector. SOS sections run in transposed direct form II on every path, so the certified coefficients describe the same recurrence everywhere. To avoid clicks, new coefficients are designed off the audio thread and faded in with a short linear crossfade. We use a linear fade instead of an equal-power one because both branches process the same input: their outputs are largely correlated, and gains that sum to one approximately keep the level. Besides measuring latency, we test the audio thread with an instrumented allocator. The test suite installs a global allocator that counts allocations (not frees) inside the audio-thread section. The tests cover a cascade with gain automation sent from a second thread and a nested series–parallel graph, and a control test plants an allocation to confirm that the counter fires. This shows that the tested paths do not allocate, which is weaker than a proof. The queue is lock-free by design, but locks are not instrumented. 

GPU execution. The batched forward kernels and the operator interfaces used by their adjoints are written once in a portable kernel language and run directly on tensors kept on the device. We measure this path on CUDA hardware only. The adjoint kernels pass the same gradient checks as the CPU reference in CI; other backends are not yet validated. Sec. IV-A measures when the GPU helps. 

Deployment. Fluxion ships as Rust crates with a SoX-style command-line interface, as Python wheels that exchange ar-rays through DLPack (zero-copy with NumPy, PyTorch, and JAX), and as experimental C-ABI and WebAssembly builds. The stripped release CLI is 3.2 MB on x86-64 and 2.8 MB cross-compiled for ARM64, and it processes 10 s of audio in 20 ms (Tab. IV); a comparable TorchFX deployment first loads CPython and PyTorch. C. Real-Time and Edge 1) Real-time behaviour: The allocation tests of Sec. III-D run in CI and find no allocations on the tested audio-thread paths. Fig. 4 shows the per-block processing time at cascade depths d ∈ { 2, 5, 10 } and buffer sizes {128 , 256 , 512 } (dead-lines of 2.7–10.7 ms at 48 kHz), with coefficient crossfades running throughout. Blocks are processed one after another, without pacing or real-time priority, so the figure shows computation cost and not operating-system scheduling delays. In every configuration, the p99 is at most 0.26% of the deadline (6.8 μs at depth 10 with 128-sample buffers). The slowest of the 73,728 blocks took 872 μs (depth 5, 512 samples, 8% of that deadline); in the other configurations, the slowest block took less than 66 μs. Our earlier study measured a TorchFX p99 of 0.71–0.74% of the deadline on the same machine at 256 samples, the smallest buffer it used. 

Comparison with anira. anira [21] runs neural inference outside the audio callback, on a thread pool. By default the callback returns an earlier result, which adds one buffer of latency (2.7–10.7 ms here). With a blocking ratio W > 0,the callback waits up to W buffer periods for the current result, and anira adds no latency when that wait covers the declared worst-case inference time. We ran a 1024-tap FIR with the same taps in both systems: anira runs it as an ONNX convolution (ONNX Runtime, W =0 .75 , which adds no la-tency at the three buffer sizes), and Fluxion runs its real-time FIR node. Both run unpaced and without real-time priority, over at least 5,000 blocks per configuration. At 128/256/512 samples, Fluxion processes a block in 25/51/101 μs (median; p99 27/68/124 μs), and anira’s callback returns in 81/91/150 μs(p99 173/177/227 μs); no anira block reached the wait limit. The anira process has a 363 MB resident set and the Fluxion process 2.7 MB. anira can run arbitrary neural models and Fluxion cannot, so this comparison applies only to DSP workloads.

Hot-swap on the device. We ran the train, certify, push, and crossfade sequence of Sec. V-B end to end. The EQ of Sec. IV-B, trained on the workstation, was copied as a frozen .fxg file over the LAN to the Pi 5 while the engine streamed 128-sample blocks. The device recomputes the certificate when the file arrives and then crossfades the new filter in through the lock-free command queue. 3) Case study: SoundFood: SoundFood (https://www. soundfood.it/) develops a smart speaker for restaurants (Fig. 5) that plays AI-generated music matched to each dish [31], [32], an application of “sonic seasoning”, the use of sound to shape taste perception [33]. Because tables start their dishes at different times, the device keeps each table’s music within a local “sound bubble”. The production chain upmixes a mono track to eight channels (7.1). Each channel runs six frozen biquad sections (two order-4 Butterworth band limits, one shelving and one peaking section), its own 1024-tap directional FIR, and a level trim, and a separate low-frequency feed uses an order-2 Linkwitz-Riley crossover and an order-4 Butterworth. We report the structure of the chain; its tuning (cutoffs, gains, and taps) belongs to SoundFood. The system started as an offline batch service (FastAPI over TorchFX) that pre-rendered and stored every track eight times (5.3 MB of mono source becomes 42.3 MB per minute of 7.1 output), holding the whole file in memory (0.6 GB peak for a one-minute track). On the device, the newest TorchFX wheel for ARM runs the chain at 0.72 × real time (83.8 s for a 60 s track, 661 MB peak, a 968 MB installation, and a 2.1 s import), and TorchFX’s compiled kernels are built for x86 only. Fluxion loads the frozen biquad rows and FIR taps of the production chain directly. The largest output deviation from the production service is 2.0 × 10 −4 full scale on one channel and at most 9.6 × 10 −5 on the others; the reference output is 16-bit PCM (step 3.1 × 10 −5). On the Pi 5, Fluxion runs the chain as eight separate certified graphs. Paced at the audio rate, the p99 block latency is at most 33% of the deadline at buffer sizes of 128, 512, and 1024 samples, with no missed deadlines over 57,000 blocks, 31% of one core, and a 13.5 MB resident set from a 468 KB harness binary. Offline, the chain runs at 4.2× real time on the device. The equalisation can therefore run on the device instead of being pre-rendered, and per-dish retuning could use the hot-swap described above. V. D ISCUSSION 

A. Summary of results 

Among the exact-recurrence systems, Fluxion has the high-est throughput in the resident GPU regime and in most CPU cells (with one thread, TorchFX is faster on the 8-channel workload), and it takes the same time as SoX on the file-to-file task. Its CPU training step is slower than those of torchaudio and GRAFX, and its GPU training path is still slower than its CPU path. The deployment footprint is about 500 × smaller on disk and 57 × smaller in memory than the Python stack, and none of the measured baselines covers training, certification, freezing, and playback in one library. Fluxion is a DSP runtime and does not offer torchaudio’s range of transforms. 

B. Research directions 

Design-parameter gradients turn filter design into an op-timisation over interpretable parameters that keep the filter stable. This could be used to study perceptual losses, style transfer between EQ curves, and regularisation that is awkward to express over raw coefficients. Versioned frozen artifacts, a stability check at export, and crossfaded coefficient swaps let edge devices replace retrained DSP while streaming, with stability checked on the artifact itself. Managing fleets of devices, versioning, and staged rollout of DSP updates are open problems. A frequency-sampling step like FLAMO’s, whose cost barely depends on depth (Tab. III), could be added to Fluxion for coarse training, followed by certification and fine-tuning with the exact adjoints on the same graph. An adjoint for the feedback operator, together with a loop-aware stability check during training, would make learnable reverberators and feedback delay networks possible; keeping these stable during training is hard, and the stability verdicts of Sec. III-C could be a starting point. 

C. Limitations 

GPU execution is validated on CUDA only. The kernel layer also targets Metal, ROCm, and WebGPU, but we have not tested it on that hardware. GPU training is measured only for the single trainable section and for gradients through frozen cascades (Sec. IV-B), and trainable multi-section cascades run on the CPU adjoint path. The feedback operator executes but is neither differentiable nor lowered to the real-time engine. The kernels do not force flush-to-zero for denormals, which matters for decaying tails near digital silence. Fluxion has no neural operators of its own. The allocation claim relies on instrumented tests of specific paths, not on static analysis of all reachable paths. Frees and locks are not instrumented, and the property holds per process, not at the operating-system level. 

D. Threats to validity 

All numbers come from one workstation and one edge board, and other hardware could change the order of close cells (the smallest CPU margin is 13%). Each baseline runs on its own best path under one float32 protocol, and we state the remaining protocol differences where the numbers appear: frequency-sampling approximations, SoX’s file-to-file pipeline, the callback-to-return measurement of our earlier study, the FIR-only comparison with anira, and the default thread counts. Timings are medians of five repetitions after warm-up, and Tab. II and Tab. III report them without disper-sion, so the closest comparisons (the 13% CPU cell and the command-line comparison) should be read as ties. The latency distributions of Sec. IV-C were measured without pacing or real-time priority. VI. C ONCLUSIONS AND FUTURE WORK 

Fluxion implements the DSP-specific numerical code (closed-form design, forward kernels, analytic adjoints, and stability checks) and uses existing libraries for autodiff, GPU code generation, and array interchange. One graph algebra is lowered to a training engine and to a real-time engine whose audio thread we test for allocations, and the freeze step carries a checked artifact from training to the edge device, including checkpoints imported from FLAMO and TorchFX. Future work includes testing the Metal, ROCm, and We-bGPU kernels on hardware, making the feedback operator dif-ferentiable and usable in real time with a loop-aware stability check during training, adding frequency-sampling gradients as a training option, and defining versioning and rollout policies for DSP updates on many devices. We do not plan fp16 or bf16 execution, because recursive filters are sensitive to coefficient quantisation at half precision. DISCLOSURE OF AI U SE
