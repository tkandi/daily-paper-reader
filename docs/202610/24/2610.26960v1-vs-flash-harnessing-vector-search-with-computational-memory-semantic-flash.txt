## Abstract 

As generative AI continues to evolve, retrieval-augmented generation (RAG) systems are driving rapid growth in vec-tor database capacity requirements. As datasets outgrow host DRAM, vector databases rely on MMap-based serv-ing over SSDs to extend capacity. However, high-fan-out ANN searches generate concurrent irregular accesses that contend for host memory and storage resources, degrading bulk throughput and inflating tail latency under mixed work-loads. In this paper, we address these challenges through memory-semantic capacity and workload-aware compute placement. VS-Flash exposes flash as a large-capacity memory-semantic space and dynamically selects the execution engine accord-ing to runtime query and workload characteristics. It offloads throughput-oriented large-batch queries to a Computational Memory-Semantic Flash (CMS-Flash) device, while execut-ing latency-sensitive small-batch queries on the host CPU. Both paths access the same resident segments, avoiding a separate host-DRAM replica. Across three billion-scale datasets, VS-Flash improves bulk-search throughput over vanilla Milvus by 36.8 × on av-erage, with up to a 57.4 × improvement. Under mixed work-loads, VS-Flash reduces the p99 latency of latency-sensitive requests by up to 24.8 × while sustaining device-side bulk search. These results show that VS-Flash delivers scalable vector search beyond host DRAM capacity while jointly im-proving bulk throughput and small-request tail latency. 

## 1 Introduction 

Vector similarity search is a core operation in retrieval-augmented generation (RAG), recommendation, and semantic retrieval [20, 23]. Vector database management systems such as Milvus [31] commonly serve approximate nearest-neighbor (ANN) indexes through the host memory hierarchy [9, 24, 31]. When a vector-search dataset exceeds the DRAM capacity

available to a query node, Milvus’s MMap-enabled Data Stor-age feature retrieves index pages and vectors on demand. The resulting fine-grained accesses during irregular ANN traversal contend for limited DRAM capacity and repeatedly invoke host-OS page placement and page-fault handling. VS-Flash replaces demand paging with a segment-centric, data-centric execution model in which segment residency governs both data movement and computation placement. It explicitly stages whole active segments from flash in device DRAM, then executes large-batch searches on device-side many-core resources beside the resident data. The same seg-ments remain directly accessible to the host CPU, allowing latency-sensitive small batches to execute without a separate host-DRAM replica. This organization couples computation offload with shared segment access, rather than treating data placement and execution as independent decisions. In summary, we make the following contributions: • We identify asymmetric interference in Milvus MMap serving: throughput-oriented large batches intensify host-side memory contention and degrade the latency of small batches under mixed workloads. • We design VS-Flash, which preloads whole segments into device DRAM, executes bulk search on a CMS-Flash device, and routes latency-sensitive requests to the host CPU without a host-DRAM replica. • We implement VS-Flash in Milvus with a device-side ANN runtime and evaluate bulk-search throughput and mixed-workload tail latency.

Each sub-search is assigned to an independent thread and produces a local top-k candidate list. The Query Node then merges the per-segment candidates into a final top-k result [9, 31]. For an HNSW index, each sub-search follows query-dependent graph neighbors within its target segment and repeatedly accesses index and vector data along an irregu-lar traversal path [21]. MMap-enabled Data Storage. Milvus conventionally keeps the index and vector data in host DRAM. As RAG databases grow beyond the available DRAM capacity, keeping the en-tire database resident becomes impractical. To support these larger datasets, Milvus utilizes memory mapping to retain only lightweight metadata in DRAM while accessing index and vector pages from SSD-backed files [9,31]. A page enters the page cache only when an ANN traversal accesses it. If the page is resident, the traversal continues from memory. Otherwise, a page fault triggers a storage-backed page-in. Concurrent sub-searches access many pages irregularly, competing for limited page-cache capacity and storage I/O bandwidth. Repeated eviction and refetching cause page-cache thrashing, while simultaneous page-ins contend for the storage path, adding latency beyond graph traversal.

Design Requirements. The observations lead to three design requirements. Fine-grained demand paging must be replaced with bulk movement at the segment granularity. Because large batches prioritize aggregate throughput over per-query latency, they should be executed on a highly parallel, many-core sub-strate rather than one optimized primarily for host-CPU-class single-core performance. Latency-sensitive small batches, in contrast, require a separate CPU execution path. Both paths must compute directly on a shared data representation with-out copying search data between host and device memories, thereby avoiding redundant memory consumption. 

Target Device. Figure 3 shows the XCENA MX1P device used as our CMS-Flash: a CXL [3] Type-3 device that com-bines flash-backed capacity, device DRAM, and many RISC-V cores. Its many-core design benefits bulk batches that ex-pose parallelism across queries and segments, whereas its modest per-core performance makes the device path less suit-able for small requests. Device-side bulk search remains close to active-segment data, while CXL exposes device DRAM to the host CPU, allowing both paths to access the same data representation.

## 3 VS-Flash Design 3.1 Overview 

VS-Flash targets memory-constrained vector-search serv-ing in which a dataset exceeds host-DRAM capacity and throughput-oriented large batches coexist with latency-sensitive small batches. VS-Flash decouples vector-search capacity from host DRAM by storing ANN indexes and vec-tors in flash and explicitly staging active segments in device DRAM. As Figure 4 shows, Memory-Semantic Flash exposes this flash-backed segment space to the host CPU over CXL, and device DRAM holds the active segments so that both the host CPU and device-side RISC-V cores work from the same memory; host DRAM does not need a duplicate index or vec-tor store. Batch Dispatcher prioritizes device-side execution and uses RISC-V cores utilization to determine when to route the smallest pending batch to the host CPU, while Preload Manager keeps the bulk-critical active segments required by the device path resident. Both paths return only per-segment top-k results, which the host merges.

When database capacity grows without a commensurate increase in host DRAM, the page cache retains a smaller fraction of the working set and demand paging generates greater host-memory contention. Milvus also fans each query batch out into segment-level sub-searches. A larger segment count can increase the number of concurrent sub-searches, further amplifying page-cache and TLB contention under irregular ANN access. VS-Flash in-stead transfers the ANN index and vector payload required for a search from flash to device DRAM in bulk at segment gran-ularity. Whole-segment transfers are therefore better suited to high-fan-out search: explicit, device-managed data movement replaces demand-paged fine-grained accesses during ANN traversal. As a result, even when the database greatly exceeds host DRAM capacity, this execution path avoids host-OS page-cache management and page-fault handling. 

Computation Offloading. Once a segment is resident in device DRAM, VS-Flash offloads its query–segment sub-searches to the CMS-Flash. A large batch provides many inde-pendent query–segment pairs, which are distributed across the device’s RISC-V cores. Each core performs ANN traversal or probing, distance computation, and local top-k selection near the resident index and vectors. The host dispatches work and merges per-segment top-k lists, while the device returns only these compact results rather than vector data, index pages, or complete candidate payloads. Device-side parallel execution increases bulk-search QPS while avoiding transfers of index pages, vectors, and full candidate payloads to the host.

Batch Dispatcher: Batch-Aware Routing. Large batches generate enough query–segment sub-searches to exploit device-side parallelism, whereas latency-sensitive small batches contribute relatively few sub-searches to each target segment and can require a wider, changing set of segments. As Figure 5 illustrates, Batch Dispatcher directs the latter requests to the host CPU while prioritizing the device-side path for bulk work. Because Memory-Semantic Flash ex-poses the same resident segments to both paths, this decision changes the execution location without copying the index or vector payload. Batch Dispatcher maintains a batch-size routing threshold based on device-side RISC-V core utiliza-tion. When this utilization exceeds 80% and the host CPU path is idle, the dispatcher adjusts the threshold on each new request arrival so that the smallest pending batch is routed to the host CPU. This adjustment diverts only the lowest-batch work and keeps the remaining requests on the device-side path. Both paths return only per-segment top-k results for host-side merging. 

Preload Manager: Explicit Segment Residency. The CMS-Flash device executes searches from device DRAM. It therefore brings a segment’s ANN index and vector pay-load into device DRAM before computation; we refer to this whole-segment transfer as preloading. VS-Flash uses a device-defined 1 GB segment as the unit of preloading, res-idency, placement, and search, and Preload Manager main-tains segment-keyed waiting queues for pending sub-searches. A large batch fans out many sub-searches to each bulk-critical unit. Consequently, a small resident set can provide enough parallel work to keep the device-side RISC-V cores computation-bound. The look-ahead window controller adjusts its depth N to-ward the smallest value that sustains computation-bound ex-ecution. For every preloaded segment, it measures the inter-val from becoming resident to exhausting its queued large-batch sub-searches, and compares this consumption time with the flash-to-device-DRAM refill latency. ## 4.2 Performance Results 

Throughput on Billion-Scale Datasets. Figure 7 compares vanilla Milvus, VS-Flash-Stage, and VS-Flash across the three billion-scale datasets. VS-Flash improves through-put over vanilla Milvus by 23.9 ×, 57.4 ×, and 36.4 × on SIFT1B, Deep1B, and Text2Image1B, respectively, for a 36.8 × geometric-mean improvement. Across the workloads, explicit whole-segment staging provides a 10.4 × average im-provement, and device-side execution provides a further 3.5 ×

average improvement over VS-Flash-Stage. VS-Flash achieves high throughput on SIFT1B, Deep1B, and T2I, with the largest gain from device-side RISC-V many-core offloading on Deep1B. Deep1B uses lower-dimensional vectors than the other datasets, shifting the dominant cost from compute-intensive distance evaluation toward the lighter-weight operations of HNSW graph traversal. As a result, the lower per-core compute performance of the device-side RISC-V cores has a smaller effect on search latency, while large batches still expose ample query–segment parallelism for the many-core device. 

Mixed-Workload Latency. Figure 8 reports p99 latency as the number of concurrent batch-600 clients increases. VS-Flash-Stage substantially reduces the p99 latency of both batch classes, showing that explicit segment staging avoids the demand-paging and storage contention incurred by vanilla Milvus. VS-Flash provides the largest reduction under high bulk pressure: with eight batch-600 clients, it reduces batch-600 and batch-25 p99 latency by 32.9 × and 24.8 ×, respec-tively. The benefit grows with bulk concurrency because Batch Dispatcher directs latency-sensitive batch-25 requests to the host CPU rather than allowing them to queue behind throughput-oriented device-side work. This separation also protects the bulk path: by removing small requests from the device-side queue, the RISC-V cores remain available for batch-600 execution. Thus, VS-Flash not only eliminates the demand-paging bottleneck, but also sustains high-throughput bulk search while protecting latency-sensitive requests under severe mixed-workload interference.

Tail Latency and Multi-Tenant Interference. Prior work shows that contention for shared CPU, memory, and I/O resources can severely degrade individual tenants’ tail la-tency [4, 7, 14, 18, 22, 26]. Existing approaches primarily con-sider general purpose storage or relational workloads, rather than vector-search interference caused by irregular ANN ac-cess, search fan-out, and page faults. VS-Flash addresses this gap for batch-heterogeneous vector-search workloads. 

Near-Data and CXL-Based Vector Search. Prior work moves ANN computation closer to data to reduce data move-ment and resource pressure [1, 25, 30, 32, 33]. ANSMET accelerates distance computation with DIMM-based near-memory processing and hybrid early termination [19]. Cos-mos offloads full ANN search to CXL-embedded cores, al-beit evaluated in simulation, while FusionANNS partitions SSD-resident ANNS between CPU filtering and GPU re-ranking [16, 29]. Other systems explore CXL-memory offloading, hardware acceleration, CPU/GPU/NPU partitioning, or SSD I/O pipelin-ing [8, 10, 11, 12, 13, 15, 17]. Unlike these systems, VS-Flash dynamically routes requests by batch size between the host CPU and device path to protect tail latency. 

## 6 Conclusion 

As vector-search databases outgrow host DRAM, MMap-based serving relies on demand paging during irregular ANN traversal. This approach creates host-memory and storage con-tention, particularly when throughput-oriented large batches coexist with latency-sensitive small batches. VS-Flash re-places demand paging with explicit whole-segment residency in device DRAM. It executes bulk searches on device-side 6cores while allowing the host CPU to access the same resident segments for small requests without a host-DRAM replica. Our evaluation shows that this organization improves bulk-search throughput and protects small-batch performance un-der mixed workloads.
