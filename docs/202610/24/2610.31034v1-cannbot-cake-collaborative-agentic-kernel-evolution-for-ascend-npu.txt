# ABSTRACT 

Efficient custom operators are essential for modern deep learning workloads, yet developing high-performance kernels for Ascend NPUs remains slow, expert-intensive, and difficult to automate. Although AI agents now approach expert performance on GPU kernel benchmarks, current models remain less capable of generating AscendC kernels for NPUs, potentially reflecting the relative scarcity of relevant training data. We thus present CAKE, a CANN-native system for deployable custom operators that combines adaptive multi-DSL routing, separate Generation and Evolution modes, and reviewed knowledge reuse through CAKE Book and a Self-Evolving Agent. On 53 CANN-Bench v1.1 operators on Ascend 950PR, CAKE’s aggregated results achieve 100% case pass rate on the standard set (1,060/1,060) and 98 .28% on the hidden set (4,167/4,240), with an overall mean score of 78.63 out of 100 and an average performance speedup of 1.334 × over the baseline. Evolution then pushes correct operators further: EngramGateFusion cuts aggregate device time by 46 .6% over 20 rounds and roughly halves the mean roofline gap. These results offer a practical path toward closing Ascend’s AI-for-kernel capability gap. 

Keywords Agentic systems · Ascend NPU · CANN · AscendC · Kernel generation · Evolutionary optimization 

# 1 Motivation and System Overview 

An accelerator reaches its advertised throughput only when every operator in a model is backed by an efficient, hardware-tuned compute kernel. Kernel quality, not a chip’s peak throughput, sets end-to-end performance, and writing these kernels by hand is slow and demands scarce low-level expertise. Automating that work has become an active research target. Large language models have made that target newly reachable: coupled with execution feedback and search, they can generate correct and competitive GPU kernels. This progress rests on a favorable ecosystem. CUDA and Triton expose abundant open kernels, documented optimization idioms, and large public code corpora, so a model can recognize and adapt patterns it has effectively already seen. NPUs such as Ascend offer no comparable foundation; their vendor programming model, AscendC, appears only sparsely in public data. In published evaluations, general-purpose models succeed on essentially none of the complex AscendC kernels they attempt in a zero-shot setting [1], and one-shot AscendC pass rates remain at or below 2.1% 

where CUDA reaches 44 .2–52 .6% [2, 3]. These results motivate supplementing pretrained models with Ascend-specific programming knowledge and execution feedback.

The consequence for a code-generating agent is that an Ascend operator is not a single kernel but a two-part artifact [3]: a host-side tiling program that decides how data are partitioned and moved, and a device-side kernel that decides how computation is scheduled. Performance is a property of the coordination between these two components: tiling determines the data available to each core, while the device kernel schedules computation and transfers. In practice the bar is higher still. The unit an engineer can actually ship is neither a host program nor a device kernel in isolation, but a deployable CANN custom operator : one that builds, packages, installs, binds to Python, passes precision checks against a reference, and profiles on real hardware. Recent Ascend systems each automate one slice of this chain (Section 1.1 and Table 1)—training a model, transcompiling a domain-specific language (DSL), optimizing an existing kernel, or supplying curated domain knowledge to an evolutionary search. The last of these, AgenticCANN, is the closest prior system to ours and the one that most directly confronts the corpus problem: it organizes AscendC expertise into a six-level taxonomy, from hardware mental model down to verified kernel exemplars, and injects the levels selectively by evolutionary phase, raising the share of elementwise kernels it can synthesize from 57% to 86% on Ascend 910B [4]. This demonstrates the value of explicit domain knowledge. Its reported feasibility also varies by operator family: 90 –100% on elementwise and normalization operators, but 56% on fusion, over a private 54 -operator sample. These results motivate a workflow that carries generated code through packaging and deployment while reusing the results of previous runs. Such a workflow needs to retain intermediate artifacts for debugging, use evaluation outcomes to guide generation, and make useful lessons available to later tasks. We present CANNBot-CAKE (hereafter CAKE), an open-source CANN-native agentic workflow released in CANNBot, Huawei’s official repository for Ascend agents. 1 CAKE generates and evolves deployable Ascend operators from either a natural-language requirement or an existing AscendC baseline. CAKE uses existing language models to coordinate these stages. A request becomes an operator contract, then a PyTorch reference, a functional form, a routed DSL baseline, host-side tiling, device AscendC code, a CANN package, a Python binding, and an evaluation record—each a durable object that can be inspected, validated, and reused. A multi-DSL router chooses among four code-generation tracks using the operator’s structural features and previous evaluation scores. It also explores less-tested tracks that may perform better. Generation mode produces one deployable operator through generation, validation, and repair. A profiling assistant, the Advisor , diagnoses performance bottlenecks and suggests changes. Evolution mode (CAKE-evo) runs a multi-round campaign that reuses shared artifacts, spawns isolated variants, and ranks them by compilation, precision, and performance. Candidates are scored by automated evaluation on CAKE-Bench, a user-defined evaluation suite that we instantiate with the official CANN-Bench task set [5]; a self-evolving agent mines those measured runs to improve the router, skills, and repair templates; and a cross-user knowledge base, CAKE Book, accumulates verified lessons in interlinked wiki pages [6]. First, a CANN-native staged pipeline (CAKE-Agents) turns operator intent into a deployable custom operator through Generation and Evolution modes, exposing every stage—contract, reference, DSL, host tiling, kernel, package, binding, and evaluation—as an inspectable object. Third, a Skills harness of more than thirty typed lifecycle tools—for description, lowering, optimization, evaluation, and debugging—gives the agents a reusable substrate for operator engineering (Section 2.1). Fourth, CAKE Book accumulates verified CANN experience as a cross-user wiki, shared and updated across users and agents and queried before generation. Routing. Learned routers such as RouteLLM dispatch a query to a stronger or weaker model [15], and compiler auto-schedulers such as Ansor use learned cost models to select a schedule within a single intermediate representation [16]. Kernel-generation agents, by contrast, are largely single-DSL [1, 7, 11]; the few that span several backends either expose support for multiple DSLs without a published selection rule or defer the choice to an opaque per-kernel agent decision [12, 17]. CAKE instead scores four peer code-generation tracks under a published rule: an item-response model estimates each track’s ability per structural dimension from past evaluated operators, so that the ordering of tracks changes with the operator rather than being fixed, and every decision is recorded with the candidate estimates that produced it (Section 3). 

Agent memory and knowledge bases. Agent memory has progressed from per-episode self-reflection [18] and single-agent skill or experience libraries [19, 20] to self-linking memory notes [21], and recently to sharing across actors through banked lessons for cooperating code agents [22] and provenance-tracked multi-user memory [23]. In the same Ascend domain, AscendOptimizer mines a single-agent experience bank for kernel rewriting [3], and AgenticCANN supplies a hand-authored taxonomy of AscendC knowledge as retrieval context [4]. CAKE Book combines three properties: it is an agent-maintained wiki of interlinked pages with an explicit error notebook rather than a flat store; it is written by the runs it serves, so its contents grow with measured evidence rather than with expert authoring effort; and its entries become canonical only after cross-user, human review and on-device verification. 

4Self-evolving agents. A growing body of work studies agents that improve themselves: recursive self-referential systems rewrite their own scaffolding [24, 25], automated agent-design methods search the space of agentic architectures [26], and evolutionary approaches maintain populations of self-modifying agents validated by benchmark fitness [27]. In the kernel domain, agentic systems evolve archives of optimized kernels [28]. CAKE’s Self-Evolving Agent targets the generation workflow. It mines many completed generation and profiling runs to promote evidence-gated improvements into the router, skills, repair templates, and CAKE Book. 

# 2 From Intent to Deployable Operator 

CAKE divides operator development into stages with explicit inputs, outputs, and validation checks. Each stage produces an artifact used by subsequent stages, allowing failures to be diagnosed before the workflow proceeds. • Operator contract generation. The request (or an api_description.md ) is compiled into an 

operator contract (op_desc.json ): the single source of truth for the operator’s identity, semantic formulas, representative I/O with dtype/shape constraints, attributes, and case table. Every later stage derives its signature from it, including the schema features that are otherwise lost downstream — 

is_list , optional , string-attribute enum s, output_shape derivations, and channel-first layout .• Reference and functional forms. CAKE builds a PyTorch reference, preserving a supplied imple-mentation verbatim and fixing random seeds for reproducibility. It then converts the reference to a stateless module_fn . The reference defines expected outputs for correctness checks, the test inputs exercise both reference and generated code, and the functional form exposes dataflow for routing and lowering. • Multi-DSL router. The router represents the contract and functional form as an eight-dimensional structural profile, removes tracks that cannot support the operator type or target device, and scores the remaining tracks using previous evaluations. Section 3 describes the model. Users can instead specify a track directly through the contract’s dsl_track field. • Lowering and project construction. The selected track lowers the functional form into host-side tiling and device-side code while preserving the contract as the interface authority. CAKE materializes the generated source, build configuration, tiling metadata, wrappers, and project skeleton as separate artifacts so that a failure can be localized to a stage rather than attributed to an opaque model response. • Package, install, and bind. A candidate is built as a CANN custom-operator package, installed into the pinned environment, and exposed through the generated Python binding. These stages are part of the deliverable rather than post-processing: code that compiles as a kernel snippet but cannot be packaged or invoked does not count as a completed operator. • Evaluate and repair. The installed operator is executed against the reference under dtype-aware precision checks and on-device timing. Compilation, packaging, binding, correctness, and profiling results are written next to the candidate. The resulting evidence routes the next action: build failures return to lowering or project construction, numerical failures return to the contract, reference, or tiling assumptions, and correct but slow candidates enter profiling-guided repair or Evolution mode. The unit of progress in this lifecycle is therefore an artifact plus its validation record. A run can stop at a failed intermediate stage without losing the evidence needed to diagnose it, while a successful run leaves a package, binding, test record, profile, and provenance trail that another engineer or agent can inspect. These records support both optimization within the current run and knowledge reuse across runs. 

2.1 The Skills harness 

The stages above describe what is produced; the Skills harness is what executes them. A skill is a typed lifecycle tool: it names the artifact it consumes, the artifact it writes, and the condition under which its output 

5is admissible. The orchestrating agent does not contain the procedures — it declares the skills it may call, currently more than thirty, and the runtime resolves each call against that declaration. Adding a capability therefore means adding a skill and listing it, not editing the agent. The harness coordinates skill selection, validation, and failure recovery. 

Stage binding, with track-specific variants. Skills are bound to stages rather than invoked ad hoc. Contract, reference, functional conversion, and tiling pre-classification are shared by every run; the router then selects a code-generation track, and the lowering stages dispatch to the variant of each skill specialized for that track — separate lowering and call-generation skills exist for the Vector and the fused Cube–Vector paths, so that the difference between them lives in the harness rather than inside a branching prompt. Review, evaluation, Advisor-guided repair, and run retrospective are shared again. A track is thus a path through a fixed skill graph, which is why the router’s choice is auditable after the fact. 

Stage validation. A stage advances only when its artifact passes a machine-checked gate. The contract illustrates these checks: before any code is generated, the op_desc is checked for dtype coverage against the full case table, for signature agreement with the task’s declared schema, and for the shape metadata that packaging later depends on. These checks catch incomplete dtype coverage, argument mismatches, and missing output-shape metadata before they propagate to compilation or packaging. A failed check returns control to the stage that produced the artifact. 

Execution tracing and failure recovery. Two cross-cutting skills record execution and coordinate repairs throughout a run. Every skill call is bracketed by a trace record, so a run leaves a complete, machine-readable account of which skills fired, in what order, and with what outcome — this trace is the input the self-evolving agent of Section 5 reads to identify recurring skill failures. Alongside it, a test-driven meta-skill governs what happens on failure: a diagnosis is treated as a hypothesis that stays open until an end-to-end pass closes it, and a failure mode seen twice must be pushed back into the lowering step or the project skeleton that permitted it rather than accumulated as another entry in a pitfall list. Retries are bounded, and a stage that does not pass its gate produces no commit, so the version history records the stages that cleared their checks. 

# 3 Adaptive Routing and Generation 

CAKE carries four code-generation tracks that can each produce a deployable operator: DSL-A , the mature AscendC-lowering track that covers both vector and cube–vector operators on the 910 series; DSL-B , a high-level tile DSL whose strength is cube–vector topology; DSL-C , the vector and cube–vector generation track for the 950; and the SIMT track detailed in Appendix A.5. A track is an implementation route , not an operator class: whether an operator is vector, cube–vector, or SIMT-shaped is an input to the routing decision, and several tracks compete for the same class. Track performance depends on both the operator’s structure and the current code-generation skills. A track that works well for one operator family may perform poorly on another, and skill updates can change this relationship. CAKE therefore estimates track suitability from previous evaluations. The router has four components (Figure 2): a feasibility gate, a feature extractor, a scoring layer, and an append-only observation ledger. 

L0: feasibility gate. A declared capability table marks each (track, chip, operator type) triple feasible or not, and infeasible tracks are removed before any scoring happens. This prevents attempts on unsupported configurations. Forward binary compatibility widens the declared set (a track feasible on 910B is feasible on 910C). On the 950, only DSL-C is feasible for vector and cube–vector operators, so those operators land on DSL-C without any scoring; and the SIMT track exclusively owns the SIMT operator type, which no other track accepts, so the two never compete. When the gate leaves nothing feasible, the router 

abstains : it emits no decision and hands the model the full track menu with each track’s skills. Abstention has two causes that are reported separately — an unrecognized device string, so that no gate can be applied at all, and a recognized device on which the requested operator type has no feasible track.

Evaluation ledger and skill versions. The observation ledger is append-only and grows one row per evaluated operator: the track used, the device, the difficulty and feature vector, the achieved normalized score, and a fingerprint of the code-generation skills that produced it. Any evaluation harness that returns a per-operator score on a comparable scale can supply y — CAKE-Bench’s per-operator score is one such source, a user’s own metric is another. This allows new operator evaluations to update the router without rerunning a fixed benchmark suite. Observations flagged as infrastructure failures, as reward-hacking candidates, or as internally inconsistent submissions are retained in the ledger but excluded from ability estimation. To account for changes in code-generation skills, the router identifies each track configuration by the pair (track, skill_version) : observations from a superseded skill version enter estimation at half weight, which widens the posterior and prompts re-measurement of the updated track. New evaluations receive full weight. 

Selecting tracks for exploration. Testing a track requires a full generation, build, and evaluation cycle. CAKE limits these additional evaluations using two criteria. A Bernoulli-style information proxy I = p(1 −p)

at the current estimate is the eligibility heuristic. For the continuous scores modeled here, this is not the Fisher information of the beta likelihood. An optimistic upper bound θ + 1 .96 se identifies tracks that could outperform the currently preferred track. Among eligible alternatives, the router selects the one with the highest upper bound. Thus, the information proxy controls eligibility, while the upper bound determines which alternative to test. Ranking by the information proxy alone would instead favor scores near 0.5, where 

p(1 − p) is largest. After a skill update, the router compares how many current-version evaluations are available for each track. Tracks with fewer observations than their peers receive a re-measurement bonus. If all tracks are equally under-sampled, no differential bonus is applied; the ordinary eligibility and upper-bound criteria still govern exploration. 

The routing loop. Each completed evaluation updates the evidence used for subsequent routing. At the routing stage the router writes its decision next to the operator’s artifacts, together with the full candidate snapshot — every feasible track’s ability estimate, predicted normalized score, information proxy, and skill fingerprint. At the evaluation stage the achieved score is written back as a new observation, the affected track’s posterior moves, and the next operator of similar character may route differently. Both events are also appended to a central timeline, which also records abstentions and routing errors. The saved features, scores, and skill versions allow a past decision to be reconstructed using the information available at the time.

4.2 The evolutionary loop 

Each round (Fig. 5) generates N variants in parallel, assigning each an optimization direction based on the identified bottleneck. For example, a memory-bound chain may benefit from fusion, while a compute-bound kernel may benefit from different tiling or instruction scheduling. Candidates are compiled, evaluated, ranked by speedup, and grouped into good, medium, and poor tiers. The next round samples implementations from these tiers as starting points. During advisor-in-the-loop consultation (AIC), the Advisor examines the profile of the best candidate and supplies bottleneck-specific suggestions for the next round. The search stops when the measured runtime approaches the modeled floor (headroom ≈ 1, Fig. 4) or the round budget is exhausted. Post-evolution mining (PMR) then extracts validated optimizations as candidate rules for reuse on other operators.

# 5 CAKE Book and System-Level Self-Evolution 

Evolution mode improves one operator implementation by searching over candidate variants under a fixed operator contract. CAKE also contains a system-level improvement loop whose target is the generator itself. This loop is implemented by two cooperating components: CAKE Book, an LLM Wiki-based agentic knowledge-management system, and the Self-Evolving Agent, a persistent AI agent that monitors CAKE runs and turns observed engineering experience into human-reviewed improvements. Together they make CAKE less dependent on a single model’s prior knowledge: compilation failures, profiling signals, successful optimizations, and human corrections become reusable system memory. 

5.1 CAKE Book as Agent-Native Reference 

CAKE Book is the knowledge layer used by CAKE agents before, during, and after operator generation. Following the open-source LLM Wiki pattern, CAKE Book maintains wiki-style pages with bidirectional links, source metadata, hardware and CANN-version tags, trust and recency weights, and an error notebook for recurring Ascend/CANN development failures. Human review remains available for proposed knowledge and repository updates. The design enables knowledge reuse in later CAKE runs; its causal effect on success and performance is not isolated by the current evaluation (Section 6.2). CAKE Book complements the static references packaged with individual skills. Static skill references capture stable procedures such as artifact schemas, prompt contracts, code templates, and evaluation commands. CAKE Book captures knowledge that changes with experience: version-specific compiler 

13 behavior, newly observed CANN packaging traps, operator-family tiling lessons, 950 Regbase/SIMT notes, profiler interpretations, and workarounds that have only recently been validated. When a skill needs such context, it can query CAKE Book as a task-time reference source. The returned context is ranked not only by semantic similarity, but also by link structure, evidence quality, hardware and software compatibility, freshness, and human review status. CAKE Book supports both retrieval and updates. For retrieval, an agent or skill submits the current task context, retrieves relevant wiki pages and linked error notes, ranks them by evidence, and packs the result into an agent-ready reference. For updates, a completed run contributes new observations: a compiler error and its fix, a profiler bottleneck and the code change that removed it, a DSL route that repeatedly failed for an operator family, or a human review note that corrects an agent assumption. CAKE Book deduplicates these observations, attaches provenance, and exposes them for review before they become trusted references for future agents. 

5.2 Run Evidence from the CAKE CI Platform 

The Self-Evolving Agent observes CAKE through the CAKE CI Platform. The platform standardizes generation and evolution runs and exposes a CLI through which an agent can inspect run status, logs, and artifacts. For each run, the agent can retrieve the operator contract, generated PyTorch reference, functional form, DSL baseline, AscendC project files, build logs, CANN package and install logs, evaluate.py 

outputs, profiling CSVs, skill traces, PROGRESS.md , evolution reports, Advisor state, issue or pull-request links, and user annotations. These artifacts preserve both successful paths and failed attempts, which is essential because many reusable CAKE lessons are negative: which route compiled but failed precision, which template broke on non-aligned shapes, or which Advisor suggestion did not transfer to a neighboring operator family. The CI interface also makes self-evolution measurable. Runs can be grouped by operator family, DSL route, target chip, CANN version, input mode, evaluation case type, and final status. This lets CAKE Book distinguish local anecdotes from repeated patterns and lets the Self-Evolving Agent detect regressions after router, template, Advisor, or reference changes. Linking an update to its source runs also allows later evaluations to check whether the same failure recurs. 

5.3 Self-Evolving Agent 

The Self-Evolving Agent runs continuously, checking newly available CAKE CI Platform runs. It reads the corresponding artifacts, and records observations through CAKE Book. Its daily work resembles an engineer’s maintenance loop: summarize recent CI successes and failures, identify repeated failure modes, compare them with existing CAKE Book pages, notice when a previously useful rule becomes stale, and identify cases where a dynamic lesson should become part of the repository. When the observation is purely knowledge-oriented, the Self-Evolving Agent interacts with CAKE Book directly. For example, it can add a new error-note page for a CANN compiler diagnostic, link it to the affected operator family and CANN version, attach the run IDs that demonstrate the workaround, and mark the page as pending human review. When the observation implies a code or repository change, the agent opens an issue or pull request against the CAKE repository. Typical pull requests include adding a static skill reference, improving a DSL prompt, tightening a lowering check, documenting a new Advisor rule, extending an evaluation audit, or updating router guidance for a hardware-specific path. Merging remains a human decision; the agent proposes changes and attaches evidence, while maintainers decide whether the evidence is sufficient. This separation keeps the self-evolving loop auditable. CAKE Book can absorb fresh, uncertain, or version-specific experience quickly without silently rewriting the public pipeline. Repository changes are slower and require review, but once merged they improve the baseline behavior of all later agents. In this sense, CAKE Book is the fast memory of the system, while the static skill references, router rules, templates, and Advisor rules are the stabilized memory. 

14 5.4 Reference Promotion and Governance 

Reference promotion is the bridge between dynamic and static knowledge. A CAKE Book entry becomes a candidate for promotion when it is repeatedly useful, supported by concrete run evidence, scoped to clear hardware and software versions, and stable enough that future agents should see it without issuing a live CAKE Book query. The Self-Evolving Agent prepares the promotion by linking successful and failing runs, summarizing the lesson, identifying the affected skill or rule file, and opening an issue or pull request. Human reviewers then check whether the proposed reference is correct, sufficiently general, and safe to apply across future runs. Governance is especially important because Ascend/CANN behavior changes across hardware and software versions. CAKE Book entries therefore carry provenance: run IDs, operator families, target chip, CANN and torch-npu versions, input shapes, pass/fail status, profiler files, and reviewer notes. Conflicting evidence does not overwrite older knowledge; it creates versioned or scoped pages. Stale-rule detection is handled in the same evidence-backed way: when CI runs show that a promoted rule no longer helps or begins to harm a route, the Self-Evolving Agent records the contradiction in CAKE Book and opens a follow-up issue or pull request for human review. Together, these components support knowledge reuse across runs. CAKE agents retrieve current lessons from CAKE Book during generation, CAKE CI Platform captures the full evidence trail of their attempts, the Self-Evolving Agent monitors that trail around the clock, and stable lessons move back into static skill references through reviewed pull requests. Operator-level optimization supplies the observations; repository review determines which lessons become part of the shared generation workflow.

# 7 Scope and Future Directions 

The CANN-Bench results cover 53 operators on both standard and hidden case sets. Router decision records illustrate operator-aware track selection, the EngramGateFusion campaign demonstrates iterative kernel optimization, and the CAKE Book records describe cross-task knowledge reuse. The aggregate benchmark results use Ascend 950PR; the Router examples and EngramGateFusion campaign retain their Ascend 910B/910C settings. Appendix A documents the programming paths and generation logic for Ascend 950. Further development will extend Evolution to additional operator families and expand the reusable knowledge available through CAKE Book. Future evaluations will examine routing and retrieval configurations under matched task sets and run budgets, and follow knowledge from CI diagnostics through reuse and reviewed reference updates. The aim is to improve operator coverage and performance while keeping generation cost and expert review effort practical. 

16 8 Conclusion 

CAKE organizes Ascend operator engineering around a unit larger than a generated kernel snippet: a deployable custom operator accompanied by its contract, reference, lowering artifacts, package, binding, evaluation record, and profile. Adaptive routing selects among changing code-generation tracks from accumulated operator evidence; Evolution mode searches within one operator contract using on-device feedback; and CAKE Book with the Self-Evolving Agent carries lessons across runs under human review. The aggregated CANN-Bench results show full standard-set case coverage and 98 .28% hidden-set case coverage across 53 operators on Ascend 950PR. The EngramGateFusion case study shows that Evolution mode can improve an already-correct operator under on-device feedback.

A.1 Register-level operand model 

Where the 910 path issues whole-tensor operations over UB-resident LocalTensor s ( membase ), the 950 exposes a register-level MicroAPI programmed through @vf micro-functions. The hardware-specific code-generation choices are therefore: • Register batches: RegTensor<T> holds a fixed VREG_SIZE -byte vector register rather than an arbitrarily large UB buffer. • Predication, not counts: active lanes are carried by a MaskReg predicate passed to every op, replacing the membase count argument. • Explicit addressing: gather/scatter index by raw byte offset with no bounds check. The regbase path offers LoadUnAlign /StoreUnAlign for UB ↔register movement, enabling unaligned access. • MicroAPI: add /sub /exp /log exist on both paths but operate on registers in the 950 MicroAPI. Operations without a supported register-level lowering, such as widening Mull or reading back a 

Squeeze count, retain their membase implementation. 

How Regbase reshapes the compute ceiling. Regbase is an architectural shift from classical SIMD to a 

dual-issue, register-based SIMD design: @vf kernels run micro-instructions directly on RegTensor operands held in the vector register file. Whereas each membase vector operation reads from UB and writes back, Regbase keeps the working set resident in registers across the micro-kernel. Removing those UB round trips moves the throughput limit from UB bandwidth toward instruction issue, widened by dual issue. 

A.2 SIMT block resources 

Each AI Vector core exposes a SIMT block that runs up to 2 048 threads organized in 32-thread warps, with warp-level shuffle, vote, and reduction intrinsics and 11-operation atomics on both on-chip and global memory. SIMT threads access the DataCache partition of the Unified Buffer—at most 128 KB, with the remaining UB capacity reserved for the SIMD path—and synchronize through block-wide barriers.

A.5 SIMT code generation 

Membase and Regbase execute predicated vector instructions over UB-resident or register-resident data. Some operators, including gather, histogram, and top-k selection, involve data-dependent addresses or control flow. Such patterns are not inherently inexpressible in SIMD: supported gather/scatter operations, masking, and staged data movement can implement many of them. However, some irregular patterns require additional transfers, predication, or serial processing, depending on the available APIs and lowering support. SIMT provides an alternative implementation path for these cases. The 950 SIMT execution model can reduce these overheads using the block resources summarized in Section A.2. The capability gate of Section 3 determines whether an operator can enter the SIMT track at all. The path is taken when two additional conditions hold beyond the Regbase/membase split: (i) the operator exhibits irregular or data-dependent memory access, and (ii) the irregular access is non-contiguous —contiguous scans with data-dependent predicates can remain on the SIMD path when supported by the available operations. Once on the SIMT path, a six-question decision tree (Figure 10) refines the choice among three programming models that trade generality for co-processor use. The simt-codegen skill implements this selection and generates the corresponding kernel structure.

Three programming models. Model A (pure SIMT ) is the most general: a single __global__ ker-nel launched with four-argument «<blocks, threads, ubuf, stream»> syntax, compiled with the 

-cce-enable-puresimt flag. It supports templates, struct arguments, and the full SIMT intrinsic set (warp shuffle, vote, atomics, cache hints) but cannot call the AscendC Micro API ( LoadAlign , DataCopy ,etc.). This model suits operators whose compute is entirely irregular—histograms, hash-table insertion, stream compaction—and whose output can be written directly to global memory. 

Model B (SIMT VF bridge ) wraps the per-thread compute in a __simt_vf__ free function dispatched from an __aicore__ entry via asc_vf_call . The three-argument launch integrates with msopgen project scaffolding (tiling macros, REGISTER_TILING_DEFAULT ), making it the default for operators that fit the standard CANN host/device contract—gather, cumulative sum, top-k with warp reductions. 

Model C (hybrid SIMT+SIMD ) extends Model B for operators that fuse an irregular access phase with a regular vectorizable phase. A __simt_vf__ function performs the data-dependent read and stages results into the DataCache; a __simd_vf__ function then runs the same SIMD vector pipe used by the Regbase path (adds, relu, exp) over the staged data; finally, DataCopy moves the result to global memory. The benefit 

22 of offloading arithmetic to SIMD depends on the workload and must be evaluated together with data-staging and synchronization costs; low SIMD utilization alone does not establish negligible overhead. A variant of Model C handles fused reductions (softmax, layer normalization): since __simd_vf__ cannot compile cross-element reductions ( ReduceMax , ReduceSum ), these are placed in the __aicore__ entry function using high-level AscendC APIs.
