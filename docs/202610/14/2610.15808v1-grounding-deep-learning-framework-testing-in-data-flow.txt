CHUNRONG FANG ∗, State Key Laboratory for Novel Software Technology, Nanjing University, China Data flow is important to many aspects of deep learning (DL) framework execution, such as automatic differentiation and operator-fusion optimization. Framework bugs involving data flow may therefore cause incorrect results or other unexpected behavior. Detecting such bugs, however, is challenging for existing testing methods that represent models primarily by operator topology. This representation records operators and their connections but omits runtime tensor values and properties as well as operator input requirements. Without this information, these methods cannot distinguish different data flows in models with similar topologies, even when those differences affect framework behavior. To address this gap, we introduce the Tensor Flow Graph (TFG) to capture the runtime tensor states of model test cases and their operators’ input requirements. Its nodes represent operators, and its edges represent tensors flowing between them. Each edge records the runtime values and properties of its tensor, while each node records the input requirements of its operator. Building on the TFG, we propose FlowMuT, a mutation-based testing method grounded in data flow. We represent mutations as constrained subgraph replacements in the TFG. FlowMuT mutation operators are derived from prior work and an analysis of mutable data flow objects. FlowMuT iteratively mutates a seed model and tests each resulting mutant. In each round, it builds a TFG for the current seed model, pairs mutation operators with TFG sites to form candidates, and filters illegal candidates using data flow constraints. It then uses LinUCB to select a candidate based on coverage and impact. After applying the selected mutation and executing the mutant, it updates selection feedback and uses each accepted mutant as the seed model for the next round. We evaluate FlowMuT on PyTorch and MindSpore using representative models from diverse application scenarios. FlowMuT submitted 55 bug reports for cases missed by all baseline methods. Developers confirmed 41 reports and fixed the bugs described in 7 reports. FlowMuT generates more diverse test cases, achieving 43.4% higher data flow diversity than the strongest baseline. It achieves a legal mutant rate of 96.7%, compared with 86.4% without constraints. These results show that testing from a data flow perspective is practical and effective. Incorrect intermediate values can affect gradient propagation, while an invalid fusion may change the computation represented by the original graph. Such bugs may cause incorrect results or erroneous behavior. Therefore, detecting them is important for DL framework testing [31]. Existing DL framework testing methods construct and execute test cases to detect framework bugs. Here, a test case is a DL model. Such a model is commonly represented as a computational graph (CG) that records its operator topology, which consists of its operators and their connec-tions [12, 13, 20, 24, 36, 50]. This description does not capture runtime tensor values and properties or operator input requirements, leaving test cases unorganized around data flow. Grounding DL framework testing in data flow presents three connected challenges. Figure 1 uses a scaled dot-product attention (SDPA) computation to illustrate these challenges. 

Challenge 1: Describing data flow. Existing methods describe a model using its CG, which records the operators and their connections but not the tensor values and properties (such as shapes, layouts, alias relations, and gradient states) that determine data flow behavior. Two model executions with the same CG may exercise very different data flow behavior. Without such data flow information, framework behavior under particular data flow states may remain untested. As Figure 1(a) shows, two executions of the same SDPA topology differ in tensor layout and storage aliasing. With separate contiguous copies, the computation produces the expected result; with expanded tensors that share storage, it exposes a framework bug. A CG records the same operators and connections in both cases and cannot capture the data flow state associated with the failure. 

Challenge 2: Generating legal test cases. Existing methods generate new test cases by applying mutation operators to the structures of seed models [12, 13, 20, 36, 50]. However, they overlook the complexity of the data flow surrounding mutation sites, where multiple tensors are produced and consumed subject to many interdependent constraints. Among other aspects, these constraints govern dtype and shape compatibility, operator input requirements, and whether a mutation preserves the intended tensor values; they must be satisfied simultaneously. Consequently, they generate a large proportion of illegal test cases whose failures do not indicate framework bugs. In Figure 1(b), a slice-and-expand mutation shares the 𝐾 and 𝑉 heads. Challenge 3: Achieving data flow diversity. A seed model can be mutated in many ways, but only a small subset of these mutations can exercise such behavior. Existing methods guide mutation selection using structural information about the model, but do not consider whether a mutation will exercise new data flow behavior. As a result, multiple test cases may repeatedly exercise similar data flow behavior, leaving other behavior untested. As Figure 1(c) shows, two mutations of equal heads satisfy the constraints. One clones them into separate storage, while the other shares them using slice and expand. Both preserve the original values but produce different layout and aliasing states. Whether either mutation exposes previously unseen framework behavior is unknown. To address these challenges, we introduce the Tensor Flow Graph (TFG), which represents a profiled model execution as operator nodes connected by tensor edges. Each edge records its tensor’s runtime values and properties, and each node records its operator’s input requirements. On the TFG, mutations are represented uniformly as constrained subgraph replacements (addressing Challenge 1) . Building on the TFG, we propose FlowMuT, a novel testing method grounded in data flow. Its operator pool combines CG-derived operators adapted from prior work with TFG-derived operators constructed from TFG objects and mutation primitives, yielding 147 mutation operators. In each mutation round, FlowMuT first builds the TFG of the current seed model, constructs mutation candidates by pairing operators with TFG sites using a novel and efficient algorithm, and filters illegal candidates using input, internal, and output constraints (addressing Challenge 2) .It then treats candidate selection as a bandit problem and uses LinUCB, a reinforcement learning method, to select a candidate based on coverage and impact (addressing Challenge 3) . Finally, it applies and executes the selected candidate, checks for framework failures, updates the selection feedback, and uses each accepted mutant as the seed model for the next round. We evaluate FlowMuT on PyTorch and MindSpore using 14 representative models from ten application scenarios. We compare it with three state-of-the-art DL framework testing methods (LEMON [50], COMET [20], and DevMuT [36]). The results show that FlowMuT detects 79 bugs, compared with 28 for the strongest baseline. We submitted 55 bug reports for cases detected only by FlowMuT. Framework developers confirmed 41 reports and fixed the bugs described in 7 reports. Analysis of a MindSpore crash detected by FlowMuT also revealed two denial-of-service (DoS) vul-nerabilities, both acknowledged by MindSpore’s security team. FlowMuT also achieves the highest data flow diversity among the evaluated methods, exceeding COMET, the strongest baseline on this metric, by 43.4%. It achieves a legal mutant rate of 96.7% with data flow constraints, compared with 86.4% without constraints. These results show that testing from a data flow perspective is practical and effective. In summary, the main contributions of this work are as follows. 

• Data Flow Representation. We introduce the TFG to organize DL framework testing around operator topology, runtime tensor states, and operator input requirements. 

• Mutation-Based Testing Method. We propose FlowMuT, which constructs and filters candidates from CG-derived and TFG-derived operators and uses LinUCB with execution feedback to guide selection. 

• Empirical Evaluation. We show that FlowMuT detects framework bugs missed by prior methods while improving data flow diversity and mutation legality.

2 Background and Related Work 2.1 Data Flow in DL Frameworks 

DL frameworks use data flow to execute models, propagate gradients, and optimize computations. Executing a DL model produces a sequence of tensors that flow between operators. The data flow 

of an execution consists of these produced and consumed tensors together with their runtime values and properties, such as shape, layout, numerical state, and gradient state. We distinguish this dynamic data flow behavior from operator topology , which records the operators in a model and their static connections. Operator topology describes the routes along which tensors may travel, whereas data flow describes what actually travels along those routes in a particular execution. Consequently, the same operator topology can realize different data flows under different inputs and execution conditions. The following two examples illustrate the role of data flow in automatic differentiation and in compilation and optimization. 

Automatic differentiation. Automatic differentiation follows the data flow produced during forward execution to propagate gradients. In PyTorch, operators construct an execution-specific graph as they run [38]. The automatic-differentiation engine traverses this graph in reverse and uses saved intermediate tensors and gradient states to compute derivatives. Work on testing automatic differentiation further shows that framework behavior can differ across forward, first-order-gradient, and higher-order-gradient execution scenarios [57]. Thus, gradient propagation depends on both operator dependencies and the runtime states of their tensors. 

Compilation and optimization. DL compiler research uses data flow information, including operator dependencies and tensor properties, to transform model execution. TVM combines graph-level transformations, including operator fusion, with operator-level tensor optimization [6]. For fusion, producer–consumer relations show which operators exchange tensors, while shape and layout information inform the fused implementation. nGraph and Glow introduce intermediate representations that progressively lower neural-network graphs toward executable code, enabling graph rewriting, kernel selection, and memory optimization [10, 42]. MLIR generalizes this or-ganization through reusable multi-level intermediate representations, while PyTorch 2 captures executed program regions for graph transformation and compilation [3, 18]. These systems use operator dependencies and tensor properties to improve execution, rather than to organize the generation of framework test cases. 

Comparison with prior work. Prior work establishes data flow as a basis for automatic differ-entiation and compiler optimization. The corresponding graphs and intermediate representations may record tensor types, dependencies, or other information required by their particular execution and optimization tasks. They are not, however, designed as a common mutation-testing abstraction. Existing testing work also uses operator constraints and execution traces for particular generation or checking tasks, as discussed next, but does not bring them together with profiled runtime tensor states to organize mutation construction, legality checking, and candidate selection. The TFG fills this role by jointly recording operator topology, runtime tensor values and properties, and operator input requirements for a profiled whole-model execution. 

2.2 DL Framework Testing 

DL framework testing constructs test inputs, executes them, and applies an oracle to identify crashes, incorrect results, or inconsistent behavior [7, 30, 35, 40, 45, 58, 61]. Methods can be grouped by the granularity of their test inputs: API-level testing exercises individual framework calls or short call sequences, while model-level testing executes complete models with connected operators [60]. The former probes operators under different arguments and execution contexts; the latter also exercises their interactions during model execution. Existing models can serve directly as tests, as Grounding Deep Learning Framework Testing in Data Flow 5

in CRADLE’s cross-backend comparison [40]. To construct new model-level tests, generation-based methods synthesize models from templates, grammars, or operator constraints, while mutation-based methods transform executable seed models. 

API-level testing. API-level methods vary tensor arguments, operator parameters, and execution contexts, sometimes in short call sequences. FreeFuzz mines argument types and values from documentation, developer tests, and models to generate API tests [52]. Other methods generate or refine API tests under different inputs and execution contexts [9, 11, 14, 17, 37, 43, 54]. These tests exercise framework APIs without requiring a complete DL model as a test case. 

Generation-based model testing. Generation-based methods synthesize models from graph templates, grammars, or operator constraints. Muffin builds models from directed acyclic graph structures and applies differential testing to forward propagation, loss computation, and backward propagation [12]. NNSmith incrementally constructs valid models using manually specified operator constraints and tensor-type propagation, and uses gradient-guided search to avoid exceptional floating-point values [24]. Gandalf combines grammar-based model generation with reinforcement learning and metamorphic relations to diversify generated models and their executions [23]. NeuRI further reduces the manual specification effort by inferring operator constraints from valid and invalid API traces and combining symbolic and concrete operators during model generation [25]. Other methods specialize model or program generation for compiler transformations, optimization passes, and particular execution environments [26, 29, 44, 59, 63, 64]. 

Mutation-based model testing. Building on model-level differential testing, LEMON mutates model structures and weights and uses a heuristic strategy to favor mutants that amplify cross-library output inconsistencies [50]. Audee combines mutations of model inputs, parameters, and weights with evolutionary search to produce executions with larger inconsistencies or anomalous numerical values [13]. COMET expands the mutation space and guides iterative mutation using coverage of layer inputs, parameter values, and layer sequences [20]. More recently, DevMuT derives mutation operators and legality constraints from developer expertise, uses Double-Q learning to select seed models and operators, and examines multiple stages of the model lifecycle [36]. These methods share a common workflow: they select a seed model, a mutation operator, and a site; generate and execute the mutant; and use an oracle and execution feedback to identify failures or guide later mutations [32, 62, 65]. 

Comparison with prior work. FlowMuT uses a profiled whole-model TFG for mutation construction, legality checking, and candidate selection. First, compared with API-level methods that vary calls and execution contexts, it mutates complete executable models and observes tensor states across operator connections. Second, among model-level methods, it follows mutation rather than generation from templates or operator specifications. Prior mutation methods primarily organize edits around layers, parameters, weights, or structural graph units; FlowMuT instead reprofiles each accepted mutant and uses its TFG to form and filter site-specific candidates using runtime tensor states and operator input requirements. It selects retained candidates using coverage and impact features. Section 3 presents the design.

They include tensor values and value summaries, shape, rank, dtype, device, memory layout, aliasing information, numerical properties, and gradient state. These requirements include properties of individual inputs, such as rank, dtype, device, layout, gradient state, and valid value range, as well as relationships among inputs, such as dimension compatibility, broadcasting, and device agreement. We construct 𝑅 (𝑣 ) by extracting operator input requirements from the official documentation and source repositories of the supported frameworks. For each operator, we normalize the extracted requirements into checks on individual input tensors and relations among multiple inputs, and attach the checks to the corresponding node annotation. Thus, 𝐹 (𝑒 ) describes the tensor in the data flow, whereas 𝑅 (𝑣 ) describes the tensors that a consumer can accept. Thus, 𝐺 identifies mutation sites, 𝐹 determines which mutation operators can be instantiated, and 𝑅 checks their compatibility with the surrounding model. 

3.2.2 Mutation as Constrained Subgraph Replacement. To unify mutations over tensors, operators, and bounded computations, FlowMuT represents each mutation as the constrained replacement of one bounded subgraph with another. Each mutation operator has three parts: a subgraph pattern, a replacement, and a set of constraints. The pattern states where the operator can be applied, the replacement states how the matched subgraph is changed, and the constraints state when the change is expected to remain legal. Each mutation operator has input, internal, and output constraints. Input constraints check edges produced outside the matched subgraph and consumed inside it. Internal constraints check the topology and data flow within the matched and replacement subgraphs. Output constraints check edges produced inside the replacement and consumed by nodes outside it. 3.3 Mutation Operator Pool 

FlowMuT combines CG-derived operators adapted from prior work with TFG-derived operators constructed from mutable TFG objects and mutation primitives. It then deduplicates and validates their union, as summarized in Figure 4. 

3.3.1 CG-Derived Mutation Operators. The CG-derived operators adapt concrete mutation rules defined over CGs in prior DL framework testing studies to the TFG-based description. This process proceeds in four steps. First, we select source studies. We begin with the studies discussed in Sec-tion 2, follow their references and later citing studies, and stop when a complete round yields no new study that meets our inclusion rule. We include a study only when it defines at least one concrete and reproducible change to a tensor, a framework operator, or a bounded computation. This procedure identifies 19 source studies: [9, 11, 13, 15, 20, 21, 23, 25, 26, 29, 32, 36, 44, 48–50, 52, 59, 64]. Second, 

we extract the mutation rules from each selected study and record their source locations, targets, actions, parameters, preconditions, and intended effects. When one rule contains independent edits, we split it into atomic rules, while different values of the same parameter remain one parameterized rule. Third, we map each extracted rule to the TFG. We retain a rule only when its target maps to a TFG edge, node, or bounded subgraph, its edit changes the topology or a recorded tensor or operator property, and the information needed to check it is available from the TFG or a documented framework requirement. Each retained rule is expressed as a mutation operator with a pattern, a replacement, and input, internal, and output constraints. Fourth, we remove rules that describe only a testing strategy or change framework internals without changing model-level data flow. We extract 155 rules from the 19 studies. Mapping and filtering remove five rules, and deduplication within the CG-derived set removes 30 more, leaving 120 unique CG-derived mutation operators. 

3.3.2 TFG-Derived Mutation Operators. The TFG-derived operators complement prior topology-oriented rules with mutations based on additional data flow information. This process proceeds in four steps. First, using 𝐺 , 𝐹 , and 𝑅 , we identify four types of mutable objects: tensors and their states, operators, producer–consumer interfaces and input relations, and bounded data flow structures. Second, we define four basic ways to change a mutable object, which we call mutation primitives . An update changes the value or label of an object without changing its connections. An insertion places a new operator and its connected edges on a tensor edge or at an interface. For example, combining an alias-annotated tensor edge with the insertion primitive produces an operator that inserts a copy and breaks sharing while preserving the tensor interface. Combining a shared edge with the rewiring primitive produces a branch-local operator that changes only one consumer path. Combining a producer–consumer interface with the insertion primitive produces an operator that makes an implicit dtype or layout conversion explicit.

output constraints. We adapt the implementation to each supported framework while preserving the operator’s target, effect, and constraints. We retain it only when positive and negative checks confirm that it performs the intended change and rejects violations of its declared constraints. This process produces the fixed pool M of 147 validated FlowMuT mutation operators, which we fix before running the evaluation. 

3.4 Test Case Generation 

In each iteration, FlowMuT generates a framework test case by mutating the current seed model and executing the resulting mutant. It first profiles the seed model 𝑓 to obtain a TFG. Using this TFG, it pairs mutation operators with sites to construct candidates and filters those that violate data flow constraints. From the retained candidates, it selects one using coverage and impact features and applies it to 𝑓 to obtain a mutant 𝑓 ′. It executes 𝑓 ′ and, if the execution succeeds, uses it as the seed model for the next iteration. The following subsections detail how these candidates are constructed and selected. 

3.4.1 Efficient Candidate Construction. A candidate 𝑐 = (𝑠, 𝑚 ) pairs a mutation operator 𝑚 with a TFG site 𝑠 anchored at a tensor edge. Rather than enumerating every subgraph, FlowMuT visits each tensor edge 𝑒 ∈ 𝐸 , treats it as the anchor of a possible site, and pairs the site with every mutation operator. Because the mutation operator pool is fixed before testing, the work for one edge is constant, giving candidate construction a time complexity of 𝑂 (| 𝐸 |) .After candidate construction, FlowMuT filters the candidates using the input, internal, and output constraints. The internal constraints determine whether the data flow around the anchor edge matches the pattern 𝑝 of 𝑚 , while the input and output constraints check the two boundaries of the mutation site. A candidate is retained only when it satisfies all three types of constraints. The retained candidates form C𝑡 for the selection procedure described next.

4.4 Measurements 

RQ1: Bug detection. We count distinct reproducible bugs reported to framework developers and record whether they are confirmed or fixed. 

Test-case legality and oracle. A test case is legal when its mutation satisfies the mutation specification and the documented preconditions of the affected operators, independently of its execution outcome. An execution failure caused by a violation of these conditions indicates an illegal test case. For a legal test case, the oracle identifies a potential framework bug when execution unexpectedly crashes or raises an uncaught exception, violates documented semantics, or produces a difference beyond the expected numerical tolerance across semantically equivalent execution modes. We count a failure as a bug only when it can be reproduced. Grounding Deep Learning Framework Testing in Data Flow 13

For bug discovery, each method ran a 12-hour campaign for each of the 14 seed models on each framework, giving 28 campaigns per method and 112 in total. For the comparative evaluation, each method or ablation configuration used 10 independent runs for every model–framework pair, with 250 mutation rounds per run. 6 Threats to Validity 

Internal Validity. Implementation differences and stochastic execution may bias the comparison. We mitigate this threat through controlled configurations and repeated runs across all methods. Component interactions may also affect ablation results, so we use matched variants and interpret each component through its primary metric. Construct Validity. Data flow signatures may not represent source coverage, and different failure symptoms may differ across executions. We mitigate this threat by reporting diversity, coverage, and detected bugs separately, and by recording developer confirmation and fix status for reported bugs. External Validity. Our evaluation covers two frame-works and diverse application tasks, but cannot represent every architecture or data flow pattern. Future work will evaluate additional frameworks, accelerators, and deployment environments. 

7 Conclusion 

We propose FlowMuT, a model-level DL framework testing method grounded in data flow. Its TFG records operator topology, runtime tensor values and properties, and operator input requirements. This shared description supports mutation construction, legality checking, and selection with LinUCB using coverage and impact features. Execution feedback guides subsequent selection, and each accepted mutant provides the TFG for the next iteration. On PyTorch and MindSpore, FlowMuT submitted 55 bug reports for cases missed by the baselines, improved data flow diversity by 43.4% over the strongest baseline, and achieved a legal-mutant rate of 96.7%.
