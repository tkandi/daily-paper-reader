## Abstract 

Reinforcement learning (RL) post-training with generative reward models (GenRM) has become a central recipe for improving large language models (LLMs), and it is also in-creasingly resource-intensive: policy rollout, GenRM-based reward evaluation, and policy training all compete for GPU resources. However, existing colocated and disaggregated systems rely on static resource allocation for these roles. Such allocation cannot adapt as each role’s workload changes dur-ing RL and therefore leaves a role’s resources underutilized. We present PivotRL , an RL post-training system that dy-namically shifts resources among different roles according to their runtime demands. PivotRL introduces a resource-shiftable runtime built on a Global Parameter Storage, to-gether with a unified mechanism that efficiently shifts role-specific context. A shift-aware scheduler enables sequence migration upon a shift, while a planner considers the aggre-gate throughput benefit and the shift overhead to determine when and how to shift. We evaluate PivotRL on a 128-GPU cluster using four model groups spanning dense and mixture-of-experts models. PivotRL enables resource shifting within seconds and improves end-to-end throughput by 1.81–2.05 ×

over colocated deployment and 1.50–1.95 × over disaggre-gated deployment, while preserving RL convergence. 

## 1 Introduction 

Reinforcement learning (RL) has become an essential step in post-training large language models (LLMs), driving re-cent advances in their reasoning capabilities [17, 42, 61]. As shown in Figure 1(a), a typical RL step consists of three stages: the policy model (i.e., the LLM) generates responses to a batch of prompts (policy rollout), the responses are scored to produce reward signals (reward evaluation), and the signals are used to update the policy (policy training). An increasingly prominent trend in this pipeline is the shift in how rewards are produced. Early RL recipes rely on rule-based verifiable rewards, which compare a response against a ground-truth answer and emit a binary correctness signal [50, 60]. While effective for tasks with well-defined answers, such rewards are unavailable for open-ended tasks such as long-form question answering, creative writing, and mathematical reasoning without golden answers. Under disaggregation, rollout suffers from the same tail effect, reward evaluation fluctuates with rollout’s instantaneous production rate, and training GPUs remain idle while waiting for the next batch. As a result, both colocated and disaggregated deployments yield suboptimal end-to-end throughput. The root cause is static resource allocation: regardless of whether colocation or disaggregation is used, each stage remains bound to a fixed set of GPUs throughout RL post-training. This static allocation cannot adapt to the dynamic workload demands across stages. When one stage has sub-stantial throughput headroom, its spare resources cannot be used by another stage experiencing higher demand. We therefore argue, as illustrated in Figure 2(c), that re-solving this mismatch calls for a more flexible deployment paradigm in which resources can shift across stages at run-time, a paradigm we refer to as resource-shiftable deployment .Under this paradigm, GPUs are dynamically reallocated ac-cording to instantaneous workload. For example, as rollout’s load decreases, its spare GPUs can shift to reward, and when rollout becomes the bottleneck, GPUs can shift back. Like-wise, once training completes, GPUs that would otherwise remain idle can be immediately reallocated to rollout or reward. By dynamically matching resource capacity with workload demand, resource-shiftable deployment can better utilize the resources and improve end-to-end throughput. To realize this paradigm, we introduce PivotRL , a system that accelerates LLM RL with generative rewards through resource shifting. It entails three key innovations. (1) Support-ing resource shifting. Each resource (i.e., a GPU) holds a set of model parameters (policy model or GenRM) and is bound to a role (i.e., an RL stage), so shifting a resource means shifting both the parameters and the execution context of the role. 

PivotRL addresses this with a Global Parameter Storage that lets any GPU fetch the parameters of any model on demand, together with a unified role-shifting mechanism, enabling smooth resource shifting between any models and any roles. (2) Rescheduling workload after a shift. A shift changes the resources a role owns, so the role’s workload must be resched-uled under its new resource allocation. PivotRL designs a shift-aware scheduler that supports shift-time sequence mi-gration across replicas, maximizing the role’s throughput under the new allocation. (3) Deciding when and how to shift. 

PivotRL introduces a planner to determine when to trigger a shift, which role should donate resources to another, and exactly which resources to shift. It evaluates candidate shift plans based on their expected throughput benefit and shift-ing overhead, and executes the most profitable plan. In summary, this paper makes the following contributions: 

• To the best of our knowledge, we are the first to systemat-ically study LLM RL with generative rewards and identify static resource allocation as a key system bottleneck. 

• We propose resource-shiftable deployment and realize it in PivotRL through three innovations: a resource-shiftable runtime built on a Global Parameter Storage with a uni-fied role-shifting mechanism, a shift-aware scheduler that reschedules workload across a role’s replicas, and a plan-ner that decides when and how to shift. 

• We evaluate PivotRL on a 128-GPU cluster across four model groups spanning dense and mixture-of-experts mod-els. PivotRL completes a resource shift within seconds and improves end-to-end throughput by 1 .81–2 .05 × over colocated deployment and 1 .50–1 .95 × over disaggregated deployment, while preserving RL convergence. 

## 2 Preliminaries 

2.1 RL Post-training with Generative Reward Models 

As shown in Figure 1(a), an RL post-training pipeline [36, 37, 59] consists of three major stages: policy rollout, reward eval-uation, and policy training. During rollout, the policy model (i.e., the model being post-trained) generates responses to a set of prompts. The generated responses are then evaluated by a reward model (RM) to produce reward signals, which are subsequently used to update the policy model. The up-dated model parameters are then synchronized back to the rollout stage, completing one step of the RL loop. Recently, generative reward models (GenRMs) have been increasingly used to provide richer reward signals [1, 14, 18, 27, 49, 62]. As shown in Figure 1(b), a GenRM itself is an LLM that reasons over the rollout response before producing its reward. This makes RL increasingly resource-intensive, as all three RL stages require substantial GPU resources. A fundamental system’s question is therefore how to efficiently deploy these stages on a given GPU cluster.

2.2 Different Deployment Paradigms 

Existing systems mainly adopt colocated [15, 39, 46, 67] or disaggregated [5, 12, 13, 23, 26, 29, 38, 52, 65] deployment. 

Colocated deployment. As illustrated in Figure 2(a), colo-cated deployment shares the entire GPU cluster across all three stages, which execute sequentially. When transition-ing between stages, the current model is offloaded to CPU memory and the next model is loaded onto the GPUs. 

Disaggregated deployment. As illustrated in Figure 2(b), disaggregated deployment statically partitions the GPU clus-ter among the three stages, which execute concurrently and asynchronously. Once a rollout sequence finishes, the re-ward stage consumes it immediately to produce a reward, while the training stage performs a policy update only after sufficient rewards accumulate to form a training batch. However, both paradigms statically allocate GPUs across stages, causing resource allocation to mismatch dynamic workload demands and leaving substantial throughput head-room. We therefore introduce resource-shiftable deployment, as illustrated in Figure 2(c), which dynamically shifts re-sources across stages to match changing workload demands. In Figure 3, we quantify the throughput headroom of differ-ent deployment paradigms using real RL workloads. Specif-ically, we measure the fraction of time each stage spends at a low per-GPU throughput, defined as throughput below 20% of its peak. We find that both colocated and disaggre-gated deployments leave substantial throughput headroom in the rollout stage. While disaggregated deployment can significantly reduce the throughput headroom of the reward stage, it comes at the cost of training idleness. In contrast, resource-shiftable deployment (implemented in PivotRL ) re-duces throughput headroom across all three stages, resulting in higher end-to-end performance. 

## 3 Challenges 

Realizing resource-shiftable deployment, and turning it into actual end-to-end throughput gains, however, is far from straightforward. It involves three core challenges. 

C1: How to support resource-shiftable deployment. 

Consider a single resource (i.e., a GPU). At any moment, it holds a set of model parameters and carries a role , defined as the RL stage to which it is currently assigned. Beyond the parameters, a role also requires its own execution context on the device, such as the CUDA Graphs captured for rollout or the optimizer states and NCCL communication groups es-tablished for training. Shifting a resource from one RL stage to another therefore includes shifting both its parameters and the additional context tied to its role. This is particularly challenging in RL post-training, where a single run spans two models (the policy model and the GenRM) and three roles (rollout, reward, and training), yielding a wide variety of shift cases that are impractical to handle in an ad hoc manner. Supporting flexible resource shifting therefore calls for a unified system infrastructure and shifting mechanism. 

C2: How to redesign the scheduler under resource shift-ing. Every shift carries an immediate side effect: the affected roles gain or lose resources. Newly acquired resources are useful only if part of the workload is rescheduled onto them, while removed resources require rescheduling the affected workload elsewhere. This rescheduling directly determines the role’s attainable throughput under the new allocation. Existing schedulers in RL systems [5, 39, 47, 67], however, typically support only dispatch (i.e., assigning sequences to replicas), not rescheduling. The scheduler must therefore be redesigned under resource shifting. 

C3: How to make shift decisions. While rescheduling is a consequence of resource shifting, deciding how to shift resources is a first-class problem. A single shift decision must determine when to trigger the shift, which role do-nates resources, which role receives them, and exactly which resources to move. These choices are tightly coupled, and shifting is not free: parameter movement and role context reconstruction both incur overhead. The benefit of a shift therefore depends on its timing, its plan, and its associated overhead, making it a complex joint optimization problem. Formulating this optimization and solving it with an efficient algorithm is the final challenge we must address. 

## 4 The Designs and Overview of PivotRL 

We introduce PivotRL , an LLM RL system that dynamically shifts resources across RL stages so that resource capacity tracks workload demand, thereby improving throughput. As shown in Figure 4, beyond the resources (i.e., GPUs) serving the three RL stages, PivotRL introduces a set of additional components, each addressing one of the challenges identi-fied in §3. ❶ A system runtime makes resource-shiftable deployment possible (§5), which consists of a Global Param-eter Storage (GPS) infrastructure (§5.1) and a role-shifting mechanism (§5.2). ❷ A shift-aware scheduler migrates work-load after a resource shift (§6), which is adopted for both the rollout and reward evaluation stages. ❸ A planner produces the best shift plan (§7), paired with a monitor that tracks workload state and a shift executor that carries the plan out. Resource-Shiftable runtime (§5). To enable resource-shiftable deployment ( C1 ), the system runtime needs to address two fundamental requirements: shifting model parameters and shifting the additional role context. For the former, PivotRL 

adopts a Global Parameter Storage (GPS), which pools the CPU memory of the entire GPU cluster into a distributed store holding the parameters of all models (i.e., the policy model and the GenRM). Any GPU can then fetch whatever parameters it requires, making a shift possible in the first place (§5.1). For the latter, PivotRL employs a unified role-shifting mechanism that distinguishes stateless from stateful data and decomposes a shift into two steps: a shift down of the old role followed by a shift up of the new one, while allowing each role to shift at its own granularity (§5.2). 

Shift-Aware scheduler (§6). To redesign the scheduler under resource shifting ( C2 ), we build on the existing abilities of the rollout and reward schedulers to continuously dispatch sequences, and augment it with shift-time handling so that rescheduling is naturally absorbed by the scheduler itself. 2

The scheduler maintains a shared waiting queue and models per-replica throughput to continuously dispatch sequences using a throughput-maximizing mechanism (§6.1). A shift down or shift up is then straightforward: the scheduler aborts the sequences needing migration and returns them to the shared queue, which re-dispatches them through the same throughput-maximizing mechanism (§6.2). 

Planner (§7). To determine when and how to shift resources (C3 ), PivotRL employs a planner with a five-step procedure that constructs a shift plan based on the current workload state (§7.1). The procedure first determines the shift-up role and prepares shift pairs. It then constructs candidate shift plans from these pairs using a dynamic programming algo-rithm (§7.2), and selects the most beneficial candidate by jointly considering its throughput gain and penalty (§7.3).

## 5 Resource-Shiftable Runtime 

In this section, we present our system runtime that supports resource-shiftable deployment. We begin by introducing the Global Parameter Storage (GPS), which offers an interface for accessing model parameters (§5.1). Leveraging this foun-dation, we propose a unified role-shifting mechanism (§5.2). 

5.1 Global Parameter Storage Design rationale. To realize unified parameter shifting, the most straightforward approach is to transfer the required parameters directly from peer GPUs. However, this presup-poses that the target parameters already reside somewhere in the cluster, an assumption that breaks once a role is shifted down entirely, leaving no replica on any GPU. An alterna-tive is to reload the parameters from disk, which guarantees availability but incurs prohibitive I/O overhead. We therefore mediate parameter transfer through CPU memory. Specifically, we maintain additional copies of the parameters for all models (e.g., the policy model and GenRM) in CPU memory across the cluster, forming the Global Param-eter Storage (GPS). GPS leverages idle CPU memory already available in the cluster, without introducing external storage. It attains both availability and efficiency: parameters remain accessible regardless of the current GPU allocation, while the high I/O cost of a disk-based approach is avoided.

Overhead and scalability. In terms of overhead, as shown in Figure 5(c), both Read and Write primarily rely on two network paths: PCIe for local CPU–GPU communication and an RDMA fabric, typically InfiniBand, for remote CPU–GPU communication. Modern clusters provide sufficient band-width for parameter transfers over both paths. For instance, in a Hopper-architecture GPU cluster, PCIe and the RDMA fabric provide up to 63 GB/s and 50 GB/s, respectively, al-lowing GPS to complete parameter shifts within seconds, as evaluated in §8.5. Moreover, since Write is only required during training, we optimize the training backend to over-lap Write with training in the subsequent RL step, further hiding its overhead from the critical path. In terms of scalability, as the cluster grows, the numbers of GPUs and CPUs increase proportionally. Consequently, the number of role replicas, which consume GPUs, and the number of replicas managed by GPS, which consume CPUs, also increase proportionally. The deployment and commu-nication patterns at a larger scale are therefore replicated across more replicas, rather than accumulating on existing replicas. Thus, the overall overhead does not increase with cluster size. We evaluate this scalability in §8.5.

Simply discarding such context can cause the shifted re-source to suffer from cold starts, such as rebuilding CUDA Graphs, or even affect RL correctness, such as reinitializing optimizer states. At the other extreme, preserving the con-text of all possible roles avoids cold starts but substantially increases GPU memory consumption. For example, GPUs would need to retain both optimizer states and CUDA Graphs even when the corresponding roles are not active, reducing the resources available for RL execution. To avoid the limitations of these two extremes, we design a role-shifting mechanism that manages role-specific context based on its data type. Specifically, we classify role context into different categories and apply the most appropriate ac-tion to each, such as discard, offload, or preserve. By tailoring these actions to each category, we minimize GPU memory consumption while reducing cold-start overhead. 

Categorizing role context. As shown in Figure 6 (left), role context falls into two types: stateless and stateful. Stateless data can be simply discarded when a role releases its GPUs. It consists of two types: (1) Temporary data , such as KV Cache, activations, and temporary buffers. These data are only useful to the current role. When shifting roles, they can be directly discarded and rebuilt through recomputa-tion. (2) Model parameters , which can be treated as stateless data because all model weights are stored in GPS. They can therefore be discarded and Read from GPS at any time. In contrast, stateful data must be retained rather than dis-carded to ensure correct RL execution and fast recovery after a resource shift. We further categorize stateful data into two 

> 5

types: (1) Offloadable data , such as optimizer states, gradients, persistent training states, and CUDA Graphs. These data are required to preserve RL progress, but do not need to remain in GPU memory while another role is running. They can therefore be offloaded to DRAM (i.e., the local CPU memory of the GPU), and reloaded when needed. (2) Preserved data ,such as the CUDA context, NCCL communication groups, and several descriptions or definitions. These data are small enough (they remain less than 3.37 GB per GPU in all our experiments), so we preserve them on the GPU. 

Shift down and shift up . Given this categorization, we split the shift into two standalone procedures: shift down for the original role and shift up for the new role. As shown in Figure 6 (left), during shift down , stateless data, including temporary data and model parameters, are discarded. Stateful data are either offloaded to DRAM or preserved on the GPU. During shift up , as shown in Figure 6 (right), temporary data are lazily reconstructed at runtime, so the system only needs to reallocate the required GPU memory for them, such as the memory for KV Cache. Model parameters are obtained directly from GPS through the Read 

operation. For stateful data, data previously offloaded to DRAM are reloaded to the GPU, while data already preserved on the GPU require no further action. 

Shifting granularity. In principle, GPS supports resource shifting at arbitrary granularities, as Read can retrieve model parameters for any set of GPUs under any parallelism strat-egy. In practice, however, we impose a restriction: rollout and reward are shifted at the granularity of individual replicas, while training is shifted as a whole. This choice is motivated by two considerations: restricting the shifting granularity (1) reduces the search space during planning, and (2) avoids ad-ditional overhead that finer-grained shifting may introduce. For rollout and reward, shifting at the replica granularity corresponds to scaling along the data parallelism dimen-sion. Thus, shifting only requires rescheduling sequences without modifying model partitioning. For training, treat-ing it as a monolithic unit avoids searching over training parallelism strategies and eliminates overheads such as re-partitioning optimizer states and establishing new commu-nication groups when parallelism strategies change. Overall, this design strikes a practical balance between shifting flex-ibility and system overhead, while finer-grained shifting remains an interesting direction for future exploration. 

## 6 Shift-Aware Scheduler 

PivotRL ’s runtime can shift resources across roles, but do-ing so raises an immediate question: once a role’s resource allocation changes, how should work be rescheduled within the role? Rollout and reward shift at replica granularity, so a 

shift-up replica may initially have no sequences, while a shift-down replica may have remaining sequences that must be rescheduled to others. This requires migrating the sequences across replicas to maximize the role’s aggregate throughput. To support such rescheduling under resource shifting, we redesign the scheduler instead of treating each shift as an external, one-shot event. Our goal is to reduce rescheduling to the scheduler’s native scheduling problem: the scheduler already has a basic dispatch capability, we can keep this capability as the core while adding shift-time handling. We realize this redesign in two steps. We first develop a throughput-optimal scheduling mechanism, which con-sists of a shared waiting queue that continuously dispatches sequences across replicas and a model that estimates each replica’s generation throughput, thereby maximizing aggre-gate throughput (§6.1). This mechanism naturally incorpo-rates rescheduling: sequences that need to migrate due to a shift can simply be returned to the queue and dispatched through the same throughput-maximizing mechanism, al-lowing the workload to be seamlessly rescheduled (§6.2).

## 7 Planner 

In this section, we introduce the planner that makes resource-shifting decisions. We first walk through our overall proce-dure (§7.1). Then, we detail its two main steps, candidate set construction (§7.2) and candidate evaluation (§7.3), to further illustrate how we make the best shift plan. 

7.1 Five-step Procedure 

As illustrated in Figure 8, the planner follows five steps. 

Determine the shift-up role. Given each role’s workload state, including replica counts, running sequences 𝑁 Seq Role ,throughput 𝑇 Role , training activity, and batch readiness, the planner first selects the role to shift up . Specifically, if the next training batch is ready, training is selected. Otherwise, the planner selects between rollout and reward evaluation: the role with a larger generation latency 𝜏 Role = 𝑁 Seq Role /𝑇 Role 

is selected, as it has greater resource demand. In the example depicted in Figure 8, the next training batch is not ready, and 

𝜏 Reward ≈ 0.08 > 𝜏 Rollout ≈ 0.03, so reward is selected. 

Prepare shift pairs. Given the target role 𝑟 ↑ to shift up , the planner identifies what to shift down to release resources for 

𝑟 ↑. This forms a set of shift pairs, each involving an exclusive set of GPUs. However, shifting is not free: once a replica starts to shift down , the sequences running on it are stalled until the migration completes. We therefore assign each shift pair a penalty 𝜙 , which captures the opportunity cost (i.e., the tokens that fail to be generated) during this shift period. Let 

𝜏 shift denote the shift duration, which we treat as a constant, and let 𝑚 be the number of replicas that shift down in the pair. Replica 𝑖 runs at a throughput of 𝑇 𝑖 , and thus forgoes 

𝜏 shift · 𝑇 𝑖 tokens. In the example, we have one 8-GPU training-to-reward shift pair and two 4-GPU rollout-to-reward shift pairs, listed in ascending order of penalty. 

Construct a candidate set (§7.2). Using the ordered shift pairs, the planner constructs a set C of feasible shift plans by combining one or more shift pairs with a dynamic program-ming algorithm. In the example, it produces three candidates. 

Evaluate candidates (§7.3). The planner estimates the bene-fit of each candidate through sequence migration simulation. In the example, the three candidates yield estimated benefits of 3774, 4183, and −3359. 

Select the best plan. Finally, the planner selects the can-didate with the largest positive estimated benefit. 7.2 Candidate Set Construction 

Since training performs shift up as a whole, it does not intro-duce multiple candidates. We therefore focus on cases where rollout or reward need to shift up .

Design rationale. Suppose the shift-up role 𝑟 ↑ owns 𝐼 repli-cas in total, of which 𝑛 are currently active. The planner must decide which of the remaining 𝐾 = 𝐼 − 𝑛 replicas to 

shift up , so a naive enumeration over all subsets yields 2 𝐾 

candidate plans, which is clearly impractical. We prune this space using two intuitions. First, given a fixed workload, shift-time migration is deterministic (§6.2), so 𝑟 ↑’s throughput after the shift depends only on how many replicas shift up (denoted by 𝑘 , 𝑘 ∈ [ 1, 𝐾 ]), not on which ones. It therefore suffices to retain one candidate per 𝑘 .Second, given the shift-up count 𝑘 , selecting different repli-cas amounts to combining different shift pairs, and these pairs differ only in their penalty 𝜙 . We therefore aim to se-lect a set of shift pairs that provides exactly 𝑘 shift-up repli-cas at the lowest total penalty (meaning achieving the same throughput at the lowest shift cost). ## 8 Evaluation 

In this section, we evaluate PivotRL with a focus on resource shifting. Our evaluation is guided by the following questions: 

• Does resource-shiftable deployment in PivotRL consis-tently provide throughput benefits over other deployment paradigms across different settings, and what is the mag-nitude of these benefits (§8.2)? 

• How does PivotRL shift resources among rollout, reward, and training to improve overall throughput (§8.3)? 

• How do different shift strategies and system components affect the overall throughput of PivotRL (§8.4)? 

• How significant is the resource shifting overhead, and how does it scale with cluster size and model size (§8.5)? 

• How do the hyperparameters introduced by resource shift-ing affect PivotRL ’s performance (§8.6)? 

• Does resource shifting affect RL convergence (§8.7)? 

8.1 Experiment Settings Environment. We conduct all experiments on a cluster of 16 GPU nodes, each equipped with 8 NVIDIA H20 (96 GB) GPUs (128 GPUs in total). Intra-node GPUs are connected via NVLink with 900 GB/s bandwidth, and inter-node com-munication is over InfiniBand with 50 GB/s bandwidth. 

Datasets and rewards. Following prior work [23, 26, 38], we use DAPO-Math-17k [4] as the training dataset and AIME-24 [3] as the validation dataset, both of which are represen-tative math reasoning datasets. During training, we use the sum of the verifiable reward and the GenRM reward as the re-ward for each trajectory, formulated as 𝑅 = 𝑅 DAPO + 𝑅 GenRM .The prompt, policy response, and GenRM response are lim-ited to 2K, 15K, and 20K tokens, respectively. 

Models and metrics. To comprehensively evaluate PivotRL 

across different policy models and GenRMs, we consider four groups of models, as shown in Table 1. These models cover different model families (Qwen [34, 57] and GLM [9]), gen-erations (Qwen2.5, Qwen3, and Qwen3.5), and architectures (dense and mixture-of-experts). 

Baselines. We select three baselines that represent the most common deployment paradigms in practice. (1) Colocated ,where rollout, reward, and training share the same GPUs across the entire cluster. (2) Disaggregated , where rollout, reward, and training use separate GPUs. (3) Rollout-Reward colocated , where rollout and reward share the same GPUs, while training uses isolated GPUs. 8.3 Case Study 

To gain insight into PivotRL ’s behavior, we track the through-put and GPU allocation of both the disaggregated baseline and PivotRL , as illustrated in Figure 10. For PivotRL , we observe the following patterns: (1) At the beginning of the trace, PivotRL assigns all resources to roll-out, while reward has little work to process. As sequences accumulate, the bottleneck gradually moves downstream, prompting the planner to shift resources from rollout to re-ward. During this period, rollout throughput decreases as fewer replicas remain, while reward throughput increases. As a result, the overall throughput generally increases or remains high because the shifted GPUs provide greater mar-ginal throughput when assigned to reward. (2) Once a train-ing batch becomes ready, PivotRL shifts GPUs to training. During this period, the overall throughput (Equation 1) ex-hibits a drop because it accounts only for rollout and reward. Nevertheless, this shift is necessary to make progress on training and advance the RL step. (3) After training finishes, the training GPUs first shift back to rollout, followed by further gradual shifts from reward to rollout. This behav-ior occurs because a new step is unlocked, creating high resource demand at rollout. During this period, the over-all throughput generally decreases because rollout has just started generating new sequences, while the downstream stages temporarily wait for these sequences to arrive. In contrast, the disaggregated baseline maintains a static resource allocation, resulting in relatively stable throughput. However, it cannot adapt resources to the changing demands of different RL stages. Thus, although PivotRL may experi-ence temporary throughput fluctuations and can be slightly worse than the baseline in some periods, it achieves substan-tially higher overall throughput by dynamically adapting resources to evolving workload demands.

## 9 Related Works 

RL post-training systems for LLMs. Existing LLM RL post-training systems follow two deployment paradigms: colo-cated systems [15, 39, 46, 67] share GPUs across stages and execute them sequentially, while disaggregated systems [5, 12, 13, 23, 26, 29, 38, 52, 65] statically partition GPUs for each stage and overlap the stages. As discussed in §2, both paradigms retain static resource allocations and cannot adapt to time-varying resource demands. We propose the resource-shiftable deployment paradigm to address this limitation. Recently, some concurrent work [35, 43, 48] has also rec-ognized the inefficiency of static resource allocation in RL with verifiable reward (RLVR), and dynamically adjusts the resources allocated to rollout and training. Unlike these works, our setting further employs a GenRM, and there-fore must shift resources across three roles spanning two models, which is considerably more challenging. Besides deployment, numerous works improve RL post-training efficiency in orthogonal ways: SortedRL, RollPacker, and Seer [6, 33, 63] mitigate long-tail generation through length-aware or fine-grained scheduling. Kimi k1.5, MiMo, AReaL, and AReaL-Hex [5, 45, 53, 56] introduce partial roll-out to break the synchronization barrier. Laminar and Stale-Flow [23, 38] further exploit finer-grained per-replica asyn-chrony. These techniques are compatible with our work. 

Elasticity in LLM inference and training systems. Alarge body of work studies elasticity in LLM inference and training. On the inference side, Llumnix [41] migrates re-quests across replicas, LoongServe [51] varies the sequence-parallel degree for long-context requests, and SpotServe [28] reconfigures parallelism and migrates state as GPU avail-ability changes. On the training side, Pollux [32] jointly optimizes resource allocation and training efficiency, Sin-gularity [40] transparently preempts, migrates, and resizes jobs, and Malleus [20] adapts hybrid parallelism to stragglers. These systems, however, confine elasticity to a single, iso-lated inference or training stack, whereas RL couples rollout, reward, and training in one workload. Elasticity here en-tails shifting GPUs from one role to another, which is more complicated than scaling a single role up or down. 

Reward-as-a-Service. Another line of work, including Dis-tRS [66] and RollArt [7], serves reward evaluation as a stan-dalone service that supplies rewards to RL jobs in a multi-tenant manner. This approach, however, requires additional dedicated resources outside the cluster. More importantly, these systems target scenarios that are orthogonal to ours. Their rewards are often naturally amenable to cross-tenant sharing, such as rewards obtained through API calls or ver-ification in sandboxes, and can therefore be provided as a shared microservice. In contrast, GenRMs are typically spe-cific to individual RL jobs. This is particularly true for recent rubric-based GenRMs [10, 11, 16, 54, 55], whose evaluation criteria are tightly coupled with the task and may need to be frequently updated or customized. Deploying GenRMs as a reward service is therefore not a good fit. Finally, a re-ward service does not change the fundamental problem: the mismatch between the static resource allocations of rollout and training and their dynamic workload still remains, and resource shifting is what actually resolves this mismatch.

## 10 Conclusion 

This paper studies RL post-training with generative reward models, where reward evaluation itself becomes a full LLM inference workload and all three stages contend for GPUs. We identified static resource allocation as a key bottleneck and proposed resource-shiftable deployment, realized in Piv-otRL through a Global Parameter Storage with a unified role-shifting mechanism, a shift-aware scheduler, and a planner that decides when and how to shift. Our evaluation shows that PivotRL improves end-to-end post-training throughput by up to 2 .05 × across different models and cluster configura-tions, while preserving RL convergence.

## A Throughput Model Details 

This appendix details the throughput model introduced in §6.1. This model is used by the scheduler to dispatch se-quences (§6.1), handle shift-time sequence migration (§6.2), and used by the planner to estimate the benefit of a candi-date shift plan (§7.3). Inspired by prior work [64], we build a throughput model in which throughput is estimated from the number of running sequences and the total number of their tokens. Most current inference systems batch active (running) sequences together and perform synchronous one-token-at-a-time generation (i.e., continuous batching [58]). Therefore, we model the inter-token latency 𝐿 to compute generation throughput. For mainstream LLMs, the generation process can be approximated by considering only the attention and feed-forward network (FFN) layers. 

Attention latency. The latency of attention layers is domi-nated by memory accesses, specifically reads from and writes to the KV Cache. The rate at which data is loaded from the GPU’s high-bandwidth memory (HBM) is generally deter-mined by memory bandwidth. Consequently, the correspond-ing latency scales linearly with the KV Cache size. Since the KV Cache size scales linearly with sequence length, atten-tion latency can be modeled as a linear function of sequence length: 

𝜏 Attn = 𝐴 × 𝑁 Token + 𝐷 1,

where 𝑁 Token is the total length of all running sequences, and 𝐴 and 𝐷 1 are hardware-dependent constants. 

FFN latency. The latency of the FFN layers is determined by whichever is greater: the memory-access cost or the compu-tation cost. FFN layers primarily perform matrix multiplica-tions, so both matrix-loading time and matrix-multiplication time must be considered. The loading time can be modeled similarly to that of the attention layers. Because the data being loaded consists of model weights, this part of the la-tency is typically constant. Consider the multiplication of an R𝑛 ×ℎ matrix by an Rℎ×ℎ′

matrix. The operation requires 2𝑛ℎℎ ′ floating-point operations, where 𝑛 is the number of active sequences in the current decoding batch, and ℎ and 

ℎ′ are the hidden dimensions. The computation time can therefore be modeled as a linear function of the number of active sequences. Together, the latency of FFN layers can be formulated as: 

𝜏 FFN = max (𝐵, 𝐶 × 𝑁 Seq ) + 𝐷 2,

## B GPS Details 

This appendix details the two engineering aspects of GPS deferred from §5.1: how GPS partitions the parameters it holds in CPU memory (Appendix B.1), and how the all-to-all collective underlying Read and Write is planned and executed (Appendix B.2). 

B.1 Parameter Partitioning Read-Intensive workload. The partitioning of GPS deter-mines which CPUs hold which parameters, and therefore how much traffic each Read and Write must move and over which links. Our choice is driven by the observation that re-source shifting is a Read -intensive workload. Within a single RL step, resources may be shifted several times, e.g., from reward back to rollout as the reward stage drains, and then from both to training once the batch is ready, and every such shift issues a Read on the newly assigned GPUs. In contrast, GPS is updated at most once per step: GenRM is frozen and thus never written, and the policy model is committed by exactly one Write after the training stage. Read s therefore outnumber Write s within a step. The asymmetry is reinforced by where the two operations sit on the critical path. Write need only complete before the optimizer applies the next update, so it can be overlapped with the remainder of the training computation and is largely hidden. Read , on the other hand, gates the GPUs that have just performed shift up : they cannot begin serving their new role until the parameters have landed. The non-overlapped cost of Read is thus the quantity that matters. 

Replication-First partitioning. Following this reasoning, GPS is fully replicated whenever the memory budget permits: every node holds a complete copy of the parameters of all involved models in its CPU memory. Full replication makes every Read node-local. A shift-up GPU can find all the slices it needs in the CPU memory of its own node, so the transfer is a CPU-to-GPU copy over PCIe and never touches the RDMA fabric. This is the fastest configuration available, and it also removes the fabric as a point of contention: concurrent 

Read s on different nodes proceed independently instead of competing for the same inter-node links. The price is paid by 

Write , which must now reach every replica and does traverse the fabric, but as argued above that cost is overlapped. 

Partitioning under memory pressure. Full replication requires the policy model and GenRM to fit together in the CPU memory of a single node. When they do not, we fall back to a hybrid layout analogous to HSDP [24]: the nodes of the cluster are divided into replication groups, the parameters are

B.2 All-to-All Collective 

Because GPS and the caller partition each weight (i.e., pa-rameter) differently, Read and Write entail re-partitioning data between a set of CPUs and a set of GPUs. We realize this re-partitioning as an all-to-all collective [8, 21, 22]. The collective is executed through NIXL [30]. NIXL builds on UCX [31] and abstracts point-to-point transfers across CPU, GPU, and interconnect types behind a single interface. This abstraction allows GPS to be hosted on CPUs while com-municating efficiently with GPUs in both directions. The remaining task is to decide which point-to-point transfers to issue. The communication plan governs this decision. We describe the plan for Read , since Write is symmetric, with the roles of the CPU and GPU sides exchanged. 

Aligning slicing granularity. The two sides of the trans-fer do not agree on slice boundaries: a weight may be cut row-wise across GPS slices and column-wise by the target parallelism 𝑃 , so a single GPS-side slice may be needed by several GPUs and a single GPU-side slice may have to be assembled from several GPS slices. As shown in step ❶ of Figure 16, we first take the common refinement of the two layouts, which yields a set of atomic slices that are indivisible on both sides. A converter performs this refinement, and in doing so also reconciles the differing parameter naming and layout conventions of the training backend, GPS, and the inference engine into one canonical representation. After refinement, every transfer moves a whole atomic slice, so no slice is ever split or concatenated in flight. 

Load-Balancing communication planning. Refinement turns the collective into a set of demands , one per (atomic slice, receiving GPU) pair. Each demand admits multiple valid senders, since replication means an atomic slice gen-erally resides on several CPUs, and any of them can serve it. Choosing arbitrarily concentrates traffic on a few senders and lets the slowest one dictate the completion time of the whole collective, so we choose deliberately. For every candi-date sender we maintain an accumulated estimated latency, i.e., the total cost of the demands already assigned to it. The cost of one transfer is estimated as the size of the slice in bytes divided by the profiled bandwidth of the link between that sender and the receiver, plus a constant per-transfer overhead. Both terms are obtained by offline profiling, and the bandwidth term is what distinguishes a node-local PCIe path from a remote RDMA one. As illustrated in step ❷, we walk the demands and greedily assign each to the candidate whose accumulated latency is currently smallest. Step ❸ shows the effect. The greedy rule equalizes latency, so a sender on a fast link is given proportionally more data than one on a slow link, and the bottleneck sender is pushed down. 

Plan caching. The plan depends only on the signature 

⟨𝑀, 𝐺, 𝑃 ⟩ of the operation and on the profiled link band-widths, none of which change between invocations with the same arguments. Since resource shifting may repeatedly re-turn to the same configurations across RL steps, we compute each plan once and memorize it, so subsequent Read s and 

Write s with the same signature skip planning entirely and issue the cached set of point-to-point transfers directly.

## E Deployment Details 

In this appendix, we provide detailed descriptions of the implementation of each method and the resource configura-tions used in our experiments. 

> 19

Implementation. PivotRL and all baselines are built upon veRL [39]. 

Colocated directly builds on the veRL framework, with only the necessary modifications to adapt the reward func-tion and datasets. Upon completion of each rollout, reward evaluation, or training phase, all resources are released and reassigned to the subsequent phase. 

Disaggregated uses the same training and inference back-ends as veRL. Each role is assigned an independent resource pool that cannot be used by other roles. In addition, disag-gregated introduces staleness 4 to enable asynchronous RL post-training. In all our experiments, we set the data stale-ness to 2. 

Rollout-Reward collocated builds upon the disaggregated implementation. It allows the rollout and reward evaluation stages to share the same set of resources, while the training stage uses a separate resource pool. Once rollout completes sampling a batch, reward evaluation is launched on the same resources to evaluate the generated samples, and the cy-cle repeats. We set the data staleness to 2, allowing rollout and reward evaluation to continue processing subsequent batches while training proceeds concurrently. 

PivotRL is also built upon the disaggregated implementa-tion. To enable resource shifting among roles, it implements all key components described in §4, including a resource-shiftable runtime (§5), a shift-aware scheduler for rollout and reward (§6) and a planner (§7). Besides we also implement a monitor to capture the workload state for the planner, and an executor to execute shift plans generated by the planner. Unlike the baselines above, PivotRL allows all three stages to utilize resources from the entire resource pool. We also set the data staleness to 2. 

Resource allocation. The resource configurations for differ-ent baselines over different model groups are listed in Table 4. In all experiments, we keep the total number of GPUs for each model group the same across all baselines. For each baseline, we tune its resource configuration to achieve the best end-to-end throughput.
