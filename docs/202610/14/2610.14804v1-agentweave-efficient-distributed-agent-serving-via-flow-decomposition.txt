## Abstract 

Agent applications are evolving into workflows composed of large language model (LLM) calls and tool invocations, termed modules . Existing distributed agent systems typically adopt a disaggregated architecture, deploying different modules on separate devices. While this enables pipeline parallelism, imbalanced module latencies introduce severe pipeline bubbles that limit throughput. A natural alterna-tive is an aggregated architecture that co-deploys all modules across all devices, eliminating bubbles by keeping every device continuously active. However, this introduces request blocking : short requests are forced to progress in lockstep with longer ones in the same batch, and newly arriving requests must wait until the entire ongoing batch completes the full workflow. To address this, we propose AGENT WEAVE , an efficient distributed serving system for agent applications built on the aggregated architecture. Its core mechanism, flow decomposition , decom-poses long agent requests into fine-grained execution units while preserving agent semantics, allowing short and newly arriving requests to proceed without being stalled by long-running ones. Complementing this, a flow-adaptive scheduler 

dynamically balances the throughput gains of decomposition against its scheduling overhead. Experiments across four representative agent applications demonstrate that A GENT WEAVE improves throughput by 1.81 ×, reduces average latency by 

2.45 ×, and reduces P90 latency by 2.04 × over state-of-the-art baselines. 

## 1 Introduction 

Large language model (LLM)-based agents [49] have emerged as a compelling paradigm for tack-ling complex real-world tasks. Yet building capable agents is non-trivial, as a single LLM [1, 8] alone is often insufficient: it may lack up-to-date knowledge [14, 38], struggle to reason over long contexts [32, 6, 56], and cannot reliably interact with external data sources [44, 29]. To overcome these limitations, modern agents augment LLMs with specialized tools that enable them to navigate external environments and solve complex tasks more effectively [44, 52, 42]. We adopt module as a unified abstraction encompassing both LLM calls and tool invocations; under this abstraction, a modern agent is naturally organized as a workflow of modules. Existing distributed serving systems [46, 33, 31, 25, 57, 28] adopt a disaggregated architecture for agent serving, where different modules are deployed on separate devices and managed independently. This design naturally forms a pipeline that allows modules to overlap execution across requests. However, it fundamentally suffers from pipeline bubbles : because module latencies are highly imbalanced in practice, faster modules are forced to idle while waiting for slower ones, leaving substantial dead time in the pipeline. When short requests R1, R3 and long requests R2, R4 arrive, modules execute in a pipelined fashion, yet the resulting pipeline bubbles severely degrade overall serving performance. A natural alternative is the aggregated architecture, which co-deploys all modules across all devices, fully utilizing every device at each step of the workflow. This eliminates pipeline-induced bubbles and accelerates per-request execution. As illustrated in Figure 1(b), all three modules are deployed across all devices. R1 and R2 are batched and processed through three modules, exiting together after completing the entire agent workflow. R3 and R4 also follow the same pattern. Compared with Figure 1(a), requests complete earlier under this design, yielding lower latency and higher throughput. Despite these advantages, the aggregated architecture introduces a critical inefficiency: request blocking . As shown in Figure 1(b), although short request R1 requires far less computation in the indexing stage, it cannot advance to reranking earlier, because all devices remain committed to indexing for the entire batch until long request R2 finishes. Consequently, short requests are forced to exit in lockstep with long ones, while newly arriving requests such as R3 must wait until the ongoing batch ( R1, R2) completes the full workflow before they can begin execution. We therefore present A GENT WEAVE , an efficient distributed serving system for agent applications. Our key idea is to decompose long requests at the agent level. As shown in Figure 1(c), we decompose 

R2 into smaller execution units R21, R22, and R23. So R1 can exit after executing with R21, rather than being coupled with the entire R2. New requests such as R3 can also enter between two units of a long request and complete earlier. This reduces request blocking while retaining the benefits of the aggregated architecture. To practically realize this idea, we further address two technical challenges. 

Challenge 1: How to decompose a request without breaking agent semantics. This requires preserving two semantics constraints: execution workflow, i.e., the module execution structure shown in Figure 2; and complete-input requirement, where a module requires a complete input to produce correct output, e.g., reranking requires the full retrieved documents to select the global top-k results. AGENT WEAVE introduces flow decomposition to decompose each request while preserving agent semantics. It develops an abstraction called flows (i.e., module’s input or output) as the decomposable unit, and rewrites the module dependency into a flow dependency graph. It decomposes flows along valid flow dependency, and inserts supplement dependencies to satisfy complete-input requirement. 

Challenge 2: How to control decomposition cost. Decomposition reduces blocking, but also introduces scheduling and flow-management costs. ## 2 Background and Motivation 

2.1 Agent Applications 

Agents have become increasingly popular in real-world applications. Figure 2 shows four rep-resentative examples (see Appendix A for details). In a retrieval-augmented generation (RAG) agent [46, 26, 14], an LLM rewrites the query, invokes an embedding tool to index documents and retrieve relevant ones, a reranking tool to refine results, and finally synthesizes the answer, thereby enabling better knowledge-grounded generation. A knowledge-based (KB) RAG agent [26, 19] follows the RAG agent but retrieves candidates from a pre-built knowledge base instead of indexing new documents. In a DeepSearch agent [5, 21], an LLM decomposes a query into subplans, coordi-nates search subagents tools to collect and summarize evidence, and consolidates the results into a structured response. In a multimodal generation agent [51, 30], an LLM refines the query, plans the scene layout, and invokes a diffusion generator to produce the final image. 

2.2 Inefficiency of Disaggregated Architecture 

Existing distributed serving systems [33, 46, 25, 57] adopt a disaggregated architecture in Figure 1(a) for agent applications, and primarily pursue two optimization directions: workflow orchestration and module serving. The first direction [46] optimizes workflow by splitting modules into finer-grained units and overlapping their execution to shorten the latency of a request. The second direction [33, 31, 25, 57] optimizes individual modules serving, most commonly the LLM-based modules, by reducing queueing delay or eliminating redundant computation and memory. However, both directions still suffer from pipeline bubbles [22, 39] caused by imbalanced module latencies. Figure 3 illustrates this imbalance: execution time is distributed unevenly across modules in all four agent applications, with latency skew reaching 41.5% in KB-RAG, where LLM-based synthe-sis accounts for 65.7% and reranking by the rerank model accounts for only 24.2%. This imbalance leaves severe bubble time in the pipeline, reducing effective overlap and limiting throughput. 

2.3 Aggregated Architecture: Benefits and Inefficiency 

This motivates an aggregated architecture in Figure 1(b), which co-deploys all modules of an agent across all devices. It removes pipeline and fully utilizes devices to process each module, therefore avoiding bubbles and additionally accelerating the request execution. However, this architecture still suffers from request blocking. Real-world requests can vary signifi-cantly in execution time, as users or platforms choose different inputs or hyperparameters to satisfy budget, accuracy, and SLO requirements [5, 35, 7, 16]. Figure 4 shows this variation for RAG agent on TriviaQA [24], where execution time significantly differs across request percentiles, with the gap even exceeding 20 ×. Short and long requests can be batched and advance together, causing request blocking, and substantially limit the latency and throughput gains of the aggregated architecture. 

2.4 Decomposition and Challenge 

The blocking stems from executing a long request as one coarse-grained unit. A naive solution is to decompose it into smaller execution units. In this way, short requests can be executed with a small execution unit and exit sooner, rather than being coupled with the entire long ones. New requests can enter between two consecutive units of the long request, rather than waiting for its entire completion. We observe that request execution mainly depends on the input or output data flowing through modules. This is evident in Figure 4: as the document directly determines the indexing cost and indirectly affects downstream execution by propagating through retrieval, reranking, and synthesis, it largely determines the end-to-end execution time. Thus, a long RAG request can be decomposed by splitting its documents to trigger only part of the original execution. By decomposing such data, we can decompose the corresponding executions and obtain smaller execution units. However, decomposition presents two challenges. First, preserving agent semantics . Semantics impose strict execution workflow, as modules must follow the specified order; and complete-input requirement, as some modules require complete input to produce correct output. Naive decomposition may violate these constraints, causing downstream modules to execute out of order or consume partial input when complete input is required. Thus, decomposition must preserve agent semantics to avoid degrading the answer quality. Second, controlling decomposition cost . Although decomposition reduces blocking, it introduces scheduling and management cost. For long requests, these costs may accumulate across scheduling rounds, significantly increasing latency. Thus, decomposition must control its granularity to avoid long-tail latency.

3.1 Overview 

Figure 5 shows the overview of A GENT WEAVE . In the offline phase, the system registers an agent application ( 1 ⃝), analyzes its workflow to derive a semantics-preserving decomposition method ( 2 ⃝), and profiles module execution time and decomposition costs for online scheduling. In the online phase, the scheduler dequeues requests and determines the decomposition size based on the offline profiling results ( 3 ⃝). It then constructs the execution batch ( 4 ⃝), dispatching the batch to the aggregated engine and returning remaining tasks to the scheduler for later rounds ( 5 ⃝). 

3.2 Flow Abstraction Flow as the Unit of Decomposition. A module’s input or output data determines its required computation. We term such data a flow , and decompose a long request by decomposing flows into subflows for module execution. We further identify which flow can be decomposed. A flow can be decomposed only when (1) it can be split into independent subflows, and (2) each subflow is a correct subset of the flow produced by its module on the complete input. Otherwise, the flow should be processed as a whole. In Figure 6, for example, document embeddings can be decomposed because each embeddings subflow is independent and represents a correct subset of the full embeddings produced by indexing on complete documents. In contrast, the query is not decomposable because partial queries are dependent on each other to express the original user intent. Some flows satisfy the first condition but not the second. They can be decomposed into independent subflows, but each subflow may not be a correct subset. For reranking (a) example in Figure 6, reranked documents can be split into independent document subflows, but it requires the complete retrieved documents as input to select the global top-k results, making subflow not a correct subset result, thus not decomposable. We treat such flows as conditionally decomposable and decompose them while preserving the complete-input requirement through supplement dependency in Section 3.3. 

Flow Dependency Graph. The flow dependency graph is a flow representation of the module workflow, where nodes denote data flows and edges denote how outputs are derived from inputs by modules. In this graph, each module’s output flow depends on its input flows, thus, the original execution order is represented as flows dependency, as illustrated by the RAG example in Figure 6. As flow is the appropriate unit of decomposition, this reformulation makes decomposition explicit. 53.3 Flow Decomposition 

Flow decomposition enables long requests to be split into smaller execution units while preserving agent semantics. The system constructs decomposition based on above abstraction. 

Decomposition Construction. The system first rewrites the workflow into a flow dependency graph, then traces and splits the decomposable flows along the dependency from the final answer. In Figure 6, it decomposes the retrieved documents into subflows, and further propagates to document embeddings and raw documents. It keeps other flows intact, as they are not decomposable. This step determines which flows are decomposed and how they propagate along the valid dependency. 

Supplement Dependency Construction. The system then splits conditionally decomposable flows and inserts supplement dependencies to satisfy complete-input requirement. A supplement depen-dency connects a later subflow to an earlier one, allowing the later subflow to receive the accumulated result from previous subflows and continue the original complete-input computation. For reranking (b) in Figure 6, the system inserts a supplement dependency from reranked document subflow 2 to subflow 1. The second reranking then consumes both the retrieved documents subflow 2 and the accumulated reranked result from subflow 1, producing the correct top-k result. This step splits conditionally decomposable flows while preserving their complete-input requirement. 

Decomposition of a Request. At runtime, the system decomposes a long request by splitting the most downstream decomposed flow in the graph, i.e., documents in RAG. Each subflow is consumed to produce output subflows along the reverse direction of flow and supplement dependencies. Since each module consumes or produces only a subflow rather than the complete flow, its execution is shorter, and the execution triggered by one subflow forms a smaller execution unit for scheduling. This runtime decomposition is controlled by the decomposition size, which sets the subflow size for each request in a scheduling round. A larger decomposition size increases per-round execution time, while a smaller one creates more execution units and introduces more overhead. Thus, the system profiles execution time and overhead under diverse decomposition sizes for online size selection. 

3.4 Flow-Adaptive Scheduler 

The flow-adaptive scheduler determines the decomposition size online in each scheduling round based on the current queue state and profiled data. The goal is to maximize system throughput while controlling the long tail latency caused by decomposition overhead.

In each schedul-ing round, the scheduler receives requests from the queue and searches decomposition size within the valid search space (Lines 6). For each candidate size S, the scheduler estimates the execution time and decomposition overhead from the offline workload profiles (Lines 7), computes the throughput gain and cost penalization (Lines 10–12), and evaluates the scheduling score (Lines 13). 4.1 Performance Throughput. The first row of Figure 7 shows that A GENT WEAVE sustains higher throughput as input rate increases, improving over the baseline by 1.33 × on RAG, 1.81 × on KB-RAG, 1.68 × on DeepSearch, and 1.28 × on Multimodal. At low request rate, all systems perform similarly because the servers are not saturated. As rate increases, the disaggregated baselines saturate earlier: Autellix performs better on LLM-dominated DeepSearch agents, while Ayo performs better on other agents, but both are limited by pipeline bubbles. A GENT WEAVE keeps devices busy and reduces request blocking, thereby sustaining higher throughput near saturation. 

Average latency. The second row of Figure 7 shows that A GENT WEAVE consistently reduces average latency, improving over the baseline by 2.28 × on RAG, 2.45 × on KB-RAG, 2.08 × on DeepSearch, and 2.15 × on Multimodal. At low input rates, queueing is limited, and the improvement mainly comes from aggregated execution, which shortens module execution. At higher input rates, AGENT WEAVE further reduces blocking with flow decomposition, so latency grows more slowly. 

P90 latency. The third row of Figure 7 shows that A GENT WEAVE reduces tail latency over the baseline by 2.04 × on RAG, 1.56 × on KB-RAG, 1.59 × on DeepSearch, and 1.66 × on Multimodal. Unlike average latency, the P90 improvement mainly comes from the aggregated architecture. Tail requests are typically long requests themselves, so decomposition does not directly shorten their execution. However, the aggregated architecture still reduces the latency of these long requests by utilizing all devices to process each module.

preserves output quality while improving serving performance. 95 Conclusion 

This paper presents A GENT WEAVE , an efficient distributed serving system for agent applications. AGENT WEAVE adopts an aggregated architecture and addresses its key challenge, request blocking, through decomposition. It exposes flow as the decomposition unit and deploys flow decomposition to safely decompose a request. It also deploys a flow-adaptive scheduler to balance decomposition gains against overhead. Experiments on four representative agents show that A GENT WEAVE achieves better serving performance over existing baselines while preserving accuracy. We discuss limitations and future directions in Appendix F.

13 A Agent Applications 

This appendix introduces the four agent applications considered in this paper, covering their use cases and how they execute as workflows involving multiple LLM or tool invocations [48]. 

A.1 RAG Agent 

Retrieval-augmented generation (RAG) [26, 14] in Figure 2(a) is one of the most widely used agents for accurate answers generation with retrieved knowledge. A standalone LLM answers from its parametric knowledge and the prompt context, which can be insufficient [14, 38] when the answer depends on newly added documents, private files, domain-specific corpora, or information that is too long to directly place in the prompt. A RAG agent addresses this limitation by coupling the LLM with retrieval tools. Instead of asking the LLM to answer directly, the agent first identifies relevant evidence and then asks the LLM to synthesize an answer conditioned on that evidence. Given a user query and a set of documents, the RAG agent executes a workflow that combines LLM calls with tool calls. It first invokes an LLM to expand or rewrite the query [13, 23], producing a clearer search intent for downstream retrieval. The agent then calls an embedding tool to encode the documents and update the vector index. Using the rewritten query, it invokes a retrieval tool to search the index and obtain candidate documents. Since the retrieved candidates may be noisy or only partially relevant, the agent further invokes a reranking tool to rescore them and select the most relevant evidence. Finally, the agent invokes the LLM again to synthesize the answer from the reranked documents [54]. Modern RAG extends retrieval-augmented generation into a multi-stage agent workflow. It combines query expansion, document indexing, vector retrieval, reranking, and answer synthesis to improve knowledge-grounded response generation. Advanced RAG therefore represents a common agent workflow that relies on multiple LLM and tool invocations for knowledge-intensive tasks. 

A.2 Knowledge-Based RAG Agent 

Knowledge-based RAG [14, 19] in Figure 2(b) is an agent for answering questions over a persistent knowledge source [4]. It follows the same general principle as RAG: the LLM should answer using retrieved evidence rather than relying only on its internal knowledge. Different from advanced RAG, the documents are processed and indexed offline into a local knowledge base, which may contain enterprise documents, product manuals, internal wikis, troubleshooting guides, code repositories, or other domain-specific resources [4, 3, 15]. This setting is widely used when user queries target private, domain-specific, or frequently updated corpora. Given a user query, the knowledge-based RAG agent executes a workflow that combines LLM calls with retrieval tools. It first invokes an LLM to expand or rewrite the query, producing a clearer search intent for the knowledge base. The agent then calls a retrieval tool to search the pre-built database and obtain candidate documents or passages. Since the retrieved candidates may still contain irrelevant or weakly related evidence, the agent further invokes a reranking tool to rescore them and select the most relevant passages. Finally, the agent invokes the LLM again to synthesize the answer from the reranked evidence. Knowledge-based RAG removes the online document encoding stage and focuses on query expansion, knowledge-base retrieval, reranking, and answer synthesis over a persistent corpus. This makes it a practical agent workflow for domain-specific question answering, where LLM reasoning is coupled with retrieval from private or enterprise knowledge sources. 

A.3 DeepSearch Multi-Agent 

DeepSearch multi-agent [5, 21] in Figure 2(c) is an agent for complex information-seeking tasks. Unlike RAG-style agents, which usually retrieve evidence from a fixed corpus or index, DeepSearch actively explores external sources through multiple coordinated agents. It is designed for questions that require broad investigation, where the answer may depend on collecting evidence from different directions and synthesizing them into a structured report. 14 Given a user query, the DeepSearch multi-agent executes a workflow that combines LLM agents with search subagent tools [27]. It first invokes a lead LLM agent to analyze the query and decompose it into multiple subquestions or research directions. The lead agent then dispatches these subquestions to multiple search subagents. Each subagent invokes search tools, reads retrieved pages or documents, refines its search when needed, and summarizes the evidence for its assigned direction. After the subagents finish, a consolidation agent aggregates their findings, removes redundant information, resolves inconsistent evidence, and generates the final response with supporting citations. DeepSearch organizes complex information seeking as a multi-agent research process. By decompos-ing a query into multiple directions, collecting evidence in parallel, and consolidating intermediate findings, it supports open-ended questions that require broader exploration than standard retrieval-based workflows. 

A.4 Multimodal Generation Agent 

Multimodal generation [51, 30, 18] in Figure 2(d) is an agent for generating images from text prompts. A diffusion model [10] can synthesize an image directly from a prompt, but short user prompts often underspecify visual details such as object attributes, spatial relations, background, lighting, or style. A multimodal generation agent addresses this limitation by using LLM calls to refine and structure the prompt before invoking the image generator. This improves prompt understanding, scene composition, and controllability. Given a user prompt, the multimodal generation agent executes a workflow that combines LLM calls with a generative tool. It first invokes an LLM-based recaptioning module to rewrite the prompt into a richer and more explicit description. The agent then invokes an LLM-based planning module to decompose the refined description into structured scene plans, such as objects, regions, layouts, or visual constraints. Finally, the agent calls a diffusion-based image generation tool to synthesize the final image from the planned description. Multimodal generation extends agent workflows beyond text-only question answering. It uses LLM-based recaptioning and planning to prepare structured inputs for a diffusion-based generator, connecting language reasoning with specialized visual generation tools. 

A.5 Common Properties 

Although the four applications target different tasks, they share several properties that distinguish agent serving from serving standalone LLM requests [12, 47, 25, 57]. First, they execute as module workflows. The final response is produced through multiple LLM calls and tool invocations, such as retrieval, reranking, search, database access, or image generation. Second, these modules are connected by data dependencies. Each module consumes intermediate data produced by earlier modules, so the workflow can only progress when the required data becomes available. Third, requests can have substantially different execution costs. Different requests carry different documents, retrieved candidates, subquestions, search results, or scene plans, which change the amount of work required by each module and lead to large differences in execution time. These properties make agent serving a workflow-level systems problem. Optimizing a single LLM call or an individual tool is insufficient, because overall performance also depends on how intermediate data moves through the workflow and how different modules are scheduled together. Therefore, an agent serving system should optimize the execution of dependency-constrained module workflows rather than treating each module invocation as an isolated request.

## C System Implementation 

AGENT WEAVE is implemented as a distributed serving system for agent workflows, with roughly 8.9K lines of Python code, based on FastAPI [43] for the control plane, Ray [37] for distributed scheduling and execution, SGLang [57] for LLM generation, embedding, and reranking, FAISS [9] for retrieval, xDiT [11] for diffusion-based generation. 16 Frontend. The frontend is an asynchronous FastAPI service that exposes a stateless request interface, while the runtime tracks each request as a long-lived stateful flow. After admission, a request enters an FCFS queue that stores remaining subflows, intermediate state, and completion status. This separates the user-facing API from decomposition state, allowing A GENT WEAVE to pause and resume requests across scheduling rounds without changing application semantics. 

Execution engine. AGENT WEAVE wraps SGLang’s asynchronous engine interface as the LLM executor, with continuous batching [53], chunked prefill [2] and prefix caching [57] techniques. AGENT WEAVE keeps decomposition and scheduling decisions outside the LLM engine. 

Tool backends. Beyond the LLM executor, A GENT WEAVE implements embedding, reranking, retrieval, web search, and multimodal generation as resident tool services, avoiding repeated initial-ization during decomposed execution. 

Scheduler. The scheduler is an event-driven loop over active request states. It is independent of tool internals and agent-specific module code. In each scheduling round, it uses profiled data to estimate execution time and scheduling overhead, selects the decomposition size, constructs the execution batch, and returns remaining tasks to the queue. 

Agent executors. Each application uses a common executor interface to define its flow semantics, including which flows can be decomposed, which context remains intact, and which intermediate results are carried as supplement dependencies. Our prototype implements this interface for RAG, KB-RAG, DeepSearch, and multimodal generation. Thus, application-specific decomposition rules remain inside each executor, while the frontend, scheduler, LLM executor, and tool backends are shared across agents. 

## D Experimental Setup 

We evaluate A GENT WEAVE on four representative agent applications: RAG, KB-RAG, DeepSearch, and multimodal generation. For all experiments, we use the same hardware for A GENT WEAVE and the baselines. The disaggregated baselines place different modules on separate GPU groups, while AGENT WEAVE adopts the aggregated architecture and co-deploys modules across all available GPUs. 

RAG. We evaluate RAG on TriviaQA [24] with two model configurations. The 14B/4B/4B config-uration uses Qwen3-14B [50] as the LLM, Qwen3-Embedding-4B [55] as the embedding model, and Qwen3-Reranker-4B [55] as the reranker. The 32B/8B/8B configuration uses Qwen3-32B [50], Qwen3-Embedding-8B [55], and Qwen3-Reranker-8B [55]. ## F Limitations and Future Work 

AGENT WEAVE has several limitations. First, it currently requires each agent application to specify its flow semantics, including decomposable flows and complete-input dependencies. Automatically 18 deriving such semantics from general agent programs remains future work. Second, the flow-adaptive scheduler uses offline profiles to estimate execution time and decomposition overhead; online profile adaptation could further improve robustness under workload and hardware changes. Finally, our evaluation focuses on four representative agents. Extending A GENT WEAVE to more dynamic production agents, external-tool failures, and multi-tenant deployments is an important future direction. 19 NeurIPS Paper Checklist
