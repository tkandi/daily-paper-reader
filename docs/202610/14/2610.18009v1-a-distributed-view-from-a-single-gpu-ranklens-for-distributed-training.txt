Abstract —Modern distributed training is costly to debug, tune, and analyze because faithful analysis often requires repeated target-scale executions. We observe that many analysis tasks depend on the original distributed execution path, but not on full all-rank execution. We present RankLens, a single-rank em-ulation system that runs one survivor rank on a single GPU while preserving the target job’s distributed semantics. The survivor rank executes the original training program and performs real local computation. At communication boundaries, the system replaces real multi-rank communication with task-dependent semantics, selectively restoring recorded communication results and recorded or estimated completion timing while preserving the asynchronous dependencies required for analysis. This enables replay from real executions and supports analysis, debugging, and tuning with existing debuggers and performance analysis tools. We evaluate the system on DeepSpeed and Megatron-LM across 8–64-GPU target configurations. RankLens achieves 100% training-tensor communication-structure match, keeps emulation timing error below 5%, supports local anomaly reproduction and execution analysis, and reduces the resource requirement of these analyses from target-scale clusters to a single GPU. 

Index Terms —Distributed Training, Single-Rank Emulation, Communication Replay, Distributed Debugging, Performance Analysis 

I. I NTRODUCTION 

The rapid scaling of AI models has placed increasing demands on training infrastructure, both in system complexity and resource requirements [1]–[4]. Modern distributed train-ing systems combine data, tensor, and pipeline parallelism and use asynchronous communication to overlap computa-tion with data transfer [5], [6]. These mechanisms introduce complex data dependencies and synchronization constraints across ranks, making the numerical state and execution tim-ing of each rank dependent on its peers [6]. Consequently, debugging and tuning tasks such as inspecting anomalous tensors, analyzing communication waits, and examining the overlap between computation and communication require the relevant distributed execution context, even when the analysis focuses on a single rank [7], [8]. Reproducing and examining these behaviors through actual distributed execution typically requires provisioning the corresponding multi-GPU configura-tion, while repeated runs to collect additional observations or

This creates a mismatch between the scope of analysis and its resource requirements: the behavior of interest may be local to a single rank, yet reproducing it remains tied to the full distributed configuration. A straightforward way to reduce this cost is to simplify distributed training into conventional single-GPU execution. However, this changes the original parallel configuration and communication paths. To reduce reliance on full-cluster ex-ecution, prior work has developed performance models for estimating training costs [9]–[13], as well as simulation and trace-based analysis tools for exploring training configurations, hardware designs, and optimizations [8], [14]–[21]. Recent systems further advance low-cost training analysis through execution modeling, framework code reuse, and hybrid em-ulation [22]–[24]. These systems focus on reproducing target-scale execution behavior and interactions under limited re-sources, while rank-local debugging and tuning further require identifying which numerical states, timing effects, and execu-tion dependencies must be preserved for direct inspection and evaluation of local changes. We therefore ask: how can the resources required for local analysis be reduced to a single GPU while preserving the numerical behavior, timing effects, and execution dependencies needed to reproduce, directly inspect, and tune the behavior of interest in the target rank’s original code? Our approach builds on a key observation: analyzing a target rank in distributed training does not necessarily require execut-ing all ranks. The effects of remote ranks can be represented at communication boundaries by communication context, result values, and completion timing, while the target rank performs its actual local computation. Different analysis tasks require different subsets of these effects. Given the required com-munication effects and execution conditions, the target rank’s original training code can therefore run on a single GPU, with the necessary communication effects restored to reproduce and analyze its local execution behavior. Turning this observation into single-rank emulation for debugging and tuning is not as simple as bypassing peer-rank execution. The system must preserve the target rank’s original distributed execution context, restore the required effects at the corresponding communication events, and preserve their asyn-chronous dependencies with subsequent computation [5]–[7], arXiv:2610.18009v1 [cs.DC] 13 Oct 2026 [25]. Distorting any of these properties can cause the replayed execution to diverge from the target execution, undermining its utility for debugging and tuning. Building on this observation, we present RankLens , asingle-rank emulation system for debugging and tuning dis-tributed training. RankLens virtualizes distributed state to preserve the logical context of the target configuration, allow-ing the original training program to follow the target rank’s distributed execution path on a single GPU while executing its local computation. At communication boundaries, RankLens maps collective and point-to-point (P2P) calls to virtual com-munication events, restores recorded communication results when required, and controls asynchronous completion through substituted Work objects. Communication timing can be re-stored from recorded executions or estimated from historical communication records when target-scale timing traces are unavailable or when tuning changes introduce communication works not covered by the original trace. The restored results are consumed by the original program, enabling developers to use existing debuggers (e.g., GDB [26] and debugpy [27]) to inspect anomalous tensors and their effects on subsequent computation and control flow. The same execution environ-ment also supports analysis of computation-communication overlap and waiting behavior with Nsight Systems [28], while allowing developers to modify local computation or scheduling and directly observe the resulting timing changes. A. Distributed Training Execution and Communication Se-mantics 

Distributed training frameworks organize execution through ranks, process groups, parallelization strategies, and commu-nication operations. For example, DeepSpeed ZeRO changes data layout and communication behavior by partitioning pa-rameters, gradients, and optimizer states [25], while Megatron-LM combines multiple parallelism dimensions, such as data, tensor, and pipeline parallelism, with corresponding process groups [5]. Consequently, the distributed execution path is determined not only by the model architecture, but also by rank organization, process-group structure, communication order, synchronization points, and framework control logic. Communication operations are embedded in this execution path and often exhibit asynchronous semantics. In PyTorch, for example, distributed communication may return an asyn-chronous Work whose result is consumed only at a later 

wait or synchronization point [6], [7]. A communication operation therefore involves not only invocation, but also sub-mission, completion, and synchronization, which jointly affect tensor states and the computation–communication timeline. Different analysis tasks depend on different communication semantics: communication-path analysis primarily relies on process-group context and invocation order, overlap analysis depends on communication completion and synchronization timing, and numerical debugging requires post-communication tensor states. Thus, low-resource debugging and tuning cannot simply reduce the number of GPUs; they must preserve the distributed execution context and communication semantics required by the target analysis. 

B. Motivating Debugging and Tuning Scenarios 

In large-scale distributed training, issues such as anomalous tensors, communication stalls, and insufficient computation– communication overlap often require further diagnosis us-ing logs, profiling tools, or runtime checks. Obtaining finer-grained information typically requires repeatedly reproducing the relevant execution window with additional tracing or instrumentation [29]. If each analysis iteration depends on the original distributed configuration, debugging and tuning remain tightly coupled to large-scale GPU resources. Numerical debugging primarily depends on tensor states around communication boundaries. Training states such as gradients, parameter shards, and activations are propagated across ranks through collective or P2P communication [5], [6], [25], allowing numerical anomalies to spread across ranks. Further diagnosis requires associating an anomaly with the corresponding communication event and inspecting the communication result observed by the target rank and its effect on subsequent local computation. Such analysis therefore requires preserving both the communication context and the corresponding communication results. C. Scope and Requirements 

We focus on local debugging and tuning through single-rank emulation of a target distributed execution. Given a target rank, the goal is to reproduce and inspect the execution behavior relevant to a specific analysis task and evaluate local changes with limited resources, rather than reconstructing the complete all-rank execution. Therefore, the system only needs to preserve the effects of peer ranks that are visible to the target rank at communication boundaries and relevant to the analysis task. Supporting such analysis imposes three requirements on single-rank replay. First, the target rank must continue along the original distributed execution path rather than falling back to conventional single-GPU training. Second, the system must restore the structure, value, or timing semantics required by the analysis task. Finally, these communication effects must be applied to the corresponding communication events while preserving the original asynchronous execution dependencies. Accordingly, we scope the problem to replay-based em-ulation of a target distributed execution. RankLens restores structural and numerical effects from execution records to re-produce on a single GPU, the target rank’s execution behavior relevant to the analysis task. Communication timing can either be replayed from recorded executions or estimated from histor-ical communication records when target-scale timing traces are unavailable. The emulated execution assumes correspondence with the target execution in communication structure and control flow, allowing developers to inspect recorded behavior or evaluate local tuning changes within the preserved execution context. III. S YSTEM DESIGN 

A. System Overview 

Figure 1 illustrates the overall architecture of RankLens ,which performs emulation based on the original training script, distributed framework configuration, parallelization strategy, and target execution configuration. Depending on the analysis objective, the system constructs layered traces to provide the required communication effects (§III-B). After trace construction, the single-rank emulation engine runs the original user training script without modifying its model definition or training loop on a single GPU. Rather than falling back to ordinary single-GPU training, the survivor rank observes a virtualized distributed execution environment, allowing it to construct process groups according to the target configuration, enter the original distributed control flow, and trigger the corresponding collective and P2P operations and asynchronous communication work (§III-C). Within this en-vironment, the survivor rank performs real local computation along the preserved execution path. When the survivor rank issues a communication operation, the system replaces real multi-rank communication with task-dependent communication semantics at the communication boundary (§III-D). Structure and timing replay preserves com-munication structure and uses recorded or estimated commu-nication timing to support performance analysis and tuning. Value-enhanced replay additionally restores recorded post-communication tensor states to support local debugging within the original program. Because local computation remains real execution, developers can modify local computation or scheduling and observe the resulting timing changes within the preserved distributed execution context. Through this single-rank execution with task-dependent communication substitu-tion, the system converts a class of distributed training analysis tasks that would otherwise require large-scale clusters into executable emulation on a single GPU.

They capture the training context, framework-visible communication works and their timing, and communication-library-level metadata and optional payloads, respectively. Together, they provide the information required for structure and timing replay and value-enhanced replay. Figure 2 shows the layered trace collection workflow. C. Single-Rank Distributed Emulation Environment 

Ordinary single-GPU training collapses framework-visible distributed state, changing process-group construction, com-munication calls, and synchronization behavior. To preserve the target distributed path with fewer resources, RankLens constructs a single-rank distributed emulation environment where one survivor rank runs on a single GPU while observing the target job’s rank, world-size, topology, and process-group semantics. The environment combines distributed state vir-tualization , which preserves the logical state needed for ini-tialization and distributed control flow, with communication virtualization , which turns collective and P2P operations into virtual communication events while preserving their interfaces, ordering, and asynchronous work lifecycle. Together, they keep the survivor rank on the target distributed path and expose communication boundaries for replay-based emulation (§III-D).

The system maintains two classes of virtualized state. Topology-level state represents the survivor rank’s intra-node and inter-node placement in the target job, preserving its rank metadata and target topology metadata. Group-level state encodes the process-group semantics induced by the paral-lelization strategy, preserving the target process groups and their parallel-group metadata. The former defines rank place-ment and node boundaries, while the latter defines distributed component construction and collective and P2P call sites. Together, they provide the logical runtime state required for the survivor rank to follow the original distributed path. While preserving the above logical state, the system de-couples it from physical execution and GPU resources. The framework still observes the target world size, rank map-ping, and process-group structure, but only the survivor rank executes the full training loop. The participation of non-survivor ranks in initialization, checks, and synchronization is replaced with deterministic local semantics, and framework-level logical device selection is mapped to the survivor GPU. This preserves the target distributed runtime semantics without provisioning the full set of training processes, GPU contexts, and model replicas required by the target job. With these mechanisms, the survivor rank executes the framework-level distributed path as a logical rank in the target distributed job and reaches the corresponding communication boundaries. Distributed state virtualization preserves the dis-tributed control flow up to these boundaries; communication virtualization then preserves the communication interfaces, ordering, and asynchronous lifecycle at the communication boundary. 

2) Communication Virtualization: Communication virtual-ization allows collective and P2P operations issued by the survivor rank to proceed without real multi-rank commu-nication. When a communication call is issued along the original distributed control flow, RankLens intercepts it at the communication-library layer and maps it to a virtual commu-nication event. The event records the communication context needed for subsequent emulation, including the communicator context, operation type, tensor metadata, message size, CUDA stream, and step-local sequence. This preserves the original communication invocation sites, signatures, and ordering while avoiding communication with peer ranks. To preserve the communication-library interface, RankLens maintains lightweight virtual communicators that reflect the target rank and group context without being backed by physi-cal multi-GPU resources. Intercepted calls preserve their com-municator context, stream association, and grouped submission boundaries, but skip the actual multi-rank communication and return compatible local semantics. For value-sensitive anal-ysis, the intercepted communication boundary also provides access to the corresponding buffers for optional restoration of recorded communication results. Timing and completion semantics are handled separately by the upper-level emulation backend. 

D. Replay-Based Emulation 

Replay-based emulation restores the communication effects required by single-rank execution without re-executing peer ranks. As described in §III-C, the emulation environment preserves the survivor rank’s original distributed execution path and converts its collective and P2P calls into virtual communication events. According to the analysis objective, RankLens restores the required communication structure, tim-ing, or values at the corresponding communication bound-aries. Timing can be obtained from recorded executions or estimated from historical communication records, while value-enhanced replay restores recorded communication results at the communication-library layer. The emulation engine first attempts to align each virtual communication event with an execution record using its training position, process-group context, operation signature, message size, and submission order. Matched records provide communication metadata, recorded durations, and optional payloads. For timing analysis, unmatched communication works can instead use durations estimated from historical communication records. 

1) Structure and Timing Replay: In structure replay, execu-tion remains driven by the original distributed training script. Dataset loading, sampler behavior, training loop execution, forward and backward computation, gradient synchronization, and parameter updates proceed through the original code, while the replay engine replaces each issued communication work with an emulated communication work. This preserves process-group semantics, communication invocation order, and per-step communication structure without restoring recorded payload contents. Structure replay uses communication meta-data to align events with the recorded execution, but does not require timing injection. For configuration-related execution-path checks, the underlying emulation environment can also run the original script without a timing trace. For timing analysis, each substituted Work object uses a matched recorded duration when available, or a duration estimated from historical traces otherwise. This permits pre-liminary timing analysis without a timing trace of the target execution, provided that communication substitution preserves the execution path relevant to the analysis. The engine con-trols when the work completes rather than blocking execu-tion at communication submission, preserving the original submit, completion, and wait phases. The training program can therefore continue independent computation after commu-nication submission, while dependent computation observes completion through the original synchronization interfaces. This extends structure replay with communication timing to support the analysis of communication waits and computation– communication overlap. 

2) Value-Enhanced Replay: For analyses that depend on post-communication tensor states, the system further supports value-enhanced replay. This extends structure and timing re-play by additionally restoring recorded communication results. It uses the optional buffer contents in the Collective Commu-nication Trace to restore post-communication tensors recorded in real runs. Rather than recomputing communication results from missing peer ranks, the system restores the recorded tensor states at the corresponding communication boundaries. In this work, value-enhanced replay uses durations and output payloads recorded from the same execution. Estimated dura-tions are used only for timing analysis. For each matched event with a recorded payload, the system restores the payload to the corresponding output buffer before subsequent computation consumes it. Value restoration must respect the asynchronous completion and synchronization dependencies established by the emulation environment, so that dependent computation observes the restored state. The original training program then continues execution using these values, while its local computation remains unchanged. By combining recorded communication results with execu-tion of the original program, value-enhanced replay supports the reproduction and inspection of local symptoms caused by recorded remote perturbations. Developers can use existing debuggers to set breakpoints, inspect post-communication ten-sors, and step through subsequent local computation to exam-ine the effects of anomalous values. Such reproduction relies on the required local execution state and inputs, as well as correspondence between the replayed and recorded execution. It exposes the effects of recorded communication results on the survivor rank without reconstructing the execution of the remote ranks. 

E. Support for Existing Debugging and Performance Analysis Tools 

RankLens preserves the target rank’s original training code and real local computation, allowing existing debugging and performance analysis tools to be used directly. For numeri-cal debugging, developers can use debugpy [27] to inspect restored tensors and their effects on subsequent computation, while GDB [26] can be used to examine native execution states and call paths in the underlying runtime. For performance analysis and tuning, Nsight Systems [28] can be used to analyze communication waits, computation–communication overlap, and the impact of local code or scheduling changes on the execution timeline. IV. I MPLEMENTATION 

RankLens realizes emulated execution at three layers: the framework runtime layer, the process-group communication backend layer, and the collective communication library layer. At the framework runtime layer, RankLens applies lightweight patching to adapt selected runtime logic in dis-tributed training frameworks, allowing the training program to preserve the logical state and execution flow required by the target distributed configuration on a single GPU. We make the necessary adaptations to PyTorch, DeepSpeed, and Megatron-LM, mainly around distributed initialization, state management, and framework control logic. As a result, the original training code can enter the single-rank emulation environment without modifying the model definition or main training loop. At the process-group communication backend layer, Ran-kLens implements a custom backend based on the PyTorch 

ProcessGroup interface. Its interface and Work lifecycle follow those of the native ProcessGroupNCCL backend, while introducing communication substitution and timing con-trol for single-rank emulation. During real distributed ex-ecution, the backend records communication-work context, operation type, message size, and measured duration. During emulation, RankLens constructs a corresponding emulated communication Work for each communication call and injects the matched duration to control its logical completion time while preserving the original asynchronous dependencies. When a measured duration is unavailable or a tuning change introduces an unmatched communication work, RankLens estimates its duration from historical records. It retrieves semantically similar samples according to features such as communication type, Process Group size, topology and rank locality, message size, and the relative position of the Work 

in the training execution flow. A local weighted regression is then applied to the neighboring samples to estimate the target communication duration, which is injected into the emulated 

Work through the same timing-control mechanism. At the collective communication library layer, RankLens instruments NCCL communicator, group, collective, and P2P interfaces through dynamic function interception and sym-bol redirection, exposing low-level communication boundaries without modifying the upper-level training code. For each intercepted call, the system records information such as the operation type, communication context, buffer metadata, mes-sage size, and CUDA stream. During emulation, the actual multi-rank communication is bypassed and replaced with local semantics compatible with the original NCCL interface. For debugging tasks that require numerical semantics, RankLens can further restore recorded communication results to the corresponding buffers at these communication boundaries, al-lowing subsequent local computation to consume the restored states. R ELATED WORK 

Related work spans three directions: performance modeling and simulation, execution-based emulation, and distributed replay and diagnosis. RankLens connects execution-based emulation with local replay to support numerical inspection and execution analysis on a single GPU. 

Performance modeling and simulation. Prior work de-velops performance models and simulators to analyze dis-tributed training and evaluate configuration and system design choices [30], [31]. Paleo, AMPeD, and Calculon use analytical models, while Habitat and NeuSight use profiling information or learned models to predict training performance [9]–[13]. Daydream, dPRO, and Lumos use trace-derived dependency graphs to analyze bottlenecks and evaluate optimizations [8], [16], [20]. ASTRA-Sim, SimAI, Proteus, TrioSim, and Multi-verse simulate distributed training workloads to study compu-tation, communication, and system configurations [14], [15], [17]–[19], [21]. RankLens focuses on executing the target rank’s real local computation with recorded communication effects, making its numerical state and execution behavior directly inspectable. 

Execution-based emulation. Related systems reuse appli-cation or framework execution to reproduce behavior with fewer resources. SMPI executes MPI applications with sim-ulated communication [32], while DNNEmu replaces com-putation with predicted operator runtimes for performance emulation [33]. TorchSim uses FakeTensor and FakeProcess-Group for runtime and memory estimation [22]. Phantora reuses unmodified ML frameworks while simulating GPU computation and communication [23]. NeuronaBox executes a subset of nodes while emulating their external communication environment [34]. PrismLLM executes selected ranks and uses assistant GPUs to replay virtual-rank graphs and participate in real communication [24]. RankLens retains one rank’s real GPU computation and restores recorded communication outputs and completion timing without communicating with peer ranks. Its replay is limited to conditions under which the recorded effects remain applicable. 

Distributed replay and diagnosis. MPI data replay enables independent process replay from recorded communication data [35]. MPIWiz combines data and order recording [36], while ReMPI records message-matching order for determinis-tic replay [37]. Flight Recorder uses communication records to diagnose stalled jobs and collective timeouts [29]. RankLens builds on local replay by combining logical distributed context, communication-result restoration, and asynchronous comple-tion control in GPU training frameworks. This supports numer-ical inspection and analysis of computation–communication overlap and synchronization behavior within the original pro-gram. VII. C ONCLUSION 

We presented RankLens , a single-rank emulation system for debugging and tuning distributed training on a single GPU. Its central insight is that rank-local analysis can pre-serve the required effects of remote execution at commu-nication boundaries while retaining real local computation. RankLens combines distributed state virtualization, restoration of recorded communication results and recorded or estimated timing, and asynchronous completion control to execute the original training program along the target rank’s distributed path. This enables developers to inspect numerical anomalies, analyze computation-communication overlap and synchroniza-tion behavior, and evaluate local scheduling changes using existing debugging and performance analysis tools. Across DeepSpeed and Megatron-LM configurations span-ning 8–64 GPUs, RankLens achieves a 100% match in training-tensor communication signature counts and keeps relative step-time error below 5% with both recorded and esti-mated communication timing. Controlled experiments further demonstrate reproduction and inspection of a communicated gradient anomaly and its effect on parameter updates, as well as identification of a beneficial computation-communication scheduling change. These results show that RankLens enables repeated local debugging and tuning on a single GPU, reducing dependence on target-scale cluster executions. VIII. A CKNOWLEDGMENT
