## Abstract 

New AI accelerators arrive before the kernels that make them fast, because peak kernel performance requires architecture-specific expertise in operand pipelines and data-movement techniques. Coding agents can now write, compile, and tune kernels on their own, so they could greatly accelerate kernel development and optimization. What agents produce de-pends on the interfaces they are given. These interfaces may expose a machine’s raw capabilities or encode the known-good methods for exploiting its hardware features efficiently. We test the performance impact of these two interfaces on Intel GPUs through controlled experiments with three cod-ing models on three kernels. With raw SYCL and execution feedback, Opus 4.8, the strongest of the three models tested, writes a single-GPU GEMM kernel reaching only 57 .5% of Intel’s tuned oneDNN library. We present SyclKittens, a hardware-aware tile programming model for Intel GPUs that encodes these known-good methods, so its operations place operands in matrix-engine layouts, prefetch through the L1 cache, and communicate over the fabric that links GPU stacks into a node. With SyclKittens under the same agent, task, and feedback budget, the agent reaches 82 .1%, showing that encoded methods turn hardware capabilities into perfor-mance. Workload-specific policies stay programmable, and engineers and agents jointly refine these schedules in SyclKit-tens to build a kernel suite that reaches ∼96% of oneDNN in geometric mean across GEMM shapes. The suite runs Llama-3.1-8B inference 1 .59 × faster than torch.compile on one GPU and up to 2 .91 × faster than a matched multi-GPU decode path on Intel’s oneCCL. SyclKittens is open source and available at https://github.com/intel/SyclKittens .

## 1 Introduction 

Supporting diverse AI hardware is limited by the difficulty of building high-performance kernel ecosystems. Tile pro-gramming models such as ThunderKittens and HipKittens package architecture-specific methods for NVIDIA and AMD GPUs, while ParallelKittens extends this approach for multi-ple GPUs [8, 30, 32]. Coding agents can improve programs through execution feedback, and kernel benchmarks show that they can write, compile, benchmark, and revise single-and multi-GPU kernels [5, 27, 37]. We ask whether a tile pro-gramming model can make Intel GPU methods reusable by programmers and coding agents while preserving workload-specific control. In our study, three agentic-coding models produce cor-rect Intel GPU kernels that are substantially slower than the tuned baselines. They use raw SYCL, a C++ program-ming model for heterogeneous systems [19]. The tasks are single-GPU matrix multiplication (GEMM), causal grouped-query attention (GQA) [1], and distributed GEMM. Each model receives Intel documentation and execution feedback and works autonomously under a fixed search budget. On single-GPU GEMM, Opus 4.8 produces the fastest raw-SYCL kernel among the three models, but it reaches only 57.5% of the throughput of oneDNN, Intel’s tuned deep-learning library [24]. An accelerator interface should encode the architecture’s methods as first-class operations while leaving workload policy programmable.

The kernel-suite evaluation tests whether these abstractions support high performance across a broad range of operations. ## 2 Background and Motivation 

2.1 Tile Programming and Coding Agents 

Tile programming models expose fixed-shape register and shared-memory tiles, layouts that address larger tensors in memory, and bulk movement, matrix, reduction, and syn-chronization operations. They sit between tensor compil-ers, which choose most schedules, and low-level GPU pro-gramming, which exposes individual lanes and instructions. This middle layer separates tile-level algorithms from the architecture-specific layouts, movement, and scheduling that realize them. ThunderKittens [30] and HipKittens [8] provide hardware-aware interfaces on NVIDIA and AMD, respec-tively, and their shared primitives provide the conceptual starting point for SyclKittens. A prior IWOCL study ported ThunderKittens directly to SYCL for Intel kernels on a sin-gle GPU [18]. SyclKittens extends that work with the Intel-specific operations in §3, including partial-tile cooperative prefetch and topology-aware communication, and evaluates their use in full-model inference. Other systems divide control between the programmer and the compiler differently. CuTe/CUTLASS provides fine-grained layout and thread-participation control through C++ templates [22, 23], while TileLang separates tile dataflow from schedule selection [36]. For Intel GPUs, programmers can use portable SYCL [19], explicit SIMD (ESIMD) vec-tors [9], compiler-selected Triton schedules through Intel’s XPU backend [15, 33], or template libraries with native hard-ware control, such as XeTLA [11] and SYCL-TLA [14]. Intel’s oneAPI toolchain also provides joint_matrix , a portable SYCL extension that drives matrix engines while hiding the operand layouts SyclKittens makes explicit. At node scale, ParallelKittens [32] extends ThunderKit-tens to multiple GPUs and composes communication with computation through NVIDIA interconnects. Intel oneCCL provides tuned collective operations [34]. SyclKittens ex-poses peer-memory operations and synchronization within kernels so that programmers can coordinate data movement with computation across Intel GPU stacks and packages. These operations let kernels overlap communication with attention in the manner of ring attention [20]. AI coding agents can generate and iteratively improve pro-grams, but for GPU kernels, correctness and performance are separate objectives. KernelBench [27] evaluates fast, correct single-GPU kernel generation over 250 PyTorch workloads. ParallelKernelBench [5] extends the setting to multi-GPU PyTorch+NCCL baselines and fine-grained CUDA or DSL kernels. Both establish that execution and profiling feedback help. Our controlled study on Intel GPUs separates the effect of the tile interface from that of example kernels. Raw SYCL

2.2 Intel GPU Model 

We study the Intel Data Center GPU Max 1550 (Intel Max GPU) [2, 4, 10, 17]. Each package is one PCIe device built from two stacks , Intel’s term for its physical GPU tiles. We run the flat device hierarchy, so each stack is exposed as its own SYCL device with 56 Xe cores and 64 GB of HBM2e, and a node presents 12 stacks across 6 packages. In work-load and performance descriptions, we call each exposed stack a GPU ; we reserve stack and package for the physical topology. Throughout this paper, tile refers only to a register or shared tile in the language, and not to a partition of the hardware. Figure 2 summarizes the stack and node hierarchy, and the three hardware properties discussed below shape the SyclKittens design in §3. 

Execution and registers. Intel software addresses reg-ister operands as linear vectors along the SIMD direction, one element per lane, whereas NVIDIA tensor-core inter-faces use matrix fragments distributed across a warp. The shared tile abstractions therefore require different physical register layouts on the two architectures. A subgroup is the SIMD execution group within a workgroup. The Intel Max GPU supports 16- or 32-lane subgroups, while its Xe Ma-trix Extensions (XMX) matrix engines only consume 16-lane subgroups. When all 16 lanes move one four-byte register el-ement, the subgroup access spans exactly one 64-byte cache line. These execution and transaction widths determine the register-tile mapping in §3.2. 

Operand delivery. The Intel Max GPU supports direct matrix-operand delivery through the cache hierarchy. A hardware 2-D prefetch warms an L1 cache of up to 512 KB per Xe core, and a 2-D demand load then moves the cached operand into subgroup registers. Shared local memory (SLM) remains available. The SyclKittens matrix path studied here uses L1 prefetch and 2-D demand loads without intermediate SLM staging (Figure 2(a)). This differs from the asynchronous global-to-shared-memory staging used by ThunderKittens. 

Node fabric. The Multi-Die Fabric Interconnect (MDFI) links the two GPU stacks within a package. XeLink, Intel’s peer load/store network between packages, connects pack-ages all-to-all through independent even- and odd-stack planes. Together, these fabrics allow any pair of stacks to communicate directly (Figure 2(b)). Multicast and reduction are composed in software over these peer paths. XeLink also provides per-link copy engines for explicit transfers. How-ever, peer-to-peer communications over these fabrics differ in bandwidth and the number of transfers they can sustain concurrently. MDFI provides substantially higher bandwidth than XeLink. Same-plane traffic uses a direct XeLink path, while cross-plane traffic traverses an additional MDFI link. In distributed GEMM, a topology-aware gather that crosses XeLink once per remote package and replicates over MDFI delivers 1 .42–2 .15 × the end-to-end throughput of the flat gather pipeline (§3.4). Appendix A reports measurement methods, full values, and a cross-vendor terminology map. The tile interface separates algorithmic operations from their architecture-specific lowering. Intel’s upcoming Cres-cent Island data center GPU illustrates which hardware prop-erties a new lowering must consider. It is based on the Intel Xe3p architecture, which retains matrix engines and an L1 operand path [21]. Its scale-up network uses PCIe switches instead of XeLink but remains a load/store fabric. Porting SyclKittens to it would require validating the operand layouts and prefetch parameters and adapting the communication schedules to the new topology. 

2.3 What Raw-SYCL Agents Implement 

We inspect the cold-iteration GEMM kernels in §4 to identify which matrix and communication methods raw-SYCL agents implement. In single-GPU bfloat16 (BF16) GEMM, Sonnet and Haiku produce correct kernels that stage operands in SLM without using XMX. Their best correct kernels reach only 5 .7% and 1 .6% of Intel’s tuned oneDNN baseline. Opus builds an XMX pipeline from SPIR-V operations, including a Dot Product Accumulate Systolic (DPAS) matrix instruction, 2-D block loads, a 𝐵 operand in the interleaved VNNI layout that DPAS requires, and prefetch. However, its thread groups do not coordinate prefetching and repeatedly request the same operand tiles. Its best correct kernel reaches 57 .5% of that baseline. oneDNN generates Intel GPU assembly through nGEN [25] and selects GEMM strategies from a tuned kernel database [26]. The comparison is therefore against oneDNN’s assembly-generating implementation. In the distributed GEMM task, input matrix 𝐴 is row-sharded, 𝐵 is replicated, and every GPU must return the full 

𝐶 = 𝐴𝐵 . A kernel can gather 𝐴 before computing the full output, or compute its local rows of 𝐶 and then gather the output. All nine raw-SYCL cold-iteration trials produce correct kernels, but the models combine these choices differently. Haiku computes local output rows but uses vector fused multiply-add (FMA) operations. Sonnet uses XMX but gath-ers the input and computes the full output on every GPU. Opus uses XMX and overlaps copies across compute and copy queues, but keeps the same replicated-compute de-composition and ignores the MDFI/XeLink topology. Across these trials, no raw-SYCL candidate combines local-output computation, XMX, and topology-aware communication. The best reaches 42 .3% of our frozen, co-measured, topology-aware SyclKittens hand reference.

## 3 SyclKittens 

SyclKittens is a header-only C++ tile programming model for Intel GPUs. Kernels declare typed register or shared-memory tiles, address tensors through global layouts, and express dataflow through tile movement, matrix and reduc-tion operations, and synchronization. The backend lowers these operations to SYCL or SPIR-V and selects their phys-ical lane mappings. Programmers retain C++ control flow and direct access to SYCL or SPIR-V intrinsics. Distributed layouts, peer memory, and GPU-resident synchronization extend the same programming model across a node. The Intel-specific operations encode matrix operand lay-outs and packing, cooperative cache prefetch, and topology-aware communication. Tile shape, prefetch ownership and distance, and work distribution remain programmable. In the cumulative single-GPU GEMM ablation, changes to operand layouts, prefetch, and workload-specific schedules raise the geometric mean from 37 .4% to 96 .3% of tuned oneDNN. The distributed movement ablation reaches 82– 90% of communication-free GEMM throughput across twelve GPUs. §3.1 defines the interface. §3.2 and §3.3 explain operand layouts, packing, and cooperative prefetch, and §3.4 describes communication within a node. 

3.1 Tile Interface 

The register-tile type rt<T,M,N,layout,shape> represents a logical 𝑀 ×𝑁 two-dimensional array of elements of type 

T. The layout parameter selects row- or column-major or-ganization, while shape selects a static physical base tile. The GEMM ablation compares 16 ×16 and 32 ×32 base tiles; rectangular shapes are also supported. Sub-tile coordinates address rectangular regions within a tile and support co-operative prefetch in §3.3. Bulk rectangular movement and matrix or reduction operations are shared with ThunderKit-tens. Kernels choose the ordering of load, compute, and store stages over workgroup tiles. A Global Layout (GL) pairs a device-memory pointer with logical batch, depth, row, and column dimensions. Tile move-ment operations use its coordinates rather than comput-ing byte offsets in each kernel. A Parallel Global Layout (PGL) [32] extends this coordinate space across devices. Ad-ditional API and lowering details appear in Appendix B. 

3.2 Matrix Operand Layouts and Packing 

SyclKittens maps logical row- and column-major tiles onto linear vectors along the SIMD direction, using the 16-lane subgroups that XMX consumes. This differs from matrix fragments distributed across a 32-lane warp in ThunderKit-tens’ NVIDIA mapping. Fixing the subgroup width at 16 avoids a 32-to-16 operand reorganization inherited from that mapping. For BF16 data, a 32-element tile row matches one 64-byte L1 transaction. A 16-element row consumes only half the cache line, leaving the other half for a later access. The 32 ×32 base tile therefore halves L1 transactions per 32 values and consumes each line immediately. In the cumula-tive GEMM ablation, this change raises the geometric mean from 37 .4% to 68 .2% of oneDNN (Table 1). 

Direct B-operand load and packing. The SyclKittens API supports two paths from global memory into registers. One stages through a shared tile in SLM, and the other moves directly from a Global Layout into a register tile.

3.3 Cooperative Cache Prefetch 

SyclKittens separates operand delivery into a prefetch phase and a demand phase. prefetch_load issues a 2-D prefetch hint that warms L1 cache without writing the tile’s regis-ters. A later 2-D demand load transfers the cached operands into subgroup registers. This split allows kernels to prefetch future operands while computing with the current tiles, with-out allocating a shared-memory staging buffer. 

prefetch_load_coop takes sub-tile offsets that identify the operand region to prefetch. Kernels assign these offsets to computing subgroups and choose the prefetch distance. The operation provides partial-tile prefetch; the schedule determines ownership and lookahead. In the cumulative GEMM ablation (Table 1), selective subgroup-masked prefetch raises the geometric mean to 88 .8% of oneDNN. Loop unrolling and snake traversal, which keeps neighboring workgroups within a compact L2 reuse region, raise it to 91 .0%. The masked schedule still warms shared operand regions more than once. With partial-tile de-duplication, each subgroup prefetches a disjoint region of the shared operands using the sub-tile coordinates from §3.1. This ownership assignment warms each shared cache region once and raises the mean to 96 .2%. A final per-shape selection of prefetch distance closes the sequence at 96 .3% of oneDNN. Appendix D reports the protocol, errors, and per-shape results for this GEMM ablation. 

3.4 Topology-Aware GPU Communication 

make_pgl combines per-device GLs and peer pointers, and 

pgl.dev_ptrs[peer] exposes remote high-bandwidth memory (HBM) to ordinary kernel loads and stores. The GPUs share a SYCL context, allowing kernels to dereference peer pointers directly. GPUs synchronize through peer-visible counters without returning to the host. After writing peer memory, the writ-ing GPU publishes completion with a system-scope release atomic ( sycl::atomic_ref ). The reading GPU waits with a system-scope acquire atomic. Observing the matching re-lease makes the preceding writes visible to that GPU. signal ,

wait , and barrier_all implement this protocol.

Feedback and selection. We use a custom Claude Code harness rather than the mini-SWE-agent implementation used by ParallelKernelBench [5, 37]. Both protocols use com-pilation, correctness, and performance feedback, while ours fixes condition-specific staged files and one evaluator. In 

single-shot runs, agents can inspect and edit staged files but cannot compile or execute candidates. Cold iterative starts from the context’s blank task stub and receives at most 20 evaluator calls. Warm iterative starts from an eligible single-shot kernel, retains that source as checkpoint 0, and receives the same feedback budget. Under feedback, the harness re-tains the fastest candidate. After development, we grade the selected candidate on five unseen seeds, with inputs and results withheld from the agent. Every task-specific correct-ness criterion must hold on every seed. 

Performance reporting. Only correct kernels receive performance scores, and peak@3 is the fastest held-out-correct result among the three starts. Single-GPU single-shot and cold-iterative throughput uses a fixed 197.5-TFLOP/s oneDNN baseline reached through the torch.mm dispatch on Intel XPU. Warm-iterative results use oneDNN co-measured with checkpoint 0 and the final kernel on the assigned GPU. Distributed throughput uses our frozen, co-measured SyclKittens hand reference, which gathers the input with a topology-aware schedule and computes the full output on every GPU. GQA uses native PyTorch XPU SDPA with 

enable_gqa=True and is_causal=True , co-measured on the same GPU and trial without importing IPEX. Figure 1(b) instead reports median best-so-far trajectories against co-measured oneDNN. Table 3 reports endpoints from correct kernels under the baseline rules above, so the values differ. Appendix C reports exact correctness gates, distributions, and protocol deviations.

Source inspection identifies implementation choices. 

As §2.3 shows, selected Raw kernels either bypass XMX or fail to coordinate the full operand pipeline. Dense GEMM across shapes and nodes. The GEMM of §3.3 reaches 96 .3% of oneDNN in geometric mean across the 27 shapes in Figure 5(a). geometric-mean throughput. Appendix D reports the direct comparison, exact tables, Stream-K results, and ablations. 

Attention reuses the HipKittens algorithm. The atten-tion kernel reuses the complete HipKittens dataflow algo-rithm through the tile interface. For each query tile, the GQA kernel retains HipKittens’ sequence of tiled 𝑄𝐾 ⊤, running-maximum and normalizer updates, output rescaling, and 𝑃𝑉 

accumulation. The dataflow therefore needs no algorithmic change. SyclKittens re-implements its tile operations with Intel’s matrix, movement, and prefetch instructions. Figure 4 reports the resulting MHA and GQA throughput. The GQA baseline dispatches through its MHA path and repeats eight KV heads to match the 32 query heads, so that margin is against a fallback rather than a tuned vendor GQA kernel. 

Decode-critical operators. The remaining SyclKittens kernels outperform their vendor baselines on the operations that dominate autoregressive decode. These operations either run briefly, so launch overhead matters, or stream weights from memory. Fused root mean square layer normalization (RMSNorm) [38], layer normalization (LayerNorm) [3], and RoPE each use one launch. Split-K GEMV matters most be-cause the five 𝑀 =1 Llama projections account for about 64% of per-token decode latency. SyclKittens maps each output-row reduction across cooperating subgroups so the GPU stays occupied as tensor-parallel shards shrink. Figure 5(b) reports these gains before §6.1 measures them inside a full decode loop. Appendices F and G report the full grids.

6.2 Node-Scale Composition 

At node scale, decode performance depends on communica-tion latency. In the evaluated batch-one decode, each tensor-parallel all-reduce carries one 4096-element BF16 hidden vector (8 KiB), so launch, process, and synchronization la-tency matter more than peak bulk bandwidth. SyclKittens keeps all GPUs in one process and one shared SYCL context; a host thread launches each GPU’s stream, and inline peer movement with system-scope device barriers keeps Python and cross-process dispatch off the per-token path.

6.3 Multi-GPU Decode 

The Llama decoder composes tensor-parallel projections and inline all-reduces with context-parallel attention. Figure 7(b) shows that, at matched GPU count, the SyclKittens decode path outperforms the oneCCL-based path at every context, by up to 2 .91 × at 32K on four GPUs. This comparison in-cludes both the source-partitioned collective and SyclKit-tens’s single-process execution model. The standalone re-sults above measure complete collective calls without the surrounding decoder, while retaining each implementation’s process model. The best layout changes with context. Flat four-way tensor parallelism wins through 32K. At 64K and 128K, TP2 ×CP3 uses six GPUs to shard the growing KV scan, and at 256K, TP4 ×CP3 uses all twelve GPUs and serves at 73.3 ms/token. The last point is a capacity result, since the two-GPU tuned oneCCL path is out of memory there and the SyclKittens configuration uses more GPUs. Appendices I, J, and K provide per-shape tables, integration and correctness details, per-layer collective costs, the ring-attention step breakdown, timing-tail summaries, and layout sweeps. 

## 7 Conclusion 

SyclKittens is a tile programming model for Intel GPUs that provides matrix operand layouts, cooperative cache prefetch, and topology-aware GPU communication as reusable oper-ations. With SyclKittens, the strongest coding agent in our study writes a faster single-GPU GEMM kernel than in raw SYCL under the same task and feedback budget. Through engineer-agent co-design, SyclKittens also supports a kernel suite that approaches oneDNN on GEMM and outperforms SDPA with IPEX on causal MHA. In Llama-3.1-8B inference, it outperforms torch.compile on one GPU and the oneCCL-based decode path on multiple GPUs. A study of human experts in raw SYCL and SyclKittens would test whether the same interface also reduces expert development effort. Once Crescent Island is available, we can test whether SyclKittens’s encoded compute methods transfer while its node schedules are retuned for a PCIe-based fabric [21]. As coding agents take on kernel development for new accelerators, our results suggest that the programming in-terface should carry each architecture’s methods. Agents then start from known-good building blocks and spend their search on workload-specific policies.

## A Hardware and Programming-Interface Map 

This section defines the terminology and programming in-terfaces used in the main paper’s Background and Motivation 

and SyclKittens sections. The cross-vendor table aligns func-tions; implementation costs remain platform-specific. A node contains six GPU packages, each with two stacks connected by MDFI, the load/store stack-to-stack interconnect. XeLink connects the GPU packages all-to-all through two indepen-dent stack planes, even and odd. 

A.1 Measured Fabric Behavior 

We characterize the two communication tiers on the same 12-stack Intel Max GPU node used in the main evaluation. Direct peer kernels issue contiguous remote loads or stores through pointers in one shared SYCL context. The collec-tive measurements use five warmups followed by 15 timed iterations and report the median; the two-stack all-reduce bandwidth uses 2 (𝑁 − 1)𝑆 /( 𝑁 𝑡 ), while distributed-GEMM speedups use raw elapsed-time ratios. These conventions are reported separately because they are not interchangeable estimates of a physical link rate. The topology-aware gather sends each source stripe over XeLink once to one landing stack per remote GPU package, then replicates it to the partner stack over MDFI. This halves XeLink egress relative to every stack fetching every remote stripe. Same-plane transfers can occupy both XeLink planes concurrently; cross-plane transfers additionally consume the six MDFI links, which lowers the number of independent flows the node can sustain. Kernels can issue peer loads and stores over both fabrics. For explicit copies, the Intel Max GPU also exposes per-link copy engines; simply offloading a naive all-pairs copy does not reproduce the bandwidth of a topology-aware schedule. 

A.2 Intel Programming-Interface Taxonomy 

The interfaces available on the same hardware differ in how much schedule structure they expose. SYCL joint_matrix is a portable matrix API. It leaves operand layout and lowering to the implementation, but does not expose the complete 2-D movement and prefetch schedule used here. ESIMD provides Intel-specific explicit-SIMD control and is the substrate for larger template libraries such as XeTLA. Direct SPIR-V built-ins expose individual XMX and 2-D block operations but leave their legal and profitable composition to each kernel author. SyclKittens application kernels use a compact tile program-ming model whose backend lowers to the same Intel SPIR-V operations. The backend defines the SIMD16/XMX contract, physical register layout, VNNI operand transform, cache-based 2-D movement, and partial-tile prefetch operations. Kernels choose prefetch ownership and distance. The con-trolled study therefore evaluates a stable tile programming model with an explicitly architecture-specific lowering.

prefetch_load emits Intel 2-D block-prefetch instructions for the base regions implied by the register-tile shape. It warms L1 but does not write the destination registers; the later load performs the XMX-compatible 2-D block load. The prefetch is therefore a performance hint, not an asyn-chronous copy whose completion is required for correctness. 

prefetch_load_coop exposes ownership within a work-group. One call warms a single 16-column, 8-row, two-block region at the supplied raw row and column offset. The GEMM schedule assigns disjoint offsets to its computing subgroups, so every shared operand region is warmed once while all subgroups continue to issue matrix work. The destination argument supplies tile shape and coordinate types only; it is not modified. 

Cache-based staging. This interface is distinct from two shared memory mechanisms often also called prefetching. SLM staging copies global data into programmer-managed local memory before a synchronized load, while SLM fetch-ahead combines a load, local-memory store, and named-barrier handoff. The measured Intel Max GPU path uses neither. Hardware 2-D prefetch places data in the config-urable 512 KB L1, and each consumer later loads its own register tile. This cache-centric split preserves ordinary load semantics while allowing the cooperative ownership policy in §3.3 to remove redundant warming. 

B.1.4 Measured Limits of SLM Operand Staging. Two measured costs keep shared local memory (SLM) off the operand-staging path on Intel Max GPU, namely narrow matrix-operand loads and compiler overhead from generic address-space qualification. 

A- and B-operand costs. Intel Max GPU has no SLM ma-trix load ( ldmatrix equivalent). Loading an XMX B-operand (16 ×16 bf16) from SLM requires ∼64 individual reads vs. a sin-gle LoadTransformINTEL from HBM. Multiple SLM-based attention-kernel attempts ran an order of magnitude below the HBM-native path (the measured SLM B-operand vari-ant reached 2 .3–3 .0 TFLOPS against tens of TFLOPS for the HBM path) because that 64:1 read penalty compounds with the compiler overhead below. 

Address-space qualification matters. ThunderKit-tens’ st<> shared-tile type stores SLM base pointers as 

uintptr_t , which Intel’s IGC compiler treats as generic address space. IGC emits approximately 1,400 runtime disambiguation IR operations, adding more cost than the SLM staging removes. Typed local_accessor<T> or 

multi_ptr<T,local_space> fixes this, and SyclKittens’s 

move_local<T> of §B.1.2 applies the equivalent annotation. Address-space annotations do not remove the 64:1 read-count difference above, which motivates the direct operand path used by the measured kernels.

## D BF16 GEMM 

Across the 27-shape evaluation suite, the SyclKittens bf16 GEMM with collaborative de-duplicated prefetch achieves 0.963 × oneDNN in geometric-mean throughput. Measure-ments use bf16 output, shape-adaptive launch policies, within-trial co-measurement, and six-node aggregation. 

D.1 Configuration 

GEMM FLOPs are 2 𝑀𝐾𝑁 for both implementations, so their TFLOPS figures are directly comparable. 

D.2 Kernel Implementation and Key Techniques 

The GEMM kernel is a single compile-time-templated trans-lation unit built into a callable per-shape module; each shape in the 27-shape evaluation suite is compiled separately. 

Data flow (per output tile). Each subgroup owns a BM ×

BN (32 ×64) fp32 accumulator register tile c_reg and streams the 𝐾 dimension in BK =32 chunks. For each K-step it loads a BM × BK bf16 𝐴 tile (row-major) and a BK × BN bf16 𝐵 tile (column-major) via 2D block loads, with the VNNI transform applied to B. It issues the DPAS contraction into c_reg and prefetches future 𝐴 /𝐵 panels at the configured lookahead distance. After the K loop, c_reg is scaled and stored. 

Key techniques. 

• Register-resident DPAS tiling. A 32 ×64 fp32 accu-mulator per subgroup (falling back to 16 ×16 register tiles for sub-32 output tiles), bf16 operand tiles, and up to 32 subgroups per work-group keep the systolic array fed. Profiling shows the kernel is DPAS-bound (XVE about 94.5% array-active, L3 bandwidth about 1.3% of peak), so large, well-populated work-groups matter more than additional cache optimization. 

• VNNI 2D block loads. Hardware block-load instruc-tions with the VNNI operand transform deliver bf16 operands to the DPAS unit in their native packed lay-out, avoiding a local-memory staging round trip. 

• Masked prefetch baseline. Before de-duplication, full-tile A prefetches are issued when sg_id % 5 != 0, and full-tile B prefetches are issued when sg_id & 8 != 0 . This selective schedule reaches 88 .8% of oneDNN. Loop unrolling and snake traversal then raise the geometric mean to 91 .0%. 

• Snake-curve group swizzle. Work-group tiles are traversed in an L2-friendly super-stack order, with the swizzle width fixed per shape (4 at 2048 3, 16 at 3072 3/8192 3, 4 at 12288 3/16384 3, 8 for other square shapes, 8 for all rectangular shapes) from a full snake-width sweep. A guard falls back to linear indexing for non-aligned grids, and grid padding with an early-return bounds check (returning when a work-group’s row or column tile index exceeds the grid) prevents tile skips and output corruption on non-divisible snake grids. 

• Collaborative de-duplicated prefetch. The partial-tile policy assigns every subgroup a disjoint slice of the shared 256 ×32 A and 32 ×256 B workgroup panels. Each panel byte is warmed once per K-step, rather than once per consuming subgroup; the prologue uses the same assignment. 

• Shape-adaptive lookahead. De-duplication reduces explicit prefetch traffic by about 3 .6× and enables deeper lookahead, namely distance 2 for all squares and mostly distance 3 for rectangles, with measured distance-1 and distance-2 exceptions. The retained masked baseline instead uses distance 1 for 𝐾 > 4096 and distance 2 otherwise. 

• K-loop unroll (32-way). Exposing 32 K-iterations to the compiler overlaps loads with MMA, measured 

+7% at 8192 3 and +16% at 10240 3 over a 16-way unroll. 

• bf16-output store. The fp32 accumulator is down-converted in-register by a 2-wide round-to-nearest-even convertor, then written with a 2-byte block store, which halves the store traffic of the earlier fp32 path and removes the fp32 global round trip. This matches the oneDNN output dtype; the co-measured bf16/fp32 time ratio is 0.95 on a healthy node.

Measurements use the shared single-GPU isolation proto-col. oneDNN and SyclKittens are loaded into one process and timed in an interleaved round robin. Within a node, each value is the per-shape median of per-trial ratios. The reported ratios are medians of the six node medians. Before a shape enters the results tables, its output is checked against torch.mm by relative Frobenius norm. All measured configurations pass, with maximum error 1 .663 × 10 −3.

F.3 Methodology 

Measurements follow the shared isolation protocol on one se-lected GPU. Eager F.rms_norm /F.layer_norm decomposes RMSNorm into multiple kernels; torch.compile lowers the same operations through Inductor to Triton on XPU. For the fused comparison, SyclKittens writes both the normalized output and residual sum (4 × traffic). The expression torch.compile(F.rms_norm(x+res)) discards the sum (3 ×) and is approximately 30% faster at identical bandwidth. All three measured implementations therefore return (norm, x+res) and use the same useful-byte denominator. An unfused add-then-norm that retains the residual moves 5 × traffic; the fused both-output kernel moves 4 ×, a 20% traffic reduction. The three implementations are interleaved round-robin within each of 10 trials, each with 10 warmup and 30 mea-sured iterations; tables report the per-configuration median. A 2 s GEMM power-condition burn-in precedes measure-ment, and the Inductor graph-cache limit is 64 to prevent eager fallback. All cold-HBM tables use one cache protocol, in which a ∼256 MB buffer is zeroed before every timed call to evict L2, following Triton’s convention, so all reads miss to HBM. Without eviction, small-𝐵 working sets below the ∼204 MB per-GPU L2 report cache bandwidth above the HBM roofline. Warm steady-state latency is recorded separately for decode. RoPE is the transformer block’s other memory-bound ele-mentwise op. The 128-bit coalesced kernel reaches 1020 GB/s. Relative to torch.compile , its geometric-mean speedups are 1 .09 × for cold bandwidth-bound shapes and 1 .98 × for warm decode shapes. 

F.7.1 Configuration. We evaluate halved rotary with 𝐷 =

F.7.2 Wide Chunk-Pair Mapping. RoPE couples ele-ment 𝑑 with 𝑑 + 64 across the two halves of a head. A con-tiguous wide load groups eight adjacent bf16 elements, so it never places a rotary pair on the same lane. The SyclKit-tens load_wide also requires a 128-element multiple and is designed for reductions, so it cannot be used unchanged. The kernel instead re-tiles the raw 128-bit packing from the earlier hand-tuned norm kernel for rotary pairs. 

• One work-item owns one 8-element chunk-pair. 

Work-item (row , 𝑐 ) takes the 𝑐 -th 8-wide chunk of the first half, 𝑥 1 [𝑐 ·8 : 𝑐 ·8+8], and its partner chunk in the second half, 𝑥 2 [𝑐 ·8 : 𝑐 ·8+8], 64 bf16 elements away. Since 𝐷 = 128, there are 8 chunk-pairs per head; consecutive work-items read consecutive 16-byte words, so each subgroup’s transaction is a fully coalesced 256-byte burst. 

• Four 16-byte loads, two 16-byte stores, all coa-lesced. Each item issues one uint4 load apiece for its 𝑥 1, 𝑥 2, cos , and sin chunks. Each load is 16 B, or eight bf16 elements. The item computes the eight ro-tary pairs in fp32 registers and stores the two output chunks as two uint4 writes. Every 𝑥 /out transaction is the widest the Intel Max GPU pipe accepts. 

• Local pair computation. RoPE requires no SLM, bar-rier, or shuffle because each chunk-pair is local to one work-item. This mapping exposes independent work at high occupancy. It requires 𝐷 to be a multiple of 16 and the base to be 16 B aligned, as it is for contiguous 

[𝐵, 𝑁 , 𝐻, 𝐷 ] bf16 with 𝐷 = 128.

H.2 Kernel Implementation and Key Techniques 

For the original hand-designed family, the GEMM kernel is DPAS-bound and reaches approximately 90% of its local roofline. Its distributed overhead therefore comes from mov-ing sharded 𝐴 across the fabric. These methods use the same compute kernel and differ in how and when they place 𝐴 in local HBM. 

Input-gather data flow (per GPU).. (1) each GPU owns one 𝑀 /12 ×𝐾 row-shard of 𝐴 in local HBM; (2) the missing 11 shards are gathered from peers into a contiguous 𝑀 ×𝐾 

landing buffer; (3) one register-resident GEMM computes the full 𝐶 = 𝐴 full 𝐵 over all 𝑀 rows. The methods trade off how step (2) overlaps step (3). 

Key techniques. 

• Topology-aware gather. Cross XeLink once per stripe and replicate within each GPU package. The 12 stacks are organized as six GPU packages with two stacks each; each pair shares a fast intra-package MDFI link outside the XeLink fabric. Flat all-gather has every stack pull all 11 remote shards, roughly 10 fabric crossings per stack. The topology-aware path sends each source stripe across XeLink exactly once to one landing stack per remote GPU package ( landing = 2*q + (p&1) ), then the landing stack replicates the shard to its partner ( partner(t) = tˆ1 ) over MDFI. This halves XeLink egress on the communication-bound workload, giving 1.42× (12288 3) to 2.15× (6144 3)end-to-end distributed-GEMM speedup over the flat gather pipeline in the main paper’s fixed-core move-ment ablation. 

• Within input-gather schedules, materialize-then-GEMM. The topology-aware path gathers all shards to local HBM and then runs one GEMM. Interleaving the gather into the GEMM mainloop or reading re-mote 𝐴 per DPAS inside the kernel is slower in the measured implementations. Remote operand reads stall the DPAS pipeline, while materialization lets the compute kernel use its local operand-delivery path. 

• Gather topology. DMA memcpy gather and EU vec128 copy gather land within 1% of each other at both shapes; both are fabric-bound. The topology-aware path changes the traffic topology. 

• Large shapes hide communication. At 12288 3 the GEMM is big enough that even flat gather reaches 63% of the baseline and the topology-aware path reaches 90%; at 6144 3 the communication-to-compute ratio is higher, so flat gather collapses to 38% while the topology-aware path reaches 82%. 

• Compute-core reuse. The topology-aware path uses the bf16 GEMM kernel (snake-swizzled 32 ×64 ×32 DPAS, per-shape snake width) verbatim; no distributed-specific compute changes, so the single-GPU tuning carries over.

Context-parallel attention combines the fence-free core from Appendix E with ring and all-gather KV distribution. Their memory footprints differ, so both paths are measured under the same performance and correctness gates on three clean nodes.

I.2 Kernel Implementation and Key Techniques 

Ring attention shards context across six GPU packages, with one active GPU stack each. At every step, each GPU com-putes partial attention for its local queries against the resi-dent KV shard, rotates that shard one XeLink hop, and up-dates the online-softmax state. The ring implementation pairs independently tuned collective and compute implemen-tations. Both methods use ThunderKittens tile primitives. 

Data flow (per ring step, per active GPU).. Each step has three stages. First, the fence-free 256-work-item flash core with 16-query blocks from Appendix E computes partial 

𝑂 /LSE for the local queries and resident KV shard. Second, the kernel merges the max, normalizer, and output accumu-lator into the running online-softmax state. Third, a double-buffered bulk memcpy moves the next KV shard from the ring neighbor through the shared SYCL context into the alternate local-HBM buffer. The in-order queue serializes compute and transfer, so the next step reads local HBM. The overlapped follow-up below uses copy engines to overlap rotation with compute. 

Key techniques. 

• Bulk-memcpy KV rotation. KV shards are copied in bulk to local HBM and attended locally. A mea-sured zero-copy variant instead reads K/V over XeLink 

> 37 Yehong Jiang, Sheng Chen, Fangwen Fu, Yen-Kuang Chen, Xinmin Tian, Stuart H. Sul, and Simran Arora

for each DPAS operation. Because these reads do not overlap asynchronously with the DPAS engine, that variant stalls compute and is 5–50 × slower. 

• Double-buffered rotation. Two KV buffers (curren-t/next) keep the active and incoming shards separate. They also support the overlapped follow-up, which hides rotation latency behind compute at large 𝑁 per .

• Fence-free 256-work-item compute core. The same software-fence-free single-pass flash kernel used for single-GPU attention (Q preloaded once, IGC SWSB hazard ordering, split-D output, LPT launch order); about 15% faster at large 𝑁 than the earlier fence-heavy 128-work-item core it replaces. 

• In-order queue serialization (no explicit fences between phases). The per-GPU in-order SYCL queue orders compute then rotate implicitly; no host-side event fence is inserted between the flash kernel and the rotation memcpy. 

All-gather attention. Instead of rotating one shard per step, each active GPU gathers the entire 𝑁 total KV up front and runs one flash pass over the full context. Two techniques define this path. 

• Fan-out push all-gather. Each active GPU reads its own KV shard once and writes it into the full 

[𝐵, 𝑁 total , 𝐻 kv , 𝐷 ] buffer of all five peers at its own slot in one parallel loop over cached peer pointers. The self-shard uses a local memcpy . This is the fan-out push pattern from the general-purpose all-gather in Appen-dix J. It sustains approximately 400 GB/s aggregate across the node, compared with the approximately 16 GB/s non-adjacent link that limits strict ring rota-tion and approximately 108 GB/s for the earlier fan-in pull gather. 

• Single flash pass without online merge. The gath-ered KV is complete, so the validated 256-work-item core attends all 𝑁 total keys in one pass. The kernel already reads the KV buffer depth for the number of GPUs holding KV shards and uses 𝑁 per for the query grid, so 𝑁 𝑞 ≠ 𝑁 𝑘𝑣 needs only a thin dispatch wrapper, no softmax-merge reduction. Ring instead performs six rotations and online merges. The trade-off is memory, because all-gather is O( 𝑁 total )per GPU and runs out of memory once the gathered con-text exceeds HBM, whereas ring stays O( 𝑁 per ). Section I.4 quantifies the crossover.

## J Multi-GPU Collectives

J.2 Kernel Implementation and Key Techniques 

Every SyclKittens collective builds on direct peer read/write, so GPU 𝑑 ’s kernel addresses GPU 𝑘 ’s HBM through the shared SYCL context, with a single host barrier per phase and no staging through host memory. Three measured tech-niques shape the per-collective kernels. 

• Remote-write fan-out. On the measured peer route, a remote write sustains ∼18.8 GB/s versus ∼15.7 GB/s for a remote read. All-gather and large-payload all-reduce use fan-out push. Each GPU reads its local slice once and writes it to all 𝑁 −1 remote destinations. Lo-cal HBM reads cost 𝑒𝑝𝑑 rather than (𝑁 −1) 𝑒𝑝𝑑 , leav-ing bandwidth for incoming remote writes and avoid-ing the HBM collapse of large-payload pull kernels. 

• Hierarchical reduction. For all-reduce and reduce-scatter the hierarchical path first sums each GPU pack-age’s two GPU stacks over MDFI, then reduces the partials from the six GPU packages over XeLink, halv-ing the XeLink message count (the copy now carries already-summed data). 

• Destination-split fused EU copy. For all-to-all, one kernel per source GPU pushes all 𝑁 chunks with by-value dispatch tables, while each workgroup owns one destination. This removes the per-message launch floor and exposes independent remote endpoints con-currently. The topology-aware all-gather uses the cor-responding fused latency path. The reduction and gather kernels dispatch adaptively be-tween latency- and bandwidth-oriented paths. All-to-all uses the destination-split path at every size because it is neutral at the launch floor and wins as endpoint traffic grows. 

J.2.1 Multi-GPU API. The collective kernels use the PGL peer-pointer table, Intel Max GPU topology planner, and system-scope atomic synchronization introduced in the tile-language appendix. These replace ThunderKittens’ CUDA NVLS multicast lowering while preserving explicit control over slice ownership, transfer direction, and schedule. We validated the API conversion of all-gather, reduce-scatter, all-reduce, and all-to-all against immutable pre-conversion binaries with complementary raw–API–API–raw and API–raw–raw–API orderings.
