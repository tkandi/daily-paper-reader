## Abstract 

Large language models (LLMs) have become the backbone of mod-ern AI applications, but pose significant challenges for efficient inference. Their autoregressive generation divides execution into two phases: prefill , dominated by large GEMMs, and decoding , dom-inated by small GEMVs. Modern serving systems further introduce complexity through continuous batching and prefill–decoding dis-aggregation, leading to dynamic workloads and phase separation. However, existing accelerators remain poorly aligned with these system-level behaviors, resulting in inefficiencies in LLM serving. In this work, we present DynaCore , a unified architecture for efficient LLM serving via system–architecture co-design. We ob-serve that the compute tile a systolic array executes, its Minimum Efficient Unit (MEU), spans all three GEMM dimensions. DynaCore 

reshapes the MEU along all three: spatially it trades array width against height asymmetrically , raising weight delivery while leav-ing the input path untouched, and temporally Split-𝐾 maps the reduction onto the array, folding partial sums through the intercon-nect the array already has. To exploit phase separation, we further propose disaggregated quantization , applying dual-side quantiza-tion to prefill and weight-only quantization to decoding, with an inner-product mixed-precision datapath that keeps output width invariant to precision. A runtime scheduling framework then se-lects an MEU per batch. Evaluation with real-world serving traces shows that DynaCore substantially reduces service-level latency over quantization and reconfigurable accelerators, improving TTFT 

by 3 .50 × and 2 .97 × and TPOT by 36 .55 × and 8 .02 ×, respectively. 

## 1 Introduction 

Large Language Models (LLMs) [7, 16, 17, 27, 45, 50, 53, 54] have become the foundation of a wide range of real-world applications, including natural language understanding [15, 38, 54, 63] and code generation [52, 58, 64]. As model sizes continue to grow, LLM serv-ing increasingly stresses computing infrastructure, with inference emerging as the primary performance and cost bottleneck. A key

challenge in LLM inference stems from its autoregressive genera-tion paradigm [30, 55, 56], which divides execution into two fun-damentally different phases: prefill and decoding [42]. The prefill phase processes all input tokens in parallel using compute-intensive matrix–matrix multiplications (GEMMs), achieving high utilization on modern accelerators. In contrast, the decoding phase generates tokens sequentially, where each step is dominated by matrix–vector multiplications (GEMVs) with limited parallelism and low arith-metic intensity. This fundamental shift from throughput-oriented to latency-sensitive computation leads to severe hardware under-utilization during decoding, making it the dominant bottleneck in end-to-end LLM serving [2, 34, 41, 42]. To mitigate the inefficiency of the decoding phase, prior works have explored optimizations across both algorithmic and system levels. From an algorithmic perspective, decoding is widely rec-ognized as a memory-bound workload in which weight accesses dominate execution (often accounting for over 90% of memory traffic), while activation footprints remain relatively small [24, 42]. This observation has motivated weight-only quantization tech-niques [31, 36, 48], which reduce memory bandwidth demand by compressing model weights, thereby improving performance in memory-bound regimes. From a system perspective, continuous batching (CB) [24, 59] improves effective parallelism by aggre-gating decoding requests. Additionally, when prefill and decod-ing are co-located on the same device, resource contention leads to significant latency variability. Prefill–decoding disaggregation (PDD) [41, 43, 62] alleviates this interference by separating the two phases across devices, reducing decoding latency. Despite these advances, existing accelerator designs remain poorly aligned with the combined effects of algorithmic and system-level optimizations in LLM serving. This misalignment arises be-cause prefill and decoding exhibit fundamentally different execution characteristics, yet current designs lack cross-layer co-design across algorithms, systems, and hardware. First, decoding remains a fundamental bottleneck due to the low hardware utilization of GEMV operations. Modern accelerators, particularly systolic-array-based designs [10, 28, 29, 32, 47], are

## 2 Background and Motivation 2.1 LLM Inference and Characteristics 

Large Language Models (LLMs) [7, 17, 27], such as GPT [1, 16, 44, 45] and LLaMA [20, 53, 54], are built on the Transformer architec-ture [55], comprising stacked attention and feed-forward layers. During inference, LLMs generate text in an autoregressive manner. 

Prefill. Given a prompt, the model first performs a prefill phase, processing all input tokens in parallel across Transformer blocks. As shown in Figure 1, this phase primarily involves large matrix-matrix multiplications (GEMMs), which are well-suited to the dense compute structures of modern accelerators. 

Decoding. After the prefill phase, the model enters the decoding phase, where tokens are generated sequentially, one at a time. As shown in Figure 1, each iteration reuses the same model weights while processing only a single token, turning the computation into a matrix-vector multiplication (GEMV) with extremely limited parallelism and data reuse. ## 2.2 Rethinking System Scheduling 

Modern LLM serving systems [34, 59, 61] introduce highly dy-namic workloads driven by runtime scheduling, which continu-ously changes the balance between prefill and decoding. These dynamics expose a fundamental mismatch between modern LLM serving and static hardware execution models. 

Continuous Batching (CB). CB [2, 34, 59] aggregates requests to improve decoding throughput, but yields highly variable GEMM shapes depending on the number of active tokens. Batch sizes fluctuate as requests arrive and complete, so computation shifts continuously between flat, memory-bound GEMVs and larger, more parallel workloads, leaving hardware utilization inconsistent. 

Prefill-Decoding Disaggregation (PDD). To mitigate inter-ference between phases, modern systems adopt PDD [41, 43, 62], which executes the two phases on separate devices and thereby re-moves the resource contention that degrades decoding throughput when they are co-located. While PDD improves performance, it also exposes a key limitation: statically deploying separate hardware for prefill and decoding leads to resource imbalance under dynamic workloads, as the ratio between phases continuously changes. 

Takeaway. LLM serving exhibits highly dynamic workload char-acteristics, where both GEMM shapes and phase ratios vary over time. This requires a unified architecture that can efficiently sup-port both phases and adapt to changing workloads. Such adaptivity must be coordinated with system scheduling, enabling joint sys-tem–architecture co-design across quantization, array organization, and execution scheduling.

## 2.4 Rethinking Quantization Strategies 

Quantization [4, 16, 18, 31, 36, 37, 48, 57] improves LLM inference efficiency by reducing the precision of weights and activations. Existing approaches typically adopt a unified configuration across both phases, as reflected in prior accelerators in Table 1. However, as the roofline in Figure 3 shows, prefill and decoding sit on opposite sides of the ridge point, making a single scheme suboptimal. 

Decoding. Operating in the memory-bound region, decoding is dominated by weight traffic, so weight-only quantization [31, 36] (e.g., W4A16) reduces the memory-bound latency floor in propor-tion to the weight bit-width. Activations, whose traffic is negligible, are best left in FP16: this preserves accuracy at little memory cost, whereas dual-side quantization [4, 37, 57] (e.g., W8A8) raises weight precision and thus traffic. Reducing compute precision brings lit-tle benefit either, since decoding demands far less arithmetic than FP16 or INT8 units can supply. This gain, however, materializes only if the compute array keeps pace with the memory system. A GEMV on an 𝑆 ×𝑆 output-stationary array activates a single row, leaving 1 /𝑆 of the PEs busy; on a 128 ×128 array at 500 MHz with 4 TB/s of bandwidth, the resulting compute time exceeds the FP16 weight-streaming time by about 31 ×, regardless of model size. De-coding on such an array is therefore utilization-bound rather than bandwidth-bound, and weight-only quantization pays off only after array utilization is restored (Section 4). 

Prefill. For long prompts, prefill sits far from the memory-bound region, so reducing memory traffic yields little. Here throughput is the constraint, and dual-side quantization (e.g., W8A8) is the better fit, doubling arithmetic throughput through INT8 units while maintaining model accuracy. Prefill GEMMs are tall only when the prompt is long, however: since 𝑀 equals the number of prompt tokens, a short prompt yields 𝑀 below the array dimension and inherits the same row underutilization as decoding. 

No Duplication Cost. Assigning different precisions to the two phases does not imply storing two copies of the model. Under PDD, prefill and decoding already execute on separate devices, each holding only the weights for its own phase, so the W8A8 and W4A16 copies reside where they are used and neither device carries the other’s format. 

Accuracy Gain. As shown in Figure 3 (bottom-right), weight-only quantization (e.g., W4A16) leads to noticeable accuracy degra-dation. In contrast, disaggregated quantization, using W4A16 for decoding and W8A8 for prefill, achieves near-lossless accuracy while maintaining high efficiency. Notably, this configuration out-performs both standalone W8A8 and W4A16, achieving a superior efficiency–accuracy trade-off. 

Takeaway. Disaggregated quantization lowers precision on ex-actly the path that asymmetric reshaping stresses, leaving activa-tions untouched on the path that needs no additional bandwidth. Supporting both precisions in one datapath, however, requires a mixed-precision design aware of the array shape, one that aligns with the temporal dimension 𝑘 as well as with the asymmetric provisioning of operand paths.

## 4.3 Flat GEMM: Asymmetric Regrouping 

Reshaping the MEU. A flat GEMM leaves 𝑀 below the array dimension, so the tiling reduces to splitting 𝑁 alone: there is nothing left to split along 𝑀 , and a square mapping simply wastes the rows it cannot fill. The core instead reduces 𝑚 to the available token count and regroups the freed rows into wider logical rows along 

𝑁 . Figure 5(b) shows 𝑀 =2 on the same core: two asserted rows, giving 𝑚 =2 and 𝑛 =8. Although 𝑚 has halved, the temporal extent is unaffected. Each group still spans four columns of the physical array, so an operand still reaches the farthest PE after max (𝑚, 𝑛 ) = 4cycles within its group, leaving 𝑘 =4 and MEU = 2 × 8 × 4.

Asymmetric Adaptation. The two operand paths move in op-posite directions under this regrouping. Halving 𝑚 removes half of the vertical weight reuse, so the buffer must issue two indepen-dent weight streams instead of one; in general, 𝑔 groups require 𝑔 

streams. The input path is untouched, since the same tokens serve every tile and are simply broadcast. This asymmetry is intrinsic to LLM decoding rather than an artifact of the mapping: with 𝑀 small there is little activation data to begin with, so widening the input path buys nothing, and all of the pressure falls on weight delivery. It is the same observation that makes weight-only quantization the prevailing choice for decoding, and Section 6 shows how the two meet.

## 5.1 Partitioning the Reduction 

The array is divided into 𝑡 groups along 𝐾 , each assigned a con-tiguous slice of the reduction and each producing an independent partial sum for the same output tile. The PE budget is then shared three ways,

Each group is an ordinary 𝑚 × 𝑛 sub-array executing an ordinary output-stationary GEMM over its own slice of 𝐾 /𝑡 , driven by the same selector pattern used for spatial regrouping. The weight buffer supplies 𝑡 streams exactly as it would for 𝑡 spatial groups, so the delivery path is unchanged. 

## 5.2 Tick-Tock Reduction 

Splitting along 𝐾 differs from splitting along 𝑀 or 𝑁 in one respect that shapes the entire design. Output tiles produced by different 𝑚 

or 𝑛 groups are independent and simply drain in parallel. Partial sums produced by different 𝑘 groups are not: they are addends of the same result and must be reduced before leaving the array. A dedicated adder tree is the obvious solution and an impractical one. Reducing across 𝑡 groups spanning the array height requires a tree for every one of the 𝑛 columns, together with wiring that gathers operands from PEs at arbitrary vertical distances. At array scale this approaches the cost of a second PE array, and its rout-ing is precisely the long-distance, many-to-one interconnect that dominates physical design. 

DynaCore instead reduces along the vertical path the array al-ready has. The final group is held stationary and serves as the destination accumulator, while every other group releases its par-tial sums downward one row per cycle. A tick moves a partial sum one row down without accumulating; a tock adds the arriving value into the local accumulator, which happens once it reaches its coun-terpart in the group below. A logical row of width 𝑛 occupies 𝑛 /𝑆 

physical rows and a group holds 𝑚 of them, so one group spans 

ℎ = 𝑚 · 𝑛 𝑆 = 𝑆 𝑡 (4) physical rows, using 𝑚 · 𝑛 · 𝑡 = 𝑆 2 from Equation 3. In Figure 6, 𝑡 =2on a 4 × 4 core gives ℎ=2: one tick and one tock. 

## 5.3 Cost at the Output Path 

The scheme is inexpensive because it is the array’s existing drain, with one change. In the baseline design, every PE holds a result and the array empties row by row, each value passing downward through the PEs beneath it, which takes 𝑆 cycles. Under Split-𝐾 the same 𝑆 cycles are spent, but the values passing through the final group are added into it rather than forwarded past it. Reduction and evacuation are thus the same phase: the array still clears in 𝑆 

cycles, and what leaves it is the reduced result rather than 𝑡 separate partial sums.

## 6.1 Outer-Product versus Inner-Product Construction 

Bit-composable PEs [23, 49] build a high-precision multiply from low-precision sub-multipliers, and at reduced precision re-task those sub-multipliers to carry more work. The question is where that work goes. 

Outer product. In the conventional choice (Figure 7(a)), one INT16 multiply decomposes into the four cross terms of {𝑎 1, 𝑎 0 } ⊗ {𝑏 1, 𝑏 0 }, shifted and summed into a single output; at INT8 the same four multipliers are re-interpreted as four unrelated operand pairs that share no reduction. Throughput quadruples, but the output tile expands from 1 ×1 to 2 ×2, so the PE needs four accumulators in-stead of one. Our synthesis results show that this construction costs over 2 × the area of a plain INT16 unit at equal multiplier count, since the added accumulators and output registers, not the multipli-ers, dominate. The penalty also compounds with the floating-point path: with four independent adders already committed to separate outputs, none can be folded into an FP16 accumulation, so FP16 sup-port would require a datapath of its own rather than reusing what is there. Together, these costs make the construction impractical. 

Inner product. DynaCore instead assigns the freed sub-multipliers to operands adjacent along 𝐾 , which the GEMM already reduces. An FP16 multiply needs an 11-bit mantissa product, implemented as a 12-bit multiplier built from nine 4-bit sub-multipliers combined by shift-and-add; two INT8 multiplies need eight of those same nine (Figure 7(b)). The INT8 mode therefore reuses the FP16 struc-ture almost entirely, packing a pair of 𝐾 -adjacent operands into the 16-bit input word and summing their products in place, exactly as the output-stationary dataflow would have summed them across two cycles. The PE still holds one accumulator and emits one 32-bit result; only the effective depth consumed per cycle changes with precision. Operand widths at the array boundary are unchanged, so nothing about the mapping, the drain, or the interconnect is affected. 

## 6.2 Matching the Array Design 

Asymmetric regrouping. Flattening the array multiplies the weight bandwidth required while leaving the input path at a single broad-cast stream, and weight-only quantization relieves exactly that side: at 4 bits the same buffer port supplies four times as many elements per cycle, while activations stay in FP16 on the path that needed no extra bandwidth. Keeping activations at FP16 precision also con-fines dequantization to the buffer interface, so no dequantization logic enters the PEs even when all 𝑆 2 of them are fed independently. 

Split-𝐾 mapping. Split-𝐾 and the inner-product datapath make the same choice at two levels: the former spends surplus PEs on the reduction dimension, the latter spends surplus multiplier capacity there. Both land where the GEMM already reduces, so the work is absorbed by existing accumulators rather than by new outputs. Precision therefore acts only on 𝑘 : packing two INT8 operands per cycle doubles the reduction depth a PE covers, leaving 𝑚 , 𝑛 , and 𝑡 

and the reduction schedule untouched. 

Summary. A single datapath supports W8A8 prefill and W4A16 decoding by directing low-precision throughput along 𝐾 rather than into additional outputs. Output width and count are invariant to precision; weight bandwidth falls by 4 × where the flattened configuration needs it most, and neither the array shape, the drain path, nor the reduction schedule is affected.

Prior work has studied system-level scheduling extensively, so we omit low-level serving heuristics and focus on the interaction between scheduling and the proposed architecture.

## 8.4 Batching Analysis 

To further characterize DynaCore across different regimes, we evalu-ate the decoding latency of Llama-3-8B on a single device with batch sizes ranging from 1 to 256. As shown in Fig. 11, latency remains nearly constant while the PE array is underutilized and increases approximately linearly once the array becomes compute-bound. The fixed 128 × 128 systolic array reaches saturation at a batch size of approximately 128. The reconfigurable designs saturate ear-lier: Planaria at around 32, SARA at around 4, and DynaCore at around 1. DynaCore reaches high utilization even at small batch sizes because its fine-grained array partitioning and split-𝐾 exe-cution expose substantially more parallelism. Beyond saturation, 

DynaCore retains an advantage over the baselines because its com-piler selects the most efficient configuration and scheduling strategy for each workload regime. Consequently, DynaCore achieves the lowest latency across the entire batch-size range, reducing latency by 85 .2× over the systolic array at batch size 1 and by 2 .09 × at batch size 256. Even at large batch size, it achieves the lowest 60 .7 ms per-request latency, com-pared with 66 .5 ms for SARA, 75 .2 ms for Planaria, and 126 .9 ms for the systolic array. 

## 8.5 Multi-Device Evaluation for LLM Serving 

Beyond single-device performance, we evaluate DynaCore in a multi-device online serving environment and focus on service-level objective (SLO) metrics that directly reflect user-perceived latency. 

Evaluation Setup. We simulate an 8-device system handling incoming LLM requests. Each device is a chip instance of a given architecture with off-chip HBM, and devices are interconnected with 16 GB/s links, modeled following [3]; this inter-device com-munication cost is incurred whenever prefill and decoding are partitioned across separate devices. Unlike the single-device setting where prefill and decoding run on the same chip, here we follow the prefill–decoding disaggregation paradigm [41, 62], which improves SLO attainment. Several devices are assigned to prefill, and the remaining devices process decoding tasks. The system is evaluated using the real-world datasets running Llama3.1-8B. For datasets without arrival timestamps, such as ShareGPT and Dolly, request arrivals follow a Poisson process. For MoonCake Conversation and MoonCake Tool, we use the real production times-tamps. The scheduler uses a first-come-first-serve policy: prefill requests form batches according to arrival time, while decoding requests use continuous batching to improve utilization. We measure two SLO metrics: Time to First Token (TTFT), which is mainly determined by prefill latency, and Time Per Output Token (TPOT), which reflects decoding performance.

## 9 Conclusion 

We present DynaCore , a phase-adaptive architecture for efficient LLM serving. By co-designing array organization, quantization, and runtime scheduling, DynaCore aligns hardware execution with the distinct characteristics of prefill and decoding. Our design integrates a splittable systolic array, disaggregated quantization, and adaptive scheduling into a unified framework. Evaluation shows that Dyna-Core substantially reduces service-level latency over FIGLUT and Planaria, improving TTFT by up to 3.50 × and 2.97 × and TPOT by up to 36.55 × and 8.02 ×, respectively, under real workloads. These results demonstrate the effectiveness of phase-aware system– architecture co-design for next-generation LLM serving.
