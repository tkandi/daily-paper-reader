FLASHRT-PAI: FAST KERNELS ARE NOT FAST PIPELINES
FOR PHYSICAL AI INFERENCE
Liang Su
David Chen
Jason Li
Kevin Guo
Teresa Lv
AnyDevice AI & Alps Lab
ABSTRACT
Vision-language-action (VLA), video-action (VA), and world action models (WAMs) form the backbone of
modern physical AI systems, yet their real-time single-batch inference remains a defining bottleneck. Latency is
dominated not by individual kernel computation, but by system-level overhead: thousands of short kernel launches,
intermediate data movement across operator boundaries, and redundant recomputation across consecutive decisions.
General-purpose graph compilers cannot address these costs, as they optimize individual calls in isolation and
lack visibility into cross-call state semantics and global pipeline structure.
We present FLASHRT-PAI, a low-latency inference engine built around model-hardware pipeline co-design
rather than isolated kernel optimization. FLASHRT-PAI combines three core mechanisms: deep kernel fusion
with launch overlap eliminates inter-operator boundaries and launch gaps; an execution contract formalizes the
pipeline’s stage DAG, update rates, and named buffers to enable cross-decision state reuse and selective refresh;
and execution-state capsules enable fast snapshot, restore, and fork of persistent pipeline state. The system also
supports drop-in acceleration of unmodified PyTorch models via parity- and latency-gated kernel replacement.
Evaluation covers six policies on RTX 5090 and four on Jetson AGX Thor. At matched 16-bit precision,
FLASHRT-PAI is 1.3–3.7× faster than official compiled paths. Combining pipeline co-design with reduced
precision delivers 3.38–12.66× speedup over official eager implementations. In LIBERO-10, four-bit π0.5
achieves 94.04% success on Thor and 93.32% on RTX 5090, compared with 92.4% for the measured official FP16
reference. FLASHRT-PAI is open source, distributed via Hugging Face Kernel Hub, and its opt-in π0.5 kernels
have been adopted into the LeRobot framework.

INTRODUCTION
Physical AI places learned policies in robot control loops:
VLAs map images and instructions to actions (Physical In-
telligence et al., 2025; NVIDIA et al., 2025), VAs generate
video and actions autoregressively (Li et al., 2026a), and
WAMs jointly denoise future video and actions (Black For-
est Labs, 2026; NVIDIA et al., 2026; Bi et al., 2026). Each
call returns an action chunk; its inference budget depends
on the host’s observation and action-update schedule. We
study this inference component on edge and workstation
GPUs, with task-level checks in LIBERO simulation.
Growing policies such as π0.7 and FLUX 3 Action have
5–7B parameters (Physical Intelligence et al., 2026; Black
Forest Labs, 2026). On Thor, official π0.5 takes 222.64 ms
eager and 129.17 ms compiled; FLUX 3 Action takes 1.35 s
on RTX 5090 (Table 3). Reducing latency must also pre-
serve action fidelity, since numerical drift can change robot
behavior.

Closing this gap takes more than faster individual kernels.
We present FLASHRT-PAI, an inference engine for low-
latency physical AI, guided by a simple principle: fast ker-
nels are necessary but not sufficient (Dehghani et al., 2021).
For each model–hardware pipeline, FLASHRT-PAI decides
what can be fused, overlapped, or reused across decisions;
an execution contract makes those choices executable. Four
limitations motivate these choices.
First, small kernels repeatedly materialize intermedi-
ates; deep kernel fusion removes selected boundaries.
At batch size one, separate normalization, residual, acti-
vation, and quantization kernels between general matrix
multiplications (GEMMs) can write values that the next
kernel immediately reads. TensorRT (NVIDIA, 2026g),
torch.compile (Ansel et al., 2024), and TVM (Chen
et al., 2018) already fuse common patterns, but some bound-
aries depend on deployment-specific facts, such as a vali-
dated quantization scale and the next GEMM’s input lay-
out.
FLASHRT-PAI uses these facts to hand-write the
producer–consumer path, folding quantization into the pro-
ducer where precision and hardware permit. In π0.5 on
arXiv:2610.24349v1  [cs.AI]  17 Oct 2026


Thor, its FP8 decoder layer uses 12 kernels versus 20 for
torch.compile+FP8 (§3.2).
Second, remaining kernel dependencies need not seri-
alize all work; launch overlap hides part of their cost.
A successor can load weights before it needs its predeces-
sor’s output, but an ordinary graph dependency waits for
the predecessor to finish. At eligible boundaries, FLASHRT-
PAI marks where the successor may start and where it
must wait, then applies CUDA’s Programmatic Dependent
Launch (PDL) (NVIDIA, 2026b). PDL is CUDA’s mech-
anism; FLASHRT-PAI supplies the safe kernel points and
pipeline order. On top of the already fused π0.5 NVFP4
path, it further shortens each decoder layer on Thor (§3.3).
Third, values needed by later decisions are often re-
computed; frozen execution state keeps them valid
and reusable. In the official π0.5 implementation, step-
dependent conditioning is rebuilt on every call; LingBot-VA
similarly recomputes cross-attention keys and values de-
rived from an unchanged instruction. CUDA Graph replay
gives stable addresses but not the application’s rules for
when such values become stale. FLASHRT-PAI names its
fixed and persistent buffers, and records each one’s owner
and refresh rule in the execution contract. It can replay
captured stages without per-kernel host dispatch and reuse
prompt- or step-dependent values across decisions. These
named buffers also form an execution-state capsule that can
be copied to snapshot, restore, or fork a session (§3.4).
Fourth, optimized kernels are hard to adopt; checked re-
placements let an existing host use them selectively. Fast
TensorRT deployments for policies such as π0.5 and GR00T
require model-specific integration (NVIDIA, 2026f;d), and
an existing PyTorch host needs a way to check a replacement
before using it. FLASHRT-PAI packages each replaceable
region with a PyTorch reference and its kernels; the host
keeps its own path unless the replacement matches the ref-
erence and lowers end-to-end latency (§5). FLASHRT-PAI
kernels are distributed through the Hugging Face Kernel
Hub, and LeRobot adopted an opt-in π0.5 kernel integra-
tion (LeRobot contributors, 2026).
We evaluate FLASHRT-PAI on a Jetson AGX Thor for robot-
side inference and an RTX 5090 for workstation inference.
Latency and numerical fidelity use fixed or recorded in-
puts offline; closed-loop task success is evaluated for π0.5
and LingBot-VA in LIBERO simulation. We compare offi-
cial implementations, torch.compile, and available Ten-
sorRT deployments (§4), and report public adoption (§6).

Contributions

• An inference engine built around model–hardware
pipeline co-design. We present FLASHRT-PAI, an

All the policy calls share three structural properties:
1. Parts of the call change at different rates: the instruc-
tion once per task, the observation once per decision,
and the denoising loop several times within each deci-
sion.
2. A deployment fixes the number of views, context-
length bucket, action horizon, and denoising-step count.
These constraints allow fixed-shape stages to be pre-
pared once and replayed.
3. Shapes vary widely within one call. The π0.5 action
expert processes ten rows per step, whereas VA and
WAM backbones process thousands of video and action
tokens. These workloads need different GEMM tiling
and fusion choices; a VA also carries history state
across decisions.
Fixed shapes make replay possible, but they do not by them-
selves determine the fastest execution path. For these poli-
cies, action shapes, the formats exchanged between adjacent
kernels, and the lifetime of prepared values guide the design
choices below.

3
DESIGN OF FLASHRT-PAI
FLASHRT-PAI chooses stage boundaries, update rates,
shapes, layouts, precision, and capture granularity together.
Hand-written kernels implement fusion and launch overlap;
an execution contract then records the completed stage DAG
and buffer rules for replay and capsules. The FLASHRT-PAI
engine owns the captured graphs and fixed-address buffers.
A session manager uses the exported contract to select stage
replays when the application reports changed inputs, and
copies declared state for capsules.
3.1
Architecture and Model Integration
Figure 2 maps a loaded checkpoint into stages with de-

Instruction-dependent work runs at prompt setup; vision,
prefix, and action work run per decision. Setup selects ker-

slower-changing values, and chooses launch boundaries. It
captures the full decision or split context/action stages, then
exports the contract.
At decision time, the robot loop fills swap windows with
observations and noise; the session manager replays the
selected captured stages over fixed-address buffers; and the
host reads the action chunk. Declared state regions can
be copied as capsules. Integration into an existing host is
described in §5.

3.2
Deep Kernel Fusion
FLASHRT-PAI fuses memory-bound work around compute-
heavy kernels: examples include residual addition with nor-
malization and output quantization, RoPE with QKV split
and cache write, and patch embedding with layout conver-
sion. Compute-heavy GEMMs and attention keep their spe-
cialized implementations. We select a fused boundary when
a supported fixed shape and layout let the producer emit
the consumer’s required format, all consumers remain valid,
and the complete path passes fidelity and latency checks.
Other boundaries remain separate.

so that the large tile dimension carries weights and the short

results (§4.5).
3.3
Launch Overlap
Fusion leaves some producer–consumer boundaries intact.
Overlap requires input-independent successor work, a safe
wait before dependent reads, and a measured gain despite
resource contention. At eligible pairs, FLASHRT-PAI uses
CUDA’s programmatic dependent launch (PDL) to start
a successor GEMM’s weight loading before its activation
is ready, then waits before reading that activation. The
pipeline selects the pair, and the kernels mark safe trigger
and wait points that an ordinary graph dependency does
not expose (NVIDIA, 2026b). PDL permits overlapping
execution but does not guarantee it; the successor still waits
before it reads the predecessor’s output. In the bottom two
rows of Figure 3, enabling PDL at the FFN and adjacent
O/QKV boundaries shortens the already fused 11-kernel
NVFP4 layer from 62.1 to 52.1 µs with the same kernels
and precision. CUDA supplies PDL; our design chooses
and validates the model-specific trigger and wait points.
Appendix A.4 gives three cases, including boundaries where
more overlap does not help.
3.4
Execution Interface and Reusable State
The execution contract exposes a completed pipeline
through a shared execution interface. Reuse is valid only
while the inputs that produced a retained value are un-


changed.
The interface records stage order, supported
shapes, and named buffers with owners, sizes, and update
methods. The engine checks stage references and selects a
captured replay for the requested shape. Appendix A.1 gives
the execution rules, interface fields, and a worked π0.5 plan.
Static buffers hold prepared values; swap windows hold re-
placeable inputs and outputs at fixed addresses; state regions
retain mutable state between stages or decisions. The engine
allocates these buffers once and captures selected stages as
CUDA Graphs keyed by shape.
The interface records stage order, input-update methods,
and the buffer regions needed for continuation. In π0.5,
instruction embeddings can be reused while the instruction
is unchanged, whereas a new observation requires rebuilding
image-conditioned K/V. If another session overwrites the
working buffers, restoring the saved regions lets the original
session continue without rebuilding its completed context.
Within a decision. Figure 4 (a) shows the split π0.5 plan.
The host fills image and noise buffers; context encodes the
image and prompt into K/V; action reads that K/V through-
out its denoising steps and transforms the noise buffer into
the action chunk. Shared named buffers let successive cap-
tured stages consume results directly. The session manager
orders stage replays according to the contract; captured
stages use fixed addresses without replay-time allocation or
host-dependent choices. The full-call plan and the split plan
return identical actions for identical inputs and noise.
Across decisions. Figure 4 (b) carries prepared values into
the next call. The normal π0.5 inference path uploads the
supplied images and reruns vision and context on every
call; it reuses unchanged instruction embeddings and fixed
step-conditioning tables. Even the encoder’s text-token K/V
depends on the image and is rebuilt. Prompt and robot-state
updates enter through the model’s supported input methods.
A host driving context and action separately must refresh
context for the current inputs before generating the next
action.
At a stage boundary, snapshot copies declared restorable
regions into an execution-state capsule; restore copies
them back, and fork copies them into another session.
The export lists region names, offsets, and lengths; loading
checks the schema and plan fingerprint, and resumption
must respect the model’s chunk boundaries. For π0.5, the
capsule holds the context K/V, the prompt embedding, and
the decoder position table (14 MB). For LingBot-VA, it also
holds the history K/V, the VAE cache, and the random-
number state (1.4 GB). After another session overwrites the
working buffers, restoring the capsule reproduces the next
actions bit for bit, without recapture and without rebuild-
ing the history (§4.4). Capsules remain process-local and
plan-specific because captured graphs contain device ad-
dresses; they support compatible sessions within a process.

DEPLOYMENT
FLASHRT-PAI offers native C++, a Python frontend, and
selective PyTorch-host replacement. All use its kernels;
captured-stage exports share the execution contract (§3.4).
Pipeline ownership determines the optimization scope.
Native engine and frontend. The native engine owns the
pipeline, fixed buffers, and captured graphs. The host fills
swap windows and reports changed inputs; the session man-
ager schedules replay and capsule copies. C++ avoids per-
kernel host dispatch. The Python frontend uses the same ker-
nels and stages for integration and evaluation, with Python
orchestration, input preparation, and output conversion.

Existing PyTorch hosts. Each replaceable region has a
specification and PyTorch reference. Qualification checks
inputs, outputs, state, shapes, and loop count; tensor-
dependent host branches prevent capture. After host-side
calibration, activation requires reference agreement and
lower whole-call latency, otherwise retaining the original
path. Kernels ship through the Kernel Hub. Graph-safe
stages can use capture(fn, windows) and export replay
and capsule interfaces. The host retains its control loop; lo-
cal edits may remove synchronization or enable capture.
Host module boundaries limit fusion, and preprocessing,
postprocessing, and tensor creation remain outside capture.
Integration work. Engineers specify stage boundaries,
buffer lifetimes, precision/layout interfaces, and kernel vari-
ants, then validate the complete policy. Loading, calibration,
and graph capture execute the specified setup; they do not
automatically discover this design. Shared kernels and con-
tract interfaces reduce repeated implementation, but a new
model–hardware pipeline still requires model-specific de-
sign and validation.
Takeaway: Integration can erase kernel speedups.
Extra conversion and synchronization can offset a faster kernel.
Evaluate replacements within the complete application path,
preserving output agreement and the existing control loop.

RELATED WORK
Graph compilers. TVM, TensorRT, and torch.compile
provide fusion, layouts, autotuning, and CUDA Graph re-
play (Chen et al., 2018; NVIDIA, 2026g; Ansel et al., 2024;
NVIDIA, 2024). FLASHRT-PAI supplies model–hardware
precision/layout interfaces and explicit cross-decision state
rules, then records the resulting pipeline in a contract. It
complements compiler optimization with the input life-
times and state-update rules of a deployed policy; compiler-
generated regions can use the same interface.
Serving systems and reuse. PagedAttention, SGLang,
Prompt Cache, and Hydragen share or reuse text-prefix
attention state (Kwon et al., 2023; Zheng et al., 2024;
Gim et al., 2024; Juravsky et al., 2024). Marconi man-
ages hybrid KV/recurrent prefix reuse; HCache acceler-
ates contextual KV restoration (Pan et al., 2025; Gao et al.,
2025). FLASHRT-PAI applies reuse to instruction, step-
conditioning, K/V, VAE, and RNG regions with different
update rates in a robot loop, under explicit ownership and
valid resumption boundaries.
Kernels and LLM runtimes. CUTLASS and FlashAt-
tention supply GEMM and attention kernels (NVIDIA,
2026c; Dao, 2024); FlashInfer adds customizable, graph-
compatible attention (Ye et al., 2025), Marlin optimizes
FP16×INT4 GEMM (Frantar et al., 2024), and TensorRT-
LLM integrates optimized kernels and LLM request schedul-
ing (NVIDIA, 2026h). FLASHRT-PAI adds policy-stage
update rules and compatible resumption boundaries for in-
struction, observation, step, and history state; these libraries
can implement its stages.
VLA inference systems. Ma et al. (2025b) reduce inference
overheads for 30 Hz π0-class execution. BLURR combines
prefix caching, mixed precision, and single-step rollout (Ma
et al., 2025a). EagleVLA combines a llama.cpp engine with
foresight-aligned asynchronous inference on Orin (Yang
et al., 2026); its engine is a FLASHRT-PAI provider (PKU
SEC Lab, 2026). Reflex adds batched visual encoding and
graph replay (Chen et al., 2026); FlashDrive co-designs
a driving VLA’s algorithm and system (Li et al., 2026b).
Some change model computation; FLASHRT-PAI preserves
architecture and denoising schedule across VLA, VA, and
WAM pipelines. Public integrations with EagleVLA-Edge
and acknowledgments from APXInf are listed as adoption
evidence in Table 8.


Vendor deployments. NVIDIA supplies π0.5 and GR00T
TensorRT paths (NVIDIA, 2026f;d), and reports Cosmos3-
Edge-Policy at 15 Hz on Thor with 32 actions per infer-
ence (NVIDIA, 2026a). DreamZero combines two-GPU par-
allelism, compilation, kernels, quantization, and caching (Ye
et al., 2026). These deployments and FLASHRT-PAI all
require model-specific integration; FLASHRT-PAI shares
contract and kernel interfaces.
Model-side acceleration and scheduling. Token prun-
ing (Yang et al., 2025), approximate feature caching (Xu
et al., 2025; Liu et al., 2024), and fewer-step distilla-
tion (Prasad et al., 2024; Akbari et al., 2026) reduce policy
computation, whereas FLASHRT-PAI’s state reuse avoids
recomputing values whose inputs are unchanged. Real-time
chunking (Black et al., 2025) overlaps inference with action
execution and is complementary to reducing the inference
latency itself.

LIMITATIONS AND CONCLUSION
Limitations. FLASHRT-PAI targets small-batch, fixed-
shape inference; new shapes need recapture, and new native
integrations require model–hardware pipeline co-design,
tuning, calibration, and validation (Appendix A). The cur-
rent evaluation focuses on warmed-up inference on two
Blackwell GPUs, with four policies on Thor, six on RTX
5090, and task success for π0.5 and LingBot-VA in LIBERO
simulation. Physical-robot behavior and complete sensor-
to-actuator deadlines are outside this evaluation. Broader
hardware and task coverage, sustained control-loop charac-
terization, and multi-session resource accounting are direc-
tions for further evaluation. Capsules resume compatible
sessions within one process (§3.4).
Conclusion. Fast kernels are necessary but not sufficient.
FLASHRT-PAI co-designs their interfaces, launch depen-
dencies, and state lifetimes, recording the result in an ex-
ecution contract. Across four policies on Thor and six on
RTX 5090, evaluated paths are 3.38–12.66× faster than offi-
cial eager paths and 1.3–3.7× faster than compiled paths at
matched 16-bit precision. FLASHRT-PAI has delivered tan-
gible impact across industry and the open-source research
community (§6): it is open source, its kernels are distributed
through the Hugging Face Kernel Hub, and its opt-in kernels
have been adopted in LeRobot.
Looking ahead, we envision FLASHRT-PAI as a standard
inference engine for physical AI, with pipeline co-design
providing a reusable foundation for production deployment.

WORKED EXAMPLES
The worked examples below show the contract and veri-
fied measurement details, then the deployment facts behind
fusion, launch overlap, and state reuse.
A.1
Worked Execution Contract
The contract is exported through a versioned C interface.
It lists captured graphs and their supported shapes, named
buffers, restorable byte regions, and an identity fingerprint
used to match saved state to its execution plan. The model
interface adds inputs with shapes and update methods, plus
stages with explicit prerequisites.
Execution rules. A retained value can be reused only while
its source inputs are unchanged. Stages consume prereq-
uisite outputs valid for the current inputs. Restored state
belongs to a compatible plan and resumes at the declared
boundary; a new observation still requires a new context
stage. These rules specify correct use of the interface. List-
ing 1 shows two of its records; names and field types follow
the implementation.
typedef struct frt_runtime_region_desc {
const char* name;
frt_buffer buffer;
uint64_t offset, bytes;
uint32_t flags, reserved;
} frt_runtime_region_desc;
typedef struct frt_runtime_stage_desc {
uint32_t graph;
uint32_t n_after;
const uint32_t* after;
} frt_runtime_stage_desc;
Listing 1. Contract records for saved regions and stage order. A
region names the buffer bytes to copy; a stage names its
graph and prerequisite stages.
Engine checks and input updates. Construction rejects
stage references to missing graphs or prerequisites that have
not been declared. An input that requires processing must
provide its update function. Replay requires a captured
variant for the requested shape, and restore checks state-
layout and plan compatibility. For example, the GR00T
N1.7 Thor frontend rejects a second prompt initialization
and requires a new frontend instance for a new prompt.
Caller responsibilities. The normal model call performs
its declared input processing and stage sequence. A host
driving individual stages must submit current inputs and
refresh dependent state before action replay. If it omits
an update or reuses context from an older observation, the
result can be an action based on outdated inputs. Shape and
plan checks do not detect such unreported changes. The
interface checks execution compatibility; the host retains
responsibility for input freshness and the robot’s control
loop.
Worked plan. In the split π0.5 plan below, the engine owns
the fixed allocations and replay handles; the application sup-
plies input updates, and the session manager orders stages
and capsule copies.

Preparation writes instruction embeddings and fixed-step
conditioning. Context reads images and the prepared prompt
and writes K/V. Action depends on context, reads that K/V
and the noise window, and produces the action chunk. A
fresh observation therefore invalidates context, even when
the instruction is unchanged. Each replay plan is selected by
its supported shape; changing a shape requires preparation
and capture before replay.
At the post-context boundary, the measured capsule contains
context K/V, instruction embeddings, and the decoder posi-
tion table, totaling 14.40 MB. The exported region list gives
names, offsets, and lengths; schema and plan fingerprint
checks restrict restore to a compatible session. Weights and
fixed step tables remain resident and are not copied in this
experiment. Restoring this state permits continuation from
the completed context; a new image refreshes the context
stage. The application supplies the input-change events that
determine when retained values are refreshed.

A.3
Deep Kernel Fusion Examples
Calibrated producer–consumer quantization.
An FP8
GEMM needs an FP8 input and a scale. In a dynamic path,
separate kernels may first find the activation maximum and
then convert the activation before the GEMM. For the π0.5
encoder FFN, FLASHRT-PAI measures an acceptable scale
on representative task inputs before capture. The preceding
normalization kernel then emits FP8 directly at that scale,
and its single FFN consumer reads those same bytes. The
producer and consumer must be selected as a pair: an FP8
output handed to a BF16 entry is an error, not a useful
fallback. Attention-output conversion is one boundary that
still uses a separate kernel.
The ten-row action shape.
The π0.5 action expert always
presents ten rows, but the stock NVFP4 GEMM tile reserves
space for 128 activation rows. Its out-of-bounds rows still
cost memory-system work. For selected decoder projec-
tions, FLASHRT-PAI swaps the GEMM operands: the large
tile carries weights, the ten activation rows use the short
dimension, and a column-major store has exactly the bytes
the next kernel expects as row-major output. No transpose
kernel is needed. The fixed row count is guarded in the
implementation. The fixed deployment shape makes this
tile choice valid throughout replay.
Phase fusion across layers.
After an FFN down-
projection, the policy must update a residual, normal-
ize for the next layer, and convert its input for the next
GEMM. If those steps run as separate kernels, each bound-
ary adds a launch and moves an intermediate through mem-
ory. FLASHRT-PAI’s practical phase kernel combines the
gated residual, next-layer adaptive normalization, and FP8
conversion. The known layer and denoising-step order tells
it which next-layer style and scale to read. Figure 3 counts
20 kernels and 193.2 µs per layer on the compiler path ver-
sus 12 kernels and 105.2 µs on the composed FLASHRT-
PAI path, measuring the combined pipeline changes at layer
granularity.
QKV split, RoPE, and cache write.
After the π0.5 QKV
projection, a conventional sequence can split the combined
output, rotate query and key positions, and write the key/-
value cache in separate passes. FLASHRT-PAI uses one
kernel to do all three while those values are already being
visited. The pipeline fixes the head geometry and the K/V
cache layout; a device-side valid-prefix position tells the
kernel where to append K/V even when prompts are padded
to a common capture shape. The cache layout and position
rule make the combined write valid throughout replay.
NVFP4 output directly from a GEMM.
In the π0.5 en-
coder feed-forward block, a GEMM produces two vectors,
gate and up. The earlier path launched a separate kernel to
compute GELU(gate)×up, quantize the result, and pack it
for the next GEMM. FLASHRT-PAI instead pairs gate and
up weights when loading the checkpoint. That puts each
pair of results next to each other inside the GEMM, allowing
its epilogue to compute the product and write packed four-
bit values and block scales directly in the next GEMM’s
required layout. An initial fused version wrote a full-width
result and doubled the next GEMM’s weight traffic, so
its feed-forward chain was slower than the separate-kernel
path. A compact, half-width store kept the next GEMM’s
original shape; decision latency then fell, and the worst
measured output cosine improved because the intermedi-
ate was quantized once rather than twice. The layout and
producer–consumer format were designed and validated for
this pipeline, not inferred from an ordinary operator graph.
A.4
Launch-Overlap Examples
Fetching weights before the activation is ready.
A
GEMM cannot read an activation produced by the previous
kernel until that kernel finishes, but its fixed weights are
already available. FLASHRT-PAI’s decoder GEMM starts
streaming a few weight tiles before the wait, then loads
the activation only after the dependency is satisfied. This
shortened the decoder GEMM chain with identical outputs,
but the gain was not monotonic: fetching all seven weight
tiles early congested the memory queue, while two or three
tiles worked best. Moving the release signal from the load
warp to the multiply warp also gave up much of the benefit.
The selected variant streams only the profitable prefix.
Choosing between persistent and separate GEMMs.
FLASHRT-PAI also built a resident grid that runs several de-


coder GEMMs in one launch. Its load warp fetches the next
GEMM’s weights while the current one finishes. With inde-
pendent GEMMs, the chain ran faster than separate launches
and came close to the measured memory-read ceiling. The
version that also performs the required normalization be-
tween GEMMs, however, was slower than separate launches.
The next GEMM must wait for the normalization result, and
a grid-wide rendezvous adds cost that weight prefetch can-
not hide. The implementation passed bit-exact checks but is
disabled in the shipped path. A faster isolated chain was not
a faster pipeline here; the useful rule is to fuse the memory-
bound work between GEMMs, not every GEMM into one
kernel.
Knowing when overlap has reached its limit.
More early
work is not always better. In Thor tuning, extending early
launch to RoPE, softmax, and FP8-conversion kernels pro-
duced no further measurable change. Prefetching the next
layer’s weights into cache also slowed every tested variant
of the decoder chain, because the prefetch competed with
demand traffic. Together with the rejected persistent se-
quence above, these cases bound the technique: it can hide
launch setup or input-independent memory traffic, but not
work whose result the successor actually needs. FLASHRT-
PAI therefore tests overlap in the full pipeline as well as in
isolated chains.
A.5
Execution-State Reuse Example
Instruction state.
The π0.5 action expert has ten denois-
ing steps and eighteen layers; its adaptive-normalization
values form a finite step-by-layer table for a given instruc-
tion.
Rebuilding those values inside every decision re-
peats work whose input has not changed. FLASHRT-PAI’s
set prompt builds the table and prompt embedding once,
keeps them in named buffers, and lets later kernels select
the needed row. A same-size prompt update overwrites
the existing embedding rather than replacing its address;
a device-side valid length masks padding without recap-
ture. In an earlier compiler implementation, in-graph Dense
GEMMs rebuilt these styles at every inference, and hand-
editing that graph to precompute them reduced its latency.
FLASHRT-PAI uses the same temporal-hoisting idea in its
prompt setup. The instruction lifetime and refresh rule spec-
ify when this prepared state can be reused and when it must
be rebuilt.
