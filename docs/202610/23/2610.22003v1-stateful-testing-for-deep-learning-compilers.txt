Modern deep learning compilers compile models lazily and cache compiled artifacts for reuse across invocations.
Compiler state is information retained by compilers across invocations that can affect later invocations.
Examples include cached code and the guards for reusing it. Compiler state from earlier invocations can
cause an incorrect result in a later invocation. To understand these stateful compiler bugs, we analyze 26
publicly reported issues in PyTorch, JAX, and TensorFlow that describe such bugs. The analysis shows that
detecting these bugs requires two steps, establishing the relevant compiler state through earlier invocations,
and making a later invocation that exposes the bug. To meet this requirement, we represent each test case as
⟨model, invocation sequence⟩. A fixed initial state and invocation sequence determine the resulting compiler
state. Based on this representation, we develop Rondo, a stateful testing method for deep learning compilers.
Rondo generates test cases by mutating invocation sequences. For each test case, it runs the invocation
sequence on the model and records compilation behavior. A Markov chain Monte Carlo (MCMC) sampler uses
this behavior as feedback to guide generation, favoring rarely observed compilation behaviors. Rondo identifies
possible bugs through three-way differential testing, comparing results without compilation, compiled results
without compiler state from earlier invocations, and compiled results with that state. A stateful bug is confirmed
when the same invocation produces an incorrect result with compiler state retained and a correct result after
that state is reset. Lastly, Rondo attempts to shorten the invocation sequence while preserving the original
bug to obtain a smaller script that reproduces it. We evaluate Rondo on four representative deep learning
frameworks using 24 common model architectures. We detect 117 bugs, including 35 stateful bugs, and submit
39 bug reports, including 18 for stateful bugs. Developers confirm 35 reports, including 16 for stateful bugs, and
fix 18 bugs, including 11 stateful bugs. Rondo achieves the highest behavior coverage and compiler Python
source-line coverage in the baseline comparison. Its bug checks achieve 99.26% alarm precision. It shortens 44
of 117 invocation sequences while preserving the original bugs, reducing the lengths of these 44 sequences by
83.34% on average.

These caching mechanisms improve efficiency and make the compilers stateful. Compiler state is
information retained by compilers across invocations that can affect later invocations. Compiler
state established by prior invocations can cause an incorrect result in a later invocation, even when
the same invocation is correct in isolation. We call these bugs stateful compiler bugs.
Existing deep learning compiler testing methods aim to detect framework bugs by generating
diverse models and model inputs [27, 37]. Most of these methods test individual model invocations.
We write such a test case as a pair ⟨model, invocation⟩, where the model describes the computation
under test and the invocation specifies the model inputs. This representation captures the current
invocation but does not explicitly capture the compiler state established by prior invocations. To
understand stateful compiler bugs, we analyze 26 publicly reported bug issues in PyTorch, JAX, and
TensorFlow. The analysis shows that these bugs can produce incorrect outputs and affect training.
Detecting these bugs requires generating invocation sequences that establish compiler state and
expose bugs in later invocations. This requirement gives rise to three challenges.
Challenge 1. Bug triggers across invocations. For a stateful bug, the invocation that creates
the relevant compiler state and the invocation that exposes the bug are different. Representing a
test case as ⟨model, invocation⟩does not explicitly capture these invocations and their order. For
example, invocation 𝐴may establish compiler state that causes a later invocation 𝐵to produce an
incorrect result. Testing 𝐴and 𝐵separately would miss this bug. Detecting it therefore requires
explicitly searching invocation sequences such as ⟨𝐴, 𝐵⟩[5, 22].
Challenge 2. A large test space. A test case for stateful bugs consists of a model and an
invocation sequence. For a fixed model, 𝑘possible choices at each position give 𝑘𝑛invocation
sequences of length 𝑛. This makes exhaustive search infeasible as sequences become longer. Finding
sequences that trigger rarely observed compiler behaviors is also difficult because compiler state is
not directly observable. For example, invocation 𝐵may trigger a new compiler behavior after 𝐴,
but does not trigger one after 𝐴′. It is therefore difficult to choose which sequences to extend or
change, and random search may repeatedly trigger common behaviors.
Challenge 3. Oracle Unavailable. After running a test case, ground truth is often unavailable
for determining whether its results are correct [52]. Traditional differential oracles compare results
from different modes, but an inconsistency alone does not establish whether it is caused by a
compiler bug or whether the bug depends on compiler state. For example, an invocation may
produce different results with and without compilation. This comparison does not tell us which
result is incorrect. It also does not show whether compiler state from earlier invocations caused
the inconsistency.
To address these challenges, we formulate the testing problem and define compiler state. The
complete compiler state is not directly observable, so we use invocation sequences to represent
compiler state. We represent each test case as ⟨model, invocation sequence⟩. A fixed initial state
and a fixed invocation sequence determine the resulting compiler state. We can explore different
compiler states by generating invocation sequences and reach the same state again by replaying
the same sequence (addressing Challenge 1). Based on this representation, we develop Rondo, a
stateful testing method for deep learning compilers. Rondo first generates test cases by mutating
invocation sequences or using an SMT solver. It runs the invocation sequences and uses feedback
to guide subsequent test case generation toward rarely observed compiler behaviors (addressing
Challenge 2). It then compares results from invocations without compiling the model, compiled
invocations without compiler state from earlier invocations, and compiled invocations with that
state. To check whether a bug depends on compilation or compiler state, Rondo compares the same
invocation with its inputs and program state fixed. A stateful bug is detected when the result is

• A new perspective on compiler testing. We study stateful compiler bugs and define
compiler state to describe their dependence on earlier invocations. We represent each

We analyze public bug issues to understand stateful compiler bugs and identify the testing require-

Bug Case 2: Changed gradient requirement. PyTorch issue #162174 concerns a change in
whether a model’s parameters require gradients. Training uses gradients to determine how to adjust
these numerical parameters [16, 18]. The first invocation does not require parameter gradients.
The compiler retains the compiled code from this invocation. Before the next invocation, gradient

parameter gradients (None).
Bug Case 3: Changed input alias relations. PyTorch issue #139789 concerns a change in
whether two inputs share storage. The program doubles the values stored in input x and then
returns x + y. The first invocation uses independent inputs, each containing four ones. Doubling
x leaves y unchanged, so the invocation correctly returns [3, 3, 3, 3]. The compiler retains the
compiled code from this invocation. The next invocation uses inputs with the same initial values
but with part of their storage shared. Doubling x also changes the overlapping elements of y. It
should return [4, 4, 3, 3], but instead returns [3, 3, 3, 3].
In 17 of the 26 bug cases, the compiler reuses compiled code even though the conditions required
by that code no longer hold. In 9 cases, the compiled code can still be used, but later invocations
use earlier values or structures that do not match the current program state. In both situations, a
later invocation incorrectly uses information retained by the compiler from earlier invocations.
Triggering these bugs requires invocation sequences that first establish compiler state and then
change relevant program state before an invocation that exposes the bug. The changes should cover
parameter values and gradient requirements, object attributes and bindings, input properties and
alias relations, function operations, modes, argument ordering, and counters or random-generator
state. These changes can leave object identity, function code, or input values unchanged.
Observation 1. Stateful compiler bugs require invocation sequences that first establish compiler
state and then expose an incorrect result in a later invocation.

2.3
Impact of Stateful Bugs
To detect stateful compiler bugs, we need to understand their observable effects. We analyze these
effects on outputs, gradients, and observable program state to determine what testing must check.
Outputs. Outputs are the results returned by a model or program. Incorrect outputs can lead
to incorrect predictions or task results. Model weights are numerical parameters that determine
a model’s computation. PyTorch issue #104984 reports that a compiled model continues to use
earlier weights after new weights are loaded. PyTorch issue #178365 reports incorrect outputs after
a function’s default argument changes. Resetting compiler state restores the correct outputs in
the latter case. The consequences can extend to the result of a complete task. JAX issue #31733
shows that the same task returns the correct solution 1 with an empty persistent compilation cache,
but returns the initial value 10 with an existing cache. Other cases incorrectly report whether two
references point to the same object or return an incorrect numeric data type, which can change
later program decisions or computations.
Gradients. Training uses gradients to determine how to adjust a model’s numerical parameters.
In PyTorch issue #162174 (Bug Case 2), the outputs are correct, but the parameter gradients are
missing (None). These missing gradients can prevent the affected parameters from being updated
as required, so correct outputs alone do not guarantee correct training.
Observable program state. Observable program state includes information a program keeps
between invocations and that we can inspect, such as the state of a random-number generator. A
random-number generator updates this state as it produces random results. PyTorch issue #197085
reports that repeated invocations of shuffle and sample return the permutation or sample from
the first invocation. There is also an inconsistency between the random-generator state and that
of the reference run. These errors can affect both the current output and the random results of
subsequent invocations.
Testing requirements. The checks must cover outputs, gradients, and observable program
state. For random operations, the compared runs must start from the same random-generator state
and check both the result and the subsequent state.
Observation 2. Detecting stateful compiler bugs requires checking outputs, gradients, and
observable program state. These bugs can affect any of these results without raising an exception.
2.4
Characterizing Compiler State
To guide how testing represents state, we examine how stateful compiler bugs differ from bugs
exposed by an individual invocation. The studied cases show that the invocation establishing the
relevant compiler state and the invocation exposing the bug are different.
A bug exposed by one invocation can be examined using that invocation’s model, inputs, and
current program state. A stateful compiler bug also depends on compiler state established by earlier
invocations. In Bug Case 2, the first invocation does not require parameter gradients and produces
the correct result. The compiler retains the compiled code from this invocation. Before the next
invocation, gradient computation is enabled for the same parameters. The current program state
now requires parameter gradients, but the later invocation uses the earlier compiled code and
produces no parameter gradients (None). Resetting compiler state restores the expected gradients
while keeping the parameter values, gradient requirements, and inputs unchanged. This case
shows that the invocation establishing compiler state can complete correctly, even though a later
invocation fails after a change to program state. Program state determines the required result,
while retained compiler state can prevent that result from being produced. Describing the current

Related Work
DL compiler testing constructs models, tensor programs, or intermediate representations (IRs),
compiles and runs them, and applies an oracle to identify crashes, incorrect results, or inconsisten-
cies [27, 29, 32]. Tests differ in the level at which they enter the compiler. Model- and program-level
tests exercise supported frontends and subsequent transformations, while IR-level tests directly exer-
cise compiler optimizations and lowering. Methods can be grouped by how they construct test cases:
generation-based methods synthesize new models or programs using operator constraints [36],
language rules, compiler information, or recorded operator usages, while mutation-based methods
modify or combine existing test cases.
Generation-based methods. Generation-based methods construct new models or programs
while satisfying the constraints required for compilation [55]. NNSmith incrementally builds valid
computation graphs using operator specifications and tensor-type propagation, and uses gradient-
guided search to find inputs that avoid exceptional floating-point values [27]. NeuRI reduces the
manual specification effort by inferring operator constraints from valid and invalid API traces
and combining symbolic and concrete operators during model generation [28]. OPERA wraps
operator instances extracted from DL library tests as single-operator models to test compiler
frontends [40]. At the IR level, GenCoG uses a domain-specific language to specify and solve
operator type constraints for generating diverse Relay graphs [49]. HirGen generates high-level IRs
using coverage criteria and IR language features [32], while MLIRSmith constructs MLIR program
templates and instantiates them through a context-sensitive grammar [47]. WhiteFox uses large
language models (LLMs) to analyze optimization source code, extract requirements for triggering
the optimization, and generate programs that satisfy those requirements. It uses tests that trigger
optimizations as feedback to guide subsequent generation [53].
Mutation-based methods. Mutation-based methods construct new tests by modifying or
combining existing models, programs, or IRs [8, 35, 50, 56]. MT-DLComp creates model variants
whose results should agree for selected inputs and applies metamorphic testing [51]. TorchProbe
uses semantics-preserving code transformations to introduce dynamic Python features into test
programs [42]. Tzer jointly mutates low-level IRs and sequences of optimization passes under
coverage feedback [29]. SynthFuzz infers parameterized, context-dependent mutations from existing
MLIR tests and adapts them to new contexts [23]. AlignGuard extracts bug-triggering patterns
from public reports and fixes, uses LLMs to synthesize mutation rules, and applies them to existing
PyTorch compiler tests. Its patterns include repeated invocations with changes to model state or
input properties [20]. OATest extracts optimization patterns from developer tests and combines
them with seed computation graphs, repairing graph connections to satisfy operator constraints [41].
These methods reuse information in existing tests to diversify program structures, the conditions
under which programs run, or compiler transformations.
Test oracle. Differential testing compares compiled results with reference results [19, 34] or
with results from different compiler configurations [27, 29, 53]. Metamorphic testing compares
programs with a declared relation between their results [33, 51, 52]. DESIL applies rules to eliminate

undefined behavior in MLIR tests and selects lowering paths that allow the tests to run for differential
comparison [45].
Comparison with prior work. Rondo detects stateful compiler bugs by using invocation
sequences to represent and explore compiler state. First, compared with methods that gener-
ate or transform models, programs, or IRs, it searches invocation sequences that establish com-
piler state for later invocations. It mutates these sequences and declared state operations, using
compilation-behavior feedback to guide generation toward rarely observed behaviors. Second,
repeated-invocation tests can expose failures after changes to model state or inputs, but confirming
a stateful compiler bug requires separating program state from compiler state. Rondo compares the
same invocation with compiler state retained and reset, keeping its inputs and relevant program
state unchanged. Third, it checks outputs, gradients, and observable program state through struc-
tured comparison and independent semantic checks. It then shortens the sequence while preserving
the original bug and, for a stateful bug, its dependence on retained compiler state. Section 4 presents
the design.
4
Methodology
This section presents the problem formulation and the testing method of Rondo. We first specify
the test representation and the bugs we aim to find, then describe how Rondo generates test cases,
checks their results, and confirms and minimizes stateful witnesses.
4.1
Problem Formulation
Given a model 𝑀and a fixed scenario, our goal is to find a test case that exposes a stateful
compiler bug. The scenario fixes the framework build, backend, device, compiler options, and initial
conditions.
Definition 4.1 (Compiler state). Compiler state 𝜅is information retained by compilers across
invocations that can affect later invocations, excluding program state. Examples include cached
compiled artifacts, guards, specializations, and profiling data. Program state 𝑠contains parameters,
buffers, mutable inputs [7], alias relations [9, 46], modes, and other declared state. A configuration
is (𝑠,𝜅).
The behavior required by program state must not depend on compiler state [25, 26, 31, 38]. The
complete internal contents of compiler state depend on the compiler and are not directly observable.
Following the testing requirement in Section 2.4, we represent compiler state by the invocation
sequence that establishes it from the scenario’s fixed initial state. We represent each test case as

4.2
Method Overview
Figure 2 shows the three modules of Rondo, and Algorithm 1 summarizes the testing loop. Test-
space Exploration first generates legal test cases through mutation or, when compilation constraints
are available, SMT-based synthesis. It runs the generated test cases and uses compilation-behavior
feedback to guide an adaptive Markov chain Monte Carlo (MCMC) search. The Test Oracle then runs
selected test cases under three modes: Without compilation, Compiled without state, and Compiled
with state. Here, state in the mode names refers to compiler state from earlier invocations; all
three modes carry their own program state forward. It compares their outputs, gradients, and
observable program state using representation-aware numeric rules and applies independent
semantic checks to identify candidate bugs. Finally, Stateful Candidate Refinement repeats the
invocation that produced the incorrect result with compiler state retained and reset, while keeping
its inputs and relevant program state unchanged. It determines the witness class and minimizes
the sequence while preserving the class, the invocation that exposed the bug, and the recorded
symptoms. Compilation behavior guides test case generation, and this comparison determines
whether the bug is stateful.

4.3
Test-space Exploration
Rondo explores compiler states by generating invocation sequences. It uses compilation-behavior
feedback to guide test case generation. In each iteration, Rondo uses mutation or SMT-based
synthesis to generate a new test case from the current sequence and runs it to collect feedback.
An adaptive MCMC sampler uses this feedback to decide whether the new test case becomes the
current test case for the next iteration. We first describe test case generation, then explain the
compilation feedback and sampling procedure.
4.3.1
Generating Test Cases. Each scenario specifies the initial state. Rondo starts from an empty
sequence or a saved prefix. In each iteration, it generates a new test case through feedback-guided
mutation or SMT-based synthesis. Mutation applies an operator that appends an invocation, replaces
an existing invocation, or removes invocations from the end of the sequence. Each generated test
case must satisfy the scenario’s preconditions before it is run.
Feedback-guided mutation. Feedback-guided mutation aims to explore compiler states that
arise when inputs or program state change across invocations. The bug analysis in Section 2.2
motivates varying input properties and values, changing model state or gradient requirements, and
testing later invocations with earlier compiler state retained. We select 7 operators for varying
invocation inputs, 4 for state changes or gradient computation, and 2 for revisiting invocations or
exploring alternative continuations. Rondo uses these 13 mutation operators to generate new test
cases from the current invocation sequence, as summarized with examples in Table 2. The shape,
dtype, layout, and device operators change the dimensions, numeric type, storage arrangement,
or device of a tensor, a multidimensional array. The resample and rescale operators change input
values or their magnitudes, while special values introduces NaN, infinity, very small subnormal
values, and positive or negative zero [13]. These mutations also cover dimensions of size 0 and
1, values near numeric boundaries, and values that affect program control flow [14]. The update

SMT-based synthesis. Mutation may struggle to generate invocations whose inputs satisfy
specific compiler conditions. SMT-based synthesis targets these conditions directly. Rondo also
generates test cases through SMT-based synthesis when it can obtain a guard or an input constraint
from the framework. A guard is a condition that checks whether a compiled artifact can be used for
the current invocation. Rondo selects an outcome of the condition that has not yet been explored
and asks the solver to generate a finite set of candidate inputs that produce this outcome and satisfy
the program’s input requirements [4, 30]. For example, a condition may require a tensor dimension
to equal 1 or be greater than 1. Rondo selects a candidate from this set and records its selection
probability. It constructs an invocation with the selected inputs, then appends it to the sequence or
replaces an existing invocation to generate a new test case. It checks the invocation for legality
before running the test case. If the solver cannot handle the constraints or finds no solution, Rondo
uses mutation to generate the test case.

Experiment Design
5.1
Research Questions
We evaluate Rondo through five research questions.
• RQ1: Bug Detection. How effective is Rondo at detecting bugs in deep learning frame-
works, and what types of bugs does it detect?
• RQ2: Diversity and Coverage. How does Rondo compare with the baselines in test
diversity and compiler coverage?
• RQ3: Component Ablation. What effect does each exploration component have on test
diversity and compiler coverage?
• RQ4: Oracle Effectiveness. How do the oracle configurations compare in true-positive
detections and false alarms?
• RQ5: Sequence Refinement. How often does sequence refinement shorten an invocation
sequence while preserving the original bug, and what is its cost?
5.2
Baseline Methods
NNSmith, OATest, AlignGuard, and RandomHistory serve as baselines to compare different
testing strategies. We adapt their testing strategies for this evaluation. For ablation, we compare
full Rondo with four variants: w/o Feedback, which removes compilation-behavior feedback; w/o
SMT, which disables SMT-based synthesis; w/o Return, which disables the return operator; and w/o
State Operations, which disables state-changing actions.

5.4
Implementations
To fairly evaluate the performance of Rondo and baseline methods, we implement them using the
same framework versions, environment, and configurations. Rondo is implemented in Python and
tested on PyTorch 2.12.1, MindSpore 2.9.0, TensorFlow 2.21.0, and JAX 0.10.2. Specifically, Rondo
consists of three modules: Test-space Exploration, Test Oracle, and Stateful Candidate Refinement. The
Test Oracle uses Without compilation, Compiled without state, and Compiled with state modes and
includes structured observation comparison and independent semantic checks. The compilation
paths under test are torch.compile with Inductor, MindSpore graph mode, tf.function with and
without jit_compile, and jax.jit with XLA. Eager mode and MindSpore PyNative mode serve as
the corresponding paths without compilation. We select 24 common model architectures, including
multilayer perceptrons (MLPs), convolutional neural networks (CNNs), and Transformers, as test
programs. The experiments are conducted on an Intel Core i7-14700K machine with 32 GB of RAM,
Ubuntu 24.04.4 LTS, and one 24 GB NVIDIA GeForce RTX 4090 GPU. The Python version is 3.12.13,
and PyTorch is built with CUDA 13.0. For bug discovery, we run Rondo on the four frameworks
using these model architectures. For coverage comparison and component ablation, each method
or configuration uses three independent runs, and coverage is measured after 600 test cases. The

compared methods and ablation configurations use the same test programs, seeds, settings, metric
definitions, and reference protocol. For oracle evaluation, we compare five levels of checking on the
same 50,074 labeled test cases: crash-only checking, two-mode numerical comparison, three-mode

Threats to Validity
Internal Threats to Validity. Errors in test runs, oracle checks, or compiler-state reset can affect
bug detection and the classification of stateful bugs. To reduce these threats, we compare the results
of Without compilation, Compiled without state, and Compiled with state and use independent
semantic checks. We confirm stateful bugs by replaying the same invocation with compiler state
retained and reset while aligning its inputs and relevant program state, and record the achieved
compiler-state reset boundary. Minimization rechecks the original bug and its defining class relation
after each reduction. External Threats to Validity. The selected programs, frameworks, and
hardware may limit generalization. To reduce this threat, we evaluate four frameworks using 24
common model architectures, including MLPs, CNNs, and Transformers. Construct Threats to
Validity. Behavior metrics and oracle alarms may not fully reflect compiler coverage or the number
of underlying bugs. We use common metric definitions, total sets, test case budgets, and config-
urations for the compared methods, and report compiler Python source-line coverage alongside
behavior coverage. We also distinguish detected bugs from oracle true-positive test cases and report
the contributions of oracle checks separately.
8
Conclusion
Single-invocation tests for deep learning compilers do not represent the compiler state that can
affect later invocations. We propose Rondo, a novel stateful testing method that uses invocation
sequences to represent and explore hidden compiler state. Rondo guides test case generation with
compilation-behavior feedback and checks results under Without compilation, Compiled without
state, and Compiled with state. It confirms stateful bugs by comparing the same invocation with
compiler state retained and reset while preserving its inputs and relevant program state. It then
minimizes invocation sequences while preserving the original bug and its defining class relation.
Evaluation on four deep learning frameworks detected 117 bugs, including 35 stateful bugs. We
submitted 39 bug reports, including 18 for stateful bugs. Developers confirmed 35 reports, including
16 for stateful bugs, and fixed 18 bugs, including 11 stateful bugs.
