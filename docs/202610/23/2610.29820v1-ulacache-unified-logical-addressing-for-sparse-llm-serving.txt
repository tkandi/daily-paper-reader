ABSTRACT
Long contexts increase the memory cost of the key-value (KV) cache in large language model (LLM) inference.
Sparse attention reduces attention computation and memory traffic by selecting historical tokens, but the retained
KV cache must remain available for later decoding steps. We present UlaCache, a KV cache management
system built around a unified logical address space spanning GPU KV pools and optional CPU memory. Stable
logical references let the inference engine allocate and select KV independently of physical placement. Common
allocation and sparse-access interfaces support data-parallel (DP) and tensor-parallel (TP) attention. For distributed
storage, local GPU buffers retain selected KV across decoding steps, so only missing entries require transfers.
When CPU storage is enabled, Parallel Bucketed LRU (PB-LRU) manages a GPU pool shared across requests. It
updates recency metadata and selects eviction victims in parallel. UlaCache transfers KV and then updates the
address mappings. With speculative decoding enabled under matched CPU and GPU memory budgets, UlaCache
achieves peak decoding throughput speedups of 1.16× (DP) and 1.70× (TP) on 8×H200, and 1.73× (DP) and
2.51× (TP) on 8×B300, compared with the state-of-the-art baseline.

INTRODUCTION
Efficient serving of long-context large language models
(LLMs) requires enough memory to keep many requests
active. Batching amortizes model execution across requests
and raises decoding throughput, but every active request
needs a key-value (KV) cache to retain its history (Kwon
et al., 2023; Agrawal et al., 2024). The memory occupied
by model weights is independent of batch size, whereas KV
storage grows with the number and length of active contexts.
As context length and concurrency grow, this cache can
exhaust GPU memory and prevent larger decode batches.
Increasing the amount of useful history that fits in a fixed
memory budget is therefore central to throughput scaling.
Sparse attention reduces the KV data read by each decod-
ing step, selecting a subset of historical tokens or blocks
for attention (DeepSeek-AI et al., 2025). Models includ-
ing DeepSeek-V4.1-Flash (DeepSeek-AI et al., 2026), the
GLM-5 family (GLM-5-Team et al., 2026), Qwen3.8-Flash-

the retained history still grows with context length and the
number of active requests, limiting the number of requests
that can decode concurrently under a fixed memory budget.
CPU memory can extend KV storage, but its effect on de-
code concurrency depends on how it is used. In the prefix-
reuse paths of HiCache and LMCache, cached KV is loaded
into the inference engine’s GPU slots to avoid prefill compu-
tation (Xie, 2025; Liu et al., 2025). This improves serving
efficiency, while the active decode batch remains bounded
by the GPU KV allocation. HiSparse instead keeps complete
histories of active requests in CPU memory and fetches se-
lected KV into GPU caches (Xie et al., 2026). This supports
decoding beyond GPU memory capacity, but GPU slots
hold copies of CPU-resident KV and do not add capacity
for distinct history.
We present UlaCache, a KV cache management system built
around a unified logical address space for GPU and CPU
memory. The inference engine allocates and selects KV us-
ing stable logical references; UlaCache resolves physical
locations, transfers the required data, and updates mappings
as KV moves. Common allocation and sparse-access inter-
faces support data-parallel (DP) attention with rank-local
storage and tensor-parallel (TP) attention with history dis-
tributed across GPUs. Implementing this abstraction effi-
ciently poses two challenges.
Challenge 1: Unified KV addressing and storage orga-
nization. Aggregating GPU and CPU memory requires a
unified KV address space that keeps logical references sta-
ble as KV data moves between physical locations. The KV
required by attention may reside on the computing GPU, a
peer GPU, or in CPU memory. The organization of local and
remote storage determines how much KV history is repli-
cated and how much data must be transferred for attention.
The challenge is to organize local KV access and distributed
history storage under a common logical address space, re-
ducing storage redundancy and the overhead of accessing
and migrating KV across devices.
Challenge 2: Efficient LRU replacement and mapping
management. Historical tokens selected by sparse attention
exhibit strong temporal locality across consecutive decod-
ing steps. This temporal locality allows GPU caching to
reduce redundant KV transfers. Least Recently Used (LRU)
replacement determines which KV entries remain cached
when capacity is limited. Each sparse access requires hit
detection and recency updates; cache misses additionally
require slot assignment for incoming KV, victim selection
when capacity is full, and mapping updates after migration.
These operations recur across requests and layers at every
decoding step. Processing them serially adds management
overhead to the decoding critical path. The challenge is to
execute LRU replacement and the associated mapping up-
dates efficiently, reducing the management overhead of local
eviction and remote KV fetch planning.
We make three contributions:
• Unified KV addressing and storage organization. We
provide a unified logical address space for KV stored
in GPU and CPU memory, decoupling the references
used by the inference engine from physical data place-
ment. Common allocation and sparse-access interfaces
support rank-local storage in DP and distributed storage
across GPUs in TP. UlaCache resolves selected addresses,
performs the required KV transfers, and commits map-
ping updates while keeping logical references stable. The
storage organization also reduces GPU–CPU history du-
plication and, for Multi-head Latent Attention (MLA),
replication across TP ranks. In TP mode, computing
ranks cache previously fetched KV in local GPU buffers
and transfer only missing entries, reducing redundant
data movement. For layers sharing sparse selections, Ula-
Cache prefetches the selected KV for later layers while
the current layer executes.
• Parallel bucketed LRU and address mapping updates.
We design Parallel Bucketed LRU (PB-LRU) to make
replacement and mapping management efficient over
GPU capacity shared across requests. PB-LRU approxi-
mates LRU by grouping GPU slots into recency buckets
and processing address translation, hit detection, and
recency updates in parallel. For incoming KV, hierarchi-
cal bitmaps locate replacement candidates and assign
destination slots while protecting entries needed by the
current attention computation. Transfer plans record the
locations of incoming and outgoing KV; mappings are up-
dated after the data transfers complete so subsequent ac-
cesses resolve to ready data. For layers sharing sparse se-
lections, UlaCache reuses access plans to avoid repeated
address lookup, deduplication, and slot assignment, re-
ducing LRU and mapping management overhead.
• System implementation and evaluation. We implement
UlaCache in SGLang and evaluate DP and TP modes
with and without speculative decoding. With speculative
decoding enabled under matched CPU and GPU memory
budgets, UlaCache achieves peak decoding throughput
speedups of 1.16× (DP) and 1.70× (TP) on 8×H200,
and 1.73× (DP) and 2.51× (TP) on 8×B300, compared
with HiSparse.

BACKGROUND AND MOTIVATION
2.1
Background
2.1.1
Sparse Attention and KV History
LLM inference consists of prefill and decoding. Prefill com-
putes KV states for the input sequence. Each decoding step
adds new states and uses the history to generate subsequent
tokens. The cache avoids recomputing the earlier states, but
must remain available while the request is active. Longer
histories and larger batches therefore increase the storage
requirement even though model weights are shared across
requests (Kwon et al., 2023).
In index-based sparse attention, an indexer selects historical
token or block positions, and the attention operator reads the
corresponding KV data (DeepSeek-AI et al., 2025; GLM-
5-Team et al., 2026). For a history of L positions and a
selection of k positions, the main attention operation reads
only the selected k entries, while storage must keep the
remaining history available. The indexer maintains compact
selection state separately from the KV records consumed
by attention. Because selections change with the query, an
entry outside the current working set can be needed at a later
step (Xie et al., 2026).
2.1.2
Attention Parallelism and KV Placement
Attention parallelism determines which GPUs compute a
request and store its history. Under TP, ranks split atten-
tion heads; KV heads are partitioned where possible and
replicated when too few are available. Multi-head Latent At-
tention (MLA) compresses KV into a representation shared
across heads. Partitioning query-head computation there-
fore does not partition this shared representation: conven-
tional head-partitioned TP keeps a copy on each participat-
ing rank (DeepSeek-AI et al., 2024; Bhatia et al., 2025).
The GPUs perform different attention computation while
retaining the same token history.
Under DP, each rank processes separate requests and stores
their histories locally. This avoids storing the same history
on every rank, but makes the capacity available to a request
depend on its assigned rank. Free slots on another rank are
not directly usable by that request without an additional
placement and access mechanism. The DP and TP labels
here describe attention parallelism; other model components
can use separate partitioning strategies (Bhatia et al., 2025).
2.1.3
CPU Storage for KV Cache
CPU memory can retain KV for reuse across requests
or back the history of active requests. Hierarchical prefix
caches such as HiCache and LMCache keep KV in CPU
memory and external storage. A prefix hit restores cached
KV into the inference engine’s GPU allocation, avoiding
repeated prefill computation and improving request-serving
efficiency. Transfers can be pipelined with layer execution
to reduce exposed loading latency (Xie, 2025; Liu et al.,

Sparse KV offloading uses CPU memory during the lifetime

that repeated selections can hit locally, reducing these trans-
fers (Xie et al., 2026). The amount of history retained and
the amount resident on GPUs can consequently differ.
2.2
Motivation
2.2.1
KV Storage and Decode Concurrency
Each active request must retain its KV history throughout
decoding, so storage capacity limits how many requests can
decode concurrently. CPU memory provides additional KV
storage, but whether it supports larger decode batches de-
pends on how that history is used during execution. Prefix
reuse and storage for active request histories are two com-
mon uses of CPU memory, with different implications for
decode concurrency.
One approach uses CPU memory to cache reusable KV and
avoid repeated computation across requests. In the prefix-
reuse paths of HiCache and LMCache, a cache hit loads
existing KV into the inference engine’s GPU slots, avoid-
ing the corresponding prefill computation (Xie, 2025; Liu
et al., 2025). Increasing CPU capacity retains more reusable
contexts, but these contexts still occupy GPU history slots
during execution. Adding CPU prefix storage therefore does
not reduce the GPU storage required for the active histories.
Once GPU KV slots limit the decode batch, additional CPU
prefix storage improves reuse but does not directly admit
more concurrently decoding requests.
Another approach uses CPU memory to retain the histo-
ries of requests that are decoding. HiSparse stores complete
histories in CPU memory, fetches selected KV to GPUs at

each step, and caches some of that data for subsequent ac-
cesses (Xie et al., 2026). Since complete histories no longer
need to fit in GPU slots, this approach supports decode
batches beyond GPU history capacity. However, each GPU-
cached entry also remains in CPU memory. GPU cache
space accelerates access without storing additional history
positions. In Figure 2(b), HiSparse allocates 30.0 million
CPU slots for complete history and 23.3 million GPU slots
for cached copies. Its 53.3 million physical slots therefore
hold only 30.0 million unique history positions. CPU stor-
age expands decode capacity, but GPU and CPU capacity
are not jointly used to retain more history.
For models using MLA, conventional head-partitioned TP
introduces an additional source of replication across GPUs.
Ranks compute different attention heads while storing the
same shared KV representation for each request (DeepSeek-
AI et al., 2024; Bhatia et al., 2025). Figure 2(a) shows that
under eight-rank TP, only 12.5% of the SGLang and HiS-
parse history allocation stores unique history; the remaining
87.5% holds replicas. This replication further reduces the
space available for additional request histories.
Increasing decode concurrency therefore calls for CPU
memory to store active request histories and for less du-
plication between GPU and CPU memory and across GPUs.
While retaining the cached copies needed to reduce access
overhead, more of the available space should store distinct
KV history, allowing the expanded storage to accommodate
larger decode batches.
2.2.2
Fixed Per-Request Cache Quotas
GPU caches reduce repeated CPU-to-GPU transfers by re-
taining selected KV across decoding steps. Limiting each
request to a fixed cache quota bounds its GPU memory foot-
print and leaves room for other requests. As the number of
active requests falls, however, the remaining requests keep
the same quotas and cannot use the capacity left idle by
absent requests.
This restriction can cause KV misses even when the com-
plete active history fits in the available GPU KV capacity.
If an individual history exceeds its request’s quota, some
entries remain outside that request’s GPU cache. When-
ever sparse attention selects one of these entries, it must
be fetched from CPU memory. The transfer occurs despite
there being enough GPU space to retain the data.
HiSparse provides a concrete example through its fixed per-
request GPU buffers (Xie et al., 2026). In our 8×B300 DP
configuration with speculative decoding enabled, the avail-
able GPU KV capacity can hold all active history at BS1,
but the per-request buffer still retains only its configured
quota. HiSparse has 23.5% higher TPOT than GPU-resident
SGLang (Figure 6). This allocation constraint motivates al-
lowing cache allocations to grow as the number of active
requests decreases, so spare GPU capacity can retain KV
that would otherwise be evicted and fetched again.

SYSTEM OVERVIEW
UlaCache decouples the logical KV references used by the
inference engine from physical placement. Common allo-
cation and sparse-access interfaces cover rank-local and
distributed storage, while UlaCache coordinates caching,
KV transfers, and mapping updates. Figure 3 shows the sys-
tem modules and their organization for DP and TP attention.
Unified logical address space. UlaCache combines GPU
KV pools and optional CPU pools into a logical address
space. The address mapping associates each logical KV
address with its current GPU or CPU physical slot. When
KV cache moves, UlaCache updates this mapping without
changing the logical addresses used by the inference engine.
The address space covers a rank’s own pools in DP mode
or aggregates the pools of a GPU group in TP mode. GPU
KV pools retain history; in TP mode, each computing rank
also maintains a local GPU buffer of selected copies. Buffer
hits reuse local data without changing the history’s mapped
storage location.
KV allocation and access. The inference engine allocates
logical KV slots for a request, and UlaCache assigns their
physical storage. Prefill writes the computed KV cache to
these slots, and decoding extends the allocation as new to-
kens are generated. After sparse selection, UlaCache reuses
local GPU buffer hits where available and resolves the re-
maining logical addresses through the address mapping.
Selected CPU data is first moved into its storage GPU pool.
The selected KV cache is then read directly from the GPU
pool or fetched into a local GPU buffer for attention.
GPU–CPU scheduling with PB-LRU. When CPU stor-
age is enabled, UlaCache uses Parallel Bucketed LRU (PB-
LRU) to schedule transfers over a GPU KV pool shared
by requests. PB-LRU groups GPU slots into recency buck-
ets, updates accessed slots in parallel, and uses hierarchical
bitmaps to select replacement slots. Its transfer plan pro-
motes selected CPU data and moves replaced GPU data to
CPU memory; UlaCache updates the address mapping after
the exchange completes.

manages its own GPU pool and optional CPU pool. In TP

selected logical addresses to the current physical locations

4.2
KV Allocation and Access
Allocation and writes. The inference engine allocates logi-
cal KV slots and records them in its request-to-token map-
ping. UlaCache binds these slots to physical storage within
the request’s rank in DP mode or across the storage ranks
in TP mode. Prefill writes the computed KV cache to the
assigned locations; decoding allocates additional logical
slots for newly generated tokens. Both phases use the same
address mapping, and existing tokens retain their logical
addresses as their KV cache moves between GPU and CPU
memory.
Sparse access. Sparse selection returns logical KV ad-
dresses. In DP mode, the rank resolves these addresses to
physical slots, promotes any selected CPU data into its GPU
pool, and supplies attention directly from that pool. In TP
mode, the computing rank reuses local GPU buffer hits
and resolves the remaining addresses to their storage ranks
and physical locations. Selected CPU data is first promoted
into the corresponding storage GPU pool, then missing KV
cache is fetched from local or peer GPU pools into the com-
puting rank’s buffer. Attention waits until the selected data
is available. Section 5 describes GPU–CPU data exchange
and the corresponding address mapping updates.
4.3
Local GPU Buffer
Each computing rank in TP mode maintains a local GPU
buffer that caches copies of KV cache selected from the dis-
tributed pools and supplies them to the attention backend.
Its capacity is independent of the retained history length.
Cached copies remain available across decoding steps, re-
ducing repeated transfers when sparse selections overlap.
Replacing a buffer copy leaves the retained KV cache in
the storage pools available for future selections. DP mode
accesses its GPU pool directly without allocating this buffer.
Lookup and transfer. After sparse selection, UlaCache
checks which logical KV addresses are present in the buffer.

4.4
Distributed Indexer
In TP mode, Index keys follow the same logical token al-
location and GPU partition as the KV cache. Each GPU
scores only its local keys, and an all-gather combines the
scores for the model’s TopK selection. This partitioning re-
duces Index key replication and redundant scoring across
TP ranks. Selected positions identify logical KV addresses
and enter the KV access path described above. The score
all-gather introduces communication and synchronization
overhead, particularly at low concurrency. In DP mode, each
rank stores and scores the Index keys of its local requests
without this cross-rank score exchange.

CPU MEMORY EXPANSION AND
PB-LRU
For each sparse access, PB-LRU identifies KV cache that
must be fetched from CPU memory and assigns GPU slots
to it. Recently accessed KV cache remains in a GPU pool
shared by requests, while replaced KV cache moves to CPU
memory. The scheduler determines which KV entries to
move and their destination slots. UlaCache moves the data,
then updates the address mappings.
5.1
Parallel Bucketed LRU
Sparse selections exhibit temporal locality across decod-
ing steps (Xie et al., 2026). PB-LRU approximates LRU
by grouping GPU slots according to when they were last
accessed. Slots accessed in the same scheduling round share
a recency bucket, avoiding the need to order individual ac-
cesses. Figure 5 illustrates parallel lookup, recency updates,
and replacement.
Parallel access processing. GPU threads resolve the sup-
plied logical KV addresses in parallel using the address
mapping. GPU-resident KV cache remains in place, and
its slots move to the current recency bucket. CPU-resident
addresses are deduplicated into a list of KV cache to fetch.
Repeated references to the same GPU slot produce one ef-
fective recency update; repeated references to the same CPU
address require one transfer.
Recency buckets. Each layer group maintains a ring of
B recent buckets and one cold bucket. The current bucket
advances once per scheduling round. Before a bucket is
reused as the current bucket, its remaining members move
to the cold bucket. This operation changes recency metadata
only: the KV cache in these slots remains on the GPU. The
cold bucket therefore contains GPU slots whose data has
not been accessed within the recent window.

5.2
KV Exchange and Mapping Updates
For each CPU-to-GPU transfer, the plan records the logical
KV address, source CPU slot, destination GPU slot, and the
logical address of any KV cache being replaced. Planning
changes bucket membership without modifying KV data or
the address mapping.
GPU kernels exchange the data after prior readers of the
affected slots complete. When the destination GPU slot is
occupied, its KV cache moves into the source CPU slot as
the incoming data moves to the GPU. Reusing this CPU
slot avoids allocating additional CPU space for the replaced
data. For an empty GPU destination, only a CPU-to-GPU
copy is required; the source CPU slot is released after the
mapping update.
After all data transfers complete, UlaCache updates the ad-
dress mapping to reflect the new GPU and CPU locations,
then signals completion. Attention and local GPU buffer
fetches wait for this signal before using the new GPU loca-
tions. The logical KV addresses remain unchanged through-
out the exchange.

6.1
Experimental Setup
Platforms and baselines. We evaluate our SGLang integra-
tion using GLM-5.3 on 8×H200 and 8×B300 GPUs, with
FP8 weights and KV cache and BF16 activations. Our base-
lines are SGLang (Zheng et al., 2024) with GPU-resident
KV cache and HiSparse (Xie et al., 2026) with CPU-backed
KV cache. For HiSparse with speculative decoding, we use
the latest official SGLang implementation. Each system
is evaluated with DP and TP attention, with and without
speculative decoding. We use multi-token prediction (MTP)
with two draft steps for speculative decoding. GPU mem-
ory allocations are matched across systems; CPU budgets
are 128 GB per H200 GPU and 192 GB per B300 GPU.
B300 uses a 272 GB persistent GPU model/cache budget
per GPU.
Workload. We use Multi-LexSum requests (Shen et al.,
2022) with input lengths of 64K–128K tokens. H200 uses
256 requests (98,125 input tokens on average); B300 ex-
tends the frozen request order to reach each configuration’s
admitted concurrency, up to 578 requests. Each request gen-
erates 2,048 tokens using greedy decoding.
Metrics. We complete prefill for all requests in a batch be-
fore starting decoding. We report output token throughput
(tokens/s) and time per output token (TPOT, ms). Through-
put comparisons use each method’s observed peak over all
measured batch sizes, independently of its admission limit.
We skip batch sizes for which the system cannot accommo-
date all requests concurrently.

6.3
Throughput Scaling
Figure 7 shows output throughput across batch sizes; crosses
indicate configurations exceeding their admission limits.
UlaCache’s larger KV capacity keeps more requests active,
extending throughput scaling beyond the baselines’ admis-
sion limits. On 8×B300, its peak throughput in TP mode
without speculative decoding is 3.51× SGLang’s peak. The
larger admissible batch lets more outputs share each batched
model execution. With speculative decoding enabled, Ula-
Cache achieves peak throughput speedups over HiSparse of
1.16× (DP) and 1.70× (TP) on 8×H200, and 1.73× (DP)
and 2.51× (TP) on 8×B300. Figure 8 relates this concur-
rency advantage to effective KV capacity.

6.4
KV Allocation and Capacity
Figure 8 compares effective KV capacity and admitted con-
currency under matched memory budgets. The stacked ca-
pacity bars separate GPU and CPU storage, excluding repli-
cas and buffers.
In DP mode, UlaCache stores request histories across both
GPU and CPU memory. HiSparse keeps full histories in
CPU memory and uses GPU buffers to cache copies, so
these buffers do not increase its history capacity. In TP
mode, UlaCache also stores different portions of each his-
tory on different ranks. The additional capacity allows more
requests to decode concurrently, as shown by the admission
bars.

reuse. HiSparse’s fixed per-request GPU buffer quotas pre-

retaining more KV cache and achieving higher hit rates. At
low concurrency, all active KV cache remains on GPUs; hit
rates decrease as concurrency grows and requests compete
for the shared capacity.

RELATED WORK
KV addressing and reuse.
PagedAttention maps logical
KV blocks to physical GPU blocks to reduce fragmentation
and enable sharing (Kwon et al., 2023). vAttention preserves
contiguous virtual addresses with dynamic physical alloca-
tion (Prabhu et al., 2025). SGLang reuses prefixes (Zheng
et al., 2024); Mooncake extends reuse through distributed
storage (Qin et al., 2025). UlaCache preserves logical ref-
erences to active sparse-attention history as KV migrates

across GPU and CPU pools.
Hierarchical caching and decode capacity.
HiCache and
LMCache restore reusable prefixes from CPU memory or
external storage into the inference engine’s GPU alloca-
tion (Xie, 2025; Liu et al., 2025). This reduces prefill work
while active histories still occupy GPU slots. UlaCache
pools distinct GPU and CPU history slots for concurrently
decoding requests.
Distributed storage and parallelism.
LoongServe pools
KV for elastic sequence parallelism (Wu et al., 2024). Helix
shards KV and attention computation across GPUs (Bhatia
et al., 2025). UlaCache’s TP mode also distributes history
across GPUs, but computing ranks fetch only the selected
KV into local buffers. Its logical addressing and replacement
mechanisms manage these sparse accesses and GPU–CPU
migration.
Hierarchical sparse-attention serving.
HiSparse stores
complete KV histories of active requests in CPU memory
and fetches selected KV into fixed per-request GPU caches,
fusing hit detection, LRU replacement, and transfers (Xie
et al., 2026). ECHO overlaps KV transfers with indexer
computation (Liu et al., 2026). Spin provides partitions,
elastic per-request buffers, GPU bucketed LRU, and hierar-
chical metadata (Zhao et al., 2026). PB-LRU also groups
slots by recency, using GPU-slot bitmaps and hierarchical
summaries for parallel victim selection from a pool shared
across requests. UlaCache integrates this replacement with
KV migration and mapping updates in rank-local and dis-
tributed storage.
FlexGen aggregates GPU, CPU, and disk resources (Sheng
et al., 2023). InfiniGen predicts KV for prefetching (Lee
et al., 2024); RetrievalAttention combines GPU caching
with CPU vector retrieval (Liu et al., 2024). OasisKV ap-
proximates dense attention through draft-guided block se-
lection and pipelined prefetching (Xiao et al., 2026). Its
complete history resides in CPU or remote memory; GPU
buffers hold copies and add no independent history capac-
ity. UlaCache uses the model’s existing sparse selections to
drive KV access and migration.
SeKV uses learned routing over GPU span summaries and
approximately reconstructs selected spans from CPU low-
rank factors (Abaskohi et al., 2026). UlaCache retains his-
torical KV without adding semantic compression.
SparseEngine integrates sparse methods through lifecycle
hooks, method-owned cache managers, and attention views,
with Chain Cache for cross-turn reuse (Hao et al., 2026). Its
abstraction governs method execution; UlaCache manages
KV placement and access under stable logical references.
8
CONCLUSION
UlaCache provides unified logical KV addressing for sparse
attention across GPU and optional CPU storage. Stable refer-
ences support rank-local and distributed history placement,
while local GPU buffers reuse selected KV in TP mode. PB-
LRU schedules replacement and migration, and UlaCache
updates mappings after transfers complete. With specula-
tive decoding enabled under matched CPU and GPU mem-
ory budgets, UlaCache achieves peak decoding throughput
speedups of 1.16× (DP) and 1.70× (TP) on 8×H200, and
1.73× (DP) and 2.51× (TP) on 8×B300, compared with
the state-of-the-art baseline.
