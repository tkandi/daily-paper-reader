Abstract —NVIDIA Grace–Blackwell systems make CPU–GPU memory increasingly unified at the programming level, but unified addressability does not make the memory system uniform. A CUDA managed allocation on GB200 may be served from GPU-local HBM, accessed through host/system memory, demand-migrated, prefetched, reused after GPU access, or evicted and reloaded under capacity pressure. The problem is that these states share a programming interface while exercising different hardware paths and runtime mechanisms, making a single “Unified Memory bandwidth” number misleading. This paper presents a placement-controlled microbenchmark study of CUDA Unified Memory on NVIDIA GB200, using GH200 as a Grace–Hopper baseline and GB10/DGX Spark as a validation platform. Our methodology separates local HBM access, host/system-memory access, explicit movement, managed first touch, prefetch, reuse, access-pattern sensitivity, oversubscription, and CPU–GPU handoff, then summarizes the observations with a measurement-calibrated model of compute, access, migration, eviction, synchronization, and handoff costs. On GB200, a 1 GB STREAM-style triad reaches 3963 GB/s from local HBM but 304 GB/s through host-mapped CPU/system memory; for a 256 MB streaming kernel, cold CPU-initialized managed memory reaches 14.1 GB/s, while managed prefetch and reuse reach 4606 GB/s and 4504 GB/s. Below the capacity boundary, prefetched and reused managed memory remain above 4.6 TB/s, but at 125% of CUDA-visible memory they fall to 968 GB/s and 1214 GB/s, showing that Grace–Blackwell unified memory must be understood through placement, access history, locality, reuse, and capacity pressure.

I. I NTRODUCTION 

Modern heterogeneous systems increasingly expose mem-ory abstractions that reduce the burden of explicit CPU–GPU data movement. CUDA Unified Memory (UM) allows host and device code to access one managed allocation while the runtime handles mapping, migration, prefetching, and placement [1], [2]. At the same time, tightly coupled platforms have changed the hardware on which these abstractions oper-ate. NVIDIA Grace–Hopper introduced coherent CPU–GPU connectivity through NVLink-C2C, while Grace–Blackwell combines Grace CPU memory, Blackwell GPU HBM, and larger NVLink-based configurations such as GB200 NVL72 [3]–[6]. These systems simplify CPU–GPU sharing, but they do not make all memory accesses equivalent. The main issue is that unified addressability does not imply uniform performance. A managed allocation may corre-spond to data resident in GPU-local HBM, accessed through host/system memory, migrated on first touch, prefetched be-fore execution, reused after GPU placement, or reloaded under oversubscription. These cases exercise different hard-ware paths and runtime mechanisms. Performance therefore depends on residency, initialization, access pattern, reuse, and whether the working set exceeds GPU memory capacity. Prior studies have shown that CUDA UM can reduce programming complexity while introducing costs from page faults, migration, prefetching, memory advice, and oversub-scription [7]–[13]. Recent work on Grace–Hopper and AMD MI300A further demonstrates the importance of placement and data movement in tightly coupled CPU–GPU systems [14]– [16]. GPU microbenchmarking has also exposed architectural behavior across generations, including Hopper and Blackwell [17]–[24]. However, existing Blackwell studies target local GPU microarchitecture, while Grace–Hopper studies char-acterize the previous generation. Grace–Blackwell memory-management behavior remains insufficiently characterized. This paper studies NVIDIA Grace–Blackwell UM us-ing placement-controlled microbenchmarks that isolate GPU-local HBM, host/system-memory access, explicit movement, managed-memory placement, access-pattern sensitivity, over-subscription, and CPU–GPU handoff. GB200 is our primary target, with GH200 providing a Grace–Hopper predecessor baseline and GB10/DGX Spark used for benchmark and workflow validation. Our measurements show that GB200 unified-memory per-formance is highly state-dependent. CPU-initialized first touch is dominated by runtime page management, whereas prefetched and reused managed memory can recover near-HBM performance. Access pattern further shapes this behav-ior: streaming accesses amortize memory-management costs effectively, while strided, random, and sparse page-like ac-cesses reduce useful-byte efficiency and expose larger run-time overheads. Under capacity pressure, managed memory remains near resident performance below the GPU-memory boundary but degrades sharply once migration and eviction dominate execution. A. Grace–Blackwell Memory Paths 

Modern GPU nodes expose multiple memory paths with dif-ferent capacity, bandwidth, latency, coherence, and placement properties. GPU-local HBM is optimized for high-throughput device execution and provides the fastest memory path for GPU kernels. CPU-attached memory provides larger system capacity and is managed by the host processor, but GPU access to that memory may require explicit transfers, runtime-managed migration, or remote/coherent access through the CPU–GPU interconnect. In traditional PCIe-attached systems, programmers commonly use explicit allocation and copy op-erations to move data into GPU memory before launching kernels. This approach gives direct placement control, but it also increases programming complexity and makes perfor-mance sensitive to transfer timing, redundant copies, and GPU-memory capacity limits [2], [7]. Grace–Blackwell changes this organization by tightly cou-pling Grace CPU memory and Blackwell GPU HBM through NVIDIA NVLink-C2C. GB200-class systems combine Grace CPUs and Blackwell GPUs within a coherent CPU–GPU plat-form, while larger configurations such as GB200 NVL72 con-nect multiple Grace–Blackwell components through NVLink and NVLink Switch infrastructure [4]–[6]. This organization reduces the programming gap between host and device mem-ory, but it does not remove the performance differences be-tween memory locations. A GPU load served from local HBM, a GPU load satisfied from CPU-attached memory, a managed page migrated into GPU memory, and an oversubscribed page reloaded after eviction can each exercise different hardware paths and runtime mechanisms. Figure 1 illustrates the memory paths that motivate our placement-controlled methodology. We therefore treat Grace– Blackwell memory as a set of measurable paths rather than as a uniform memory pool. 

B. Addressing, Managed Memory, and Coherent Access 

The term “UM” is often used broadly, but several lay-ers contribute to application-visible behavior. We distinguish unified virtual addressing, CUDA managed memory, and the hardware-level coherent CPU–GPU memory system. Unified virtual addressing provides a common virtual ad-dress space in which CPU and GPU pointers can coexist. This simplifies pointer use across host and device code, but it is primarily an addressing mechanism. It does not guarantee that data is physically located near the processor accessing it, that a page has migrated to GPU memory, or that CPU-attached memory and GPU HBM have the same latency or bandwidth. CUDA UM, or managed memory, is the runtime and driver layer exposed through APIs such as cudaMallocManaged ,

cudaMemPrefetchAsync , and cudaMemAdvise [1]. Managed memory allows CPU and GPU code to access the same allocation while the CUDA runtime manages page map-ping, placement, migration, access permissions, and eviction. Unlike unified virtual addressing alone, managed memory can introduce runtime actions such as page-fault servicing, prefetching, migration between memory domains, and page replacement. Its performance therefore depends on where pages are resident, whether data has been touched by the CPU or GPU, whether prefetching or advice is used, and whether pages are reused. The hardware-level coherent memory system defines the physical paths available on the platform. On Grace–Blackwell, this includes Grace CPU memory, Blackwell GPU HBM, NVLink-C2C CPU–GPU connectivity, NVLink GPU–GPU connectivity, and coherence mechanisms that enable tighter CPU–GPU sharing than in conventional PCIe-attached sys-tems [4], [5], [25]. These mechanisms can make sharing and remote access more efficient, but they do not make every mem-ory reference equivalent. Local HBM access, coherent CPU-memory access, migrated managed pages, and oversubscribed managed pages remain distinct performance cases. This distinction also matters for higher-level programming models. In directive-based models such as OpenACC and OpenMP offload, a unified or coherent memory space can reduce the amount of explicit data-management code required, since CPU and GPU code may refer to the same data without manual staging in every case. However, this programmability benefit does not eliminate data movement: the runtime, com-piler, or driver may still need to establish mappings, migrate pages, preserve coherence, or serve accesses through a slower memory path. 

C. Runtime Policy, Locality, and Capacity Pressure 

CUDA managed memory exposes several runtime behaviors that directly affect performance. When a GPU accesses a managed page that is not resident or not mapped for GPU access, the system may service a page fault, update page-table mappings, migrate data, and resume execution. Programmers can influence this behavior with cudaMemPrefetchAsync ,which can move managed pages before kernel execution, and cudaMemAdvise , which provides placement and access hints to the runtime [1], [9]. Prior work has shown that these mechanisms can improve performance when they reduce demand faults or improve placement, but their effectiveness depends on platform topology, access locality, reuse, and memory pressure [8], [13]. Access pattern determines whether memory-management costs are amortized efficiently. Streaming access consumes many useful bytes per migrated page or memory transaction, making it favorable for bandwidth-oriented kernels. Strided ac-cess reduces useful bytes per cache line, memory transaction, or page. Random and irregular access can reduce coalescing, increase cache and TLB pressure, and make page movement poorly aligned with useful work. Therefore, the same managed allocation can perform differently under streaming, strided, random, and sparse page-like access, even when the total allocation size is unchanged. Capacity pressure introduces another source of cost. When a managed-memory working set approaches or exceeds GPU-local memory capacity, UM can allow execution to continue without manually restructuring the application around the HBM limit. However, if pages are evicted and later reused, execution can become dominated by repeated migration and reloading rather than useful computation. Prior studies have shown that oversubscription can cause severe slowdowns, especially for irregular workloads and access patterns with poor locality [10]–[12]. On Grace–Blackwell, the practical cost of oversubscription depends on the combined behavior of local HBM access, CPU-memory access, page migration, eviction, synchronization, and runtime placement policy. 

D. Need for Placement-Controlled Measurement 

Grace–Blackwell motivates placement-controlled character-ization because a unified allocation may correspond to lo-cal HBM access, CPU-memory access, first-touch migration, prefetched or reused pages, CPU–GPU handoff, or oversub-scribed pages undergoing eviction. These cases cannot be explained by one bandwidth number. We therefore isolate local and remote access, explicit movement, managed-memory state, access-pattern sensitivity, handoff, and capacity pressure, and use these measurements to parameterize the analytical model. III. R ELATED WORK 

A. CUDA UM and Oversubscription 

CUDA UM reduces explicit CPU–GPU data management but introduces runtime costs from page mapping, migration, prefetching, and eviction. Prior studies show that managed-memory performance depends strongly on prefetching, mem-ory advice, locality, reuse, and whether execution exceeds GPU memory capacity [2], [7]–[9], [13]. Allen and Ge an-alyze UVM page-fault generation and servicing [10], Kim et al. target irregular workloads with batch-aware memory management [11], and Shao et al. show that oversubscription can degrade sharply once eviction and re-migration dominate execution [12]. These studies establish the importance of page faults, local-ity, prefetching, and capacity pressure, but largely target earlier discrete GPUs or earlier NVLink systems. We instead study these effects on GB200 Grace–Blackwell, where managed memory operates across tightly coupled Grace memory and Blackwell HBM connected by NVLink-C2C. 

B. Tightly Coupled CPU–GPU Memory Systems 

Fusco et al. characterize data movement on Grace Hopper using latency, pointer-chasing, copy, ping-pong, internode, and application benchmarks [14], establishing GH200 as an impor-tant predecessor for tightly coupled Grace–Blackwell systems. Schieffer et al. provide the closest prior work, studying GH200 system-memory behavior including first touch, page migration, page size, oversubscription, and system-, managed-, and GPU-allocated memory [15]. Our work extends this direction with a direct GB200– GH200 comparison under a common methodology, controlled access-pattern measurements, CPU–GPU handoff and reuse experiments, oversubscription-threshold characterization, and a measurement-calibrated analytical model that separates ac-cess and memory-management costs. Cross-vendor work by Wahlgren et al. characterizes Unified Physical Memory on AMD MI300A, including bandwidth, latency, coherence, page faults, TLB behavior, and application implications [16]. C. GPU Microbenchmarking and Blackwell Characterization 

GPU microbenchmarking has long been used to expose architectural behavior not fully described by vendor docu-mentation, including memory hierarchy, instruction behavior, and cache effects [17]–[21]. More recent studies apply this approach to Hopper and Blackwell [22]–[24], [26], primarily focusing on local GPU microarchitecture and compute behav-ior. System-level suites such as NVIDIA HPC Benchmarks provide broader end-to-end measurements [27], but do not isolate managed-memory state, CPU/system-memory access, handoff, or oversubscription effects. Our work instead uses placement-controlled microbench-marks to isolate GPU-local HBM, CPU/system-memory ac-cess, managed-memory state, access-pattern sensitivity, over-subscription, and CPU–GPU handoff on Grace–Blackwell, then uses those measurements to parameterize an analytical model. B. Benchmark Suite 

The benchmark suite is organized around the memory paths and runtime mechanisms that must be separated to understand Grace–Blackwell UM. Table II summarizes the benchmark groups. The suite progresses from baseline memory paths to runtime-managed placement, access locality, capacity pres-sure, and CPU–GPU handoff. Benchmarks emit CSV-formatted output with common fields for working-set size, trial number, runtime, and band-width, together with benchmark-specific metadata such as memory mode, access pattern, warm-up count, active element count, useful bytes, and allocation footprint. The latter fields are especially important for sparse or irregular accesses, where a large allocation may produce relatively few useful bytes during a single kernel execution. 

C. Memory Placement and Runtime Policies 

We evaluate several memory placement and runtime-policy conditions. Explicit GPU-local memory uses cudaMalloc 

and cudaMemcpy to place data in GPU HBM before kernel execution. Kernel time is measured after placement, so this mode provides the device-resident baseline. Managed memory uses cudaMallocManaged and CPU initialization before GPU access. In this mode, the measured kernel may include page-fault servicing, page-table updates, migration, and placement overhead. Managed prefetch uses cudaMemPrefetchAsync before the timed kernel and records prefetch time separately when supported. Managed advice uses cudaMemAdvise to evaluate preferred GPU location, accessed-by GPU, and preferred CPU location hints [1]. Managed reuse performs a prior GPU access before measurement to distinguish cold first-touch behavior from reused GPU-resident behavior. Host/system-memory access is measured using pinned mapped host memory allocated with 

cudaHostAlloc and accessed on the GPU through a device pointer obtained with cudaHostGetDevicePointer .This path measures GPU access to CPU-backed memory rather than explicit copying or managed migration. 

D. Access Patterns, Oversubscription, and Handoff 

Access-pattern benchmarks separate memory-management overhead from locality effects. Streaming access touches con-tiguous elements and represents the best case for coalesced bandwidth. Strided access touches memory at a fixed interval and reduces useful bytes per cache line, memory transac-tion, or page. Random access uses a shuffled index array to represent irregular workloads. Page-touch access touches one element at 4 KiB, 64 KiB, and 2 MiB intervals. These intervals provide controlled sparse-access patterns for studying locality at different granularities and are not interpreted as direct measurements of the runtime’s internal page size. Oversubscription experiments allocate managed-memory working sets as a percentage of CUDA-visible memory. For array-based kernels, the reported footprint includes all ar-rays used by the benchmark. We evaluate streaming, strided, and random oversubscription to identify where performance changes from bandwidth-oriented execution to behavior dom-inated by page migration, eviction, and reloading. Random oversubscription results are interpreted carefully because the shuffled index array adds metadata storage and increases total memory pressure. The CPU–GPU handoff benchmark measures alternating CPU and GPU access to the same data under managed, prefetched managed, host-mapped, and explicit-copy policies. It compares CPU-only, GPU-only, and alternating CPU–GPU execution while varying the number of GPU passes performed after each CPU update. This benchmark quantifies how in-creasing GPU reuse amortizes CPU–GPU handoff and data-movement costs.

V. C HARACTERIZING THE GRACE -B LACKWELL MEMORY 

HIERARCHY 

This section establishes the baseline memory paths used to interpret the managed-memory, access-pattern, and over-subscription results in Sections VI and VII. We compare HBM, host-memory, and explicit-copy paths, then show that one streaming kernel runs near HBM bandwidth on resident, prefetched, or reused data but far slower on first-touch man-aged pages. 

A. Local HBM and Host/System-Memory Access 

Local GPU HBM provides the highest-throughput memory path for GB200 kernels. For a 1 GiB STREAM-style triad, GB200 reaches a median useful bandwidth of 3963 GB/s. The same benchmark on GH200 reaches 3165 GB/s, so the GB200 local-HBM path provides approximately 1.25 × higher measured bandwidth for this kernel. This serves as the baseline for evaluating the remaining memory placement modes. GPU access to host/system memory is substantially slower than local HBM, but still provides hundreds of GB/s of useful bandwidth. On GB200, the host-mapped 1 GiB triad reaches 304 GB/s, or about 7.7% of the local-HBM triad bandwidth, compared with 345 GB/s on GH200. Thus, unlike the local-HBM, copy, and prefetch paths, the host-mapped path does not improve on GB200 in this benchmark; its measured bandwidth is about 12% lower than on GH200. Because this path traverses coherent CPU/system memory rather than local HBM, the result should not be interpreted as a regression in Blackwell HBM performance, and our measurements do not isolate the specific interconnect, coherence, or memory-system factor responsible. It nevertheless reinforces that host/system-memory access is a distinct performance path and should not be treated as equivalent to local HBM for bandwidth-bound kernels. The copy-only HBM baseline also shows that measured performance depends on the kernel’s memory traffic. On GB200, the 1 GiB HBM copy benchmark reaches 2958 GB/s, while the triad reaches 3963 GB/s. We therefore use kernel-specific baselines when normalizing later results instead of assuming a single HBM bandwidth number for all access patterns. 

B. Explicit Movement and Managed Prefetch Bandwidth 

Explicit transfer and prefetch measurements provide amovement-bandwidth baseline for interpreting managed-memory behavior. On GB200, 1 GiB explicit host-to-device copies reach a median bandwidth of 211 GB/s, while device-to-host copies reach 193 GB/s. These transfer paths are faster than the corresponding GH200 measurements, where host-to-device and device-to-host copies reach 130 GB/s and 67 GB/s, respectively. Managed prefetch bandwidth is lower than explicit copy bandwidth but still provides an important mechanism for moving page-management work outside the timed kernel. On GB200, CPU-to-GPU managed prefetch reaches 115 GB/s for a 1 GiB allocation, while GPU-to-CPU prefetch reaches 75 GB/s. On GH200, the corresponding prefetch directions reach 42 GB/s and 18 GB/s. These measurements show that prefetching is not free, but also that GB200 substantially im-proves the measured page-movement baseline compared with GH200. This distinction is important because later managed-memory results separate the cost of moving pages before a kernel from the cost of servicing faults during kernel execu-tion. Figure 2 summarizes these baseline memory paths for the 1 GiB measurements. The results show that GB200 improves local-HBM, explicit-transfer, and managed-prefetch bandwidth relative to GH200, but GPU access to host/system memory remains much slower than local HBM on both platforms.

B. Access-Pattern Sensitivity 

Managed-memory performance also depends strongly on access pattern. Here, stride denotes the number of array ele-ments between consecutive accesses. The allocation footprint remains fixed at 256 MiB, but increasing stride reduces the number of elements actually touched by the kernel. Conse-quently, each cache line, memory transaction, or managed-memory region may contribute fewer useful bytes to the computation. Because we report useful bandwidth using only the bytes associated with accessed elements, decreasing spatial locality appears directly as lower useful bandwidth. Figure 5 compares explicit HBM, cold managed memory, managed prefetch, and managed reuse for the GB200 strided-access benchmark. The explicit-HBM baseline falls from 4585 GB/s at stride 1 to 67.7 GB/s at stride 1024. This decline occurs even without managed-memory migration because in-creasingly sparse accesses make less effective use of each memory transaction and reduce the amount of useful data transferred per unit time. Prefetched and reused managed memory largely follow this explicit baseline: at stride 1, they reach 3659 GB/s and 3685 GB/s, and at stride 64 they reach 177 GB/s and 177 GB/s, respectively. Cold managed first touch behaves very differently. At stride 1, cold managed memory reaches only 8.6 GB/s, and it falls to 0.01 GB/s by stride 1024. Sparse accesses compound the locality loss because the runtime may still incur page mapping and migration work for memory regions from which only a small fraction of bytes are actually used. C. Sparse Page-Like Access 

The page-touch benchmark further illustrates the importance of useful-byte efficiency. The benchmark touches one element per page-like stride while reporting both useful bytes and allocation footprint. For a 256 MiB managed allocation, a 4 KiB stride reaches 27.0 GB/s of useful bandwidth, while a 64 KiB stride reaches 1.85 GB/s and a 2 MiB stride reaches only 0.043 GB/s. These numbers should not be interpreted as direct measurements of the runtime’s internal page size. Instead, they show how sparse access patterns reduce the amount of useful work performed per allocation footprint. Together, these results show that CUDA managed mem-ory on GB200 is not characterized by a single bandwidth value. Cold CPU-initialized managed memory is dominated by page-management and migration costs. Prefetching and reuse can recover near-resident performance for streaming and regular access. However, strided, random, and sparse page-like patterns reduce useful-byte efficiency and can expose large gaps between the programming abstraction and the underlying memory-management cost. VII. C APACITY PRESSURE AND CPU–GPU H ANDOFF 

Sections V and VI show that GB200 unified-memory be-havior depends on placement, access history, and locality. This section examines two additional system-level effects: capacity pressure as the working set approaches or exceeds GPU mem-ory, and CPU–GPU handoff when the same data alternates between processors. These measurements expose the capacity-and handoff-related costs represented in the analytical model of Section VIII; the handoff sweep also provides a directly testable case for quantitative model validation. 

A. Capacity Pressure and Oversubscription 

Managed memory can preserve programmability when the working set approaches or exceeds GPU memory capacity, but performance changes sharply once pages must be evicted and later reloaded. Figure 7 compares streaming oversubscription behavior across GH200, GB200, and GB10/DGX Spark. The GH200 and GB200 measurements show the same qualitative threshold behavior: prefetched and reused managed memory remain near resident bandwidth below the capacity boundary, then drop sharply once the managed footprint exceeds CUDA-visible memory. On GB200, prefetched managed memory sustains 4683– 4736 GB/s from 25% to 90% of CUDA-visible memory, while reused managed memory sustains 4674–4701 GB/s over the same range. These values are close to the resident streaming bandwidth observed in Sections V and VI. At 105%, prefetched managed bandwidth drops to 2385 GB/s and reused managed bandwidth drops to 2722 GB/s. At 125%, the same modes fall further to 968 GB/s and 1214 GB/s. This drop indicates that execution is no longer limited primarily by streaming HBM bandwidth and is consistent with increasing page migration, eviction, and reloading costs. GH200 shows the same trend at lower absolute bandwidth. From 25% to 90% of CUDA-visible memory, prefetched and reused managed memory remain near 3.2 TB/s. At 105%, they fall to approximately 1180 GB/s and 1229 GB/s, and at 125% they fall to 424 GB/s and 453 GB/s. Thus, GB200 increases resident and prefetched streaming bandwidth relative to GH200, but both systems expose the same capacity-pressure transition once the working set exceeds GPU memory capacity. In contrast, cold managed first-touch bandwidth remains low across the sweep on both GH200 and GB200 because it is already dominated by runtime page-management overhead before oversubscription becomes the main limiting factor. The GB10/DGX Spark data is included as validation evidence: it confirms that the benchmark workflow exercises the same managed-memory policies, but we do not use it to draw final Grace–Blackwell conclusions because GB10 has a different memory organization and much lower absolute bandwidth. B. CPU–GPU Handoff and Reuse 

Many heterogeneous applications alternate between CPU-side updates and GPU-side computation. To measure this behavior, our handoff benchmark compares CPU-only time, GPU-only time, and alternating CPU–GPU execution under managed, prefetched managed, host-mapped, and explicit-copy policies. The key question is how much GPU reuse is needed before moving data into HBM is worth the cost. Figure 8 shows the handoff/reuse tradeoff for a 1 GiB working set. With one GPU pass after a CPU update, de-fault managed memory is expensive: alternating execution takes 272.1 ms, compared with a CPU-only plus GPU-only baseline of 54.2 ms. The additional 217.9 ms reflects the cost of demand-driven page management and data movement. Managed prefetch reduces this cost substantially: alternating execution takes 79.9 ms, with 24.6 ms of extra cost over the corresponding baseline. Explicit copy takes 60.5 ms, only 5.4 ms above baseline. Host-mapped memory takes 60.2 ms and adds little handoff cost relative to its matched baseline, but its GPU-only pass is much slower because the GPU accesses CPU-backed memory directly rather than local HBM. As reuse increases, the policy tradeoff changes. With 32 GPU passes after each CPU update, explicit copy takes 73.3 ms total, managed prefetch takes 92.6 ms, host-mapped memory takes 218.7 ms, and default managed memory takes 284.4 ms. Thus, host-mapped access is competitive when data is used only once, but local placement becomes increasingly valuable as GPU reuse increases. This behavior motivates a simple break-even view: moving data into HBM is worthwhile when the one-time movement cost is repaid by enough faster GPU accesses. The nearly fixed policy-dependent handoff cost and approx-imately linear growth with GPU reuse suggest an affine model with a one-time fixed cost and a marginal cost per GPU pass. The decomposition and reuse model serve complementary purposes. The former connects placement, migration, eviction, locality, and synchronization to behaviors observed throughout the benchmark suite, while the latter quantitatively predicts the CPU–GPU placement tradeoff. In practice, our results suggest three guidelines: prefetch or establish GPU residency before bandwidth-intensive managed-memory kernels, avoid sustained oversubscription when the working set exceeds avail-able HBM, and prefer explicit or prefetched placement when data will be reused across GPU passes. Host-mapped access is most attractive when GPU reuse is low and avoiding an up-front movement cost is more important than per-pass band-width. Together, these results show why unified addressability alone cannot predict performance: the dominant cost changes with placement, locality, capacity pressure, and reuse. IX. C ONCLUSION 

We characterized NVIDIA Grace–Blackwell UM on GB200 with placement-controlled microbenchmarks, using GH200 as a Grace–Hopper baseline and GB10/DGX Spark for validation. Relative to GH200, GB200 raises resident and prefetched bandwidth, but cold first touch, CPU-memory access, irregular locality, and oversubscription remain ma-jor performance limits. On a 1 GiB STREAM triad, local HBM reaches 3963 GB/s, while host-mapped system memory reaches 304 GB/s, 7.7% of HBM. On a 256 MiB streaming kernel, cold CPU-initialized managed memory reaches only 14.1 GB/s, while prefetched and reused managed memory reach 4606 and 4504 GB/s. Strided, random, and sparse accesses use fewer of the bytes they move and expose larger managed-memory overheads. Prefetched and reused managed memory stay above 4.6 TB/s up to 90% of CUDA-visible memory, but at 125% they fall to 968 and 1214 GB/s. Our analytical model separates compute, local and re-mote memory access, page management, migration, eviction, and synchronization costs. It also quantitatively captures the reuse-dependent CPU–GPU placement tradeoff: across the larger handoff working sets, the model achieves approximately 0.40% median absolute percentage error and identifies the measured fastest policy for all 20 validation size–reuse com-binations. These results show when prefetching or explicit placement can amortize movement costs and when remote or oversubscribed access becomes the dominant limitation.
