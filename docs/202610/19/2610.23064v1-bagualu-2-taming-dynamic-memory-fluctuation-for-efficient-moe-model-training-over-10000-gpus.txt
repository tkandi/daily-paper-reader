Abstract —Fine-grained Mixture-of-Experts (MoE) is the de facto architecture for scaling large language models. How-ever, dynamic expert load imbalance causes severe memory fluctuations that degrade training efficiency. Existing systems rely on static memory provisioning: they either over-provision, leaving GPU memory idle during normal execution, or under-provision, inviting out-of-memory crashes and costly manual rollbacks when load spikes occur. To address these challenges, we propose BaGuaLu-2, a large-scale MoE training system that eliminates this dilemma through flexible provisioning. By transforming memory allocation from a static, one-time tuning choice into a continuous and fine-grained control. BaGuaLu-2 grants exact activation memory on demand for each training batch. Furthermore, it offsets any dynamic management over-head through system optimizations. BaGuaLu-2 demonstrates exceptional scalability, training a model with 1040 billion pa-rameters across 12,288 GPUs while sustaining over 2 EFlops at 35% MFU. Compared with state-of-the-art systems, BaGuaLu-2 delivers 1.14 × and 1.13 × average throughput improvements over Megatron-Kuai and AdaPipe, respectively. 

I. I NTRODUCTION 

Large language models (LLMs) have demonstrated remark-able capabilities across domains, driving an ever-growing demand for larger and more capable models. To meet this demand, fine-grained Mixture-of-Experts (MoE) has emerged as the dominant architecture for scaling LLMs [1]–[7], as it increases model capacity without proportionally increasing the computation per token. Accelerating MoE training process has become a major focus in current systems research. 

*Corresponding authors 

A fundamental characteristic of the MoE architecture is its dynamic sparse routing mechanism, which inherently intro-duces expert load imbalance. We observe this phenomenon consistently when scaling training to clusters comprising tens of thousands of GPUs. In approximately 2.9% of training iterations, imbalanced load exhibits maximum 2.6× spikes. The imbalanced load leads to dynamic memory fluctuation, where training jobs have the risk to exceed physical hardware capacity and triggering Out-of-Memory (OOM) errors, which halt the training process. In response to the huge memory requirement of large-scale model training, existing systems optimize GPU memory usage from multiple angles. For weight and optimizer-states, model parallelism [8] and ZeRO [9] effectively shards these memory usage across devices. For activation memory, systems rely on recomputation [10] and offloading [11] to reduce peak consumption. However, these static approaches fail to resolve dynamic memory fluctuation introduced by load imbalance. Existing training systems are trapped in a rigid dilemma: as shown in Figure 1(b), if the system over-provisions memory to avoid OOM errors, GPU memory is wasted during most of the iterations, resulting in persistently low Model FLOPs Utilization (MFU). Conversely, if the system under-provisions 

memory to maximize MFU, it cannot dynamically respond to memory spikes at runtime. Upon encountering a spike, the system crashes and requires manual intervention. Restart and set the system in a conservative, over-provisioning memory configuration. We identify activation memory as the root cause of both the memory bottleneck and the fluctuation at scale. Figure 1(a) shows the per-GPU memory demand breakdown in large-scale training. Weight and optimizer-state memory can be distributed across GPUs and remains stable across iterations. Activation memory, in contrast, cannot be effectively distributed—larger clusters require proportionally more input data to maintain compute density—and fluctuates unpredictably due to expert load imbalance caused by MoE’s dynamic sparse routing. Thus, dynamically managing activation memory is the key to addressing the efficiency and stability challenges of large-scale MoE training. However, existing systems’ activation memory management suffers from two fundamental deficiencies. 

Static Memory Provisioning. Existing systems treat acti-vation provisioning as a coarse-grained, fixed policy: the policy is determined before training and cannot be adjusted at runtime. For example, although AdaPipe [10] supports adap-tive recomputation across pipeline stages, each pipeline stage remains a fixed strategy throughout training. This prevents the system from responding to per-batch memory fluctuation. 

Large Memory Mitigation Overhead. The extra computa-tion or communication introduced by activation mitigation is directly exposed on the critical path and cannot be overlapped. For example, the activation offloading in Megatron-Kuai [11] achieves only limited overlap at inter-layer boundaries. Activa-tion mitigation therefore becomes a pure performance penalty, and systems tend to minimize its use, further limiting the scope N N+200 N+400 N+600 N+800 N+1000 N+1200 N+1400

Constrained by these deficiencies, existing systems can only make a static binary choice between over-provision and under-provision. They are unable to dynamically allocate exactly the resources needed based on the actual memory fluctuation of each training iteration. We propose flexible activation provi-sioning , which transform activation memory provisioning from a static choice into continuous control , thereby achieving fully-utilized GPU memory. As shown in Figure 2, this enables the system to tame dynamic memory fluctuation in both regimes: (i) when MoE load imbalance is moderate, the system applies steady activation mitigation to enable high-throughput parallelism, consuming almost all available memory; (ii) when load imbalance is severe, the system dynamically intensifies activation mitigation to prevent OOM, avoiding the far greater cost of a cold restart. We design three techniques to realize flexible-provisioning at training runtime. 

Activation Memory Modeling (§IV). We design an activation memory cost model, which can accurately predict activation memory usage and mitigation time consumption. It guides the following runtime memory provisioning strategies. 

Adaptive Activation Provisioning (§V-A). Considering pipeline schedule phase and current MoE imbalance load, we apply flexible memory budget for each micro batch. Within a batch, operators can use different mitigation strategies, giving the system continuous control over memory consumption. 

Fused Dual-Batch Execution (§V-B). We propose interleaved execution for adjacent micro batch to avoid directly exposing activation mitigation overhead on the critical path. Using a light-weight runtime solver, mitigation operations are inserted into hardware bubble so that the execution overhead is hidden. These techniques are implemented in BaGuaLu-2, a large-scale MoE training system. We scale up to 12,288 GPUs for training 1040 billion parameters MoE model. BaGuaLu-2 achieves throughput of over 2 EFlops and an MFU of 35%. Compared with state-of-the-art training systems Megatron-Kuai [11] and AdaPipe [10], BaGuaLu-2 improves both train-ing stability and peak performance, with average throughput gains of 1.14 × and 1.13 ×, respectively. II. B ACKGROUND AND MOTIVATION 

A. MoE Training at Scale 

The Mixture-of-Experts architecture has undergone a sig-nificant structural shift in recent years. Table I surveys repre-sentative MoE models. Early designs such as Mixtral [12] and DBRX [13] adopt a coarse-grained architecture with a small number of large experts, while more recent models such as DeepSeek-V3 [1] select 8 out of 256 fine-grained experts for each token. This shift toward fine-grained MoE increases the number of activated experts and, critically, amplifies MoE-related activation memory, making activation management a first-class concern for training MoE model at scale. Alongside this trend, the nature of expert load imbal-ance has also evolved. Early MoE systems suffered from persistent, widespread imbalance across training iterations, which motivated compute-focused mitigation strategies [14], [15]. Advances in routing algorithms [16], [17] have largely eliminated this chronic imbalance. However, imbalance has not disappeared: it now manifests as rare, high-magnitude spikes. As shown in Figure 1(a), our measurements reveal that 

97 .1% of training iterations exhibit an imbalance rate below 

1.2×, while 2.9% of iterations exceed that rate with maximum 

2.6×. This shift in character changes the relevant system objective: since spikes are infrequent, the cost of slowing down to handle them is low, but an OOM failure, which requires manual intervention and job restart, is catastrophic. Existing MoE training systems [15], [18]–[21] focus on compute load balancing. They are poorly equipped to prevent the memory failures caused by occasional spikes. To train fine-grained MoE model at scale, mitigating ac-tivation memory becomes important. The standard approach to mitigating activation memory draws on two families of techniques. Recomputation discards activations during the forward pass and recomputes them from saved checkpoints during the backward pass, trading compute for memory [22]. 

Offloading transfers activations to CPU memory during the forward pass and prefetches them back to GPU before the corresponding backward computation [23]. Despite their dif-ferences, all existing systems share the same static workflow to apply activation mitigation: (1) profile or model the memory footprint of a target configuration, (2) select an activation mitigation strategy that fits within a fixed memory budget, and (3) apply that strategy uniformly throughout training. This workflow implicitly assumes activation memory is stable across iterations . The occasional memory spikes of fine-grained MoE break this assumption: a strategy sized for the average case will OOM on a spike, while a strategy sized for the worst case wastes memory during the most of iterations. 

B. Dynamic Memory Pressure: A Quantitative Case 

To quantify the cost of static activation management in MoE training, we run a representative training workload on 512 GPUs using a 423B-A30B MoE model, as shown in Figure 1. We use a state-of-the-art training system AdaPipe [10], and config its memory management policy as under-provisioning: the activation memory budget is set for the average case, maximizing memory utilization and MFU during normal iter-ations but leaving no headroom to absorb spikes. Specifically, selective recompute is applied for several operators. This policy achieves a high average MFU of 30 .0% during normal iterations, but encounters OOM failures in approximately 

2.9% of spike iterations, each requiring a job restart that incurs a recovery overhead of 284 seconds, which is 16 ×

the time cost of a normal iteration. We profile the cold-start overhead and find most of the time is spent on large-scale distributed initialization and GPU kernel warmup, which is hard to eliminate. Note that this measurement excludes human response latency, which can further increase the total recovery time. After restart casued by OOM, the policy is switch to over-provisioning. Specifically, full-layer recompute is applied so that activation memory consumption is not influenced by MoE imbalance rate. This policy runs stably but delivers a sustained MFU of only 24 .6% , because the unused memory headroom forecloses more efficient configurations. We argue from first principles that this spike is an inevitable consequence of the input token distribution, not an artifact of any particular routing algorithm, via a four-step chain. 

(1) Routing randomness. Fine-grained top-k routing lets each token independently select its experts, introducing per-micro-batch sampling noise. Long-run load-balancing mechanisms — an auxiliary loss [16] or a bias correction [17] — cannot suppress this noise: each correction is computed from aggre-gate load observed over past iterations and fixed before the current micro-batch is routed, so neither can condition on that batch’s realized content. (2) Token-distribution skew. A micro-batch whose token distribution happens to be unfavorable — a property of the data, not the algorithm — therefore concentrates tokens on a small subset of experts regardless of the balancing mechanism in place, since any correction reacts to past load at least one iteration too late; our measurements show this occurs in a small fraction of micro-batches, with up to 2.6× imbalance. (3) Expert placement. Fine-grained architectures pair a large expert count with a high expert-parallelism degree, so each device hosts only a few local experts; expert-level imbalance therefore translates directly into device-level token concentration , since skew on locally-hosted experts accumulates activations on that device while skew on remote experts is carried away by all-to-all dispatch. This directionality is why a given skew’s impact cannot be determined until the gate is computed (§V-A). (4) Warmup accumulation. During the pipeline warmup phase (Figure 5c), multiple forward micro-batches stack without an intervening backward pass, so a single skewed batch can push the cumu-lative peak beyond device memory capacity. The root cause is thus the finite-sample variance of per-token independent routing acting on a shifting data distribution — an architectural property of any fine-grained MoE, not a correctable bug. We support this argument with direct evidence that real input data measurably alters expert-load skew, which by the same mechanism implies similar variation across training iterations. III. O VERVIEW 

We propose BaGuaLu-2, a training system that handles dynamic memory fluctuation in large-scale MoE model train-ing. Figure 4 presents an overview. Before training starts, BaGuaLu-2 follows existing practice to generate an optimal hybrid-parallel strategy from training specification, with the assumption of balanced MoE workload. At runtime, BaGuaLu-2 performs flexible activation provisioning to deal with im-balanced and unpredictable MoE workload. At each pipeline scheduling point, BaGuaLu-2 decides the execution plan (memory usage and operator execution order) for the next micro batch with three steps: 

Activation memory modeling (§IV). Given the current pipeline state and MoE imbalance rate, BaGuaLu-2 evaluates the activation memory demand of the upcoming micro-batch using the cost model developed in §IV, and assesses the cost-benefit tradeoff of each mitigation strategy. Adaptive Activa-tion Provisioning (§V-A). Then, BaGuaLu-2 applies diverse activation mitigation strategies for each batch. A pipeline-aware memory budget is computed for the micro-batch, and an iterative algorithm selects per-operator mitigation strate-gies (recomputation, offloading, or quantization) to keep the peak memory within GPU capacity while minimizing perfor-mance overhead. Fused dual-batch execution (§V-B). Finally, BaGuaLu-2 examines the chosen mitigation strategies of the current and adjacent micro-batches and uses a lightweight solver to interleave operators’ execution across computation and communication streams, hiding the mitigation overhead in hardware bubbles. These three steps collectively produce the execution plan for the next pipeline state with optimized activation memory con-sumption, minimizing total execution time without exceeding the device memory limit. IV. A CTIVATION MEMORY MODELING 

We now develop the activation cost model , a unified perfor-mance model that jointly captures the time and memory cost of activation management. We first define the cost model from the operator level to a full iteration (§IV-A), then quantify existing activation mitigation strategies under this model (§IV-B). 

A. Activation Cost Model 

Operator activation cost (Figure 5a). We characterize each operator by an activation cost : a tuple (∆ t, ∆m) where 

∆t is the operator’s execution time and ∆m is the change in activation memory (positive for forward allocation and negative for backward release). Visually, the activation cost traces a trajectory on an activation memory curve whose x-axis is time and y-axis is GPU memory occupancy: a forward operator corresponds to a right-triangle with its hypotenuse rising to the upper-right, and a backward operator corresponds to a right-triangle with its hypotenuse falling to the lower-right (Figure 5). As each operator corresponds to a single kernel launch, the piecewise-linear approximation closely tracks the actual memory footprint. Operators in an MoE transformer block show very different characteristics. We illustrate three representative operators: LayerNorm, Linear, and MoE dis-patch communication. Comparing LayerNorm and Linear, the ratio of ∆m and ∆t has a significant difference. It leads to different mitigation bandwidth introduced in the next section. And for dispatch communication, there is no memory cost because it has no trainable parameters. 

Micro-batch activation cost (Figure 5b). A forward or backward micro-batch is a sequence of operators executed on a single pipeline stage. Its activation cost is the concatenation of its constituent operators’ costs, yielding an approximated composite triangle on the activation memory curve with total height P ∆m and total width P ∆t. Since every operator only contributes a small portion of the total activation memory, this approximation is acceptable. For simplicity, we will use this approximation in the following analysis on micro-batch and iteration level modeling. 

Iteration activation cost (Figure 5c). Under pipeline par-allelism, a training iteration executes multiple micro-batches across three pipeline scheduling phases. On the activation memory curve, these phases manifest as characteristic patterns of micro-batch cost triangles: Warmup. only forward batches execute. Forward triangles stack sequentially, and the memory curve rises monotonically as each micro-batch’s activations ac-cumulate. Steady state (1F1B). forward and backward batches interleaved. V. M ODEL -G UIDED RUNTIME MEMORY PROVISIONING 

Problem Formulation. For dense models, every micro-batch produces the same activation cost, so the activation memory curve is identical across batches and iterations. For example, in Figure 5c, the peak activation memory starts at the end of the warmup phase and sustains until the beginning of the cooldown phase. A static mitigation strategy planned before training is sufficient to prevent out-of-memory errors. MoE models break this assumption. The dynamic token-to-expert routing causes the ∆m of MoE-related forward oper-ators to fluctuate with the imbalance rate: when more tokens are routed to locally-hosted experts, the activation footprint grows. As shown in §II-B, this fluctuation is unpredictable and can spike by 1.5× or more, making any fixed strategy either wasteful in the common case or unsafe during spikes. Given a cluster and an MoE model, the system must decide, for each operator in each micro-batch, which activation mitigation strategy to apply. The optimization objective is: 

min X ∆t s.t. peak memory ≤ Mmax ,

where Mmax is the GPU memory capacity and the sum is over all operators in the iteration. In other words, the system minimizes the total execution time (i.e., the total width of the activation memory curve) subject to keeping the curve’s peak height within GPU capacity. Because the activation costs of MoE operators are only known at training runtime (once the imbalance rate is observed), this optimization must be solved 

online , during each iteration’s pipeline scheduling points. 

Runtime Workflow. At a pipeline scheduling point, BaGuaLu-2 obtains the activation memory cost of current batches with the activation cost model (§IV). Then, BaGuaLu-2 employs two complementary optimizations that address the two dimensions of the activation cost tuple respectively. 

Dynamic Activation Memory Mitigation (§V-A) selects per-operator activation mitigation strategy to keep the peak mem-ory within the GPU capacity, taming the height of the acti-vation memory footprint curve. Fused Dual-Batch Execution 

(§V-B) interleaves adjacent forward and backward micro-batch operations to reduce the total execution time, compressing the 

width of the curve. Figure 7 illustrates the effect of the two optimizations using the activation memory curve of a training iteration. The naive curve exceeds GPU capacity at several micro-batches. After applying dynamic activation memory mitigation, the peak is brought within capacity, but the added recomputation and offload operations increase the total execution time. After dual-batch fused execution, the timespan recovers by hiding mitigation operations behind useful computation. 

A. Dynamic Activation Memory Mitigation 

The goal of runtime activation provisioning is to select, for each operator in each micro-batch, a mitigation strategy (none, recompute, offload, or quantize) such that the peak activation memory stays within GPU capacity while minimizing the total time overhead. In this section, we address four questions: how to deal with unpredictable MoE spikes, how much memory each micro-batch can afford considered the unpredictable workload, which mitigation strategy to apply given the budget, and how to handle conflicts when composing strategies. 

Deferred Planning for Unpredictable MoE Spikes. The actual MoE imbalance workload is unpredictable until the execution of MoE gate operator within the forward micro batch. Therefore, it is impossible to exactly preserve the acti-vation memory quota for an incoming forward batch. However, we find that deferring activation memory provisioning to the next micro batch is acceptable, because in §IV the iteration-level activation cost model reveals that the activation memory peak is compounded by multiple batches. Pipeline-Aware Memory Budget Assignment. The activation memory budget depends on both the pipeline schedule phase and the actual memory pressure at runtime. Algorithm 1 com-putes a per-micro-batch budget that guarantees all concurrent micro-batches fit within GPU memory. Let B denote the total number of micro-batches, Bw the number of warmup batches, 

Mmax the GPU memory capacity, and M0 the minimum per-batch activation memory (achieved under full recomputation, retaining only the block input tensor). During warmup (lines 3–9), no backward pass releases memory, so the budget for each new micro-batch is computed by evenly distributing the remaining capacity among all yet-to-be-launched batches, while reserving M0 for each to guarantee feasibility. During the steady phase (lines 10–16), each forward is preceded by a backward that frees the activations of an earlier micro-batch (line 11), and the freed memory is fully allocated to the incoming batch (line 12). In both phases, the budget is updated to the actual memory consumed (lines 7, 14), so that over-estimation in one batch does not cascade into under-allocation for subsequent batches. 

Roofline-Guided Iterative Activation Mitigation. Given the memory budget for a micro-batch, the system must select which operators to mitigate and with which strategy. In terms of the activation cost model, this is choosing a mitigation strategy for each operator such that the total P ∆m (the micro-batch triangle height) stays within the budget while minimizing the total P ∆t (the micro-batch triangle width). We solve this with a greedy iterative algorithm (Algorithm 2). Using the roofline model of individual mitigation strategy characterized in (§IV-B), every operator has a candidate mit-igation strategy. At each iteration, we evaluate the memory reduction of every candidate single-operator mitigation on the current configuration, select the one with the largest reduc-tion, verify that it does not conflict with previously applied strategies (detailed below), and apply it if valid. The algorithm terminates when the memory budget is satisfied. The potential memory reduction is re-evaluated at each iteration, since applying one strategy may change the benefit of subsequent ones (e.g., recomputing a set of operators makes offloading its intermediate nodes unnecessary).

When different strategies are applied to different consumers of the same tensor, inconsistencies arise. We identify two common patterns: Case 1: Multi-precision conflict. The same tensor is transformed into different precisions at different consumers, causing multiple copies to coexist. For example, the MoE layer input serves as an input to both the MoE router (which typically requires FP32 for numerical stability) and the shared expert (which typically uses BF16 or FP8). If quantization is applied independently to each consumer, both an FP32 and an FP8 copy are stored, increasing rather than reducing total memory. Case 2: Multi-device conflict. The same tensor is offloaded at one consumer but remains on the GPU at another, so the GPU copy cannot be freed. For example, the core attention output tensor serves as the activation tensor for core attention operator and the input tensor for the following out-projection. If offloading is applied to the attention output but the out-projection saves the same tensor on GPU, the GPU tensor persists, and the offload yields no memory savings. To detect these conflicts, we perform a check after each candidate strategy. The check traces each optimized oper-ator back to its source activation tensor and verifies that all consumers of the same tensor have consistent precision and device placement. If a conflict is detected, the candidate strategy is rejected. Since the algorithm selects the strategy in decreasing order of memory benefit, a conflicting candidate always conflicts with a previously applied strategy that yields a larger reduction; skipping the current candidate is therefore always preferable to reverting the earlier, more beneficial one. 

B. Fused Dual-Batch Execution 

Motivation. After dynamic activation memory mitigation en-sures that the activation memory curve stays within GPU capacity, this step optimizes total execution time. The applied mitigation strategies increase the total execution time, because extra operators are introduced to delay the original operator execution. To address this problem, we analyze each pipeline scheduling point and find optimization opportunities when reordering the operators of adjacent micro batches is possible. During the steady phase of pipeline parallelism, each GPU simultaneously holds four types of operators: a set of forward operators F for the current forward batch, a set of backward operators B for the current backward batch, a set of activation offloading operators O for the previous forward batch, and a set of activation recovery (i.e., reload and recomputation) op-erators R for the next backward batch. The data dependencies among the same type of operators form a simple chain, while there are no data dependencies across different types, because they belong to different batches. There is an opportunity to refine execution orders from different types to achieve better overlapping between computation and communication streams. The optimization goal is to minimize overall execution time by planning an execution order of four types of operators. 

Formulation. We formulate this planning problem as a dy-namic programming (DP) problem. Let state F [i][ j][ k][ l] be the minimum execution time of the first i forward operators, the first j backward operators, the first k offloading operators and the first l recovery operators. The DP transfer equation can be formulated as follows:

Naively solving this DP problem could be expensive, as a single micro batch typically consumes only tens of milliseconds. Thus, we propose two optimizations to reduce the number of DP states and eliminate transfer costs: First, we observe that DP states could be compacted. There are many consecutive computation operators in a transformer block, splitting them into different states cannot provide more overlapping opportunities to reduce execution time. Therefore, we divide the original set F into several stages, splitting by the communication operators. And operators in the same stage are compacted into a single DP state. For example, an MoE transformer forward batch has more than 20 operators but only 4 stages, as there are only two all-to-all communication operators used by expert parallelism. This compaction strategy significantly reduces the number of DP states. Second, we find opportunities for memorizing the optimal DP transfer points. The operator sets are fully determined by the micro-batch memory budget described in the previous section, therefore we could store DP states keyed by a discretized budget value. Moreover, we find the memory budgets exhibit strong temporal locality. The pipeline phase repeats every Bw micro-batches, and MoE imbalance rates are stable for the majority of iterations. Most iterations hit the cache and skip algorithms entirely, reducing the amortized overhead to nearly zero.

Hardware. All evaluation is conducted on a cluster with our vendor’s GPU. The GPU has 480 TFLOPS peak performance of BF16 computation and 64 GB HBM. Each compute node has 8 GPUs, where intra-node GPU bandwidth is 400 GB/s and inter-node bandwidth is 400 Gbps × 4. There are 1536

Parallelism. At each scale, we use an automatic parallelization algorithm [18] to search hybrid parallelism strategies under the assumption of balanced MoE workload. For pipeline paral-lelism, interleaved 1F1B scheduling is used: the “VP” column in Table II denotes the number of layers per virtual pipeline stage. Baselines. We compare against two state-of-the-art training systems. Megatron-Kuai [11] is a training system for long-context dense models that features fine-grained activation recomputation and offloading. AdaPipe [10] is a training system for memory-efficient pipeline parallelism. It features adaptive recomputation and pipeline stage partitioning. Its optimization only targets dense models, and we find that adaptive pipeline partitioning is ineffective in the MoE training scenario. Only the adaptive recomputation part of AdaPipe is enabled in our evaluation. As discussed in §I, both baseline systems manage memory statically. We initialize each baseline with a memory strategy configured for balanced MoE load. When an out-of-memory crash occurs, we adjust the reduction strategy according to the observed imbalance rate and manually restart training. We find that imbalanced MoE token-to-expert distribution occurs in approximately 2.9% of iterations. D. Ablation Study 

Speedup Breakdown. To quantify the contribution of each op-timization, We progressively enable BaGuaLu-2’s components starting from the baseline configuration. Figure 11 shows the cumulative effect. Each optimization contributes a positive, compounding speedup. Static memory optimization (L1 →L2) provides a 1.16 × improvement by enabling fine-grained, composable mitigation strategies that replace coarse-grained layer-level policies. Dynamic activation memory mitigation (L2 →L3) adds a further 1.05 × by dynamically adapting the strategy degree to per-iteration memory pressure. Runtime overlap scheduling (L3 →L4) contributes an additional 1.13 ×

by hiding offload/reload and recomputation latency through the dual-batch interleaving. The combined effect of all three optimizations yields the full BaGuaLu-2 performance. 

Activation modeling accuracy. BaGuaLu-2’s runtime deci-sions depend on the accurate modeling of the actual memory footprint. We compare the predicted activation memory against measured values across multiple scales and parallelism con-figurations. BaGuaLu-2 achieves a mean prediction error of 

1.56% across all configurations, confirming that §IV faithfully depicts the memory behavior of MoE training activations. 

Runtime decision overhead. BaGuaLu-2 has three runtime components: dynamic memory budget assignment, activation mitigation strategy selection and DP-based batch scheduling. We find memory budgets exhibit strong temporal locality — the pipeline phase repeats every Bw micro-batches, and MoE imbalance rates are stable for the majority of iterations — so most iterations hit the cache and skip algorithms entirely, reducing the amortized overhead to near zero. The total runtime overhead is less than 10 ms per iteration, while per iteration training time is more than 18 seconds. VII. R ELATED WORK 

MoE Model Training Systems. Early systems for MoE training focus on coarse-grained MoE architectures, address-ing computation and communication bottlenecks separately. SmartMoE [18] and FlexMoE [21] improve expert parallelism strategies to mitigate computation load imbalance. Lina [20], FasterMoE [19] and Janus [24] optimize the all-to-all commu-nication that dispatches tokens to experts, while other work re-duces communication overhead through communication over-lapping [25]–[29]. However, these systems all overlook the memory pressure that arises during fine-grained MoE training, where dynamic expert routing causes activation memory to vary unpredictably across micro-batches. 

Memory-Efficient Training Systems. Reducing memory con-sumption during training has been studied extensively. Early work targets single-GPU settings through checkpointing [22] and offloading [23], [30], [31]. More recent systems address small-scale distributed training by optimizing memory usage for parameters and optimizer states [32], [33]. Another works specifically target activation memory, but assumes static com-putation graphs where activation sizes are known at compile time [10], [11], [34]–[40]. None of these accounts for the dynamic activation memory introduced by MoE routing, where each micro-batch may produce a different activation footprint depending on the runtime token-to-expert assignment. VIII. C ONCLUSION 

We present BaGuaLu-2, a large-scale MoE training sys-tem that transforms activation memory management from a static, one-time configuration choice into continuous, per-batch control. By combining fine-grained activation provisioning with overlapped execution, BaGuaLu-2 dynamically allocates exactly the activation memory each training batch requires, eliminating the over-provision vs. under-provision dilemma that plagues existing systems. BaGuaLu-2 scales to 12,288 GPUs on a model with 1040 billion parameters, sustaining over 2 EFlops at 35% MFU, with average throughput gains of 

1.14 × over Megatron-Kuai and 1.13 × over AdaPipe. IX. A CKNOWLEDGMENTS
