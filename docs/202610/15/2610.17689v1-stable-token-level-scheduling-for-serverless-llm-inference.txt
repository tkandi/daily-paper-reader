Abstract —Serverless inference is emerging as an efficient deployment model for Large Language Models (LLMs) due to its ability to elastically scale resources, improve GPU utiliza-tion through resource sharing, and reduce infrastructure costs. However, existing approaches primarily optimize time to first token (TTFT) while overlooking inter-token latency (ITL), a key determinant of user experience during response generation. We observe that LLM inference comprises a computation-intensive prefill stage and a bandwidth-bound decode stage, where admitting new requests can disrupt ongoing decoding and increase latency. To address this, we propose Token Window Pacing (TWP), a closed-loop scheduling framework that lever-ages runtime feedback from ITL, queue depth, and workload characteristics to regulate request admission at the token level instead of the batch level. TWP dynamically adjusts a self-regulating token window and incorporates chunk-based prefill to minimize interference from incoming requests. Experiments on realistic serverless workloads show that TWP delivers stable TTFT, significantly reduces latency spikes, lowers P99 tail latency, minimizes ITL variation, and improves throughput by up to 45% over ServerlessLLM and 58% over conventional sched-ulers. These results demonstrate that feedback-driven token-level scheduling enables stable, high-throughput serverless LLM inference without modifying the underlying model. 

Index Terms —Token Window Pacing, Serverless Schedul-ing, Inter-Token Latency, Time-To-First-Token, Dynamic Token Scheduling 

I. I NTRODUCTION 

Large language models (LLMs) are becoming popular for modern interactive applications such as conversational sys-tems, programming assistants, and search engines, where strict latency requirements make responsiveness a key component of user experience. To reduce the high cost of provisioning dedi-cated GPUs, many systems now rely on serverless inference, in which model instances are dynamically instantiated on demand and multiple tenants share a pooled GPU infrastructure under a pay-per-use model. It is cost-effective in that it allows service providers to optimize GPU usage via load sharing without incurring costs related to reserved capacity by end users. The downside, however, is that the practice introduces nontrivial scheduling problems that have yet to be adequately addressed in the LLM-serving literature. 

A. How LLM Inference Works 

Figure 1 illustrates the execution pipeline of LLM inference. Each request undergoes two phases: prefill and decode . During the prefill phase, the model processes the entire input prompt in a single forward pass. This step initializes the Key-Value Cache (KV-cache), which stores the attention state associated with prompt tokens and remains resident in GPU memory throughout the lifetime of the request. Prefill executes once per request and its cost scales with prompt length. After prefill , the request enters the decode phase, where output tokens are generated iteratively, one token at a time. Decode execution is synchronous across all active requests: the system cannot advance to the next decode step until the current step completes for every request in the batch. Consequently, the latency of a decode iteration depends on the aggregate workload of the active batch, making scheduling decisions highly consequential. Admitting a new request introduces an additional prefill operation that competes with ongoing decode execution for GPU resources. The resulting interference delays token generation for all active requests, increasing inter-token latency (ITL) system-wide. 

B. The Admission Control Gap 

Serverless workloads are inherently bursty, with production traces showing that invocation rates can fluctuate by multiple orders of magnitude over short time intervals, and that a small fraction of functions account for a disproportionate share of total traffic [1]. Such variability is particularly challenging in interactive applications, where request-rate spikes are common and can coincide across many tenants. In addition, cold-start rates exceeding 25% in a large fraction of deployments further amplify instability in request arrival patterns [2]. Under such circumstances, a scheduler without knowledge of the internal state of the decode engine may over-aggressively accept incoming requests during bursts, thus saturating the GPU above its efficient operating region. The result is poor efficiency in terms of serving requests, with an increase in inter-token latency (ITL), which is defined as the latency between two subsequent tokens sent to a user. This becomes a self-reinforcing issue because higher ITL leads to slower token creation rates. This leads to increased time required for the batch to be emptied. The recovery time becomes extended, and all the users within that session experience poor stream throughput during this entire process. C. Our Approach 

We propose TWP a scheduler that completes this feedback loop at token granularity. The core insight is that ITL, obtained at the end of every decode stage, directly and with no overhead indicates GPU decode pipeline congestion. ITL is a better indicator compared to queue depth, which can keep growing even when ITL values are low, and also more useful than KV-cache occupancy, which fails to reflect latency cost. By combining ITL and queue depth, as well as KV-cache occu-pancy in a proportional feedback controller, TWP controls a 

dynamic token window in order to ensure proactive overload prevention.

This section provides the background necessary to motivate the design of TWP. We first examine the cost and latency characteristics of LLM inference and the admission challenges that arise in shared serving environments. We then place TWP in the context of prior work on serverless scheduling and LLM serving, highlighting the gap addressed by our approach. 

A. Cost Structure, Latency Metrics, and Admission Hazards 

The introduction established that LLM inference has two phases and that the decode phase is synchronous across the batch. Here we look at the cost structure of each phase in more detail, define the two latency metrics that TWP optimises, and identify two distinct admission hazards that motivate the design. 

Prefill cost: Prefill is expensive and prompt-length-dependent: every input token attends over all preceding tokens, so the compute cost scales quadratically with prompt length. Its output — the KV-cache — occupies GPU memory propor-tional to prompt length from the moment of admission. A long prompt therefore consumes both a large burst of compute and a lasting block of memory the instant it enters the system. This is relevant for admission because both resources are shared with the ongoing decode work of already-active requests. 

Decode cost: Each decode step reads the full KV-cache of every active request and writes one new entry per re-quest. The dominant cost is memory bandwidth: loading KV-cache tensors from GPU high-bandwidth memory (HBM). Up to a saturation batch size B0, the GPU’s memory bus amortises this cost across requests and step time stays flat — batching is effectively free in this regime. Beyond B0,attention computation becomes the bottleneck and step time rises with each additional request, raising ITL for every active user simultaneously. This piecewise ost structure defines the operating region TWP aims to stay within. 

TTFT and ITL: In a serverless deployment, TTFT — the delay from request submission to the first output token — has three components: a cold-start penalty if no warm container is available (the model must be loaded from storage before inference can begin), followed by the prefill phase, followed by the first decode step. ITL governs the streaming experience thereafter. Formally:

The noisy-neighbour penalty: A second admission hazard arises at the moment a new request enters the system. Prefill issues a large, bursty memory operation: KV-cache entries for every input token must be written to HBM in the same step that the ongoing decode kernels are reading their own caches. This contention on the shared memory bus transiently raises ITL for all currently active requests — an effect that scales with prompt length and is entirely invisible to a scheduler that makes decisions only at arrival time. We call this the 

noisy-neighbour penalty . A long prompt admitted in one shot can temporarily double active users’ ITL. Spreading ingestion across multiple steps in fixed-size chunks bounds this penalty per step to a small fraction of the full-prompt cost, at a modest TTFT cost we derive in §iii.. 

B. The Serverless Scheduling Landscape 

We survey the existing work relevant to TWP, organised around the distinct problems each body of work addresses, and identify the gap that remains open. 

Cold-start reduction: Fu et al. [2] introduce Serverless-LLM, which optimizes checkpoint loading across DRAM and NVMe memory tiers to reduce cold-start latency by a factor of 10 to 200 times. It also implements live migration that only transfers token states between servers, making serverless LLM serving practically feasible. Building on this, Cui et al. [7] present TIDAL, a solution that enhances Function as a Service (FaaS) by overlapping model loading with early inference through weight-centric tracing and adaptive state forking. However, they note that CPU-bound initialization remains unaccelerated. Yu et al. [8] introduce λScale, whose 

λPipe binomial multicast pipeline constructs execution graphs across nodes during loading; the system is currently lim-ited to single-node memory capacity. Zhu et al. [9] reduce repeated loading by using Tangram, which shares tensor-level parameters within a unified GPU memory pool and employs affinity-aware scheduling. This approach incurs a slight throughput overhead due to on-demand key-value cache allocation. Lou et al. [10] optimize the process by overlapping model loading with container initialization through network-aware placement. Sui et al. [11] demonstrate that pre-warming alone is insufficient and propose opportunistic pre-loading when there is idle capacity. Additionally, Lou et al. [12] introduce universal GPU workers capable of pre-warming multiple models simultaneously. All of these strategies address the startup component cs i in Equation (1). Once a container is warmed up, the main challenge becomes regulating the decoding batch to maintain a low inference turn-around time (ITL). 

Continuous batching and memory management: 

Orca [3] introduces continuous batching, making the decode step the natural scheduling unit and eliminating padding waste—directly motivating TWP’s step-synchronous control. vLLM [4] adds PagedAttention, managing KV-cache in fixed-size pages to eliminate fragmentation; the resulting per-step occupancy measurement underpins TWP’s second admission guard. 

Chunked prefill and phase separation: SARATHI [13] and Sarathi-Serve [5] split prefill into fixed-size chunks merged with decode steps, substantially reducing the noisy-neighbour penalty. These establish the chunked admission mechanism TWP adopts, but neither connects observed ITL back to admission rate. Splitwise [14] separates prefill and decode onto dedicated hardware pools; TWP achieves phase-awareness within a single shared pool. 

SLO-aware and token-level scheduling: Bari et al. [15] use deadline-driven criticality scheduling for TTFT and time-between-token SLOs, but require known deadline targets and target single-instance deployments. TokenScale [16] proposes Token Velocity as a predictive autoscaling metric, reinforcing that token-level signals outperform request-level metrics for capacity decisions. LAPS-SD [17] combines Least-Attained-Service with SJF for speculative decoding, highlighting that output-length uncertainty is a fundamental scheduling chal-lenge shared with TWP. Han et al. [18] propose TALE, which dynamically adjusts chain-of-thought token budgets via zero-shot prompting or post-training internalisation; though targeting reasoning efficiency rather than serving infrastruc-ture, it reinforces that token counts carry actionable workload-intensity signals. 

Serverless scheduling, LoRA serving, and large-scale systems: Thompson et al. [19] derive competitive online scheduling algorithms for serverless systems with setup delays, staying within a (1 + ϵ) cost factor of optimal, but assume uniform costs and make no distinction between prefill and decode phases. Ni et al. [20] address multi-adapter cold-start with Predictive-LoRA, prefetching hot LoRA adapters via an LSTM predictor and eliminating fragmentation through page-based memory management, though accuracy degrades under dynamic patterns. Sui et al. [21] propose ServerlessLoRA, sharing model backbones across isolated functions via CUDA IPC with contention-aware batching and dynamic GPU of-floading, at the cost of duplicated CUDA context overhead. Hu et al. [22] present DeepServe, a production serverless platform with a microkernel serving engine and NPU-fork for fast weight transfer across nodes; specialised hardware interconnects are required and true zero-instance cold starts remain unsupported. 

Memory-constrained inference and adaptive batching: 

Alizadeh et al. [23] load only sparsity-selected weights from flash into DRAM using a low-rank predictor, with windowing and row-column bundling for throughput; the work reinforces that KV-cache and weight residency must be managed jointly, a principle TWP operationalises in its per-step memory guard. Ali et al. [24] propose BATCH, tying batch size to profiled latency targets for non-autoregressive serverless inference; the insight that batching decisions should be grounded in observed latency aligns with TWP, though BATCH uses static thresholds and ignores KV-cache dynamics and the prefill– decode distinction. 

The open gap: No existing system effectively closes the feedback loop between the observed decode-phase Inference Time Latency (ITL) and the request admission gate in a shared serverless Large Language Model (LLM) pool. DynamicBatch employs a static batch-size limit without mechanisms to pre-vent saturation before this limit is reached. ServerlessLLM’s rapid loading unintentionally leads to batch saturation by accepting requests faster than the decode phase can handle them. The root of the problem lies in the structure of the system: all existing schedulers make admission decisions at the moment a request arrives, without considering any information about the status of the current batch from the decode loop. Our system, TWP, addresses this issue by making admission decisions during the decode step, using the ITL measured in the previous step to inform these choices. III. ITL AS A CONGESTION SIGNAL 

We establish the formal and empirical case for ITL as the primary feedback signal in TWP. All characterisation in this section is derived from measurements on our experimental platform. 

A. Definition and User-Visible Meaning 

Definition 1 (Inter-Token Latency) . Let tk be the wall-clock time at which decode step k completes. The inter-token latency 

at step k is ℓk = tk − tk−1.

Because the decode loop is synchronous, every active re-quest experiences the same ℓk at each step. From a user’s perspective, ℓk is the gap between successive tokens in the response stream. A stable, low ℓ produces smooth streaming; a high or volatile ℓ produces visible stuttering regardless of how fast the total response eventually arrives. 

B. The ITL–Batch-Size Relationship 

The duration of a decode step is governed by either KV-cache transfers from GPU high-bandwidth memory (HBM) or attention computation. For small batches, memory transfers dominate and the GPU can load KV-caches for multiple requests without increasing total transfer time. Consequently, step duration remains constant at a minimum value ℓmin until the batch size reaches a saturation point B0.Beyond B0, attention computation becomes the bottleneck. Each additional request increases the computation required to process its KV-cache, causing step duration to grow approxi-mately linearly with batch size. The resulting ITL model is

C. Instability Without Admission Control 

At steady state, tokens arrive at rate λ ¯L and are processed at rate B∗/ℓ (B∗). For B∗ > B 0, the service rate satisfies 

B∗/ℓ (B∗) → 1/α as B∗ → ∞. Thus, the maximum achievable token processing rate is bounded by 1/α .When λ ¯L > 1/α , the token arrival rate exceeds the maxi-mum service rate. The backlog therefore grows continuously, implying that no finite steady-state batch size exists. In the absence of an explicit bound on token load, B∗ diverges without limit. Even when λ ¯L < 1/α , transient bursts can temporarily raise the effective arrival rate above 1/α . During such periods, the system enters the compute-bound regime, causing the active batch size to grow. Recovery occurs only after the excess queued requests are processed, which may require many decoding steps. As a result, all active users experience elevated ITL throughout the recovery period. Admission con-trol through a token window prevents unbounded batch growth and limits the duration and severity of these overload episodes. 

D. Why ITL Dominates Alternative Signals 

Queue depth reflects demand but not congestion. The queue can grow while Bt < B 0 and ITL remains at ℓmin . Throttling on queue depth alone would delay admission during periods where the system has available headroom. 

KV-cache occupancy reflects memory pressure but not compute pressure. A batch of many short-output requests may have high occupancy while still residing comfortably in the bandwidth-bound regime. Memory occupancy is a necessary guard against hard out-of-memory failures but is not sufficient as the sole control signal. 

ITL responds within one decode step to any change in Bt.It requires no additional measurement infrastructure: the step wall-clock time is already tracked by the serving engine as a standard bookkeeping value. It directly encodes the cost being imposed on every active user by the current batch composition. And from Equation (1), it is the quantity that both TTFT and streaming latency are built from — making it the single most actionable signal for an admission controller that cares about both metrics. The minimum ensures the system always keeps enough requests active to use available GPU parallelism; the maximum limits how far the window can expand during a quiet period, preserving headroom to absorb a subsequent burst without crossing B0.

TWP is implemented as a scheduling layer between the request queue and an existing LLM serving backend. At each decode step, it observes the step latency, active batch size, and KV-cache occupancy, updates the token window, and determines which queued requests to admit before the next step. The backend remains unchanged and continues to handle model execution and KV-cache management. As a result, TWP can be integrated into any serving framework that exposes a step-level decode interface, without modifications to model weights, kernels, or GPU execution primitives. TWP requires three deployment-time parameters. The ini-tial token window is set to H0 = B0 ¯L, where B0 is the mea-sured saturation batch size and ¯L is the expected mean output length. The control gain γ determines the responsiveness of the feedback controller, while the prefill chunk size C controls the trade-off between TTFT and decode interference. In our implementation, we use H0 = 400 tokens, γ = 0 .15 , and 

C = 64 tokens. These values are obtained through offline characterization and remain fixed throughout all experiments. TWP controls request admission, batching, and execution ordering, but does not modify the underlying model archi-tecture or execution stack. This design enables deployment on existing LLM serving systems with minimal integration effort. VI. E VALUATION 

We evaluate TWP against conventional scheduling policies and ServerlessLLM [2] to assess its ability to reduce latency while maintaining throughput under bursty workloads. 

A. Experimental Setup 

Implementation and Environment: TWP is implemented in Python as a scheduling layer integrated into a custom LLM serving pipeline supporting request-level and token-level scheduling. Experiments are conducted on NVIDIA Tesla V100 GPUs (32,GB) with CUDA 11.8. Unless otherwise stated, all results use a single GPU serving the Meta-Llama-3.2-3B model [25] in FP16 precision. Workload: Requests are generated from the GSM8K bench-mark [26]. Arrivals follow a Poisson process with rate λ = 18 

req/s over a 60-second interval, producing up to 250 requests per run. Prompt lengths are heterogeneous: 60% short (30–80 tokens), 30% medium (120–250 tokens), and 10% long (350– 512 tokens). The saturation batch size is B0 = 8 .

Baselines: We compare TWP against representative scheduling policies spanning classical queueing, batching, and serverless execution strategies. ServerlessLLM is reim-plemented within our runtime to ensure a fair comparison under identical resource and execution conditions. Table II summarizes the evaluated schedulers.

This work presented (TWP), a feedback-driven scheduling layer for serverless LLM inference that regulates request admission at decoding-step granularity using only runtime signals available in existing serving systems. TWP operates without modifying model architectures, attention kernels, KV-cache management, or GPU execution primitives, making it broadly deployable. Experiments on Poisson-driven workloads in a shared serverless environment show that TWP consistently outper-forms existing scheduling policies and ServerlessLLM. It achieves up to 58% higher throughput, reduces tail TTFT by 15–20%, and provides the lowest inter-token latency variability among all evaluated methods.
