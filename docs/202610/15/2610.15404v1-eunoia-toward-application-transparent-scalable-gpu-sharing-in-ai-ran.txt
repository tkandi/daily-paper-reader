# Eunoia: Toward Application-Transparent, Scalable GPU Sharing in AI-RAN 

# Zongshen Wu, Marko Milenković, Jiarong Xing, Rahman Doost-Mohammady 

Rice University Houston, TX, US 

Abstract 

The AI-RAN paradigm makes the next-generation cellular network more versatile by co-locating AI and RAN work-loads on the same commodity hardware. While the GPU is a promising platform for AI-RAN realization, a generic con-current AI application interferes with the latency-sensitive RAN on GPU compute resources. In this paper, we propose Eunoia, a dynamic real-time AI-RAN GPU scheduler that is transparent to both AI applications and the RAN work-load and operates at the granularity level of the RAN slot. We deploy Eunoia onto NVIDIA Aerial AI-RAN and evalu-ate Eunoia on both an over-the-air 5G private network and an emulated multi-cell network. We demonstrate that in a 27-cell AI-RAN, Eunoia keeps the RAN’s uplink 𝑃 99 latency under 3 ms while delivering higher AI performance than other RAN-safe static partitioning methods. 

1 Introduction 

The convergence of cellular networks and artificial intelli-gence (AI) is a defining force behind 6G, where intelligence moves into the last mile of connectivity, within low-latency reach of wireless users and enabling novel verticals. This paradigm, coined AI-RAN [12], equips the radio access net-work (RAN) with the ability to host edge AI models, includ-ing machine learning models and large foundation models, alongside the RAN itself. Three use cases are outlined by the AI-RAN alliance [1]: (1) AI for the RAN, e.g., real-time control for scheduling, traffic steering, and sub-millisecond inference loops inside the distributed unit (DU) [6, 11]; (2) AI 

on the RAN that uses the same infrastructure to serve large language models (LLMs), video analytics, and distributed Physical AI workloads to the RAN users [26]; (3) AI and 

RAN that runs non-RAN related AI models alongside RAN. The use of data-center-grade GPUs for high-performance RAN baseband processing, realized by NVIDIA Aerial [10, 16], makes the AI-RAN vision practical. Aerial is capable of running the complete 5G physical layer, the O-DU-Low, for tens of 5G cells on a single Hopper or Blackwell GPU and can achieve gigabit-per-second network throughput on par with other advanced commercial cellular products. Recent studies have characterized the performance and efficiency of this approach [18, 23]. used for running AI model inference, not only placing in-ference just one hop away from the RAN users, but also considerably improving the economics of AI-RAN. However, co-locating these workloads on the same GPU is not trivial. The RAN must deliver carrier-grade availability with per-slot processing deadlines at the DU. Uplink decoding and downlink encoding for every slot must finish within a few milliseconds; otherwise HARQ retransmissions accumulate, the user equipment (UEs) lose synchronization, and cells drop. GPU resource starvation at that time scale, even briefly, is unacceptable to an operator. The current widely used solution for co-locating sensi-tive GPU workloads is through hardware-supported static partitioning. NVIDIA offers Multi-Instance GPU (MIG) [15] that statically partitions the GPU into fixed slices at the hardware level based on a set of predefined configurations. Thus, each partition has to be provisioned for the worst case, which leads to underutilized resources in lower load sce-narios. Multi-Process Service (MPS) [14] is a finer-grained solution, but only enforces a per-process upper bound on streaming multi-processor (SM) usage, and does not carry arXiv:2610.15404v1 [eess.SP] 11 Oct 2026 any notion of priority or active provisioning [3]. Both MIG and MPS solutions force the operator to choose between RAN reliability and AI throughput, and the choice must be re-made for every change in cell count, bandwidth, or AI model mix. The Green Context is another recent feature introduced by NVIDIA that allow SM partitioning with sub-process granularity. However, they require modifications to each application code, which makes them difficult to use in a heterogeneous AI-RAN application environment. Compute sharing for virtualized RAN (vRAN) has been explored on CPUs [7, 8]. CPU vRAN sharing relies on core pinning and OS scheduling primitives which do not directly translate to GPUs. None of them addresses the AI-RAN set-ting directly. YinYangRAN [19] predicts the traffic patterns and adjusts the MPS management through orchestration for AI-RAN. However, reconfiguring MPS settings is not real-time (>100 ms) and requires workload fallback on CPU during the reconfiguration. Recent work has studied fine-grained GPU sharing among AI workloads, given the large inefficiencies in AI data centers [4, 22]. However, they oper-ate at the granularity of kernels or inference requests, target latencies of tens of milliseconds, and treat all tenants as peers. AI-RAN is posing a more challenging problem that existing methods, where the resource demand for RAN workloads changes at the slot-level (sub-millisecond) granularity and if not properly handled, it will cause RAN crashes or signifi-cant performance degradation. Therefore, there is a need for a GPU sharing framework for AI-RAN that can track RAN GPU resource demand at sub-millisecond granularity, while efficiently allocating every spare SM to the AI workloads. Weaver [25] proposes a framework for GPU sharing between RAN and Foundation model training. However, it uses Green Context as GPU sharing mechanism, only considers RAN LDPC decoding (look-aside RAN acceleration) on the GPU and does not generalize to many concurrent cells. In this paper, we present our vision for fine-grained, appli-cation-transparent GPU sharing that scales to diverse AI-RAN workloads. Because AI-RAN can host a wide range of AI applications, it requires a versatile execution framework that can co-locate diverse AI models with equally diverse RAN workloads, such as distributed units (DUs) serving cells with different configurations. We argue that such a frame-work must satisfy three requirements. (1) Transparency: it should not require modifications to RAN or AI application code, and should instead infer GPU resource demands and priorities through existing or lightweight interfaces. (2) Fine granularity in time and space: it should infer SM demand at sub-millisecond timescales, matching RAN slot durations, and allocate resources at the granularity of a few SMs. (3) 

Scalability: current data-center GPUs can run the entire PHY for tens of cells, each with a different configuration (e.g., number of antennas or bandwidth), while concurrently serv-ing several AI models through spatial or temporal sharing. The framework must therefore scale to such deployments while ensuring that RAN workloads consistently meet their processing deadlines. As a first step towards this vision, we design and prototype Eunoia, which addresses the RAN side of these requirements. Eunoia is transparent to the RAN: it reads real-time RAN metrics through the RIC and uses them to infer the DU’s SM demand without modifying RAN code. It reallocates SMs at sub-millisecond timescales and at a single TPC granularity, and it scales across many cells and varying traffic loads. Our key insight is that the GPU demand of the RAN is a function of RAN state: the number of active cells and UEs, per-cell uplink and downlink throughput, modulation and coding scheme, physical resource block allocation, and MIMO layers. All of these are observable at slot-level granularity from the O-DU through standard interfaces such as FAPI [21], and they are known before the corresponding GPU kernels launch. A design block diagram of Eunoia is illustrated in Fig. 1 We evaluate Eunoia with TimelyLLM [13] as a co-located AI workload. Extending transparency to the AI side remains an open challenge: when multiple AI models share the GPU, with varying levels of priority with respect to the RAN, the framework must decide how to prioritize among them and through what interface those models should express their requirements. We discuss these open questions in §5. 

2 Background and Motivation 2.1 Background 

AI-RAN. AI-RAN paradigm initiates the leverage on AI applications for RANs and vice versa. Pioneer work such as Agora [5], Nuberu [8], and Megastation [24] provide ap-proaches to support RAN on commodity hardware. Recent work like Concordia [7], EdgeRIC [11], ETHOS [23], and TimelyLLM [13] shed light on the AI-RAN framework de-sign with paragon AI applications. 

GPU Architecture. NVIDIA GPUs consist of different en-gines, with the major one being the Compute/Graphics En-gine. The Compute/Graphics Engine is then subdivided into General Processing Clusters (GPCs). A GPC is comprised of multiple Texture Processing Clusters (TPCs), which contain two SMs each. A block is scheduled to one SM for execution, and one kernel from the AI application consists of multiple blocks. 

GPU resource partition & scheduling. NVIDIA provides its official GPU resource partition tools, including MIG [15] and MPS [14]. Meanwhile, other GPU resource partition and scheduling methods have emerged, typically for AI work-loads like Deep Neural Network (DNN) and LLM. libsmc-trl [2, 3] proposes a light-weight disaggregated run-time SM Eunoia: Toward Application-Transparent, Scalable GPU Sharing in AI-RAN 

partition method for CUDA process and stream. Orion [22] arranges the order of DNN kernels regarding their offline trained GPU usage pattern for scheduling. Reef [9] uses preemption to schedule the DNN workloads. LithOS [4] at-omizes the kernels to alleviate head-of-line blocking for TPC scheduling with resizing.

2.2 Challenge: Avoiding resource interference between AI workloads and RAN 

We conduct experiments with an end-to-end 5G network set up in our lab where the NVIDIA Aerial RAN stack is running on a GH200 server with a Foxconn O-RU and an Amarisoft UE emulator. Through the UE emulator, we connect 4 UEs to the network, while simultaneously running TimelyLLM, a low-latency LLM serving system for edge robotic control. Fig. 2 shows the various metrics for each process when run 1) without any constraint (unmanaged), and 2) with Eunoia as the GPU management framework. In the unmanaged case, the RAN simply stalls at 120 seconds while using Eunoia, the RAN stably runs with the AI workload. TimelyLLM occupies the majority of SMs (Fig. 2(a)) and thus in the unmanaged case the uplink processing latency of the RAN (Fig. 2(b)) crosses the 3ms deadline and the number of PHY errors sig-nificantly increases (Fig. 2(c)), which causes the RAN to crash. Eunoia avoids this by carefully monitoring the RAN param-eters and inferring the SM usage and carefully allocating them to the RAN while allowing the rest of the SMs to be used by TimelyLLM. 

3 Eunoia System Design 

In this section, we present Eunoia system design, aligning with the three requirements for GPU sharing, fine granularity, scalability, and transparency . Eunoia consists of three main modules, shown in Fig. 1, RAN Monitor, SM Predictor, and SM Allocator. 

3.1 Eunoia RAN Monitor 

We use an extension of a shared memory-based interface de-veloped in [23] to develop the RAN monitor module. Through this interface, we develop the RAN Monitor module with the O-DU as a dApp [6] supporting slot-level profiling granular-ity with sub-millisecond overhead. We measure a variety of RAN metrics, including cell-level parameters such as number of active cells and their respective UEs, and per-user metrics (e.g., MCS, PRB, throughput, TBS). The O-DU-Low running on the GPU supports multiple RAN cells within one process which allows monitoring all cells simultaneously through the same interface. Separately, the RAN Monitor module also profiles the GPU compute resource usage using Nsight [17] with sub-millisecond slot level granularity. Since Nsight is an offline profiling tool, we will use it for fine-granularity SM usage profiling and offline training incorporating both wireless and GPU usage metrics. 

3.2 Eunoia SM Predictor 

The predictor is required to support versatile multi-cell cases with scalability, which is challenging since the metrics dimen-sion varies along the cell numbers. Therefore, SM Predictor aggregates the input over cells, in order to serve different cell counts, UE loads, and TDD patterns without retraining. The SM Predictor module predicts the RAN’s per-slot SM demand from the metrics exposed by the RAN Monitor module and passes it to the SM Allocator module. It is an ensemble of four multi-layer perceptrons (3 hidden layers of 128 ReLU units each), whose predictions are averaged. Each slot’s in-puts are normalized cell-aggregated DL and UL load metrics: PRB×layers, transport-block bytes and count, the number of active cells, and for UL also the MCS-weighted load and the largest per-cell load. They are taken over a short window of slots around the target slot, together with their 20-slot run-ning means, the TDD slot position, and the cell configuration (cell count and DMRS symbols). The networks are trained to predict the 99.8th percentile of the next slot SM usage instead of the mean as a conservative measure for RAN safety. The training labels are per-slot SM usage measured with Nsight Systems on emulated, but fully realistic, workloads. At run time, the predictor needs only the wireless metrics. Inference is implemented in C on the CPU, which provides minimal overhead, and the modules exchange data through the dApp interface. 

3.3 Eunoia SM Allocator 

The SM Allocator should be transparent to both the RAN stack and AI applications for practicality. The SM Alloca-tor converts the SM prediction into TPC mask indexes, and then applies these indexes accessibility through libsmctrl [2]. The TPC mask limits the accessible GPU SMs of a kernel launch at run time. The SM Allocator controls the GPU SM accessibility for both the RAN process and the AI application, through their individual TPC masks. Therefore, the RAN pro-cess and the AI application utilize their own isolated shares on the GPU SM resource, avoiding SM contentions. In this case, the SM Allocator module dynamically manages the hardware SM partition between the latency-sensitive RAN process and the AI application, with per-slot time granu-larity and per-TPC GPU spatial granularity. 4.2 Scheduling Unseen OTA and Multi-cell Scenarios 

Unseen OTA AI-RAN Scenario: We deploy Eunoia on the private 5G network setup and demonstrate a single-cell AI-RAN case. The AI-RAN serves 4 OTA UEs in the cell and concurrently runs TimelyLLM. The UEs run fluctuated bi-directional traffic flows, and the TimelyLLM uses a 70B pa-rameter Llama model. This scenario is demonstrated in Fig. 2, the comparison between Eunoia and no GPU SM manage-ment. Therefore we omit the description here for brevity. 

Unseen Multi-cell AI-RAN Scenario: We further scale up the test cases to multiple cells accelerated by the GPU for the evaluation. We use TestMAC and RU emulator to build scaled-up multi-cell unseen scenarios for the testing, sup-porting up to 27 concurrent cells, considering the limitation on building OTA networks with such number of cells. Fig. 4 shows a dynamic test case of the AI-RAN running up to 27 cells and the TimelyLLM robotic application concurrently. There are up to 138 UEs with DL traffic and up to 61 UEs with UL traffic in this fluctuated scenario. The TimelyLLM runs the Llama-3.1-8B (AWQ-INT4) model. We compare Eunoia with MPS clients acquiring static SM partition according to their priorities on these two processes. Eunoia applies the generalized model with the weights trained in §4.1. Corre-spondingly, we evaluate two types of SM partition for MPS clients, one prioritizing the RAN process, the other prefer-ring TimelyLLM. Fig. 4(a) demonstrates the SM scheduling patterns of Eunoia and static MPS client partition. Eunoia schedules the SM budget adaptively, according to the predic-tion. The RAN prioritized partition assigns 108 SMs to the RAN and 24 SMs to TimelyLLM. Meanwhile, the AI prior-itized partition assigns 52 SMs to the RAN and 80 SMs to TimelyLLM. Fig. 4(b) shows that Eunoia and the static par-tition with RAN priority provide almost the same goodput for the UL process. In contrast, the static partition with AI priority noticeably jeopardizes the RAN UL goodput. Fig. 4(c) shows that the static MPS client partition prioritizing AI in-creases the UL latency significantly, which severely harms the RAN stability. Fig. 4(d) shows the Time-to-First-Action (TTFA) comparison of TimelyLLM. The static MPS client par-tition with AI priority severely jeopardizes the RAN stability to reach low TTFA, which is not practical. Consequently, Eunoia provides lower TTFA for TimelyLLM with protection on RAN latency, compared with the static partition with RAN priority.

5 Conclusion and Future Works 

In this paper, we propose Eunoia, an application-transparent scalable AI-RAN GPU SM scheduler that coordinates both RAN process and AI application dynamically in real time. Eunoia characterizes the AI-RAN GPU SM usage, predicts the next-slot SM usage, and allocates the SM resource to both RAN and AI. We demonstrate the effectiveness of Eunoia using OTA AI-RAN and multi-cell AI-RAN setup co-located with TimelyLLM. Eunoia provides significant advantage over the static MPS client SM partition on AI-RAN management. However, it remains an early prototype. Eunoia is a first step toward a general AI-RAN GPU sharing framework, which must support the full range of AI-RAN use cases. In AI-on-RAN, AI workloads serve RAN users and must meet their own quality-of-service and latency requirements, so the framework must transparently infer each application’s requirements and arbitrate among multiple co-located mod-els. In AI-for-RAN, AI models directly drive RAN decisions in real time, either within the PHY pipeline or through disag-gregated interfaces such as the real-time RIC; the framework must therefore allocate resources to these models at the same priority as RAN processing, ensuring RAN stability and per-formance. Our future work will extend Eunoia to support these use cases.
