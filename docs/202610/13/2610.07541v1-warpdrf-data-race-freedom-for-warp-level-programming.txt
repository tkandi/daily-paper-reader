## Abstract 

Warp primitives such as tensor core operations, shuffles, re-ductions, and barriers are critical to high-performance GPU kernels, and every major GPU language supports some set of them. The threads that participate in a primitive, and therefore synchronize, are determined dynamically by how threads diverge and reconverge, and by intra-warp schedul-ing such as independent thread scheduling. In practice, many high-performance kernels use these primitives and behave as expected, following an intuitive but unwritten data-race-freedom contract that has never been stated precisely or empirically tested. We present WarpDRF, the first abstract warp program-ming model to make this contract precise, with participation rules parameterized by reconvergence guarantees and per-primitive requirements so that instantiations match different GPU languages. We prove (formalized in Rocq) that a kernel satisfying WarpDRF executes every warp primitive with the participants the reference semantics assigns and produces the same results, so a programmer can reason in the ref-erence semantics alone. We implement the model in MLIR with a reference interpreter and fuzz 10K conformance tests for each of three configurations across CUDA, HIP, HLSL, Metal, and SPIR-V on 16 device and backend pairs; at least one WarpDRF configuration describes each, with CUDA hon-oring the strictly weakest configuration. Finally, we extend Faial, a static data-race analyzer for CUDA, into the first DRF checker for an empirically validated warp model, and apply it to llama.cpp, where most kernels that use warp primitives already satisfy the contract, but three contain previously unknown data races, showing the need for tools that check it.

1.1 WarpDRF: Contract, Conformance, Code 

We present WarpDRF, a data-race-freedom contract for warp programming. WarpDRF is a simplified execution model that hides low-level detail such as lockstep execution and inde-pendent thread scheduling, replacing it with two dependent conditions on memory ordering and warp primitive partici-pation. We do not capture any one language in full, but target a pragmatic subset that maps straightforwardly onto CUDA, HIP, HLSL, Metal, and SPIR-V. We build an executable model in MLIR and test 16 device and backend pairs against it, with CUDA honoring the weakest configuration. We then pro-duce the first static checker for an empirically validated warp programming model and apply it to the performance-critical CUDA kernels of llama.cpp, a widely used open-source LLM inference engine, where most kernels already satisfy the contract and three contain previously unknown data race. 

Defining the contract. We define WarpDRF over a delib-erately small language: threads grouped into warps, ordinary memory accesses, warp primitives, and control flow whose conditions may differ across threads. Warp primitives oper-ate over participants, the threads that execute them together, and optionally order their memory accesses. A kernel satisfies WarpDRF when two conditions hold in its reference execution for every input. First, conflicting memory accesses must be ordered, and warp primitives can optionally be set to provide that ordering. Second, every dynamic execution of a warp primitive, which we call an instance, has an unambiguous set of participants, ranging from all threads in the warp to any valid subset. The condi-tions are dependent, since a primitive orders memory only for its participants. Figure 1 highlights a real llama.cpp ker-nel in which insufficient synchronization causes a bug, and participation assumptions are non-portable. Each language instantiates its own configuration of Warp-DRF by specifying when threads reconverge and what else it requires of a primitive’s participants. From those choices we derive when a kernel satisfies the contract. We prove a guarantee for the contract: on any conforming system, a kernel that satisfies WarpDRF forms the same participant set at every primitive and computes the same results as the reference execution, so a programmer can reason in the ref-erence semantics alone. We formalize the proof in Rocq over SIMT-Step’s synchronous subgroup operations ( SSO ) [10], in which threads advance independently and a primitive waits for every thread that may still reach it. 

Testing implementations against the contract. Speci-fications say little about warp execution, so we test whether implementations respect the contract. WarpDRF gives each test one expected result, allowing its reference interpreter to serve as the oracle. Across 10K tests for each of three configurations on 16 de-vice and backend pairs, every language conforms to at least one of them. Empirically, CUDA honors the strictly weakest configuration, and thus that configuration is portable across every system we tested. In it, warp primitives are valid only when every thread in the warp executes them, ruling out non-uniform participation. Some languages additionally de-fine partial-participation behavior, but those guarantees are specific to the language and execution mode. 

Checking kernels against the contract. We build a checker for the CUDA configuration by extending Faial, a static data-race analyzer that previously had no support for warp prim-itives [11]. We run it over llama.cpp and check the 95 ker-nels that use warp primitives. ## 2 Background 

2.1 Execution Hierarchy and Synchronization Scopes 

A GPU kernel executes a grid of logical threads organized into hierarchical groups. CUDA and HIP call the larger group a thread block , Metal calls it a threadgroup , and SPIR-V calls it a workgroup . Implementations partition each group into tightly coupled execution groups: CUDA uses warps , AMD hardware uses wavefronts , Metal uses SIMD-groups , and SPIR-V uses subgroups [2, 6, 24, 39]. We use block and warp for these concepts. We use warp primitive as an umbrella term for two categories. A warp collective , such as a shuffle, ballot, reduction, or cooperative matrix instruction, exchanges or combines values across threads. A warp barrier waits for participating threads and may provide warp-scoped memory ordering. The execution hierarchy determines the scope of com-munication and synchronization. Registers are private to a thread, shared or workgroup memory is addressable within a block, and global memory is addressable device-wide. A block barrier such as __syncthreads() coordinates the threads in one block and orders their relevant memory accesses. A memory-ordering warp barrier such as __syncwarp() has narrower scope: it coordinates and orders accesses only among threads of one warp. It cannot establish ordering between different warps, even when they belong to the same block [24, 39]. Collective participation and memory ordering are separate effects. Shuffles, ballots, and reductions in CUDA and HIP, their Metal SIMD-group counterparts, and SPIR-V group-nonuniform operations exchange or aggregate register val-ues but do not by themselves order accesses to shared or workgroup memory. In particular, the _sync suffix on CUDA and HIP collectives identifies participating threads; it does not turn the collective into a memory barrier [1, 5, 24, 39]. Memory ordering instead requires an explicit barrier carry-ing the appropriate scope and memory semantics. SPIR-V makes this separation syntactic. Group-nonuniform opera-tions carry only an execution scope, while control barriers also carry a memory scope and memory semantics. Simi-larly, Metal uses flags to select the memory classes ordered by a SIMD-group barrier. WarpDRF therefore treats these warp collectives as participation events rather than mem-ory boundaries. Only barriers with documented memory semantics provide scoped memory ordering. 

2.2 Divergence and Collective Participation 

Threads diverge when a thread-dependent branch or loop sends them along different dynamic control-flow paths. An implementation may serialize those paths, predicate instruc-tions, allow threads to progress independently, or combine these techniques. Reconvergence describes when the threads resume joint execution, but GPU languages provide different guarantees about where this occurs. SPIR-V identifies struc-tured merge points, and a shader that declares the Maximally ReconvergesKHR execution mode requires threads to rejoin at them as early as the program structure allows, whereas general CUDA does not promise an analogous rejoining at arbitrary source-level joins [24, 39]. SIMT-Step formalizes these alternatives using dynamic blocks [10]. Table 1 summarizes how each API determines the partici-pants of a warp primitive under divergent control flow. All four APIs support complete-group execution but differ on partial participation. Section 3.4 represents these differ-ences as target configurations. One source-level warp primitive may execute multiple times, for example when it appears in a loop or a repeated function call. We call each execution a primitive instance .Each instance has its own participant set, and a collective’s result depends on both those participants and the values they supply. Threads reaching the same source location through different loop iterations or calls therefore need not belong to the same instance. Section 3.2 formalizes these instances and their participant sets. Cooperative matrix operations make the full-group re-quirement explicit: CUDA WMMA requires all threads in a warp to execute each operation, while SPIR-V requires all invocations in the cooperative-matrix scope to be active or none [24, 39]. Neither specification assigns portable se-mantics to execution by a proper subset, which motivates WarpDRF’s fully convergent contract. 2.3 Why Memory DRF Is Insufficient 

Two ordinary memory accesses conflict when they touch the same location and at least one is a write. A conflicting pair is a data race unless one access happens before the other. To construct this relation, a DRF model begins with the synchronization operations in an execution and the ordering that each one provides. For example, a block barrier is a block-scoped synchronization operation by definition, so it can order accesses by threads in that block. GPU DRF models account for the hierarchy by restricting such ordering to scopes such as a workgroup or device [11, 19]. Warp primitives complicate this starting point. Unlike a block barrier, a warp primitive may execute under divergent control flow, and any coordination or memory ordering ap-plies only to threads that execute it together. A memory-race analysis must therefore determine the group before using a warp primitive to order accesses. ## 3 The WarpDRF Contract 

WarpDRF retains the classic data-race-freedom argument: programmers use high-level synchronization to order con-flicting memory accesses rather than reason about low-level execution schedules [3]. What this work adds is a definition of that synchronization. Classic models take their synchro-nization operations as given: a lock or a block barrier is a named operation whose ordering rules are stated in advance. For a warp primitive, which calls make up a single operation is in question, because any coordination or memory ordering applies only to threads that execute it together. WarpDRF therefore fixes that grouping before using it. Its reference semantics identifies the threads that execute each primitive together, which makes participation predictable under divergent control flow. Each language then instanti-ates the contract: from its specification, such as SPIR-V’s maximal reconvergence, we derive which participant groups that language defines. Once those groups are fixed, order-ing conflicting accesses is the classic argument. Language specifications are often informal, so these derivations are best-effort. In Section 4 we design a conformance testing methodology and show that some variant of them holds across every language and device we tested.

Reference semantics. We adopt the bulk-synchronous, block-level semantics used by earlier GPU analysis tools [8, 12, 32]: one thread runs until it reaches a barrier, then another runs until it reaches a barrier, and the barrier is released once every thread has arrived. There is no interleaving, only a sequentialized execution of barrier intervals. WarpDRF derives participation from control flow rather than from a declaration and extends this semantics to warps by replacing block barriers with the participants of a warp primitive. The difficulty is that, unlike a block barrier, a warp primi-tive admits partial participation. Prior work describes cor-rect use of block barriers with notions such as textual align-ment [21], which asks that every thread reach the same bar-rier in the same loop iteration. To extend that idea to warps we borrow dynamic basic blocks [10], which lift SPIR-V’s no-tion of a dynamic instruction instance [23] to a basic block: each execution of a basic block creates a new dynamic block, and a dynamic block is executed by a group of threads rather than by one. The entry point of the program is a dynamic block executed by all threads, and a branch creates dynamic blocks executed by the threads that take the same path. Dynamic blocks give us the machinery to define participa-tion. If a warp primitive occurs in a dynamic block executed by the thread set 𝑇 , and 𝐶 permits that primitive to occur there, then its participants are 𝑇 . Distinct loop iterations and repeated calls produce distinct dynamic blocks, so threads that reach the same source location by different paths are not grouped automatically. Section 4.4 tests this behavior. This extends the bulk-synchronous semantics of earlier GPU analyses [8, 32]: SIMT-Step’s dynamic blocks [10] de-termine each warp primitive’s group instead of assuming that every synchronization operation has a fixed group. The reference semantics therefore picks threads in turn and runs each until it reaches a warp primitive, updating the set of dynamic blocks as it goes. A primitive is released once all of its participants have arrived, which the semantics cannot determine until the paths of the remaining threads are resolved. Threads are picked in a fixed order, so a kernel has exactly one reference execution for a given input. 

3.2 The Contract 

WarpDRF states its conditions over the reference semantics rather than over the executions a target system may produce. Classic DRF is stated the same way: a program is data-race-free if no sequentially consistent execution has a race, and a guarantee then transfers that reasoning to real implemen-tations. Both conditions are properties of the kernel. First, conflicting memory accesses must be ordered. Second, every warp primitive must run with a group that the configuration 

𝐶 guarantees. The second condition is new. Without it a kernel could rely on a grouping that 𝐶 leaves open, and a target system free to group threads differently would change either the memory ordering or the result of a primitive. 3.3 The Guarantee 

The guarantee is the classic DRF one [3]: a kernel that satis-fies WarpDRF produces the same reads and the same final memory on a target system as it does in the reference seman-tics, so a programmer can reason in the reference semantics alone. Earlier GPU semantics establish analogous agreement between lockstep and interleaving executions for race-free kernels [12, 27]. The novel component of WarpDRF is that participation must be settled before the memory argument can run. A target system is conforming when it behaves as its config-uration 𝐶 describes, does not let a primitive instance take effect until every thread that may still reach it has arrived or WarpDRF: The Unwritten Contract of GPU Warp Programming 

taken a path that excludes it, provides the ordinary DRF guar-antee with warp primitives supplying the synchronization edges among their participants, and preserves the specified behavior of operations under compilation. The last two are standard. 

Theorem 3.1 (WarpDRF guarantee) . If a kernel satisfies WarpDRF for configuration 𝐶 , then on a conforming target system it executes each warp primitive with the participants that the reference semantics assigns, and produces the same reads and the same final memory as the reference execution. 

The theorem does not require every participant group to be a complete warp. If 𝐶 enables maximal reconvergence in SPIR-V, the theorem covers the partial groups guaranteed by that mode, provided the reference semantics determines those groups. 

Instantiating conformance. Theorem 3.1 is stated against conformance, a property we require of a target, not one we establish. Before outlining a proof we therefore fix a base semantics, instantiating conformance with a concrete warp execution model. SIMT-Step provides a family of such mod-els for a single warp, totally ordered by strength, where a stronger model restricts when a primitive may execute and therefore admits fewer executions [10]. We examine two members of this family. The first is too weak to support WarpDRF, and the next strongest is sufficient. Both use the same memory model, which we deliberately make weak. Synchronous subgroup operations. The next strongest model is synchronous subgroup operations ( SSO ). An in-stance executes only when every thread that may still reach it is already waiting there. Deciding which threads those are is the delicate part of the semantics: the test inspects both arms of an unresolved branch and the relevant loop iterations, and it does not predict the result of a future read. The rule constrains only the moment at which a primitive ex-ecutes. Between primitives, threads advance independently and in any order, so SSO is far weaker than lockstep and admits the fine-grained interleaving that independent thread scheduling exposes. SSO is nonetheless strong enough to support WarpDRF, and it remains strong enough under de-layed visibility.

Proof outline. Fix a finished reference execution for the in-put, which condition 1 makes memory-data-race-free. The argument matches any SSO execution with delayed visibility against it, in two parts. The first part rearranges reference steps, which is needed because SSO lets threads advance in any order while the ref-erence fixes one. An action enabled in a state remains enabled after a different action runs, because a thread excluded from an instance cannot become one of its participants later. Two Zheyuan Chen, Simon Kagle, Tiago Cogumbreiro, and Tyler Sorensen 

adjacent independent actions can then be exchanged without changing any recorded event, where reference memory DRF rules out the case that would otherwise block the exchange, a conflicting pair of accesses with nothing between them to order it. Together these move any action enabled at the start to the front, so any finite target prefix can be matched by a permutation of the reference execution. The second part relates delayed visibility to the reference memory, in which a write takes effect at once. Let logical memory be the result of applying every pending write to shared memory in issue order. We induct over target steps, maintaining that the two executions agree on thread code and local values, that logical memory agrees with reference memory at every address, and that all pending writes to one address belong to a single thread. The key fact is that a pend-ing write cannot conflict with another thread’s access before its author participates in a memory-ordering primitive, and this follows from reference DRF alone. Read agreement there-fore follows from the reference being race-free, and we never assume that the target is race-free. Primitive readiness, par-ticipants, and arguments depend only on thread code and local values, so they agree as well, and the joint step returns the same result to each participant. The two parts combine as follows. No target execution races, because its events match those of a prefix of a memory-DRF reference execution, so none aborts. The waiting rule gives each instance the participants the reference assigns, which condition 2 places among the groups 𝐶 guarantees. Publishing the remaining pending writes at termination makes the final memories agree. Every terminating SSO 

execution therefore agrees with the reference on the partici-pants of each instance, the reads of each thread, and the final memory, which establishes the theorem. 

3.4 Instantiating Configurations 

The contract does not change from one target system to another; the configuration does. Two choices dominate an instantiation. One is per primitive: which operations or-der memory among their participants, and which require the complete warp. The other is reconvergence: which join points bring threads back together, and therefore which divergent regions may contain a primitive that runs with a partial group. Table 1 summarizes these choices for the APIs studied here, and Section 2.1 describes their memory-ordering rules. 

SPIR-V. Our partially convergent SPIR-V configuration requires an entry point to declare the optional Maximally ReconvergesKHR execution mode. For such an entry point, SPIR-V requires invocations to reconverge according to the extension’s structured rules [22]. These rules fix selection and loop merges as well as loop continue targets. OpSwitch 

retains additional freedom: invocations with the same selec-tor remain together, while invocations with different selec-tors that reach the same case may or may not be grouped together. Figure 3 therefore represents switch directly rather than translating it into nested conditionals. Among primitives, SPIR-V’s cooperative matrix operations are the ones with req (𝑝 ) = full : they require every invocation in the matrix scope, which for the physical warps WarpDRF considers is the complete warp. 

CUDA and HIP. As Section 3.1 notes, we do not model bitmasks. Our tests pass __activemask() , which queries the participants dynamically and so corresponds more closely to the SPIR-V mapping. In pilot experiments we could not find any reconvergence rule that reliably gave unambiguous participation for primitives with partial groups. We regard this as a serious problem with __activemask() . Code that uses it to group a partial warp may work today, but we did not observe any rule that says it will keep working. Despite these surprisingly unconstrained behaviors around 

__activemask() , one rule did hold empirically, even if we could not find it stated in the CUDA specification. At a join point where every thread of the warp reconverges, all reli-ably participate in a subsequent primitive. This configuration is weaker than the SPIR-V one and is therefore portable: re-quiring every primitive to run with the complete warp leaves nothing for a reconvergence policy to disagree about. SPIR-V and CUDA therefore give two configurations worth testing broadly, which Section 4 does. Section 5.1 then im-plements the portable one, which that testing shows to be empirically valid for CUDA, in the Faial race checker. 

## 4 Testing Implementations 

WarpDRF’s guarantee requires a conforming target system. We ask if a system conforms, focusing on participation, the novel component of WarpDRF and the property languages document the least. The contract specifies the reference se-mantics, which can serve as an oracle. The oracle is efficient to compute because WarpDRF has a single output for a given input; there is no need to enumerate interleavings. We build this executable model in MLIR and test 16 device and back-end pairs against it. We check the systems of Table 3 against the three configurations of Section 3.4. Checking every con-figuration establishes whether a system conforms to any instantiation of WarpDRF, and the cases where they disagree provide interesting insights into how systems implement warp executions. The conformance campaign generates kernels with non-obvious participation, translates each to the target languages, and compares target results with the interpreter under dif-ferent participation rules. 4.1 Conformance Tests and Oracle 

To test conformance, we implement the language of Sec-tion 3.1 as the WarpDRF MLIR dialect. Its operations are the memory accesses, warp primitives, and structured control flow of Figure 3. This dialect could be used as the foundation for more analysis, but for now we use it for conformance testing. To provide an oracle, we implement an interpreter for the WarpDRF dialect. Computing the expected result follows the schedule of the model itself: execute each thread in turn, switching at a warp primitive and releasing it once all its par-ticipants arrive. The interpreter creates a dynamic execution graph that tracks dynamic blocks, similar to SIMT-Step [10], and updates each block’s participation list as threads branch. To provide concrete tests, we implement raisers to the different GPU languages of Table 3. Control flow and ex-pressions map naturally to each language. The GLSL path emits a shader embedded in an Amber script, which Amber compiles to SPIR-V and executes through Vulkan. We note that HLSL does not have a mapping to synchronizing warp primitives; however, our tests only deal with participation, so it does not impact this investigation. 

A WarpDRF conformance test. A test is a WarpDRF di-alect module and a launch configuration giving the number of threads and the warp width. It initializes arrays that con-tain values for the test. For each target, we launch exactly one complete warp: if the target warp width is 𝑊 , the launch contains 𝑊 threads. As in SIMT-Step, we obtain 𝑊 from the target rather than fixing one width for every device [10]. Participation is observed through wave_count_bits , a warp primitive of the WarpDRF language that returns the number of threads participating in it; the artifact gives its mapping to each target language. Every thread calls it and stores the result at an array index no other thread writes. The resulting array of counts is what we compare: the inter-preter produces one count per thread, and a target system that groups threads differently produces different counts. Such a mismatch is a difference in participation, the second condition of WarpDRF, and thus would violate WarpDRF under the instantiated configuration.

## 5 Checking Kernels Against the Contract 

Section 4 found a stable full-warp boundary across the tested implementations. We now ask whether deployed kernels fol-low that rule. We produce the first static checker for an empirically validated warp programming model by extend-ing Faial for the portable CUDA configuration. WarpDRF-Faial checks memory ordering and full-warp participation separately. We apply it to the performance-critical CUDA kernels of llama.cpp, a widely used open-source LLM infer-ence engine. Most analyzed warp-using kernels satisfy both conditions after source and caller validation; the remaining kernels reduce to four source-level patterns. 

5.1 WarpDRF-Faial: a WarpDRF checker for CUDA 

WarpDRF-Faial checks CUDA kernels for the two conditions of Section 3.2, reporting each condition separately and re-porting a kernel as WarpDRF only when both conditions succeed. Our analysis builds on the GPU verification frame-work Faial [11, 33]. 

Verifying Condition 1 (memory DRF). Our analysis as-signs a block phase and a warp phase to each memory access. Two instructions alter the phases: a block-level barrier syn-chronization ( __syncthreads ) increments the block phase for every thread in the block, and a warp barrier synchroniza-tion ( __syncwarp ) increments warp phase for the threads in that warp. To check the DRF condition we apply the two-thread reduction technique [31], where a conflict happens when the block phases are equal and either the threads are in different warps, or the two accesses are in the same warp and have equal warp phases. Alarm: the counterexample (a program state) of the two accesses that may race. 

Verifying Condition 2 (unambiguous participation). 

The analysis checks that: 1) each warp primitive has a full-warp mask, 2) each branch guarding a warp primitive has a warp-uniform condition, and 3) each loop containing a warp primitive has warp-uniform bounds. In short, the code that controls warp primitives must be warp-uniform, while the re-maining code can be warp-divergent. The thread-dependent load in block_reduce does not control its subsequent warp reduction, so the checker accepts it. Alarm: the warp primi-tive that may execute with only part of its warp.

## 6 Related Work 

Scoped memory models and data-race freedom. Weak ordering established the DRF style of reasoning: program-mers use synchronization to order conflicting accesses and then reason in a simpler reference model [3]. Heterogeneous race-free models adapt that argument to hierarchical ma-chines by attaching scopes to synchronization and memory operations [19, 42], and formal work has characterized the guarantees that heterogeneous systems, PTX, and Vulkan actually provide [4, 34, 45]. All of this begins with synchro-nization operations whose participants are already fixed. WarpDRF: The Unwritten Contract of GPU Warp Programming 

WarpDRF keeps the DRF argument but not that premise: a warp primitive orders only the threads that execute it together, so its participants must be established before its memory ordering can be used. 

GPU verification and race detection. Earlier work com-pares interleaving and lockstep GPU semantics and estab-lishes their agreement for race-free programs [12, 27]. GPU-Verify was extended to reason about implicit, coarse-grained synchronization within fixed warps and about atomics [7]. Dynamic tools including BARRACUDA, CURD, and HiRace detect races in GPU executions, while Simulee targets CUDA synchronization bugs through memory-access modeling [15, 20, 40, 47]. These approaches do not define the participant group of an explicit warp primitive under divergent control flow; WarpDRF makes that group part of the contract. 

Testing implementations against specifications. A spec-ification is only useful if implementations follow it, and a line of work establishes that empirically. Stress testing has exposed weak and undocumented memory behavior in de-ployed GPU applications and devices [25, 43], mutating lit-mus tests measures how well a suite discriminates between candidate models [30], and large campaigns survey confor-mance across many devices at once [29]. Related work has found shader compiler defects with generated programs [14] and characterized forward-progress guarantees that no spec-ification states [44]. These campaigns target memory consis-tency and progress, where a reference model already fixes the expected result. Section 4 applies the method to partici-pation, which first required a contract to supply one. 

Warp execution and participation. Warp-level coop-eration is a standard performance idiom, with libraries pro-viding warp-wide reductions, scans, and data exchange [37] and irregular kernels built directly on warp behavior [36]. What those operations group is less settled. NVIDIA’s inde-pendent thread scheduling weakens the assumption that a warp executes in lockstep [38], and hardware and compiler work treats grouping as an optimization variable, regrouping threads after divergence or delaying execution to increase convergence [13, 16, 17]. This line studies grouping as a performance question. A separate line makes participation precise. SIMT-Step determines the threads that execute a subgroup operation to-gether from dynamic basic blocks [10], SPIR-V control-flow work and maximal reconvergence expose the structured joins such reasoning needs [22, 26], and uniformity and barrier-divergence analyses identify where a collective may execute safely [8, 21, 28]. Verification tools cover fixed-warp syn-chronization, producer-consumer patterns, and source-level correctness requirements [7, 35, 41]. These describe how participants form. WarpDRF makes participation a condi-tion of a data-race-freedom guarantee, then checks whether implementations and deployed kernels satisfy it. 

## 7 Conclusion 

This paper introduced WarpDRF, a data-race-freedom con-tract for GPU warp programming. WarpDRF combines scoped memory ordering with predictable participation in each warp primitive. It provides a portable model for full-warp pro-grams and a separate model for languages that define partial-warp reconvergence. We implemented WarpDRF through an MLIR interpreter, a cross-platform conformance suite, and a warp-aware extension to Faial. Across the tested systems, full-warp programs behaved consistently, whereas partial participation varied across languages, compilers, and targets. Applying WarpDRF-Faial to llama.cpp exposed complemen-tary memory and participation problems. Together, these re-sults provide a rigorous foundation for specifying, reasoning about, and checking warp programs across GPU languages and implementations.
