## Abstract 

GPU working sets have outgrown GPU memory, so applica-tions must oversubscribe it, keeping only hot data on the GPU. NVIDIA’s Unified Virtual Memory (UVM) supports oversub-scription , but its performance degrades once data exceeds the GPU’s memory. This stems from its fault-driven data place-ment, wasting interconnect bandwidth, and underutilizing the GPU. This raises the question: can UVM oversubscrip-tion become practical on stock GPUs, exploiting GPU memory speed and minimizing wasted interconnect bandwidth, without placement hints, profiling runs, or application changes? 

To this end, we present Ember, a UVM management frame-work for oversubscribed workloads. Ember introduces a 

hybrid address space ; allocations start as mapped into host memory, omitting data migration. Ember’s counter-driven region promotion uses GPU’s hardware counters to fetch hot regions to the GPU, its decay-based eager reclamation proac-tively evicts cold regions in batches, while via online region re-placement , Ember tracks the hot set at runtime. We implement Ember within NVIDIA’s open-source UVM driver for unmodified applications and as a userspace variant on stock CUDA. At 1 .5× oversubscription, it is 6 .8–10 .6×

faster than UVM on six applications across three PCIe GPUs, and generates LLM tokens 4 .7–16 × faster at sizes where manual placement cannot run at all. Without a profiling run, it beats a profile-guided alternative by 2 .1× on kernel time.

oversubscribe GPU memory, keeping a subset of their data on the GPU and serving the rest from host memory over the interconnect, since otherwise they cannot run at all once their data exceeds device memory [43]. To simplify GPU memory management, NVIDIA intro-duced Unified Virtual Memory (UVM) [41], which places CPU and GPU memory in a single virtual address space and implicitly transfers data between them. Since UVM pages data into the GPU on demand, an allocation may also exceed the device memory, allowing applications to oversubscribe the GPU. Unlike manual data placement, which couples an application to a specific memory layout and requires rewrit-ing per application and GPU generation [6, 39, 53], UVM lets host and GPU share pointer-based structures [42, 55]. By default, a GPU access to a non-resident page raises a page fault and the driver must migrate the page into GPU memory before the access can complete, with later accesses served at device-memory bandwidth. UVM also allows developers to 

prefetch a range into the device, or map it so the GPU reads host memory directly at interconnect speed. Despite the benefits, UVM sees little adoption for working sets exceeding GPU memory, as performance collapses once the GPU capacity line is crossed. Figure 1 shows a GPU sort whose runtime grows from 4 .1 s to 1150 s at 1 .5× oversub-scription. Thus, production systems either manually orches-trate the placement policies [6] or disable UVM [47], with vendors recommending steering placement by hand [19, 55]. Making UVM practical beyond device memory has four obstacles (§3). First, UVM suffers from reclamation-induced arXiv:2610.13408v1 [cs.OS] 9 Oct 2026 execution stalls (C1 ). Once the device memory is full, a page fault must also reclaim a device-resident page before the driver migrates the new one, and the reclaimed pages may become the next faults. This cycle runs on the critical path, stalling computation. Architectural proposals shorten this path [7, 17, 33, 40, 67, 69, 71], but they rely largely on simu-lations or on features absent from commodity GPUs. Second, to reduce page faults, developers can map a mem-ory range so that the GPU accesses host memory directly. However, memory requests are then served over the intercon-nect, leading interconnect-bound mapped access (C2 ). Thus, mapping alone cannot resolve UVM’s performance issues. Third, to leverage GPU memory performance, UVM al-lows the programmer to selectively prefetch data. However, beyond the VRAM capacity, every transfer must first evict pages to free up space on the device. Prefetching moves up to 

∼1.5× the amount of data that the default UVM does, trading faults for prefetch-amplified reclamation traffic (C3 ). Hence, prefetching only defers UVM’s performance collapse. Fourth, while mapping and prefetching can be combined through placement hints, there is no principled rule speci-fying which to apply where, and a wrong hint can degrade performance [2, 14, 28]. A hint also applies to a whole man-aged allocation and must be given before launch. However, access patterns shift during runtime [64, 65], leading to stale, allocation-granular placements (C4 ). Prior work either fixes placement before the run and per allocation [25, 49, 53], or decides at runtime but still migrates by default, mapping only as a fallback, so reclamation stays on the critical path [60]. 

Research question: Can UVM oversubscription become practical on stock GPUs, exploiting GPU memory speed, minimizing wasted interconnect bandwidth, without place-ment hints, profiling runs, or application changes? 

To answer this question, we present Ember, a GPU mem-ory management framework designed for oversubscribed workloads. Our key insight is that mapping should be the default, not a fallback. Concretely, Ember decides which regions leave device memory and when, reclaiming cold re-gions in batches before memory fills, avoiding computation stalls ( C1 ). Underneath, it builds a mapped-by-default hybrid address space , in which every allocation starts as mapped and is reachable from the GPU without migration ( C2 ). Only hot regions are promoted to GPU memory, either as advised by the developer in userspace or as reported by the GPU’s hardware access counters in the kernel ( C3 ). The split is also re-evaluated at runtime, demoting regions whose demand has decayed and promoting those that become hot ( C4 ). We implement two variants of Ember: Ember-static , a userspace variant on stock CUDA that fixes the data split at allocation time, and Ember-adaptive , a patch to NVIDIA’s open-source UVM kernel module that decides the split on-line and transparently supports unmodified applications. ## 2 Background 

2.1 Unified Virtual Memory (UVM) 

NVIDIA implements UVM in the nvidia-uvm kernel module, which manages the unified address space. The driver divides each allocation into fixed-size 2 MiB VA blocks and tracks, per block, which of its pages (e.g., 64 KiB pages on aarch64) are on the GPU. This is the unit at which placement is decided, and we call it a region . Physical GPU memory is allocated and reclaimed in chunks of up to 2 MiB. When the GPU accesses a page that is not resident, it faults into the driver and stalls for thousands of cycles until the page is migrated [63]. 

2.2 Data Placement 

There are three ways to place a page in UVM memory model. 

Migrate. Migration through page faults is UVM’s default strategy. To amortize fault costs, CUDA prefetches specu-latively with a tree-based neighborhood (TBN) policy [17]. Each 2 MiB VA block forms a tree whose leaves are its pages, and each internal node tracks how much of its subtree is GPU resident (Figure 2). A page fault makes its leaf resident, which raises a resident count at every node above it. When more than half of a node’s subtree is resident, the driver

Thus, faults progressively migrate larger ranges, up to 2 MiB, betting on spatial locality [68]. Under oversubscription, migrating a page requires free-ing GPU memory. UVM reclaims space with an age-based, approximately LRU policy that evicts chunks back to host memory over the same interconnect used for migration [17]. 

Prefetch. A developer can move a range into the GPU ahead of use with cudaMemPrefetchAsync [14, 42], avoiding many faults with one transfer. Prefetching is still migration, how-ever, so past capacity it must first free GPU memory. 

Map. A developer can place a range in host memory, directly accessed by the GPU. cudaMemAdvise attaches a placement policy to a range; SetPreferredLocation hints where it should live; and SetAccessedBy adds it to the GPU page table. By combining these calls, the range can be preserved in the host (i.e., never migrated) and be available to the GPU without a fault. Such mapped access only fetches the cache lines a kernel requests via the interconnect on every access. Outside UVM, pinned explicit movement stages data into pinned host buffers and copies it using cudaMemcpy , achiev-ing high bandwidth but ruling out oversubscription, since the working set must fit in GPU memory. 

2.3 GPU Hardware Access Counters 

NVIDIA GPUs expose roughly 256 hardware access counters ,which count the GPU’s accesses to host-resident memory at a configurable granularity [10, 42]. Once a counter crosses its threshold, the GPU writes an entry into a buffer and keeps running, so unlike a fault it does not stall. The driver reads these entries off the access path to see which range was accessed and how often, and we call each entry a notification .The counters are too few to cover a large mapped dataset, and the driver does not migrate based on them by default [10]. The driver also discards notifications when the operating system’s page size is 4 KiB, the default on x86 Linux, because the migration path they would drive is unsupported at that size [45]. 2.4 Coherent Interconnects 

Recent systems connect the CPU and GPU over a cache-coherent interconnect (e.g., NVLink-C2C on Grace Hop-per [44, 56]), where they share one page table. The GPU accesses host memory directly, and the gap between device-memory and interconnect bandwidth is lower compared to PCIe (Table 2). However, GPU memory remains a separate, finite pool, and a resident set must still be chosen. Finally, physically unified memory promises to remove the distinc-tion between host and device memory altogether [5]. 

## 3 Technical Challenges and Key Ideas 

UVM enables GPU memory oversubscription without data-movement code. However, under oversubscription, its three placement mechanisms and their combinations fail. 

C1: Reclamation-induced execution stalls. Hiding data movement is a core benefit of UVM, but its TBN prefetcher and age-based eviction thrash once the working set exceeds VRAM (§2.2). Past the VRAM line, UVM runs up to 10 ×

slower than mapping the same data from the host ( UVM-mapped ), which stays flat even though it is interconnect-bound (Figure 3). UVM-mapped never incurs a page fault and never migrates data, so nothing is ever reclaimed, which helps locate UVM’s cost. A UVM kernel with random ac-cesses runs 7 × longer than one with sequential accesses, even though it incurs 5 × fewer page faults, because it evicts 26 ×

more data. TBN explains the difference, since it prefetches a neighborhood for each fault, which a sequential kernel consumes and never needs again, whereas a random kernel uses little of it and evicts pages before it accesses them again. Figure 4 shows what that costs. Once memory is full, evic-tion never stops, and because each eviction interleaves with execution and stalls the warps whose pages it takes, warp occupancy falls and never recovers. 

Key idea #1: To avoid reclamation traffic and page faults, Ember maps allocations in host memory by default (§5.1).

C2: Interconnect-bound mapped access. While UVM-mapped does not reclaim any data and can even improve performance in some scenarios (Figure 5a), it leaves device-memory bandwidth unused. Every access is bounded by the interconnect, which has 15–150 × lower bandwidth than device memory over PCIe and still ∼9× lower over NVLink-C2C (Table 2). Compute-intensive kernels are affected most, since every reuse of their data crosses the interconnect. For instance, a GPU-accelerated k-means application runs up to 6.5× slower when served purely from the host (Figure 5b), and LLM workloads are bounded in a similar fashion (§7.4). 

Key idea #2: To recover device-memory bandwidth, Em-ber splits each allocation, serving selected regions from device memory and leaving the rest mapped on the host (mapped-by-default hybrid address space , §5.1). 

C3: Prefetch-amplified reclamation traffic. Prefetching large data ranges ahead of use ( Prefetch ) fills the GPU, leav-ing no room for subsequent data fetches, once the VRAM capacity is reached. On random accesses, Prefetch collapses similarly to stock UVM (Figure 5a). It falls back to on-demand faulting at UVM-like fault rates (Figure 5c), but evicts up to 

∼1.5× the data of stock UVM (Figure 5d). Thus, prefetching replaces faults with bulk transfers but increases the eviction volume and, as a consequence, the reclamation traffic [1]. 

Key idea #3: To avoid reintroducing eviction thrashing, Ember promotes only the regions the GPU’s access coun-ters show as hot, and stops promoting before device mem-ory fills ( access-counter-driven region promotion , §5.2). 

C4: Stale, allocation-granular placement. Combining mapping and selective prefetching can help, but it is not enough, because the split between them must be both fine-grained and adjustable at runtime. Specifically, an allocation mixes hot and cold data [68]. A decision at the allocation granularity can lead either to promoting cold data to VRAM, occupying useful space, or to leaving hot data in host mem-ory. ## 4 Overview 

Ember is a GPU memory management framework tailored for oversubscribed workloads. It aims to (i) benefit from GPU memory performance while the working set fits, (ii) avoid the collapse on oversubscription, and (iii) require no changes to hardware, GPU kernels, or applications. 

4.1 System Architecture 

We build two variants of Ember: (i) Ember-static establishes the hybrid address space from user space with placement hints and fixes the data split between host and device before kernel launch, for hot sets known up front and for machines without bare-metal access (e.g., cloud instances). (ii) Ember-adaptive executes inside the UVM driver and adjusts this split at runtime from the GPU’s hardware access counters, for hot sets that are unknown or change during the run (§7.8). 4.2 Life of an Allocation 

Figure 6 presents a managed allocation in Ember. Each region is either mapped or device-resident .

Deployment phase. To deploy Ember-static, a developer adds three placement calls after each cudaMallocManaged 

(Listing 1), which establish the hybrid address space and fix the split at launch. Ember-adaptive needs only the kernel module to be loaded ( ①) and leaves the application intact. 

Allocation phase. Every managed allocation reaches Ember without an API call ( ②), and the migration engine maps it, with the host memory as its preferred location ( ③). As in stock UVM, pages are populated lazily. A page first accessed by the host is created in host memory and mapped; one first touched by the GPU has no copy to move yet, so Ember reads the fault as demand and creates the page in device memory at no transfer cost (§5.2). A kernel can therefore start without waiting for any data to move, even when the allocation is many times larger than the device memory ( ④). 

Promotion phase. Under Ember-adaptive, every region starts mapped, so the GPU reads it over the interconnect while the hardware access counters record its accesses. The access monitor collects notifications from the access counters and connects each to their VA block. The counting happens in hardware, without costing GPU time. When an access count crosses a threshold ( ⑤), the placement policy engine marks it to be promoted ( ⑥), and the migration engine locks the VA block, migrates its host-resident pages and updates the page table ( ⑦). After this point, the region is device-resident , and since the counters capture only host memory, its recorded demand only decays from here on (§5.3). 

Reclamation phase. Before the GPU memory fills, the pol-icy ranks resident regions by their migration history and by their recorded demand before promotion, and writes the coldest back in batches ( ⑧) to provide space for upcoming promotions without evicting in the critical path. A reclaimed region returns to host memory, where the access counters see it again, so a region evicted by mistake is promoted back as soon as the GPU keeps accessing it. 

4.3 System Model Deployment model. Ember targets discrete GPUs, whose device memory is oversubscribed. Ember-static runs on the stock driver without requiring elevated privileges or bare-metal access on the host. A developer deploys it using place-ment hints (Listing 1). It preserves the UVM memory se-mantics but fixes the split before launch, preventing it from following the access patterns of long-running applications. Ember-adaptive lifts this restriction by making placement de-cisions at runtime via a kernel module that extends NVIDIA’s UVM module. It requires hardware access counters, standard in most GPUs, and a machine on which an administrator can load a module (§8). Ember handles all managed alloca-tions, so unmodified binaries can seamlessly adopt it, with the policy parameters (Table 1) set at module load time. 

Programming model. Ember requires no change to the UVM programming model. An application allocates man-aged memory and dereferences the returned pointer in both host and device code, as before. Managed memory keeps its semantics, the coherence guarantees of stock UVM, and allocations may exceed device memory. Ember only transpar-ently determines where each page resides during execution. Currently, allocations outside the Ember-managed path, such as GPU-only buffers and buffers created within third-party libraries, retain their existing semantics and remain outside Ember’s control (§8). An application that issues its own place-ment hints on a managed range overrides Ember for that range, so application-specific optimizations are preserved. 

## 5 Design 

Ember realizes its key ideas (§3) via three core components: the migration engine provides the hybrid address space and carries out data movement (§5.1), the access monitor produces the placement hints (§5.2), and the placement policy engine 

consumes them to make placement decisions (§5.3). 

5.1 Migration Engine 

The migration engine owns the address space and manages physical data placement, realizing the mapped-by-default hy-brid address space and Ember’s block promotion mechanism.

Mapped re-gions indicate the performance floor as they are immediately available once mapped, never faulted in and evicted again, and bounded, in the worst case, by interconnect bandwidth. On the other hand, device-resident regions provide a per-formance ceiling , since a resident region is served at GPU memory bandwidth for as much data as the GPU can hold. Ember allows regions in both states to coexist within a single allocation (Figure 8). A region is mapped as soon as its pages exist and remains mapped until it earns promotion, inverting the stock UVM arrangement, where fetching data on the GPU is the default and mapping is the exception. This inversion makes any allocation immediately usable, starts kernel execution without data movement, and defers reclamation until the policy engine initiates it. 

Region state. Ember defines a region to be exactly one VA block, and extends the driver’s per-VA-block state with a migration history, and attaches a decayed demand [32] to each physical chunk backing a resident region (§ 5.3). As an alternative, Ember could group several VA blocks into a larger region to reduce the number of migration operations. However, since each block carries a lock, a single placement change would need to acquire multiple locks and force the migration path to reason about lock ordering and re-entrancy. Instead, inheriting the driver’s granularity preserves every invariant it maintains over a VA block, at the cost of a unit of state fixed by the driver, and a larger region would have to be re-established against each new driver release (§8). Ember recovers the batching benefit that a larger region would have given by promoting a configurable span of con-secutive blocks at once (§5.2). Reclamation works in physical chunks rather than blocks because chunks are the unit in which the driver hands back device memory. 

Region promotion/demotion. When Ember initiates a region promotion, the migration engine locks its VA block, moves every host-resident page into GPU memory in one operation, and updates the GPU page table. Thus, each pro-moted block costs only one bandwidth-saturating transfer. Demotion is the inverse operation. When Ember performs a region demotion, the migration engine gathers a set of physical chunks and writes them back to host memory as a bounded batch. Ember preserves this operation off the criti-cal path to avoid interleaving with computation, removing the observed stalls under the stock UVM reclamation policy (Figure 4). Synchronization. The migration engine holds at most one VA-block lock at a time. A promotion locks only the block it moves, and a demotion runs as a separate pass. In this way, threads do not wait on a second lock, thereby avoiding deadlocks. Within a migration, Ember calls the driver’s own routine and holds that lock for its whole duration, including the page table update, as the routine requires. The recorded residency of a block therefore never disagrees with where its pages are, and other threads see the new state only once the move has finished. Access counter updates require no locks, since they serve only as hints. A lost or stale count delays a promotion by one interval without compromising correctness, with the block state staying valid. 

5.2 Access Monitor 

The access monitor translates GPU memory traffic into data-placement signals, enabling counter-driven region promotion .Using the GPU’s hardware access counters, it decides when a mapped region should be moved into GPU memory. 

Hardware access counters. The UVM driver exposes hard-ware access counters that report how often a GPU reaches a host-resident range. While UVM does not use them and migrates on faults, Ember infers data placement hints based on them, attributing each one to the VA block whose pages were accessed. This costs no GPU time and never blocks the kernel. However, GPU counters have limitations. 

Limited counter view. The access counters monitor only host memory [10]. They cannot report the access frequency of GPU-resident regions or identify cold data suitable for evic-tion. Ember infers coldness in its policy engine instead, from the demand each region showed before promotion (§5.3). 

Limited counter number. A GPU has ≈ 256 counters [10], that cannot cover a mapped set of hundreds of GiB at the VA-block granularity. Ember compensates for this limitation by widening the scope of the action each counter notifica-tion triggers. A notification is tied to one VA block, but a promotion covers a configurable span of consecutive blocks around it, as a sequence of independent per-block promo-tions (§5.1). Thus, in Ember, one observed block stands in for its neighborhood, and a few hundred counters can drive placement decisions across a mapped set that is much larger. 

> 6

Promotion threshold. Ember’s decisions are based on a threshold that determines when a region earns promotion. It encodes a break-even point, reached once a region has been frequently accessed, where serving further accesses from GPU memory outweighs the migration cost. This threshold is crucial; if set too low, Ember may promote regions that are not reused, while high values might leave hot data on the host, repeatedly paying for access over the interconnect. Therefore, Ember exposes it as a tunable parameter. 

Fault-driven promotion. A region can also be promoted without a counter notification. A mapped region never faults, so a fault occurs only on a page that has not yet been popu-lated: the host has not accessed it, and there is no copy to map. Ember handles it by creating a page in GPU memory at no transfer cost. Thus, data a kernel produces starts resident while data the host produced starts mapped (§4). 

5.3 Placement Policy Engine 

The access monitor provides placement hints, while the pol-icy engine contains the rules for enforcing them. Different policies can be applied without changes to the migration path or the application. Ember implements two policies (Figure 9), 

threshold promotion and decay-based eager reclamation .

Threshold promotion. Under this policy, a mapped region is served from host memory while its counter accumulates (❶); crossing a threshold 𝜃 makes it a promotion candidate (❷), and Ember migrates it to GPU, if there exists avail-able memory ( ❸). Note that eviction is disabled . Once the GPU memory fills, Ember freezes the resident set and leaves remaining regions in the host ( ❹). Thus, Ember benefits from GPU memory bandwidth for the initially accessed data, incurs no reclamation traffic, and resorts to interconnect-bound accesses for data beyond the GPU memory capacity. 

Decay-based eager reclamation. Despite the potential ben-efits of the static threshold promotion , a frozen GPU-resident dataset can become stale as the hot dataset shifts. For this reason, Ember also includes a decay-based eager reclamation 

policy. Inspired by prior work [36], Ember applies eager recla-mation and orders potential eviction candidates by decayed demand. It frees space before demand arrives ( ❺), removing eviction from the hot path. Thus, it allows upcoming pro-motions to proceed ( ❻), with victims inferred from decayed demand ( ❼) and written back in batches ( ❽). Above a GPU occupancy threshold, Ember reclaims until it falls back to a lower one. In this way, space for the next promotion becomes available before its notification arrives, and the computation can avoid the memory reclamation and eviction stalls on the hot path. Below the upper threshold, it replaces GPU-resident regions that are colder than the hottest one by a configurable ratio. The gap between the two thresholds prevents promotion and reclamation from clashing, as reclaiming down to the lower threshold leaves room for several promotions before the upper one is reached again. A promotion that finds no free space fails and retries on the region’s next notification, leaving reclamation as the only path to evict GPU-resident data (§6). 

Demand decay. Choosing eviction candidates requires know-ing which GPU-resident regions have gone cold, which the hardware counters cannot report (§ 5.2). Ember therefore records the demand before it disappears, adding the access count of every serviced notification to the physical chunk backing a region. Thus, a region arrives in GPU memory al-ready carrying a measure of its past access frequency, which, then, halves at fixed time intervals. This means that a moved region sinks to the coldest position on its own over time. 

Online region replacement. Demotion returns a region to the mapped state. A region reclaimed while it was still hot re-earns promotion within one notification interval, at the cost of an interconnect round trip. A region undergoing migration is excluded from placement decisions until its migration completes. The policy engine skips the regions the driver marks as in-flight and handles each promotion atomically; two service threads cannot start the same promotion twice. 

Migration-aware protection. Ember’s decay mechanism might eventually cool a region that is still genuinely hot. To address this, a region that returns to the GPU shortly after being reclaimed has its migration score increased, granting its underlying physical chunks a bounded residency grace period proportional to that score. The score decays more slowly than the demand, keeping a contested region pro-tected across several reclamation passes. Reclamation never evicts a protected region while an unprotected one exists. If all regions are protected, Ember selects the first to expire, ensuring that its protection can delay reclamation but never stalls an allocation. Victims are ordered lexicographically, unprotected before protected, ranked by lowest migration score, oldest residency, and lowest decayed demand. 

Capacity accounting. Capacity accounting is conservative, as promotion stops at the upper occupancy threshold that triggers reclamation. The margin below full memory shows the accounted headroom. It also keeps GPU memory from filling, so the stock fault-and-evict path never runs, neither under Ember-adaptive nor with Ember-static’s prefix ( C1 ). That headroom is important as it covers what Ember cannot observe. For instance, a GPU’s free-memory figure can over-state what is usable, and allocations outside the managed path consume GPU memory invisibly to Ember (§8).

6.1 Ember-adaptive Memory allocation. On a cudaMallocManaged call, Ember creates the VA range, sets its preferred location to the CPU, and adds every GPU to its accessed-by mask. Pages are still populated lazily, as in stock UVM. The call itself moves no data, and Ember decides only where each page lands when it is first touched, without any input from the application. A GPU fault can still occur on a page with no host copy (e.g., kernel’s output). Ember places that page in GPU mem-ory with no recorded demand, making it a prime eviction candidate. After a potential reclamation, it remains mapped and is promoted if it proves to be hot, per Ember’s policies. 

Monitoring. Ember employs access counters for managed ranges and handles their notifications via the driver’s exist-ing path. Each notification is associated with a VA block. The block’s counter value is added to the decayed demand of the physical root chunk holding the block’s pages, under a short lock on the chunk list of the driver’s GPU memory allocator. Thus, demand lives on physical chunks, while the VA block carries only its migration history and a flag marking an in-flight promotion. Ember also lifts the 4 KiB-page restriction of GPU counters (§2.3) for ranges under its own policy. 

Promotion. When a counter notification arrives, Ember locks the block and promotes it as a whole, swapping the notification’s accessed-page mask with the block’s host-resident mask and forcing the destination to the GPU. Ember reuses the driver’s migration routine, moving the block’s host-resident pages to GPU memory and updating the GPU page table in a single operation. Ember extends the promo-tion range to a span around the block, 64 MiB by default, centered on it except near an allocation boundary, where it shifts to accommodate the span size. A span promotion skips the pages the driver protects and stops at the reclamation threshold, so it never displaces data. A promotion halted for lack of space resumes at the region’s next notification. Em-ber records these events and the bytes moved, so the policy

Reclamation. Ember reclaims memory through a periodic background worker in the driver’s GPU memory allocator. Every 25 ms it halves each root chunk’s demand and then selects victims. On arrival, the score sets a grace period on the chunks backing the block, 100 ms plus 250 ms per score point, capped at 2 s. The eviction candidate search then proceeds, respecting the region state ordering (§5.3). 

6.2 Ember-static 

Ember-static requests the initial placement from userspace and freezes the split. Since Ember-static does not perform reclamation, it does not require counters. 7.2 Hybrid Address Space 

First, we evaluate the effect of Ember’s hybrid address space. 

Methodology. On GH200, a kernel reads a 14 GiB window of a 142 GiB managed buffer in eight phases, once per phase. After each one, the window slides forward by a fixed share of its size, from 0%, where the hot set never moves, to 100%, where it is replaced between phases. We compare the static variants to isolate the effect of the hybrid address space. 

Results. Figure 11 shows the results. The Prefetch variant is fastest when the hot set does not change (0 .15 s), but slows down considerably once it shifts, since each prefetch is stale by the next phase. UVM-mapped’s runtime remains stable (≈ 1.33 s), incurring the interconnect cost on every access. Stock UVM, regardless of the data shift, remains the slowest. Ember-static matches the Prefetch when the hot set is static and degrades at full drift, but still outperforms all baselines. Its advice and prefetch add 1 .33 s once (Figure 11, right), a cost that gets amortized over time via repeated reads. 

Takeaway #1: Ember combines the benefits of prefetch-ing, when the hot set does not change, with the robustness of mapping once it moves, at only a one-time setup cost.

7.7 Comparison with Profiled Placement 

Next, we evaluate Ember-adaptive to quantify the benefits of its dynamic data placement and reclamation policy. 

Methodology. We compare Ember with HELM [25], which profiles an application and assigns each allocation a policy (e.g., migrate , pin to host , pin to device ). We measure both the profiling time to decide on data placement and the actual ker-nel time of the application. We also tried ARIADNE [60], the closest in-driver system, but could not run it, since it builds against driver release 535 .86 and relies on legacy interfaces. 

Results. Ember-adaptive outperforms HELM on all five benchmarks (Figure 15, left), by a mean of 7 .9×, even though HELM profiles each application first. Profiling, metric pro-cessing, and selection take 39 to 1449 s, account for 18% to 95% of HELM’s end-to-end runtime, and heavily depend on the problem size. 7.8 Ember-adaptive vs Ember-static 

Finally, we aim to identify when each Ember variant is the right choice for an application. 

Methodology. On the RTX 5080, a kernel reads a 20 GB managed buffer, at 1 .3× GPU memory, with a configurable share accessed in random order and the rest in a linear sweep, and each page accessed 32 to 1024 times. We sweep two reuse 

> 11

patterns. In the first, all accesses to a page occur in a single pass. In the second, each pass accesses every page once, and reuse comes from repeated passes. We report runtime over the whole grid and, at 0% randomness, the data movement. 

Results. Ember-static incurs a one-time 0 .74 s for advis-ing the buffer and prefetching a 16 GB prefix, whereas Em-ber-adaptive incurs one migration per promotion. Ember-adaptive is faster at low reuse (32 accesses), by 1 .3–4 ×, where the prefetch is not amortized, and at both ends of the random-ness axis, where a pure sweep is a sliding window, tracked by Ember’s counters, while a purely random pattern implies that there is no hot set worth pinning. Ember-static is faster in between, by up to 3 .2× once a page is reused 128 times or more, due to its pinned hot set. Static pays its overhead once and adaptive on every promotion, so which variant wins follows reuse (Figure 16a,b). In terms of data movement (Fig-ure 16c,d), Ember-static migrates its 16 GB prefix once, while Ember-adaptive moves 6 .8 to 24 .4 GB inside a pass and 17 .7to 65 .2 GB when accesses span different passes, since every pass demotes regions that the next one promotes again. Overall, when the data fits in GPU memory, Ember-adaptive runs 1 .2–1 .8× slower than Ember-static. However, Ember mainly targets oversubscribed workloads, where the hot set typically exceeds GPU memory and must be adjusted at runtime, thereby favoring Ember’s adaptive variant. On inte-gration cost , Ember-adaptive requires no application changes, only a module load, while Ember-static adds 8–28 lines per application, under 5% in every case, none of them in a GPU kernel, in launch code, or in an algorithm (Appendix B). 

Takeaway #7: Ember-static is the better choice when a stable hot set is frequently re-read, and Ember-adaptive otherwise, when reuse is low, confined to a single pass, or spread too uniformly to leave a hot set worth pinning. 

## 8 Limitations and Future Work 

Library buffers. Ember places only memory allocated via 

cudaMallocManaged . Buffers a library allocates internally, such as Thrust’s temporaries in radix sort, take device mem-ory that neither variant can see or place. Ember-static suffers more, since it sizes its prefix from one free-memory query before launch, which a later library allocation invalidates. Ember-adaptive sizes its headroom at runtime, so it stops promoting when a library takes the memory (§5.3). 

Device-access observability. Ember cannot observe that a resident region has gone cold; it infers this from the de-mand the region showed before promotion, decayed over time (§5.3). A region that is still hot can thus be reclaimed by mistake and moved twice. The open driver contains an undocumented vidmem access-bit buffer that reports access and dirty bits over device memory [45], reachable only from kernel space and limited to eight address ranges at a time. It is disabled by default on Blackwell, where it is reported to cause undefined behaviour on some parts, so we do not use it. Feeding it into reclamation would replace inference with measurement for those ranges; this and other policy refine-ments are orthogonal to Ember and left for future work. 

Deployment. Ember-adaptive needs bare-metal access to load a kernel module. Our GH200 instance is a cloud VM without that access, which is why §7.6 reports Ember-static alone. The module also builds against the internal interfaces of an open-source driver release and must be rebased for each new one. The rebase is usually mechanical, but a release that changes those interfaces can make a mechanism harder to implement or unavailable, as it did for ARIADNE (§7.7). Nothing in the design is specific to CUDA: the hybrid address space needs only driver-controlled migration and host map-ping, which other stacks also provide (e.g., AMD ROCm [4]). Ember-adaptive additionally needs a non-faulting signal of remote access frequency. 

Multi-GPU. Ember places data between one GPU and host memory. On a multi-GPU node, peer memory forms a third tier between the two, so a region has three homes rather than two, and each notification has to be attributed to the GPU that raised it. We aim to explore it as future work. 

## 9 Related Work 

UVM optimizations. Prior work analyzes the cost of UVM’s faults, prefetching, and eviction [1, 2, 14, 17, 28, 30, 38, 63] and addresses its weaknesses with hardware changes [7, 40, 69, 71] as well as eviction and throttling policies [33, 67]. Adaptive runtimes retune prefetching and eviction behav-ior [16, 21, 27, 59, 66, 70], and other works decide on data mi-gration based on heuristics, such as hardware counters [35], fault history [26], or profiling [34]. All of them keep accesses on the migration path, preserving the reclamation traffic. In contrast, Ember leaves the cold set mapped in host memory, removing that traffic while adjusting the GPU-resident set. 

Data movement and placement. Several systems combine mapped access with migration. Some take data placement decisions ahead of time based on compile-time analysis or of-fline profiling runs [9, 25]. Others decide at runtime based on page access count threshold [18], compiler instrumentation that identifies sparsely used pages [13], or the number of GPU cores faulting on a block concurrently [59, 60]. Another work aims to restore the visibility of GPU counters by keep-ing one page of each region mapped in host memory, at the cost of one sampled page per region, and makes placement decisions based on those [10]. Ember decides at runtime and chooses mapping as the default, with regions migrated only once the demand based on the GPU counters instructs it, requiring no offline profiling, additional faults, or sampling. 

Application-level placement. Other systems encode data placement within the application, for out-of-memory graph processing [20, 37, 54], DNN training, and LLM inference, with a dataflow known in advance [8, 49, 53, 58]. Ember keeps the application intact and requires no such knowledge. 

> 12

Multi-GPU placement and memory pooling [15, 31, 64, 65] is orthogonal, as the GPUs together can fit the working set. 

Tiered memory. CPU tiering classifies pages from hint faults or sampled events and migrates them between DRAM and a slower memory [32, 48, 51, 52]. TPP demotes proac-tively to keep headroom [36], an idea Ember adopts. These designs cannot be directly applied to GPU tiering, as the GPU’s ∼256 counters observe only host memory, and its slow tier sits 15–150 × below GPU memory. Therefore, Em-ber aggregates counter notifications into per-region demand that decays over time, and infers when resident data turns cold. 

## 10 Conclusion 

UVM enables applications to oversubscribe GPU memory, but performance collapses once the working set exceeds the GPU’s memory capacity. Its placement decisions are reactive (i.e., per-fault) and do not consider access patterns, leading to increased reclamation traffic under memory pressure and execution pipeline stalls. To tackle this, we present Ember, a GPU memory management framework tailored for over-subscribed workloads, that preserves the UVM memory and programming model. Ember splits allocations into smaller regions and initially maps them into host memory, which is directly reachable by the GPU, migrating a region only after the GPU hardware counters report it as hot. Ember adjusts its placement decisions at runtime and proactively re-claims memory, keeping eviction off the critical path. Across various workload classes, GPUs, and interconnects, Ember outperforms existing UVM placement strategies under over-subscription as well as optimized profile-guided frameworks without requiring a profiling run.
