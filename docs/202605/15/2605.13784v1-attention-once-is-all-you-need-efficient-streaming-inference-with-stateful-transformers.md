## 摘要
传统的 Transformer 推理引擎是请求驱动的，在每次查询时都会产生 O(n) 的预填充（prefill）开销。在流式工作负载中，数据持续到达且查询需要探测不断增长的上下文，这种开销是难以承受的。我们引入了一种以有状态会话（stateful sessions）为中心的数据驱动计算模型：随着新数据的到达，持久化的 KV 缓存会增量更新，从而将预填充移出关键路径，使查询延迟变为 O(|q|)，且与累积的上下文大小无关。在此基础上，Flash Queries 利用数据到达之间的空闲 GPU 周期来预评估注册的问题，并在用户提问之前返回缓存的答案。这种模式在无状态引擎中在结构上是无法实现的，因为它们在请求之间会丢弃中间状态。一种具有单元预算准入（cell-budget admission）和前缀感知分组预填充（prefix-aware grouped prefill）的多租户连续批处理调度器，允许数十个有状态会话在单个 GPU 上共存，同时保留完整的二次方自注意力。在流式市场数据基准测试中，参考实现相比传统推理引擎（如 vLLM、SGLang、TensorRT-LLM、llama.cpp）实现了高达 5.9 倍的加速，并在累积上下文增长时保持查询延迟恒定。

## Abstract
Conventional transformer inference engines are request-driven, paying an O(n) prefill cost on every query. In streaming workloads, where data arrives continuously and queries probe an ever-growing context, this cost is prohibitive. We introduce a data-driven computational model centred on stateful sessions: a persistent KV cache advanced incrementally as new data arrives, so prefill is moved off the critical path and query latency becomes O(|q|), independent of accumulated context size. Building on this, Flash Queries reclaim idle GPU cycles between data arrivals to pre-evaluate registered questions and return cached answers before the user asks, a pattern that is structurally impossible in stateless engines because they discard intermediate state between requests. A multi-tenant continuous-batching scheduler with cell-budget admission and prefix-aware grouped prefill lets dozens of stateful sessions coexist on a single GPU while preserving full quadratic self-attention. On streaming market-data benchmarks the reference implementation achieves up to 5.9x speedup over conventional inference engines (vLLM, SGLang, TensorRT-LLM, llama.cpp), holding query latency constant as accumulated context grows.

## 论文详细总结（自动生成）

这篇论文由 LayerScale 公司的 Victor Norgren 撰写，提出了一种名为“有状态 Transformer（Stateful Transformers）”的推理架构，旨在解决流式数据处理中的高延迟问题。以下是对该论文的结构化总结：

### 1. 核心问题与研究动机
*   **核心问题**：传统的 Transformer 推理引擎（如 vLLM、llama.cpp）是“请求驱动”的。在流式场景下（如金融行情、传感器监控），数据持续到达，而查询是随机发生的。由于传统引擎在请求结束后会丢弃 KV 缓存，每次新查询都必须重新处理整个累积的上下文（Prefill 阶段），导致延迟随上下文长度 $n$ 呈线性增长 $O(n)$。
*   **研究动机**：在实时交易等领域，延迟至关重要。现有的亚线性架构（如 Mamba、RWKV）虽然推理快，但在复杂推理和长文本检索上不如全注意力 Transformer。作者希望在保留 Transformer 全注意力能力的同时，实现与上下文长度无关的恒定查询延迟。

### 2. 核心方法论
该论文提出了一种从“请求驱动”向“数据驱动”转变的推理模型，核心技术包括：
*   **有状态会话（Stateful Sessions）**：KV 缓存跨请求持久化。新数据到达时，系统仅增量更新缓存，而不是在查询时重新计算。
*   **分层上下文分区（Hierarchical Context Partitioning）**：
    *   **Region 0 (Frozen)**：系统提示词，处理一次后固定。
    *   **Region 1 (Sliding)**：流式数据缓冲区，支持 FIFO 淘汰。
    *   **Region 2 (Ephemeral)**：查询和响应令牌，查询结束后即清空。
*   **数据与查询平面分离**：数据通过无锁环形缓冲区异步摄取（数据平面），查询则作为轻量级消费者直接读取预计算好的状态（查询平面），使查询复杂度降为 $O(|q|)$（$|q|$ 为查询长度）。
*   **闪电查询（Flash Queries）**：利用数据到达之间的 GPU 空闲周期，对预设问题进行预计算。当用户真正提问时，直接返回缓存结果，延迟接近于零。
*   **多租户调度器**：引入单元预算准入（Cell-budget admission）、自适应分块预填充和前缀感知分组等机制，允许单 GPU 支持数十个并发的有状态会话。
*   **设备端采样**：在 GPU 上直接进行 Greedy Argmax 采样，避免了将 Logits 传回 CPU 的同步开销。

### 3. 实验设计
*   **场景与数据集**：模拟金融流式任务，使用合成的 OHLCV（开盘、最高、最低、收盘、成交量）股票行情数据。
*   **Benchmark 流程**：初始化 100 个样本，随后进行 15 轮迭代。每轮添加 55 个新样本（约 880 tokens），然后发布一次查询。上下文从 2,600 tokens 增长到约 14,800 tokens。
*   **对比方法**：
    *   **本地引擎**：vLLM, SGLang, TensorRT-LLM, llama.cpp。
    *   **云端 API**：GPT-4o-mini, GPT-5.2, Claude 3.5 Haiku, Claude Opus 4.5。
*   **评估指标**：查询延迟（ms）、准确率（%）、延迟随上下文增长的缩放曲线。

### 4. 资源与算力
*   **硬件**：所有本地实验均在单张 **NVIDIA L40S GPU** (48GB GDDR6) 上完成。
*   **模型**：统一使用 **Meta-Llama-3.1-8B-Instruct** (BF16 精度)，以排除模型权重差异对推理框架性能的影响。
*   **训练时长**：本文侧重于推理架构优化，未涉及模型训练。

### 5. 实验数量与充分性
*   **实验规模**：进行了 15 轮迭代测试，涵盖 6 种不同类型的分析查询（趋势分类、数值检索等）。
*   **充分性**：实验对比了当前最主流的开源推理引擎和闭源 API，覆盖了从 2k 到 15k tokens 的上下文演变过程。
*   **客观性**：通过在相同硬件上运行相同的 Llama-3.1-8B 模型，确保了对比的公平性。但实验主要集中在金融 OHLCV 数据这一特定领域，对于其他类型的流式数据（如长对话、实时日志分析）的泛化性实验相对较少。

### 6. 主要结论与发现
*   **恒定延迟**：该架构成功实现了 $O(1)$ 风格的查询延迟，无论上下文如何增长，查询延迟稳定在约 **43ms**。
*   **显著加速**：相比 SGLang 快 2.4 倍，相比 vLLM 快 3.2 倍，相比 llama.cpp 快 5.9 倍。相比云端 API（如 GPT-5.2），速度提升达 22 倍至 92 倍。
*   **利用率提升**：通过 Flash Queries 机制，将 GPU 的空闲周期转化为有用的预计算工作，提高了加速器的实际产出。
*   **精度保持**：在提升速度的同时，完全保留了 Transformer 的二次方注意力机制，准确率与基准引擎一致。

### 7. 优点
*   **架构创新**：打破了传统的“请求-响应”循环，将预填充移出关键路径，解决了长上下文流式推理的痛点。
*   **实用性强**：Flash Queries 机制非常契合监控和自动化交易等预测性强的业务场景。
*   **系统级优化**：不仅有算法层面的改进，还包含了调度器、内存管理和设备端内核的深度优化。

### 8. 不足与局限
*   **内存开销**：以空间换时间。每个有状态会话需要持久占用 KV 缓存空间（如 32k 上下文约需 17GB），这限制了单卡能支持的最大并发会话数。
*   **应用限制**：目前主要针对因果（Causal）注意力模式和单序列上下文，对于需要跨文档检索或双向注意力的任务支持不足。
*   **数据假设**：假设数据是增量追加或滑动窗口模式，对于频繁修改历史数据的非线性编辑场景不适用。
*   **实验偏差**：主要基于合成金融数据，真实世界中复杂多变的流式文本可能对 Region 1 的淘汰策略提出更高挑战。
