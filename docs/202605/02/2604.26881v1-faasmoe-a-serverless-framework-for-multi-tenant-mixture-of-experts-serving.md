## 摘要
混合专家（MoE）模型通过为每个输入激活一小部分专家模型，在保持高效推理成本的同时提供了高容量。然而，部署 MoE 模型需要所有专家都驻留在内存中，这导致了激活专家所使用的资源与预置资源之间存在差距。这种资源利用不足在多租户场景下尤为显著。在本文中，我们提出了 FaaSMoE，这是一种构建在函数即服务（FaaS）平台上的多租户 MoE 推理服务架构。FaaSMoE 通过将专家部署为无状态的 FaaS 函数，实现了 MoE 控制平面与执行平面的解耦，从而支持跨租户的按需调用和缩减至零（scale-to-zero）的专家调用。FaaSMoE 进一步支持函数内可配置的专家粒度，通过权衡单个专家的弹性来降低调用开销。我们使用一个开源的面向边缘的 FaaS 平台实现了一个原型，并在多租户负载下使用 Qwen1.5-moe-2.7B 对其进行了评估。与全模型基准相比，FaaSMoE 使用的资源不到三分之一，为多租户环境下可扩展的 MoE 推理服务提供了一条实用且资源高效的路径。

## Abstract
Mixture-of-Experts (MoE) models offer high capacity with efficient inference cost by activating a small subset of expert models per input. However, deploying MoE models requires all experts to reside in memory, creating a gap between the resource used by activated experts and the provisioned resources. This underutilization is further pronounced in multi-tenant scenarios. In this paper, we propose FaaSMoE, a multi-tenant MoE serving architecture built on Function-as-a-Service (FaaS) platforms. FaaSMoE decouples the control and execution planes of MoE by deploying experts as stateless FaaS functions, enabling on-demand and scale-to-zero expert invocation across tenants. FaaSMoE further supports configurable expert granularity within functions, trading off per-expert elasticity for reduced invocation overhead. We implement a prototype with an open-source edge-oriented FaaS platform and evaluate it using Qwen1.5-moe-2.7B under multi-tenant workloads. Compared to a full-model baseline, FaaSMoE uses less than one third of the resources, demonstrating a practical and resource-efficient path towards scalable MoE serving in a multi-tenant environment.

### 1. 核心问题与整体含义（研究动机和背景）
*   **核心问题**：MoE 模型虽然在推理时仅激活一小部分专家（稀疏激活），但为了保证覆盖率，所有专家必须常驻内存。在多租户场景下，如果每个租户都部署一个完整的模型实例，会导致巨大的内存浪费和资源利用率低下。
*   **研究背景**：现有的优化方法（如专家并行、卸载等）多针对单模型效率，未能有效解决多租户环境下非活跃专家的资源占用问题。
*   **整体含义**：论文提出利用 FaaS（函数即服务）的“按需调用”和“缩减至零（Scale-to-Zero）”特性，将 MoE 专家解耦为独立的无状态函数，从而实现跨租户的专家资源共享和弹性伸缩。

### 2. 方法论
FaaSMoE 的核心思想是将 MoE 推理的控制平面与执行平面解耦：
*   **控制平面（Orchestrator）**：负责轻量级计算，包括分词（Tokenizer）、自注意力机制（Self-Attention）和门控网络（Gating）。它决定 Token 的路由路径，并将请求分发给相应的专家函数。
*   **执行平面（Expert Blocks）**：将专家模型部署为无状态的 FaaS 函数。
*   **关键技术细节**：
    *   **可配置专家粒度**：支持将多个专家打包进同一个 FaaS 函数（Expert Block）。这在“单专家弹性”与“调用开销”之间做了权衡：较小的块提供更细粒度的共享，较大的块则减少了函数调用频率和网络开销。
    *   **微批处理（Micro-Batching）**：Orchestrator 将路由到同一专家块的 Token 进行整合，通过一次异步 HTTP 调用发送，以摊销序列化和网络延迟。
    *   **部署策略**：支持“共享编排器（Shared Orchestrator）”和“私有编排器（Private Orchestrator）”两种模式，分别侧重于全局效率和租户隔离。

### 3. 实验设计
*   **模型与平台**：使用 **Qwen1.5-MoE-2.7B** 模型，部署在开源边缘 FaaS 平台 **tinyFaaS** 上。
*   **数据集/场景**：模拟多租户环境，包含 6 个并发客户端，每个客户端从 **BIG-Bench** 数据集中抽取 5 个异构任务（共 30 个请求）。
*   **对比方法（Benchmark）**：
    1.  **Baseline**：每个租户托管一个完整的 MoE 模型实例（传统方式）。
    2.  **Local Distribution**：非弹性的本地服务器方案，仅分离专家但不具备 FaaS 的自动缩放能力。
    3.  **FaaSMoE-Shared**：跨租户共享一个编排器。
    4.  **FaaSMoE-Private**：每个租户拥有独立的编排器。

### 4. 资源与算力
*   **硬件环境**：实验在一个 **仅限 CPU** 的服务器上运行，配置为 300 GB 内存。
*   **算力说明**：论文明确指出未使用 GPU。理由是目前主流 FaaS 平台（如 AWS Lambda）主要支持 CPU，且 MoE 的单个专家计算量相对较小，适合在 CPU 上进行短时、弹性的函数执行。

### 5. 实验数量与充分性
*   **实验规模**：
    *   对比了 4 种不同的部署策略。
    *   针对专家块大小（Block Size）进行了消融实验，测试了 6, 10, 15, 20, 30 等不同粒度。
    *   对 FaaS 内部开销（网关、平台、执行工人）进行了细分分析。
*   **充分性评价**：实验在资源消耗（CPU 和内存）的测量上较为详尽，能够清晰展示 FaaS 架构带来的资源节省。但由于客户端数量较少（6 个），且在 CPU 环境下运行，其在大规模生产环境或 GPU 加速场景下的表现仍需进一步验证。

### 6. 主要结论与发现
*   **资源节省显著**：相比于 Baseline，FaaSMoE 将平均每租户的 CPU 使用率从 187.81% 降至 54.4%，内存消耗从 36.25 GB 降至 12.04 GB，**资源占用减少了三分之二以上**。
*   **粒度权衡**：专家块大小对性能有显著影响。实验发现 Block Size 为 20 时，内存消耗达到最低点（呈 U 型趋势），这反映了运行时副本开销与单函数内存占用之间的平衡。
*   **编排器位置**：共享编排器（Shared）比私有编排器（Private）更节省资源，因为它能实现跨租户的微批处理和连接复用。

### 7. 优点
*   **架构创新**：首次系统性地将 FaaS 的弹性特性与 MoE 的稀疏激活特性相结合，解决了多租户下的资源冗余问题。
*   **灵活性高**：通过可配置的专家粒度和编排器部署模式，允许系统根据成本、延迟和隔离需求进行调优。
*   **开源贡献**：提供了基于 Python 和 tinyFaaS 的开源原型实现。

### 8. 不足与局限
*   **延迟开销**：解耦专家执行引入了频繁的网络通信和序列化开销，论文承认这会增加推理延迟（虽然可以通过 RPC 优化或流水线技术缓解）。
*   **硬件限制**：实验完全基于 CPU，未探讨在 GPU Serverless 环境下的表现，而高性能 LLM 推理通常依赖 GPU。
*   **评估规模**：实验任务量较小，未能充分展示在极高并发或长文本生成场景下的系统稳定性。
*   **网络瓶颈**：频繁的函数调用可能在网络层产生瓶颈，论文对此部分的量化分析略显不足。
