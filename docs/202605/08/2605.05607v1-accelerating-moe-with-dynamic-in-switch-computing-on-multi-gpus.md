## 摘要
混合专家模型 (MoE) 已被许多领先的大模型采用以降低计算需求。然而，MoE 专家并行 (EP) 中频繁的 GPU 间通信成为了性能挑战。我们观察到 MoE 中存在大量冗余的 GPU 间数据传输，这可以通过交换机内计算 (in-switch computing) 潜在地解决。不幸的是，现有的解决方案 NVLink SHARP (NVLS) 仅支持具有规则模式的静态集合通信，无法处理 MoE 中具有不规则模式的动态通信。为了弥补这一功能差距，我们提出了 DySHARP，这是一种用于加速 MoE 的完整动态交换机内计算解决方案，涵盖了通信原语和通信感知调度：1) 动态多内存寻址 (Dynamic multimem addressing) 协同设计了指令集架构 (ISA)、架构和运行时，作为 NVLS 的动态扩展，减少了冗余流量。然而，由此产生的流量减少在两个方向上本质上是不对称的，阻碍了其直接转化为加速。2) 以 Token 为中心的算子融合 (Token-centric kernel fusion) 深度融合了分发-计算-合并流水线，解决了这种不对称性，从而将流量减少转化为实际的加速。与最先进的解决方案相比，DySHARP 实现了高达 1.79 倍的加速。

## Abstract
Mixture-of-Experts (MoE) has been adopted by many leading large models to reduce computational requirements. However, frequent inter-GPU communication in MoE expert parallelism (EP) becomes a performance challenge. We observe substantial redundant inter-GPU data transfers in MoE that can be potentially addressed by in-switch computing. Unfortunately, the existing solution, NVLink SHARP (NVLS), can only support static collectives with regular patterns, incapable of dynamic communication with irregular patterns in MoE. To bridge the functionality gap, we propose DySHARP, an integral dynamic in-switch computing solution to accelerate MoE, encompassing both communication primitives and communication-aware scheduling: 1) Dynamic multimem addressing co-designs ISA, architecture, and runtime, as a dynamic extension to NVLS, reducing redundant traffic. However, the resulting traffic reduction is inherently asymmetric between two directions, preventing it from directly translating into speedup. 2) Token-centric kernel fusion deeply fuses the dispatch-computation-combine pipeline, resolving this asymmetry to translate traffic reduction into actual speedup. Compared with the state-of-the-art solution, DySHARP achieves up to 1.79$\times$ speedup.

### 1. 核心问题与研究动机
*   **研究背景**：混合专家模型（MoE）通过专家并行（EP）在多 GPU 上扩展参数量，但其频繁的 GPU 间通信（分发 Dispatch 和合并 Combine）成为了性能瓶颈，通常占执行时间的 50-80%。
*   **核心问题**：作者观察到 MoE 通信中存在大量**冗余数据传输**（例如：同一个 Token 被发送到多个 GPU，或多个专家输出聚合回同一个 Token）。
*   **技术瓶颈**：现有的交换机内计算技术（如 NVIDIA 的 NVLink SHARP, NVLS）仅支持**静态、规则**的集合通信（如 AllGather），无法处理 MoE 这种**动态、不规则**（目标 GPU 不固定、内存地址不对称）的通信模式。如果强行使用静态方案，会产生高达 340% 的无效流量。

### 2. 方法论：DySHARP 架构
论文提出了 **DySHARP**，一套涵盖硬件指令、架构和软件调度的全栈动态交换机内计算方案：

*   **动态多内存寻址 (Dynamic Multimem Addressing)**：
    *   **核心思想**：扩展 NVLS，允许数据包携带一个“代数索引（Algebraic Index）”和一个轻量级的“目标专家列表”。
    *   **硬件映射**：在目标 GPU 的 Hub 中引入硬件内存管理器，通过 **AL Table（代数-布局映射表）** 将全局代数索引动态映射到本地物理布局索引，解决地址不对称问题。
    *   **ISA 扩展**：引入 `dymultimem.st`（用于分发时的多播）和 `dymultimem.ld_reduce`（用于合并时的交换机内归约）指令。
*   **以 Token 为中心的算子融合 (Token-centric Kernel Fusion)**：
    *   **核心思想**：将 MoE 层视为 Token 级别的流水线，而非四个孤立的算子。
    *   **Token Tracker**：引入硬件追踪器，以 Token/Tile 为粒度检测数据就绪状态，实现分发、计算和合并的深度重叠。
    *   **解决不对称性**：交换机内计算在单一方向上减少流量（如分发时减少 GPU 到交换机的流量），会导致双向带宽不平衡。通过融合调度，让分发和合并同时进行，从而填满双向带宽，将流量减少转化为实际加速。
