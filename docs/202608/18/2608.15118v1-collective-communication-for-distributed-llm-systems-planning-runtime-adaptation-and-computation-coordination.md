## 摘要
分布式大语言模型（LLM）系统日益依赖集合通信原语，如 AllReduce（AR）、ReduceScatter（RS）、AllGather（AG）和 AlltoAll（A2A）。在现代 LLM 训练和推理集群中，异构 GPU 互连、多网卡网络、混合并行策略、低延迟推理请求和高吞吐训练流水线，促使以越来越多样化的方式规划、执行和重叠集合通信。本文提出了一种面向集合通信的、教程式且以集合为中心的分类法。我们将近期进展组织为三个层次：通信规划，生成拓扑感知的集合调度；通信执行与自适应，将这些调度映射到实际集群中的 GPU 运行时和硬件上；以及计算-通信协同，将集合优化转化为端到端的训练和推理收益。我们进一步讨论了分布式 LLM 系统中集合通信的开放挑战和未来机遇。

## Abstract
Distributed large language model (LLM) systems increasingly rely on collective communication primitives such as AllReduce (AR), ReduceScatter (RS), AllGather (AG), and AlltoAll (A2A). In modern LLM training and serving clusters, heterogeneous GPU interconnects, multi-NIC networking, mixed parallelism strategies, low-latency inference requests, and high-throughput training pipelines have motivated increasingly diverse ways to plan, execute, and overlap collective communication. This paper presents a tutorial-style, collective-centric taxonomy for collective communication. We organize recent advances into three layers: communication planning, which generates topology-aware collective schedules; communication execution and adaptation, which maps these schedules onto GPU runtimes and hardware in real clusters; and computation-communication coordination, which turns collective optimization into end-to-end training and inference benefits. We further discuss open challenges and future opportunities for collective communication in distributed LLM systems.

## 论文方法论

### 总体框架：三层分类法

论文将集合通信优化组织为三个相互衔接的层次，其核心思想是描述"集合操作从算法设计到实际系统收益"的完整路径：

1. **通信规划（Communication Planning）**
   - 决定集合操作的**逻辑调度**：参与节点、数据分块策略、通信顺序、拓扑假设。
   - 分为两个子方向：
     - **拓扑感知的手工规划**：由专家根据网络层次、带宽不对称性和拓扑几何来人工设计集合算法。代表工作：
       - **BlueConnect**：将 AllReduce 递归分解为 ReduceScatter 与 AllGather 两个阶段，在高带宽节点内链路上完成大部分归约，再让归约后的数据走较慢的节点间链路，在 192 块 GPU 上相对 GLOO 降低 87% 同步开销。
       - **Themis**：将数据块按各网络维度的带宽容量比例进行调度，实现 1.25–1.49× 的训练迭代加速。
     - **基于优化的调度合成**：将集合设计形式化为搜索或优化问题，从拓扑与工作负载约束中自动生成调度。
       - **SCCL**：将集合语义、拓扑与顺序决策编码为求解器约束，搜索合法的分块级调度，其合成的 AllGather 调度在评估拓扑上最高比 NCCL 快 2.2×（小输入场景）。
       - **TE-CCL**：将分块视为容量受限链路上的多商品流（multi-commodity flow），显式建模路由、容量分配与拥塞，实现最高 3.18× 于 RCCL 的算法带宽。
       - **SyCCL**：利用集合需求与集群拓扑的对称性对搜索空间进行预剪枝，缓解搜索空间爆炸问题。

2. **通信执行与自适应（Communication Execution and Adaptation)**
   - 将逻辑调度**落地**到真实 GPU 集群的运行时与硬件资源（GPU kernel、channel、stream、NIC 绑定、传输协议、路径质量等）。
   - 两个子方向：
     - **可编程集合执行**：提供抽象以构建自定义集合程序。
       - **MSCCL++**：分层 GPU 通信栈，底层暴露原语通信函数（Primitive API），上层提供面向工作负载快速定制的接口（Collective API），实现 1.7× 集合通信加速与 1.2× 推理加速。
     - **自适应集合执行**：根据运行时观测动态调整集合的执行方式。
       - **AutoCCL**：在训练早期迭代中自动剖析 NCCL 的算法、协议与通道配置，并在后续重复集合中复用最优配置，实现 1.07–1.32× 的训练每迭代时间改善。
       - **MCCS**：将集合通信从租户侧的库迁移为云提供商管理的服务，利用全球网络视图动态重配置集合策略，相对 NCCL 最高实现 2.4× 算法带宽。

3. **计算-通信协同（Computation-Communication Coordination）**
   - 核心思想：**优化单个集合操作本身并不必然带来端到端收益**，关键取决于通信在执行图中的位置以及是否能被有效计算所隐藏。
   - 两个应用场景：
     - **训练图中的通信调度**：
       - **CoCoNet**：用统一 DSL 同时描述计算与通信，通过依赖保持变换（分割、重排、融合、重叠）自动生成优化代码，实现 BERT 训练相对 PyTorch DDP 最高 1.68× 加速、GPT-2 推理相对 Megatron-LM 最高 1.77× 加速。
       - **Centauri**：沿"原语、拓扑感知组、工作负载"三个维度分割集合通信，使子通信可在不同时点就绪并与依赖计算交错，在 FSDP+DP 配置下相对 ZeRO-1/2/3 实现最高 1.49× 训练吞吐量。
     - **推理流水线中的通信集成**：
       - **MegaScale-Infer**：通过注意力与专家（FFN）模块的解聚部署与 ping-pong 微批次流水线，隐藏跨模块通信，相对 TensorRT-LLM 最高提升 1.90× 每 GPU 解码吞吐量。
       - **NanoFlow**：将推理执行重构为细粒度纳米批次（nano-batch），按依赖关系调度纳米操作，暴露 GPU 计算、内存访问与通信间的并发，相对 TensorRT-LLM 平均提高 1.91× 吞吐量。

### 关键概念与指标

- **集合原语**：AllReduce（AR）、ReduceScatter（RS）、AllGather（AG）、AlltoAll（A2A）、Broadcast。
- **并行模式及其通信需求**：数据并行（DP，梯度同步）、张量并行（TP，层内部分结果聚合）、流水线并行（PP，相邻阶段激活传输）、专家并行（EP，MoE 中动态 token 路由）。
- **训练指标**：迭代时间、吞吐量、扩展效率、暴露通信时间、实现带宽。
- **推理指标**：首 token 时间（TTFT）、每输出 token 时间（TPOT）、尾延迟、请求优先级、SLO。

## 主要结论与发现

1. **集合通信优化已发生范式转变**：从加速孤立的通信原语，演变为大规模 LLM 训练与推理中的跨层次系统挑战。
2. **三层分类法有效连接碎片化研究**：通信规划（逻辑调度）→ 执行与自适应（运行时映射）→ 计算-通信协同（端到端收益），描述了一条从算法设计到系统效益的完整路径。
3. **优化必须超越单一层**：更快的原语（faster primitive）并不必然转化为端到端收益；只有当通信在关键路径之外被隐藏、或运行时能够适配硬件资源时，优化才真正发挥作用。
4. **训练与推理的集合通信需求差异显著**：训练侧重迭代时间与吞吐量，有相对稳定的通信图，适合离线规划与早期剖析；推理则受请求长度、批组成、路由决策等动态因素影响，通信直接暴露在在线服务的关键延迟路径上。
5. **开放挑战**：动态工作负载下的自适应集合通信、统一通信库（打破 NCCL、DeepEP、MegaScale-Infer 等库之间的资源隔离）、异构硬件可移植性、压缩感知的集合通信、通信卸载（DPU/SmartNIC）、以及大规模集群下的容错与可靠性。

## 对实践者的启示

- **先分析瓶颈再选择优化层次**：如果集合通信耗时主要来自拓扑不匹配的调度，应优先采用拓扑感知规划（如 BlueConnect、Themis）；如果运行时配置选择不当（如 NCCL 的 channel/protocol 配置），则可借助 AutoCCL 等自适应方法；如果通信本身已高度优化但仍暴露在关键路径上，则应考虑计算-通信协同与重叠（如 Centauri、NanoFlow）。

- **关注可编程与统一通信栈的趋势**：未来系统更可能向可编程执行接口（如 MSCCL++ 的 Primitive API）和跨库统一运行时演进，实践者在选型时应考虑与这类技术方向的兼容性。
