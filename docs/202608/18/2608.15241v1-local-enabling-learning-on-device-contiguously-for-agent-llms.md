## 摘要
设备端大语言模型智能体在本地硬件上与用户反复交互，产生对适配有价值但不应发送到远程训练器的私有轨迹。理想情况下，这类智能体应持续学习——在每次交互中自适应，而无需暂停或中断面向用户的推理——然而现有推理运行时假设权重稳定，现有强化学习系统假设资源分离，因此两者都无法支持这种连续性。我们提出了LOCAL，首个支持大语言模型智能体设备端连续学习的单GPU运行时。关键洞察在于GPU调度、适配器版本管理和KV缓存有效性不能由独立子系统处理：适配器更新会使旧版本的缓存KV张量失效，而缓存保留会影响训练可用的内存。LOCAL将适配器版本、任务优先级和缓存状态对三个协作组件可见——协作调度器、版本感知的KV缓存管理器和多智能体模型运行时——它们共享这些状态，使调度、执行和缓存维护保持一致。在配备7B级模型的单块24 GB GPU上，与FIFO相比，LOCAL将前台排队等待p95降低了3.1倍；与不可抢占训练相比，将p95首token时间（TTFT）降低了1.55倍；将发布后首次命中预填充p99降低了25.6%，跨智能体TTFT p99降低了21.9%；并在紧张的KV预算下保持后台学习持续推进。

## Abstract
On-device LLM agents interact repeatedly with users on local hardware, producing private traces that are valuable for adaptation but should not be sent to a remote trainer. Ideally, such agents would learn contiguously---adapting from every interaction without pausing or suspending user-facing inference---yet existing inference runtimes assume stable weights and existing RL systems assume separated resources, so neither can support this continuity. We present LOCAL, the first single-GPU runtime that enables contiguous on-device learning for LLM agents. The key insight is that GPU scheduling, adapter version management, and KV-cache validity cannot be handled by independent subsystems: adapter updates invalidate cached KV tensors from older versions, and cache retention affects the memory available for training. LOCAL makes adapter version, task priority, and cache state visible to three cooperating components---a cooperative scheduler, a version-aware KV-cache manager, and a multi-agent model runtime---that share this state to keep scheduling, execution, and cache maintenance mutually consistent. On a single 24 GB GPU with 7B-class models, LOCAL lowers foreground queue-wait p95 by 3.1x over FIFO, lowers p95 time-to-first-token (TTFT) by 1.55x versus non-preemptible training, cuts post-publish first-hit prefill p99 by 25.6% and cross-agent TTFT p99 by 21.9%, and keeps background learning progressing under tight KV budgets.

## 1. 论文的核心问题与整体含义

- **研究背景**：端侧 LLM 智能体在本地与用户反复交互，产生大量私有轨迹（用户纠正、偏好、工具调用结果等）。这些轨迹对模型适配很有价值，但出于隐私不应上传到远程训练器。
- **核心矛盾**：理想情况是“连续学习”：智能体在每次交互后都能持续自适应，同时不中断面向用户的推理。但现有系统无法支持这一目标：
  - **推理运行时**（如 vLLM、SGLang）假设“权重稳定”，即模型参数在服务期间不变，因此 KV cache 始终有效。
  - **强化学习 / 训练系统**（如 HybridFlow、OpenRLHF、ReaL）假设“资源分离”，即 rollout、reward、训练分别放在不同加速器上。
- **本文整体含义**：LOCAL 提出首个单 GPU 运行时，使设备端 LLM 智能体能够在同一模型实例上同时进行前台推理与后台连续学习；核心观点是 **GPU 调度、适配器版本管理、KV cache 有效性三者必须共享状态、协同处理**，不能作为独立子系统存在。

## 2. 论文提出的方法论

LOCAL 由三个协同组件组成，共享适配器版本、任务优先级、缓存有效性三类状态。

### 2.1 协作调度器（Cooperative Scheduler）

- **统一任务模型**：所有 GPU 操作都被表示为任务，包含任务类别、硬优先级、所需适配器状态、估计时长、估计峰值内存、最长不可让出区间、任务效用等元数据。
- **前台严格优先**：前台推理队列永远优先于后台任务队列；有前台任务时，不启动新的 judge、训练或 cache 维护任务。
- **协作式可中断训练**：不假设任意 GPU 内核可抢占。后台训练只在安全边界（如 mini-step、优化器提交、适配器发布前）响应中断信号，从而把前台阻塞时间限制到“到下一个安全边界的剩余时间”，而不是整个训练过程。
- **时间片感知的后台准入**：后台任务只有满足内存和可让出区间约束时才会被准入：
  - \(\hat{m}(x) + M_{reserve} \le M_{free}\)
  - \(\hat{y}(x) + \delta \le W_{bg}\)
  其中 \(\hat{m}\) 是估计内存，\(\hat{y}\) 是最长不可让出区间，\(W_{bg}\) 是后台窗口，\(\delta\) 是保守裕度。
- **在线成本估计**：对 judge、训练、prefill 时长使用指数移动平均（EMA）估计；prefill 还按前缀长度分桶记录每 token 速率。

### 2.2 版本感知 KV Cache 管理器（Version-Aware KV Cache Manager）

- **Agent 作用域 KV 身份**：KV entry 只有在以下有效性键完全匹配时才可复用：
  \[
  \kappa = (\text{token span}, \text{context namespace}, \text{adapter}, \text{adapter version})
  \]
  只有 token 相同但 adapter 版本不同，仍会被判定为 stale。
- **热度统计**：同时维护前缀热度 \(H_P(p)\) 和适配器热度 \(H_A(\nu)\)，并组合为联合 KV 热度：
  \[
  H_{KV}(e) = (\epsilon + H_P(p))(\epsilon + H_A(\nu))\left(1+\alpha_L\frac{\min(L_e,L_{\max})}{L_{\max}}\right)
  \]
  乘性形式保证：热门前缀不能保护无关 adapter；热门 adapter 不能保护无关前缀。
- **保留优先级**：
  \[
  \Pi_{keep}(e) = H_{KV}(e)\cdot \frac{\hat{C}_{recompute}(e)}{\max(1,B_e)}
  \]
  用于决定哪些 KV 值得保留、哪些应优先 evict / offload。
- **Stale-coverage prefill**：当新 adapter 版本训练完成但未发布时，先以 staged 状态存在；cache 管理器把热门前缀的新版本 prefill 作为后台任务提交，从而在新版本对前台可见前就预热 cache，降低发布后首次命中延迟。
- **优先级保留与卸载**：内存紧张时，按 \(\Pi_{keep}\) 升序卸载；先淘汰联合前缀–adapter 热度低且占用大的对象；活跃 adapter 权重和当前请求 KV 不可卸载。

### 2.3 多智能体模型运行时（Multi-Agent Model Runtime）

- **跨智能体 pre-prefill**：利用多智能体通信结构预测哪些共享上下文前缀可能被下游智能体消费，并生成调度器可见的预填充任务。
- **预填充优先级**：
  \[
  \Pi_{xpre}(c) = D_{ma}(c)\cdot H_{KV}(e_c)\cdot \hat{C}_{prefill}(e_c)
  \]
  其中 \(D_{ma}(c)\) 来自下游置信度、pending consumer 数量、缺失 token 数等。
- **内存压力卸载请求**：训练前若投影内存需求会消耗前台 reserve，则先请求 KV cache manager 卸载低优先级对象；如果不能释放足够空间，后台任务保持 pending。
- **边界约束**：跨智能体 pre-prefill 和 stale-coverage prefill 都必须经过调度器，不能绕过前台优先级；预取结果只有在 token span、namespace、adapter、version 全部匹配时才能被前台请求复用。

## 6. 论文的主要结论与发现

- **协作调度有效**：
  - Foreground-first 相比 FIFO，前台队列 p95 降低 **3.1×**，p99 降低 **3.4×**。
  - 相比 Round-robin，p95 略低，但 p99 降低 **2.1×**，训练 commit 增加 **1.6×**（34 vs 21）。
- **可中断训练改善延迟**：
  - 与不可抢占训练相比，可抢占训练将 p95 队列等待和 p95 TTFT 降低 **1.55×**。
  - 累计训练导致的前台阻塞减少 **2.6×**。
  - 代价是训练吞吐从 346.8 降至 271.8 steps/hr，下降 **21.6%**。
- **优于传统 sleep/train/wake 路径**：
  - 在 foreground-first / round-robin / FIFO 下，LOCAL 相比 vLLM full-LoRA 睡眠训练窗口，p95 queue wait 分别低 **5.9× / 12.8× / 6.3×**。
- **缓存机制有效**：
  - Stale-coverage prefill 使发布后首次命中 prefill p99 下降 **25.6%**。
  - Cross-agent pre-prefill 使跨智能体 TTFT p99 下降 **21.9%**。
- **内存压力下仍可运行**：
  - 在峰值 GPU 内存 21.6–23.5 GB 范围内，LOCAL 仍能完成 31–35 个训练 commit，且无 OOM。
  - KV 页面预算从 512 增至 1024 页，队列 p95 由 1.312s 降至 0.850s，说明内存配置通过调度准入影响延迟。

## 7. 优点

- **问题定位清晰**：准确识别“稳定权重 + 分离资源”两个假设如何阻碍端侧连续学习，问题定义完整且有实际意义。
- **系统设计统一**：将调度、缓存有效性、内存压力放在共享状态上，不是简单堆叠现有推理和训练模块。
- **版本感知 KV cache**：把 adapter identity 和 version 纳入 cache key，是该场景下 KV 复用正确性的关键，提供了明确的缓存合同。
- **协作式中断而非预抢占**：考虑到了训练内核不可任意中断的现实，采用安全边界让步，设计务实。
- **实验机制覆盖较全**：涵盖调度、训练抢占、缓存预热、跨智能体复用、内存压力等关键维度；对比了 FIFO、round-robin、vLLM sleep/train/wake 等有代表性基线。
- **指标选择贴近实际体验**：关注尾延迟 p95/p99、TTFT，而不是只看均值，符合交互式智能体的需求。

## 8. 不足与局限

- **实验外部效度有限**：仅在 tau-bench retail、xLAM-7b-r、单 GPU 设置中验证；没有在不同 agent 基准、不同模型家族、不同 GPU 上进行交叉验证。

- **实现栈绑定**：LOCAL 基于 FlashInfer，vLLM 对比并非在同一推理引擎内做细粒度配置，结果可能受实现栈影响。
