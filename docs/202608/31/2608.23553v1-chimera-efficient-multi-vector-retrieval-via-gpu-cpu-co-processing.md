## 摘要
多向量检索已成为语义搜索应用中的核心基础操作，这类应用需要进行细粒度匹配，例如信息检索、推荐系统和生物信息学。然而，其较高的计算复杂度和内存开销使低延迟检索难以实现。现有系统主要致力于优化查询延迟，但其设计仍以 CPU 为中心。尽管 GPU 具有显著的计算优势，但其有限的内存容量要求采用异构架构，即数据集驻留在主机内存中，而 GPU 作为加速器使用。现有的基于 GPU 的系统 PLAID 受 CPU-GPU 数据移动瓶颈限制，因为向量数据必须在查询时从主机内存传输至 GPU。我们提出 Chimera，一种面向多向量检索的 GPU-CPU 协同处理系统，可消除这一传输瓶颈。Chimera 将高度压缩的低精度量化编码存储在 GPU 上，同时将高精度数据保存在 CPU 内存中。在查询时，系统利用 GPU 中驻留的数据高效生成候选结果并进行筛选，随后通过 GPU-CPU 协同评分机制进一步优化结果；该机制完全避免了向量数据传输，同时支持计算重叠。在真实数据集上的实验表明，Chimera 显著优于现有方法，在相同召回率下，QPS 最高可提升 16.0 倍。

## Abstract
Multi-vector retrieval has become a core primitive in semantic search applications that require fine-grained matching, such as information retrieval, recommender systems and bioinformatics. However, its high computational complexity and memory costs make low-latency retrieval difficult. Prior systems have attempted to optimize query latency, but their designs remain CPU-centric. While GPUs offer substantial computational advantages, their limited memory capacity necessitates a heterogeneous architecture in which the dataset resides in host memory and the GPU serves as an accelerator. Existing GPU-based system, PLAID, is bottlenecked by CPU-GPU data movement, as vector data must be transferred from host memory to the GPU at query time. We propose Chimera, a GPU-CPU co-processing system for multi-vector retrieval that eliminates this transfer bottleneck. Chimera stores highly compressed, low-precision quantization codes on the GPU while maintaining high-precision data in CPU memory. At query time, it leverages GPU-resident data for efficient candidate generation and filtering, and further refines results through a GPU-CPU collaborative scoring scheme that completely avoids vector data transfer while enabling computation overlap. Experiments on real-world datasets demonstrate that Chimera significantly outperforms existing approaches, achieving up to 16.0x higher QPS at the same recall level.

# 1. 核心问题与整体含义

## 研究背景

- 多向量检索（Multi-Vector Retrieval, MVR）将一个对象表示为一组向量，而非单一向量。例如在 ColBERT 式文本检索中，查询和文档均由 token 级向量组成。
- 其常用相似度是 **Chamfer Similarity**：对于每个查询 token，在文档所有 token 中寻找内积最大的一个，再对所有查询 token 的最大值求和。这种细粒度“晚交互”机制通常比单向量检索更准确，但计算和存储代价更高。
- 多向量表示使数据规模显著膨胀：论文以 LoTTE 为例说明，若每篇文档仅使用单向量表示约需 1.2 GB，而 token 级多向量表示约需 130 GB，远超一张 V100 32 GB GPU 的显存容量。

## 核心挑战

论文聚焦于“**数据无法完全放进 GPU 显存**”条件下的低延迟多向量检索，具体有两个主要瓶颈：

1. **计算量大**
   - 对一个查询集合 \(Q\) 和文档集合 \(V\)，需要计算大量 query-token 与 document-token 间的内积，并执行 max 聚合。
   - 精确 Chamfer 相似度计算难以在大规模场景下满足实时延迟要求。

2. **CPU–GPU 数据传输成为瓶颈**
   - GPU 虽然适合大规模并行向量计算，但显存不足以容纳完整多向量语料，因此原始或高精度向量通常放在 CPU 主存。
   - 现有 GPU 系统 PLAID 在查询时需将待评分文档向量从 CPU 传到 GPU；由于多向量评分的算术强度低，这一过程容易受 PCIe 带宽限制，GPU 计算能力无法充分发挥。
   - 文中展示，在 LoTTE 上 PLAID 的传输时间可占总时延约三分之一，而 CPU 系统 IGP 的时延则接近 200 ms。

## 整体含义

Chimera 的核心意义在于：不再把 GPU 简单当作“临时拉取数据的计算加速器”，而是将 GPU 和 CPU 分别绑定到适合其存储与计算特点的工作上：

- GPU 保存极低精度、紧凑的量化码和索引，用于大规模候选生成、近似过滤；
- CPU 保存较高精度量化码，仅对少量最终候选进行精确重排；
- 查询时避免传输文档向量，只传输查询向量、少量文档 ID 和分数。

这是一种面向显存受限、PCIe 互连的异构检索系统设计。

# 2. 方法论：Chimera 的核心思想与技术细节

## 2.1 问题定义与目标函数

给定查询多向量：

\[
Q = \{q_1, q_2, \ldots, q_m\}
\]

以及文档多向量：

\[
V = \{v_1, v_2, \ldots, v_n\},
\]

论文使用 Chamfer Similarity 作为文档相关性：

\[
F(Q,V)=\sum_{q\in Q}\max_{v\in V}\langle q,v\rangle.
\]

即：

- 每个 query token 从文档 token 中取内积最大的匹配项；
- 将各 query token 的最大匹配分数相加；
- 返回得分最高的 top-\(k\) 文档。

目标是在尽量维持 Recall@\(k\) 的条件下，提高查询吞吐量（QPS）并降低延迟。

---

## 2.2 混合精度、异构存储

Chimera 的基础设计是 **hybrid-precision storage（混合精度存储）**：

| 数据类型 | 存储位置 | 用途 |
|---|---:|---|
| IVF 聚类中心、倒排列表、CAGRA 图索引 | GPU | 快速候选生成 |
| RaBitQ 的 1-bit 高位量化码 | GPU | 低成本近似打分、候选过滤 |
| RaBitQ 的 full-bit 量化码，通常为 4 bit/维 | CPU 主存 | 最终高精度评分 |
| 查询 token 向量 | 查询时传入 GPU | 驱动整个检索流程 |

其中，RaBitQ 是论文采用的向量量化方法。它先对归一化向量进行随机正交旋转，再将每一维压缩为 \(B\) bit 的编码；文中通常采用 \(B=4\)，可实现约 \(8\times\) 压缩，并保持接近未压缩向量的召回表现。

关键点在于：

- GPU 上永久驻留所有 1-bit 码及索引；
- CPU 保留完整的 4-bit 或 8-bit 码；
- 在线查询期间，**不再把文档向量码从 CPU 传到 GPU**；
- 跨设备传输只涉及查询、多批候选 ID 和低精度打分结果。

---

## 2.3 三阶段检索流水线

Chimera 的在线查询由三个阶段构成。

### 阶段一：候选生成（Candidate Generation）

目标是从全部文档中找出可能相关的初始候选集合。

流程如下：

1. 对每个查询 token，在 IVF 聚类中心中寻找最相近的 \(n_{\text{probe}}\) 个中心。
2. 与传统 IVF 不同，Chimera 不直接暴力扫描全部中心，而是在 IVF 中心之上建立 GPU 图索引 **CAGRA**。
3. 通过 CAGRA 图搜索快速定位邻近聚类中心。
4. 读取这些中心对应的倒排列表（posting lists），获得若干候选 document token。
5. 将这些 token 所属的源文档取并集，得到初始候选文档集合 \(S\)。

该设计采用更细粒度的 IVF 聚类。相比 PLAID 较粗的聚类，细粒度聚类具有更短的 posting list 和更高的选择性，减少无关文档进入后续阶段。

---

### 阶段二：候选精炼（Candidate Refinement）

候选生成通常需要保留较多文档以保证召回率，因此 Chimera 在 GPU 上利用 1-bit 编码做一次低成本过滤。

对于候选文档 \(V\)，论文计算只覆盖已取回 token 的“部分 Chamfer 分数”：

\[
F'(Q,V)=\sum_{q\in Q}
\begin{cases}
\max_{v\in V\cap L_q}\langle q,v\rangle, & V\cap L_q\neq \emptyset\\
0, & V\cap L_q=\emptyset
\end{cases}
\]

其中 \(L_q\) 是查询 token \(q\) 在候选生成阶段检索到的文档 token 列表。

其直觉是：

- 真正相关文档中，与查询 token 最接近的 token 往往已经出现在邻近 IVF 簇内；
- 因此，只根据这些已取回 token 的局部匹配分数，也能较好近似文档间的相对排序；
- 文中实验显示，该阶段在保持约 95% 候选召回的前提下，可将候选文档数减少约 \(10\times\)。

之后仅保留 top-\(k_{\text{refine}}\) 个候选进入最终评分。

---

### 阶段三：GPU–CPU 协同文档评分（Document Scoring）

这是 Chimera 消除 CPU–GPU 向量传输瓶颈的核心。

#### 基本思路

对剩余的 \(k_{\text{refine}}\) 个候选：

1. GPU 基于所有文档 token 的 1-bit 码计算完整的低精度文档分数；
2. 根据低精度分数，筛出排名靠前的 \(k_{\text{full-bit}}\) 个文档；
3. CPU 从主存读取这些文档的 full-bit 量化码，并计算更高精度的 Chamfer 分数；
4. 依据 full-bit 分数返回最终 top-\(k\)。

这样，GPU 只使用自己的 1-bit 数据，CPU 只访问自身主存的高精度数据，避免了 CPU 主存到 GPU 的文档向量搬运。

#### 分块流水化并行

若 GPU 先处理完全部候选，CPU 才能开始 full-bit 精排，CPU 会长时间空闲。为此，Chimera 将候选文档拆成 \(c\) 个 chunk：

- GPU 顺序计算每个 chunk 的 1-bit 分数；
- GPU 完成第 \(i\) 个 chunk 后，异步把低精度分数传给 CPU；
- CPU 对目前已见的前 \(i\) 个 chunk 进行排序；
- CPU 立即对当前进入 top-\(\frac{i}{c}k_{\text{full-bit}}\) 的新文档计算 full-bit 分数；
- 同时 GPU 继续处理后续 chunk。

因此：

- GPU 的低精度过滤和 CPU 的高精度评分可以重叠执行；
- CPU 无需等待全部 GPU 分数；
- 实际上可能额外评估少量 full-bit 文档，但论文测得额外开销通常很小。

---

## 2.4 GPU 内核优化

论文还实现了定制 CUDA 内核，目标是缓解该工作负载的内存带宽、线程分歧和原子操作竞争问题。

### LUT 二值内积计算

直接计算 query 浮点向量与 1-bit 文档编码的内积时，需要逐 bit 条件累加，容易引起 GPU warp 分支分歧。

Chimera 将每 4 个 bit 作为一组：

- 对每个 query token 预计算一个查找表；
- 每个 4-bit 模式对应这 4 个维度的加权和；
- 计算内积时将逐 bit 条件判断转换为查表与累加。

收益包括：

- 消除条件分支造成的 warp divergence；
- 减少重复读取 query 相关数据；
- 将 LUT 放在 shared memory 中提高复用；
- 在文档打分阶段沿查询维度进行分块，以控制共享内存占用并保持较高 occupancy。

### 分阶段的文档分数聚合

Chamfer 分数需要对每个 query token 在文档 token 上取最大值，然后跨 query token 求和。

- 在候选精炼阶段，token 按簇而非按文档组织，多个线程可能更新同一文档的同一 query-token 分数，因此使用 `atomicMax`。
- 为缓解原子操作竞争，论文将聚合操作融合到内积计算内核中，让原子更新与后续内积计算交错执行，并避免中间 token 分数数组的写回和重新读取。
- 在完整文档评分阶段，文档 token 的访问规律更规整，Chimera 先用协同线程将数据合并读取到 shared memory，再执行最大值和求和归约，以改善全局内存访问合并效率。

## 3.3 对比方法

论文对比了以下系统：

| 方法 | 类型 | 特征 |
|---|---|---|

为尽量公平比较，作者声称：

- 各方法使用相同等级的向量压缩，即通常为每维 4 bit；
- 基线索引参数依据原论文或开源实现设置，并调到最佳查询性能；
- 每个实验重复 3 次，报告平均结果。

需要注意的是：

- PLAID 和 Chimera 按单查询方式评测；
- CPU 基线则允许用多线程并发处理不同查询；
- 论文认为此设置分别符合这些方法的典型使用方式，但这也意味着不同架构下的并发策略并不完全对称。

## 5.2 充分性与客观性评价

### 较充分之处

- 三个数据集覆盖从 136 GB 到 308 GB 的多向量语料，规模足够大，能体现 GPU 显存不足时的实际问题。
- 同时覆盖吞吐、平均延迟、尾延迟、召回、MRR、NDCG、传输量、索引构建时间，而不是只报告单一 QPS 指标。
- 既比较 CPU 图索引系统，也比较 GPU 系统 PLAID 及“全 GPU 驻留”的 PLAID+，有助于区分算法优化和跨设备传输规避带来的贡献。
- 消融实验覆盖算法设计、GPU 内核优化和 CPU–GPU 协同分块，能较系统地解释性能来源。
- 作者控制了压缩位数，并明确说明实验重复 3 次取平均，具备一定可复现性与公平性意识。

### 仍不完全充分之处

- 仅使用文本检索数据集，未验证推荐系统、生物信息学等论文强调的其他多向量应用。
- 实验主要在单 GPU、单机 PCIe 异构环境下完成；尽管论文讨论了多 GPU 扩展，但没有给出多 GPU 实证结果。
- A100 仅有延迟对比，缺少完整吞吐、功耗、成本和配置细节，也没有覆盖 H100、Grace Hopper / NVLink-C2C 等不同内存互连架构。
- 论文未报告 ground-truth 的具体构建方法、精确检索代价或标注可靠性细节；这会影响对 Recall 指标绝对含义的判断。
- 作者称各系统均调至最佳查询性能，但参数搜索范围、调参预算及不同方法的复现细节有限，外部读者较难严格核验“最佳配置”的公平性。
- CPU 基线采用多线程并行查询，而 Chimera 与 PLAID 按单查询处理，虽然作者解释了设计差异，但这使系统级并发吞吐比较存在一定口径差异。
- 每项实验仅重复 3 次，对于尾延迟、吞吐波动和系统级性能研究而言，统计重复次数偏少，未报告方差或置信区间。

# 6. 主要结论与发现

- Chimera 通过在 GPU 保存 1-bit 量化码、在 CPU 保存 full-bit 码，避免了查询时将文档向量从 CPU 传到 GPU。
- 在 Recall@100 = 0.90 时，Chimera 的单查询传输量仅约 **0.04–0.09 MiB**，而 PLAID 为 **28.1–56.1 MiB**；Chimera 的传输时间低于 0.08 ms，PLAID 则需要 6.6–7.7 ms。
- 在 V100 上，Chimera 在相同召回率下持续优于 PLAID、PLAID+、IGP 和 GEM，尤其在高召回要求下优势更明显。
- 论文摘要和结论强调其相对现有方法的最高 QPS 提升为 **16.0 倍**；但表 2 中若仅与 PLAID 比较，在个别更高召回设置下报告了更大的数字，例如 LoTTE、Recall@100=0.99 时为 **59.48 倍**。这表明“16 倍”应理解为作者对主要实验口径或总体结论的保守概括，而非所有表格配置中的最大数值。
- 在 A100 上，Chimera 相比 PLAID 的平均单查询延迟降低约 **6.7–14.6 倍**。
- 候选精炼阶段可在约 95% 候选召回目标下将候选文档集合缩小约 **10 倍**。
- 协同分块评分可提高吞吐：在 LoTTE 上最佳 chunk 设置带来 1.17 倍提升，在 HotpotQA 上为 1.23 倍；但对 MS MARCO 的增益较小，说明该机制依赖 CPU 与 GPU 工作负载是否均衡。
- 内核消融显示，文档分数聚合优化比 LUT 优化更关键：禁用聚合优化可带来约 2.06–2.16 倍的延迟恶化；两者同时移除时，延迟增加约 2.24–2.40 倍。
- Chimera 的在线性能提升并非仅来自消除传输：细粒度 IVF + 图索引、候选精炼和定制 GPU 内核同样显著减少了进入高代价评分阶段的计算量。

# 7. 优点与亮点

## 系统设计亮点

- **准确识别异构检索的真正瓶颈**：论文并未仅将优化重点放在 GPU 算力，而是针对“显存不足导致向量必须跨 PCIe 搬运”的根本限制设计系统。
- **存储层次与算法流程协同设计**：1-bit 码放 GPU、full-bit 码放 CPU，不只是压缩数据，也明确匹配了各阶段的精度需求和处理器能力。
- **避免传输文档向量，而不是试图隐藏传输**：Chimera 只传输小规模控制信息、分数和文档 ID，设计上比单纯异步预取或批处理更彻底。
- **多级渐进式过滤**：候选生成、局部低精度精炼、完整低精度评分、高精度 CPU 重排逐级缩小搜索空间，能在高召回与低计算成本之间灵活调节。
- **CPU–GPU 真正并行协作**：分块协同评分避免了 CPU 等待全部 GPU 结果的问题，改善设备利用率。

## 算法与实现亮点

- 使用“**细粒度 IVF + 中心图索引 CAGRA**”兼顾 IVF 的较低内存开销和图搜索的高选择性。
- 基于 RaBitQ 的量化方案，理论上提供无偏内积估计，并比传统低精度标量量化更有机会在高召回下保持排序质量。
- LUT 二值内积和按阶段定制的分数聚合内核，针对 GPU 的分支分歧、非合并访问、shared memory 压力与原子竞争进行了具体优化。
- 论文不仅给出总体性能，也测量了传输时间、额外 full-bit 计算、chunk 数影响及索引构建时间，系统分析相对完整。

# 8. 不足与局限

## 系统与部署限制

- Chimera 的单 GPU 设计仍假设：**IVF 相关索引和全部 1-bit 文档码可以放入单张 GPU**。对于更大的语料，这一条件仍可能不成立。
- 论文提出了多 GPU 分片扩展方案，但未提供多 GPU 实验，因此其横向扩展效率、跨 GPU 合并开销和负载均衡效果尚未验证。
- 系统的价值很大程度上建立在传统 CPU 主存 + GPU 显存 + PCIe 互连之上；在统一内存或高带宽 CPU–GPU 互连平台上，PLAID 一类传输型方案的瓶颈可能发生变化，Chimera 的相对优势需要额外实测。
- CPU 最终评分仍是潜在瓶颈。若候选过滤不够准确、查询较长、文档 token 较多或高召回要求极高，CPU full-bit 重排的压力可能迅速增大。

## 方法层面的风险

- 多级近似过滤存在误剪枝风险：若真相关文档的关键 token 未在候选生成阶段被取回，后续高精度阶段无法恢复该文档。
- 1-bit 分数用于两次过滤，虽然实验支持其排序有效性，但其效果可能依赖于 ColBERTv2 表示、数据分布、token 数量和 RaBitQ 编码质量。
- 超参数较多，包括 \(n_{\text{probe}}\)、\(k_{\text{refine}}\)、\(k_{\text{full-bit}}\) 和 chunk 数 \(c\)。论文提供了调参顺序，但实际部署中不同数据集、查询长度和召回目标下仍需成本较高的参数搜索。
- 分块并行策略在最坏情况下可能产生更多 full-bit 评分；论文认为这种顺序分布很少出现，但没有提供针对极端查询或对抗性候选排序的深入测试。

## 实验覆盖与报告局限

- 只在三项文本检索基准上验证，没有直接展示在推荐、多模态检索、蛋白质检索等其他多向量任务中的效果。
- 没有报告单位查询能耗、单位吞吐成本、不同 GPU 显存容量下的性价比，因而尚不能全面判断部署经济性。
- 没有给出完整的端到端在线服务压力测试，例如高并发多请求调度、请求批处理、缓存命中、动态索引更新和长时间稳定性。
- 对比中 PLAID+ 因 MS MARCO 无法装入 GPU 而被省略，这正说明 Chimera 的显存适应性优势，但也使“无传输条件下与全 GPU 基线”的比较无法覆盖最大数据集。
- 索引构建时间虽然显著优于 IGP 和 GEM，但仍比 PLAID 更慢；对于频繁重建索引或持续增量更新的应用，该离线成本可能需要进一步评估。
- 论文未展示对更新、删除、增量插入、在线量化重编码等动态数据管理场景的支持。
