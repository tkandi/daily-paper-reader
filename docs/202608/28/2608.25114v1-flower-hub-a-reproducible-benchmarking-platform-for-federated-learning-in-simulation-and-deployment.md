## 摘要
联邦学习（FL）已成为在去中心化数据上训练模型的关键方法，然而，FL 中的基准测试仍然难以复现、比较和扩展。现有评测往往依赖定制化基础设施，以不完整的研究代码形式发布，并主要在模拟环境中进行，这限制了其可移植性和实际相关性。我们提出 Flower Hub，一个用于发布、发现和执行去中心化与联邦应用的平台。我们展示了它如何通过将基准测试封装为可执行、版本化的应用，并配以标准化元数据、固定依赖关系和显式评估工作流，从而实现可复现的基准测试。我们以一种跨多个领域的基准套件验证了这一方法，该套件覆盖 cross-silo 和 cross-device 场景，并包含医学影像、金融表格学习、法律指令微调、钓鱼 URL 检测以及音频标注等任务。我们进一步证明，同一个基准测试应用无需修改应用代码，即可在模拟和部署两种运行时环境中运行，从而支持在不同学习环境下进行统一评估。除模型质量之外，我们的基准设计还支持面向系统的报告，包括运行时和通信指标。本文推动了 FL 场景中的基准测试从临时性的代码产物，向可移植、可执行且可复用的基准应用演进。

## Abstract
Federated learning (FL) has emerged as a key approach for training models across decentralized data, yet benchmarking in FL remains difficult to reproduce, compare, and extend. Existing evaluations are often tied to custom infrastructure, released as incomplete research code, and conducted primarily in simulation, which limits portability and practical relevance. We present Flower Hub, a platform for publishing, discovering, and executing decentralized and federated applications. We show how it enables reproducible benchmarking by packaging benchmarks as executable, versioned applications with standardized metadata, pinned dependencies, and explicit evaluation workflows. We instantiate this approach with a multi-domain benchmark suite spanning cross-silo and cross-device settings, and including tasks in medical imaging, financial tabular learning, legal instruction tuning, phishing URL detection, and audio tagging. We further demonstrate that the same benchmarking application can run across both simulation and deployment runtimes without changing the application code, enabling unified evaluation across varying learning environments. Beyond model quality, our benchmark design supports system-aware reporting, including runtime and communication metrics. This work advances benchmarking in FL settings from ad hoc code artifacts towards portable, executable, and reusable benchmark applications.

## 2. 方法论：核心思想、关键技术细节、流程说明

### 2.1 核心思想

- Flower Hub 的核心是：**将联邦学习基准封装为应用（app）**，并且：
  - **应用逻辑与基础设施解耦**；
  - 基准具备**标准化元数据**、**固定依赖**、**版本管理**；
  - 同一套应用代码可在**模拟运行（simulation）**和**部署运行（deployment）**中直接执行；
  - 同时支持记录**系统级指标**与**机器学习指标**。

### 2.2 关键技术机制

- Flower Hub 建立在 Flower 基础设施上，核心组件包括：
  - **SuperLink**：中心通信协调层；
  - **SuperNode**：客户端长期运行节点；
  - **ServerApp**：定义联邦训练流程、聚合策略、评估逻辑；
  - **ClientApp**：定义本地训练、评估、预处理和数据管道；
  - **SuperExec**：负责调度和启动应用进程。
- 设计上的关键点：
  - 研究者只需要写 **ServerApp + ClientApp**，不需要自己实现底层通信/协调逻辑；
  - 通过统一命令 `flwr run`，同一应用可在模拟和部署之间切换；
  - 模拟模式下可使用 Flower Datasets 做数据划分；
  - 部署模式下客户端从本地磁盘加载数据；
  - 配置文件同时包含：
    - 任务相关设置：数据集、模型、训练超参、聚合策略；
    - 系统相关设置：划分方式、客户端采样率、轮数、资源需求等。
- Flower Hub 还提供：
  - **版本控制**：可发布多个版本，用户可指定版本运行；
  - **兼容性识别**：根据本地环境自动选择可用版本；
  - **应用签名/审查机制**：允许第三方对应用做加密签名，形成可验证的信任记录。

### 2.3 可理解的流程

- **发布流程**：
  1. 将 FL 项目整理成标准 Flower 工程；
  2. 编写 metadata、README、依赖锁定、配置文件；
  3. 通过 `flwr app publish` 发布到 Flower Hub；
  4. 平台保存版本与元数据，供后续下载和运行。
- **运行流程**：
  1. 用户通过 `flwr new @account/app` 获取应用；
  2. 通过 `flwr run @account/app` 执行；
  3. 选择 simulation 或 deployment；
  4. 客户端参与训练并返回更新；
  5. 平台记录模型指标和系统指标。
- **评测目标**不仅是模型精度，还包括：
  - 通信成本；
  - 训练时长；
  - 端到端延迟；
  - CPU/GPU 内存占用等。

## 6. 主要结论与发现

- Flower Hub 可以把联邦学习 benchmark 变成：
  - **可执行**
  - **可版本化**
  - **可共享**
  - **可复现**
  - **可在 simulation/deployment 间无缝切换**
- 从实验上看：
  - **没有单一聚合方法在所有任务上都最好**；
  - **FedProx** 在多数任务上表现最好或接近最好；
  - **FedAvg / FedAvgM** 整体较稳定；
  - **FedAdam / FedAdagrad / FedYogi** 在部分非 IID、强不平衡任务上表现不稳定甚至较差；
  - 法律微调因预训练初始化较强，FedOpt 家族在该任务上相对更能发挥；
  - 金融欺诈和音频任务更难，受强异构性和任务本身难度影响明显；
  - URL 检测相对容易，整体指标很高。
- 系统层面发现：
  - 通信成本主要由**模型参数规模**决定；
  - 总延迟中，**非训练开销**（通信、同步、预处理）非常重要；
  - 训练时间并不总是主导瓶颈，FL 评测必须同时看系统效率。

## 7. 优点

- **平台定位清晰**：不是单纯再做一个 benchmark，而是提出一个可复用的 **benchmark 平台**。
- **解决真实痛点**：
  - 复现难
  - 迁移难
  - 代码/基础设施耦合重

- **工程设计扎实**：
  - 标准包结构
  - 固定依赖
  - 版本管理
  - 元数据规范
  - 应用签名机制

  - 5 个任务，跨 5 个领域
  - 多种数据模态
  - cross-silo 与 cross-device 都覆盖
- **评价维度更完整**：
  - 不只看精度，还看通信、内存、延迟等系统指标
- **可复现性较强**：
  - 应用公开发布在 Flower Hub
  - 支持用户按版本获取并执行
- **部署导向明确**：
  - 通过同一应用代码跑通真实部署，增强实用性。

## 8. 不足与局限

- **主要是平台/基准论文，而非算法突破论文**
  - 更像基础设施和生态建设，不是提出新 FL 优化算法。
- **缺少深入消融**

  - 例如版本控制、签名机制、元数据规范对复现的定量影响没有单独分析。
- **超参数优化有限**
  - 作者明确表示没有做大规模调参；
  - 因此结果主要代表 baseline，而非各方法的最优上限。
- **部署规模仍有限**
  - 虽然验证了跨区域部署，但规模不算特别大；
  - 未覆盖更复杂、更长期运行的真实生产级联邦系统。
- **任务覆盖仍不完整**
  - 未覆盖 personalization、privacy、robustness、资源极端受限环境等更多 FL 方向；
  - 对异构计算、断连、恶劣网络条件等极端系统问题覆盖有限。
- **公平性与偏差风险**
  - 不同任务采用不同模型和训练轮数，跨任务比较只能看趋势，不能直接横向等价比较；
  - 由于只选取 6 种聚合策略，未必代表当前所有先进 FL 方法；
  - 法律任务使用参数高效微调，和其他从头训练任务并不完全同类。
- **外推性有限**
  - 结果说明平台“能跑”和“可复现”，但不等于能保证在所有现实场景都具有同样的可用性。
