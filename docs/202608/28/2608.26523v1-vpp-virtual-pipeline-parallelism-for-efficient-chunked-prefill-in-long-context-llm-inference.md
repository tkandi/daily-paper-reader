## 摘要
分块预填充流水线并行（Chunked Prefill Pipeline Parallelism, CPP）是 LLM 推理中的一项关键技术。然而，等尺寸分块会表现出不均衡的延迟，因为后续分块需要关注更长的前缀 KV cache，并产生更高的注意力计算开销，从而导致流水线空泡。现有方法通过动态分块重调大小（Dynamic CPP, DCPP）来缓解这种不均衡，但我们的测量表明，这种做法是以调度开销换取负载均衡，而在长序列上会变得不划算。在本研究中，我们提出虚拟流水线并行（Virtual Pipeline Parallelism, VPP），其保持分块大小固定，并通过虚拟阶段优化流水线布局。V 形的虚拟阶段遍历将每个分块开销较高的中间阶段与相邻分块较轻的头部和尾部阶段重叠；与此同时，异步通信和流水化打包进一步减少了通信停顿以及跨请求排空空泡。我们在 vLLM-Ascend 中实现了 VPP，并在 16 个 Ascend 910C NPU 上，对三种基于 MoE 的 LLM 进行了评估，序列长度最高达 100 万 token。VPP 在长序列上的吞吐量相比 DCPP 最高提升 13.1%，在混合工作负载上提升 6.7%，同时在短序列上保持性能不变。对于一个 512K-token 的 DeepSeek-V3.1 prefill 工作负载，VPP 将流水线空泡比从 6.4% 降至 0.1%，相较于 DCPP 实现了 98.0% 的降低。

## Abstract
Chunked prefill pipeline parallelism (CPP) is a key technique for LLM inference. However, equal-size chunks exhibit imbalanced latency, as later chunks attend longer prefix KV caches and incur higher attention costs, leading to pipeline bubbles. Existing approaches mitigate this imbalance through dynamic chunk resizing (Dynamic CPP, DCPP), but our measurements show that this trades scheduling overhead for load balancing, which becomes unfavorable on long sequences. In this study, we propose Virtual Pipeline Parallelism (VPP), which keeps chunk sizes fixed and optimizes the pipeline layout through virtual stages. A V-shaped virtual-stage traversal overlaps each chunk's expensive middle stages with the lighter head and tail stages of its neighbors, while asynchronous communication and pipelined packing further reduce communication stalls and cross-request drain bubbles. We implement VPP in vLLM-Ascend and evaluate it on three MoE-based LLMs with sequences up to 1M tokens on 16 Ascend 910C NPUs. VPP improves throughput by up to 13.1% over DCPP on long sequences and 6.7% on mixed workloads, while preserving performance on short sequences. On a 512K-token DeepSeek-V3.1 prefill workload, VPP reduces the pipeline bubble ratio from 6.4% to 0.1%, achieving a 98.0% reduction compared with DCPP.

## 1. 核心问题与整体含义（研究动机与背景）

- 本文关注的是**长上下文 LLM 推理中的 chunked prefill 与 pipeline parallelism（流水线并行）结合后，如何减少流水线空泡（bubble）并提升吞吐/TTFT**。
- 背景上，LLM 推理通常分为：
  - **Prefill**：并行处理输入 prompt，计算密集；
  - **Decode**：逐 token 生成，内存密集。
- 对长上下文请求，prefill 会占用加速器很久，造成：
  - 头阻塞（HOL blocking）
  - TTFT 增大
  - 与 decode/短请求互相干扰
- Chunked prefill 通过把长 prompt 切成多个 chunk，改善调度灵活性；但当它与 pipeline parallelism 结合形成 **CPP** 时，**等大小 chunk 会因为后续 chunk 的 KV cache 更长而逐渐变慢**，导致不同 stage 进度不一致、流水线空泡增多。
- 现有 **DCPP** 通过动态调整 chunk 大小来平衡 chunk 耗时，但作者指出：
  - 它需要 runtime cost estimation、在线校准和更复杂调度；
  - 在长序列下，**更细粒度的执行碎片化带来的调度/通信开销，可能反而抵消负载均衡收益**。
- 因此，论文的整体含义是：  
  **长上下文 prefill 的不均衡，不一定要靠“改 chunk 大小”解决，也可以通过“重排流水线布局”来吸收这种可预测的 latency 增长。**

## 2. 方法论：核心思想、关键技术细节、公式/流程

### 2.1 核心思想

- 作者提出 **VPP（Virtual Pipeline Parallelism）**：
  - **保持 chunk 大小固定**
  - 不做动态切块
  - 通过**虚拟 stage + V-shaped（V 形）遍历**重构 pipeline 的执行顺序
- 利用一个关键经验规律：  
  **在 causal attention 下，固定大小 chunk 的耗时会随着 chunk index 近似线性增长**，因为后面的 chunk 需要 attend 更长的 prefix KV cache。

### 2.2 V-shaped 虚拟阶段调度

- 文中以 2 个物理 pipeline rank、4 个虚拟 stage 为例：
  - `s0, s1, s2, s3`
  - 边界 stage 放在 `pp0`，中间 stage 放在 `pp1`
- 一个 chunk `Ck` 的执行路径为：
  - `s0(pp0) → s1(pp1) → s2(pp1) → s3(pp0)`
- 这形成了典型的 **“先前进、再折返”** 的 V 形路径。
- 其核心是把：
  - 当前 chunk 的“重”中间阶段，
  - 与前后 chunk 的“轻”头尾阶段  
  尽量重叠执行，从而填平等待窗口。

### 2.3 关键公式含义

- 作者用一个近似模型描述每个 chunk 的 stage 级 latency：
  - **`τk = (k + 1) t`**
  - 其中 `t` 表示第一个 chunk 的 per-stage latency
- 对于中间 rank `pp1` 来说，chunk `Ck` 的中间两 stage 约为：
  - **`2τk = 2(k+1)t`**
- 同时，在 `pp0` 上，可以并行安排：
  - 前一个 chunk 的尾 stage：`τk-1 = kt`
  - 后一个 chunk 的头 stage：`τk+1 = (k+2)t`
- 两者和为：
  - **`τk-1 + τk+1 = kt + (k+2)t = 2(k+1)t = 2τk`**
- 这说明：
  - **邻近 chunk 的轻阶段，能够近似匹配当前 chunk 的重阶段**
  - 从而达到 pipeline 平衡

### 2.4 两个额外优化

#### A. VPP-Async：异步通信与计算重排

- 传统 VPP 中，跨 rank 的 send/recv 是同步阻塞的，会把通信延迟暴露在关键路径上。
- 论文通过**重排 stage 执行顺序**，把原本容易形成双向通信等待的阶段错开：
  - 交换 `s3/Ck-1` 和 `s0/Ck+1` 的顺序
- 结果是：
  - 通信在对端做计算时发起
  - 使通信与计算重叠
  - 减少 exposed communication stall

#### B. Pipelined Packing：跨请求打包填充尾部空泡

- 单个请求结束时会有不可避免的 drain bubble。
- 论文利用真实 serving 场景中“请求持续到达”的特性：
  - 把**下一请求的前几个 chunk** 填进当前请求的尾部空闲窗口
- 作用：
  - 压缩跨请求排空空泡
  - 提升整体吞吐

### 2.5 实现细节

- 基于 **vLLM-Ascend** 实现
- 使用：
  - Python 实现调度控制面
  - PyTorch + HCCL 实现通信与执行
- 采用：
  - fold-back 拓扑
  - dual-queue scheduler
  - 两组交替 HCCL 通信组，避免双向传输死锁

## 6. 主要结论与发现

- **VPP 在长上下文 prefill 上优于 DCPP**
  - 长序列吞吐最高提升 **13.1%**
  - 混合负载提升 **6.7%**
- **短序列性能基本不受损**
  - 在短请求场景下，VPP 与 DCPP 整体接近
- **512K DeepSeek-V3.1 任务上效果尤其显著**
  - pipeline bubble ratio 从 **6.4% 降到 0.1%**
  - 相比 DCPP 减少 **98.0%**
- **VPP 的收益主要来自：**
  - 减少 pipeline bubble
  - 减少执行碎片化带来的计算开销
  - 提高通信-计算重叠
- **DCPP 的局限被明确揭示**
  - 在长序列下，动态切块带来的调度碎片化、额外通信与 kernel launch 开销，可能超过其负载均衡收益
- **对 sparse attention 的结论**
  - 当 attention 增长规律不再近似线性时，VPP 的效果会减弱，但通常仍优于基线

## 8. 不足与局限

- **对 attention 规律有依赖**
  - VPP 的效果建立在“chunk latency 近似线性增长”之上；
  - 若 sparse attention 或其他机制削弱这一规律，收益会下降
- **硬件与生态偏单一**
  - 实验主要在 **Ascend 910C + vLLM-Ascend** 上完成；
  - 对 NVIDIA GPU、不同通信栈或其他 serving 框架的泛化性未充分验证
- **模型类型偏 MoE**
  - 重点评估的是 MoE 模型；
  - 对纯 dense model 的适配效果没有同样丰富的实验支撑
- **并行层数较固定**
  - 论文主要演示在 **两级 pipeline（pp2）** 上的效果；
  - 更深 pipeline 下的行为虽在结论中被提及，但缺少大规模系统性验证
- **对动态到达负载的覆盖仍有限**
  - 虽然有 mixed workload，但仍属于实验合成/控制场景；
  - 真实生产流量中的突发性、长尾请求分布、异构优先级等情况未完全展开
- **工程复杂度仍存在**
  - 相比简单 CPP，VPP 引入虚拟 stage、重排、packing、双队列与异步通信管理，部署复杂度更高
