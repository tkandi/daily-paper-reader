## 摘要
大型语言模型推理系统通常为峰值负载配置资源以满足严格的延迟目标，导致流量低于峰值时大量GPU计算资源闲置。本文提出DeltaServe，一种与主机无关的协同服务设计，能在保持推理服务水平目标（SLO）的同时，将闲置的推理能力转化为LoRA微调吞吐量。DeltaServe通过一个仅需多LoRA批量支持即可集成的简洁钩子接口与现有推理引擎整合。它利用了推理预填充和LoRA微调前向传递的共享执行结构，并使用一个考虑SLO的调度器，仅在推理有足够余量时才允许并执行微调。该调度器由一个离线校准、在线细化的CUDA图感知延迟模型驱动。我们将DeltaServe与vLLM、SGLang和S-LoRA集成。在来自某公司的生产跟踪数据上，DeltaServe运行于vLLM时，在100%满足推理SLO的条件下，比LLMStation的微调吞吐量高出2.9倍，而LLMStation的SLO合规性为85%。与运行vLLM+torchtune的基线相比，DeltaServe在无需额外硬件且完全满足SLO的情况下，微调吞吐量提升了39%。

## Abstract
LLM serving systems are provisioned for peak load to meet strict latency targets, leaving substantial GPU compute idle whenever traffic falls below peak. We present DeltaServe, a host-agnostic co-serving design that converts this idle inference capacity into LoRA fine-tuning throughput while preserving inference service-level objectives (SLOs). DeltaServe integrates with existing inference engines through a compact hook interface that requires only multi-LoRA batching support. It exploits the shared execution structure of inference prefill and LoRA fine-tuning forward passes, and uses an SLO-aware scheduler to admit and execute fine-tuning only when sufficient inference headroom is available. The scheduler is driven by a CUDA-graph-aware latency model calibrated offline and refined online. We integrate DeltaServe with vLLM, SGLang, and S-LoRA. On a production trace from Company X, DeltaServe on vLLM delivers 2.9x higher fine-tuning throughput than LLMStation at 100% inference SLO compliance, versus 85% for LLMStation. It also achieves 39% higher fine-tuning throughput than a baseline running vLLM+torchtune, using no additional hardware and maintaining full SLO compliance.

### 2. 方法论：核心思想与关键技术
DeltaServe 的关键设计围绕“复用推理前向路径、解耦微调后向计算、精细SLO感知调度”展开，具体包括：

- **主机无关的集成架构**：仅要求主机推理引擎支持多LoRA批量处理（multi‑LoRA batching），以一组简洁的钩子（hooks）附加到现有引擎（如vLLM、SGLang、S‑LoRA）上，而不修改其调度内核或客户端请求路径。
- **利用推理预填充与前向传播的同构性**：将LoRA微调的前向步骤伪装成一次性的“仅预填充”请求，与正在进行的推理批次合并执行。微调样本像普通请求一样进入主机的前向流水线，完成激活捕获后立即退役，不对客户端可见。
- **SLO感知的准入调度器**：
    - 建立 **CUDA图感知的解析延迟模型**：通过公式 \( T \approx \alpha \sum_i (n_i + B_d)^2 + \beta (T_{in} + B_d) + \gamma T_{ft} + \varepsilon K + c \) 预测混合批次的执行时间，并对CUDA图回放（graph）与即时执行（eager）两种模式分别拟合系数。
    - 将SLO（如TTFT、TPOT）转化为**动态余量预算** \(\Delta_{\text{budget}} = T_{\text{SLO}} - (t_{\text{now}} - t_{\text{arrival}})\)，据此决定每个步骤可接纳的微调token数量。
    - 调度算法（Algorithm 1）在反向子进程运行、激活缓冲区满、无推理余量等情况下自动抑制微调准入；优先选择较短微调序列，在预算和缓冲容量内贪婪接纳。
- **解耦的反向执行子进程**：微调的反向传播、梯度计算和优化器更新运行在独立的GPU子进程（基于CUDA MPS）中，与推理主机分离CUDA上下文。子进程通过零拷贝的GPU共享内存访问激活与模型权重。当推理预填充出现时，反向子进程会在每个Transformer层边界被抢占，将GPU立即让给推理；仅在解码阶段与之并发。
- **微调前向中断**：若推理请求在纯微调前向步骤执行期间到达，DeltaServe 在层边界中止微调前向，丢弃部分激活，并将样本退回池中，随后立即调度推理，以降低尾延迟。

### 7. 优点
- **设计轻量且通用**：不侵入式修改主机引擎，仅依赖multi‑LoRA批量处理，便于迁移到不同推理系统，降低落地门槛。
- **调度模型精细**：解析延迟模型区分CUDA图与即时执行模式，在线自适应校准，使准入决策准确率高。
- **干扰解耦彻底**：反向计算以子进程、层边界抢占方式运行，将微调对推理的主要干扰（尤其预填充阶段）降至最低。
- **实验扎实**：结合合成负载与真实生产数据，多引擎集成和消融研究充分证明方法的有效性与普适性。
- **资源效率突出**：在不增加任何GPU的前提下，将闲置算力转化为实际生产价值（微调吞吐），并严格保证在线服务的SLO。
