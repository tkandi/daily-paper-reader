## 摘要
近似最近邻搜索（ANNS）在十亿级向量数据集上已成为现代检索系统的基础算子，支持大规模推荐、语义搜索和LLM/RAG工作负载。尽管GPU为批量向量搜索提供了大规模并行性和高带宽内存，但其有限的显存容量使得完全常驻GPU的十亿级索引难以部署。在CPU-GPU异构设计中，将基向量保留在主机内存可以避免容量限制，但天真地将细搜索卸载到GPU会引入新瓶颈：大量基向量数据必须通过PCIe传输。我们提出InSituANN，一个基于IVF的ANNS引擎，可在单个商用GPU上实现十亿级向量搜索。InSituANN将原始基向量保留在主机内存中，原地执行细搜索，并使用GPU进行紧凑路由和可选剪枝。因此，查询处理避免了高维基向量的PCIe传输，同时保留了IVF的简洁性。除查询性能外，我们进一步为InSituANN设计了超快的IVF构建路径。在SIFT-1B上，InSituANN在5.2分钟内构建IVF索引，比实测的30.4小时HNSW构建快约350倍。在十亿级数据集上匹配召回率时，InSituANN的端到端吞吐量比受PCIe限制的Rummy基线提高了104.9倍至4298.2倍，在SIFT-1B和DEEP-1B上比DiskANN提高了2.4倍至4.6倍。加上强大的召回率-吞吐量权衡和比基于图的方法更低的索引空间，这些提升使得十亿级检索在成本高效的硬件上变得实用。我们在https://github.com/mindtravel/InSituANN-OpenSource开源InSituANN。

## Abstract
Approximate nearest neighbor search (ANNS) over billion-scale vector datasets has become a foundational operator for modern retrieval systems, powering large-scale recommendation, semantic search, and LLM/RAG workloads. Although GPUs offer massive parallelism and high-bandwidth memory for batched vector search, their limited VRAM capacity makes fully GPU-resident billion-scale indexes difficult to deploy. In CPU-GPU heterogeneous designs, keeping the base vectors in host memory avoids this capacity limit, but naively offloading fine search to the GPU introduces a new bottleneck: large volumes of base-vector data must be streamed over PCIe.   We present InSituANN, an IVF-based ANNS engine that enables billion-scale vector search on a single commodity GPU. InSituANN keeps original base vectors in host memory, performs fine search in situ, and uses the GPU for compact routing and optional pruning. As a result, query processing avoids PCIe transfers of high-dimensional base vectors while retaining the simplicity of IVF. Beyond query performance, we further design an ultra-fast IVF construction path for InSituANN. On SIFT-1B, InSituANN builds the IVF index in 5.2 minutes, about 350x faster than the measured 30.4-hour HNSW build. At matched recall on billion-scale datasets, InSituANN improves end-to-end throughput by 104.9x-4298.2x over the PCIe-bound Rummy baseline and by 2.4x-4.6x over DiskANN on SIFT-1B and DEEP-1B. Together with strong recall-throughput trade-offs and lower index space than graph-based alternatives, these gains make billion-scale retrieval practical on cost-efficient hardware.   We open-source InSituANN at https://github.com/mindtravel/InSituANN-OpenSource.

## 1. 论文的核心问题与整体含义

- **研究背景**：十亿级向量近似最近邻搜索（ANNS）是推荐、语义搜索、LLM/RAG 等系统的基础算子。GPU 并行性强、显存带宽高，但单一商用 GPU 显存容量无法容纳十亿级原始向量（如 SIFT-1B 的 float32 格式占 512 GB，8-bit 格式占 128 GB）。
- **核心矛盾**：在 CPU-GPU 异构设计中，若将基向量留在主机内存、把细搜索卸载到 GPU，则必须在查询时通过 PCIe 批量搬运候选向量。例如仅取 SIFT-1B 的 2% 候选，就要传输 2.56 GB，在 PCIe 4.0 x16 上至少需要 81 ms，远超 GPU 本地计算时间，PCIe 成为新瓶颈。
- **整体含义**：InSituANN 重新审视 IVF 结构，提出“阶段感知放置”思想：GPU 只做紧凑、规则的粗路由和可选剪枝，CPU 在主机内存中原地扫描原始向量进行细搜索，从而避免高维基向量的 PCIe 传输。这使得十亿级向量检索可以在单块商用 GPU + 大容量主机内存的廉价硬件上高效部署，同时保持 IVF 的简单性、更新友好性和低索引开销。

## 2. 论文提出的方法论

- **整体架构**：基于 IVF 索引，分为两个互补模式：
  - **InSituANN-Flat**：GPU 执行质心粗搜索，返回 probe 列表；CPU 直接扫描主机内存中的对应原始向量，计算精确距离完成最终排序。
  - **InSituANN-PQ**：在 Flat 基础上增加一层残差 PQ（Product Quantization）剪枝。GPU 扫描紧凑的残差 PQ 码，返回有界候选 ID；CPU 再对候选原始向量做精确重排。
- **关键技术细节**：
  - **GPU 粗搜索**：将查询-质心距离计算转化为批量稠密矩阵运算（利用 Tensor Core），并在 GPU 上完成 top-P 质心选择，只返回列表 ID 和可选距离，避免传输全距离矩阵。
  - **更细的 IVF 分区**：使用较大的质心数量（十亿级规模使用约 0.5M 个质心）来缩短倒排列表，降低 CPU 扫描量；额外的路由开销由 GPU 稠密计算吸收。
  - **CPU 原位细搜索**：向量按列表主序连续存储，CPU 顺序扫描主机内存；使用 AVX-512/FMA 向量化 L2 距离内核；对同一批查询共享同一被访问列表（touched-list scheduling），一个向量加载后最多与 4 个查询同时计算。
  - **残差 PQ 剪枝**：对每个基向量编码残差 \(x - c(x)\)（相对于所属质心），残差动态范围更小，量化精度更高。GPU 根据查询残差构建 LUT，扫描 PQ 码计算近似 ADC 距离，用层次合并（chunk→group→query）逐步缩减候选，最终只返回每个查询最多 \(N_{rerank}\) 个候选 ID。
  - **紧凑 PQ 码卸载**：质心路由状态只占几百 MB，将剩余空闲 GPU 显存用于存放紧凑 PQ 码（例如 1.4B 向量 20 字节码共 28 GB），从而在 GPU 端完成剪枝，原始向量仍留在主机内存。
  - **流水线调度**：GPU 处理下一批查询的路由/剪枝时，CPU 同时对上一批查询进行精确重排，隐藏设备空闲时间。
- **超快索引构建**：
  - 质心训练使用 5M 子集（而非全量数据），减少 Lloyd 迭代中的向量分配次数。
  - 使用 CAGRA 图仅建立在质心表上（0.5M 节点），加速训练样本和全量数据的质心分配。
  - “Ultra-fast”模式进一步减少 Lloyd 迭代次数、降低 CAGRA 搜索预算、增大训练/分配批次，SIFT-1B 总构建时间 5.2 分钟，且构建后丢弃质心图，不保留十亿节点图。
- **更新机制**：采用快照-增量设计，插入向量追加到列表局部 delta 缓冲区并定期发布，删除通过 tombstone 位图标记，后台合并重建，避免在线路径上的图重连或原地列表修改。

## 6. 论文的主要结论与发现

- **性能提升**：在十亿级数据集匹配 Recall@10 时，InSituANN-PQ 相比 Rummy 端到端吞吐量提升 104.9×–4298.2×；相比 Faiss-CPU-IVFPQ 提升 4.1×–47.8×；相比 DiskANN 在 SIFT-1B 和 DEEP-1B 上提升 2.4×–4.6×；相比 HNSW 在高召回区提升最高 16.2×。
- **延迟改进**：InSituANN 的批处理延迟在毫秒级，而 Rummy 达到秒级；PQ 模式延迟分布更紧凑，Flat 模式在高召回或某些数据集（如 SPACEV-1B）上更具优势。
- **构建效率**：Ultra-fast 模式在 SIFT-1B 上 5.2 分钟完成 IVF 构建，是 HNSW 的约 350 倍；Fast 模式 11.5–13.4 分钟，DiskANN 需要 26.6–40.3 小时。
- **模式互补**：PQ 模式在剪枝可靠时提供最高吞吐；Flat 模式在极高召回或 PQ 质量下降时扩展前沿，两者结合覆盖更广的召回-吞吐需求。
- **更新开销可控**：快照-增量更新对 Recall 影响小于 0.002，Flat 模式大批次吞吐开销低至 0.57%，PQ 模式小批次约 21%，大批次降至 4–7%。

## 7. 优点

- **硬件匹配的设计哲学**：将密集路由放在 GPU，将带宽受限的向量扫描放在数据所在的 CPU，从根源上消除 PCIe 基向量传输。
- **充分利用空闲 GPU 显存**：用紧凑 PQ 码在 GPU 上做剪枝，既减少了 CPU 扫描量，又没有破坏“原始向量留驻主机”的原则。
- **极快的构建速度**：通过子集训练 + 质心图辅助分配，实现分钟级十亿级索引构建，适合需要频繁重建或数据新鲜度高的场景。
- **低索引空间**：不保留十亿节点图，仅需质心表、列表元数据和可选紧凑 PQ 码，远低于 HNSW/DiskANN 等图方法的存储开销。
- **更新友好**：快照-增量设计支持轻量插入/删除，无需图重连或原地重排。
- **实验全面**：包含多种数据集、多种基线、消融、延迟分布、构建时间、更新和硬件移植性，论证充分。
- **开源**：代码公开，可复现性较好。

## 8. 不足与局限

- **基线覆盖不完整**：FusionANNS 和 BANG 未能纳入定量比较，可能遗漏与最新 GPU 系统的直接对比；PilotANN 仅用于 100M 数据集。
- **特定数据集上 PQ 效果有限**：SPACEV-1B 上残差 PQ 剪枝质量下降较早，Flat 模式才能达到最高召回，说明 PQ 路径的普适性有一定限制。
- **更新场景下 PQ 小批次开销较高**：10M 插入/删除时 PQ 模式在批次大小 8 下吞吐下降约 21–22%，可能影响低延迟小批次更新负载。
- **硬件单一**：主要结果基于 RTX 5090 和 Intel Xeon 平台，H100 移植性实验只覆盖 Flat 的延迟和 PQ 的部分吞吐，未系统比较不同 CPU 内存带宽或 NUMA 架构的影响。
- **未讨论多 GPU 或分布式扩展**：设计针对单 GPU + 大内存主机，对更大规模或需跨节点部署的场景未提供方案。
- **查询类型聚焦 L2 距离**：文中主要讨论 L2 搜索，对内积、余弦相似度等常见度量是否同样适用未详述。
- **超快构建可能牺牲路由质量**：Ultra-fast 减少迭代和搜索预算，虽然构建加速明显，但可能对极高召回率下的搜索质量有微弱影响，论文未量化该损失对最终 Recall-QPS 前沿的影响。
