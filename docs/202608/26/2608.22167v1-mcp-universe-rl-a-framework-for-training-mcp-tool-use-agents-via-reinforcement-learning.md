## 摘要
强化学习（RL）已成为提升大语言模型（LLMs）工具使用能力的有效方法，但现有大多数 RL 框架止步于策略更新。对每个新领域，用户都面临两个系统级难题：为数百条并发轨迹各自搭建隔离环境并接入训练，以及调度 rollout，使 GPU 在长时间、多轮次且大量时间阻塞于缓慢工具调用的 episode 中保持忙碌。我们提出 MCP-Universe RL（MCP-U RL），一个开源框架，接管这两项工作。它采用模型上下文协议（MCP）作为与环境交互的接口，使任何已作为 MCP 服务器暴露的工具无需任何 RL 专用集成代码即可接入训练。该框架一次性构建了两个缺失层，并跨领域复用：环境编排层通过可插拔的容器后端来供应、隔离和回收 MCP 环境；rollout 编排层采用分阶段流水线重叠执行多个轨迹，使 GPU 在 episode 等待工具时保持忙碌。后端无关的训练层随后通过现有 RL 后端应用更新，并集成 veRL 和 slime。仅需一个配置、只更改任务规范，我们就在 gpt-oss-20b 上训练了软件工程、深度研究和通用工具使用智能体，并在所有三个任务上提升了任务奖励。

## Abstract
Reinforcement learning (RL) has become an effective way to improve the tool-use ability of large language models (LLMs), but most existing RL frameworks stop at the policy update. For every new domain, the user is left with two hard systems problems: standing up an isolated environment for each of hundreds of concurrent trajectories and connecting it to training, and scheduling the rollout so that the GPU stays busy across long, multi-turn episodes that spend much of their time stalled on slow tool calls. We present MCP-Universe RL (MCP-U RL), an open-source framework that takes over both. It uses the Model Context Protocol (MCP) as the interface to the environment, so any tool already exposed as an MCP server plugs into training with no RL-specific integration code. It builds the two missing layers once and reuses them across domains: an environment-orchestration layer that provisions, isolates, and recycles the MCP environments over a pluggable container backend, and a rollout-orchestration layer whose staged pipeline overlaps trajectories to keep the GPU busy while episodes wait on tools. A backend-agnostic training layer then applies the update through an existing RL backend, with veRL and slime integrations. With one configuration, changing only the task specification, we train software-engineering, deep-research, and general tool-use agents on gpt-oss-20b and improve task reward in all three.

- **核心问题**：现有强化学习（RL）框架大多只负责策略更新，但在训练工具使用智能体时，用户还要在每个新领域重复搭建两套系统：
  - **环境编排层**：为数百条并发轨迹分别创建、隔离、回收有状态环境，避免状态冲突导致奖励错误。
  - **Rollout 编排层**：在多轮、工具调用频繁且耗时的 episode 中调度 GPU，避免 GPU 在等待工具时长时间空闲。
- **整体含义**：论文提出 **MCP-Universe RL（MCP-U RL）**，一个开源框架，以 **Model Context Protocol（MCP）** 作为统一环境接口，一次性构建上述两个缺失层并跨领域复用。这样，新增领域只需要编写任务规范，而不需要为 RL 集成写额外代码。

## 2. 论文提出的方法论

- **统一环境接口**：任何工具只要暴露为 MCP 服务器，就能直接接入训练，无需 RL 专用集成代码。所有领域都通过同一个 MCP 接口进入共享训练循环。
- **三层架构**：
  - **环境编排层（Environment-Orchestration Layer）**：
    - 负责环境的创建、隔离、回收与复用。
    - 提供 `create`、`reset`、`health_check`、`destroy` 等 provisioner 接口，支持可插拔容器后端（如 Docker 和 daemonless/Apptainer 后端）。
    - 对有共享配置的环境采用预暖池复用；对每个任务需要不同镜像的环境按需创建。
    - 环境在 episode 和评估期间保持存活，因为奖励通常从实时环境中读取。
  - **Rollout 编排层（Rollout-Orchestration Layer）**：
    - 将每个 episode 组织为 **Acquire → Run → Eval** 三阶段流水线，重叠执行多条轨迹。
    - 记录 token 级轨迹，标记可训练 token，并运行任务评估器获得奖励。
    - 通过 **per-stage concurrency** 配置，为不同阶段设置不同数量的 worker：Run 阶段以 GPU 为主，Acquire 阶段以 CPU/内存为主；默认让 Run worker 数量至少是 Acquire 的两倍，从而在保持内存预算不变的情况下提高 GPU 利用率。
    - 支持 **colocated** 和 **fully asynchronous** 两种 GPU 放置方式：前者共享 GPU 并交替执行 rollout 与更新；后者在独立 GPU 上并行执行，并使用队列流水线，采用一步 off-policy 更新。
  - **训练引擎层（Training-Engine Layer）**：
    - 将 rollout 批次转换为后端无关形式：prompt 和 response token id、可训练 mask、每轨迹奖励。
    - 提供 **veRL** 和 **slime** 的适配器；新增后端只需写适配器。
- **任务规范（Task Specification）**：
  - JSON 格式，包含 `mcp_servers`、`instruction`、`evaluators` 三个必需字段。
  - 对有状态领域，可添加 `dockerfile_path`、`build_args`、`prepares`、`cleanups` 等可选字段。
  - 评估器和钩子通过命名注册表函数引用，扩展新领域只需新增函数并在任务规范中引用。

## 3. 实验设计

- **训练策略**：

  - 奖励为二值，来自各任务评估器
- **三个训练领域**：
  - **软件工程（Software Engineering）**：
    - 数据集：R2E-Gym，真实 GitHub issue 修复任务，每个任务有容器镜像和隐藏测试套件。

  - **通用工具使用（General Tool Use）**：

    - 评估器通过 SQL 或代码 verifier 查询应用最终数据库状态，返回二值奖励。
- **Rollout 吞吐实验**：
  - 在软件工程负载上测量 throughput。
  - 固定 Acquire worker = 24 和 live environment = 120，改变 Run worker 数量（24、48、64、96、120）观察吞吐变化。
  - 比较 colocated 与 fully asynchronous 两种 GPU 放置方式。

## 6. 论文的主要结论与发现

- 仅用一种框架配置、只改变任务规范，即可在三个差异很大的领域训练工具使用智能体，并提升任务奖励。
- 训练过程中，智能体学会了进行更多调查性轮次、读取更多页面、调用更多工具，表现为响应长度显著增长。
- 各领域奖励提升：
  - 软件工程：成功率约从 0.11 → 0.43，峰值接近 0.6；响应长度从 13k → 33k token。
  - 深度研究：成功率约从 0.22 → 0.52，峰值达 0.65；响应长度从 <3k → 约 40k token。
  - 通用工具使用：成功率约从 0.48 → 0.55，峰值接近 0.7；响应长度从 1k → 超过 5k token。
- Rollout 解耦（给 Run 阶段更多 worker）使吞吐从 147 tok/s 提升到 410 tok/s，**约 2.8×**，且不增加 live environment 数量。
- Fully asynchronous 放置相比 colocated 放置，端到端训练吞吐约提升 2×（572s/step vs 1164s/step，steps/h 为 6.3 vs 3.1）。

## 7. 优点

- **接口统一**：以 MCP 作为唯一环境接口，极大降低了新领域接入门槛，无需为每套工具编写 RL 集成代码。
- **基础设施复用**：环境编排和 rollout 编排层一次构建、跨领域复用，解决了工具使用 RL 的重复工程问题。
- **可配置的调度系统**：per-stage concurrency 根据资源需求解耦 GPU 与 CPU/内存，在内存预算不变的情况下显著提升吞吐。
- **后端无关的训练层**：集成 veRL 和 slime，并通过适配器支持其他后端，增强了框架的灵活性与可扩展性。
- **开源与可复现性**：代码以 Apache-2.0 发布，提供三个领域的可运行配置，声称可复现论文中的训练曲线。
- **实验覆盖广泛**：三个领域的任务在环境状态、工具类型、评估方式上差异明显，能够较好地展示通用性。
