## 摘要
在有限硬件上训练大语言模型正日益成为跨 GPU 计算、主机内存、PCIe 传输和存储带宽的调度问题。现有卸载系统减少了 GPU 驻留，MegaTrain 表明 CPU 主导的层流式执行器可以在单个 GPU 上训练大模型，但固定检查点与放置启发式仍使通信暴露在关键路径上。我们提出 LazyTrain，一个位于层流式执行器之上的优化层。LazyTrain 将检查点选择、激活放置、重计算以及 CPU-GPU-NVMe 通信重叠形式化为混合整数调度问题，并在训练期间执行求解得到的策略。它还进一步将 8 位优化器状态与快速梯度裁剪耦合为单个混合 8 位算子：状态压缩降低优化器状态内存，而快速裁剪抵消额外的 CPU 端更新开销。在 H800 上从 Qwen2.5-3B 到 Qwen3.6-27B 的实验中，LazyTrain 相比匹配基线运行将持续 TFLOPS 提升约 1.24 倍；RTX 3090 实验同样在每个模型规模上将最大可行批量大小提高一档。在主要的 Qwen3.6-27B H800 MetaMathQA 运行中，LazyTrain 在批量大小 72 时达到 219.95 TFLOPS 和 1361 tokens/s，GPU 内存峰值为 68.84 GB，并在完整评估集上获得 95.42% 的精确匹配准确率。源代码见 https://github.com/DataArcTech/LazyTrain。

## Abstract
Training large language models on limited hardware is increasingly a scheduling problem across GPU compute, host memory, PCIe transfer, and storage bandwidth. Existing offloading systems reduce GPU residency, and MegaTrain shows that a CPU-master layer-streaming executor can train large models on a single GPU, but fixed checkpointing and placement heuristics still leave communication exposed on the critical path. We propose LazyTrain, an optimization layer over a layer-streaming executor. LazyTrain formulates checkpoint selection, activation placement, recomputation, and CPU-GPU-NVMe communication overlap as a mixed-integer scheduling problem, then executes the solved policy during training. It further couples 8-bit optimizer states with fast gradient clipping as a single Hybrid 8-bit operator: state compression reduces optimizer-state memory, while fast clipping counteracts the additional CPU-side update overhead. Across H800 experiments from Qwen2.5-3B to Qwen3.6-27B, LazyTrain improves sustained TFLOPS over matched baselines runs by approximately 1.24$\times$; RTX 3090 experiments likewise increase the maximum feasible batch size by one at each model scale. In the primary Qwen3.6-27B H800 MetaMathQA run, LazyTrain reaches 219.95 TFLOPS and 1361 tokens/s at batch size 72, peaks at 68.84\,GB of GPU memory, and obtains 95.42\% exact-match accuracy on the full evaluation split. The source code is available at https://github.com/DataArcTech/LazyTrain.

## 1. 论文的核心问题与整体含义

- **研究背景**：大语言模型（LLM）训练在有限硬件上越来越依赖 GPU 计算、主机内存、PCIe 传输和存储带宽的联合调度。模型参数、梯度、优化器状态和激活值往往超出单卡 GPU 内存，必须借助 CPU 内存和 NVMe 存储。
- **现有方法局限**：ZeRO 系列、FSDP、Gemini 等通过分片和卸载降低 GPU 驻留；MegaTrain 进一步采用 CPU 主导的层流式执行器，在单 GPU 上训练大模型。但 MegaTrain 的激活调度仍是**固定启发式**：检查点间隔、激活放置、重计算块和传输窗口不联合搜索，导致 CPU-GPU 或 NVMe 传输暴露在关键路径上，通信开销无法被计算窗口隐藏。
- **核心问题**：有限资源训练的本质是一个**受约束的调度问题**。瓶颈不仅是张量放不进 GPU 内存，而是计算窗口、CPU-GPU 流量、参数/梯度移动、可能的 NVMe 激活溢出对共享资源的竞争。需要一种方法在满足内存上限的同时，将激活传输尽量隐藏在计算窗口内。
- **论文目标**：提出 LazyTrain，在层流执行器之上构建优化层，将检查点选择、激活放置、重计算和 CPU-GPU-NVMe 通信重叠形式化为混合整数规划（MILP），离线求解并执行策略，实现更高吞吐和更大可行批量。

## 2. 方法论

### 2.1 核心思想
- LazyTrain 保持 MegaTrain 风格的**层流式执行器**：参数和优化器状态驻留 CPU，逐层流入 GPU 计算，梯度回传 CPU。
- 训练前将调度问题编码为 MILP，用 SCIP 求解，得到检查点路径、激活存储层级（GPU HBM / CPU DRAM / NVMe）和传输窗口分配策略；运行时直接执行固定策略。
- 目标不是最大化卸载量，而是**最小化重计算代价 + 增量暴露通信**，即只惩罚无法被计算隐藏的激活传输。

### 2.2 关键变量与约束
- **层边界空间**：对 L 层 Transformer，边界集合 B = {0, …, L}；边 (s, e) 表示一个反向重计算块，边界 s、e 物化，中间层可重计算。
- **二元变量**：
  - `x_{s,e}`：是否选择重计算边 (s, e)；
  - `z_i`：边界 i 是否物化；
  - `g_i, c_i, n_i`：物化边界放置于 GPU HBM、CPU DRAM 或 NVMe，满足 `z_i = g_i + c_i + n_i`。
- **约束**：
  - 路径流约束：所选边形成从输入边界 0 到输出边界 L 的一条合法路径；
  - 容量约束：各层激活在各存储层的总占用不超过预算；
  - PCIe 带宽约束：每个计算窗口内激活 D2H/H2D 流量 + 强制参数/梯度流量不超过可隐藏容量；超出部分记为暴露通信 `ε`；
  - NVMe 端点带宽约束：NVMe 读写流量不超过 SSD 端点容量，避免慢 I/O 暴露。
- **目标函数**：
  \[
  \min \sum_{(s,e)\in E} R_{s,e}x_{s,e} + \lambda_z\sum_i z_i + \lambda_n\sum_i n_i
  + \sum_w \left(\frac{\Delta^D_w}{B_D}+\frac{\Delta^H_w}{B_H}+\frac{\epsilon^W_w}{B_W}+\frac{\epsilon^R_w}{B_R}\right)
  \]
  其中 `R_{s,e}` 为重计算代价，`Δ` 为激活引起的增量暴露通信（减去无激活卸载时的基线滑差），`λ_z, λ_n` 为避免不必要物化和 NVMe 的微小惩罚项。
- **求解流程**：算法按模型配置、批量大小、内存预算、带宽窗口构造 MILP，调用 SCIP（PySCIPOpt）分支定界求解，保留可行或最优调度。

### 2.3 Hybrid 8-bit 算子
- 将少量优化器状态（如 2% 参数切片）以 **8-bit AdamW** 格式存储在 CPU，块大小 4096；大部分参数仍由 DeepSpeed CPUAdam 处理。
- 8-bit 状态压缩降低 CPU 优化器内存，但引入量化/反量化和 CPU 更新开销；为此耦合**快速梯度裁剪**：使用 CPU foreach 核计算每张量范数，以 FP32 聚合全局范数，减少裁剪开销，抵消 8-bit 更新成本。
- 两者作为单一组件“Hybrid 8-bit operator”进行消融。

## 6. 主要结论与发现

- **吞吐提升**：H800 上 27B 匹配实验中，LazyTrain 达到 219.95 TFLOPS / 1361 tokens/s，较 MegaTrain 的 176.90 TFLOPS / 1075.8 tokens/s 提升约 **1.24 倍**。
- **可行批量扩展**：RTX 3090 上每个模型规模最大可行批量大小比 MegaTrain 增加 1；ZeRO-3 Offload 在 14B/27B 上 batch size 1 即 OOM。
- **消融主因**：移除 MILP 调度导致吞吐从 219.95 降至 193.17 TFLOPS（**-12.2%**），为最大退化；移除 Hybrid 8-bit 仅降至 219.29 TFLOPS（-0.3%），说明 MILP 调度是主要贡献。
- **精度保持**：27B 完整评估集精确匹配准确率 95.42%，与基线相当或略高。
- **NVMe 调度有效性**：最终 27B 调度使用 30 GPU / 21 CPU / 1 NVMe 检查点，求解器报告零增量暴露通信，说明在扩展可行空间的同时不牺牲计算重叠。

## 7. 优点

- **问题建模创新**：将激活调度从固定启发式提升为 MILP 优化，统一考虑检查点拓扑、层级放置、重计算和通信重叠。
- **目标设计合理**：最小化“重计算 + 增量暴露通信”，避免单纯追求卸载量，符合实际吞吐优化目标。
- **系统集成完整**：优化层与层流执行器解耦，离线求解、运行时简单执行；Hybrid 8-bit 算子作为整体组件，减少 CPU 端内存与更新开销。
- **实验说服力强**：跨 3B–27B 多规模、H800/RTX 3090 双硬件、多基线、消融与精度评估，主实验为匹配配置，结果清晰。
- **开源与可复现**：提供源代码、调度配置和评估脚本。

## 8. 不足与局限

- **硬件范围有限**：仅单 GPU H800 和 RTX 3090，未覆盖多 GPU、多节点或 TP/PP 并行场景。
- **实验重复性不足**：多数结果来自单次运行，未报告多次重复的均值和方差，可能影响稳定性结论。

- **调度静态性**：MILP 离线求解，不随运行时带宽波动自适应调整；在线调度仍为未来工作。
