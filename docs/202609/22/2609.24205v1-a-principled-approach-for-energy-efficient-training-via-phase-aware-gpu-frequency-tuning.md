## 摘要
现代人工智能模型训练带来了前所未有的计算需求，已成为数据中心能源消耗的主要来源之一。然而，训练过程中消耗的能源有相当一部分并未转化为有效计算，这是由于训练流水线各环节存在瓶颈。我们提出 PAFT，一种具备阶段感知能力且可动态适应的 GPU 频率调节系统，能够在仅产生极小性能开销的情况下，降低训练工作负载的能源消耗。PAFT 背后的关键洞见是：瓶颈不仅是性能问题，也代表着能源优化机会。当 GPU 受制于停顿时，PAFT 会主动降低其时钟频率，使其运行速度与受瓶颈影响的设备保持一致，从而在不影响执行时间的情况下节省能源。PAFT 通过持续监测流水线行为并实施细粒度的频率调整来实现这一目标，同时适应工作负载和系统的变化。在十二种广泛使用的模型上进行的实验表明，PAFT 始终优于所有基线方法，最高可节省 46% 的能源，而平均开销仅为 4%。

## Abstract
Modern AI model training imposes unprecedented computational demands, making it a key contributor to datacenter energy consumption. Yet a significant fraction of the energy consumed during training does not translate to useful computation due to bottlenecks throughout the training pipeline. We present PAFT, a phase-aware, dynamically adaptable GPU frequency tuning system that reduces energy consumption of training workloads with minimal performance overhead. The key insight behind PAFT is that bottlenecks represent an energy optimization opportunity, rather than purely a performance problem: when GPUs are bound to stall, PAFT opportunistically reduces their clock frequencies to match the pace of bottlenecked devices, saving energy without impacting execution time. PAFT achieves this by continuously monitoring pipeline behavior and applying fine-grained frequency adjustments, adapting to workload and system changes. Experiments conducted on twelve widely used models show that PAFT consistently outperforms all baselines, achieving energy savings of up to 46% with an average overhead of 4%.

## 1.1 研究背景

现代深度学习训练通常需要大量 GPU 长时间运行，能源消耗已成为数据中心运营成本和 AI 可持续性的重要问题。论文指出，训练期间的 GPU 能耗并不都对应有效计算，主要原因是训练流水线中存在各种瓶颈：

- **数据加载瓶颈**：存储带宽不足或共享文件系统波动导致 GPU 等待输入数据。
- **数据预处理瓶颈**：图像解码、裁剪、增强等 CPU 任务耗时较长，使 GPU 空闲。
- **计算不均衡**：多 GPU 训练中，某个较慢 GPU 会拖慢整个同步组，其他 GPU 只能等待。
- **通信与同步开销**：AllReduce、AllGather 等集体通信使部分 GPU 处于停顿状态。
- **基础设施波动**：资源争用、异构 GPU、热降频、硬件老化等因素会导致运行时性能变化。

这些场景下，GPU 可能仍然以较高甚至最高频率运行，但实际处于空闲、等待或低有效利用状态，因此产生了大量“无效能耗”。

> **训练瓶颈不仅是性能问题，也是节能机会。**

# 2. 方法论与技术细节

## 2.1 核心思想

PAFT 不使用整个训练任务统一的 GPU 频率，而是根据：

1. 当前训练阶段；
2. 每个 GPU 的执行状态；
3. 是否存在数据加载或预处理瓶颈；
4. 是否存在 GPU 间计算不均衡；
5. 当前阶段长度是否足以抵消调频开销；
6. 当前系统状态是否发生变化；

动态决定每个 GPU 在每个阶段应采用的频率。

其基本策略可以概括为：

- 如果 GPU 因外部瓶颈而必然等待，则降低 GPU 活跃计算阶段的频率，延长这些阶段的执行时间，填充原本的空闲间隔。
- 如果多个 GPU 之间存在速度差异，则降低较快 GPU 的频率，使其执行时间接近最慢 GPU，从而减少同步等待。
- 如果某个 GPU 或某个阶段出现异常变慢，则提高相应 GPU 在对应阶段的频率，避免额外的训练延迟。
- 如果某一阶段过短，不足以抵消频率切换成本，则将其与相邻阶段合并后统一调节。

## 2.2 训练流水线划分

PAFT 对训练过程进行阶段化建模，主要包括：

- 数据加载；
- 数据预处理；
- Host-to-Device 内存传输；
- 前向传播；
- 反向传播；
- 梯度同步与集体通信；
- 权重更新。

论文中将数据加载与预处理视为一个非 GPU 活跃阶段，而将内存传输、前向、反向、同步和权重更新视为 GPU 活跃阶段。

## 2.3 瓶颈检测机制

PAFT 通过向训练脚本和 NCCL 通信层注入轻量级探针，记录每个阶段的：

- 阶段标签；
- epoch 和 iteration 编号；
- 开始和结束时间戳；
- 执行该阶段的 GPU ID；
- 阶段持续时间。

### 非 GPU 计算阶段的瓶颈检测

对于数据加载或预处理瓶颈，PAFT 观察相邻迭代之间的间隔，例如：

- 第 \(i\) 次迭代权重更新结束；
- 第 \(i+1\) 次迭代内存传输开始。

如果二者之间存在较长间隔，则说明 GPU 已经完成上一批次计算，但正在等待下一批次数据。

### GPU 活跃阶段的瓶颈检测

对于计算不均衡或同步停顿，PAFT同时分析：

- 不同 GPU 在同一阶段上的执行时间差；
- 同一 GPU 在不同阶段之间的等待间隔；
- 同步点前后各 GPU 的到达时间。

如果某个 GPU 持续较慢，而其他 GPU 在同步点等待，则该 GPU 被视为潜在的拖尾设备，其他 GPU 则拥有降频节能空间。

## 2.4 GPU 硬件特征分析

不同 GPU 架构的频率切换延迟差异较大，因此 PAFT 在运行前使用硬件分析模块构建：

- 支持的 GPU 频率集合；
- 任意频率对之间的切换延迟矩阵。

论文测得的平均频率切换延迟为：

- A100：约 8.4 ms；
- GH200：约 32 ms；
- V100：约 121 ms。

PAFT 会将阶段持续时间与切频延迟进行比较：

- 如果阶段太短，单独调整频率可能得不偿失；
- 这类阶段会与邻近且特征相似的阶段合并；
- 实验中，内存传输通常与前向传播合并，同步通常与权重更新合并。

## 2.5 在线 profiling 与动态适应

PAFT 不是完全依赖离线 profiling，而是采用持续在线分析。

系统首先让 GPU 以最高频率运行若干迭代，建立基准值，包括：

- 迭代基准时间 `base_iter`；
- 各阶段基准时间 `base_phase_k`；
- 时间均值和标准差。

随后，PAFT 持续比较当前执行时间和基准时间。如果出现显著偏差，则认为：

- 基础设施负载发生变化；
- 数据加载或通信瓶颈发生变化；
- 当前频率设置造成了过大性能损失；
- 原先的基准已经过时。

此时系统会重新进入 profiling 阶段，更新基线和调频策略。

## 2.6 频率优化目标

论文使用能量—性能联合指标 EDP 衡量综合效率：

\[
EDP = E \times D
\]

其中：

- \(E\) 表示训练期间消耗的能量；
- \(D\) 表示训练持续时间。

PAFT设置一个可接受的性能开销阈值 \(\sigma\)，默认值为 **5%**。其目标是在不超过该性能容忍范围的条件下，尽可能降低能耗。

## 2.7 频率调整算法流程

PAFT的基本算法流程如下：

1. **识别最慢 GPU**
   - 将每个 GPU 的当前迭代时间与基准迭代时间比较；
   - 找出执行最慢的 GPU。

2. **处理慢 GPU**
   - 对最慢 GPU 的每个可调阶段计算性能比例；
   - 如果某阶段明显变慢，且方差没有过大，则提高该 GPU 在该阶段的频率；
   - 目的是避免瓶颈进一步扩大。

3. **处理非慢 GPU**
   - 如果没有检测到新的 slowdown 事件；
   - 对其他 GPU 的可调阶段检查是否存在性能余量；
   - 如果阶段执行时间低于允许阈值，则降低该阶段频率。

4. **逐步调整频率**
   - 每次只增加或减少一个硬件支持的频率步长；
   - A100上示例步长约为 15 MHz；
   - 在下一个阶段开始时应用目标频率。

5. **持续反馈**
   - 每次迭代后重新评估；
   - 若性能偏离基线，则重新 profiling；
   - 通过多个迭代逐步逼近合适频率。

这种设计比较保守，不会一次性大幅改变频率，但能够降低误调频导致性能退化的风险。

# 6. 主要结论与发现

## 6.1 PAFT整体有效

在12个模型上，PAFT整体优于最高频率、GEEP-AFS和Zeus：

- 相对于最高频率配置，整体平均 EDP 改善约 **17%**；
- 平均性能开销约 **4%**；
- 特定场景下最高节能约 **46%**；
- 在多数场景中性能开销控制在预设的 5% 左右。

## 6.2 瓶颈越明显，节能机会越大

当数据加载慢、CPU预处理重或 GPU 间存在计算不均衡时，GPU中存在更多必然等待时间，PAFT可以利用这些等待空间进行降频。

典型结果包括：

- 慢数据加载场景下，ShuffleNet 的能耗最高降低约 46%；
- 计算不均衡场景下，部分 NLP 模型的能耗最高降低约 28%；
- 动态瓶颈变化时，PAFT仍能重新 profiling 并调整频率。

## 6.3 阶段感知优于统一调频

论文发现：

- 全局统一频率可能获得较大节能，但容易造成明显训练延迟；
- 只调节 GPU 活跃阶段可以降低部分性能开销，但可能忽略非 GPU 阶段的节能机会；
- 只调节数据加载和预处理阶段通常节能有限，因为 GPU 本身可能已经处于空闲状态；
- 根据阶段和 GPU 分别调节，能够更好地平衡能耗和训练时间。

## 6.4 单一静态频率难以适应动态训练

不同模型、不同阶段和不同瓶颈强度下，最优频率并不相同。尤其是在共享基础设施中，系统状态会不断变化，因此离线 profiling 或固定频率策略容易失效。

PAFT的在线 profiling 能够根据当前状态重新调整基准和频率配置，这是其区别于许多已有方法的重要原因。

## 6.5 探针本身开销很小

实验显示，脚本探针和同步探针带来的训练时间增加接近于零。论文认为，PAFT的主要性能开销来自主动降低频率，而不是监控和探测机制。

# 7. 方法与实验设计的优点

## 7.1 将性能瓶颈转化为节能机会

这是论文最有价值的思想之一。它没有简单地将所有瓶颈视为需要消除的问题，而是认识到：

- 一些等待时间短期内不可避免；
- 在等待期间保持最高 GPU 频率没有意义；
- 降低频率可以在不影响关键路径的前提下降低功耗。

这一思路具有较强的系统优化启发意义。

## 7.2 具有较细的阶段粒度

相比只使用 GPU 利用率、内存带宽利用率或整体训练时间的策略，PAFT直接识别：

- 数据加载；
- 预处理；
- 前向；
- 反向；
- 同步；
- 权重更新；

从而能够区分不同阶段对频率的敏感程度。

## 7.3 支持逐 GPU 调节

PAFT不是对所有 GPU 应用统一频率，而是：

- 将每个 GPU 视为独立优化对象；
- 识别最慢 GPU；
- 让较快 GPU适当降频；
- 必要时提升慢 GPU在关键阶段的频率。

这对于存在 straggler、异构设备或动态资源争用的分布式训练较为重要。

## 7.4 能够适应运行时变化

PAFT采用持续在线 profiling，而不是只在训练开始时做一次静态配置，因此能够应对：

- 数据加载速度变化；
- 共享存储争用；
- 网络通信抖动；
- GPU性能波动；
- 瓶颈设备动态迁移。

## 7.5 充分考虑调频本身的硬件开销

论文没有假设频率切换是零成本操作，而是实际测量不同 GPU 的切频延迟，并据此：

- 合并过短阶段；
- 避免频繁切换；
- 只对足够长的阶段进行调频。

这一点增强了方法的工程合理性。

## 7.6 评价指标较全面

论文同时报告：

- 能耗；
- 训练时间；
- EDP；
- 探针开销；
- 不同性能阈值下的权衡；
- 不同瓶颈强度；
- 不同节点规模。

相比只报告节能比例，这种评价更加完整。

# 8. 不足与局限

## 8.1 GPU 能耗不等于整体训练能耗

论文只测量 GPU 能耗，未统计 CPU、内存、存储、网络和制冷系统能耗。因此：

- GPU节能不一定等比例转化为整机节能；
- 对 I/O 或 CPU 预处理密集型任务，系统总能耗收益可能低于 GPU 能耗收益；
- 对数据中心运营成本和碳排放的结论仍需谨慎外推。

## 8.2 主要训练实验集中于单一 GPU 平台

虽然论文测试了 V100、A100 和 GH200 的频率切换延迟，但实际训练能效评估主要基于：

- 4 张 NVIDIA A100 80 GiB SXM。

因此，对以下平台的适用性尚未得到充分验证：

- AMD GPU；
- 不同 NVIDIA 消费级或数据中心 GPU；
- 多种互联结构；
- MIG 切分环境；
- 更大规模的数百或数千 GPU 集群。

论文虽然声称通过驱动抽象可以扩展到其他厂商，但尚未给出实证结果。

## 8.3 探针需要人工标注

当前实现需要用户在训练脚本中手动添加阶段探针，论文明确将自动注入留给未来工作。这带来几个限制：

- 增加使用门槛；
- 对复杂训练框架集成不够透明；
- 对动态算子、条件执行和自定义通信模式的支持可能不完整；
- 手动标注错误可能影响瓶颈判断和调频效果。

## 8.4 瓶颈场景部分依赖人工注入

数据加载和计算不均衡实验通过人为注入延迟进行模拟。该方法有利于控制变量，但与真实生产环境仍存在差异：

- 真实 I/O 争用可能具有更复杂的长尾分布；
- 网络拥塞和通信抖动不一定表现为固定延迟；
- GPU 热降频、节点故障和多租户争用可能同时发生；
- 实际瓶颈可能跨多个阶段，而不是单一阶段延迟。

因此，PAFT在真实超大规模生产集群中的效果仍需要进一步验证。

## 8.5 规模仍然有限

论文测试了最多4个节点，虽然覆盖了分布式训练，但与当前大模型训练常见的数百至数千 GPU 规模相比仍有差距。尚未充分回答：

- PAFT控制面在大规模集群上的通信和协调开销；
- 每个 GPU 独立调频是否会引入过多控制状态；
- 跨节点频率策略是否可能造成新的同步模式；
- 在大规模通信拓扑下，阶段探针是否会影响训练稳定性。

## 8.6 对训练收敛和最终精度的验证不足

论文认为频率调整不会改变训练语义、收敛性和准确率，但实验部分主要关注：

- 能耗；
- EDP；
- 训练时间。

没有系统报告：

- 不同频率策略下的最终模型精度；
- loss 曲线；
- 收敛速度；
- 长时间运行下的数值稳定性；
- 混合精度、梯度累积或检查点恢复的影响。

因此，关于模型质量不受影响的结论更多是机制上的推断，而不是充分的实验证据。

## 8.7 优化目标仍较依赖固定阈值

PAFT默认使用5%的性能开销阈值。尽管论文分析了5%、10%和15%的敏感性，但实际应用中不同场景的约束可能不同：

- 在线训练可能要求严格的完工时间；
- 研究性训练可能更重视能耗；
- 云平台可能同时考虑成本、碳强度和服务等级协议；
- 不同阶段可能应使用不同的性能容忍度。

目前PAFT主要使用统一阈值，尚未形成更加灵活的多目标优化框架。

## 8.8 频率切换与驱动行为可能影响可迁移性

PAFT依赖：

- NVML；
- NVIDIA GPU频率控制；
- GPU驱动对频率设置的支持。

不同驱动版本、GPU模式、云平台权限和容器环境可能影响调频能力。此外，实际硬件可能存在：

- 设置频率与实际运行频率不完全一致；
- 自动 boost 机制干扰；
- 热限制和功耗限制覆盖软件设置；
- 频率切换延迟随负载变化。

这些因素可能导致论文实验结果在其他环境中有所下降。

## 8.9 没有完整公开所有复现细节

论文给出了硬件、软件、模型和总体实验设置，但仍缺少一些有助于复现的重要信息，例如：

- profiling 使用的具体迭代窗口大小；
- 性能偏差触发重新 profiling 的精确规则和参数；
- 不同模型的 batch size；
- 各方法完整的调优参数；
- GPU功耗采样频率；
- 绝对能耗和功率曲线；
- 所有实验的原始数据。

因此，方法思想较清晰，但完全复现仍可能需要额外工程工作。

# 总结

PAFT提出了一种面向深度学习训练的阶段感知 GPU 动态调频方法，其关键创新在于把训练过程中的数据、计算和同步瓶颈视为可利用的节能空间。系统通过轻量级探针持续追踪训练阶段，结合 GPU 频率切换延迟建模、在线 profiling、瓶颈检测和逐 GPU 调频，在满足约5%性能开销约束的情况下，动态降低不处于关键路径上的 GPU 或阶段的运行频率。

在12个模型、三类工作负载、多种瓶颈强度以及最多4节点的分布式训练实验中，PAFT整体优于最高频率、GEEP-AFS和Zeus，报告了最高约46%的 GPU 能耗降低、约17%的平均 EDP 改善和约4%的平均性能开销。论文的主要贡献在于将训练性能优化与能耗管理结合起来，并证明瓶颈感知、阶段感知和在线自适应调频能够比静态或应用无关的频率策略取得更稳定的能效收益。

不过，PAFT当前仍主要验证于小规模 NVIDIA A100 环境，依赖人工插入探针，能耗测量仅覆盖 GPU，动态瓶颈部分由人工延迟模拟，对大规模生产集群、异构 GPU、模型收敛质量和整机能耗的验证仍不充分。因此，它更适合被视为一种具有较强工程潜力的训练能效优化原型，而不是已经完全解决通用大规模训练能耗问题的成熟方案。
