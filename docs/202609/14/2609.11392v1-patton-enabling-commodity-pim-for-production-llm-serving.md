## 摘要
存内处理（Processing-in-Memory，PIM）有望加速受内存带宽限制的解码注意力计算，但仅加速注意力不足以满足生产级 LLM 服务的需求；在此类服务中，引擎需要动态地分配、填充、共享、缓存及回收逻辑 KV 缓存块。要在商用 PIM 上支持这一生命周期，需要高效的物理内存分配、块到地址映射以及命令生成。对于 Value 缓存而言，这些需求在 GEMV 效率、单 token 写入效率和内存容量之间造成了根本性冲突：针对 GEMV 优化的布局会将新生成的 Value 向量分散至不同行中，使写入代价高昂；而更细粒度的内存共享虽可提升容量利用率，却会使 GEMV 归约发生碎片化。我们提出 PATTON，一种将生产级 LLM 服务引擎与商用 PIM 集成的 PIM 运行时系统。PATTON 引入分层粒度分配机制：块大小的 Key 和 Value 粒度与逻辑 token 块一一对应，从而固定其物理位置和命令；同时，较粗粒度将多个块分组，以实现高效的 GEMV 执行和内存利用。Commit Zone 在将部分 Value 块提交至经 GEMV 优化的位置之前，对其进行暂存，以实现高效的单 token 写入。PATTON 跟踪这些位置，以生成 KV 缓存写入以及 QK 转置/SV 命令。在注意力执行和由运行时引发的预填充重计算中，相较于所评估的基线方法，PATTON 平均实现了 1.95 倍加速和 4.83 倍更高的能效；它无需修改 PIM 处理单元，并且在 vLLM 中维持了与原生 GPU KV 缓存相当的 KV 缓存命中率。

## Abstract
Processing-in-Memory (PIM) is promising for accelerating memory-bound decode attention, but attention acceleration alone is insufficient for production LLM serving, where engines dynamically allocate, populate, share, cache, and reclaim logical KV cache blocks. Supporting this lifecycle on commodity PIM requires efficient physical memory allocation, block-to-address mapping, and command generation. For the Value cache, these requirements create a fundamental conflict among GEMV efficiency, single-token write efficiency, and memory capacity: GEMV-optimized layouts scatter newly generated Value vectors across rows, making writes costly, while finer-grained memory sharing improves capacity utilization but fragments GEMV reductions. We present PATTON, a PIM runtime that integrates production LLM serving engines with commodity PIM. PATTON introduces hierarchical granule allocation: block-sized Key and Value granules map one-to-one to logical token blocks, fixing their physical placements and commands, while coarser granules group blocks for efficient GEMV execution and memory utilization. A Commit Zone stages partial Value blocks for efficient single-token writes before committing them to GEMV-optimized locations. PATTON tracks these placements to generate KV cache writes and QK-transpose/SV commands. Across attention execution and runtime-induced prefill recomputation, PATTON achieves an average 1.95x speedup and 4.83x higher energy efficiency over evaluated baselines, requires no PIM processing-unit modifications, and maintains a KV cache hit rate comparable to the native GPU KV cache in vLLM.

  - Softmax-Value（SV）相关的矩阵向量乘法（GEMV）。

  - 真实推理引擎（如 vLLM）需要不断管理 KV 缓存的完整生命周期；
  - 包括动态分配、写入新 token 的 KV、请求间共享、缓存、换出/回收、以及缓存未命中后的 prefill 重计算等；
  - 这要求运行时能把逻辑 KV 块高效映射到 PIM 的物理内存地址，并生成适配 PIM 的读写与计算命令。

### 核心矛盾

论文聚焦于 Value 缓存布局中的三方冲突：

1. **GEMV 效率**  
   - 为 PIM GEMV 优化的 Value 布局通常要求数据按适于行内/跨行归约的方式排列；
   - 这样有利于批量读取与归约。

2. **单 token 写入效率**  
   - 解码时每步只生成一个新 token 的 Value 向量；
   - 在 GEMV 优化布局中，一个新 Value 向量可能被分散写入多个 PIM 行或位置，导致频繁、昂贵的细粒度写操作。

3. **内存容量利用率与共享能力**  
   - 若采用更细粒度的块分配和共享，KV 缓存的碎片更少、容量利用率更高；
   - 但这会破坏 GEMV 所需的连续/规则聚合布局，导致归约碎片化并降低 PIM 计算效率。

### 整体意义

- PATTON 的意义不只是“加速一个 attention kernel”，而是尝试解决**生产级 LLM serving runtime 与商用 PIM 硬件之间的系统集成问题**。
- 它主张在**不修改商用 PIM 处理单元**的条件下，通过运行时层的内存管理、映射和命令生成，使 PIM 能兼容 vLLM 一类动态 KV 缓存机制。
- 该工作因此属于软硬件协同系统设计：重点在于让 PIM 加速能实际适配动态请求、KV 复用和缓存回收等线上服务行为。

## 2. 方法论：PATTON 的核心思想与关键技术

## 2.1 总体架构

PATTON 是一个连接生产级 LLM 服务引擎与商用 PIM 的**PIM 运行时系统**。其主要职责包括：

- 对逻辑 KV cache block 进行物理内存分配；
- 建立逻辑块到 PIM 物理地址的映射；
- 支持 KV 缓存的动态写入、共享、缓存和回收；
- 根据块所在位置生成：
  - KV cache 写入命令；
  - QK-transpose 相关命令；
  - SV/GEMV 计算命令；
- 在缓存驱逐或未命中时，配合运行时处理 prefill 重计算。

其关键设计由两部分组成：

1. **分层粒度分配（hierarchical granule allocation）**
2. **Commit Zone（提交区）**

## 2.2 分层粒度分配

### 基本思想

PATTON 不采用单一的 KV 存储粒度，而是同时维护面向不同目标的多层粒度：

- **块大小粒度（block-sized granules）**
  - Key 和 Value 的基本分配粒度与逻辑 token block 一一对应；
  - 每个逻辑块都能映射到确定的物理位置；
  - 这一设计使地址映射和命令生成更加直接、稳定；
  - 同时也适应了 vLLM 等系统以逻辑块管理 KV cache 的方式。

- **更粗粒度的聚合单元（coarser granules）**
  - 将多个较小的 KV 块组织在一起；
  - 目标是让 Value 数据以更适合 PIM GEMV 的方式布局；
  - 通过较规则的行/列组织，减少 GEMV 的碎片化归约，提高内存侧计算效率；
  - 粗粒度组织也有助于在 PIM 物理存储上改善容量管理。

### 解决的问题

这一设计试图在逻辑视角与物理计算视角之间解耦：

- 从服务引擎视角看：
  - KV 块仍可作为细粒度逻辑对象被动态分配、共享和回收；
  - 更容易支持分页式 KV cache、前缀共享等生产服务机制。

- 从 PIM 视角看：
  - 多个细粒度块可被组织成适于 GEMV 的粗粒度单元；
  - 减少因逻辑块过于细碎而带来的计算归约开销。

换言之，PATTON 利用“细粒度逻辑映射 + 粗粒度物理计算组织”来平衡动态性和计算效率。

## 2.3 Commit Zone：解决单 token Value 写入低效问题

### 问题来源

在自回归解码中，每次生成一个 token，仅产生对应的一小段 Key/Value 数据。对于 Value cache：

- 若直接写入 GEMV 优化后的最终物理位置；
- 新生成的 Value 向量可能需要散布到多个行或多个位置；
- 从而产生大量非连续、小粒度写入；
- 这会显著削弱 PIM 布局带来的 GEMV 收益。

### PATTON 的做法

PATTON 引入 **Commit Zone**，即一个用于暂存部分 Value 块的区域：

1. 新 token 产生的 Value 数据首先被写入 Commit Zone；
2. Commit Zone 按适合单 token 追加写入的方式组织；
3. 当积累到可以形成适于 GEMV 的完整/足够大的 Value 块时；
4. PATTON 再将这些暂存内容“提交（commit）”到最终的 GEMV 优化物理布局中。

### 作用

Commit Zone 将两个相互冲突的写入模式分离：

- **在线解码写入阶段**：优先追求低开销、连续或局部的单 token 写入；
- **后续注意力计算阶段**：优先采用对 GEMV 有利的布局。

因此，它避免了每个 token 都直接触发复杂的跨行散写，同时尽可能保留最终 Value 布局的 PIM GEMV 效率。

## 6. 主要结论与发现

- **生产级 PIM 加速的瓶颈不只是 attention 算子本身，而是 KV cache 生命周期管理。**
  - 动态分配、写入、共享、缓存、回收和缓存未命中后的重计算，都可能影响端到端收益。

- **Value cache 的存储布局存在不可忽略的三方权衡。**
  - 适合 GEMV 的布局不一定适合单 token 写入；
  - 细粒度共享虽提升容量利用率，却可能使 PIM 归约碎片化。

- **PATTON 的分层粒度分配能同时服务逻辑块管理与物理 GEMV 执行。**
  - 细粒度映射有利于动态 KV cache 管理；
  - 粗粒度组织有利于 PIM 计算与容量利用。

- **Commit Zone 能缓解单 token Value 写入和 GEMV 优化布局之间的冲突。**
  - 它使新 Value 可以先以写入友好的方式暂存，再批量提交到计算友好的布局。

- 在论文评估范围内，PATTON 相比所评估基线：
  - 平均实现 **1.95× 加速**；
  - 平均实现 **4.83× 能效提升**；
  - 并在 vLLM 中维持与原生 GPU KV cache **相近的缓存命中率**。

- PATTON 不要求修改 PIM 处理单元，说明其可通过运行时和内存管理软件层适配“商用”PIM，降低硬件定制门槛。

## 7. 优点与亮点

### 7.1 将问题从算子加速提升到生产系统集成

- 许多 PIM/LLM 工作侧重单个 attention、GEMV 或矩阵乘法内核；
- PATTON 强调 KV cache 的完整运行时生命周期；
- 这一视角更契合线上推理服务，尤其适合带有分页 KV 管理、请求复用和动态调度的系统。

### 7.2 准确识别了 Value cache 布局的核心矛盾

- 论文没有简单假设“把 KV 放到 PIM 中即可加速”；
- 而是具体指出：
  - GEMV 排布；
  - 单 token 追加写入；
  - 内存共享/容量利用；
  三者之间的结构性冲突。
- 这使设计目标更明确，也体现了对 PIM 数据布局和 LLM 解码行为的联合理解。

### 7.3 分层粒度设计具有较强工程合理性

- 逻辑块和物理计算聚合单元分层处理；
- 既保持与 vLLM 风格块管理的兼容性，又避免细粒度块直接导致 GEMV 碎片化；
- 这种设计在动态服务系统中比完全静态、连续的 KV 布局更具可行性。

### 7.4 Commit Zone 是实用的写优化机制

- 将频繁的小粒度单 token 写入与最终计算布局解耦；
- 避免为了优化计算而牺牲解码写入效率；
- 这一机制特别贴合自回归生成“逐 token 产生 KV”的访问模式。

### 7.5 同时考察性能、能效和缓存行为

- 除平均加速外还报告能效提升；
- 除计算时间外还检查 KV cache hit rate；
- 并且将 prefill 重计算纳入考量，说明评估并非只关注理想情况下的 PIM 核函数吞吐。

### 7.6 无需改动 PIM 处理单元

- 若该主张在完整系统中成立，则其部署门槛相对较低；
- 可避免依赖专门为 LLM 定制的新 PIM ISA 或计算单元；
- 对利用已有商用 PIM 能力进行系统软件创新具有现实价值。

## 8. 不足与局限

## 8.1 实验细节在所提供内容中不足

当前摘要没有说明：

- 使用的具体 LLM 模型和参数规模；
- 数据集、真实 trace 或请求分布；
- 上下文长度范围；
- batch size、并发请求数和到达过程；
- PIM/GPU/CPU 硬件配置；
- 基线名称及调优方式；
- 各项结果的绝对延迟、吞吐、功耗和统计离散度。

这使外部读者难以判断 1.95× 和 4.83× 提升的适用范围、测量边界及可复现性。

## 8.2 对真实生产负载的泛化性仍待验证

- 生产 LLM 请求的上下文长度、输出长度、前缀共享率和并发度通常高度动态；
- Commit Zone 的收益可能依赖于：
  - Value 块填满速度；
  - 请求长度分布；
  - 请求是否频繁中断或取消；
  - KV 块被共享、迁移或回收的频率。
- 若负载以短请求、低并发或高频抢占为主，暂存和提交策略的效率可能发生变化。

## 8.3 Commit Zone 可能引入额外容量和管理复杂度

- Commit Zone 需要额外的暂存空间；
- 运行时需要追踪块的状态及其从暂存位置到最终位置的迁移；
- 可能带来：
  - 元数据开销；
  - 提交时的数据复制或写回成本；
  - 并发访问同步问题；
  - 驱逐、故障恢复和请求取消场景下的状态一致性挑战。
- 摘要未说明这些开销是否被充分量化。

## 8.4 “无需修改 PIM 处理单元”不等于零硬件依赖

- 虽然不修改 PIM processing unit 是优势，但方案仍可能依赖特定商用 PIM 的：
  - 内存组织方式；
  - 行激活和写入粒度；
  - 命令接口；
  - bank 并行特性；
  - GEMV 支持能力。
- 因此，其跨不同厂商、不同代际 PIM 的移植性仍需进一步验证。

## 8.5 可能缺少尾延迟和服务质量分析

- 线上推理系统通常重视 P95/P99 延迟、请求公平性和首 token 延迟；
- PATTON 中的提交、映射更新和 PIM 命令生成可能产生阶段性抖动；
- 若论文仅报告平均加速，可能无法完整反映多租户或交互式服务下的用户体验。

## 8.6 能效结论依赖测量方法

- PIM 的能效优势通常显著受功耗建模边界影响；
- 需要明确是否计入：
  - GPU 侧 KV 写入和数据传输；
  - CPU/runtime 管理开销；
  - 主机内存与互连能耗；
  - PIM 空闲功耗；
  - prefill 重计算的完整能耗。
- 摘要没有披露能耗测量或估算方法，因此 4.83× 的能效结果仍需结合正文谨慎解读。
