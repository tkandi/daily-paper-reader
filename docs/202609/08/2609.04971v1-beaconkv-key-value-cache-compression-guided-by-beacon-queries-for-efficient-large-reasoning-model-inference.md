## 摘要
大型推理模型（LRM）通过生成更长的思维链（CoT）实现卓越的问题求解能力，但由此产生的键值（KV）缓存会随序列长度线性增长，从而造成严重的内存瓶颈；对于较长的推理轨迹，其占用通常会超过 GPU 的容量。现有的 KV 缓存压缩方法依赖近期查询来估计未来词元的重要性，隐含地假设近期查询能够可靠地近似未来的注意力模式。我们发现，在长时程推理中，这一假设并不成立：某些解码步骤会生成思维重访词元（Thought Revisiting Tokens，TRT），重新关注较远的历史上下文，例如在推理轨迹早期形成的任务求解计划。通过系统分析，我们发现，与 TRT 对应的查询会在嵌入空间中聚集成少量相似性组。基于这一观察，我们提出 BeaconKV，一种无需训练的 KV 缓存压缩方法。该方法维护信标查询，即每个全局查询簇的紧凑代表，从而无需存储完整的查询历史，便可预测哪些 KV 对将被再次访问。在四种开源大型推理模型和多样化的推理基准上，BeaconKV 总体上优于现有压缩方法，在几乎保持完整缓存准确率的同时，最高可将内存占用降低 5.8 倍，并将吞吐量提升超过 4.3 倍。

## Abstract
Large Reasoning Models (LRMs) achieve superior problem-solving through extended Chain-of-Thought (CoT) generation, but the resulting key-value (KV) cache grows linearly with sequence length and creates severe memory bottlenecks, often exceeding GPU capacity for long reasoning traces. Existing KV cache compression methods rely on recent queries to estimate future token importance, implicitly assuming these serve as reliable proxies for future attention patterns. We demonstrate that this assumption fails in long-horizon reasoning: certain decoding steps generate Thought Revisiting Tokens (TRT) that re-attend to distant previous context, such as task-solving plans formulated early in the trace. Through systematic analysis, we discover that queries corresponding to the TRT cluster into a small number of similarity groups in the embedding space. Based on this insight, we propose BeaconKV, a training-free KV cache compression method that maintains beacon queries, compact representatives for each global query cluster, to anticipate which KV pairs will be revisited without storing the entire query history. Across four open-source LRMs and diverse reasoning benchmarks, BeaconKV generally outperforms existing compression methods, achieving up to $5.8\times$ memory reduction while nearly preserving full cache accuracy and improving throughput by over $4.3\times$.

# 1. 核心问题与整体含义

## 研究背景

- 大型推理模型（Large Reasoning Models, LRMs）依赖较长的思维链（Chain-of-Thought, CoT）进行数学、代码和科学推理。相比普通短文本生成，这类模型单次推理常生成数千至数万 token。
- Transformer 在自回归解码时，需要保存所有历史 token 的 Key-Value（KV）缓存；因此 KV 缓存大小随生成长度线性增长，成为长推理部署的主要显存瓶颈。
- 论文给出的例子是：Qwen3-4B 生成 32K token、batch size 为 16 时，仅 KV cache 就可能超过 **77 GB**，接近单张 80GB GPU 的显存上限。

## 现有方法的问题

- 既有 KV 压缩方法，如 SnapKV、RPC、R-KV，通常在缓存满时根据**最近若干 query 对历史 KV 的注意力权重**给每个 KV 项打分，并淘汰低分项。
- 其隐含假设是：**近期 query 的注意力模式可以代表未来 query 的需求**。
- 论文认为这一假设在长程推理中不成立：
  - 模型多数时候进行局部推理，只关注最近 token；
  - 但在某些时刻会突然重新关注很早之前的题目条件、求解计划或中间结论；
  - 如果这些远距离上下文此前因“近期未被关注”而被淘汰，后续推理质量就会下降。

## 整体含义

论文提出，长 CoT 推理并非仅仅是局部连续生成，而存在一种“**回访早期思路**”的注意力行为。为支持这种行为，KV 缓存压缩不能只看当前局部注意力，还应保留对未来全局回访有潜在价值的历史上下文。

# 2. 方法论：BeaconKV

## 核心思想

BeaconKV 是一种**无需训练（training-free）**的 KV cache 压缩方法。其核心是：

1. 识别推理过程中会重新关注远处上下文的 token，称为 **Thought Revisiting Tokens（TRT，思维重访词元）**；
2. 发现 TRT 对应的全局 query 在查询嵌入空间中并非随机分布，而是聚成少数几个相似簇；
3. 用每个簇的少量代表性 query 作为“**信标查询（Beacon Queries）**”；
4. 在 KV 淘汰时，同时用：
   - **近期查询**维护局部上下文；
   - **信标查询**预测未来全局回访可能访问的历史 KV；
5. 保留两者认为重要的 KV 项，从而避免过早删除未来推理仍会用到的远距离内容。

---

## 关键观察：TRT 与全局 Query

论文将 query 按注意力距离分为两类：

- **局部查询（Local Queries）**：注意力主要集中在当前位置附近，服务于局部文本连贯性和当前计算。
- **全局查询（Global Queries）**：会注意到较早、较远位置的 token，例如初始问题约束、早期设定的解题方案等。
- 产生全局注意力模式的 token 被定义为 TRT。

论文的统计定义为：

- 对一个 query，取其注意力最高的 Top-K 历史 token，文中使用 \(K=150\)；
- 计算 query 位置与这些 key 位置之间的平均距离；
- 若平均注意力距离大于 200，则将该 query 视作全局 query，否则为局部 query。

作者在 R1-Distill-Qwen-7B 的 AIME24 样例上观察到，TRT 会跨越数百甚至上千 token，重新读取题意、约束及早期推理计划。

## 信标查询的构建：Continual FPS

### 为什么要选代表性历史 Query

若直接存储全部历史 query，虽然可以更全面地估计未来注意力，但会额外造成显存开销。因此 BeaconKV 只维护少量、覆盖查询空间的代表。

作者使用 **Farthest Point Sampling（FPS，最远点采样）**选取 query：

- 在预 RoPE（pre-RoPE）查询空间中计算 query 间余弦相似度；
- 首先选取与整体 query 集合平均相似度最低的 query；
- 随后每次选择与已选集合“最不相似”的 query；
- 重复直到达到目标数量。

直观而言，FPS 不是选择最常出现的 query，而是选择能尽量覆盖不同 query 方向、几何上最具代表性的 query。

### Continual FPS：在线、有限内存版本

直接对完整 query 历史运行 FPS 会带来较高存储和计算开销。因此论文提出 **Continual FPS**：

- 每个注意力头维护一个有上限的 pre-RoPE query 缓冲区；
- 当缓冲区达到最大容量 \(B_Q^{\max}\) 时，对当前缓冲区执行 FPS；
- 将其压缩回较小容量 \(B_Q^{\min}\)；
- 如此循环进行“填充—压缩（fill-and-compress）”。

可写为：

\[
Q_{\text{obs}}^{\text{pre}} \leftarrow \operatorname{FPS}(Q_{\text{obs}}^{\text{pre}}, B_Q^{\min})
\]

其中：

- \(Q_{\text{obs}}^{\text{pre}}\)：保存的 pre-RoPE 观察 query；
- \(B_Q^{\max}\)：query 缓冲区触发压缩的上限；
- \(B_Q^{\min}\)：压缩后保留的 query 数量。

论文主实验中设置：

- 信标 query 数量：最多 32、压缩后通常保留 16；
- 最近 query 数量：16；
- 常用平衡配置为 **16 个 beacon query + 16 个 recent query**。

## KV 重要性评分与淘汰流程

### 1）构造观察查询集合

当 KV cache 达到最大预算时，BeaconKV 构造：

\[
Q_{\text{obs}} =
Q_{\text{beacon}} \cup Q_{\text{recent}}
\]

其中：

- \(Q_{\text{beacon}}\)：历史上通过 Continual FPS 选出的信标查询；
- \(Q_{\text{recent}}\)：最近生成 token 的 query。

### 2）RoPE 位置对齐

这是该方法一个较关键的实现细节：

- 对于 **beacon query**，在当前解码位置 \(t\) 重新施加 RoPE：
  
\[
\operatorname{RoPE}(q, t)
\]

  目的是模拟“如果代表某类全局回访的 query 在当前时刻出现，它会关注哪些历史 KV”。

- 对于 **recent query**，保留其原始生成位置 \(\tau\) 的 RoPE：
  
\[
\operatorname{RoPE}(q, \tau)
\]

  以维持标准的局部注意力信号。

### 3）以注意力权重计算 KV 分数

对于每个历史 KV 项 \(j\)，计算 observation queries 对它的注意力权重，并用**最大值聚合（Max Aggregation）**：

\[
\text{Score}[j]
=
\max_{h \in g}
\max_{q \in Q_{\text{obs}}}
W[h,q,j]
\]

其中：

- \(g\) 是一个 GQA（Grouped Query Attention）头组；
- \(W[h,q,j]\) 表示 query \(q\) 在头 \(h\) 对位置 \(j\) 的注意力权重。

作者选择 Max 而非 Mean 的原因是：

- TRT 是稀疏、偶发但重要的事件；
- 某一个信标 query 对某个 KV 项的高注意力，可能就意味着该 KV 是未来推理的关键；
- 均值聚合容易将这种稀疏高信号被大量低注意力值稀释。

### 4）保留与驱逐

缓存压缩时始终保留：

- 前缀 token；
- 最近的一小段 token；
- 其余位置中按分数最高的 KV 项。

即：

\[
I_{\text{keep}}
=
\{1,\ldots,n_{\text{prefix}}\}
\cup
\{L-n_{\text{recent}}+1,\ldots,L\}
\]

然后从剩余 KV 中选取得分最高的项，直到满足压缩后的预算 \(B_{\text{KV}}^{\min}\)。

- 设最大 KV cache 预算为 \(B_{\text{KV}}^{\max}\)；
- 当缓存达到最大预算时进行淘汰；
- 淘汰后压缩至：

\[

\]

即每次释放约 \(1/8\) 的输出 token 对应 KV 空间。

# 6. 主要结论与发现

1. **长程推理中存在 TRT 现象。**  
   模型并不总是仅关注近期 token；部分 token 会重新访问很早之前的题目约束、规划和推理内容。

2. **仅基于近期 query 的 KV 淘汰机制存在系统性盲点。**  
   因为 TRT 出现具有稀疏性和不可预测性，若仅观察最近 query，可能会提前删除未来将被重访的远距离 KV。

3. **全局 query 在 pre-RoPE 嵌入空间中呈现少量相似簇。**  
   这使得用少量 beacon query 覆盖潜在全局注意力模式成为可能。

4. **BeaconKV 在多数模型、任务和缓存预算下优于现有压缩方法。**  
   特别是在低 KV budget 的激进压缩场景，优势更明显。

5. **最大准确率提升可达 31.7 个百分点。**  
   论文报告该结果出现在 Qwen3-14B 的 AIME24 任务、最大 KV budget 为 1024 时，相对于已有压缩方法。

6. **系统效率方面可显著降低内存占用。**  
   在 Qwen3-4B、32K 生成、batch size 14 的测试中：
   - Full KV 峰值显存：77.0 GB；
   - BeaconKV（2K budget）：13.3 GB；
   - 显存降低约 **5.8 倍**。

7. **吞吐得到明显提高。**  
   同一测试中：
   - Full KV：82.3 tokens/s；
   - BeaconKV：356.4 tokens/s；
   - 吞吐提升约 **4.3 倍**。

8. **Max 聚合通常优于 Mean 聚合。**  
   这支持作者观点：TRT 对应的关键注意力信号是稀疏的，均值会削弱少数高价值信号。

# 7. 优点与亮点

## 方法层面

- **抓住了推理模型区别于普通长上下文模型的现象。**  
  论文没有将长 CoT 简单视为普通长序列，而是提出 TRT，强调推理过程存在跨阶段回访和全局一致性维护需求。

- **从 query 几何结构出发设计压缩策略。**  
  相比只依赖最近注意力或 key 冗余度的方法，BeaconKV 从“未来可能出现何种 query”角度预测历史 KV 的价值，视角较新。

- **无需训练。**  
  不需要微调主模型、训练额外 gate 或蒸馏模块，因此部署门槛较低，也避免了特定任务训练造成的泛化问题。

- **Continual FPS 控制了 query 历史的额外内存。**  
  方法并非简单将完整 query 历史加入缓存，而是通过在线压缩保持固定大小的代表集合，契合其解决显存问题的目标。

- **兼顾局部与全局信息。**  
  采用 beacon query 与 recent query 的混合观察集，避免只关注远程回访而损害局部生成连贯性。

- **RoPE 重定位设计合理。**  
  将 beacon query 旋转到当前时间位置，以模拟未来全局 query 的访问行为；同时保留 recent query 的原位置，分别处理全局与局部信号。

## 实验层面

- 同时报告准确率、峰值显存、吞吐量和延迟，而非只报告单一指标；
- 覆盖多个模型规模和推理领域；
- 在激进压缩场景中展示明显收益，具有较强的实际部署意义；
- 提供了多项消融来验证 beacon 数量分配、聚合函数及 query 选择策略的作用；
- 与 Full KV 的结果对照表明，方法的目标不是单纯提高压缩比，而是在高压缩下尽量逼近完整缓存推理质量。

# 8. 不足与局限

## 任务与模型覆盖不足

- 论文主要评估开放源推理模型和推理 benchmark，尚未验证以下场景：
  - 普通长上下文问答；
  - 文档检索与长文阅读理解；
  - 摘要生成；
  - 多轮对话；
  - 长篇开放式写作；
  - Agent 工具调用与交互式任务。
- 因此，TRT 与 beacon query 的机制是否广泛适用于非推理生成任务，尚无充分证据。
- 没有覆盖闭源前沿模型，也未验证更大规模模型、MoE 模型或不同注意力架构上的表现。

## TRT 定义与因果解释仍有限

- TRT 的识别依赖“Top-K 注意力位置的平均距离”与阈值 200，这一阈值具有经验性；
- 注意力距离较远不一定严格等价于“重访思维”或“访问关键推理计划”，概念解释仍主要建立在注意力可视化和个例分析之上；
- 论文证明了全局 query 的聚类现象与方法性能相关，但没有严格证明这些聚类一定对应可泛化的语义推理状态。

## 超参数依赖

BeaconKV 需要设置多个参数，例如：

- beacon query 数量；
- recent query 数量；
- query buffer 的最大、最小容量；
- KV cache 的最大和最小预算；
- prefix 与近期 token 的保留长度；
- 淘汰触发周期。

论文使用固定配置并显示 \(16+16\) 的 beacon/recent 组合通常较好，但最佳配置可能随模型、任务、上下文长度和预算变化。作者也承认，动态自适应地调整这些参数是未来工作。

## 额外计算开销

- BeaconKV 虽降低了 KV cache 大小和后续注意力成本，但在淘汰时需执行：
  - query 缓冲维护；
  - FPS；
  - beacon/recent query 的额外注意力评分。
- 系统实验显示，它相较 RPC 有一定解码延迟增加。例如在 Qwen3-4B、1K budget、batch size 320 时：
  - RPC 延迟：7593.7 秒；
  - BeaconKV 延迟：7790.9 秒。
- 虽然准确率收益显著，但对于低延迟、极高频的在线服务场景，这部分额外开销需要进一步优化和评估。

## 可复现性与系统报告不完整

- 论文仅明确说明一组效率实验使用单张 A100 80GB，未完整报告全部实验硬件、框架、软件版本、运行时配置及总计算成本；
- 未报告准确率的方差、置信区间或统计显著性；
- 未给出不同实现下 FPS 与 attention scoring 的详细 kernel 级开销分析；
- 这些信息不足会限制系统性能结果的完全复现与公平比较。

## 与基线的配置差异

- 尽管在相同 KV budget 下比较，但不同基线保留近期 token 的数量不同；
- R-KV 保留最近 8 token，而其他方法通常保留最近 32 token；
- 这符合原始方法设置，但对于严格的 apples-to-apples 比较，仍可进一步统一保留窗口、淘汰频率、前缀策略和注意力计算实现。
