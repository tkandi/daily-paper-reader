## 摘要
将 AI 计算分布到多 GPU 服务器的各个 GPU 上，是 AI 系统领域的核心问题之一。我们提出了 Einsummable，这是一个原型系统，能够接收类似 PyTorch 的 AI 计算描述，并将其自动分布到多 GPU 服务器上，无需程序员编写设备分配、分片标注或通信操作。Einsummable 将每个操作建模为对张量关系进行的一次关系连接，随后执行聚合，其中元组包含子张量。每个操作通过我们称为“连接-聚合规范”（join-agg specs）的机制公开其可能的分解方式。随后，优化器在整个计算范围内选择分解方案，以最小化通信代价代理指标。由于它搜索的是分解方式，而非一组具名策略，Einsummable 能够发现基于网格的自动并行器无法发现的执行计划。每个分解后的操作均通过合成交换程序来实现；该程序是对 Volcano 交换算子的拓扑感知泛化。Einsummable 不调用任何预定义的集合通信操作：所有通信和聚合均为专用操作，并在编译时推导得到。尽管完全自动化，Einsummable 仍可优于专门设计的实现。例如，在一台配备八块 A100 GPU 的服务器上运行 LLaMA Transformer 块时，Einsummable 实现了 8.97 ms 的几何平均运行时间，而经过手工调优的 PyTorch 和 vLLM 分别为 13.80 ms 和 15.90 ms。

## Abstract
Distributing an AI computation across the GPUs of a multi-GPU server is one of the central problems in systems-for-AI. We present Einsummable, a prototype system that accepts a PyTorch-like description of an AI computation and automatically distributes it across a multi-GPU server, with no device assignments, sharding annotations, or communication operations written by the programmer. Einsummable models every operation as a relational join followed by an aggregation over tensor relations, in which the tuples contain sub-tensors. Each operation exposes its possible decompositions through what we call "join-agg specs". An optimizer then selects decompositions across the whole computation to minimize a communication-cost proxy. Because it searches decompositions rather than a menu of named strategies, Einsummable discovers plans that mesh-based auto-parallelizers cannot. Each decomposed operation is implemented by synthesizing an exchange program, which is a topology-aware generalization of Volcano's exchange operator. Einsummable invokes no canned collectives: all communication and aggregation is special-purpose, derived at compile time. Despite being fully automatic, Einsummable can outperform custom-designed implementations. For example, on LLaMA transformer blocks on an eight-GPU A100 server, Einsummable achieves a geometric-mean runtime of 8.97 ms, versus 13.80 ms for hand-tuned PyTorch and 15.90 ms for vLLM.

# 2. 方法论：核心思想与关键技术

## 2.1 统一的关系连接—聚合抽象

Einsummable 将每个 AI 算子建模为：

1. 对张量关系执行一次关系连接（join）；
2. 再对连接结果进行聚合（aggregation）。

其中，关系中的元组并不一定包含标量，而是可以包含张量的子块或子张量。

从抽象角度看，一个算子可以表示为：

\[
\text{Output} = \operatorname{Aggregate}\left(\operatorname{Join}(R_1,R_2,\ldots,R_n)\right)
\]

其中：

- \(R_i\) 表示输入张量关系；
- `Join` 表示根据索引或维度匹配关系组合子张量；
- `Aggregate` 表示求和、规约或其他形式的聚合；
- 输出关系由连接和聚合结果构成。

这种表示方式的关键意义在于：矩阵乘法、张量收缩以及部分 Transformer 算子都可以在同一抽象框架下表达。

## 2.2 Join-agg specs：暴露算子分解空间

每个算子通过所谓的 **连接—聚合规范（join-agg specs）** 描述其可能的分解方式。

这些规范不是简单地为算子指定一种固定并行策略，而是向优化器公开：

- 哪些索引或张量维度可以被切分；
- 哪些输入可以局部化；
- 哪些中间结果需要复制、重分布或规约；
- 连接和聚合可以采用哪些等价的计算分解；
- 不同分解方式可能产生的通信需求。

因此，Einsummable 优化的对象不是“数据并行”“张量并行”这类高层命名策略，而是算子本身的具体分解方式。

## 2.3 跨全流程的联合优化

优化器不是逐个算子独立决策，而是尝试在整个计算范围内选择分解方案。

其基本流程可以概括为：

1. 接收类似 PyTorch 的计算描述；
2. 将计算中的算子转换为连接—聚合表示；
3. 为每个算子生成可能的 join-agg specs；
4. 枚举或搜索不同算子分解组合；
5. 根据计算图中的数据流和设备拓扑评估通信代价；
6. 选择整体通信代价较低的方案；
7. 为每个分解后的算子生成专用通信和聚合代码；
8. 编译形成最终的多 GPU 执行程序。

可以将其抽象为如下优化目标：

\[
P^* = \arg\min_{P \in \mathcal{P}} C_{\text{comm}}(P)
\]

其中：

- \(\mathcal{P}\) 是所有可能的算子分解与设备布局方案；
- \(P^*\) 是优化器最终选择的方案；
- \(C_{\text{comm}}\) 是通信代价代理指标。

需要注意的是，摘要明确提到优化器主要以**通信代价代理指标**为目标，但没有提供完整的代价函数、搜索算法复杂度、是否纳入计算负载、显存占用和通信计算重叠等细节。因此，不能仅凭摘要判断其目标函数是否完整等价于最终运行时间。

## 2.4 自动生成拓扑感知的通信程序

每个完成分解的算子都通过合成交换程序实现。

论文将该机制描述为：

- 对 Volcano 系统中 `exchange` 操作的拓展；
- 能够感知 GPU 之间的硬件拓扑；
- 根据实际数据分布和设备布局自动生成通信路径；
- 不依赖预定义的集合通信原语。

与直接调用 `all-reduce`、`all-gather` 或 `all-to-all` 等固定集合通信相比，该方法的特点是：

- 通信操作由编译过程自动推导；
- 通信与聚合可以针对具体算子定制；
- 不被现有集合通信接口的固定语义限制；
- 有机会减少不必要的数据移动。

## 2.5 与传统自动并行方法的区别

论文强调，Einsummable 搜索的是“分解方案”，而不是有限的、预先命名的并行策略。

因此，它理论上能够发现：

- 非规则的张量切分；
- 不同算子之间不一致的分片方式；
- 针对局部数据流优化的通信路径；
- 超越固定网格布局的设备协作方式；
- 与具体 GPU 拓扑相适配的专用通信程序。

这也是论文标题“Every Kernel Is a Join”的核心含义：不同 AI kernel 可以统一看作连接—聚合问题，并由同一编译优化框架进行处理。

- 适合特定硬件拓扑的执行方案。

## 7.4 通信程序具有拓扑感知能力

对 GPU 拓扑进行感知，使系统能够针对实际硬件连接关系生成通信程序，而不是假设所有设备之间具有相同的通信代价。

## 7.5 实验结果具有较强的工程吸引力

在提供的实验中，Einsummable 的运行时间明显低于两个现实基线：

- 比手工调优 PyTorch 的 13.80 ms 更快；
- 比 vLLM 的 15.90 ms 更快。

如果实验设置公平，这一结果说明系统不仅具备自动化能力，也具备实际性能竞争力。

## 7.6 不依赖预定义集合通信

所有通信和聚合都在编译时推导，这种设计具有较强的可定制性，并可能避免通用集合通信接口带来的额外约束。

# 8. 不足与局限

## 8.1 实验覆盖范围有限

根据目前提供的内容，实验主要集中于：

- 单类模型组件：LLaMA Transformer 模块；
- 单种 GPU 配置：8 张 A100；
- 少量基线：手工调优 PyTorch 和 vLLM。

因此，尚不足以证明该方法在以下场景中同样有效：

- 不同模型架构；
- 不同规模模型；
- 不同 GPU 数量；
- 不同网络或互联拓扑；
- 训练场景；
- 长序列和大 batch 场景；
- 完整端到端推理服务。

## 8.2 可能存在较高的编译和搜索开销

直接搜索算子分解空间可能带来较大的优化成本。当前内容没有说明：

- 优化器的搜索复杂度；
- 编译时间；
- 搜索是否需要大量试运行；
- 对大规模计算图是否可扩展；
- 是否采用启发式、动态规划或代价剪枝；
- 编译时间是否计入系统总成本。

如果搜索时间很长，系统可能更适合固定模型或高复用率工作负载，而不适合频繁变化的动态模型。

## 8.3 优化目标可能不够完整

摘要中主要强调最小化通信代价代理指标，但真实运行时间还受到以下因素影响：

- GPU 计算负载；
- 设备间负载不均衡；
- 显存容量；
- kernel 启动开销；
- 通信与计算重叠；
- 同步和调度开销；
- 内存访问效率；
- 算子融合效果。

如果代价模型过度关注通信，可能会选择通信量较低但计算效率较差的计划。

## 8.4 与强基线的比较信息不足

手工调优 PyTorch 和 vLLM 是有意义的基线，但仍可能缺少：

- 专门的张量并行实现；
- 其他自动并行系统；
- NCCL 集合通信版本；
- Megatron-LM 等成熟大模型并行框架；
- 针对相同模型和硬件的高度优化 kernel 库。

因此，当前信息不足以确定 Einsummable 是否全面优于所有主流并行系统。

## 8.5 端到端收益尚不明确

论文报告的是 LLaMA Transformer 模块的运行时间，而不是明确的完整模型端到端指标。因此尚不清楚：

- 自动并行对完整推理延迟的影响；
- 对吞吐量的影响；
- 对首 token 延迟和后续 token 延迟的影响；
- 对训练迭代速度的影响；
- 对服务调度和动态 batch 的影响。

单个模块上的优势不一定能直接转化为完整系统中的同等收益。

## 8.6 资源需求和硬件适用范围尚不明确

目前只知道使用了 8 张 A100，但没有更多硬件细节。方法的效果可能依赖：

- GPU 间是否具有高速互联；
- 具体拓扑结构；
- 显存大小；
- GPU 数量；
- 通信库和驱动版本。

如果系统高度依赖特定拓扑，其在普通 PCIe 多 GPU 服务器或跨节点集群中的适用性可能受限。

## 8.7 复杂度和可维护性问题

为每个分解后的算子生成专用通信和聚合程序，可能带来：

- 编译器实现复杂；
- 调试难度增加；
- 生成代码数量膨胀；
- 对动态形状支持困难；
- 对不规则算子和控制流支持受限；
- 运行时出现异常时定位困难。

## 8.8 自动化结果的稳定性尚未充分说明

自动优化器可能在不同输入规模或硬件环境下生成不同计划。当前内容没有说明：

- 搜索结果是否稳定；
- 是否存在局部最优；
- 是否有失败或超时案例；
- 是否支持计划缓存；
- 是否能够解释为何选择某一分解；
- 计划对输入形状变化是否敏感。

这些问题会影响系统的工程可用性。

## 8.9 当前结论更适合作为原型验证

综合来看，论文最有力地证明的是：

> 在特定的多 GPU LLaMA Transformer 场景中，基于连接—聚合统一抽象的自动并行系统可以生成高性能执行计划。

但基于当前提供的内容，还不能充分证明：

- 该方法对所有 AI 计算都有效；
- 搜索成本在大规模模型上可接受；
- 在训练、跨节点和动态服务环境中具有稳定优势；
- 它能够系统性地替代成熟的人工并行框架。

总体而言，Einsummable 的主要贡献在于提出了一种统一、自动且拓扑感知的多 GPU 并行编译框架，并通过 LLaMA Transformer 模块上的结果展示了其性能潜力；其进一步价值仍需要更多模型、硬件、工作负载、端到端指标和消融实验来验证。
