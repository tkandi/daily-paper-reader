## 摘要
智能体搜索和 GPU 内核的自动优化是大型语言模型推理的强大工具。然而，它们的有效性并不取决于搜索本身的复杂程度，而取决于所求解优化问题的清晰性。我们提出一种应用优先的方法，以驱动分层代码生成工具从算子规范一直生成至 GPU 指令，并表明，定义清晰的计算模型能够使优化问题变得可处理。

## Abstract
Agentic search and automated optimization of GPU kernels are powerful tools for large language model inference. Their effectiveness, however, depends not on the sophistication of the search itself, but on the clarity of the optimization problem being solved. We provide an application-first approach that drives a hierarchical code generation tool from operator specifi cation down to GPU instructions, and show that a clearly defined computational model makes the optimization problem tractable.

- **缺乏零成本基线**：自动搜索往往需要一个可运行、正确且相对合理的默认实现作为起点。

## 2. 方法论：核心思想、技术细节与算法流程

## 2.1 分层算法树：将算子描述与硬件映射分离

论文将张量算子表示为一个**分层算法树（hierarchical algorithm tree）**。树中每层对应不同硬件层级：

- **设备层（device）**：所有 Compute Units，CU，并行处理不同的输出 tile；
- **CU / block 层**：一个计算单元及其 Local Data Share，LDS，即共享内存；
- **wavefront / warp 层**：一个 AMD wavefront 的寄存器级局部计算；
- **指令叶子层**：单条 MFMA / WMMA 等矩阵指令。

每个节点持有输入和输出矩阵的视图，并负责：

- 根据 tile 策略划分输入和输出；
- 执行局部计算；
- 累加结果；
- 对边界 tile 进行裁剪和越界保护。

论文通过 Visitor 模式遍历同一棵树：

- `ComputeVisitor`：用于计算或数值验证；
- `EmitVisitor`：用于生成 GPU 内核代码；
- `FeasibilityVisitor`：用于检查 LDS、VGPR 和并行度约束，并推导可行 tile。

这一设计的关键优点是：

> 验证的计算结构、检查资源可行性的结构、最终生成代码的结构保持一致，降低“参考实现正确但生成代码不正确”的风险。

## 2.2 CU-centric 的闭式 tile 推导

论文以 CU 为中心进行推导。其资源约束按照以下顺序施加：

1. **LDS 容量决定 CU 级 tile；**
2. **VGPR 容量决定 wavefront 级 tile；**
3. **CU 数量评估全局并行度与 occupancy；**
4. **MFMA 原子指令形状保证 tile 对齐。**

这不是传统严格的自顶向下或自底向上设计，而是从 GPU 中最关键的资源拥有者——CU——出发，分别向上检查 grid 并行度、向下验证指令对齐。

### （1）LDS 约束：确定 CU / block tile

对于 GEMM：

\[
C = A \cdot B,
\quad A \in \mathbb{R}^{M \times K},
\quad B \in \mathbb{R}^{K \times N}
\]

在一个 CU 中，需要同时缓存 \(A\) 与 \(B\) 的 tile。若 CU tile 为 \((t_M,t_N,t_K)\)，元素字节数为 `elem`，则共享内存约束是：

\[
(t_M+t_N)\cdot t_K\cdot elem \leq LDS.
\]

论文采用对称选择 \(t_M=t_N\)，并尽可能填满 LDS。对于验证平台的 64 KB LDS、FP32 元素（4 byte），推导得到：

- \(t_M=t_N=128\)
- \(t_K=32\)

即，一个 block / CU 计算 \(128\times128\) 的输出 tile，并按 \(K=32\) 分块从 LDS 中读取数据。

### （2）VGPR 约束：确定 wavefront tile

在 wavefront 层，输出子块 \(C\) 的累加器长期保存在 VGPR 中。若 wavefront 大小为 `wf=64`，则每个线程持有的累计元素数量近似为：

\[
\frac{t_{wm}\cdot t_{wn}}{wf}.
\]

进一步结合 MFMA 原子形状 \((m,n,k)\)，论文给出寄存器预算形式：

\[
V(u)=u\cdot \frac{t_{wn}}{n}\cdot c+V_{\text{overhead}}
\leq V_{\text{budget}},
\]

其中：

- \(u=t_{wm}/m\)；
- \(c\) 表示每个线程持有的 MFMA 累加片段大小；
- \(V_{\text{overhead}}\) 包含输入 fragment、中间变量和额外控制状态；
- \(V_{\text{budget}}\) 是每线程可用 VGPR 数。

在示例 GEMM 中，作者选择：

- wavefront tile：\((32,32,8)\)；
- 每线程需要存储约 \(32\times32/64=16\) 个 FP32 累加元素；
- 硬件 VGPR 上限为每线程 256 个寄存器，因此可行。

### （3）并行度 / CU 数约束

全局 grid 的 block 数需足以填满设备：

\[
\left\lceil M/t_M\right\rceil
\times
\left\lceil N/t_N\right\rceil.
\]

对于 \(4096^3\) GEMM：

- tile 为 \(128\times128\)；
- grid 为 \(32\times32=1024\) blocks；
- GPU 有 120 个 CUs；
- 即约为每 CU 8.5 个 blocks，作者认为具有较好的并行度。

如果每 CU 的 block 数低于约 1，则会标记为 occupancy 不足，并缩小 tile 以增加可并行 block 数。

### （4）MFMA 指令对齐

所有 tile 维度还需要是 MFMA 指令形状的整数倍。验证平台采用：

- `mfma_f32_16x16x4f32`
- 即 \(m=16,n=16,k=4\)。

因此：

- \(t_M,t_N\) 应为 16 的倍数；
- \(t_K\) 应为 4 的倍数。

示例中的 \(128,128,32\) 满足这些条件。

## 2.3 面向四类算子的扩展

### GEMM

GEMM 是整个框架的基础算子。论文通过 LDS、VGPR、CU 数和 MFMA 对齐，解析地推导 block tile 和 warp tile，并通过 FlyDSL 生成 GPU 内核。

### 2D 卷积

论文采用直接卷积，而不是 `im2col`、Winograd 或频域变换。其重点是：

- 分析输出 tile 所需的输入 halo；
- 更大的空间 tile 可提升输入重用、减少 halo 重读；
- 但空间 tile 增大也会提高 LDS 消耗；
- 对推理场景中的固定卷积核进行预打包，使 tile 内通道数据连续；
- 对低输入通道数场景，例如 RGB 的 \(IC=3\)，使用“spatial-to-channel replication / pixel shuffle”技巧，将空间维度复制到通道维，从而减少部分和。

### 在线 Softmax

Softmax 的算术强度仅约为 `0.2 FLOPs/byte`，因此作者将其视为带宽受限算子。

论文采用在线 softmax，通过维护：

- 行最大值 \(m_{\text{run}}\)；
- 归一化分母 \(\delta_{\text{run}}\)；
- 新 tile 处理后的修正因子 \(s=\exp(m_{\text{run}}-m_{\text{new}})\)。

在线归约的核心是最大值和分母状态的可结合合并操作。论文特别强调边界处理：

- 对越界元素不能补零；
- 应补为 \(-\infty\)，实际 FP32 中可近似为 \(-10^{38}\)；
- 否则零会在指数运算后向分母贡献非零值，导致 softmax 结果错误。

### 融合注意力

目标计算为：

\[
R=\operatorname{softmax}
\left(
\frac{QK^T}{\sqrt d}
\right)V.
\]

传统未融合实现会物化 \(L\times L\) 的注意力矩阵，造成 \(O(L^2)\) HBM 读写；融合实现按 Q tile 并行、按 K/V tile 串行流式处理：

1. 将一个 \(Q\) tile 保留在寄存器中；
2. 逐个读取 \(K,V\) tile；
3. 在寄存器中计算 score tile：
   \[
   S_t=Q_{\text{tile}}K_t^T/\sqrt{d};
   \]
4. 在线更新行最大值、归一化分母；
5. 计算指数权重 \(E_t\)；
6. 累加：
   \[
   O\leftarrow O\cdot s+E_tV_t;
   \]
7. 全部 K/V tile 处理结束后，输出 \(O/\delta\)。

作者给出融合相对于未融合方式的 HBM 流量节约比：

\[
\text{savings}=\frac{L^2\cdot elem}{4Ld\cdot elem}
=\frac{L}{4d}.
\]

该结论说明：收益随序列长度 \(L\) 线性增长，且是算法结构性收益，而非某一 tile 配置的偶然结果。

## 2.4 MFMA fragment 布局的实证纠错

论文的重要工程发现是：MFMA 指令的形状本身不足以推断寄存器 fragment 的线程拥有关系。

对 `mfma_f32_16x16x4f32`，作者发现实际输出寄存器布局与其依据 AMD ISA 文档的自然预期相反。文中给出的实测布局为：

\[
acc[f]=C[\text{col group}\times4+f][\text{row in }m],
\]

其中：

\[
\text{col group}=\lfloor tid/16\rfloor,
\quad
\text{row in }m=tid\bmod16.
\]

这意味着：

- 一个线程的列组编号控制输出行；
- 线程在 \(m\) 维的位置控制输出列；
- 与“线程行索引控制输出行”的直觉映射相反。

这一问题在两个 GEMM 串联时尤其关键，例如融合注意力中：

\[
QK^T \rightarrow E_tV.
\]

若代码生成器错误假设中间结果的 fragment 布局，就可能生成：

- 能编译；
- 能运行；
- 但数值结果悄然错误

的 kernel。作者通过结构化测试确认真实布局，并在 MFMA+MFMA 注意力 kernel 中将 \(E_t\) 以转置布局写入 LDS，使第二个 GEMM 能以正确的 A-fragment 索引读取。

- 未覆盖更实际的 BF16、FP16、FP8、因果掩码、GQA/MQA、KV cache、批处理、多头并行等 LLM 推理配置；
- 未报告多次测量的波动、统计显著性、功耗或能效；
- 缺少“闭式默认值作为 autotuning warm start”能减少多少搜索成本的定量实验证明。

因此，实验充分证明了方法的**可行性和概念价值**，但尚不足以证明方法在多平台、多精度和真实推理工作负载下具有普遍竞争力。

## 6. 主要结论与发现

- 通过将算子表示为分层算法树，并将硬件抽象为 LDS、VGPR、wavefront、CU 数、MFMA 指令形状等最小描述符，可解析地推导关键 tile 参数。
- 对 GEMM、二维卷积、在线 Softmax 和融合注意力，作者认为 tile 选择可遵循统一的 CU-centric 流程：
  1. LDS 决定 CU tile；
  2. VGPR 决定 wavefront tile；
  3. CU 数量决定并行度下限；
  4. MFMA shape 保证指令对齐。
- 在验证 GPU 上，FP32 \(4096^3\) GEMM 达到：
  - `12.3 TFLOPS`；
  - 为 `23.1 TFLOPS` MFMA 峰值的 `53%`。
- 直接 3×3 卷积相对于 naive baseline 达到：
  - `1.7×` 加速。
- 对 \(d=128\) 的融合注意力：
  - \(L=4096\) 时，融合版本慢于未融合版本，速度为 `0.95×`；
  - \(L=8192\) 时为 `1.25×`；
  - \(L=16384\) 时为 `1.50×`；
  - \(L=32768\) 时为 `1.68×`。
- 在 \(L=16384,d=128\) 时：
  - 融合注意力 HBM 流量约为 `34 MB`；
  - 未融合实现约为 `4329 MB`；
  - 即未融合版本的 HBM 流量高约 `129×`。
- 尽管 HBM 流量节省巨大，融合 kernel 距理论 roofline 仍有明显距离；主要原因是中间 \(E_t\) 写入 LDS 再读出的额外 LDS 带宽开销。
- 实测发现目标 CDNA GPU 的 MFMA 输出 fragment 布局与文档导出的直觉预期不一致。作者建议将 fragment ownership 视为必须通过实验验证、并编码到硬件描述符中的属性，而不能仅依据指令名字和 shape 推断。

## 7. 优点与亮点

### 方法层面

- **明确的反搜索立场，但非排斥搜索**  
  论文没有否定 autotuning，而是将闭式推导定义为零搜索成本的默认解和后续搜索的起点，定位较合理。

- **资源约束与 tile 决策的映射清晰**  
  LDS、VGPR、CU 数量分别控制不同层次的 tile 与并行度，逻辑易解释、可检查。

- **分层算法树具有组合性**  
  GEMM 可作为基础节点，Softmax 可作为流式归约节点，融合注意力则将两个 GEMM 和在线 Softmax 组合起来。这种结构较适合扩展到复杂融合算子。

- **正确性与代码生成统一**  
  计算验证和代码生成共享同一算法树，理论上有助于减少实现语义漂移。

- **显式处理边界语义**  
  用裁剪视图、越界谓词和算子相关 padding 规则处理边界；特别指出 Softmax 不能用零填充，是实用且重要的细节。

- **FeasibilityVisitor 的设计实用**  
  将 tile 推导、资源检查和“哪个约束成为瓶颈”的解释统一起来，便于工程调试与硬件迁移。

### 工程与实验层面

- **MFMA fragment 布局的实测纠错价值较高**  
  这是对 GPU 代码生成器非常具体的实践贡献。它揭示了 tensor instruction 编程中“程序能运行但结果错误”的高风险来源。

- **融合注意力的流量分析直观**  
  \(\frac{L}{4d}\) 的流量节省关系清晰地解释了为什么序列越长，融合越有利。

- **呈现了不利结果和瓶颈分析**  
  作者报告 \(L=4096\) 下融合变慢，并将剩余性能差距归因于 LDS 往返流量，而非仅展示最佳数据，透明度较好。

- **硬件描述符简洁**  
  只保留参与推导的硬件参数，有利于将方法迁移到新硬件时重新运行同一推导过程。

## 8. 不足与局限

### 8.1 性能水平与对比不足

- GEMM 仅达到 MFMA 理论峰值的 `53%`。作者承认其未实现多条独立 MFMA 指令发射、ping-pong buffering 等成熟技术，因此与手工优化 kernel 仍有显著差距。
- 融合注意力在 \(L=16384\) 下仅达到 `1.50×` 加速，而作者估计理论 roofline 可达约 `33×`，表明当前实现的资源利用并不充分。
- 缺少与 rocBLAS、hipBLAS、HipKittens、Triton、FlashAttention/FlashAttention-2 等强基线的端到端性能比较。
- 2D 卷积只与未详细定义的 naive baseline 比较，`1.7×` 的实际竞争力难以判断。

### 8.2 实验覆盖有限

- 真实测量基本仅限一个 AMD CDNA GPU，不能充分证明跨硬件可移植性；
- 第二个 GPU 描述符仅展示推导形式，并无实测性能验证；
- 未覆盖 NVIDIA Tensor Core、不同 AMD CDNA 世代、消费级 GPU 或其他 ISA；
- 仅展示 FP32，而 LLM 推理中更常用 BF16、FP16、FP8 或混合精度；
- 注意力实验主要是单头、固定 head dimension、无 causal mask 的理想化场景；
- 未评估 batch、多头、GQA/MQA、KV cache、变长序列、decode 阶段等关键推理负载。

### 8.3 闭式公式自身的适用边界

论文较强地表述“问题清晰时，解就是闭式公式”，但这一论断可能只适用于基本的资源可行性和初始 tile 选择。实际高性能 kernel 还受许多难以由简洁闭式模型覆盖的因素影响：

- 指令流水和 MFMA 延迟隐藏；
- wave 数量、调度器行为及占用率细节；
- LDS bank conflict；
- cache 层级、L2 重用、TLB 行为；
- 全局内存访问合并与对齐；
- 异步 load/store；
- 多 stage buffering；
- 不同 shape 的动态性能特征；
- 编译器寄存器分配和代码生成质量。

论文也间接承认这一点：其默认 GEMM 和融合注意力距离峰值仍较远。

### 8.4 硬件描述符可能过于简化

- 论文的 `HardwareDescriptor` 只包含 LDS、VGPR、wavefront、CU 数、带宽、理论峰值和 MFMA 原子形状等参数；
- 但 MFMA fragment 布局已经证明，仅有指令 shape 并不足够；
- 同理，其他硬件特性也可能需要被显式编码，例如 LDS bank 映射、寄存器分配粒度、指令吞吐/延迟、cache 容量、异步拷贝能力和调度限制等；
- 因此，“只需替换 descriptor 即自动迁移”的结论尚需更多硬件验证。

### 8.5 可复现性信息不完整

- 没有明确 GPU 精确型号；
- 没有给出 ROCm、驱动、编译器、FlyDSL 版本；
- 没有报告 benchmark 重复次数、方差、预热策略；
- 代码“available upon request”，而非公开可复现仓库；
- 文中虽称发现 AMD ISA 文档与实测布局存在差异，但没有给出完整最小可运行测试代码和原始输出细节。
