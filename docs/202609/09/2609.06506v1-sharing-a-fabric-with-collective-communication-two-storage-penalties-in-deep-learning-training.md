## 摘要
HPC 系统上的分布式深度学习训练通常使 NCCL/RCCL 集合通信与并行文件系统 I/O 共用同一网络结构。我们在 Slingshot-11 系统上使用真实的 GNN 训练工作负载表明，这种共享会带来两种不同的代价。主要代价是具有重尾特征的 DataLoader 停顿：在稳态下，典型的 DataLoader 等待时间仅为 15 ms，但在 28% 的 Lustre 迭代和 12% 的 VAST 迭代中会激增至数秒。次要代价是集合通信中的流量类别竞争：在一项隔离基准测试中，Lustre I/O 可使 all-reduce 的停顿增加最多 145 倍。这两种代价源于不同的机制。I/O 停顿延迟会影响所有经过共享网络结构的存储路径，而 all-reduce 网络竞争仅在存储与集合通信共享同一流量类别时发生。二者的共同根源在于存储 I/O 穿越了共享网络结构。本文表明，通过 DYAD 进行节点本地 NVMe 暂存（我们的代码已公开发布于 https://github.com/flux-framework/dyad）可使存储 I/O 避开该路径，从而消除这两种影响。在完整的一个训练 epoch 中，DYAD 相较于直接读取 Lustre 实现了 7.4 倍加速，相较于 VAST 实现了 1.06 倍加速。到第二个 epoch 时，随着本地缓存完全预热，DataLoader 停顿被完全消除，使 DYAD 相较于 VAST 达到 1.31 倍加速。

## Abstract
Distributed DL training on HPC systems often shares one network fabric between NCCL/RCCL collective communication and parallel-filesystem I/O. Using a real GNN training workload on a Slingshot-11 system, we show that this sharing imposes two distinct costs. The primary cost is heavy-tailed DataLoader stalls: the typical DataLoader wait is just 15 ms at steady state, yet spikes to multiple seconds in 28% of Lustre iterations and 12% of VAST iterations. The secondary cost is traffic-class contention on collective communication: Lustre I/O stalls the all-reduce by up to 145$\times$ in an isolated benchmark. The two costs arise from different mechanisms. I/O stall latency affects any storage path that traverses the shared fabric, whereas all-reduce network contention occurs only when storage and collective communication share the same traffic class. Their common root cause is that storage I/O traverses the shared fabric. This work shows that node-local NVMe staging via DYAD (Our code is publicly available at https://github.com/flux-framework/dyad) eliminates both effects by keeping storage I/O off that path. Across a full training epoch, DYAD achieves a 7.4 times speedup over direct Lustre reads and a 1.06 times speedup over VAST. By the second epoch, once the local cache is fully warmed, DataLoader stalls are eliminated entirely, allowing DYAD to reach a 1.31 times speedup over VAST.

# 论文总结：与集合通信共享网络结构的存储代价

## 1. 核心问题与整体含义

### 研究背景与动机

- 在现代 HPC（高性能计算）集群中，分布式深度学习训练通常同时依赖：
  - **NCCL/RCCL 集合通信**，例如反向传播时的梯度 `all-reduce`；
  - **共享存储 I/O**，例如从 Lustre、VAST 等文件系统读取训练样本。
- 这两类流量常会经过同一套高速网络 fabric。即使存储系统不同、协议不同，底层仍可能共享 NIC、交换机或注入带宽资源。
- 论文研究的问题是：**存储 I/O 穿越与集合通信共享的网络结构时，究竟如何、以及在多大程度上拖慢深度学习训练？**

### 核心发现

作者指出，共享网络 fabric 会产生两种彼此相关、但机制不同的性能代价：

1. **主要代价：DataLoader 的重尾停顿（heavy-tailed stalls）**
   - DataLoader 在大多数迭代中很快，但少数请求会因网络/存储排队延迟突然变慢到数秒甚至数十秒。
   - 一个 I/O worker 的慢请求即可阻塞整个 batch，导致 GPU 等待数据。
   - 此现象不仅发生于 Lustre，也发生于使用独立流量类别的 VAST；因此它并不只是集合通信与 I/O 同一 traffic class 竞争所致。

2. **次要代价：存储 I/O 对 all-reduce 的流量类别竞争**
   - 当 Lustre I/O 与 RCCL 集合通信经过同一 Slingshot traffic class 时，两者会竞争注入 credits，显著拉长 all-reduce。
   - 在隔离微基准中，Lustre I/O 可使 all-reduce 延迟恶化最多 **145 倍**。
   - VAST 使用独立 traffic class 后，该影响显著降低，但仍可出现最高 **24 倍**的极端干扰。

### 整体含义

- 论文的关键观点不是“Lustre 比 VAST 慢”，而是：
  > **只要训练数据读取仍经过共享网络 fabric，就可能产生严重的 DataLoader 延迟长尾；仅隔离 traffic class 可以缓解集合通信干扰，却无法消除存储访问本身的随机停顿。**
- 因此，作者主张将训练数据暂存到**节点本地 NVMe**，使常规训练读取走 PCIe/本地存储路径，而非共享 fabric，从根本上规避两类问题。

## 2. 方法论：DYAD 的核心思想与关键技术

## 2.1 总体思路

论文采用并扩展了 **DYAD**：一个面向 HPC 的 producer-consumer 文件流式系统。

其目标是：

- 不在训练开始前把完整数据集预拷贝到每个节点；
- 而是按训练过程中的实际请求，**按需、细粒度地将数据从 Lustre 拉取到节点本地 NVMe**；
- 后续访问直接命中本地 NVMe，避免重复经过共享网络。

核心策略可概括为：

> **懒加载（lazy staging） + 字节范围读取（byte-range fetch） + 节点本地 NVMe 缓存 + 数据集扁平化（flattening） + 文件单一所有者（single-file ownership）。**

---

## 2.2 为什么不能直接做全量预暂存或文件级缓存

论文认为常规 burst buffer 或文件级 staging 不适用于该场景，原因包括：

- 数据集总规模约 **687 GB**：
  - 原始 HDF5 数据约 157 GB；
  - 预计算图边缓存约 529 GB。
- 若在训练开始前从 Lustre 预暂存完整数据集，预计需要约 **20 分钟**，会显著推迟训练启动。
- 训练采用全局随机 shuffle：
  - 单个 epoch 内大部分样本仅访问一次；
  - 直接按“首次触碰整个文件”进行缓存，会将数 GB 的 HDF5 shard 拉取到本地；
  - 这远超单次 GPU 计算阶段约 **144–214 ms** 的可隐藏 I/O 时间窗口。

因此，文件级首次访问会造成严重阻塞，而逐样本、按字节范围获取则更适合。

## 2.3 DYAD 的关键设计

### 1）懒加载（Lazy staging）

- DYAD 不在训练前全量复制数据。
- 每当 DataLoader 需要某个样本时，才从源端存储读取对应数据并写入本地 NVMe。
- 好处：
  - 训练可立即开始；
  - 仅传输实际被访问的数据；
  - 避免短实验、调试任务等未跑完整 epoch 时产生无效预加载。

### 2）字节范围读取扩展（Byte-range fetch）

作者为 DYAD 新增了范围读取接口：

- 客户端调用：`dyad_consume_range()`
- 请求形式：读取任意区间 `[offset, offset + length)`。
- 本地缓存使用 **64 KB 对齐的数据块**。
- 若请求未命中：
  1. 将所需范围按 64 KB block 对齐；
  2. 通过 `pread()` 从 Lustre 源端读取；
  3. 通过 `pwrite()` 写入本地 NVMe 缓存；
  4. 使用 bitmap 记录哪些数据块已驻留；
  5. 后续同一块数据仅需从本地读取。

这一机制将一次预取所需的数据控制在约 **2.3 MB**，使其能够尽量在 GPU 计算窗口内完成并被隐藏。

### 3）并发安全的缓存管理

- 每个缓存块是否存在由 bitmap 标记。
- 多个请求竞争同一个未缓存块时，使用互斥锁保护 bitmap 更新。
- 锁不覆盖实际 I/O 操作，避免请求因网络读取时间而被串行化。
- 允许幂等式重复读取：即便两个请求同时拉取同一块，也不会破坏正确性。

### 4）HDF5 数据集扁平化

原始 HDF5 的样本访问需要进行：

- group hierarchy 解析；
- 对象头查询；
- 元数据路径遍历。

在全局 shuffle 下，单个 `(pdbid, poseid)` 样本每 epoch 基本只访问一次，因此 HDF5 元数据缓存难以发挥作用。

作者进行一次性离线预处理：

- 将每个样本映射为预先计算好的：
  - 文件位置；
  - 字节偏移 `offset`；
  - 样本长度 `length`。
- 训练时直接按已知 offset 发起一次 `pread()`，避免每次访问都经过 HDF5 元数据解析。

这一步是 DYAD 首 epoch 也能快于直接 Lustre 读取的重要原因之一。

### 5）单文件所有者（Single-file ownership）

- 每个数据文件由一个确定的 rank/节点负责。
- 该节点负责从 Lustre 拉取并缓存文件中的相应字节范围。
- 其他节点若需要该数据，则通过 RDMA 从 owner 节点读取，而不是都直接并发访问 Lustre。
- 作用：
  - 减少多个 rank 对相同 Lustre shard 的元数据访问与随机读取竞争；
  - 缩短存储流量在共享 fabric 上持续的时间；
  - 间接减弱与 RCCL all-reduce 的竞争。

## 2.4 训练时序与性能逻辑

每个训练迭代主要分为：

1. 等待 DataLoader 提供预取 batch；
2. Host-to-Device（H2D）拷贝；
3. 前向计算；
4. 反向计算与梯度 all-reduce。

关键条件是：

- GPU 的前向与反向计算合计形成约 **144–214 ms** 的 I/O 隐藏窗口；
- 若下一 batch 的数据预取可在该时间窗口内完成，则 DataLoader 等待趋近于零；
- 直接存储访问容易因网络长尾延迟超过该窗口；
- DYAD 通过细粒度读取与本地缓存，使大部分预取能在窗口内完成。

## 3.3 Benchmark 与测量方式

### 1）隔离微基准：all-reduce 干扰

作者构建了独立 benchmark：

- 使用 MILAN 的真实 EGNN 模型和训练循环；
- 执行真实前向、反向和 DDP all-reduce；
- 每个配置：
  - 先运行 200 次 warm-up；
  - 再运行 100 次无 I/O 测量迭代；
  - 随后以相同过程开启 I/O；
- 测量指标为最坏情况下：

\[
\text{干扰倍率} = \frac{\text{开启 I/O 时的 all-reduce 延迟}}{\text{无 I/O 时的 all-reduce 延迟}}
\]

该测试意在隔离“存储流量对集合通信”的影响。

### 2）端到端训练实验

- 每组运行完整单个 epoch；
- 每个 epoch 有 **5,120 次迭代**；
- 共处理约 **524 万样本**；
- 对比 direct Lustre、direct VAST 和 DYAD。
- 记录：
  - 全 epoch 墙钟时间；
  - 样本吞吐量；
  - DataLoader wait；
  - backward + all-reduce 时间；
  - 超过 1 秒的慢迭代比例；
  - 最坏迭代时间；
  - 多 epoch 缓存预热后的变化。

### 3）多 epoch 缓存预热实验

- 连续运行 DYAD 三个完整 epoch。
- 用于观察：
  - 首次访问 Lustre 的代价；
  - 缓存完全驻留本地 NVMe 后的稳定性能；
  - DataLoader 长尾是否消失。

- DYAD 的源端仍是 Lustre，而非换用更快的存储系统，因此“DYAD 优于直接 Lustre”的比较具有一定公平性。

### 不够充分的部分

- 端到端实验仅使用一个应用、一个数据集、一个模型和一个固定规模（4 节点、16 GPU）。
- 没有展示不同节点规模、不同 batch size、不同 DataLoader worker 数、不同缓存块大小下的结果。
- 没有直接对比其他节点本地缓存/预取系统，例如 NoPFS、FanStore、HVAC、HDF5 Cache VOL、UnifyFS 等。
- 多 epoch 的 VAST 和 Lustre对比似乎主要复用了单 epoch 时长，未展示它们连续多 epoch 的细粒度统计。
- 论文强调生产系统外部流量造成随机排队，但未重复多次独立试验并报告方差、置信区间或跨时段稳定性。
- 因此，实验对“该特定系统与工作负载上的机制”证据较强，但对更广泛 HPC 环境的普适性仍有待验证。

## 6. 主要结论与发现

### 1）DataLoader 长尾是主要性能瓶颈

- 在 VAST 上：
  - DataLoader 平均等待时间为 **324 ms**；
  - p95 为 **1.782 s**；
  - **11.5%** 的迭代等待超过 1 秒。
- 在 Lustre 上：
  - DataLoader 平均等待时间为 **1.987 s**；
  - p95 为 **11.381 s**；
  - **28.2%** 的迭代等待超过 1 秒。
- 尽管稳态中位等待时间很低：
  - Lustre 为 3 ms；
  - VAST 为 15 ms；
  但少量极端慢请求会使整体 epoch 时间大幅恶化。

### 2）Lustre 对 all-reduce 的影响主要来自同 traffic class 竞争

隔离微基准显示：

| 存储路径 | all-reduce 最坏干扰倍率 |
|---|---:|
| shm/tmpfs | 1.0× |
| 本地 XFS/NVMe | 1.0× |
| VAST，独立 TC | 24× |
| Lustre，与 RCCL 同 TC | 145× |

这说明：

- 本地存储不经过共享网络，几乎不影响 all-reduce；
- VAST 的 TC 隔离有效减轻了集合通信争用；
- Lustre 与 RCCL 共享 TC 时，注入 credit 竞争会造成严重的 all-reduce 波动。

### 3）但 all-reduce 不是 epoch 变慢的主因

- 对 Lustre 而言，额外 epoch 时间中：
  - 约 **93%** 来自 DataLoader 停顿；
  - 约 **7%** 来自 all-reduce 尖峰。
- 对 VAST 而言：
  - DataLoader 的额外等待累计为 **1,608 s**；
  - all-reduce 的额外时间仅为 **119 s**。

因此，只优化集合通信 traffic class 隔离并不足够，必须处理 DataLoader 的长尾 I/O。

### 4）DYAD 首 epoch 已优于 VAST 和 Lustre

| 配置 | 单 epoch 时间 | 相对 Lustre | 相对 VAST |
|---|---:|---:|---:|
| Lustre | 11,843.9 s | 1.00× | 约 0.14× |
| VAST | 1,693.9 s | 约 7.0× 更快 | 1.00× |
| DYAD，第 1 epoch | 1,595.8 s | **7.4× 更快** | **1.06× 更快** |

DYAD 在首 epoch 的优势并不只来自缓存命中，因为这时每个样本基本仍需首次从 Lustre 获取。作者将其归因于：

- 扁平化格式避免 HDF5 元数据访问；
- 单文件 owner 降低 Lustre 并发竞争；
- 细粒度读取降低单次请求的阻塞长度；
- 使多数预取可隐藏在 GPU 计算期间。

### 5）缓存预热后，DataLoader 的秒级停顿消失

DYAD 连续运行时：

| 指标 | Epoch 1 | Epoch 2 | Epoch 3 |
|---|---:|---:|---:|
| DataLoader 平均等待 | 90.4 ms | 13.8 ms | 14.1 ms |
| DataLoader 最大等待 | 5.0 s | 901 ms | 827 ms |
| DataLoader 等待超过 1 s | 2.93% | 0% | 0% |
| 总 epoch 时间 | 1,595.8 s | 1,293.3 s | 1,280.1 s |

- 在第 2 个 epoch 后，所需样本均已驻留在 owner 节点的本地 NVMe；
- 训练不再从 Lustre 进行源端读取；
- DataLoader 的秒级长尾停顿完全消失；
- DYAD 达到相对 VAST **1.31×** 的加速，相对 Lustre约 **9.2×–9.3×** 的加速。

## 7. 优点与亮点

### 机制分析清晰，区分了两类常被混淆的性能问题

- 论文没有简单地将问题归结为“文件系统慢”或“网络拥塞”。
- 它明确区分：
  - **经过 fabric 所造成的 DataLoader 长尾延迟**；
  - **共享 traffic class 所造成的 all-reduce 竞争**。
- 这一拆分具有实际系统设计价值：前者需要让 I/O 离开 fabric，后者可通过 traffic class 隔离缓解。

### 采用真实训练工作负载，而非纯合成 benchmark

- 使用 MILAN 的真实 EGNN 前向、反向和 DDP all-reduce；
- 使用数百万级样本与完整训练 epoch；
- 结论比仅靠网络压测或 I/O microbenchmark 更有可信度。

### 强调尾延迟而非平均值

- 该工作的重要贡献在于揭示：
  - 中位 DataLoader 等待只有几毫秒；
  - 但数秒级长尾足以主导总训练时间。
- 通过 p95、最大值、超过 1 秒迭代比例、逐迭代曲线和尾部分布等多种指标，证据较完整。

### DYAD 设计贴合该工作负载特征

- 懒加载避免长时间预热；
- 字节范围读取避免文件级首次加载；
- 本地 NVMe 缓存避免后续请求经过共享网络；
- 数据集扁平化解决 HDF5 元数据路径开销；
- 单文件 owner 缓解多客户端访问同一 shard 的竞争。

这些优化不是简单的“加缓存”，而是针对“全局 shuffle、样本小、文件大、单 epoch 复用低”的训练访问模式。

### 首 epoch 和后续 epoch 都有收益

- 首 epoch 即比直接 VAST 快 1.06 倍，说明方法不仅依赖缓存复用。
- 缓存完全预热后进一步达到 1.31 倍加速，展示了长期训练中的稳定价值。

## 8. 不足与局限

### 实验规模与应用覆盖有限

- 仅评估一个主要应用：蛋白质—配体预测 GNN。
- 仅使用一个 SAIR 数据集和一种 HDF5 数据组织方式。
- 未验证图像训练、语言模型训练、推荐模型、视频数据集或高数据增强场景。
- 因此，结论在“细粒度随机样本读取 + HDF5 大文件 + DDP”场景下很有说服力，但不能直接推广到所有 DL 训练任务。

### 节点规模较小

- 实验固定在 4 节点、16 GPU。
- 未展示在数十、数百或上千节点时：
  - DYAD owner 节点是否成为热点；
  - RDMA 跨节点缓存访问的扩展性；
  - 缓存目录/KVS 的可扩展性；
  - 文件所有权静态划分的负载均衡情况。

### 对比基线不够全面

- 虽然比较了 Lustre、VAST、本地 NVMe 和 DYAD，但没有与现有 DL 缓存或 burst-buffer 系统进行端到端对比。
- 特别是缺乏与以下类别方法的实测比较：
  - HDF5 Cache VOL；
  - NoPFS；
  - DeepFetch；
  - FanStore；
  - HVAC；
  - UnifyFS 等。
- 因而难以判断 DYAD 相对于已有本地缓存/预测预取方案的绝对优势。

### DYAD 并非在首 epoch 完全消除网络影响

- 论文摘要中使用“eliminates both effects”的表述，但从细节数据看，首 epoch 的 DYAD 仍需从 Lustre 拉取首次访问的数据。
- 首 epoch 中：
  - 仍有 **2.93%** 的迭代 DataLoader 等待超过 1 秒；
  - 最坏 all-reduce 时间仍达 **10.2 s**；
  - 说明其是显著缓解，而非在冷缓存状态下完全消除 fabric 干扰。
- 真正意义上的 DataLoader 长尾消失发生在第 2 epoch、本地缓存已充分预热之后。

### 缓存容量与数据集规模关系未被充分讨论

- 论文指出单个节点 NVMe 未必容纳整个数据集，因此采用跨节点分片缓存。
- 但未报告：
  - 每节点 NVMe 容量；
  - 数据实际缓存占用；
  - 数据集超过总本地 NVMe 容量时的替换策略；
  - 多任务共用节点本地盘时的隔离与公平性；
  - 缓存失效、训练数据更新、容错恢复的处理方式。
- 这些问题会影响方案在共享生产集群和超大数据集上的部署可行性。

### 依赖预处理和数据格式转换

- 数据集扁平化是性能提升的重要组成部分，但它要求：
  - 对 HDF5 数据进行一次性预处理；
  - 维护样本 offset/length 索引；
  - 训练程序或 I/O 路径适配新的读取方式。
- 这降低了对任意现有 HDF5 工作流的直接透明性。
- 对频繁更新、动态生成或复杂嵌套的 HDF5 数据，预处理的维护成本可能更高。

### 外部干扰的统计严谨性仍可加强

- 论文的核心现象来自生产系统中随机的网络/存储排队。
- 但文中未充分提供：
  - 多次重复实验；
  - 标准差或置信区间；
  - 不同时间段、不同系统负载下的结果；
  - 外部网络流量的直接测量。
- 因此，尽管观察到的长尾现象非常显著，具体比例和极端值仍可能受系统运行时背景负载影响。

（完）
