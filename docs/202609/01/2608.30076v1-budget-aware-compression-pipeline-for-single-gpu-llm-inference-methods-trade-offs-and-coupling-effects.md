## 摘要
在单张 NVIDIA GPU 上部署 700 亿参数语言模型，受到设备显存、长上下文吞吐量和工程集成成本的制约。我们将单 GPU 推理建模为围绕这三个维度的预算感知设计问题，并研究剪枝、量化与 KV 缓存压缩在真实执行条件下的相互作用。受控消融实验表明，逐层剪枝可提升权重量化的鲁棒性。KV 缓存稀疏化通过在不损害解码速度的前提下降低内存占用，与 INT8 KV 量化形成互补；而静态向量量化器通常会与动态缓存产生冲突。基于这些耦合关系的研究结果以及显式预算跟踪，我们构建了一条实用流水线，将一个 700 亿参数模型压缩至约 33 GB；在单张 A40 上处理 1 万 token 提示时，吞吐量约为 57 token/s，并且在通用与推理基准测试上的绝对准确率下降控制在 5% 以内。我们贡献了设计准则和可复现的评估协议，可联合报告质量、内存和端到端速度，并为在真实单 GPU 约束下进行自动化流水线搜索奠定了基础。

## Abstract
Single-GPU deployment of 70B-parameter language models on an NVIDIA GPU is constrained by device memory, long-context throughput, and engineering integration cost. We cast single-GPU inference as a budget-aware design problem over these three axes and study how pruning, quantization, and KV-cache compression interact under realistic execution. Controlled ablations show that layer-wise pruning makes weight quantization more robust. KV-cache sparsification complements INT8 KV quantization by reducing memory without hurting decoding speed, while static vector quantizers often conflict with dynamic caching. Guided by these coupling results and explicit budget tracking, we assembled a practical pipeline and compressed a 70B model to about 33 GB, sustained about 57 tokens/s on 10k token prompts on a single A40, and kept absolute accuracy within 5% on common and reasoning benchmarks. We contribute design rules and a reproducible evaluation protocol that jointly report quality, memory, and end-to-end speed, and we provide a foundation for automated pipeline search under realistic single-GPU constraints.

# 2. 方法论：核心思想、关键技术与流程

## 2.1 三维预算感知建模

作者将部署目标形式化为三维预算：

\[
B=(B_{\text{mem}}, B_{\text{thr}}, B_{\text{int}})
\]

其中：

- \(B_{\text{mem}}\)：显存预算，要求模型权重、激活和 KV Cache 总占用不超过 A40 的 48 GB；
- \(B_{\text{thr}}\)：吞吐预算，正文中设为在约 10k token 上下文下至少达到 10 tokens/s；
- \(B_{\text{int}}\)：集成预算，描述方法接入现有 serving stack 所需的代价，如是否需要新内核、固定形状编译、图重写或失去动态 KV Cache 支持。

此外，模型质量被视为硬约束：在 ARC、Winogrande、GPQA 等常识和推理基准上，准确率绝对下降不超过约 5%。

## 2.2 最终压缩流水线

论文推荐的主流水线为：

> **AWQ 权重量化 → ShortGPT/连续性感知层剪枝 → PyramidKV 稀疏化 + INT8 KV Cache 量化**

具体包括：

### （1）AWQ 4-bit 权重量化

- 使用 AutoAWQ 实现 **W4A16**：
  - 权重为 4-bit；
  - 激活保持 FP16。
- 选择 AWQ 而不是 GPTQ 的主要原因不是困惑度最低，而是：
  - 在 70B DeepSeek-R1-Distill-Llama 上，AWQ 的 ARC、Winogrande、GPQA 表现整体更均衡；
  - 与主流 Transformers / FlashAttention 路径兼容性较好；
  - 其激活敏感通道保护机制使得后续结构化剪枝更稳定。
- AWQ 将 70B 模型权重文件从 FP16 的约 132 GB 降至约 37–38 GB。

### （2）结构化深度剪枝：ShortGPT

- 作者采用 ShortGPT 风格的 **Transformer Block 级剪枝**，即直接删除部分完整层，而非删除零散权重或隐藏维度。
- 层重要性由 BI（Block Influence）系数衡量。给定相邻层 \(i\) 和 \(i+1\) 的隐藏状态 \(X_{i,t}\)、\(X_{i+1,t}\)，定义：

\[
BI_i = 1 - \mathbb{E}_{X,t}
\left[
\frac{X_{i,t}^{\top}X_{i+1,t}}
{\|X_{i,t}\|_2 \|X_{i+1,t}\|_2}
\right]
\]

- 直观上：
  - 若相邻层输出方向变化小，则层的表示变换有限，BI 较低；
  - BI 较低的层可能更冗余，优先作为剪枝候选；
  - BI 越高则表示该层造成更明显的表征变化，重要性可能更高。

### （3）连续性感知的层重排序/剪枝规划

论文在 ShortGPT 的逐层 BI 排序之外提出了一个更偏部署导向的改进：**连续性感知（continuity-aware）的层选择策略**。

核心观察：

- 对 DeepSeek-R1-Distill-Llama-70B 而言，低重要性层往往在网络深度方向形成连续区间；
- 单纯按 BI 从低到高挑选离散层，可能破坏网络层间的信息流连续性；
- 若优先删除一段连续的、整体低重要性的层带，则较高剪枝比例下的质量损失更可控。

该策略包含：

1. **局部连续性系数**  
   在层 \(k\) 周围的窗口内，计算相邻 BI 值的平均变化；变化越小，说明该区域的重要性分布越平滑、连续。

2. **候选生成**  
   同时构建两类候选：
   - 单个低 BI 层；
   - 平均 BI 低、且局部连续性高的连续层窗口。

3. **贪心规划**  
   每次选择基础重要性最低的候选，并对距离已选区间较近的候选给予连续性奖励，从而偏好选择相邻的低重要性层段。

论文中使用的典型超参数包括：

- 候选窗口长度 \(w=3\)；
- 连续性阈值 \(\tau_c=0.8\)；
- 低重要性阈值为窗口平均 BI 小于整体 BI 中位数的一定比例；
- 邻近奖励范围 \(r \in \{1,2\}\)；
- 奖励系数 \(\lambda=0.1\)。

### （4）PyramidKV + INT8 KV Cache

- 对长上下文，作者采用 PyramidKV 做 KV Cache 稀疏化：
  - 根据层级化的重要性保留策略，只维护更重要的 KV 条目；
  - 文中给出 PyramidKV window size 为 1024，附录又提到 window size 512、retention ratio 0.25，存在配置描述不完全一致的问题。
- 在稀疏化基础上，再对保留下来的 KV Cache 做 INT8 量化：
  - 使用每头缩放（per-head scaling）的对称 INT8 KV 量化；
  - 目标是在尽量减少显存的同时，避免 INT4 KV 量化带来的更明显解码性能下降。

## 2.3 模块耦合规律

论文的关键贡献之一是总结组合规律。

### 正向耦合 1：先 AWQ、后层剪枝

作者认为，推荐顺序应为：

> **先在完整稠密模型上进行 AWQ 校准和量化，再执行层剪枝。**

原因是：

- AWQ 的通道缩放和异常值保护依赖原始完整模型的激活统计；
- 如果先剪枝，层间信息流与激活分布变化，原来的量化校准假设可能失效；
- 先量化后剪枝则可先获得更稳定的低比特权重表示，随后通过缩短网络深度减少量化误差的逐层累积。

### 正向耦合 2：PyramidKV 与 INT8 KV 量化互补

- PyramidKV 先减少需要缓存的 token 数量；
- INT8 再降低每个保留 KV 条目的存储成本；
- 该组合相较全量 FP16 KV Cache 可进一步降低约 1.6 GB 峰值显存，同时保留约 57 tokens/s 的报告吞吐。

### 负向耦合 1：向量量化与动态 KV Cache 冲突

- QTIP、QuIP# 等向量量化方法可将权重压到 2-bit，但通常依赖：
  - 静态缓存预分配；
  - 固定形状编译；
  - 专用低比特内核。
- 这些要求会与 PyramidKV、SnapKV 等动态 KV 保留/驱逐机制冲突。
- 因此，虽然向量量化在单独测试中压缩率较高，但在目标管线中会导致动态缓存失效、吞吐下降或编译失败。

### 负向耦合 2：AWQ 后叠加非结构化稀疏

- Wanda 非结构化剪枝在测试中几乎未带来实质吞吐收益；
- 它还会破坏 AWQ 的异常值感知权重重构，造成量化稳定性变差；
- 文中提到在数学提示上出现异常符号序列、困惑度显著恶化的现象。

- 下游任务以英文选择题、问答和推理任务为主，缺少开放式生成、长文档问答质量、多语言、代码、工具调用、安全性等评测；
- 吞吐定义在正文中存在不够一致之处：
  - 正文强调约 **57 tokens/s**；
  - 表 9 中 PyramidKV + INT8 的吞吐为 **57.21 tokens/s**；
  - 但附录表 10 中，使用 10,240-token 输入时，INT8 配置的**纯 decode speed**约为 **8.59 tokens/s**，而“total tok/s”为 215.13；
  - 这些指标显然对应不同统计口径，论文虽称保留原始 prefill/decode 日志，但正文没有充分澄清“57 tokens/s”究竟是何种端到端定义。
- 因此，实验整体较系统，但关于不同推理阶段、不同框架和不同吞吐指标之间的可比性，仍需要更严格说明。

# 6. 主要结论与发现

1. **单项最优不等于流水线最优。**  
   压缩策略应按照显存、速度和集成成本共同选择。2-bit 向量量化虽然压缩率高，但若与动态 KV Cache 冲突，则不一定适合长上下文单卡部署。

2. **AWQ 是本文目标场景下较均衡的 4-bit 权重量化选择。**  
   相比 GPTQ，AWQ 在 70B 模型上的部分下游任务准确率更高，并且工程兼容性较好；最终被选作管线起点。

3. **结构化层剪枝比非结构化稀疏更适合现有单卡推理栈。**  
   - Wanda 的速度收益有限，且可能破坏 AWQ 后的量化稳定性；
   - SliceGPT 可显著提高吞吐，但质量损失大，并需重新设计内核；
   - ShortGPT 在较低剪枝比例下可获得较温和的吞吐提升和较低集成成本。

4. **剪枝顺序很重要：先量化、后剪枝更稳健。**  
   作者认为先在稠密模型上完成 AWQ 校准，再删除冗余层，可以避免剪枝先改变激活统计而削弱量化效果。

5. **连续性感知层重排序能改善高比例层剪枝的质量。**  
   在剪除 20/80 层时，连续性感知策略将：
   - ARC-E 从 ShortGPT 的 0.7012 提升至约 0.7243；
   - GPQA-Diamond 从 0.2879 提升至约 0.4091。  
   说明连续删除低重要性层带，优于离散地删除低 BI 层。

6. **PyramidKV 与 INT8 KV Cache 量化具有互补性。**  
   PyramidKV 减少保留 KV 条目，INT8 再压缩存储精度；在 70B、约 11,427 token 输入中，该组合报告峰值显存约 39,029 MB、吞吐约 57.21 tokens/s。

7. **最终管线可实现单张 A40 上的 70B 长上下文部署。**  
   论文报告最终模型工件约为 33 GB，并认为在 10k token 输入场景下可满足 48 GB 显存预算，且常识和推理任务绝对精度损失控制在 5% 左右。

# 7. 优点与亮点

## 方法层面

- **问题定义贴近部署现实**：将工程集成成本正式纳入预算，而非只讨论参数量、显存或困惑度。
- **强调方法耦合而非模块堆叠**：揭示“先量化后剪枝”“KV 稀疏化配合 INT8”“静态向量量化与动态缓存冲突”等实际规律。
- **连续性感知层剪枝具有直观系统价值**：不是只依据单层重要性打分，而是考虑低重要性层在深度方向上的连续结构。
- **保留模型拓扑结构**：使用整层删除而非高非结构化稀疏，有利于复用现有 GEMM 和注意力内核。

## 实验设计层面

- 同时报告模型大小、峰值显存、TTFT、吞吐、困惑度、下游准确率和 OOM 状态；
- 有从 8B 筛选到 70B 验证的分层实验设计；
- 包含正负耦合案例，而非仅展示成功组合；
- 给出了连续性感知剪枝的超参数敏感性；
- 公开说明了硬件、软件版本、校准样本规模、随机种子和预热处理，具备一定可复现性；
- 对 vLLM、llama.cpp、ExLlamaV2 等系统的比较范围保持了一定克制，没有宣称在所有 serving 场景中全面优于这些系统。

# 8. 不足与局限

## 8.1 实验覆盖不足

- 主要集中于：
  - 单张 A40；
  - 单一 70B 稠密模型族；
  - 英文 QA、常识与推理基准；
  - 约 10k token 长上下文。
- 未验证：
  - 24 GB 及以下消费级 GPU；
  - H100、L40S、RTX 4090 等不同硬件；
  - MoE 模型；
  - 多 GPU 推理；
  - 多语言任务；
  - 开放式生成质量；
  - RAG、代码生成、Agent、工具调用和安全关键任务。

## 8.2 结果口径存在不一致

- 正文声称最终系统在 10k token prompt 上“约 57 tokens/s”，但附录中的纯解码速率约为 8–11 tokens/s，且总吞吐达到约 200–277 tokens/s。
- 不同表格可能采用了不同的吞吐定义或计时范围，但文中没有统一解释：
  - 是只统计生成阶段；
  - 是 prefill 与 decode 的混合吞吐；
  - 是否启用 continuous batching；
  - 是否包含不同输出长度或不同上下文长度。
- 这会影响对最终部署性能的准确理解，也降低与外部系统结果的直接可比性。

## 8.3 端到端公平比较仍有限

- AWQ、GPTQ、QTIP、QuIP#、PyramidKV、ShadowKV 等方法依赖不同内核与运行时假设；
- 作者将部分高集成成本方法视为不适合目标管线，但没有提供充分调优后的统一硬件、统一模型、统一上下文长度、统一服务框架比较；
- 因此，“最终组合更优”的结论主要针对本文定义的集成预算和软件栈，而不能直接推广到所有推理引擎。

## 8.4 离线压缩成本未被量化

- 论文没有报告量化、校准、层重要性计算、剪枝、模型保存和验证的耗时与资源消耗；
- 没有比较不同方案在部署前转换阶段的 GPU 小时、CPU 内存、磁盘占用和工程人工成本；
- 对于实际生产部署而言，这些成本可能影响方案选择。

## 8.5 质量约束仍较粗粒度

- “绝对精度损失不超过 5%”是一个实用但较宽泛的目标；
- GPQA-Diamond 等高难推理任务对层剪枝十分敏感，例如 20 层剪枝时即使采用连续性感知策略，GPQA-Diamond 仍从 0.6313 降至约 0.4091；
- 因而，该方案在知识密集型或高难推理场景下的可靠性仍需谨慎评估。

## 8.6 论文内部描述存在少量不一致或缺失

- 正文称最终使用 PyramidKV window size 1024，但附录复现说明提到 window size 512、retention ratio 0.25；
- 结论部分提到“layer-fusion distillation”，但方法和实验部分并未清晰展示相应蒸馏流程或结果；
- “集成成本”虽有三档或清单化描述，但未形成可重复计算的统一量化指标；
- 代码和 YAML 被描述为“available upon request”，而非明确给出公共仓库链接，复现便利性仍有限。
