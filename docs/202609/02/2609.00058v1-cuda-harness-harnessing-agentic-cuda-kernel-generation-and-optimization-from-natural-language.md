## 摘要
开发高性能 CUDA 内核需要在算法实现、正确性验证以及面向硬件的并行优化方面具备专业知识，这构成了较高的专业门槛，也使得直接从自然语言生成 CUDA 内核（Text2CUDA）变得十分必要。与此同时，大语言模型（LLM）具备通用代码生成能力，促使一系列研究探索基于 LLM 的 CUDA 内核生成方法。这些方法主要关注将 PyTorch 等高级框架代码转换为 CUDA（Torch2CUDA），而非 Text2CUDA；在 Text2CUDA 中，模型必须理解高级输入的语义，并处理底层内核的实现与验证。此外，由于依赖预定义的测试输入，这些方法容易受到奖励投机（reward hacking）的影响。本文提出 CUDA-Harness，一种用于驱动自然语言到 CUDA 内核生成与优化的智能体框架。具体而言，我们引入中间结构化生成（Intermediate-Structured Generation），以连接高级语义理解与底层内核生成。为减轻 Text2CUDA 中的奖励投机问题，我们构建了基于合成的验证（Synthesis-Based Verification）机制，以提供隔离的测试数据和渐进式验证。此外，我们提出反馈自适应演化（Feedback-Adaptive Evolution）策略，在优化性能的同时优先保证正确性。最后，通过广泛的实验，我们证明了 CUDA-Harness 的有效性；进一步评估表明，该方法能够泛化至不同的大语言模型和硬件平台，并可扩展到 C-to-CUDA 转译任务。

## Abstract
Developing high-performance CUDA kernels demands specialized knowledge in algorithm implementation, correctness validation, and hardware-aware parallel optimization, creating a substantial expertise barrier and making generating CUDA kernels directly from natural language (Text2CUDA) essential. Meanwhile, the general-purpose code generation capability of Large Language Models (LLMs) prompts a series of works exploring LLM-based CUDA kernel generation. They mainly focus on transpilation from high-level frameworks such as PyTorch to CUDA (Torch2CUDA) rather than Text2CUDA, where models must understand the high-level input semantics and handle low-level kernel implementation and validation. Additionally, these methods are vulnerable to reward hacking due to reliance on predefined test inputs. In this paper, we propose CUDA-Harness, a framework for harnessing agentic CUDA kernel generation and optimization from natural language. Specifically, we introduce Intermediate-Structured Generation to connect high-level semantic understanding with low-level kernel generation. To dilute reward hacking in Text2CUDA, we construct Synthesis-Based Verification to provide isolated test data and progressive validation. Furthermore, we propose Feedback-Adaptive Evolution, a kernel evolution strategy that prioritizes correctness while optimizing performance. Finally, through extensive experiments, we demonstrate the effectiveness of CUDA-Harness, with further evaluations illustrating generalization across LLMs, hardware platforms, and to C-to-CUDA transpilation.

CUDA 高性能内核开发同时涉及：

## 1.2 现有方法的主要问题

论文认为现有 LLM-based CUDA 方法存在三方面不足：

- **研究重点偏向 Torch2CUDA**：即把已经包含完整算法细节的 PyTorch 程序转换为 CUDA，而不是从可能不完整或含糊的自然语言生成 CUDA。

- **容易出现奖励投机（reward hacking）**：许多智能体方法依赖预先给定的测试输入进行迭代优化，模型可能针对固定测试数据生成“看似正确”的实现，而非真正实现目标算法。

> 自然语言理解 → 中间结构化规划 → CUDA 内核生成 → 隔离测试数据合成 → 编译、正确性与性能验证 → 基于反馈的迭代优化。

其核心目标不是单纯提高代码生成能力，而是通过一个外部“工程化框架”约束 LLM 的生成和优化过程，使其能够更可靠地生成正确且高效的 CUDA 程序。

# 2. 提出的方法论

CUDA-Harness 主要由三个相互衔接的组件构成：

1. **Intermediate-Structured Generation，中间结构化生成**；
2. **Synthesis-Based Verification，基于合成的验证**；
3. **Feedback-Adaptive Evolution，反馈自适应演化**。

## 2.1 中间结构化生成

### 核心思想

论文不让智能体直接从自然语言生成最终 CUDA 代码，而是先生成一个结构化的 **Kernel Implementation Manifest（内核实现清单）**，再依据清单生成具体的 CUDA 程序。

这样做的作用是将：

- 高层语义理解；
- 算法细节补全；
- 低层 CUDA 实现；

拆分为相对独立的阶段。

### 内核实现清单

每个 manifest 条目对应一个独立的内核实现任务，包含：

- 内核名称；
- 输入和输出描述；
- 功能与算法说明；
- 与语言无关的参考代码片段；
- 测试输入和输出的形状；
- 数据类型信息；
- 其他实现和验证所需的约束。

在这一阶段，智能体主要负责理解自然语言并补全其未明确说明的内容，而不是立即编写具体 CUDA 代码。

### 自包含 CUDA Scaffold

在 manifest 之后，系统实例化一个固定的 CUDA 程序脚手架。脚手架通常包括：

- CUDA 头文件；
- kernel 和 launcher 的声明；
- host 端 launcher；
- device 端 kernel；
- 二进制测试数据的读取函数；
- 输出写回函数；
- `main` 函数；
- 参数检查和测试数据加载；
- 内存管理与 kernel 调用。

论文将内存分配、数据传输、线程块配置和 kernel 启动等操作集中到 launcher 中，使智能体主要关注：

- kernel 的具体计算逻辑；
- 与 kernel 匹配的 launcher 实现。

此外，脚手架：

- 禁止使用随意构造的 dummy input；
- 通过命令行参数读取外部准备好的测试数据；
- 在编译时通过 `#pragma message` 输出调用约定。

这使得生成阶段无法直接看到测试数据细节，从而减少针对固定输入进行过拟合的可能。

## 2.2 基于合成的验证

### 隔离测试数据合成

由于 Text2CUDA 通常没有现成的测试数据，CUDA-Harness 使用 NumPy、PyTorch 等标准数值库在独立环境中合成：

- 测试输入；
- 参考输出。

测试数据合成和 kernel 生成使用相互隔离的上下文，避免生成 kernel 的智能体修改测试数据或参考结果来迎合自身实现。

### 数值范围设计

论文指出，如果测试输入集中在较小数值范围内，则绝对误差容忍项可能主导验证标准，使数值上错误的 kernel 也可能通过测试。因此，作者倾向于使用更宽的数值分布，例如：

- 均值为 5.0；
- 标准差为 10.0 的高斯分布。

这样可以覆盖更广的数值范围，增强验证对错误实现的识别能力。

但大幅值输入也可能放大浮点累积误差，导致正确 kernel 被误判。论文明确选择了：

> 宁可增加部分 false negative，也要减少 false positive。

因为接受一个错误 kernel 会进一步误导后续优化过程。

### 渐进式多阶段验证

验证采用 fail-fast 顺序：

1. **编译检查**：判断 CUDA 程序能否在指定编译参数下成功构建；
2. **功能正确性检查**：将 kernel 输出与参考输出比较；
3. **性能测试**：只有编译和正确性均通过后，才在目标 GPU 上进行性能测量。

编译结果可抽象为：

\[
C(K;\phi)=\mathbb{I}[K\text{ 在编译参数 }\phi\text{ 下能够编译}]
\]

其中：

- \(K\) 表示待测 kernel；
- \(\phi\) 表示编译环境，例如 `-arch=sm_80`；
- \(\mathbb{I}\) 是指示函数。

功能验证定义为：

\[
V(K,x,y)=\mathbb{I}\left[|K(x)-y|\leq \epsilon_{atol}+\epsilon_{rtol}|y|\right]
\]

其中：

- \(x\) 是测试输入；
- \(y\) 是参考输出；
- \(\epsilon_{atol}\) 和 \(\epsilon_{rtol}\) 分别是绝对和相对误差容忍度。

以延迟为例，性能得分定义为：

\[
P_{\text{latency}}(K,x)=\frac{1}{\text{Latency}(K,x)}
\]

性能越高表示执行延迟越低。

### MCP 验证工具链

论文基于 Model Context Protocol（MCP）向智能体提供统一工具接口，包括：

- 编译工具；
- 功能正确性验证工具；
- 性能分析工具。

工具在实际部署环境中执行，因此理论上可以绑定不同的 GPU、编译器和 profiling 环境。

## 2.3 反馈自适应演化

### 正确性优先的修正

论文观察到，智能体容易在代码尚未正确时就引入激进优化，例如复杂的：

- shared memory 使用；
- 向量化；
- warp-level 操作；
- 特殊线程组织；
- 非保守的内存访问模式。

因此，CUDA-Harness 根据失败阶段采取不同策略：

- **编译失败**：根据编译器错误信息进行针对性修复；
- **功能验证失败**：回退到更保守、更简单的实现；
- **正确性通过后**：才进入性能优化阶段。

这种机制避免在错误实现的基础上不断叠加优化，减少错误累积。

### 基于奖励的性能优化

论文使用编译、正确性和性能结果构造奖励：

\[
r(K)=-1+C(K)+C(K)V(K)P(K)
\]

其含义是：

- 编译失败时获得惩罚；
- 编译成功但功能错误时不会进入性能奖励；
- 只有编译成功且功能正确时，性能 \(P(K)\) 才会影响最终奖励。

在没有传统可更新模型参数的情况下，系统引入 **优化洞察总结（optimization insight summarization）**。对于优化前后的 kernel：

\[
e=M_e\left(\text{Diff}(K_{\text{post}},K_{\text{pre}}),
r(K_{\text{post}})-r(K_{\text{pre}})\right)
\]

智能体比较：

- 前后版本代码差异；
- 奖励变化；
- 使用的优化策略；

并总结哪些策略有效或无效，作为后续迭代的经验。

### 演化流程

在每轮迭代中：

1. 以当前最佳 kernel 作为基础；
2. 生成多个候选 kernel；
3. 依次执行编译、功能验证和性能测试；
4. 保留性能最好的正确实现；
5. 总结本轮代码变更与奖励变化；
6. 将优化洞察累积到下一轮；
7. 重复若干轮后输出最佳 kernel 及其 launcher。

论文在主要实验中设置：

- 迭代轮数 \(N=3\)；
- 每轮生成候选数 \(G=3\)。

- 没有系统报告不同迭代轮数 \(N\)、候选数量 \(G\)、提示模板或采样策略对结果的影响。
- 没有与更多专门的 Text2CUDA 方法进行深入比较，部分对比对象主要来自 Torch2CUDA 或通用代码智能体。
- 跨硬件实验报告了总体指标，但没有提供不同 CUDA 版本、编译器版本、驱动版本和详细运行配置。
- 没有进行端到端成本—性能权衡分析，例如 LLM 调用次数、总延迟、GPU profiling 成本和收益之间的关系。

总体而言，实验能够支撑论文关于“框架有效性”和“具有一定泛化性”的结论，但对于稳定性、成本、任务覆盖和真实生产环境可靠性的论证仍不够充分。

## 5.3 公平性与客观性

### 有利于公平比较的设计

- 主要实验固定使用同一个底层 LLM；
- 统一在 A40 上进行主要测试；
- 使用统一的编译、功能验证和性能指标；
- 生成阶段只进行一次，性能测试阶段才重复运行；
- 对错误 kernel 将 RScore 置零，避免只比较少数成功样本的性能。

### 潜在公平性问题

- CUDA-Harness 使用了多轮候选生成和硬件反馈，而部分 baseline 可能采用更简单的生成流程，计算预算并不一定完全匹配。
- 不同方法的提示设计、工具访问权限和演化预算是否严格一致，论文提供的信息有限。
- CUDA-Harness 的性能优化直接利用目标硬件反馈，而某些对比方法可能没有同等程度的 profiling 工具支持。
- benchmark 测试数据虽然被隐藏，但合成数据与 benchmark 数据之间仍存在分布差异，且验证信号并非完全可靠。

# 6. 主要结论与发现

## 6.1 完整框架显著优于基线

在 CUDABench 上，完整 CUDA-Harness 的总体结果为：

- 编译成功率：99.7；
- 功能正确率：80.5；
- RScore：110.7。

相比 baseline：

- 编译成功率：90.1；
- 功能正确率：60.9；
- RScore：80.1。

在三个难度等级上，CUDA-Harness 均取得更高的编译率、正确率和性能分数。

## 6.2 难度越高，中间结构化生成越重要

随着提示信息减少、难度提升，直接从原始自然语言生成 CUDA 的 baseline 性能下降更明显。论文认为，Intermediate-Structured Generation 通过 manifest 显式补全：

- 算法细节；
- 输入输出语义；
- 数据类型和形状；
- 测试信息；

因此能缓解自然语言不完整带来的问题。

## 6.3 正确性优先机制对维持功能正确性有效

CUDA-Harness\* 的结果表明：

- 加入奖励驱动优化可以改善编译率和性能；
- 但如果移除 Correctness-First Refinement，功能正确率会受到影响；
- 完整 CUDA-Harness 在优化过程中更能避免正确性退化。

这说明单纯依赖性能奖励可能使智能体倾向于追求更快但错误的实现，而正确性优先回退机制是必要的。

## 6.4 合成验证具有较强但不完美的一致性

合成验证与 benchmark 验证的混淆矩阵显示：

- 合成验证通过且 benchmark 通过：73.6%；
- 合成验证通过但 benchmark 失败：8.7%；
- 合成验证失败但 benchmark 通过：6.9%；
- 两者均失败：10.8%。

论文报告：

- 准确率：84.4%；
- 精确率：89.4%；
- 召回率：91.4%。

这说明合成测试数据能够提供较强的正确性反馈，但不能完全替代真实 benchmark 验证。

## 6.5 方法具有跨模型和跨硬件泛化能力

在 DeepSeek-V3.2 和 GLM-5.1 上，CUDA-Harness 仍然优于对应 baseline，说明框架收益并不完全依赖 Seed2.0 Lite。

在 A40、GTX 1660 SUPER 和 Jetson AGX Orin 上：

- 编译成功率和功能正确率相对稳定；
- RScore 会因硬件性能差异而变化；
- 但 CUDA-Harness 在各平台均优于 baseline。

## 6.6 可迁移到 C-to-CUDA 转译

在 BabelTower 上：

- baseline 编译率：94.8；
- baseline 功能正确率：90.1；
- baseline Score：451.6；
- CUDA-Harness 编译率：98.7；
- CUDA-Harness 功能正确率：97.1；
- CUDA-Harness Score：514.8。

这表明中间结构化生成不仅适合 Text2CUDA，也可用于从已有顺序程序中提取语义并辅助并行 CUDA 实现。

# 7. 优点与亮点

## 7.1 问题定义具有现实意义

论文将研究重点从“代码转换”扩展到更具挑战性的自然语言到 CUDA 生成，关注的是：

- 语义不完整；
- 测试数据缺失；
- 正确性和性能需要同时保证；

这些问题更接近真实用户使用场景。

## 7.2 生成流程具有清晰的模块化结构

通过 manifest 和 scaffold，论文将复杂任务拆分为：

- 语义规划；
- 代码实现；
- 测试合成；
- 编译验证；
- 功能验证；
- 性能优化。

这种模块化设计降低了单次生成的认知负担，也便于后续替换底层 LLM 或工具链。

## 7.3 关注奖励投机这一关键风险

相比只关注速度提升，论文显式讨论了：

- 固定测试输入导致的过拟合；
- 测试数据与 kernel 生成共享上下文导致的信息泄漏；
- 小数值输入造成的宽松误差判断；
- 错误 kernel 通过验证后误导后续优化。

隔离测试数据合成、使用更宽数值分布和采用渐进式验证，体现了较强的可靠性意识。

## 7.4 正确性与性能之间的优先级设计合理

论文没有简单地把性能作为唯一目标，而是明确采用：

> 编译优先、正确性优先、性能其次。

这种顺序符合 CUDA 工程实践，也避免了在错误实现上进行无效优化。

## 7.5 具备硬件感知的闭环优化能力

系统直接在目标 GPU 上进行：

- 编译；
- 功能测试；
- 性能 profiling。

因此得到的优化反馈不是模型估计值，而是来自真实执行环境的可验证结果。

## 7.6 泛化实验较全面

跨 LLM、跨 GPU 以及 C-to-CUDA 的实验增强了方法的外部有效性，说明 CUDA-Harness 并非只针对单一模型、单一硬件或单一输入形式设计。

# 8. 不足与局限

## 8.1 合成验证仍无法完全解决奖励投机

虽然隔离上下文和隐藏 benchmark 输入能够降低风险，但合成数据验证仍可能与真实任务分布不一致。论文自身的结果也表明：

- 约 8.7% 的样本是合成验证通过但 benchmark 验证失败；
- 约 6.9% 的样本是合成验证失败但 benchmark 验证通过。

因此，合成验证只能提供近似的正确性信号，不能从根本上保证任意输入上的正确性。

## 8.2 依赖自然语言语义补全，仍存在误解风险

false positive 分析显示：

- 38.1% 来自 prompt 误解；
- 30.5% 来自遗漏 benchmark 特定的后处理步骤；
- 31.4% 与 CUDABench 模板对 `uint8`、`int32` 等数据类型处理不正确有关。

这说明系统的错误来源不仅来自 CUDA 编程，还来自：

- 自然语言歧义；
- 隐含后处理逻辑；
- benchmark 或模板实现缺陷。

在真实应用中，如果用户描述不完整，manifest 阶段的错误语义补全可能会被后续整个流程继承。

## 8.3 测试覆盖范围不够透明

论文没有详细披露：

- CUDABench 的任务总数；
- 算子类别；
- 张量形状和数据类型分布；
- 不同任务难度的具体构成；
- 任务是否覆盖复杂控制流、稀疏计算、动态形状和多 kernel 协作。

因此，难以判断其结果能否推广到更广泛的 CUDA 应用，例如：

- 大规模归约；
- 稀疏矩阵计算；
- 图算法；
- 动态内存访问；
- 多阶段流水线；
- 复杂同步和跨 kernel 协作。

## 8.4 缺少随机性与统计显著性分析

论文没有明确报告：

- 多次独立运行；
- 不同随机种子的结果；
- 均值、方差或置信区间；
- 失败案例的完整统计。

LLM 生成具有较强随机性，而每个 kernel 的生成似乎只执行一次，可能无法充分衡量结果稳定性。

## 8.5 计算和时间成本缺乏量化

虽然主要实验设置为 \(N=3\)、\(G=3\)，但论文没有给出：

- 单个任务的平均 LLM 调用次数；
- 总 token 消耗；
- 平均生成时间；
- 编译与 profiling 时间；
- GPU 使用成本；
- 与 baseline 相比的额外开销。

因此，方法在实际部署中的效率和性价比仍不清楚。较高的正确率和性能可能是以更多候选生成和硬件测试为代价获得的。

## 8.6 性能指标受硬件和测量环境影响

RScore 采用执行时间倒数，虽然直观，但会受到以下因素影响：

- GPU 型号和具体负载；
- CUDA、驱动和编译器版本；
- kernel 预热策略；
- 测量次数；
- 时钟频率和系统噪声；
- 输入规模和数据布局。

论文虽说明使用 Nsight Systems 和多次测量平均延迟，但没有充分说明所有测量细节，也未给出方差或统计显著性。

## 8.7 对比方法之间的预算可能不完全一致

CUDA-Harness 具有：

- 多阶段结构化生成；
- 多轮候选演化；
- 编译器反馈；
- 正确性测试；
- 目标硬件 profiling。

如果 baseline 没有获得相同的调用预算、工具访问权限和迭代次数，那么结果优势可能部分来自更大的搜索和验证预算，而不仅是方法设计本身。

## 8.8 仍然依赖可信的外部执行环境

框架需要：

- CUDA 编译器；
- 可用 NVIDIA GPU；
- 正确配置的 CUDA runtime；
- 测试数据生成环境；
- profiling 工具；
- MCP 工具链。

在没有 GPU、驱动不兼容或安全策略严格的环境中，CUDA-Harness 难以直接使用。

## 8.9 “RLVR”表述与实际优化机制存在一定距离

论文将性能反馈称为 Reinforcement Learning with Verifiable Reward，但系统没有通过梯度更新模型参数，而是通过：

- 生成候选；
- 评估奖励；
- 总结优化洞察；
- 将经验注入下一轮提示或上下文；

来实现测试时演化。因此，它更接近基于可验证奖励的搜索和上下文内策略改进，而不是传统意义上对策略模型进行参数更新的强化学习。该术语的使用需要谨慎理解。

## 8.10 对真实用户交互和安全性的讨论较少

论文重点是 benchmark 和自动验证，但没有深入讨论：

- 自然语言需求如何进行交互式澄清；
- 用户错误描述如何被发现；
- 生成代码的安全沙箱；
- 恶意 kernel、越界访问和资源耗尽；
- 多 GPU、异步执行和生产部署；
- 数值稳定性与跨输入分布的可靠性。

这些问题是 Text2CUDA 从实验系统走向实际工程工具时必须进一步研究的方向。
