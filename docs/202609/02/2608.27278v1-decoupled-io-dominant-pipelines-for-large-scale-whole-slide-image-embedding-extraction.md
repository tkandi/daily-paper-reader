## 摘要
全视野切片图像（WSI）是计算病理学的核心数据，但其规模极为庞大，因此基于图像块的处理成为基础模型推理的实际处理单元。然而，在大规模场景下，生成和处理海量图像块会迅速引入显著的 I/O 与任务编排开销，并且常常成为端到端性能的主要瓶颈。我们提出了一种面向大规模 WSI 嵌入提取的解耦式、I/O 感知流水线，将整个工作流分解为三个阶段：（1）图像块生成与暂存；（2）易并行的嵌入推理；（3）分片向量数据库写入。该设计将数据传输与计算相互隔离，实现高效的图像块供给，以及仅需极少通信的可扩展多节点推理。最终系统构建了一个分布式向量数据库，其中的嵌入与丰富的元数据（如患者、切片和图像块属性）进行持久关联，从而支持高效的过滤、检索和下游复用。该表征数据库具有紧凑且可复用的特点，可用于检索、分类和小样本学习等任务，尤其适用于资源受限的环境。我们表明，将 I/O、计算和写入过程解耦，能够实现大规模、高吞吐量的 WSI 嵌入提取。通过刻画系统的扩展边界，我们证明，在超过中等并发度后，存储将成为主要瓶颈，从而应将 WSI 嵌入提取重新认识为一个以数据为中心的系统问题，而非纯粹受计算能力限制的工作负载。

## Abstract
Whole-slide images (WSIs) are central to computational pathology but are prohibitively large, making patch-based processing the practical unit for foundation model inference. At scale, however, generating and handling massive numbers of patches on quickly introduces significant I/O and orchestration overhead, often dominating end-to-end performance. We present a decoupled, I/O-aware pipeline for large-scale WSI embedding extraction that decomposes the workflow into three stages: (1) patch generation and staging, (2) embarrassingly parallel embedding inference, and (3) sharded vector database ingestion. This design isolates data movement from compute, enabling efficient patch delivery, scalable multi-node inference with minimal communication. The resulting system produces a distributed vector database where embeddings are persistently coupled with rich metadata (e.g., patient, slide, and patch attributes), enabling efficient filtering, retrieval, and downstream reuse. This representation database is compact and reusable for tasks such as retrieval, classification, and few-shot learning, particularly benefiting low-resource environments. We show that decoupling I/O, computation, and ingestion enables high-throughput WSI embedding extraction at scale. By characterizing the scaling envelope, we demonstrate that storage dominates beyond moderate concurrency, reframing WSI embedding extraction as a data-centric systems problem rather than a purely compute-bound workload.

## 1. 核心问题与整体含义

### 研究背景

- 全视野切片图像（Whole-Slide Images, WSI）是计算病理学中的关键数据形式，单张图像可达数十亿像素甚至更大，无法像普通图像一样直接输入深度学习模型。
- 实践中通常将 WSI 切分为大量图像块（patch），并逐块输入病理基础模型，如 **HIPT、H-Optimus-0、Virchow2**，提取向量嵌入（embedding）。
- 当处理规模从单张或少量切片扩展至数千张 WSI、数亿级 patch 时，主要挑战不再仅是 GPU 推理速度，而是：
  - 从 WSI 读取图像区域；
  - 生成、保存和管理海量小 patch 文件；
  - 在计算节点间协调数据访问；
  - 从存储系统加载 patch；
  - 写入并构建大规模向量数据库索引；
  - 保存 patch 与患者、切片、空间坐标等元数据的关联。

### 核心问题

论文试图回答的问题是：

> 在超级计算机等大规模并行环境中，如何高吞吐、可扩展地从海量 WSI 中提取基础模型嵌入，并避免 I/O、元数据操作和任务编排开销使 GPU 长时间空闲？

作者的核心判断是：**大规模 WSI 嵌入提取本质上是一个 I/O 主导、数据中心型（data-centric）的系统问题，而不是纯粹的 GPU 计算问题。**

即使各 patch 的推理互相独立、几乎不需要通信，系统仍会因为共享文件系统带宽、海量小文件创建和元数据访问竞争而出现扩展效率下降。

## 2. 提出的方法论

## 2.1 总体思想：三阶段解耦流水线

论文提出一个 **解耦式、I/O 感知的 WSI 嵌入提取流水线**，将端到端过程拆分为三个可独立扩展、分别优化的阶段：

1. **Patch 生成与暂存（Patch Generation and Staging）**
2. **嵌入推理（Embedding Inference）**
3. **分片向量数据库写入（Sharded Vector Database Ingestion）**

其关键思想不是让所有步骤在线耦合执行，而是将 I/O 密集型、GPU 计算密集型和数据库写密集型任务隔离，使不同阶段按其资源瓶颈独立调优：

| 阶段 | 核心任务 | 并行模式 | 主要瓶颈 |
|---|---|---|---|
| 阶段 1 | 从 WSI 提取 patch 并暂存 | MPI 空间划分 | 小文件写入、元数据操作、存储竞争 |
| 阶段 2 | 用病理基础模型提取 embedding | SPMD / 每 GPU 一个任务 | patch 读取和数据供给延迟 |
| 阶段 3 | 将 embedding 和元数据写入向量库 | 分片并行写入 | 读写带宽、索引构建、写放大 |

该设计试图减少不同阶段之间的资源干扰。例如，patch 生成不与 GPU 推理同步竞争；推理任务也不必同时承担数据库建库的写入压力。

## 2.2 阶段一：MPI 空间分解的 Patch 生成

### 基本流程

对于一张指定金字塔层级的 WSI：

1. 所有 MPI rank 构建相同的全局 patch 坐标网格；
2. 使用循环式划分（cyclic partitioning）分配任务；
3. rank \(r\) 处理坐标序列：
   \[
   r,\ r+R,\ r+2R,\ldots
   \]
   其中 \(R\) 是 MPI rank 总数；
4. 对分配到的每一个 patch 坐标：
   - 将第 \(L\) 层坐标映射回 level-0 坐标；
   - 调用 `read_region` 从 WSI 中读取 patch；
   - 计算白色背景比例；
   - 保存 patch 至 rank 本地目录；
   - 写入空间坐标、质心、白背景比例、文件路径等元数据；
5. 所有 rank 完成后通过一次 barrier 同步；
6. rank 0 汇总元数据，生成全局 `index.csv`。

### 设计特点

- **关键提取循环无通信**：每个 rank 独立读取并写出自己的 patch。
- **循环划分提高负载均衡性**：适应组织区域不规则、有效 patch 分布不均的问题。
- **后期统一元数据汇总**：避免在主计算路径中频繁通信。
- 但该阶段会产生大量小文件，因此性能强烈受并行文件系统的元数据服务能力限制。

---

## 2.3 阶段二：SPMD 无通信嵌入推理

### 基本流程

每个 GPU 对应一个独立任务或 rank，采用 SPMD（Single Program, Multiple Data）模式：

1. 每个 rank 读取完整 patch 索引文件，并构建相同的数据集视图；
2. 使用步长索引（strided indexing）分配 patch：
   \[
   D_r = \{D[i] \mid i \bmod R = r\}
   \]
3. 每个 rank 使用本地 DataLoader 分批读取 patch；
4. 对每个 batch 执行基础模型前向推理，提取：
   - patch embedding；
   - 若模型支持，则额外提取 attention 或相关特征；
5. 每个 rank 将局部结果序列化为独立输出文件；
6. 最后由 rank 0 通过文件协调机制收集、合并和排序各 rank 输出，并生成每张 WSI 的最终 embedding 文件。

### 模型覆盖

作者测试了三种病理基础模型：

- **HIPT**
- **H-Optimus-0**
- **Virchow2**

这些模型在输入 patch 分辨率、向量维度和计算强度上不同，用于验证结论是否具有模型无关性。

### 核心观察

虽然推理阶段不存在梯度同步、All-Reduce 或参数通信，但 GPU 仍会因等待 patch 从共享存储加载而空转。因此：

> “没有通信”并不等于“能够线性扩展”。

---

## 2.4 阶段三：分片向量数据库构建

### 基本流程

1. 将 embedding 文件和对应元数据按文件粒度划分给多个数据库 shard；
2. 每个 shard 由一个独立 rank 或进程构建；
3. 分批流式插入 embedding 及其元数据；
4. 在本地 shard 上构建向量索引；
5. 通过应用层对多个 shard 并行查询，或单独查询某个 shard。

### 数据库设计含义

论文强调，embedding 不是一次性中间文件，而应作为长期可复用资源持久保存。向量数据库中保留：

- 患者级元数据；
- 切片级元数据；
- patch 文件与空间坐标；
- patch 质心；
- 白色背景比例；
- embedding；
- 可能的 attention 特征。

这样下游任务可以直接基于嵌入进行：

- 相似病例检索；
- 队列级检索与过滤；
- 分类；
- 小样本学习；
- 多模态分析；
- 空间病理分析。

从而避免每次新任务都重新访问原始 WSI 并重复生成 patch、重复推理。

## 2.5 性能模型

论文用如下简化模型解释性能瓶颈：

\[
T(R) = \max \left(\frac{N}{R}, \frac{N \cdot B}{BW_{\text{storage}}}\right)
\]

其中：

- \(N\)：待处理 patch 总数；
- \(R\)：有效计算处理速率或并行计算资源；
- \(B\)：每个 patch 对应的数据传输字节数；
- \(BW_{\text{storage}}\)：有效存储带宽。

含义是：

- 增加 GPU 或计算资源可以降低计算时间项 \(\frac{N}{R}\)；
- 但无法降低存储访问项 \(\frac{N B}{BW_{\text{storage}}}\)；
- 当并发达到一定规模后，存储项成为主导，吞吐量趋于饱和，扩展效率下降。

  - 比较 HIPT、H-Optimus-0、Virchow2 的大规模写入性能；
  - 对 HIPT 约 1.7 亿 embedding 行进行 1、2、4、8 节点强扩展。

总体而言，论文包含数十个可见配置点，且覆盖流水线全部三阶段，不只是单一推理 microbenchmark。

## 5.2 充分性评价

### 相对充分之处

- 覆盖了从单切片到 4,185 张切片生产规模的多个层次。
- 覆盖三个不同计算特征和 embedding 特征的病理基础模型。
- 同时使用：
  - 宏观吞吐和扩展指标；
  - GPU 利用率；
  - I/O 比例；
  - 文件数量与写入吞吐；
  - kernel-level profiling；
  - 数据库写入速率与内存使用。
- 证据链较完整：从 patch 小文件、推理供数、GPU 空闲，到 embedding 落库，都显示存储是共同瓶颈。

### 不充分或公平性有限之处

- 缺乏与外部基线系统的严格端到端定量比较。
- 没有直接量化“紧耦合流水线”相对于所提“解耦流水线”的总体加速比、资源利用率变化或成本节省。
- 没有报告不同存储策略下的对照，例如：
  - 原始 WSI 直接在线读取；
  - patch 打包为大文件或 WebDataset；
  - 本地 NVMe 缓存；
  - burst buffer；
  - 对象存储；
  - 并行打包格式如 HDF5、Zarr、LMDB、Parquet。
- 虽然作者强调元数据和向量数据库复用价值，但未实验验证下游检索、分类或 few-shot 任务的查询性能、准确率收益和实际节省的重复计算成本。
- 生产级实验覆盖 4,185 张 WSI，但文中未给出更系统的统计分布，如不同 WSI 大小分桶下的尾延迟、失败率、重试次数和总资源消耗。

## 6. 主要结论与发现

1. **大规模 WSI embedding 提取是 I/O 主导工作负载。**
   - 即使模型推理在 GPU 上高效执行，端到端性能仍由 patch 读取、文件系统带宽和元数据操作决定。
   - GPU kernel 效率高并不意味着端到端 GPU 利用率高；GPU 会在 batch 间等待输入数据。

2. **Patch 数量而非单纯输出字节数，是 patch 生成阶段的重要性能决定因素。**
   - 将 patch 尺寸从 224 增大至 256 后，文件数下降约 25%，总输出大小变化很小，但写入吞吐和运行时间显著改善。
   - 这说明大量小文件创建和元数据访问成本十分显著。

3. **无通信的易并行任务仍可能无法线性扩展。**
   - 推理阶段无需 All-Reduce 或梯度同步，但 GPU 数从 1 增至 40 时，扩展效率明显下降。
   - 三种模型在高并发下效率均下降，表明共享存储竞争是主要制约。

4. **推理中的 I/O 占比会随并发提高而上升。**
   - 例如 H-Optimus-0 的 I/O 比例从单 GPU 的 1.8% 上升至 40 GPU 的 15.5%；
   - HIPT 从 35.4% 降至部分中等规模配置的约 9.5%，但在 40 GPU 又升至 15.0%，体现模型计算强度与存储竞争共同作用；
   - Virchow2 的 I/O 比例从 1.2% 增至 12.9%。

5. **向量数据库写入同样受 I/O 约束。**
   - 对约 1.7 亿条 HIPT embedding，VDB 写入吞吐可从约 2.2 万 rows/s 提升至约 18.8 万 rows/s；
   - 8 节点相对单节点速率的加速比约为 6.15 倍；
   - 4 节点的并行效率最高，为 86.7%，是较合理的运行点；
   - 更高并发会受存储读带宽、元数据访问和索引写放大影响。

6. **embedding 应被视为可持久复用的数据基础设施。**
   - 将 embedding 与患者、切片、patch 和空间元数据持久保存，可减少未来任务重复读取原始 WSI 和重复推理的开销。
   - 这对于资源受限研究机构尤其有价值。

## 7. 优点与亮点

### 7.1 明确重构问题定义

- 论文没有把重点局限于“怎样让病理模型推理更快”，而是提出更系统的观点：
  - WSI embedding 提取的关键不只是模型 FLOPs；
  - 更是数据生成、搬运、暂存、索引和复用。
- 这一问题定位具有较强现实意义，尤其适合亿级 patch、跨节点并行和共享存储环境。

### 7.2 三阶段解耦架构合理

- 将 patch 生成、GPU 推理、数据库写入拆开，符合三者截然不同的资源瓶颈。
- 有助于：
  - 为 patch 阶段单独优化存储布局；
  - 为推理阶段独立分配 GPU；
  - 为建库阶段选择合适的写入并发；
  - 降低跨阶段资源竞争；
  - 提升任务恢复和检查点管理的灵活性。

### 7.3 并行策略与任务特征匹配

- Patch 阶段采用 MPI 空间坐标循环分配，避免集中调度和关键路径通信。
- 推理阶段采用 SPMD 加步长划分，避免传统分布式训练中的同步开销。
- 数据库阶段采用 shard 级并行和文件级 checkpoint，适合可恢复的大规模写入。

### 7.4 生产规模具有说服力

- 使用 Frontier 超算、4,185 张 WSI、4.14 亿 patch、1.70 亿非白 patch，规模显著大于许多仅基于少量 WSI 的系统研究。
- 评估不只停留在单 GPU 或单节点微基准，而是包含多节点、多模型和生产级异质数据负载。

### 7.5 证据链比较完整

- 从 patch 文件数影响；
- 到 GPU 利用率和 I/O 等待；
- 再到 kernel 级 profiling；
- 最后到 VDB 写入扩展性；

多层证据共同支持“系统受存储而非算力限制”的结论，避免仅依赖单一吞吐指标。

### 7.6 强调 embedding 的长期数据资产价值

- 将向量数据库与上游 embedding 生产过程直接整合，而不是把 embedding 当作临时 `.npy` 或特征文件。
- 元数据关联设计有助于可解释检索、空间定位、病例过滤和跨任务共享。

## 8. 不足与局限

### 8.1 缺少严格的端到端外部基线比较

- 论文指出传统紧耦合 WSI 流水线存在局限，但没有在相同数据、模型和硬件上，直接比较：
  - 紧耦合在线 patch—推理—写出方案；
  - 所提解耦方案；
  - 常见预处理缓存方案；
  - 其他 HPC WSI 数据流水线。
- 因而目前更能证明“该问题存在 I/O 瓶颈”，而不能完全量化证明“所提架构相对现有最佳实践的总体性能优势”。

### 8.2 “暂存为海量小文件”本身是瓶颈来源

- 阶段一将 patch 写为大量独立文件，虽然便于并行和实现，但也直接制造了小文件和元数据压力。
- 论文识别了这个问题，却没有充分比较或验证替代方案，例如：
  - 将 patch 打包为 shard 文件；
  - 使用 TAR/WebDataset；
  - 使用 Zarr、HDF5、LMDB、Parquet 等容器格式；
  - 使用节点本地 NVMe 缓存；
  - 使用 burst buffer 或分层缓存；
  - 直接从 WSI 进行流式解码而不持久化 patch。
- 因此，“解耦”解决了流程隔离问题，但未必是从根本上减少数据膨胀的最优设计。

### 8.3 向量数据库的应用价值缺少下游验证

- 文中主张持久 embedding 数据库可支持检索、分类、few-shot learning 和低资源环境复用，但没有提供：
  - 检索延迟、召回率或吞吐；
  - 元数据过滤性能；
  - 跨 shard 查询性能；
  - 分类或 few-shot 实验；
  - 与重复在线推理相比的成本和能耗节省。
- 因而“可复用表示数据库”的系统价值在概念上合理，但应用层收益尚未被充分量化。

### 8.4 泛化性受平台和存储环境限制

- 全部实验在 Frontier 与 Orion/Lustre 上执行。
- Frontier 的 GPU、并行文件系统和调度机制具有代表性，但结果未必可直接外推到：
  - 云端对象存储；
  - 医院本地 PACS/DICOM 系统；
  - 普通 GPU 集群；
  - 单机多 GPU 工作站；
  - 网络文件系统或商业云块存储。
- 尤其在实际医疗环境中，数据访问权限、脱敏、网络隔离和跨机构传输可能是比吞吐更复杂的限制。

### 8.5 模型与数据模态覆盖有限

- 实验只覆盖 H&E WSI 和三个视觉病理基础模型。
- 尚未验证：
  - 多染色类型；
  - 免疫组化；
  - 荧光病理；
  - 3D 病理；
  - 多模态 WSI—文本—基因组模型；
  - 多尺度 patch、重叠 patch 或自适应采样策略。
- 不同模型输入分辨率、embedding 维度和预处理复杂度差异可能进一步改变 I/O 与计算边界。

### 8.6 集中汇总可能成为大规模尾部瓶颈

- 阶段一由 rank 0 收集所有元数据并生成全局索引；
- 阶段二由 rank 0 汇总所有 rank 输出、排序并写出最终 embedding 文件。
- 这一设计在实验规模下可行，但随着单张 WSI 的 patch 数量、节点数或输出体量继续扩大，rank 0 的集中式聚合可能形成：
  - 内存瓶颈；
  - 元数据处理瓶颈；
  - 单点故障风险；
  - 尾部延迟来源。
- 论文未对这一集中汇总步骤的成本和可扩展上限进行独立分析。

### 8.7 运行成本和能耗未量化

- 作者提出 embedding 数据库可降低未来重复计算和数据读取开销，也提到能效价值。
- 但论文没有报告：
  - 总节点小时；
  - GPU 小时；
  - 存储占用；
  - 每百万 patch 的成本；
  - 能耗或碳排；
  - embedding 持久化与重复推理之间的成本平衡点。
- 这些指标对于评估大规模医学数据基础设施的实际部署价值十分重要。
