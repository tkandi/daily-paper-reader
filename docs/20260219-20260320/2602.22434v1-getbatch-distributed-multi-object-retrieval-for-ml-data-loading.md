## 摘要
机器学习训练流水线以批次形式消耗数据。单个训练步骤可能需要从分布在存储集群中的分片中提取数千个样本。发送数千个独立的 GET 请求会产生单次请求开销，而这种开销通常在数据传输时间中占主导地位。为了解决这个问题，我们引入了 GetBatch——一种新的对象存储 API，它将批量检索提升为一等存储操作，通过单一的、确定性的、容错的流式执行取代了独立的 GET 操作。对于小对象，GetBatch 实现了高达 15 倍的吞吐量提升；在生产训练工作负载中，与独立 GET 请求相比，它将 P95 批量检索延迟降低了 2 倍，将 P99 单对象尾部延迟降低了 3.7 倍。

## Abstract
Machine learning training pipelines consume data in batches. A single training step may require thousands of samples drawn from shards distributed across a storage cluster. Issuing thousands of individual GET requests incurs per-request overhead that often dominates data transfer time. To solve this problem, we introduce GetBatch - a new object store API that elevates batch retrieval to a first-class storage operation, replacing independent GET operations with a single deterministic, fault-tolerant streaming execution. GetBatch achieves up to 15x throughput improvement for small objects and, in a production training workload, reduces P95 batch retrieval latency by 2x and P99 per-object tail latency by 3.7x compared to individual GET requests.

### 1. 核心问题与研究动机
*   **核心问题**：在大规模机器学习（ML）训练中，数据加载通常面临“随机访问灵活性”与“顺序访问高效性”之间的权衡。
*   **研究背景**：
    *   **随机访问（Map-style）**：如 PyTorch 的默认模式，方便实现完美随机采样，但在对象存储（如 S3）中，为每个小样本发送独立的 GET 请求会产生巨大的协议开销（TCP 握手、元数据处理、调度延迟），导致 GPU 等待数据（I/O Stall）。
    *   **顺序访问（Iterable-style）**：通过将样本打包成大文件（如 TAR 分片）来提高吞吐量，但牺牲了采样的随机性，且需要复杂的客户端缓冲区和混洗逻辑。
*   **动机**：开发一种存储原生 API，既能保持随机采样的灵活性，又能通过批量处理消除单次请求的开销。

### 2. 方法论
*   **核心思想**：引入 **GetBatch** API，将批量检索提升为对象存储的一级操作。客户端只需发送一个包含多个对象路径的请求，存储集群内部并行检索并以单一流（TAR 格式）返回。
*   **关键技术细节**：
    *   **分布式执行模型**：采用“指定目标（Designated Target, DT）”协调机制。代理节点选择一个 DT 负责汇总，其他存储节点作为“发送者（Senders）”并行读取本地数据并流式传输给 DT。
    *   **确定性顺序**：DT 强制要求输出流中的对象顺序与请求列表完全一致，确保特征与标签的严格对齐，这对可重复训练至关重要。
    *   **容错机制（Continue-on-error）**：允许在个别样本丢失时继续执行，并在流中插入占位符，防止长时训练任务因偶发错误中断。
    *   **协同定位提示（Colocation Hints）**：客户端可提示数据分布，使代理能选择拥有最多目标数据的节点作为 DT，减少跨节点流量。

### 6. 主要结论与发现
*   **吞吐量大幅提升**：对于 10KB 的小对象，GetBatch 相比独立 GET 实现了高达 **15 倍** 的吞吐量提升；对于 100KB 对象提升约 6 倍。

### 7. 优点
*   **架构简洁**：将复杂的并行检索和排序逻辑下沉到存储层，简化了客户端数据加载器的代码。
*   **兼顾灵活性与性能**：在不改变现有随机采样逻辑的前提下，达到了接近顺序读取的性能。
*   **原生支持归档**：能够直接从 TAR 分片中提取单个成员并重新打包，无需客户端下载整个分片。

### 8. 不足与局限
*   **后端依赖**：目前仅在 NVIDIA AIStore 中实现，并非 S3 等标准对象存储协议的通用功能，迁移成本较高。
