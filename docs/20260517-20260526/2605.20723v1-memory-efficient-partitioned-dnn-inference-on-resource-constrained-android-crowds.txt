# Memory-Efficient Partitioned DNN Inference on Resource-Constrained Android Crowds

## Abstract 

Deploying large deep neural networks on memory-constrained mobile devices is a cen-tral challenge in edge ML. While compression, pruning, and quantization reduce per-parameter cost, transformer-based models remain too large for the 3.3–7.4 GB RAM envelope of commod-ity Android handsets. We present the DNN pipeline scheduling subsystem of CROWDio, which achieves practical ONNX inference across resource-constrained Android workers without 

model modification, by distributing memory pres-sure across devices via five mechanisms: JIT de-ferred partition loading, a single-partition-resident constraint, a 4-tier affinity scheduler, a zlib-compressed tensor transport, and a streaming 1:1 dependency model. Evaluated on Distil-BERT (Sanh et al., 2019) ( ≈67 M parameters, SST-2) across five Android handsets over ten runs, our system holds peak per-device RSS to 43 ±2 MB and limits battery draw to 50 ±3 mAh per run, while streaming concurrency cuts batch latency 34% below barrier synchronisation. 

## 1. Introduction 

Resource-efficient ML uses compression, pruning, quan-tization, and distillation to reduce inference footprints. A complementary, under-explored axis is deployment-aware partitioning : rather than shrinking a model, distribute its layers across multiple memory-constrained devices so the aggregate fleet memory accommodates the full model while no single device exceeds its RAM budget (Li et al., 2020; Huang et al., 2019).

Commodity handsets carry 3.3–7.4 GB RAM; a mid-sized transformer such as DistilBERT requires 2–4 GB for a single ONNX session, leaving negligible headroom for the OS and background processes. Existing solutions—pruning (Han et al., 2016), post-training quantization (Jacob et al., 2018), distillation— still assume a single-device host and require model modifi-cation. Split computing systems (SPINN (Laskaridis et al., 2020), Neurosurgeon (Kang et al., 2017)) target a single, fixed partition point to a reliable cloud backend; neither ad-dresses the stochastic availability and heterogeneous RAM of a volunteer crowd, nor the need to schedule dynamically across more than two pipeline stages. We present the DNN pipeline scheduling subsystem of CROWDio (Manamperi et al., 2026), contributing: • JIT deferred loading (Section 3.2): shards loaded only when tasks are pending, bounding peak RAM. • Single-partition residency (Section 3.2): one ONNX session per worker, hard-capping RSS. • 4-tier affinity scheduler (Section 3.5): prioritises res-ident → cached → idle → evict, cutting cold-load latency on the critical path. • Compressed tensor transport (Section 3.4): zlib-encoded self-describing payloads with filesystem fall-back. • Streaming 1:1 dependency model (Section 3.3): per-input task independence replaces batch barriers.

## 3. Memory-Aware Partition Scheduling 

3.1. System Overview 

CROWDio has three layers over persistent WebSocket con-nections (Fette & Melnikov, 2011) (Figure 1). The Devel-oper SDK generates a linear DAG from ordered ONNX artefacts and submits SHA-256-checksummed model blobs (see Section 4). The Foreman handles scheduling (Sec-tion 3.5) and failure recovery. Android Workers execute ONNX inference under the single-residency constraint (Sec-tion 3.2) and report telemetry every 30 s.

The single-partition-resident constraint limits each worker to one active ONNX session at a time. Combined with JIT loading, peak RSS is bounded to one shard’s footprint re-gardless of pipeline depth. A monolithic DistilBERT ONNX session requires 2–4 GB (Sanh et al., 2019); our scheme holds per-device RSS to 43 ±2 MB (Section 5), as no worker ever holds more than one partition simultaneously. Partition correctness is verified end-to-end: chained ONNX Runtime output vs. full PyTorch output yields max-abs error ≈ 0.

3.4. Compressed Tensor Transport 

Intermediate activations are encoded as self-describing JSON payloads ( dtype , shape , compression , base64-zlib byte string) embedded over the existing Web-Socket channel, with symmetric serialisation in Python (SDK/Foreman) and Kotlin (Android worker). This achieves 62 ±4% compression on [1 , 768] FP32 tensors (3 072 raw bytes), reducing inter-stage transfer to ≈1 168 bytes per tensor on average. The protocol is codec-agnostic: LZ4 or Snappy may be substituted for lower-latency deployments without changes to the framing schema. When compressed payload size exceeds threshold τws (de-fault: 1 MB), the payload is written to a shared filesystem store and only a reference key is forwarded to the Foreman, avoiding double-transfer through the broker (Table 2). This two-path design ensures the WebSocket channel is never saturated by large intermediate tensors, which is critical under Wi-Fi contention in a multi-device crowd. 

3.5. 4-Tier Model Affinity Scheduler 

The affinity scheduler wraps any base ranking algorithm (FIFO, EDAS (Ghorabaee et al., 2017), ARAS (Zavadskas & Turskis, 2010), MABAC (Pamucar & Cirovic, 2015)) with two pre-dispatch gates. 

Model gating restricts dispatch to workers whose required partition is already in session memory, preventing the race condition where inference arrives before a JIT-loaded parti-tion is ready (Section 3.2). 

Affinity promotion ranks eligible workers by residency tier (Table 3). Crucially, Tier 4 is not an unconstrained fallback: it triggers an explicit UNLOAD MODEL of the resident shard followed by a fresh LOAD MODEL , incurring the highest latency while still preserving the single-residency invariant. EdgePipe (Zhao et al., 2022) reports 43% inter-stage transfer reduction from equivalent affinity strategies, validating this design. Within a tier, workers are ranked by live heartbeat teleme-try (CPU, RAM, battery, RTT, temperature) weighted via Shannon entropy (Shannon, 1948; Pramanik et al., 2021): criteria that are uniform across workers receive near-zero weight; high-variance criteria dominate. ## 4. End-to-End Execution 

SDK submission. The developer specifies ordered ONNX stage artefacts and execution mode. The SDK performs stage normalisation, auto-topology generation (linear DAG with source/intermediate/sink classification), acyclicity val-idation, and submits a SUBMIT PIPELINE JOB mes-sage with base64-encoded, SHA-256-checksummed model blobs. 

Foreman job creation. The Foreman materialises N ×S

task records and registers the DAG per Section 3.3. cell a 

is eagerly broadcast to all workers; JIT load instructions for 

cell b /cell c are stored and dispatched only on the first upstream task completion, enforcing the memory budget invariant (Figure 3). 

Worker inference. The worker decodes the input activa-tion (inline or from the filesystem store per Section 3.4), runs inference via a session-cached OrtSession , and re-encodes the output as a compressed payload. Sessions are cached per model path and released on UNLOAD MODEL .

Pipeline progression. The dependency manager injects the upstream payload into the downstream task, decrements its dependency counter to zero, and enqueues it for the affinity selector (Section 3.5). On all-task completion, logit scores across inputs are averaged and the majority-class prediction returned to the SDK. 

Failure recovery. On worker disconnect, the dynamic topology planner scores surviving workers by success rate, RAM, battery, GPU availability, and residency tier, and re-dispatches affected tasks without interrupting in-flight inferences.

## 6. Discussion and Conclusion 

We presented the DNN pipeline scheduling subsystem of CROWDio, enabling multi-stage ONNX inference of Distil-BERT across resource-constrained Android workers without pruning, quantization, or cloud back-ends. JIT loading and single-residency (Section 3.2) bound peak RAM to one shard’s footprint, making deployment feasible on handsets where a monolithic session (2–4 GB) would starve the OS. Streaming concurrency (Section 3.3) eliminates cross-input straggler blocking, cutting batch latency 34% below barrier mode (Table 4). The core insight is that deployment-aware partitioning and per-shard compression are complementary: partitioning distributes memory pressure across the fleet while compression reduces each shard’s transfer and storage footprint. Several trade-offs merit attention. The single-residency con-straint is conservative on higher-RAM ( >6 GB) devices where holding two shards simultaneously would still leave OS headroom; memory-adaptive multi-partition residency is a natural extension. The 48 s cold-start cost—covering partition download and ONNX session initialisation—is significant for latency-sensitive applications, but collapses to 6 s on Tier-2 warm runs (Section 3.5); aggressive pre-fetching informed by job arrival patterns is a natural mit-igation. zlib compression adds CPU-bound serialisation on the critical path; LZ4 or Snappy may be preferable for lower-latency deployments. Auto-topology generation is currently restricted to linear chains; branch or merge topolo-gies require developer-supplied explicit graphs (Moritz et al., 2018). Future work will combine memory-adaptive residency, non-linear topology support, and energy-aware scheduling (Pra-manik & Biswas, 2024) with quantization-aware shard train-ing to push transformer-class inference to sub-2 GB RAM devices. 

## Impact Statement 

This work lowers the barrier for transformer inference in low-resource settings by enabling commodity Android hand-sets to participate in inference without model modification.
