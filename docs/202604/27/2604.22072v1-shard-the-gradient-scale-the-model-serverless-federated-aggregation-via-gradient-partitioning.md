## 摘要
无服务器平台上的联邦学习（FL）聚合面临着严峻的可扩展性瓶颈：现有架构（如 lambda-FL、LIFL）在聚合器之间划分客户端，但每个聚合器都必须在内存中持有完整的模型梯度。当梯度超过单个函数的内存限制（例如 AWS Lambda 上的 10 GB）时，无论树深度或分支因子如何，聚合都变得不可行。我们提出了 GradsSharding，它将梯度张量划分为 M 个分片，每个分片由一个无服务器函数独立进行平均，该函数接收来自所有客户端的贡献。由于 FedAvg 平均是逐元素进行的，因此该方法产生的结果与基于树的方法在位级别上完全一致，从而在构造上保证了模型准确性不变。每个函数的内存限制在 O(|θ|/M)，与客户端数量无关，从而能够聚合任意大的模型。我们通过 HPC 实验和真实的 AWS Lambda 部署，在 43 MB 到 5 GB 的模型规模下，将 GradsSharding 与 lambda-FL 和 LIFL 进行了评估。结果显示，在梯度大小约为 500 MB 时出现成本交叉点，在 VGG-16 规模下成本降低了 2.7 倍，并且 GradsSharding 是唯一在超出无服务器内存上限后仍可部署的架构。

## Abstract
Federated learning (FL) aggregation on serverless platforms faces a hard scalability ceiling: existing architectures (lambda-FL, LIFL) partition clients across aggregators, but every aggregator must hold the complete model gradient in memory. When gradients exceed the per-function memory limit (e.g., 10 GB on AWS Lambda), aggregation becomes infeasible regardless of tree depth or branching factor. We propose GradsSharding, which instead partitions the gradient tensor into M shards, each averaged independently by a serverless function that receives contributions from all clients. Because FedAvg averaging is element-wise, this produces bit-identical results to tree-based approaches, so model accuracy is invariant by construction. Per-function memory is bounded at O(|θ|/M), independent of client count, enabling aggregation of arbitrarily large models. We evaluate GradsSharding against lambda-FL and LIFL through HPC experiments and real AWS Lambda deployments across model sizes from 43 MB to 5 GB. Results show a cost crossover at approximately 500 MB gradient size, 2.7x cost reduction at VGG-16 scale, and that GradsSharding is the only architecture that remains deployable beyond the serverless memory ceiling.

*   **核心问题**：在无服务器（Serverless）架构下进行联邦学习（FL）聚合时，存在严重的**内存瓶颈**。
*   **研究动机**：
    *   **内存天花板**：现有的无服务器聚合架构（如 $\lambda$-FL, LIFL）是基于“客户端划分”的，即每个聚合器处理一部分客户端的完整模型。当模型梯度大小超过单个函数内存上限（如 AWS Lambda 的 10GB）时，聚合将彻底失效。
    *   **资源浪费**：传统持久化服务器在客户端训练期间处于闲置状态（闲置率高达 80%-99.6%），而无服务器架构按需计费，非常适合这种爆发式负载。

### 2. 论文提出的方法论：GradsSharding
*   **核心思想**：将聚合维度从“划分客户端”转变为**“划分梯度张量”**。
*   **关键技术细节**：
    1.  **分片（Shard）**：客户端将本地训练得到的梯度向量 $g_i$ 划分为 $M$ 个连续的分片。
    2.  **上传（Upload）**：客户端将 $M$ 个分片并行上传至云存储（S3）。
    3.  **聚合（Aggregate）**：启动 $M$ 个独立的 Lambda 函数。每个函数仅负责聚合所有客户端的第 $j$ 个分片。由于 FedAvg 是逐元素平均，这种分片聚合在数学上与整体聚合完全等价（位一致性）。
    4.  **重构（Reconstruct）**：客户端下载 $M$ 个聚合后的分片并拼接，更新全局模型。
*   **优势公式**：每个函数的内存需求从 $O(|\theta|)$ 降至 **$O(|\theta|/M)$**，其中 $|\theta|$ 是模型参数量。这使得通过增加分片数 $M$，可以聚合任意规模的模型。

### 6. 主要结论与发现
*   **内存解耦**：GradsSharding 成功将内存消耗与模型大小解耦，是唯一能处理超过 3.2GB 梯度（Lambda 实际内存限制下的阈值）的架构。

### 7. 优点
*   **数学等价性**：保证了模型准确率和收敛性与传统方法完全一致。
*   **极高的扩展性**：理论上可以处理无限大的模型，只要增加分片数即可。
*   **成本效益**：在大模型场景下，通过降低单函数内存分配显著减少了 AWS 账单金额。
*   **并行优势**：消除了树状架构中层级间的顺序依赖。

### 8. 不足与局限
*   **S3 操作开销**：对于小模型（<500MB），由于分片增加了 S3 的 PUT/GET 请求次数，成本反而高于传统方法。
*   **I/O 依赖**：性能高度依赖于云存储的带宽，若 S3 出现波动，聚合延迟会显著增加。
*   **分片策略单一**：目前采用均匀分片，对于层大小差异极大的异构模型（如混合专家模型 MoE），可能存在负载不均。
*   **客户端负担**：客户端需要处理分片上传和下载拼接，增加了客户端的计算和网络负担。
