## 摘要
图形处理器（GPU）擅长处理规则的数据并行工作负载，能够轻松利用大规模硬件并行性。相比之下，许多重要的不规则应用自然地表现为具有 fork-join 控制结构的任务并行性。虽然用于 fork-join 任务并行的 CPU 运行时已经成熟，但在 GPU 上高效支持它仍然具有挑战性。我们提出了 GTaP，一种支持 fork-join 任务并行的 GPU 常驻运行时。GTaP 基于持久内核（persistent kernel）模型，并支持两种工作单元粒度：线程块和单个线程。为了在 GPU 上实现 fork-join，GTaP 将 join 表示为延续（continuations），并将每个任务作为可拆分为多个执行段的状态机来执行。我们还扩展了 Clang 的前端，引入了一种基于 pragma 的编程模型，使程序员能够在不暴露底层机制的情况下表达 fork-join。GTaP 采用工作窃取（work stealing）进行负载均衡，提供了比全局队列方法更好的可扩展性。对于线程级工作单元，我们进一步引入了执行路径感知队列（EPAQ），允许程序员根据用户定义的标准划分任务队列，从而减少因在 warp 内混合异构控制流而导致的 warp 分歧（warp divergence）。在代表性的不规则应用中，GTaP 在许多情况下优于 72 核 CPU 上的 OpenMP 任务并行执行，特别是对于具有计算密集型任务的大规模问题。我们还展示了 GTaP 的设计选择优于朴素的 GPU 替代方案。EPAQ 的收益取决于工作负载：它可以提高某些基准测试的性能，而对其他测试影响较小；在 Fibonacci 上，EPAQ 实现了高达 1.8 倍的加速。

## Abstract
Graphics Processing Units (GPUs) excel at regular data-parallel workloads where massive hardware parallelism can be readily exploited. In contrast, many important irregular applications are naturally expressed as task parallelism with a fork-join control structure. While CPU runtimes for fork-join task parallelism are mature, it remains challenging to efficiently support it on GPUs.   We propose GTaP, a GPU-resident runtime that supports fork-join task parallelism. GTaP is based on the persistent kernel model, and supports two worker granularities: thread blocks and individual threads. To realize fork-join on GPUs, GTaP represents joins as continuations and executes each task as a state machine that can be split into multiple execution segments. We also extend Clang's frontend with a pragma-based programming model that enables programmers to express fork-join without exposing low-level mechanisms. GTaP employs work stealing for load balancing, providing better scalability than a global-queue approach. For thread-level workers, we further introduce Execution-Path-Aware Queueing (EPAQ), which allows programmers to partition task queues using user-defined criteria, reducing warp divergence caused by mixing heterogeneous control flows within a warp.   Across representative irregular applications, GTaP outperforms OpenMP task-parallel execution on a 72-core CPU in many cases, especially for large problem sizes with compute-intensive tasks. We also show that GTaP's design choices outperform naive GPU alternatives. The benefit of EPAQ is workload-dependent: it can improve performance for some benchmarks while having little effect on others; on Fibonacci, EPAQ achieves up to a 1.8$\times$ speedup.

### 1. 核心问题与研究动机
*   **核心问题**：GPU 擅长处理规则的数据并行任务，但在处理具有 **Fork-Join** 控制结构的**不规则任务并行**（如递归分解、动态搜索）时效率低下。
*   **研究动机**：
    *   现有的 GPU 任务运行时通常不支持“在 Join 点挂起并恢复”的语义，或者需要程序员手动管理复杂的延续（Continuations）。
    *   缺乏一个既能提供高层编程接口（类似 OpenMP），又能支持细粒度（线程级）调度和高效负载均衡（工作窃取）的统一框架。
    *   GPU 的 SIMT 架构在处理异构任务流时容易产生严重的线程束分歧（Warp Divergence）。

### 2. 方法论
GTaP 提出了一个完整的 GPU 常驻运行时系统，核心技术包括：
*   **持久内核模型（Persistent Kernel）**：启动一个长期运行的 GPU 内核，内部循环获取并执行任务，避免频繁的内核启动开销。
*   **状态机任务表示**：通过将任务函数转换为基于 `switch-case` 的状态机，将 Join 点转化为延续。当子任务未完成时，父任务保存状态并退出；待子任务完成后，父任务重新入队并从断点处恢复。
*   **编译器自动化支持**：扩展了 Clang 前端，支持 `#pragma gtap task` 和 `taskwait` 指令。编译器自动处理局部变量的溢出（Spilling）到任务记录中，并生成状态机代码，降低了编程门槛。
*   **双粒度工作单元**：支持“线程块级（Block-level）”协作执行和“单个线程级（Thread-level）”独立执行，适应不同规模的任务。
*   **高效工作窃取（Work Stealing）**：实现了一种 GPU 常驻的随机工作窃取算法。针对线程级工作单元，设计了**线程束协作式批量操作（Warp-Cooperative Batched Pop/Steal）**，减少了对共享元数据的竞争。
*   **执行路径感知队列（EPAQ）**：允许将任务根据预定义的标准（如子问题规模）分发到不同的队列，使同一 Warp 内的线程更有可能执行路径相似的任务，从而缓解分歧。

### 3. 实验设计
*   **基准测试程序**：
    *   **Fibonacci**：测试极细粒度递归和运行时开销。
    *   **N-Queens**：测试高度不规则的任务生成和计算密集型逻辑。
    *   **Mergesort/Cilksort**：测试内存密集型任务及并行合并逻辑。
    *   **Synthetic Tree**：通过合成树结构控制计算/内存比例，进行消融实验。
*   **对比方法（Baseline）**：
    *   **CPU 端**：72 核 NVIDIA Grace CPU 上的 OpenMP 任务并行实现。
    *   **GPU 端消融**：全局队列（Global Queue）调度、顺序 Chase-Lev 队列操作、关闭 EPAQ 的配置。

### 4. 资源与算力
*   **硬件平台**：使用单节点 **Miyabi-G** 超级计算机，配备 **NVIDIA GH200 Grace Hopper Superchip**（包含 72 核 Grace CPU 和 H100 96GB GPU）。
*   **软件环境**：基于 LLVM/Clang 21.1.8 开发的编译器扩展，CUDA Toolkit 12.9。
*   **算力说明**：实验主要测量内核执行时间，排除了主机端初始化时间。

### 5. 实验数量与充分性
*   **实验规模**：涵盖了 5 种不同特性的应用场景，每组实验运行 20 次取中位数，并标注了四分位距（IQR）。
*   **消融实验**：针对负载均衡策略（工作窃取 vs 全局队列）、队列操作算法（批量 vs 顺序）、工作单元粒度（线程 vs 线程块）以及 EPAQ 的有效性进行了详细对比。
*   **充分性评价**：实验设计较为全面，不仅对比了 CPU 顶尖性能，还深入探讨了 GPU 内部不同设计决策对性能的影响，客观地展示了方法在不同负载下的优劣。

### 6. 主要结论与发现
*   **性能超越 CPU**：在计算密集型任务（如 N-Queens）中，GTaP 相比 72 核 CPU 上的 OpenMP 实现了高达 **14.6 倍** 的加速；在合成树任务中实现 **15.2 倍** 加速。
*   **负载均衡有效性**：工作窃取在 GPU 上表现出比全局队列更好的可扩展性，尤其是在增加工作单元数量时。
*   **粒度选择**：线程级工作单元适合任务量充足且分歧小的场景；线程块级协作则在任务稀疏或不规则性极高时更具优势。
*   **EPAQ 收益**：EPAQ 的效果取决于负载。在 Fibonacci 上通过减少 Warp 分歧实现了 **1.8 倍** 的加速，但在 N-Queens 等任务中收益不明显。
*   **局限性**：对于纯内存密集型且具有长串行尾部的任务（如普通 Mergesort），GPU 表现远逊于 CPU。

### 7. 优点
*   **易用性**：通过 Pragma 指令隐藏了复杂的 GPU 延续管理和状态机转换，使开发者能以类 OpenMP 的方式编写代码。
*   **灵活性**：支持两种工作粒度，能够覆盖从简单的递归到复杂的协作式数据并行任务。
*   **高性能调度**：针对 GPU 架构优化的批量队列操作显著提升了工作窃取的效率。

### 8. 不足与局限
*   **内存绑定任务瓶颈**：在处理内存延迟敏感且并行度不足的任务阶段时，GPU 的吞吐量优势无法弥补单核性能的弱势。
*   **参数依赖性**：运行时需要预先定义最大任务数、队列大小等宏参数，这要求程序员对应用规模有一定预判，缺乏完全动态的内存管理。
*   **EPAQ 的局限**：EPAQ 需要程序员手动指定分类标准，且无法处理执行过程中才产生的动态分歧。
*   **单机限制**：目前仅支持单 GPU，尚未扩展到多 GPU 或集群环境。
