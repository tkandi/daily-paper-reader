## 摘要
联邦学习 (FL) 研究日益依赖于具有数百或数千个虚拟客户端的单节点模拟，这使得效率和可复现性变得至关重要。然而，并行客户端训练通常会通过共享随机状态和调度变异性引入非确定性，迫使研究人员在吞吐量与可复现性之间进行权衡，或者在复杂的框架内实现自定义控制逻辑。我们提出了 BlazeFL，这是一个用于单节点联邦学习模拟的轻量级框架，通过自由线程共享内存执行和确定性随机性管理来缓解这种权衡。BlazeFL 使用基于线程的并行性，在服务器和客户端之间进行内存中参数交换，避免了序列化和进程间通信的开销。为了支持确定性执行，BlazeFL 为客户端分配了隔离的随机数生成器 (RNG) 流。在固定的软件/硬件栈下，且当随机算子使用 BlazeFL 管理的生成器时，该设计在基于线程和基于进程的模式下，跨重复的高并发运行产生位级一致的结果。在 CIFAR-10 图像分类实验中，BlazeFL 相对于广泛使用的开源基准显著减少了执行时间，在通信主导的工作负载中实现了高达 3.1 倍的加速，同时保持了轻量级的依赖占用。我们的开源实现可在以下网址获得：https://github.com/kitsuyaazuma/blazefl。

## Abstract
Federated learning (FL) research increasingly relies on single-node simulations with hundreds or thousands of virtual clients, making both efficiency and reproducibility essential. Yet parallel client training often introduces nondeterminism through shared random state and scheduling variability, forcing researchers to trade throughput for reproducibility or to implement custom control logic within complex frameworks. We present BlazeFL, a lightweight framework for single-node FL simulation that alleviates this trade-off through free-threaded shared-memory execution and deterministic randomness management. BlazeFL uses thread-based parallelism with in-memory parameter exchange between the server and clients, avoiding serialization and inter-process communication overhead. To support deterministic execution, BlazeFL assigns isolated random number generator (RNG) streams to clients. Under a fixed software/hardware stack, and when stochastic operators consume BlazeFL-managed generators, this design yields bitwise-identical results across repeated high-concurrency runs in both thread-based and process-based modes. In CIFAR-10 image-classification experiments, BlazeFL substantially reduces execution time relative to a widely used open-source baseline, achieving up to 3.1$\times$ speedup on communication-dominated workloads while preserving a lightweight dependency footprint. Our open-source implementation is available at: https://github.com/kitsuyaazuma/blazefl.

### 1. 核心问题与研究动机
*   **研究背景**：联邦学习（FL）研究高度依赖单机模拟（Single-node Simulation），通常涉及成百上千个虚拟客户端的频繁采样、训练与聚合。
*   **核心矛盾**：
    *   **效率瓶颈**：传统 Python 框架受限于全局解释器锁（GIL），多采用多进程（Multiprocessing）或分布式运行时（如 Ray），这引入了巨大的序列化、反序列化及进程间通信（IPC）开销，尤其在模型参数较大时。
    *   **复现难题**：并行执行会导致非确定性。随机状态共享不当、调度差异以及浮点数聚合顺序的不确定性，使得即使固定全局种子，多次运行的结果也无法达到“位级一致”（Bitwise-identical）。
*   **研究目的**：开发一个既能利用多核并行提升吞吐量，又能保证实验结果严格可复现的轻量级单机 FL 模拟框架。

### 2. 方法论
BlazeFL 的核心思想是利用 Python 最新的**自由线程（Free-threading, PEP 703）**特性，结合精细的随机性管理。
*   **基于线程的共享内存执行**：
    *   利用 Python 3.13+ 的自由线程模式，在单个进程内以多线程方式运行客户端。
    *   服务器与客户端之间直接通过共享内存交换参数，彻底消除了跨进程的序列化和 IPC 开销。
*   **受控的确定性执行**：
    *   **隔离 RNG 流**：为每个客户端分配独立的随机数生成器（RNG）流。无论调度顺序如何，特定客户端在特定轮次的随机行为（如数据增强、Dropout）保持一致。
    *   **固定顺序聚合**：服务器按预定义的采样顺序（而非任务完成的先后顺序）收集并聚合客户端更新，避免了浮点数加法不满足结合律导致的微小舍入误差累积。
*   **协议化接口（Protocol-based Interfaces）**：
    *   采用 Python 的 `typing.Protocol` 实现结构化子类型，无需强制继承特定基类，降低了现有 PyTorch 代码迁移的门槛。

*   **模型架构**：涵盖了从轻量级 CNN 到深层残差网络（ResNet-18, ResNet-50, ResNet-101）。
*   **Benchmark（基准）**：广泛使用的开源框架 **Flower**（配合 Ray 后端）。
*   **对比配置**：
    1.  BlazeFL (Free-threaded)：基于线程的模式。
    2.  BlazeFL (Process-based)：基于多进程且使用共享内存张量的模式。
    3.  Flower (Ray backend)：标准分布式执行模式。
*   **评估指标**：端到端墙上时钟时间（Wall-clock time）、模型准确率标准差、SHA-256 哈希一致性。

*   **训练规模**：100 个客户端，每轮采样部分客户端，执行 5 轮通信，每轮本地训练 5 个 Epoch。

### 5. 实验数量与充分性
*   **实验维度**：
    *   **扩展性实验**：测试了不同并行度 $P \in \{1, 2, 4, 8, 16, 32, 64\}$ 下的耗时。
    *   **复现性实验**：在 $P=32$ 的高并发下重复运行 10 次，计算准确率波动和模型哈希值。
    *   **消融/诊断实验**：追踪了 Flower 框架中非确定性误差随通信轮次累积的过程（Logits 散度分析）。
*   **充分性评价**：实验设计较为客观，不仅对比了运行速度，还深入分析了导致非确定性的底层原因（如浮点数聚合顺序），验证了框架在不同硬件和模型规模下的表现。

### 6. 主要结论与发现
*   **显著提速**：在通信主导（模型小、参数交换频繁）的 CNN 任务中，BlazeFL 比 Flower 快 **3.1 倍**。在 ResNet-18 上也有约 1.4 倍的提升。
*   **位级复现**：BlazeFL 在所有并行配置下均实现了 **0 误差复现**（SHA-256 哈希完全一致），而 Flower 即使固定全局种子，准确率仍有约 0.18% 的波动。
*   **瓶颈转移**：在显存受限（如 RTX 6000）且模型较大时，多线程模式可能受限于 PyTorch 内部的 CUDA 分配器锁（Global Mutex），此时性能优势会减弱，甚至可能需要回退到多进程模式。

### 7. 优点与亮点
*   **前瞻性技术应用**：率先在 FL 领域应用 Python 的 Free-threading 特性，解决了长期困扰 Python 并行计算的 GIL 问题。
*   **极致的复现性**：通过隔离 RNG 流和固定顺序聚合，解决了并行模拟中“看似随机”的非确定性问题，对算法微调和 Debug 极具价值。
*   **轻量化设计**：依赖极少（仅 PyTorch 和标准库），不强制要求复杂的分布式运行时（如 Ray 或 MPI），易于部署和集成。

### 8. 不足与局限
*   **单机限制**：设计目标仅限于单机模拟，无法直接扩展到多节点分布式生产环境。
*   **硬件依赖性**：虽然在同一机器上可复现，但论文承认跨平台、跨硬件（不同 GPU 架构或库版本）的位级一致性仍难以保证。
*   **生态成熟度**：依赖于非常新版本的 Python（3.13+），部分第三方库可能尚未完全适配自由线程模式。
*   **显存压力**：在单进程多线程模式下，所有线程共享显存，高并发大模型容易触发 CUDA OOM（显存溢出），而多进程模式在显存管理上相对更独立。
