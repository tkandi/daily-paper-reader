## 摘要
现代 GPU 采用基于芯粒（chiplet）的设计，具有多个私有缓存层级，但目前的编程模型（CUDA/HIP）呈现的是扁平的执行层级，无法表达芯粒级别的局部性或同步。这种不匹配导致在 LLM 推理等受内存限制的工作负载中，出现冗余的内存流量和低下的缓存利用率。我们提出了 Fleet，这是一种将计算映射到内存作用域的多级任务模型。Fleet 引入了 Chiplet-tasks，这是一种将工作和数据绑定到芯粒的新抽象，并允许通过其共享的 L2 缓存进行协作。Wavefront 级、CU 级和设备级任务与现有抽象一致，而 Chiplet-tasks 则揭示了此前未被处理的层级。Fleet 被实现为一个具有每芯粒调度功能的持久化内核运行时，允许芯粒内的计算单元通过协调缓存重用来协作执行任务。在搭载 Qwen3-8B 的 AMD Instinct MI350 上，通过持久化内核执行和每芯粒调度，Fleet 在 Batch Size 为 1-8 时实现的解码延迟比 vLLM 低 1.3-1.5 倍。在较大的 Batch Size 下，协作式权重分块提高了 L2 命中率（Batch Size 为 32 时从 12% 提高到 54%，Batch Size 为 64 时从 39% 提高到 61%），减少了高达 37% 的 HBM 流量，并相比于不感知芯粒的巨型算子基准实现了 1.27-1.30 倍的加速。

## Abstract
Modern GPUs adopt chiplet-based designs with multiple private cache hierarchies, but current programming models (CUDA/HIP) expose a flat execution hierarchy that cannot express chiplet-level locality or synchronization. This mismatch leads to redundant memory traffic and poor cache utilization in memory-bound workloads such as LLM inference.   We present Fleet, a multi-level task model that maps computation to memory scopes. Fleet introduces Chiplet-tasks, a new abstraction that binds work and data to a chiplet and enables coordination through its shared L2 cache. Wavefront-level, CU-level, and device-level tasks align with existing abstractions, while Chiplet-tasks expose a previously unaddressed level of the hierarchy. Fleet is implemented as a persistent kernel runtime with per-chiplet scheduling, allowing workers within a chiplet to cooperatively execute tasks with coordinated cache reuse. On AMD Instinct MI350 with Qwen3-8B, Fleet achieves 1.3-1.5x lower decode latency than vLLM at batch sizes 1-8 through persistent kernel execution and per-chiplet scheduling. At larger batch sizes, cooperative weight tiling increases L2 hit rate (from 12% to 54% at batch size 32 and from 39% to 61% at batch size 64), reducing HBM traffic by up to 37% and delivering 1.27-1.30x speedup over a chiplet-unaware megakernel baseline.

### 1. 核心问题与整体含义
*   **研究动机**：现代 GPU 架构（如 AMD MI300/350、NVIDIA Blackwell）已转向多芯粒（Chiplet）设计，每个芯粒拥有私有的 L2 缓存。然而，现有的编程模型（CUDA/HIP）仍采用扁平的执行层级（Grid -> Workgroup -> Wavefront），无法表达芯粒级别的内存局部性或进行芯粒内的协作。
*   **核心问题**：这种硬件架构与编程模型的不匹配导致在 LLM 推理等内存受限（Memory-bound）的任务中，不同芯粒会重复从 HBM 加载相同的权重数据，造成 L2 缓存利用率低下和冗余的内存流量。
*   **研究目标**：通过引入一种新的层级化任务抽象，使开发者能够显式地将计算任务与芯粒级的内存作用域（L2 缓存）绑定，从而优化大模型的解码效率。

### 2. 方法论
Fleet 提出了一种多级任务模型和配套的持久化内核（Persistent Kernel）运行时：
*   **四级任务层级**：
    *   **Wavefront-task**：对应寄存器/LDS，处理 SiLU、残差相加等逐元素操作。
    *   **CU-task**：对应单个计算单元（CU），处理注意力头、RMSNorm 等。
    *   **Chiplet-task（核心创新）**：跨越单个芯粒（如 AMD 的 XCD）上的所有 CU，通过共享的 L2 缓存协调数据访问。
    *   **Device-task**：协调全卡所有芯粒共同完成一个大算子（如全量 GEMM）。
*   **关键技术细节**：
    *   **持久化内核运行时**：在 GPU 端实现软件调度器。每个芯粒分配一个 CU 作为“调度器”，其余为“工作单元”，避免了频繁的内核启动开销。
    *   **协作式分块（Cooperative Tiling）**：采用 **M-major（行优先）** 遍历顺序。在计算矩阵乘法时，让芯粒内的所有工作单元在同一时间窗口内读取相同的权重列，从而使权重驻留在 L2 缓存中供多个工作单元复用。
    *   **层级化同步协议**：为了减少昂贵的跨芯粒 Fence 操作，Fleet 先在芯粒内部利用 L2 一致性进行局部计数，仅在芯粒任务全部完成后才发出一次全局同步信号。

### 3. 实验设计
*   **场景**：大语言模型（LLM）的自回归解码（Decode）阶段。
*   **模型与数据集**：使用 **Qwen3-8B** 稠密模型（bf16 精度）。
*   **Benchmark（对比方法）**：
    1.  **vLLM (v0.17.2)**：代表目前最先进的算子级内核启动框架。
    2.  **Mirage MPK**：一种不感知芯粒结构的持久化巨型内核（Megakernel）基准，用于孤立分析 Fleet 芯粒感知优化的增益。
*   **测试指标**：每 Token 延迟（TPOT）、L2 缓存命中率、HBM 读取/写入流量、Roofline 算力利用率分析。

### 4. 资源与算力
*   **硬件平台**：单张 **AMD Instinct MI350X** GPU。
    *   配置：256 个 CU（分布在 8 个 XCD 芯粒上），每个芯粒 4MB L2 缓存，总计 32MB L2；256MB Infinity Cache (LLC)；288GB HBM3。
*   **训练/运行时间**：文中未提及模型训练时长（属于推理优化研究），实验主要集中在推理阶段的算子执行周期和延迟测量。

### 5. 实验数量与充分性
*   **实验覆盖**：涵盖了从 Batch Size 1 到 64 的多种场景。
*   **消融实验**：设计了 **M-tile（协作式）** 与 **M-split（非协作式）** 的对比实验。这非常客观地证明了性能提升究竟来自于“调度开销的减少”还是“L2 缓存的复用”。
*   **充分性**：实验通过硬件性能计数器（rocprofiler-sdk）直接测量了 HBM 流量和 L2 命中率，数据链条完整，能够有力支撑其方法论。

### 6. 主要结论与发现
*   **延迟降低**：在小 Batch Size (1-8) 下，Fleet 比 vLLM 快 **1.3–1.5 倍**，这主要归功于持久化内核消除了内核启动开销。
*   **缓存优化**：在大 Batch Size (32-64) 下，协作式分块显著提升了 L2 命中率。例如 BS=32 时，L2 命中率从 12% 提升至 **54%**。
*   **带宽节省**：通过 L2 复用，HBM 读取流量最高减少了 **37%**。
*   **调度效率**：Chiplet-task 减少了调度器与工作单元之间的通信频率，任务数量比传统分解方式减少了约 2.6 倍。

### 7. 优点
*   **架构契合度高**：精准捕捉了多芯粒 GPU 的硬件特性，填补了软件抽象层级的空白。
*   **软件定义调度**：无需修改硬件，通过纯软件方式在持久化内核中实现了复杂的层级同步和数据亲和性调度。
*   **性能显著**：在内存带宽受限的 LLM 解码场景下，提供了切实可行的带宽缓解方案。

### 8. 不足与局限
*   **硬件局限性**：实验仅在 AMD MI350 上完成，虽然理论上适用于 NVIDIA Blackwell，但缺乏跨平台的实测数据。
*   **寄存器压力**：由于 Megakernel 将所有算子融合在一个内核中，导致寄存器占用极高，限制了 GPU 的并发执行度（Occupancy），这在一定程度上抵消了部分延迟隐藏能力。
*   **场景覆盖**：目前仅针对 Decode 阶段进行了深度优化，未详细讨论 Prefill（预填充）阶段或多卡张量并行（TP）下的扩展表现。
*   **编译自动化**：目前任务图的生成仍部分依赖手动配置，尚未完全实现全自动的超优化编译。
