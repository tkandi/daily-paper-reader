## 摘要
长程轨迹生成已成为智能体强化学习（RL）中的主要系统瓶颈。随着智能体与环境在多轮交互中不断交互，轨迹迅速增长至数万个词元，使得同步RL训练越来越受到轨迹展开的制约。我们提出WAR，一种工作负载感知的轨迹展开系统，通过联合优化解码与调度，大幅加速同步智能体RL。WAR基于一个关键观察：最优的轨迹展开优化策略取决于运行时负载：（1）在低负载下，WAR通过后缀解码实现免模型的推测解码，利用先前完成轨迹中的后缀模式作为未来轨迹展开的推测性草案。与基于模型的草案生成器不同，后缀解码不引入额外的草案模型，避免了与轨迹展开生成发生GPU争用。（2）在高负载下，批解码趋于饱和，留给推测加速的空间有限，WAR将优化重心转向缓存感知调度。全局调度器根据缓存局部性、轨迹进展和服务器负载，将请求分配到不同的轨迹副本上，减少冗余的KV缓存重计算并缓解负载不均衡。通过将解码层面的后缀复用与系统层面的轨迹调度相结合，WAR在不改变底层RL算法的情况下，在不同工作负载区间实现了稳健的吞吐量提升。WAR将长上下文智能体轨迹展开的吞吐量在低负载下提升了1.4倍，在高负载下提升了最高1.6倍。这些结果表明，WAR消除了同步智能体RL中的一个主要轨迹展开瓶颈，为可扩展的长上下文智能体训练提供了一条实用的路径。

## Abstract
Long-horizon rollout generation has become the dominant systems bottleneck in agentic reinforcement learning (RL). As agents interact with environments over many turns, trajectories rapidly grow to tens of thousands of tokens, making synchronous RL training increasingly constrained by rollout. We propose WAR, a workload-aware rollout system that substantially accelerates synchronous agentic RL by jointly optimizing decoding and scheduling. WAR is built on a key observation: the optimal rollout optimization strategy depends on runtime load: (1) Under low load, WAR enables model-free speculative decoding with SuffixDecoding, which reuses suffix patterns from previously completed trajectories as speculative drafts for future rollouts. Unlike model-based drafters, SuffixDecoding introduces no additional draft model and avoids GPU contention with rollout generation. (2) Under high load, where saturated batched decoding leaves limited room for speculative speedup, WAR shifts the optimization focus to cache-aware scheduling. A global scheduler places requests across rollout replicas based on cache locality, trajectory progress and server load, reducing redundant KV-cache recomputation and mitigating load imbalance. By combining decoding-level suffix reuse with system-level rollout scheduling, WAR delivers robust throughput improvements across workload regimes without changing the underlying RL algorithm. WAR improves long-context agentic rollout throughput by 1.4x under low load and up to 1.6x under high load. These results show that WAR removes a major rollout bottleneck in synchronous agentic RL and provides a practical path toward scalable long-context agent training.

- **研究动机**：在同步智能体强化学习中，智能体需与环境进行多轮交互，轨迹长度极易增长到数万词元（token），导致轨迹展开阶段成为整个训练流程的主导系统瓶颈。这些长轨迹的生成不仅消耗大量计算与内存，还因长度不均衡造成 GPU 利用率低下（长尾延迟），严重拖慢训练。
- **核心观察**：轨迹展开的优化策略不应一成不变，应当根据**运行时负载**切换。低负载时 GPU 资源未饱和，可用解码级加速提升利用率；高负载时批解码已饱和，解码加速的收益有限甚至产生开销，此时优化系统级调度（如缓存局部性、负载均衡）效果更好。
- **整体含义**：论文提出 **WAR（Workload-Aware Rollouts）**，一个**工作负载感知的同步智能体 RL 轨迹展开系统**，通过联合优化解码和调度，在不同负载下都大幅提高吞吐，不改变 RL 算法本身，为可扩展的长上下文智能体训练提供实用路径。

## 2. 方法论

WAR 的核心是**根据当前工作负载，在解码级加速和系统级调度之间动态选择**。具体设计如下：

- **负载感知切换机制**  
  使用**运行时的有效批大小**作为轻量级负载指示器，经验性地设定阈值。当请求数少、负载低时激活推测解码；当请求数多、负载高时启用缓存感知调度。

- **低负载：模型无关的推测解码（SuffixDecoding ）**  
  - 采用**后缀解码**（SuffixDecoding）：一种免模型（model‑free）的推测解码方法，利用已完成轨迹中的后缀模式来构造草案令牌，无需引入额外的草稿模型，避免与目标模型争抢 GPU 资源。
  - 原理：维护后缀树，缓存历史轨迹的 token 序列模式；在解码时匹配当前上下文，生成后续 token 草案，再由目标模型并行验证。
  - 在 RL 框架中，每个 rollout worker 独立维护后缀树，并在**每步结束后**跨 worker 同步新生成的轨迹，扩大后缀复用的覆盖范围。
  - 支持**动态开关**（根据批大小启用/禁用）、安全模式切换、CUDA Graph 兼容，并暴露出接口供外部主动更新后缀缓存。

- **高负载：缓存感知的全局调度**  
  - 全局调度器在**请求数 ≥ 阈值**时激活，综合考虑四个维度为每个排队请求打分：
    - **缓存命中率 H**：请求与候选 replica 的 KV-cache 重合度（局部性亲和力）。
    - **在线估计的助手轮次** `\hat{T}_g`：根据同一 prompt group 的历史轮次进行指数平滑估计，倾向于优先调度较短的轨迹以尽快释放缓存。
    - **服务器上的进行中请求数** `N_{inflight}^{rep}`：代表副本负载，倾向于选择负载较低的副本。
    - **请求等待时间** `t_{waiting}^{req}`：防止超过沙盒生存时间（TTL）导致轨迹被提前终止。
  - 综合评分公式：
    ```
    S = S_waiting + S_turn + S_cache + S_inflight
    ```
    其中各项的幅度设计为 `|S_waiting| ≫ |S_turn| ≫ |S_cache| ≫ |S_inflight|`，以确保紧急请求优先派遣，同时平衡进度、缓存与负载。
  - 此外，借鉴 **CONCUR**（基于 AIMD 的拥塞控制）动态调整每个副本的最大并发数 `Wt`，以防止缓存命中率过低，进一步缓解负载不均。

- **与现有框架的结合**  
  WAR 基于 veRL 实现（约 7000 行 Python 代码），SGLang 作为推理引擎，Megatron‑LM 负责训练，不改动原有 RL 算法或训练流程。

## 3. 实验设计

- **任务与数据集**  
  在软件工程（SWE）智能体任务上评测，使用包含 **500 个 prompt** 的 SWE 数据集。每个 prompt 进行 8 次 rollout，最大助手轮次设为 120，支持多轮环境交互。
- **模型与上下文长度**  
  使用 **Qwen3‑32B**，通过 YaRN 扩展上下文长度至 **96K tokens**。
- **对比基准与变体**  
  在 veRL v0.8.0 基线上，测试四种配置：
  - `veRL base`（无优化）
  - `sched only`（仅缓存感知调度）
  - `spec only`（仅 SuffixDecoding）
  - `sched spec`（两者皆启用）
- **主要指标**  
  端到端 rollout 时间、预填充（prefill）吞吐、解码（decode）吞吐；辅助指标：KV‑cache 命中率、推测解码的接受长度。
- **工作负载变化**  
  通过改变训练批大小（4, 8, 16, 32, 64）模拟不同负载强度，每种设置运行 **5 个 RL 步**。
- **公平性控制**  
  通过过滤掉在 prefill tokens、decode tokens 和助手轮次上与基线偏差超过 5% 的实验运行，确保吞吐量差异主要来自系统优化而非生成工作量的变化。

## 6. 主要结论与发现

- **负载感知的必要性**：相同优化在不同负载下效果截然不同，低负载下推测解码带来显著加速，高负载下则可能因额外开销反而降低吞吐。
- **互补效果**：`sched spec` 组合在所有负载下均实现稳健吞吐提升，低负载时主要受益于推测解码（1.4 倍提升），高负载时主要受益于缓存感知调度（最高 1.6 倍提升）。
- **缓存感知调度的关键作用**：仅通过调度即可在高负载下将 prefill/decode 吞吐提升约 47%，同时维持较高的 KV‑cache 命中率（从约 0.1 提升到约 0.5），有效减少重计算和负载不均。
- **SuffixDecoding 的有效性与局限性**：在 SWE 任务中，接受长度可达 2.6–6.0，表明后缀模式复用很有效；但当批大小超过约 16 后，批解码已饱和，推测解码的收益被开销抵消，应予以关闭。
- **等待因子不可或缺**：若去掉等待优先，高负载下部分请求会因沙盒超时而提前终止，导致轨迹不完整，吞吐测量失真。

## 7. 优点

- **根据负载动态切换**：首次将工作负载作为 rollout 优化的一级因素，避免了“一刀切”的策略，设计思路清晰。
- **免模型推测解码**：使用 SuffixDecoding 避免了草稿模型对 GPU 资源的争用，特别适合 RL 训练中不断更新的策略模型场景。
- **多维调度策略**：综合考虑缓存局部性、轨迹进度、副本负载和紧急程度，且通过调整分数幅度大小来设定优先级，工程上务实有效。
- **与现有框架兼容**：基于 veRL/SGLang 实现，不修改 RL 算法，易于集成到现有产线；通过跨 worker 同步后缀缓存，扩大了复用范围。
- **实验严谨**：对生成工作量进行过滤以隔离系统优化效果，多维度消融验证各模块贡献，辅以辅助指标（命中率、接受长度）解释现象。

## 8. 不足与局限

- **场景与模型单一**：仅在 Qwen3‑32B 模型和 SWE 智能体任务上评估，未泛化到其他模型（如不同规模、不同结构）或其他长上下文智能体任务（如数学推理、代码生成以外的环境），结论的普适性待确认。
- **负载感知切换阈值依赖经验设定**：文中使用有效批大小并经验式设定阈值，未提出自动化的自适应切换方法，可能需要针对不同硬件和任务重新调优。
- **训练步数有限**：每组仅运行 5 个 RL 步，难以充分反映策略更新后推测解码接受率或调度稳定性的长期变化。
- **未与异步方法直接对比**：论文仅对标同步 veRL 基线，并没有与异步 rollout 系统在训练吞吐或策略质量上做定量对比，未展示 WAR 与异步方案之间的取舍。

- **推测解码在高负载下的退化**：仅通过实验观测到高负载时应关闭 SuffixDecoding，但未提供更精细的在线决策机制，可能导致负载波动时的性能抖动。
