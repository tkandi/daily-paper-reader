## 摘要
文本到图像（T2I）工作流越来越多地部署在无服务器平台上，因为用户通常组合定制化工作流并间歇性地调用它们。现有平台通常将每个工作流部署为一个不透明的GPU函数，将工作流中的所有组成模型一起供应、放置和扩展。这种单体设计掩盖了工作流结构，增加了扩展开销，迫使用户管理低层次的GPU协调，并限制了多租户集群中的细粒度公平性。在本文中，我们提出了ServerlessT2I，一个无服务器原生的系统，它将T2I工作流分解为松耦合的模型函数，这些函数可以独立管理和调度。通过显式管理单个模型的执行，ServerlessT2I实现了按模型扩展、声明式工作流组合、透明的GPU驻留通信以及公平感知调度。为了使这种分解高效，ServerlessT2I利用计算受限的T2I推理所空闲的GPU内存来构建数据平面，以减少模型加载和数据通信的开销。ServerlessT2I进一步引入了面向多租户服务的公平调度器。使用生产环境下的trace，在相同GPU预算下，ServerlessT2I能够维持比现有T2I工作流服务系统高达2倍的请求速率；对于固定的请求速率，它节省高达3倍的GPU资源，同时满足服务等级目标（SLO）。

## Abstract
Text-to-image (T2I) workflows are increasingly deployed on serverless platforms because users often compose customized workflows and invoke them intermittently. Existing platforms typically deploy each workflow as an opaque GPU function, provisioning, placing, and scaling all constituent models in the workflow together. This monolithic design obscures workflow structure, inflates scaling overhead, forces users to manage low-level GPU coordination, and limits fine-grained fairness in multi-tenant clusters. In this paper, we present ServerlessT2I, a serverless-native system that decomposes a T2I workflow into loosely coupled model functions that can be independently managed and scheduled. By explicitly managing individual model execution, ServerlessT2I enables per-model scaling, declarative workflow composition, transparent GPU-resident communication, and fairness-aware scheduling. To make this decomposition efficient, ServerlessT2I harvests slack GPU memory left idle by compute-bound T2I inference to build a data plane that reduces model loading and data communication overheads. \sys{} further introduces a fair scheduler for multi-tenant serving. Using production traces, ServerlessT2I sustains up to 2$\times$ higher request rates than existing T2I workflow serving systems with the same GPU budget; for a fixed request rate, it saves up to 3$\times$ GPU resources while satisfying service level objectives (SLOs).

## 1. 论文的核心问题与整体含义
- **研究动机**：文本到图像（T2I）工作流（如 Stable Diffusion + ControlNet/LoRA）在无服务器平台上日益流行，但其构成由多个大模型（文本编码器、扩散模型、VAE 解码器、适配器）组成，且用户需求高度定制、流量突发性强。现有平台通常将整个工作流打包成一个“单体 GPU 函数”进行部署，带来三大问题：
  1. **扩展开销大（L1）**：按整工作流复制，即使只有某一个模型是瓶颈，也要加载整个工作流，冷启动慢，GPU 内存浪费。
  2. **用户需暴露底层通信复杂性（L2）**：多 GPU 并行化需要用户自行管理张量放置与传输，违背无服务器“隐藏基础设施”的原则。
  3. **多租户公平性不足（L3）**：GPU 稀缺，突发流量导致严重积压，现有按请求数数或 RPM 限额无法体现不同工作流巨大的算力差异（资源消耗差异可达 16×），造成分配不公。
- **整体含义**：本文提出 ServerlessT2I，将 T2I 工作流分解为松散耦合、独立可调度的模型函数（ModelFn），并利用推理时大量闲置的 GPU 内存构建一个 GPU 驻留的数据平面，以实现高效、公平的无服务器化 T2I 服务。

## 2. 方法论：核心思想与关键技术细节
- **核心思想**：将 T2I 工作流从“单体 GPU 函数”转变为“模型 DAG”，每个模型作为独立函数执行，同时回收计算限制引起的空闲 GPU 内存来降低模型加载和跨函数通信的开销。

- **关键技术细节**：
  - **编程接口与 DAG 表示**：
    - 用户以类似无服务器函数的方式实现每个模型的 `setup_io()`、`load_model()`、`execute()` 方法，声明输入输出即可。
    - 通过一个 orchestrator 函数声明式地组装工作流，系统自动根据 I/O 依赖推导 DAG，隐藏底层数据搬运与放置。
  - **GPU 驻留数据平面**：
    - **模型加载优化**：观察到模型加载时间远大于单步推理（如 Flux 工作流中高达 3.2×–13.5×），传统逐层 pipeline 无法完全隐藏。ServerlessT2I 在 GPU 内存中**缓存模型的前若干层**（首层），其余层从主机内存异步加载。通过公式计算最小前缀层数 $\mathbf{L'}_e$ 以完全隐藏加载：
      \[
      L'_e = \left\lceil \frac{(L(T_{\text{load}} - T_{\text{comp}}) + T_{\text{comp}})}{T_{\text{load}}} \right\rceil
      \]
      其中 $L$ 为总层数，$T_{\text{load}}$ 为单层加载时延，$T_{\text{comp}}$ 为单层计算时延。只需简单 profiling 即可获得。
    - **高效通信**：基于 NVSHMEM 构建 GPU 间通信平面，使用单侧操作（one-sided）和**回调式数据获取**。对于 ControlNet 并行等复杂模式，消费者 GPU 注册回调，在需要张量时从生产者 NVSHMEM 区域直接拉取，消除 PCIe 往返和同步等待。
    - **统一 GPU 内存管理与权重虚拟化**：GPU 内存分为 PyTorch 区域、NVSHMEM 区域。通过**模型权重虚拟化**将逻辑层与物理存储解耦，使缓存权重可透明分配于两个区域。权重可层粒度 LRU 驱逐（优先保留首层），并将 NVSHMEM 区域大小与 PyTorch 区域弹性协调。
  - **公平调度**：
    - **vTime 记账**：以模型函数执行为单位，累计每个租户的 GPU 墙钟时间（含加载、计算、传输），以此作为租户的“服务量”度量。
    - **两层调度器**：
      1. **公平过滤器（Layer 1）**：只允许累计 vTime 与当前最小 vTime 之差在可配置松弛量 $\Delta$ 内的租户参与调度。
      2. **优先级评分（Layer 2）**：对候选模型函数按 `score = 等待时间 - 剩余关键路径时间 - 执行时延` 排序，优先执行评分高的函数，以兼顾减少排队延迟和提升效率。
    - **公平性保证**：对于一直有可调度工作的租户，任何两个租户的服务量之差被界限在 $2(\Delta + L_{\max})$ 之内，其中 $L_{\max}$ 为单次调度的最大 vTime 计数。

## 3. 实验设计
- **数据集/工作负载**：
  - 使用自家生产集群（2026年3月）的 T2I 请求 trace，该 trace 突增性显著（75% 的 function 的 IAT CoV > 1）。
  - 构建 20 个代表性工作流，包括基模型 SD3.5、Z‑Image、Flux1‑Dev、Flux1‑Schnell、Flux2‑Klein 等，配上 ControlNet、LoRA 适配器（S1：5 个基础工作流；S2：20 个含适配器工作流）。
- **Benchmark 与对比方法**：
  - **基准系统**：vLLM‑Omni 和 Diffusers，均作为“单体 GPU 函数”部署。
  - 为这些基准增加了三种缓存变体以公平对比：
    - `NoCache`：无缓存
    - `WCache`：工作流级缓存（整个工作流权重缓存于空闲 GPU）
    - `MCache`：模型级缓存（单个模型权重缓存于空闲 GPU），与 ServerlessT2I 一样采用 LRU 淘汰策略。
  - 主要指标为 **SLO 达成率**（默认 SLO scale = 3× 单独推理时延）。
- **实验场景**：
  - 端对端测试：变化请求率规模、SLO 严格度、GPU 数量（8 到 32 卡）、请求突发性（CoV 缩放），评估 SLO 达成率及 GPU 内存利用率。
  - 微基准测试：模型加载时延分解（首层缓存的效果），ControlNet/CFG 并行加速比，权重虚拟化对 NVSHMEM 区域大小的影响，以及公平调度器在不同 slack 下的公平性/效率权衡。
  - 系统开销测试：对比单体系统，测量 DAG 分解带来的额外时延，并模拟 256 卡、600 并发请求的高并发场景验证扩展性。

## 6. 主要结论与发现
- **性能提升**：
  - 相同 GPU 预算下，ServerlessT2I 能承受 **最高 2 倍** 的请求速率。
  - 固定请求速率下，可节省 **最高 3 倍** 的 GPU 资源。
  - 可满足比基准严格 **最高 7 倍** 的 SLO，同时承受 **2 倍** 的突发流量，并保持 90% 以上的请求达标。
- **机制有效性**：
  - 首层缓存策略可将模型加载延迟降低 90%，端到端延迟降低 21%，接近理想完全不加载的情景。
  - GPU 驻留通信与回调机制使 ControlNet 并行等特殊并行模式接近理论最优。
  - 权重虚拟化成功缓解 NVSHMEM 区域固定尺寸带来的 GPU 内存紧张，避免系统停顿或过多重载。
- **公平性**：vTime 调度器能够在可配置的 slack 下有效限制多租户之间的服务量差距，同时通过第二层评分保持高 SLO 达成率，实现了公平与效率的平衡。

## 7. 优点
- **分解式设计**：将工作流细粒度化为模型 DAG，实现按需独立缩放，从根本上降低了冷启动开销和内存浪费。
- **创新性利用闲置 GPU 内存**：洞察到 T2I 推理计算受限、内存利用率低，将这部分内存转化为缓存权重和通信缓冲区，一举两得。
- **透明的性能优化**：通过 NVSHMEM 和回调机制，让用户无需了解底层的张量搬运；通过权重虚拟化，透明地统一了 PyTorch 和 NVSHMEM 内存区域。
- **真实且全面的评估**：使用生产 trace 与广泛工作流，对比例有的放矢（为基线添加缓存），实验维度丰富。
- **公平性度量精准**：vTime 直接基于 GPU 墙钟时间，比基于请求数或操作数更准确反映资源消耗，两层调度提供可调节的公平-效率权衡。

## 8. 不足与局限
- **适用范围**：明确限定于 T2I 工作流，未扩展到视频生成模型（推理及加载特征不同，且用户工作流较少）。
- **缓存依赖流行度倾斜**：文中提到主机内存缓存前 15 个最热门工作流即可服务 99% 请求，若工作流多样性急剧增加或流行度分布均匀，缓存命中率下降可能影响效果。
- **NVSHMEM 区域弹性**：NVSHMEM 区域大小需要在初始化时指定，本文主要通过权重虚拟化缓解，但如果通信压力极大而区域设置过小，仍可能出现慢速。需要运维经验设置合理大小。
- **调度 slack 配置**：Δ 值需操作人员根据需求在公平性和效率之间手动调节，缺乏自适应调整机制。
- **故障恢复**：文中简要提及故障恢复（重新执行受影响模型函数），但未进行深入评估，可能在实际大规模集群中成为关注点。
- **对比基线**：虽然与 vLLM‑Omni 和 Diffusers 做了细致对比，但未与某些专门针对多租户 T2I 调度或加载优化的近期学术系统直接比较（如 DistriFusion、xDiT 等主要针对单工作流加速，文中已说明互补性，仍可视为局限）。
