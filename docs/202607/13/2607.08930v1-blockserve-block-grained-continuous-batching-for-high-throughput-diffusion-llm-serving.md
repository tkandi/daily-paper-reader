## 摘要
扩散大语言模型（dLLM）的高效服务受到收敛异质性的阻碍：当批处理多个请求时，不同序列以不同速率收敛，导致快速请求被落后请求阻塞，产生计算气泡和尾部延迟。我们提出 BlockServe，一个连续批处理框架，它将块粒度调度（在块边界立即驱逐已完成的请求）与混合状态执行相结合，通过 gather-scatter 索引将双重缓存和并行解码扩展到异构批次。此外，计算感知的准入控制器通过基于 token 预算的补充来扩展有效批次容量。在五个基准测试上的 Dream 和 LLaDA 实验中，BlockServe 实现了比 Fast-dLLM 高 1.9–10.6 倍的吞吐量，并具有可比的生成质量，确立了块粒度调度作为高吞吐量离线 dLLM 推理的基础。

## Abstract
Efficient serving of diffusion large language models (dLLMs) is hindered by convergence heterogeneity: when batching multiple requests, different sequences converge at different rates, causing faster requests to stall behind slower stragglers and introducing compute bubbles and tail latency. We present BlockServe, a continuous batching framework that integrates block-grained scheduling -- immediately evicting completed requests at block boundaries -- with mixed-state execution that extends dual cache and parallel decoding to heterogeneous batches via gather-scatter indexing. Furthermore, a compute-aware admission controller expands effective batch capacity through token-budgeted refill. On Dream and LLaDA across five benchmarks, BlockServe achieves 1.9--10.6$\times$ throughput over Fast-dLLM with comparable generation quality, establishing block-grained scheduling as a foundation for high-throughput offline dLLM inference.

## 论文核心问题与整体含义
扩散大语言模型（dLLM）采用并行去噪生成文本，天然以固定长度的“块”为单位输出。当对多个请求进行批处理时，不同序列收敛至完成的速率存在差异——部分请求在较少的去噪步数后即可结束，而另一些请求需要更多块才收敛。这种**收敛异质性**导致在先完成的请求必须等待同一批次中最慢的请求（straggler）结束，形成大量的 GPU 空闲时间（**计算气泡**），并产生严重的尾部延迟。现有的自回归 LLM 连续批处理技术以 token 为粒度进行调度，无法适用于 dLLM 的块级生成范式。因此，本文旨在提出一种专门面向 dLLM 的块粒度连续批处理框架，以解决上述收敛异质性带来的性能瓶颈，提升离线批量推理的吞吐量。

## 方法论
### 核心思想
- 将调度粒度从“请求级锁步”下移到**块级抢占**：每个调度量子对应一次包含 S 步去噪的完整块周期，在块边界立即驱逐已完成的请求，不再等待整个批次同步。
- 通过**混合状态内存管理**，使同一批次中处于不同块索引的请求能够在统一的稠密张量中同时执行，避免因请求进展不同而无法并行。
- 用**计算感知的准入控制**替代固定批次容量，根据请求长度和当前进度动态调整并发度，在不触发显存溢出（OOM）的前提下最大化有效批次大小。

### 关键技术细节
1. **块粒度调度（Block-Grained Scheduling）**
   - 调度循环（详见 Algorithm 1）：从按提示长度排序的待处理队列 \(P\) 中，根据 token 预算将候选请求准入活跃集 \(A\)；并行执行一次块周期；更新每个请求的块索引 \(b_i\)；在块边界检查并移除已完成（\(b_i \ge K_i\) 或生成结束符）的请求。
   - 这种“执行-检查-驱逐”的模式让已完成请求不再继续占用资源，从根本上消除了 straggler 造成的计算气泡。

2. **混合状态内存管理（Mixed-State Memory Manager）**
   - **逻辑位置对齐**：将整个批次铺设为一个大小为 \(|A| \times \max_{r_i \in A} (p_i + (b_i+1)L)\) 的稠密张量（公式 1，其中 \(p_i\) 为提示长度，\(L\) 为块长度）。通过左填充和基于注意力掩码的累积索引，为每个请求生成独立且逻辑正确的显式位置 ID，确保 RoPE 旋转位置编码和前缀缓存的语义在混合进度下仍保持一致。
   - **向量化混合调度执行**：通过 **gather-scatter 索引**解耦逻辑位置与物理地址，使每个去噪步骤仅对活跃块区域进行 KV 缓存更新和并行解码。该机制使得可以在一个统一的块周期内推进所有请求，而不要求它们的块索引相同，从而利用双重缓存和并行解码等单请求优化技术。

3. **计算感知的准入控制**
   - 定义批次开销为当前活跃集所需的最大行宽与请求数的乘积（公式 1）。当一个完成请求被驱逐后，边界框可能缩小，释放出新的预算空间。
   - 采用贪婪的“长度感知”填充策略：从按提示长度排序的队列中依次选取候选请求，仅当其初始行宽（\(p_{cand} + L\)）不扩大当前边界框时方予准入，且总开销不超过通过离线 profiling 确定的 token 预算 \(\beta_{budget}\)。这一策略可安全地突破静态批次大小限制，实现 2–4 倍的批容量提升。

### 公式与算法
- **批次开销**：\(\text{Cost}(A) = |A| \times \max_{r_i \in A} (p_i + (b_i+1)L)\)
- **调度循环**（伪代码见 Algorithm 1）：循环执行“准入 → 块周期执行 → 更新块索引 → 驱逐已完成请求”，直至队列及活跃集均为空。
- **有效计算比**：\(R = \frac{1}{T B} \sum_{t=1}^{T} a_t\)，衡量平均活跃请求数占名义批量大小的比例，用于量化 straggler 效应和空泡减少程度。

- **Fast-dLLM (Static)**：开启 Dual Cache 和 Parallel Decoding 的 dLLM 推理加速器，但按固定批次处理，所有请求同步。

## 主要结论与发现
1. **吞吐量大幅提升**：BlockServe 在 LLaDA 和 Dream 上较 Fast-dLLM 分别实现了 2.6–7.7 倍和 1.9–10.6 倍的吞吐量提升（最强配置下），总墙钟时间显著缩短。
2. **质量基本维持**：各任务准确率与基线相比在可接受范围内波动，未出现系统性下降，证明吞吐增益不以严重牺牲生成质量为代价。
3. **消除尾部延迟**：从延迟-生成长度小提琴图和有效计算比可以看出，BlockServe 彻底消除了因等待慢请求而出现的长尾延迟和计算比骤降，使活跃请求比例接近或超过 1.0。
4. **批容量扩展**：Token 预算准入机制使最大安全批次大小提升 2.0–4.0 倍，有效利用 GPU 内存。
5. **关键设计验证**：块长度 \(L=32\) 在调度开销与生成稳定性之间获得最佳平衡；提示长度排序可将吞吐量再提升 4.7%–9.2%，证实了减少 padding 浪费的重要性。

## 不足与局限
### 实验覆盖与偏差风险
- **单一硬件环境**：所有实验均在单个 H200 上完成，未评估多 GPU 分布式推理下的可扩展性和通信开销。
- **离线设定为主**：实验采用离线批处理模式（处理整个数据集），未模拟真实的在线请求到达、动态并发场景，因此无法直接引用于交互式服务。
- **模型与任务局限**：仅评估了 7B–8B 参数的扩散 LLM，未测试更大规模模型（如 13B、30B）或更多样化的生成任务（如翻译、摘要），通用性尚需验证。
- **质量波动**：部分实验（如 Dream + GSM8K 在更大块长时）出现近 9% 的准确率下降，说明块粒度调度与并行解码的近似效应在某些任务上可能叠加，影响输出质量，文中并未深入分析原因。

### 应用限制
- **依赖离线 profiling**：Token 预算需针对特定 GPU 和模型预先测定，更换硬件或模型时需重新 profiling，部署灵活性受限。
- **未考虑动态请求长度混合**：准入控制依赖提示长度和当前进度来防止 OOM，但在生成长度未知或极度变长的情况下，边界框预测可能失准。
- **仅解决计算气泡问题**：未涉及 KV 缓存内存的精细化复用或跨推理阶段的内存优化问题（如 dLLM-Serve 所关注的相位多路复用），因此在显存极度受限的场景下可能仍需进一步优化。
