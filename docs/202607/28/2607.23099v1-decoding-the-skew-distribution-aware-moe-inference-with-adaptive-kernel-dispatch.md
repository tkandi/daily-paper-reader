## 摘要
混合专家（MoE）推理由稀疏的专家GEMM组成，其形状随运行时路由分布而变化。现有服务系统通常使用静态令牌计数桶选择融合MoE内核，忽略了决定块填充、内存复用和内核效率的逐专家路由分布。我们引入了一个分布感知框架，用于建模和基准测试MoE推理。该框架结合了紧凑的有效专家指标和基于Dirichlet的逆向建模过程，生成可控的路由分布，以进行系统的硬件研究。通过该框架，我们表明最佳融合MoE内核随路由偏斜和令牌数量而变化。我们进一步提出了DA-MoE，一个针对NVIDIA GPU的GPU驻留内核调度运行时，它将实时路由直方图与离线调优的分布进行匹配，并在无需CPU-GPU同步的情况下选择接近最优的融合MoE内核。在HumanEval-X服务跟踪上，DA-MoE在DeepSeek-V3上将几何平均融合MoE延迟提高了1.16倍，在Kimi K2上提高了1.29倍，峰值加速分别为1.40倍和1.56倍。

## Abstract
Mixture-of-Experts (MoE) inference consists of sparse expert GEMMs whose shapes vary with the runtime routing distribution. Existing serving systems typically select fused-MoE kernels using static token-count buckets, ignoring the per-expert routing distribution that determines tile padding, memory reuse, and kernel efficiency. We introduce a distribution-aware framework for modeling and benchmarking MoE inference. The framework combines the compact Effective Experts metric with a Dirichlet-based reverse-modeling procedure that generates controllable routing distributions for systematic hardware studies. Using it, we show that the best fused-MoE kernel changes with routing skew and token count. We further present DA-MoE, a GPU-resident kernel-dispatch runtime for NVIDIA GPUs that matches the live routing histogram to offline-tuned distributions and selects a near-optimal fused-MoE kernel without CPU--GPU synchronization. On HumanEval-X serving traces, DA-MoE improves geomean fused-MoE latency by 1.16X on DeepSeek-V3 and 1.29X on Kimi K2, with peak speedups of 1.40X and 1.56X.

### 1. 论文的核心问题与整体含义

*   **研究问题**：现有混合专家（MoE）大模型推理系统（如 TensorRT-LLM、vLLM）在调用高度优化的“融合 MoE 内核”时，通常只根据静态的“总 token 数”（即批次大小）来选择一个预调优的内核。这种做法**完全忽略了每一层、每一次前向传播中，token 在各个专家之间的分布情况（路由偏斜）**。
*   **核心矛盾**：MoE 推理中的专家 GEMM 计算高度依赖矩阵乘法加速器（如 Tensor Core）的**瓦片（tile）形状**。较大的 tile 有利于数据复用但会产生更多零填充浪费，较小的 tile 能减少填充但增加内存访问。**最佳 tile 形状（进而最佳内核）并非固定不变，而是随路由分布偏斜程度和 token 数量的变化而显著移动**。
*   **整体含义**：本文将 MoE 推理性能优化的视角从“token 总数”提升到“**分布感知**”层面，证明了动态感知并适配路由分布是进一步提升推理效率的关键，并为此提供了从理论建模到实际运行时的完整解决方案。

### 2. 论文提出的方法论

论文的核心贡献分为两部分：一个用于建模与分析的框架（§III），以及一个实际的运行时调度系统 DA-MoE（§IV）。

*   **2.1 分布感知的建模与基准测试框架**
    *   **有效专家（Effective Experts）指标**：为了量化路由分布的偏斜程度，提出了一个简洁的标量指标 `eff_exp = (∑ti)² / ∑ti²`，其中 `ti` 是路由到专家 `i` 的 token 数。该值范围在 [1, N] 之间，具有跨批次大小不变的特性，直观反映了“实际承载负载的专家数量”。
    *   **基于 Dirichlet 的逆建模**：利用对称 Dirichlet 分布 `Dir(α)` 可以生成不同偏斜程度概率向量的特性，通过二分搜索（Algorithm 1）寻找匹配特定 `eff_exp` 值的集中度参数 `α`。这样就可以为任意规模的 MoE 模型**生成可控偏斜程度的路由分布**，用于系统的硬件性能扫描。
    *   **分布族标记 `ddist:X`**：将生成的路由分布参数化为 `ddist:X`，其中 `X` 为偏斜乘数（`X=N` 时极限偏斜，`X=1` 时接近均匀分布），方便定义和遍历不同的偏斜场景。

*   **2.2 DA-MoE：分布感知的 GPU 端自适应内核调度**
    *   **离线自动调优**：对于每一个 token-count 桶，用上述框架生成一系列不同偏斜度的合成路由分布。将每个分布表示为一个“范例（exemplar）”，即按降序排列并进行 L2 归一化的逐专家 token 计数向量。然后针对每个范例，在所有可用的 TRTLLM 融合 MoE 内核中进行性能基准测试，**记录下延迟最低的内核 ID**，形成一个“范例→最佳内核”的查找表并上传到 GPU 显存。
    *   **在线动态调度（全部在 GPU 上完成，无需 CPU 同步）**：
        1.  当模型的路由器生成每个 token 的专家选择后，**在 GPU 上**构建当前层的实时路由直方图（每个专家分到的 token 数）。
        2.  将该直方图排序并 L2 归一化后，与当前 token-count 桶下的所有离线范例进行**余弦相似度**比较。
        3.  选择最相似的范例所对应的内核 ID，通过**条件 CUDA Graphs（Conditional CUDA Graphs）** 的 `cudaGraphConditional` 节点直接在 GPU 内部进行动态分支，调度执行选定的最佳内核，从而完全避免了将路由数据拷贝回 CPU 并重新启动图的巨大开销。

### 6. 论文的主要结论与发现

*   **路由分布是关键变量**：最佳 GPU 内核的选择不仅依赖于 token 总数，更显著依赖于逐专家的 token 分布。仅基于 token 数的静态选择方案（NoDA）在真实负载下存在 20%-59% 的性能损失。
*   **有效专家指标有效**：提出的 `Effective Experts` 指标能有效捕获路由偏斜度，且基于 Dirichlet 的逆建模方法能生成高度拟合真实路由的合成分布，用于离线分析和调优。
*   **DA-MoE 实现显著且接近最优的加速**：在真实的 HumanEval-X 服务场景下，DA-MoE 在 DeepSeek-V3 和 Kimi K2 上分别实现了 1.16x 和 1.29x 的融合 MoE 几何平均延迟提升，峰值可达 1.56x。在大部分 token 数下，DA-MoE 的延迟与 Oracle 的差距在 4% 以内。

### 8. 不足与局限：包括实验覆盖、偏差风险、应用限制等

*   **对特定软件的依赖**：DA-MoE 的在线调度依赖于 CUDA Graphs 的条件节点，这限定了其只能用于较新版本的 NVIDIA CUDA 栈（12.8+）。论文也指出，类似 AMD HIP 的编程模型暂不提供等效功能，限制了跨平台应用。
*   **离线调优的扩展性**：当前离线调优需要为每个 token-count 桶内的多个偏斜级别预先运行内核基准测试。随着未来模型专家数、GPU 代际和内核变体数量的爆炸式增长，全扫描式的离线调优开销可能变得不可接受，文中未深入探讨如何降低此开销。
*   **小模型和特定条件下的收益不明确**：实验发现，在专家并行度为 1（EP=1）且 token 数较大（512）等场景下，DA-MoE 的收益消失或减小。这表明其适用性依赖于工作负载能暴露出的足够显著的分布差异，对于计算密度极高或分布已足够平均的场景可能价值有限。
*   **实验工作负载的代表性**：性能评估主要基于代码生成的 HumanEval-X 负载。虽然这与用于分析的 MMLU 数据不同，但更广泛、更多样的现实世界服务加载（如长文本摘要、多轮对话）下的路由分布模式及对应的加速效果未有更多验证。
