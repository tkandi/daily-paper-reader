## 摘要
智能体AI系统在共享GPU/CPU基础设施上组合异构工具工作负载，但现有框架默认将所有支持GPU的工具分配到GPU。我们对19个AI工具在GPU和CPU上进行性能分析，发现其中11个倾向于GPU，4个模糊不清，1个因PCIe传输占主导而倾向于CPU，3个设备中立，从而证明一概而论的GPU优先调度是次优的。我们将设备调度建模为在显存预算下为每个工具分配三种选项之一：立即GPU执行、排队GPU执行或CPU卸载，并识别出导致端到端延迟偏离静态性能的两种运行时因素：GPU利用率争用和显存容量争用。我们提出一种智能体调度器，它将LLM智能体与算法运行时监控器配对，监控器通过运行平均值、对称重探测、交换重探测和探索提示扩展LLM的观测能力，而从不指定采用何种映射。在涵盖串行执行、并行争用和内存受限执行的13种场景中，智能体调度器在所有13种场景下均达到暴力搜索最优映射，在映射精度上与最佳经典基线相当，同时避免了在完整映射上的赌博机式探索，并且优于HEFT、StarPU和全GPU策略，同时无需任何离线训练。

## Abstract
Agentic AI systems compose heterogeneous tool workloads on shared GPU/CPU infrastructure, yet existing frameworks assign all GPU-capable tools to the GPU by default. We profile 19 AI tools across GPU and CPU and find that 11 are GPU-preferred, 4 are ambiguous, 1 is CPU-preferred due to PCIe transfer dominance, and 3 are device-neutral, establishing that blanket GPU-first scheduling is suboptimal. We formulate device scheduling as assigning each tool to one of three options: immediate GPU execution, queued GPU execution, or CPU offload, under a VRAM budget, and identify two runtime factors that cause end-to-end latency to diverge from static profiles: GPU utilization contention and VRAM capacity contention. We present an agentic scheduler that pairs an LLM agent with an algorithmic runtime monitor, where the monitor expands what the LLM can observe via running averages, symmetric reprobing, swap reprobing, and exploration hints, without ever prescribing which mapping to adopt. Across 13 scenarios spanning serial execution, parallel contention, and memory-constrained execution, the agentic scheduler reaches the brute-force optimal mapping in all 13 scenarios, matching the best classical baseline on mapping accuracy while avoiding bandit-style exploration over complete mappings, and outperforming HEFT, StarPU, and the all-GPU policy while requiring zero offline training.

## 1. 论文的核心问题与整体含义（研究动机和背景）

现代智能体 AI 系统（如 LangGraph、CrewAI）常以 DAG 形式编排多种异构工具（如深度学习推理、向量搜索、文档解析等），并默认将所有支持 GPU 的工具直接分配到 GPU 上执行。然而，该工作通过对 19 个真实 AI 工具进行 GPU 与 CPU 的性能剖析发现：
- 仅 11 个工具为“GPU‑偏好”型（speedup > 5×）；
- 4 个工具处于“模糊”区（0.5 ≤ speedup ≤ 5×）；
- 1 个工具因 PCIe 传输开销占主导而“CPU‑偏好”（speedup < 0.5×）；
- 3 个工具为“设备中立”（无 GPU 实现或 speedup ≈ 1×）。

因此，盲目的“全 GPU 优先”策略是次优的，甚至可能违反显存预算。此外，并行工具间还存在 **GPU 利用率争用**（并发导致实际延迟远高于独立时）和 **显存容量争用**（超过显存上限导致不可行），这两类运行时因素会进一步使静态剖析结果失效。因此，**核心问题**是：如何在显存约束和依赖约束下，为每个工具动态选择“立即 GPU 执行”、“排队 GPU 执行”或“CPU 卸载”三种模式，以最小化端到端延迟。

## 2. 论文提出的方法论

提出一种**智能体调度器**，由 LLM 智能体与运行时监控器协同工作，无需任何离线训练。

### 2.1 问题形式化
- 工作流建模为 DAG \(G = (V, E)\)，每个节点 \(v\) 表示一个工具调用，边表示数据依赖。
- 每个工具可选择三种执行模式之一：\(a_v \in \{ \text{cpu}, \text{gpu\_now}, \text{gpu\_queue} \}\)。
- \(\text{gpu\_now}\)：立即 GPU 执行，占用显存；\(\text{gpu\_queue}\)：排队 GPU 执行，等待时不计入同时显存占用，但引入加载开销；\(\text{cpu}\)：CPU 执行。
- 目标：在依赖可行和显存容量 \(M\) 约束下，最小化叶子节点完工时间的最大值（makespan）。

### 2.2 系统架构
1. **离线剖析器**：测量每个工具在隔离状态下的 CPU 耗时、GPU 耗时、模型加载时间及 GPU 内存占用，生成结构化工具卡片。
2. **LLM 调度器**：接收工具卡片、DAG 结构及来自运行时监控器的反馈（运行平均值、重探测结果等），推理并输出下一轮的设备映射。使用 DeepSeek‑R1‑Distill‑Qwen‑32B‑AWQ，以 in‑context learning 方式工作，无需微调。
3. **运行时监控器**：不制定调度策略，只扩展 LLM 的**观测空间**。根据运行时因素渐进激活：
   - **Factor A（GPU 利用率争用）**：维护滑动窗口的每工具‑设备延迟运行平均值，替换静态剖析。
   - **Factor B（显存容量争用）**：实施**对称重探测**（试探将单个工具更换为另一可行设备）和**交换重探测**（当单工具移动不可行时，交换一对工具的角色，例如将 A 改为 gpu_now 同时将 B 改为 gpu_queue），并生成探索提示，向 LLM 提供“what‑if”证据。

### 2.3 推理示例
- 当提供工具卡片时，LLM 可利用速度比（\(\text{cpu\_time}/\text{gpu\_time}\)）和离线卸载指南直接输出 optimal 映射。
- 当无卡片时，LLM 可能基于语义先验给出错误映射，但数轮后监控器积累运行平均值和重探测数据，LLM 据此修正（如图 4 所示）。

## 3. 实验设计

### 3.1 工具与剖析
- 使用 19 个 AI 工具，涵盖 NLP（DistilBERT、BERT、LLaMA）、视觉（ResNet‑50、CLIP）、语音（Whisper）、OCR 及数据处理等，均用真实数据集（ImageNet、SST‑2、MNLI、LibriSpeech 等）进行剖析。
- 为解决部分工具延迟过短无法稳定观测争用的问题，构造“放大版”工具（例如 bert_base_x12，即重复 12 次相同运算）。

### 3.2 评估场景
构造 13 个四工具 DAG 场景，分为三类：
- **S1–S4**：串行依赖（菱形 DAG），研究纯依赖下的 CPU/GPU 二元放置，无争用。
- **S5–S10**：扇出并行 DAG（四个工具同时就绪），激活 GPU 利用率争用，但内存仍无限制，二元放置。
- **S11–S13**：扇出 DAG 并施加硬显存预算（1100 MB 或 1700 MB），引入三元模式（gpu_now, gpu_queue, cpu）。

每个场景的暴力搜索最优映射（oracle）均通过离线枚举得到。

### 3.3 对比方法
- **All‑GPU**：所有兼容工具归 GPU（等同于主流框架默认策略）。
- **HEFT**：以剖析成本做列表调度的经典异构算法。
- **UCB1**：将每个完整映射视为臂的多臂赌博机算法。
- **StarPU**：带在线性能模型的自适应贪婪调度器。
- 在 S11–S13 中，还额外对比了**内存感知贪婪**基线（按 GPU speedup 排入 gpu_now 直至显存满，其余去 CPU）。

评估指标：到达 oracle 映射的匹配度（0–4 个工具）和归一化至 oracle 的端到端延迟。

## 4. 资源与算力

- 工具执行：NVIDIA RTX A5500 GPU + AMD EPYC 7713 CPU。

## 6. 论文的主要结论与发现

- **静态剖析不可靠**：在 GPU 利用率争用下，工具延迟可膨胀 43%–250%；显存约束进一步使全 GPU 映射不可行。需要运行时观测反馈。
- **智能体调度器达到 oracle 最优**：在所有 13 个场景中，提出的 LLM‑监控器协同架构均能收敛到暴力搜索所得的最优映射，匹配 UCB1 的放置准确率（10/10 场景全 4/4），但无需像 UCB1 那样探索完整映射空间。
- **零训练优势**：相较于 RL 设备放置方法，本工作无需数千次训练剧集，仅通过提示中的上下文学习即可生效。
- **监控器设计关键**：运行平均值解决利用率争用，对称重探测和交换重探测解决内存约束下的组合发现，探索提示防止陷入局部最优。三者缺一不可（见消融）。
- **与经典调度器的对比**：
  - HEFT 因静态成本模型在并行争用下表现较差（只有 2/10 场景达到 oracle 映射）。
  - StarPU 的在线模型可以应对部分争用，但在多数场景仍产生 1.3×–1.7× 的额外延迟。
  - 全 GPU 策略在所有有显著争用或内存约束的场景中严重劣化。

## 7. 优点

- **零训练、冷启动即可用**：可快速移植到新硬件或新工具集，只需重新剖析。
- **LLM 与监控器分工明确**：LLM 负责高层决策，监控器扩展观测空间但不做策略指示，设计解耦，易于扩展。
- **渐进式监控激活**：在无争用时几乎不需监控开销；仅当出现利用率或内存争用时才逐步开启测量和重探测，开销可控。
- **overall 性能强**：在所有 13 个场景均达到暴力最优，且避免了赌博机的指数级探索开销。
- **消融实验扎实**：清晰揭示了三种监控机制的必要性，增强了方案的可信度。

## 8. 不足与局限

- **缺乏理论收敛保证**：探索策略仍是启发式，不保证从任意初始状态到达全局最优。文中承认需未来数据驱动策略改进。
- **LLM 稳定性问题**：在 S13 案例的收敛后，个别轮次出现扰动（Round 12 的 1/4 匹配），说明 LLM 的生成有随机性，连续部署需额外机制防止抖动。
- **场景规模有限**：所有评估均限于 4 工具 DAG，更大规模工作流下的效果和开销未知。真实智能体系统可能涉及数十个工具和更复杂的 DAG 结构。
- **剖析成本依赖性**：若工具或硬件变更，需重新进行离线剖析，尽管简便，但仍需测量步骤。全盲冷启动（无任何 card）时，初轮准确度依赖语义先验，可能不理想。
- **LLM 能力依赖**：性能依赖 LLM 的推理质量，低质量模型可能导致错误映射或收敛过慢。论文只使用了 32B 模型，更小模型的表现有待检验。
- **缺乏真实工作负载验证**：场景为合成构造，虽覆盖典型模式，但未在与 LangGraph、AutoGen 等真实框架集成的环境中评测，可能遗漏实际工程中的额外约束（如网络通信、异构 GPU 拓扑等）。
