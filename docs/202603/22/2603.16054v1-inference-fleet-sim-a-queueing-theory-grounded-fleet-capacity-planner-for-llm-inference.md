## 摘要
为大语言模型（LLM）推理确定 GPU 集群规模比看起来要困难得多。一些显而易见的问题——需要多少个 GPU、哪种型号、如何在双池集群中进行切分——并没有闭式解。它们取决于完整的 token 长度分布、路由策略以及在重尾工作负载下变得异常复杂的排队动态。现有工具针对固定的 GPU 数量优化单个引擎的配置，但没有一个工具能解决上游问题，即应该购买多少个 GPU 以及如何布置它们。inference-fleet-sim 填补了这一空白。它结合了解析式 M/G/c 排队模型与离散事件模拟（DES），以寻找能够凭经验满足 P99 TTFT（首字延迟）SLO（服务水平目标）的最低成本集群配置。它包含一个受物理启发的 GPU 性能模型，涵盖了 A10G、A100 和 H100，支持单体式、双池路由式和解耦式拓扑，且无需访问真实硬件。我们在源自两个公共工作负载追踪（LMSYS、Azure）和一个合成的重代理（agent-heavy）追踪的七个集群规划场景中运行了该工具。每个场景都揭示了简单分析会出错的结果——例如正确的切分阈值、最便宜的 GPU 类型、以及一个表面上空闲的集群是否实际上已失效——并展示了为什么必须对排队、路由和硬件进行联合模拟才能找到正确答案。

## Abstract
Sizing a GPU fleet for LLM inference is harder than it looks. The obvious questions -- how many GPUs, which type, where to split a two-pool fleet -- have no closed-form answers. They depend on the full token-length distribution, the routing policy, and queueing dynamics that turn ugly under heavy-tailed workloads. Existing tools optimize per-engine configuration for a fixed GPU count; none of them address the upstream question of how many GPUs to buy and how to arrange them.   inference-fleet-sim fills that gap. It combines analytical M/G/c queueing with discrete-event simulation (DES) to find the minimum-cost fleet configuration that empirically meets a P99 TTFT SLO. It includes a physics-informed GPU performance model covering A10G, A100, and H100 across monolithic, two-pool-routed, and disaggregated topologies, all without requiring access to real hardware. We run the tool on seven fleet-planning scenarios drawn from two public workload traces (LMSYS, Azure) and one synthetic agent-heavy trace. Each one surfaces a result that simple analysis gets wrong -- the right split threshold, the cheapest GPU type, whether an apparently idle fleet is actually broken -- and shows why joint simulation of queueing, routing, and hardware is necessary to find it.

#### 2. 方法论：核心思想与技术细节
该工具采用**两阶段优化**架构，结合了数学解析的快速性与仿真的准确性：

*   **第二阶段：离散事件仿真（DES）验证**：
    *   对解析扫描出的 Top-k 候选方案进行请求级仿真。
    *   模拟连续批处理（Continuous Batching）和事件驱动的排队过程，验证其在真实动态下的 SLO 达成率。

#### 6. 主要结论与发现
*   **切分阈值非直观**：最优的短/长序列切分阈值无法直接从 CDF 图表中读出，必须考虑槽位效率与排队碎片的交互。
*   **低利用率不代表安全**：在 Agent 负载下，即使集群利用率仅 30%，也可能因重尾请求导致的“队头阻塞”而违反 SLO。
*   **慢 GPU 可能更省钱**：通过合理的双池布局，低成本的 A10G 在某些场景下比 H100 更具性价比。
*   **解耦推理的逆直觉**：在预填充（Prefill）与解码（Decode）解耦的架构中，**高性能 GPU 应优先用于解码池**而非预填充池。
*   **电网灵活性**：通过限制最大并发批次，H100 集群可在满足 SLO 的前提下临时削减 30%-40% 的功耗。

#### 7. 优点
*   **填补空白**：首次系统性地解决了 LLM 推理集群的“采购级”规划问题。
*   **高效结合**：将解析模型的速度与 DES 的精度相结合，实现了巨大的搜索空间优化。
*   **物理启发**：性能模型基于硬件底层逻辑（内存带宽、KV 缓存），具有很强的泛化能力和预测精度。
*   **实用性强**：考虑了硬件故障率和电网功耗等现实生产因素。

#### 8. 不足与局限
*   **泊松流近似**：按长度拆分流量后，子流不再是严格的泊松流，解析模型可能存在一定偏差。
*   **请求级仿真粒度**：未模拟 Token 级的抢占、复杂的调度重排或投机采样，可能在极精细的调度研究中精度不足。
*   **线性模型简化**：GPU 性能模型采用线性 Roofline 假设，忽略了如 FlashAttention 优化、量化加速等非线性效应（虽可通过校准常数部分补偿）。
*   **单节点假设**：假设每个 GPU 实例为单节点副本，未显式建模多节点张量并行（TP）时的跨节点通信开销。
