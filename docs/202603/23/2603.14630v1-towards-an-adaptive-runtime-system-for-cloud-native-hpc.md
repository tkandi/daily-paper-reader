## 摘要
高性能计算（HPC）与云计算的持续融合提出了一个根本性挑战：为静态且同构的超级计算机设计的 HPC 应用程序，难以适应云环境的动态性、异构性和波动性。传统的并行编程模型（如 MPI）难以利用云的关键优势（如资源弹性和低成本的竞价实例），同时也无法应对性能波动和处理器异构性等挑战。本文展示了 Charm++ 并行运行时系统的异步、消息驱动范式如何弥合这一差距。我们提出了一套工具和策略，使 HPC 应用程序能够在跨 CPU 和 GPU 资源的动态云基础设施上高效且具韧性地运行。我们的工作有两项关键贡献：首先，我们证明了 Charm++ 中感知速率的负载均衡能够提升在云端异构 CPU 和 GPU 实例上运行的应用程序性能。我们进一步展示了 Charm++ 的核心原则如何缓解由网络争用和处理器性能波动等常见云挑战引起的性能下降，而这些挑战因许多科学和工程应用中紧耦合、全局同步的特性而变得更加严峻。其次，我们扩展了现有的资源管理框架，以支持 GPU 和 CPU 竞价实例，并实现最小的中断开销。总之，这些贡献提供了一个稳健的框架，用于调整 HPC 应用程序，以在云端实现高效、具韧性且具成本效益的性能。

## Abstract
The ongoing convergence of HPC and cloud computing presents a fundamental challenge: HPC applications, designed for static and homogeneous supercomputers, are ill-suited for the dynamic, heterogeneous, and volatile nature of the cloud. Traditional parallel programming models like MPI struggle to leverage key cloud advantages, such as resource elasticity and low-cost spot instances, while also failing to address challenges like performance variability and processor heterogeneity. This paper demonstrates how the asynchronous, message-driven paradigm of the Charm++ parallel runtime system can bridge this gap. We present a set of tools and strategies that enable HPC applications to run efficiently and resiliently on dynamic cloud infrastructure across both CPU and GPU resources. Our work makes two key contributions. First, we demonstrate that rate-aware load balancing in Charm++ improves performance for applications running on heterogeneous CPU and GPU instances on the cloud. We further demonstrate how core Charm++ principles mitigate performance degradation from common cloud challenges like network contention and processor performance variability, which are exacerbated by the tightly coupled, globally synchronized nature of many science and engineering applications. Second, we extend an existing resource management framework to support GPU and CPU spot instances with minimal interruption overhead. Together, these contributions provide a robust framework for adapting HPC applications to achieve efficient, resilient, and cost-effective performance on the cloud.

#### 1. 核心问题与整体含义（研究动机和背景）
随着高性能计算（HPC）与云计算的融合，传统 HPC 应用面临严峻挑战。HPC 应用通常为静态、同构的超级计算机设计，而云环境具有**动态性、异构性和波动性**。
*   **研究动机**：传统的并行编程模型（如 MPI）难以处理云端的网络延迟波动、硬件异构性（不同代际的 CPU/GPU 混合）以及竞价实例（Spot Instances）的随机中断。
*   **核心目标**：利用 Charm++ 的异步消息驱动范式，构建一个能够自适应云端复杂环境的运行时系统，实现高效、具韧性且低成本的云原生 HPC 运行。

#### 2. 方法论：核心思想与关键技术
论文基于 **Charm++** 运行时系统，提出了以下核心技术：
*   **过度分解（Overdecomposition）**：将应用分解为比处理器数量更多的“chares”（任务对象）。当某个任务等待网络通信时，运行时可调度其他任务，从而利用计算掩盖云端高延迟网络的通信开销。
*   **速率感知动态负载均衡（Rate-aware Load Balancing）**：针对云端异构实例（如不同频率的 CPU 或不同型号的 GPU），运行时系统根据各处理器的实际处理速率动态迁移任务对象，确保负载平衡。
*   **GPU 竞价实例支持**：
    *   **守护进程机制**：在每个 GPU 实例上运行守护进程，利用 CUDA IPC 实现 GPU 数据的内存级快照（Checkpoint），避免了中断时昂贵的主机-设备间数据迁移。
    *   **迁移模型**：支持在中断发生时将 GPU 任务迁移至其他存活节点或新启动的替代节点。
*   **主动容量重平衡（Capacity Rebalancing）**：扩展了 `CharmCloudManager` 框架。系统不再是被动等待中断发生，而是监听云服务商的“重平衡通知”，提前启动替代实例，并在旧实例关闭前完成任务迁移，从而最小化算力缺口。

#### 3. 实验设计
*   **Benchmark 程序**：
    *   **Jacobi2D**：用于测试通信密集型场景及 GPU 性能。
    *   **LULESH**：非结构化拉格朗日冲击流体动力学代理应用，用于测试计算密集型场景。
*   **对比场景**：
    *   **网络性能**：对比不同过度分解因子（ODF=1, 4, 16, 64）下的弱扩展性。
    *   **异构性**：在混合了不同代际 CPU（Intel/AMD）和 GPU（NVIDIA A10G/L40S）的集群中对比有无负载均衡的性能。
    *   **中断处理**：对比三种模式：(A) 基于共享文件系统的快照；(B) 响应式内存快照；(C) 主动容量重平衡。

实验在 **Amazon Web Services (AWS)** 上完成，使用了多种实例类型：

#### 5. 实验数量与充分性
论文进行了多维度的实验：
*   **弱扩展性实验**：覆盖了从单节点到大规模集群（256 PEs / 64 GPUs）的性能表现。
*   **异构性实验**：通过多样化的 Spot 实例池模拟真实的云端异构环境。
*   **故障注入实验**：利用 AWS Fault-Injection Simulator (FIS) 模拟真实的竞价实例中断。
*   **充分性评价**：实验设计较为全面，涵盖了 CPU 和 GPU、计算密集与通信密集应用，且对比了传统文件系统方法，客观地展示了自适应运行时的优势。

#### 6. 主要结论与发现
*   **网络优化**：过度分解在某些情况下可将运行时间减少 50% 以上，有效掩盖了云端非专用网络的延迟。
*   **异构性能提升**：速率感知负载均衡在异构 CPU 集群中提升了 10%-25% 的性能，在异构 GPU 集群中提升了约 10%。
*   **中断开销大幅降低**：
    *   内存快照比文件系统快照效率高出 50% 以上。
    *   **主动重平衡策略**将中断处理开销进一步降低了 50%。
    *   在 50% 节点发生中断的极端情况下，CPU 应用的总运行时间仅增加不到 1%，GPU 应用增加 3.4%（相比之下，无重平衡时分别增加 16% 和 20%）。

#### 7. 优点
*   **原生云支持**：不同于传统的“补丁式”方案，该系统深度集成了云端的重平衡通知和竞价实例特性。
*   **高效的 GPU 容错**：通过守护进程和 CUDA IPC 实现的 GPU 内存快照是一个技术亮点，显著降低了 GPU 任务的迁移成本。
*   **灵活性**：能够处理极其复杂的异构环境，使 HPC 用户可以混合使用廉价的旧款实例和高性能的新款实例。

#### 8. 不足与局限
*   **编程模型限制**：该方案高度依赖 Charm++ 编程模型，对于现有的海量 MPI 应用，需要进行重构或使用适配层才能受益。
*   **实验规模**：虽然涵盖了 64 个 GPU，但相比顶级超级计算机的规模仍较小，在大规模（数千节点）下的元数据管理开销尚待验证。
*   **超时参数依赖**：主动重平衡中的 `Ttimeout` 参数需要根据应用特性手动调整，缺乏自动化的最优参数搜索机制。
