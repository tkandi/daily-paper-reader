## Abstract 

Local deployment of MoE-based LLMs on CPU-GPU nodes is attractive for cost and privacy reasons, yet limited GPU memory forces most experts into CPU memory. Prefill is then compute-bound and benefits from aggressive GPU load-ing, while decode is I/O-bound and requires conservative PCIe transfers. These demands cannot be amortized un-der low batching—typical of local assistants and document tools—forcing phase-agnostic schedulers into a seesaw: fa-voring prefill’s aggressive loading injects unmaskable I/O that stalls decode, while favoring decode’s conservative trans-fers starves prefill’s GPU of work. We observe that expert routing is predictable in phase-specific ways, allowing us to decouple the two phases and optimize prediction, scheduling, and execution independently for each phase. PDScope pre-dicts expert activations to guide placement and prefetching, adapts these policies to each phase’s bottleneck via cross-layer cost modeling, and compiles decisions into overhead-free pipelines using a static computation graph, cache prefetch-ing, and zero-copy asynchronous I/O. On mainstream MoE models, PDScope achieves 2.5–10.3× higher prefill through-put and 2.1–6.1× higher decode throughput than existing systems, showing that phase-aware co-design unlocks effi-cient MoE inference under memory constraints and extends naturally to multi-batch settings. 

Keywords: Mixture-of-Experts; Offloading; LLM Inference

These two phases place conflicting demands on system re-sources: prefill benefits from aggressive expert loading to maximize GPU utilization, while decode requires conserva-tive I/O strategies to avoid transfer bottlenecks. This trade-off creates an inherent seesaw effect: optimizing for one phase inevitably degrades the other, as any static resource allocation cannot satisfy both phases simultaneously. Existing systems explore different trade-off points with unified scheduling logic. Static placement strategies [2, 10, 16, 23] (e.g., kTransformers [2]) keep hot experts (those process-ing more tokens) resident on the GPU, prioritizing decode stability but leaving GPU compute underutilized during pre-fill. On-demand loading strategies [8, 11, 13, 44] (e.g., Fate [9]) fetch experts only when needed, improving prefill through-put but introducing I/O bubbles during decode. Dynamic scheduling strategies [33, 45] (e.g., MoE-APEX [33], Hyb-riMoE [45]) monitor runtime load and adapt expert place-ment at each layer, but they react to the current layer rather than anticipating the next. As Fig. 1 shows, none of these phase-blind approaches escapes the seesaw: on all evaluated models, the on-demand and dynamic schedulers that lead prefill throughput fall behind in decode, while static place-ment shows the opposite. A common limitation underlies this dilemma: scheduling decisions are made solely from current runtime state, without exploiting the inherent predictabil-ity of expert routing. Without lookahead, prefill schedulers cannot distinguish between hot experts that will be needed soon and those that will not, leading to underfetching of critical experts; decode schedulers cannot avoid unnecessary transfers that do not contribute to future tokens, leading to overfetching and I/O bubbles. This myopia prevents existing systems from breaking the seesaw trade-off. In contrast, we observe that the two phases are predictable in complementary ways. In prefill, the parallel processing of many tokens provides sufficient context to accurately predict upcoming expert activations across layers; in decode, per-token generation follows consistent patterns that allow for stable I/O planning. Phase heterogeneity is therefore not a disturbance to be smoothed over, but a schedulable resource: instead of forcing both phases into a single scheduling frame-work, each phase can be modeled, scheduled, and optimized independently at the prediction, scheduling, and execution layers, decomposing the conflicting resource requirements into two separate optimization spaces. We reframe efficient MoE inference as a phase-adaptive scheduling problem: not how to build a fixed execution flow, but how to dynamically configure its optimal operating point for each phase using predicted routing information. This problem is most pronounced in single-batch scenarios on sin-gle CPU-GPU nodes, common in interactive applications like local coding assistants or document processing tools. Here, requests arrive in single or few batches, eliminating inter-request parallelism that could mask resource contention be-tween prefill and decode. Without such parallelism, all phase-agnostic systems face the same dilemma—using a unified scheduling strategy to adapt to two diametrically opposed optimization goals, leading to severe resource contention and pipeline stalls. Optimizing for this worst-case scenario un-locks the potential of local MoE deployment; improvements for low-batch phase conflicts naturally extend to multi-batch settings where phase conflicts are less severe (§5.3). Building on this insight, we present PDScope 1—an in-ference system that treats phase-awareness as a first-class scheduling primitive. Its design includes three key elements that work in concert: 

Phase-aware prediction , PhasePer, formalizes expert activation prediction as a phase-specific ranking problem. Exploiting the layer-group effect (§3.1), it achieves 94% Top-6 accuracy on DeepSeek-V2-Lite [4] and Qwen3-30B-A3B [35], providing reliable lookahead for phase-appropriate prefetch-ing. Phase-adaptive scheduling , AdaptSched, co-optimizes current layer placement and upcoming layer prefetching through cross-layer cost modeling, adopting aggressive poli-cies during prefill and conservative policies during decode. 

Overhead-free execution engine compiles scheduling de-cisions into efficient sequences through static computation graph, cache prefetching, and zero-copy I/O co-design, pre-venting runtime overhead from offsetting phase-aware gains. As shown in Fig. 2, PDScope instead allocates more com-putation to the GPU during prefill and minimizes PCIe over-head during decode, achieving more balanced resource uti-lization than phase-blind schedulers. These gains translate into 2.5–10.3× higher prefill throughput and 2.1–6.1× higher decode throughput than existing systems on mainstream MoE models.

2.2 Disparity between Prefill and Decode 

The resource demand disparity between prefill and decode stems from their fundamentally different token-level paral-lelism. Fig. 3 quantifies this using Mixtral-8x7B on the A100 platform under a CPU-GPU load-balancing scheduler (Hyb-riMoE [45]). Prefill activates 8 experts per layer, with high token-level parallelism saturating the CPU. Processing more tokens on the GPU alleviates this pressure, yet PCIe transfer latency can stall the GPU. Prefill should therefore prioritize hot experts under PCIe constraints. Decode activates only 2 experts per token; with minimal per-expert computation, loading for load balancing risks making PCIe the bottleneck. Decode should therefore minimize unnecessary I/O. These are two fundamentally different objectives. 

2.3 CPU-GPU Inference Related Work 

Existing systems improve MoE inference through two com-plementary techniques: expert prefetching and expert sched-uling. Prefetching transfers experts in advance to overlap computation with I/O [12, 40, 42]. Its effectiveness hinges on predicting next-layer expert activation. Existing methods fall into three categories: statistics-based methods [3, 8, 20, 43] assume frequently activated experts remain frequent; gate-based methods [9, 18, 29, 45] exploit correlations between adjacent-layer gating inputs; token-based methods [6, 11, 36, 39] reuse historical routing decisions for similar token representations. Scheduling decides where to place experts and when to prefetch [28, 31, 32, 37, 38]. Strategies fall into three categories: static placement [2, 10, 16, 23] avoids run-time I/O entirely; on-demand loading [1, 11, 19, 41] keeps experts in CPU memory and loads them only when needed; dynamic scheduling [15, 26, 45] monitors hardware load and dispatches experts to idle devices, though this introduces inspection overhead. While these methods optimize across the spatial dimen-sion (where to place) and the temporal dimension (when to prefetch), they remain agnostic to the phase dimension (prefill vs. decode). Consequently, their unified logic forces a single operating point that statically compromises between

## 3 Challenges and Motivation 

3.1 Expert Prefetching Challenge 

Analysis of Mixtral-8x7B [14] reveals a layer-group effect 2

(Fig. 4), where the distributions of routing weights 𝑤 𝑖 and the similarities of hidden states 𝑎 across layers cluster MoE layers into input, middle, and output groups with distinct sta-tistical characteristics. As a result, no single heuristic works globally: statistics-based methods suffer from suboptimal overall accuracy; token-based methods falter in the middle groups; gate-based methods, while effective in the middle, fail where inter-layer similarity is low. Exploiting expert activation predictability thus requires layer-group aware-ness—yet manual or statistical identification of each group’s properties is challenging. A learnable predictor, using rele-vant variables as input features to capture these associations in a data-driven manner, offers a more viable solution. 

3.2 Expert Scheduling Challenge 

Existing scheduling strategies attempt to handle the pre-fill/decode disparity with unified logic. As shown in Fig. 1, this seesaw effect is stark: static placement excels in decode but fails in prefill; on-demand loading and dynamic sched-uling show the opposite. This section examines dynamic scheduling’s failure mechanism: it adapts via real-time load balancing, appearing to be the most promising approach, yet still falls short due to its layer-by-layer greedy nature. Tak-ing HybriMoE [45] as an example, the scheduler monitors per-layer load and greedily assigns hot experts to idle GPUs and cold experts to idle CPUs, pursuing instant balance. 3.3 Execution Challenge: Overhead Sensitivity 

Scheduling gains are bounded by system overhead. Execut-ing a single expert incurs three non-computational costs: CPU cache loading, PCIe transfer, and GPU kernel launch. These overheads differ between prefill and decode, so they cannot be used indiscriminately as scheduling criteria. In prefill, the CPU is busy, and I/O preparation steps (e.g., pinned memory allocation and DMA setup) compete with computation for CPU resources. Decode faces a different predicament: low token-level par-allelism prevents overhead amortization. ## 4 System Design 

4.1 Overview 

PDScope is a phase-aware inference system for memory-constrained MoE inference. As shown in Fig. 6, its workflow comprises offline profiling and online execution. 

Offline phase. The system profiles the MoE model, col-lecting per-layer traces (hidden states, routing weights, ex-pert IDs) to train PhasePer. It also builds a cost table mapping token count to runtime cost on CPU and GPU, which un-derpins AdaptSched’s global optimization and adapts to the target platform’s bandwidth and compute capability. Hot ex-perts are recorded in a table and preloaded into GPU memory as a static cache to amortize cold-start overhead. 

Online phase. PhasePer provides predictions using phase-specific models. AdaptSched consumes these predictions to co-optimize current-layer placement and upcoming-layer prefetching: aggressive prefetching in prefill sustains GPU throughput; conservative I/O in decode minimizes PCIe bub-bles. Decisions are compiled into a static computation graph that prescribes all operations and data movements, elimi-nating per-expert runtime scheduling decisions. Execution follows this graph: a graph-guided cache prefetcher hides memory latency, while a zero-copy asynchronous I/O engine maximizes PCIe bandwidth via pipelined transfers. This run-time stack directly addresses the phase-sensitive overheads analyzed in §3.3, ensuring scheduling decisions translate to performance without adding runtime overhead that would offset gains.

To match the layer-group effect described in §3.1, PhasePer instantiates a dedicated lightweight predictor for each MoE layer. Predictors for layers in the input and output groups, where activation is skewed and features are noisier, use shal-low networks to prevent overfitting. For the middle group, where inter-layer features are stable, predictors are deeper and include a residual block modulated by a gating unit that takes 𝑎 as input to dynamically calibrate the network.

4.3 Phase-Adaptive Cross-layer Scheduler 4.3.1 Design principle. As shown in Fig. 7, AdaptSched differs from layer-by-layer schedulers by leveraging the pre-dictions of PhasePer for cross-layer visibility 3. This enables it to co-optimize current-layer placement and next-layer prefetching to maximize PCIe utilization. In prefill, it priori-tizes token-heavy experts to maximize tokens processed on the GPU. In decode, it balances on-demand loading, prefetch-ing, and unloading to avoid I/O inefficiencies. Prefetch depth is dynamically calibrated based on predictor confidence to avoid interfering with critical on-demand traffic.

4.4 System-Level Optimization Engine 

The system engine translates AdaptSched’s scheduling de-cisions into performance by co-optimizing computation or-chestration, memory access, and data movement. 

4.4.1 Static graph orchestration and runtime opti-mization. AdaptSched’s decisions are compiled into a static computation graph for each layer through a two-phase strat-egy that decouples scheduling from execution. 

Pre-compilation phase. While the runtime executes layer 𝑙 − 1, the scheduler uses PhasePer’s predictions to pre-compile a draft graph for layer 𝑙 . This draft prescribes placements and prefetches only for experts with high predic-tion confidence—top-ranked (hot) and bottom-ranked (cold) experts in 𝐸 𝑛𝑒𝑥𝑡 —decoupling their execution from runtime scheduling. Recompilation phase. Once the true gating outputs of layer 𝑙 become available, PDScope recompiles the complete static graph, resolving all remaining experts using the full AdaptSched logic. The recompiled graph overwrites decisions from the draft, ensuring that prediction errors never propagate to execution. This pipeline rolls forward: while layer 𝑙 executes, the scheduler pre-compiles a draft for layer 𝑙 +1. Pre-compilation overlaps scheduling and graph construction overhead with computation, while recompilation corrects for prediction uncertainty using ground-truth information. The runtime then executes each static graph asynchronously. The graph further orchestrates two classes of execution optimizations: CPU-side prefetching of predicted expert weights into the last-level cache before computation begins, and GPU-side kernel launch batching that consolidates all resident and prefetched experts into a single coordinated submission be-tween the attention and MoE phases. 4.4.2 Zero-copy asynchronous I/O optimizer. 5.6 Runtime Trace Analysis 

To gain a microscopic understanding of the performance differences, we capture runtime execution traces of a single layer of Qwen3-30B-A3B on A100 with 1024 input tokens and 64 output tokens (Fig. 14). Hot expert preloading is disabled to avoid confounding with runtime prefetching. In prefill, KTransformers executes all expert computation on the CPU, with performance limited by CPU compute capability. HybriMoE, despite its dynamic load-balancing capability to reduce GPU idleness, does not achieve supe-rior performance. In contrast, PDScope’s trace shows higher GPU utilization. Computation gaps are smaller because the static graph eliminates the dynamic scheduler’s polling over-head and AsyncIO improves I/O transfer performance. A higher proportion of experts are also prefetched per layer, reflecting PhasePer’s accurate predictions and AdaptSched’s cross-layer coordination. The "Sort"—which encompasses both scheduling decisions and graph construction—takes 8.1 ms and overlaps with 12 GPU expert computations and 4 CPU expert computations, confirming that these operations can be hidden within the pipeline without adding extra delay. In decode, KTransformers runs efficiently on CPU with optimized kernels and no scheduling overhead. HybriMoE’s second expert transfer does not arrive at the GPU at the ex-pected time, failing to achieve ideal load balancing. PDScope improves system performance through three mechanisms:

(1) PhasePer ensures prefetched experts are used, reducing bandwidth waste; (2) AdaptSched’s decode-phase schedul-ing is more precise, avoiding performance loss from exces-sive I/O; and (3) system optimizations such as kernel launch batching and cache prefetching ensure data readiness before computation begins, reducing computation gaps. These traces validate PDScope’s core claims: phase-adaptive scheduling eliminates greedy underfetching in prefill and ag-gressive I/O in decode; system-level optimizations translate decisions into performance without runtime overhead. 

## 6 Discussion 

This paper targets low-batch inference as the canonical model for studying phase heterogeneity. PDScope does not support the prefill/decode overlap used in distributed inference: on memory-constrained CPU-GPU nodes, prefill bottlenecks shift to CPU and I/O (§2.2)—overlapping decode would only intensify contention. PDScope supports multi-batch phase-consolidated batching (§5.3): AdaptSched reuses the same prefill logic, while decode operates in Mode d, where opera-tions are planned without resource contention. For platform diversity, the offline cost table calibrates op-eration latencies, enabling AdaptSched to adapt to different hardware. The full offline phase takes under 30 minutes per model on A100. AdaptSched is resilient to prediction er-rors: even when PhasePer accuracy drops to 45–70%, prefill throughput decreases by only 6.4–11.3%. Step 2’s layer-local re-evaluation prevents cascading errors by falling back to on-demand loading for mispredicted experts. Detailed analysis is in the Appendix §?? .The hot expert table is derived from the offline phase, a static cache with limited capacity under tight memory. Disabling it in §5.4 has limited impact on performance. 

## 7 Conclusion 

This paper identifies phase heterogeneity—the fundamen-tally different compute and I/O demands of prefill and de-code—as the root cause of inefficiency in MoE inference on memory-constrained CPU-GPU nodes. Existing phase-agnostic systems, regardless of their scheduling strategy, inevitably compromise one phase for the other. PDScope demonstrates that explicitly separating the two phases across prediction, scheduling, and execution layers turns this het-erogeneity from a liability into a schedulable resource. Our evaluation shows that PDScope achieves up to 10.3× prefill and 6.1× decode throughput over state-of-the-art baselines.

8.3 Robustness to Prediction Errors 

Although PhasePer demonstrates strong generalization ca-pability in cross-dataset tests (§5.5), we further evaluate the potential impact of predictor accuracy degradation on AdaptSched’s performance under extreme conditions. For this purpose, we replaced PhasePer with the prediction strat-egy used by Fate, which directly predicts the next layer’s expert activation based on the previous layer’s hidden state passed through the gating module. Tests on an A100 GPU with an input length of 4096 and output length of 64 showed that prefill throughput for the in-put/output layer groups decreased by an average of 6.4%–11.3%, while the middle layer group decreased by only 0.9%–2.4%. Combined with the ablation study results (§5.4), these find-ings demonstrate that even with lower prediction accuracy, AdaptSched’s scheduling performance remains significantly superior to layer-by-layer on-demand scheduling strategies without prediction. This robustness under prediction inac-curacy stems from the interaction between AdaptSched’s design and the statistical properties of expert activation in sparse MoE models. 

Statistical basis of robustness. The fundamental logic can be understood through the relationship between the

random baseline hit rate and the ranking advantage con-ferred by prediction. We use Mixtral-8×7B as an example. Under the (unrealistic) assumption of random expert selec-tion—ignoring all routing preferences—the probability of any given expert being selected for a token is 2 /8 = 25%. This is the random baseline hit rate. 

Why ranking matters more than perfect accuracy. 

For a predictor to deliver systematic prefetching benefits, it does not need perfect accuracy. Instead, it only needs to achieve a hit rate for the true "hot experts" (those that ulti-mately process the most tokens) that is consistently higher than the 25% random baseline. Within a large batch, expert activation can be viewed as multiple independent Bernoulli trials. The value of the predictor lies in generating a rank-ing of expert "hotness" that is more accurate than random. Even with moderate absolute accuracy, if the predictor’s hit rate for the true hot experts exceeds the baseline, those experts are more likely to appear higher in the predicted ranking. Consequently, prefetching I/O operations are sta-tistically more likely to perform "useful work," improving overall throughput. 

System-level safeguard. If a hot expert is not prefetched, AdaptSched’s layer-local re-evaluation mechanism defaults to on-demand loading for that expert, limiting the latency penalty of any single prediction error. This explains AdaptSched’s robustness even with relatively simple predictors. 

Implications for different models. For models with small expert counts and low I/O costs, the direct overhead of prediction errors is low, and this mechanism effectively absorbs inaccuracies. For models like Mixtral-8×7B, where each layer has 8 experts under Top-2 activation, most experts have a considerable probability of being used during long-prompt processing. Thus, even prefetching a non-"hottest" expert can often yield partial performance benefits. 

8.4 Fine-Tuning Dynamics and Error Propagation 

We further analyze two practical aspects that complement the above robustness discussion. 

Error propagation prevention. Even in the rare case of consecutive mispredictions, AdaptSched’s layer-local re-evaluation (Step 2 in Algorithm 1) acts as a safety net. When PhasePer incorrectly predicts the top-𝑘 experts for layer 

𝑙 + 1, the scheduler may prefetch experts that are never used. However, Step 2 re-evaluates the on-demand loading boundary for the current layer 𝑙 based on actual token counts, ignoring prefetched but unused experts. For the affected layer 

𝑙 + 1, the missing experts are fetched on-demand, incurring at most one extra I/O round trip per mispredicted layer. This prevents cascading errors across multiple layers. 

Online fine-tuning trigger frequency and latency hiding. The error threshold over a 16-token sliding window is conservatively low. On all evaluated datasets (ShareGPT, DPO, LLaVA), the average interval between fine-tuning trig-gers exceeds 500 inference steps for prefill and over 1000 steps for decode, because prediction errors are rarely con-secutive. The fine-tuning overhead (2.1 ms per trigger) is entirely overlapped with GPU idle periods that naturally occur during expert I/O transfers. In the decode phase, fine-tuning is scheduled during the attention computation of the next token, again achieving full overlap. Consequently, fine-tuning adds zero observable delay to the critical path.

8.7 The Lookahead Depth of AdaptSched 

A key question for AdaptSched’s cross-layer scheduling is whether looking ahead only one layer (i.e., layers 𝑙 and 𝑙 + 1) sufficiently captures the available optimization potential, or if a longer horizon (e.g., layers 𝑙 , 𝑙 +1, and 𝑙 +2) is necessary. To investigate this, we compared a two-layer lookahead strategy against the default one-layer lookahead. The two-layer strategy faces a practical limitation. If layers 

𝑙 and 𝑙 + 1 are both dominated by hot experts under cross-layer visibility, while layer 𝑙 + 2 is dominated by cold experts, the CPU has insufficient work to remain busy, and PCIe has little idle time to prefetch experts for layer 𝑙 + 2. In this case, the two-layer strategy must still degrade to one-layer looka-head to ensure optimal expert placement for layers 𝑙 and 

𝑙 + 1, rather than leaving the CPU idle across both layers. In practice, the two-layer strategy yields tangible benefits only when layers 𝑙 and 𝑙 + 1 are both dominated by cold experts and layer 𝑙 + 2 by hot experts—a scenario where prefetching for layer 𝑙 + 2 can be effectively overlapped with CPU-bound computation of the preceding two layers. Furthermore, two-layer lookahead requires maintaining prefetch caches for experts across three layers simultaneously, imposing addi-tional memory pressure. Experiments on an A100 GPU with 4096-input and 64-output tokens show that the throughput difference between one- and two-layer lookahead is only 1.1%–2.3% for prefill and 0.8%–5.4% for decode across the four models. These re-sults indicate that in long-context scenarios, one-layer looka-head effectively resolves the core scheduling questions—"whether to prefetch" and "how many to prefetch"—and delivers near-optimal performance.
