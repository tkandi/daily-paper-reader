## 摘要
大规模机器学习（ML）的快速增长使得跨多个GPU的分布式训练成为现代ML系统的基本组成部分。随着模型规模和计算吞吐量的持续增长，通信开销已成为多GPU训练中的主要瓶颈，尤其是当计算与通信顺序执行时。本文探索了使用两种可移植的运行时控制来实现计算与集合通信的并发执行：针对计算内核的共享内存驱动的占用率塑造，以及针对通信内核的提升调度优先级。我们的方法通过逐块的共享内存分配来调节计算内核的驻留，为通信内核的推进留下足够的片上资源。此外，为通信流分配更高的优先级可确保一旦资源可用，通信能够持续进展。在NVIDIA A40、A100、H100和AMD MI250X GPU上的实验表明，所提出的方法能够实现有效的计算-通信重叠，并将总执行时间减少高达25.5%，无需修改供应商库或内核实现。

## Abstract
The rapid growth of large-scale machine learning (ML) has made distributed training across multiple GPUs a fundamental component of modern ML systems. As model sizes and computational throughput continue to increase, communication overhead has become a dominant bottleneck in multi-GPU training, particularly when computation and communication are executed sequentially. This work explores concurrent execution of computation and collective communication using two portable runtime controls: shared-memory-driven occupancy shaping for computation kernels and elevated scheduling priority for communication kernels. Our approach regulates computation-kernel residency through per-block shared-memory allocation, leaving sufficient on-chip resources for communication kernels to make progress. In addition, assigning higher priority to communication streams ensures steady communication progress once resources become available. Experiments on NVIDIA A40, A100, H100, and AMD MI250X GPUs demonstrate that the proposed method enables effective computation-communication overlap and reduces total execution time by up to 25.5 percent, without modifying vendor libraries or kernel implementations.

- **核心瓶颈**：大规模多GPU机器学习训练中，由于模型参数和序列长度剧增，集合通信（如 allreduce、alltoall）的时延占比越来越大，而传统的顺序执行（计算→通信→计算）导致 GPU 资源空转，通信成为主要瓶颈。

- **本文的动机**：在不修改厂商库、内核源码或编译器的情况下，通过纯粹、可移植的运行时控制实现高效的计算‑通信重叠。

### 2. 方法论
本文提出一种**资源感知的计算‑通信重叠**策略，核心由两个互补的运行时控件构成：

- **基于共享内存的计算核占用率塑造**  
  - 针对 GEMM 内核，通过调整分块尺寸（`TILE_M`、`TILE_N`、`TILE_K`）间接控制每线程块申请的共享内存量。  
  - 增大分块会提高算术强度，但也占据更多共享内存，从而降低可并发的线程块数量（即降低占用率）。  
  - 故意限制 GEMM 的驻留块数以留出足够的片上资源（共享内存、寄存器等），使轻量化的通信内核能够与计算内核**共驻同一 SM/CU**。  
  - 这一机制对 NVIDIA 和 AMD GPU 通用（AMD 上对应 LDS 资源），且不改变内核逻辑。

- **通信流的优先级提升**  
  - 利用 `cudaStreamCreateWithPriority` 或 `hipStreamCreateWithPriority`，为通信内核（NCCL/RCCL 集合操作）指定比继代计算内核更高的调度优先级。  
  - 在保证迭代内依赖 (`K_i_g → K_i_c`) 的前提下，显式允许调度器在跨迭代时优先执行上一轮通信，实现 `K_i_c ≻ K_{i+1}_g` 的并发。  
  - 优先级只影响跨迭代之间的并发，不破坏正确性，确保通信一经资源就绪便立即推进，避免被计算内核“饿死”。

- **多流调度基础**  
  - 每个设备分配两个流：**计算流**执行 GEMM，**通信流**执行集合操作。  
  - 通过 CUDA/HIP 事件建立流间依赖：通信内核必须等待其对应的 GEMM 完成，但后续 GEMM 可与之前通信并发。  
  - 这构成基线重叠机制，本文在此基础上叠加优先级调度。

### 6. 主要结论与发现
- **优先级感知重叠可显著减时**：在 NVIDIA 平台上，优化后的总执行时间相比基线最多缩短 **25.5%**（A40 上 cb-ar 场景）。  
- **重叠率大幅提高**：NVIDIA GPU 上优化方案的重叠率可达 **90%**，接近理论上限（受限于迭代内依赖）。  
- **基线重叠的局限性**：仅靠多流并发，低块数时效果好，但块数增加导致资源拥挤，通信被延迟或饿死，重叠退化为近似串行。  
- **架构差异明显**：AMD MI250X 因每个 CU 的共享内存和 L2 容量较小，高块数下优先级优化反而可能略微劣于基线，因为缩减 GEMM 并发损失的计算能力已超过通信加速的收益。  
- **tile 尺寸的影响**：更大的 `TILE_K`（opt2）在内存绑定负载中，通过延长计算段为通信提供更多隐藏窗口，配合优先级可进一步提升效果；在资源极度饱和时，两种 tile 性能趋同。

### 7. 优点
- **高可移植性**：完全不修改 GPU 库（NCCL/RCCL）、内核源码或编译器，仅依赖 CUDA/HIP 的标准 API（流优先级、事件、共享内存分配），易于集成到现有框架。  
- **双机制协同**：同时从资源分配（共享内存占位控制）和调度策略（优先级）两个维度解决并发竞争问题，思路清晰。  
- **跨厂商实证**：在 NVIDIA 三代架构和 AMD CDNA2 上系统评估，提供跨平台可信证据。  
- **分析透彻**：通过重叠率、时间比等多指标，深入揭示了块数、tile 大小、优先级与重叠效益之间的非线性关系，给出可操作的指导原则。

### 8. 不足与局限
- **仅面向单节点**：实验均基于单节点内多 GPU 的集合通信，未考察跨节点网络（如 InfiniBand）下的表现，通用性受限。  
- **负载模拟而非真实训练**：虽源自 Llama 模型统计，但仍是孤立的 GEMM+集合通信微基准，缺少完整训练流程、梯度同步、混合精度、多流并行等实际因素。  
- **tile 搜索空间有限**：仅对比两种 tile 配置，未探索更多 `TILE_M`、`TILE_N` 组合的自动化调优策略。  
- **AMD 平台劣势**：MI250X 上优化空间较小，甚至在高并行度下出现负收益，本文未给出针对该架构的特定改进方案。  
- **粒度固定**：方法依赖于固定的 tile 和大块通信，未考虑更细粒度的算子拆分或分块通信策略，可能错失进一步重叠的机会。
