## 摘要
基于大型语言模型的多智能体系统（LLM-MAS）已成为一种强大的范式，通过将复杂任务分解为由专业LLM驱动的智能体协作工作流来解决。然而，大规模部署此类多智能体工作负载带来了显著的系统挑战。每个用户查询会产生一个迭代的LLM调用流水线，与单轮查询相比，资源消耗大幅增加。在资源受限的云环境中，这些工作流在解码阶段面临不确定且依赖输入的成本、重尾多模型需求导致的内存碎片和过度配置，以及跨集群调度的权衡。我们提出Maestro，一个专为在严格GPU预算下服务LLM-MAS而设计的工作负载感知调度系统。Maestro明确利用智能体的语义和角色：它预测每个阶段的输出长度和内存使用，并基于预测驱动分层调度器。在节点层面，Maestro通过分层权重缓存和弹性内存配置实现动态多模型共置。在集群层面，它执行延迟感知路由以避免冷启动延迟和内存过载。在全局层面，它强制实施工作流感知优先级，以最小化交互式任务的队头阻塞。通过原型实验和基于轨迹的模拟，Maestro将KV预留HBM减少了67.2%，并在高竞争情况下将SLO达成率相比EDF提高了23.6个百分点。

## Abstract
Large Language Model based Multi-Agent Systems (LLM-MAS) have emerged as a powerful paradigm for tackling complex tasks by breaking them into collaborative workflows of specialized LLM-powered agents. However, deploying such multi-agent workloads at scale poses significant system challenges. Each user query spawns an iterative pipeline of LLM calls, greatly amplifying resource consumption compared to single-turn queries. In resource-constrained cloud settings, these workflows face non-deterministic and input-dependent costs at decode stage, heavy-tailed multi-model requirements with memory fragmentation and over-provisioning, and cross-cluster scheduling trade-offs. We present Maestro, a workload-aware scheduling system designed for LLM-MAS serving under strict GPU budgets. Maestro explicitly leverages agent semantics and roles: it predicts the output length and memory usage of each stage and uses this prediction to drive a hierarchical scheduler. At the node level, Maestro enables dynamic multi-model co-location via hierarchical weight caching and elastic memory provisioning. At the cluster level, it performs latency-aware routing to avoid cold-start delays and memory overloads. At the global level, it enforces workflow-aware prioritization to minimize head-of-line blocking for interactive tasks. Across prototype experiments and trace-driven simulations, Maestro reduces KV-reservation HBM by 67.2% and improves high-contention SLO attainment over EDF by 23.6 percentage points.

### 1. 核心问题与研究背景

- **研究动机**：基于大型语言模型的多智能体系统（LLM‑MAS）将复杂任务分解为由多个专业智能体协作完成的流水线，但大规模部署时面临严峻的资源与调度挑战。
- **核心矛盾**：在资源受限的私有或本地集群中，GPU 容量有限且碎片化，每个用户查询会触发一连串依赖的 LLM 调用，资源消耗被急剧放大。
- **三大具体挑战**：
  - **非确定性、依赖输入的执行成本**：解码阶段的输出长度和时延高度依赖智能体角色、工具调用和推理策略（如 Chain‑of‑Thought），难以事前准确估计，导致队头阻塞。
  - **长尾多模型需求与内存竞争**：少数模型被频繁调用，多数模型调用稀疏；为每个模型固定分配 GPU 造成浪费，按需加载又引入秒级冷启动延迟，而多模型共置则加剧 GPU KV 缓存的内存压力。
  - **跨集群路由的权衡**：最近集群网络时延低，但可能缺少已加载的模型权重或充足内存；迁往远地集群虽然模型就绪，但往返时延高，影响首 token 延迟和流水线整体时间。

- **现有方案不足**：已有的预测感知调度器（如 FastServe）、多模型共置（MuxServe、QLM）和跨集群框架（SkyServe、AIBrix）主要面向独立单轮查询，忽略智能体工作流的阶段依赖和角色差异，未能将低开销的阶段级成本估计与跨集群分配相结合。

### 6. 主要结论与发现

- Maestro 在严格 GPU 预算下有效优化了 LLM‑MAS 服务：通过工作负载感知的分层调度，KV 缓存预留的 HBM 使用量减少了 **67.2%**。
- 在高竞争（高负载、高批量比）条件下，SLO 达成率比 EDF 提高 **23.6 个百分点**（从 50.0% 升至 73.6%），交互排队时延降低 **84.8%**。
- 两阶段预测（工具意图 + 输出长度回归）的 MAE 降至 165.43 tokens，比 Magnus 低 19.2%，R² 达 0.7774；语义特征和工具调用意图分类对非 CoT 模式尤为关键。
- 多模型共置使 1 个 GPU 就能以可接受的性能降级运行原本需 3 个 GPU 的工作流（旅行助理完成时间增加 12.1%，但 GPU 成本减少 66.7%）；在 5 模型共置时实现 205% 的内存超额使用，有效缓解长尾模型的资源闲置问题。
- 跨集群调度中，结合 KV 装箱和延迟感知的亲和评分比简单负载均衡降低超过 58% 的交互排队时延，并缓解冷启动影响。

### 7. 优点与亮点

- **系统视角创新**：首次将智能体语义、工作流依赖、多模型长尾需求和跨集群就绪状态统一纳入调度决策，使调度器不仅感知请求负载，更理解工作流“内容”。
- **分层设计有机整合**：在节点、集群和全局三个层次上，通过预测驱动的内存管理、路由评分和 SRTF 抢占形成一个闭环反馈系统，各部分信号（内存头空间、退化代价、模型就绪状态）相互衔接。
- **预测精细且轻量**：两阶段的工具意图分类和长度回归捕捉到智能体输出的双模态分布，并使用校准概率指导回归，同时保持较低的在线推理延迟（P50 约 11 ms）。
- **内存超配实用化**：通过显式内存记账和安全边际，在 5 模型共置下实现 3 倍以上的虚拟 KV 预算，且通过弹性 VMM 和分级回收机制降低风险，减少 GPU 浪费。
- **实验全面**：既包括物理集群原型，也包含大规模轨迹驱动模拟，覆盖多种负载、基线比较和组件消融，验证了调度框架在实际系统中的收益。

### 8. 不足与局限

- **预测模型泛化性**：工具调用预测和长度回归虽然精度有所提升，但训练依赖于特定智能体角色和工作流模式；对于未见过的工具集或新类型的智能体交互，其性能可能退化。
- **抢占粒度保守**：仅支持在 LLM 调用边界（阶段间）抢占，不进行 token 级或迭代级抢占。对于特别长的解码阶段，队头阻塞仍可能发生，只是系统设计有意回避了更深的引擎集成。
- **外部工具执行没有联合调度**：虽然工具执行时延记录在剖析中，但当前系统并不在 CPU/网络资源层面对工具调用进行调度，可能影响端到端的延迟优化，在重度工具依赖的系统中尤为明显。
- **实验环境单一**：所有物理实验均基于同构的 A100 节点和两个服务等级；对于异构加速器、多租户生产环境下的公平性和隔离性未做评估，对更大规模集群（例如数百节点）的可扩展性也缺乏分析。
- **训练成本与预测更新策略不明**：论文未说明预测模型在线更新、冷启动时的默认行为或在大规模数据重训练下的开销，可能存在概念漂移时鲁棒性不足的风险。
- **缺乏与更先进基线的对比**：调度基线主要选择经典算法，没有与近年先进的预测驱动调度器（如 A‑SRPT）或更细粒度的多模型管理器（如 MuxServe）直接对比，弱化了性能优势的说服力。
