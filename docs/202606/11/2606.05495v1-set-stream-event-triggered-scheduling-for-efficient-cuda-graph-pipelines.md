## 摘要
实现GPU峰值性能仍是一大挑战，系统吞吐量受限于主机-设备同步延迟和内核调度开销，即使采用激进的内核优化和批量处理也是如此。此外，现有方法常因调度开销而未能充分利用计算核心和拷贝引擎等硬件资源。为解决这些问题，我们提出了一种用于任务并行管线的CUDA运行时框架，以最小化同步开销和内核执行间隙。该方案结合了两项创新：（1）一种多流任务并行管线编程模型，利用事件链和工作窃取机制充分利用可用硬件资源；（2）一种基于图的执行流程，结合每流缓冲区，确保多个并发运行作业的内存安全。在典型真实工作负载上的大量评估显示，与最先进的CUDA图基线相比，其加速比为1.15至1.44倍，并将调度开销降低18%至54%。

## Abstract
Achieving peak GPU performance remains a significant challenge as the system throughput is constrained by host-device synchronization delays and kernel scheduling overheads, even with aggressive kernel optimizations and batch processing. Furthermore, existing approaches often underutilize hardware resources such as compute cores and copy engines due to scheduling overheads. To address these problems, we propose a CUDA runtime framework for task-parallel pipelines to minimize the synchronization overheads and the gap between kernel executions. The proposed solution combines two innovations: (1) a multi-stream task-parallel pipeline programming model that leverages event-chaining and work-stealing mechanisms to fully utilize available hardware resources; (2) a graph-based execution flow with per-stream buffers to ensure memory safety for multiple in-flight jobs running concurrently. Extensive evaluations on representative real-world workloads show 1.15--1.44X speedup and reduce scheduling overheads by 18--54% compared to state-of-the-art CUDA graph baselines.

### **2. 论文提出的方法论：核心思想、关键技术细节、流程**

SET框架的核心思想是**将每个任务封装为可复用的CUDA Graph可执行体**，并利用事件驱动的回调机制，实现主机与设备任务的**协同调度**。这摒弃了传统粗粒度的批次级同步或全局轮询。

**关键技术细节与组件：**

*   **任务封装（Job-as-Graph）**：将每个计算任务抽象为有向无环图（DAG），表示内核间的依赖关系。任务所需的内存拷贝（Memcpy）和内核参数均在图构建时预设，对于动态变化的参数，则使用占位符（placeholders），以便在运行时高效更新。
*   **内存安全与工作窃取**：系统为每个worker预分配专用的设备端缓冲区（`Mi`）。CUDA Graph可执行体（`Gi`）严格绑定在其专属缓冲区上。当发生工作窃取时，系统会进行**即时（Just-In-Time, JIT）参数更新**，将被窃取的可执行体重定向到窃取者的内存空间，从而在无新设备分配的情况下保证了内存安全。
*   **事件链协同调度**：这是SET的核心机制。调度流程由四个组件实现：
    1.  **Workers**：`b`个Worker，每个封装一个独立的CUDA流、一个预实例化的CUDA Graph可执行体和一套专用缓冲区。
    2.  **每Worker任务队列（`Qi`）**：主机侧线程安全的队列，存储的是已经完全准备好参数的可执行体，而非简单任务索引，以降低后续启动开销。
    3.  **空闲Worker池（`Wpool`）**：一个线程安全的队列，维护当前空闲的Worker索引。仅在任务完成时更新，避免了轮询开销。
    4.  **提交者（Submitter）与调度器（Dispatcher）**：两个独立的主机线程。
        *   **提交者**：作为“生产者”，持续监视所有任务队列的槽位，一旦有空闲，就更新图的参数并将任务入队。
        *   **调度器**：作为“消费者”，持续监视空闲Worker池。一旦有Worker空闲，调度器首先尝试从其专属队列获取任务；若队列为空，则通过**工作窃取**从其他Worker的队列中获取任务。
        *   **异步资源回收**：每次任务启动后，调度器会在该Worker的CUDA流末尾附加一个**回调事件**。一旦设备执行完所有操作，该事件会在独立线程上触发，自动将该Worker的索引放回空闲池，实现了 `O(1)` 的同步开销和即时的资源回收。

**流程总结**：SET通过 任务注入 (入队) -> Worker状态监控 (空闲通知) -> 任务分派 (本地获取或工作窃取并JIT更新) -> 异步完成 (回调回收) 的闭环，实现了对GPU管线的细粒度、低延迟调度。
